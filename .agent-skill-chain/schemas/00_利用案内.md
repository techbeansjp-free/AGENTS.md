# schema利用案内

## 目的

このdirectoryはpackage入力の形、必須field、未知fieldの扱いを機械判定する契約を置く。文章による説明をschemaの代替にしない。

## ownerと編集

packageが所有する。schema変更は対応するpolicy、runtime、migration、反例test、version契約と同じ変更単位で行う。利用projectはschemaを改変せず、schemaに適合する入力を所有する。

## 使い方

| schema | 検証対象 |
|---|---|
| [project-policy-manifest.schema.json](project-policy-manifest.schema.json) | `.agent-skill-chain/project-policy.json`とfragment inventory。`policy.worktree.finalizeIgnoredPathAllowlist`はfinalize時に削除可能なignore対象のproject追加分を、安全なdirectory prefixだけに制限する |
| [project-choice.schema.json](project-choice.schema.json) | `project/choices/`の選択値 |
| [project-rule.schema.json](project-rule.schema.json) | `project/rules/`のrisk比例rule |
| [project-conformance-binding.schema.json](project-conformance-binding.schema.json) | `project/conformance/`の証拠binding |

| [workflow-mode-decision.schema.json](workflow-mode-decision.schema.json) | Step 0のモード判定、Q-01〜Q-08の回答・根拠、PoC宣言 |

fragmentを追加するときはmanifestへ列挙し、対応する個別schemaと組立後policyの両方を検証する。schemaだけを読んで運用手順を推測せず、[運用ポリシー](../docs/00_運用ポリシー.md)も確認する。

finalize ignore allowlistのpackage既定値はruntimeの`DEFAULT_FINALIZE_IGNORED_PATH_ALLOWLIST`が所有し、schema fieldは利用projectの追加分だけを受け付ける。schemaのpatternとruntime validatorはともに絶対path、親参照、`.`、`.git`、Unicode制御文字、非NFC、backslash、glob・正規表現meta文字を拒否し、未知field拒否と同じ変更単位で保守する。

## 置かないもの

projectの選択値、実際のrule、証拠、秘密情報を置かない。説明都合で必須fieldや未知field拒否を弱めない。

## 正本

入力構造は各schema自身、現行・互換versionは`package.json`、意味上の不変条件はpackage conformance catalogとruntimeを正本とする。

## project ruleの廃止

利用projectのpolicy ownerは、既定branchのmanifest `policy.projectRuleRetirementProposals`へproject rule廃止提案を先行登録する。最大16件で、各項目は次の形を持つ。

```json
{
  "ruleId": "ASC-OLD-001",
  "beforeSha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "reason": "利用しなくなったruleを廃止する",
  "owner": "project policy owner"
}
```

`ruleId`は対象ruleのID、`beforeSha256`はそのtrusted fragment fileのraw UTF-8 SHA-256を小文字64hexで指定する。例のhashは置換する。`reason`と`owner`は制御文字のない非空文字列とし、秘密を記入しない。owner文字列は認証の根拠にならず、既定branchの保護と変更authorityを維持する。

1. 既定branchの最新commitを固定し、対象fragmentのraw UTF-8を取得する。`git show <trusted-commit>:.agent-skill-chain/project/rules/old.json > /tmp/asc-retirement-before.json`で取り出し、`sha256sum /tmp/asc-retirement-before.json`の値を使う。JSON整形、改行、Unicodeの正規化をしない。
2. rule本体を残した登録PRで、manifestの`policy.projectRuleRetirementProposals`配列へ提案を加え、ownerのreviewを経て既定branchへ反映する。
3. 後続PRで指定ruleのfragmentとmanifest `ruleFiles`参照を両方削除する。trusted側のIDとraw SHAがexact一致する完全削除だけを受理する。候補側だけの提案、hash不一致、source欠落、部分弱化、未承認ruleの便乗削除は拒否する。複数削除は全ruleに個別の提案が必要である。
4. `policy validate`または`policy migrate`の比較結果で`acceptedRetirements`のrule ID・fragment path・提案SHA・観測SHAを確認する。`policy evaluate`等、fragment sourceを持たないlegacy monolith経路では削除を受理しない。最後のruleを廃止した`ruleFiles: []`とassembled `rules: []`は有効なproject extensionであり、package safety floorとoperationのrule存在検証は残る。

提案は自動消費しない。撤回はownerが別PRで該当提案を削除する。未適用の削除は撤回後に再び拒否される。trusted fragmentを変更した場合はhashを再計測し、更新提案を先に反映する。

rollbackでは削除PRを戻し、fragmentとmanifest参照を同時に復元する。既定branchで既に廃止済みのIDを再導入する場合は新規ruleのstaged契約を守る。廃止提案は別変更で撤回する。機構そのもののrollbackは実装変更をrevertして従来の全削除拒否へ戻す。

## project choiceの縮小を承認する

`projectChoices.testLayers`、`projectChoices.forbiddenTestFileSuffixes`、`projectChoices.quality.forbiddenTypes`の3 fieldは単調性契約を持ち、要素を減らす変更は`ASC-TRUST-001`で拒否される。採用していない値を誤って宣言した場合は、既定branchのproject policyへ`projectChoiceShrinkProposals`を登録する**二段階**の手順で取り除く。

1. **既定branchへ提案を登録するPR。** `.agent-skill-chain/project-policy.json`の`policy`へ次を足す。`afterSha256`は、縮小を適用した後のchoices fragment fileの内容をUTF-8のbyte列としてSHA-256でhashした値である。

```json
"projectChoiceShrinkProposals": [
  {
    "fieldPath": "projectChoices.forbiddenTestFileSuffixes",
    "afterSha256": "<縮小後のchoices fragment fileのsha256>",
    "reason": "この禁止をproject要件として採用していない",
    "owner": "利用側project owner"
  }
]
```

2. **縮小を適用するPR。** choices fragment fileを縮小する。**登録済み提案の`afterSha256`とfileのraw byteのsha256が完全に一致する場合だけ**受理される。整形の差1 byteでも一致しない。

**候補branch側へ登録した提案は受理判断に使えない。** 提案は既定branch側のpolicyからのみ読む。同一PRで提案を登録して同時に適用することはできない。

**提案に無い縮小、および対象3 field以外の縮小は従来どおり拒否される。** 単調性の検知そのものは変わらない。
