# ステップ2: 要件定義

入力は`full`モードの要求。成果物はユーザーストーリー、ユビキタス言語、ドメインモデル・不変条件、機能・非機能要件、受け入れ条件、Gherkin IDを含む`01_要件定義.md`。要件を観測可能にし、権限境界を明示する。`poc`ではこのStepを独立実行せず00へquick相当で集約し、正式開発へ移す場合は昇格根拠と不足成果物を列挙して`full`へ単調昇格してから実行する。ステップ3へ合成する。

## テンプレート契約

作業開始前に[成果物用語と責務境界](../../docs/01_開発ワークフロー.md#成果物用語と責務境界)を全文読み、要求を増減せず、要件と受け入れ条件を分離して追跡する。

[ドメイン用語台帳](../../docs/01_開発ワークフロー.md#ドメイン用語台帳)と既存の耐久用語台帳を作業開始前に全文読む。00の候補語を要求・business rule・一次資料へ対応付け、用語ID、コンテキスト、成立例・反例、owner、状態を確定する。曖昧な全体共通語を作らない。

作業開始前に[01_要件定義.md](../../templates/issue/01_要件定義.md)を全文読み、その見出し構造と必須欄を使ってステージング内の`01_要件定義.md`を作る。独自構成で再作成せず、該当しない欄は理由付きで扱う。

project choicesを読み、作業開始前に[セキュリティ方針・資産](../../templates/specs/10_セキュリティ/00_セキュリティ方針・資産.md)、[非機能要件一覧](../../templates/specs/11_非機能/00_非機能要件一覧.md)、[運用設計](../../templates/specs/12_運用保守/00_運用設計.md)を全文読む。UIまたはtoken capabilityが`not-applicable`でない場合は[デザイントークン](../../templates/specs/17_デザイン/00_デザイントークン.md)と[レイアウトトークン](../../templates/specs/18_レイアウト/00_レイアウトトークン.md)も全文読み、DC行をNFR・ACへ追跡する。
