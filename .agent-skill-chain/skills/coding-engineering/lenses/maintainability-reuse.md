# 保守性・再利用のLens

## 適用条件

共通化、shared部品、refactor、新しいabstractionを検討するとき。

## 判断する問い

- 必要な範囲で既存実装を検索したか。
- 似たcodeは同じ意味を持つか。
- 同じ理由で変更されるか。
- 共有する境界は十分安定しているか。
- 抽象化が実際に理解・変更・testを容易にするか。

## 代表的な失敗

2箇所の類似だけで共通化、文字列重複をDRY違反扱い、将来用framework、scope外refactor。

## scope内の修正

意味が異なれば分離し、変更理由が異なれば共有しない。境界が未成熟なら今は重複を許容する。適合する既存validatorやhelperを再利用する。

## 既存手続きへの接続

要求・scope・外部contract変更が必要ならStep 9の既存処理へ渡す。

## 通常は助言に留めること

file行数・method数・小file数は品質の判定値にしない。namingや小さな構造変更は自律判断する。
