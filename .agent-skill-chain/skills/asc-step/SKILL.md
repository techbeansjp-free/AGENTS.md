# agent-skill-chain Step選択

1. 新規の通常開発指示では、まず`agent-skill-chain doctor`でこのadapterのhash一致と`workflowReadiness`を確認し、[開発ワークフロー正本](../../../.agent-skill-chain/docs/01_開発ワークフロー.md)の「標準入口」「モード判定質問」を必要な節だけ読む。一次Intent、既存の正しさの基準、変更予定path、Q-01〜Q-08、14領域のリスクと未解決事項をread-onlyで確認し、専用Git worktreeを用意して`workflow candidate`の`phase:preflight`へ渡す。`route=candidate`かつQ-01〜Q-08がすべて根拠付きで真なら同じ事前入力に`workerProvider:codex`、既存の対象テストargv、`gaps`を加えた`phase:execute`を標準経路として1回実行する。`route=clarify`なら未確定の正しさの基準だけを明確にし、`route=upstream`またはquick失格なら必要な上流判断を先に行う。unknownを推測でclearedにせず、隔離・Provider・対象テストが使えない場合もCandidateを強行しない。結果の`authority:none`と対象テストを正式Evidenceに読み替えず、Git差分、独立review、封印済みstaging、`candidate-adopt`、trusted verification、Step 10、Deliveryを既存gateで進める。同一HEADで収束したreview sessionはStep 10で再利用し、変更や未解決事項があれば再検分する。続く正式Step 0では「モード」「モード判定質問」「ステップ0〜11」を必要な節だけ参照し、同じcontextで既読の節は再読せず、modeと開始Stepを確定する。正本の他の節は、選択したStep skillが節linkで参照したときにその節だけ読む。正本を全文読まない。 `doctor`は結果を保持して必要欄を読み、出力の前半・後半を見るために再実行しない。同じcontextで同じworktree・設定・trusted policyについて成功観測がある間は、manifest全文の再読や追加の`policy validate`を開始時の固定作業にしない。拒否理由、設定変更、観測との矛盾があれば該当箇所を再確認する。
2. Step 1以降のshort-lived（未設定時の既定）は、直前の`workflow advance --apply --prepare-next`が返した`preparation.executionPlan`を次の入口に使う。なければ`agent-skill-chain workflow advance --staging=<staging path> --plan`を実行する。`action`の証明責務・正式入力参照・未確認事項・終了条件を確認し、`executor=fresh-worker`なら`agentDispatch`をAgent toolへそのまま渡す。`executor=cli`は指定されたpreview・既存authority・gateを満たすCLI操作を行い、workerを起動しない。worker返却後の記録と収束後処理は`action.coordinatorCompletion`をcoordinatorが実行し、workerの許容操作へ混ぜない。`none`または`state=blocked`なら停止する。`--apply --prepare-next`は対象1工程だけを記録して次の契約を返し、次semantic工程へ同じworkerで進まない。compatibleは従来の`--apply`なしpreviewと`targetStep`を使う。再開は同じ出力の`resume`（再開状態）を起点に、そこが指すpath・SHA・digestから始める。契約・`resume`はadvisoryであり、gateの照合を置き換えない。**journal/steps.jsonlを自分で解析しない。** 旧journalの再確定除外とquick→full昇格のStep 0/1特例はCLIが持つ。mode選択やワークフロー正本を再読しない。
   `prompt`は文字列化済みなので手組みせず、再reviewは`alternatives[].agentDispatch`（旧previewは`agentDispatchAlternatives`）を使う。通常の単発調査は自然言語のAgentで並走できるが、ASC工程担当を通常taskへ格下げしない。起動拒否の理由を修正して再委譲し、mainが実装・是正を代行しない。復旧不能なら理由を利用者へ返す。
   Worker待機中は短間隔の空poll、同じlog・成果物の再読、完了推測のための重複CLI実行をしない。hostの待機操作は1回につき利用者への進捗更新間隔（おおむね60秒）まで待ち、通知または期限到達時だけ状態を確認する。待機中に別の調査を始めて親contextへtool結果を積み増さない。Worker返却後は`workUnitId`とHEADを観測し、必要な正式記録へ進む。待機指示は品質gateや異常終了の検出を省略しない。
   低リスクquickでは、Candidateが返した一次Intent・正しさの基準・base/HEAD・変更path・対象テストと、既存仕様・Step 0のQ根拠だけで00の目的・AC・不変条件・設計適用・検証計画を具体化できる場合、現在のcoordinatorが生成済み00の必要欄を一度だけ完成させる。その後`workflow advance --plan`を1回実行し、detached Candidate結果worktreeの出自とclean状態をCLIが再観測し、`executor=cli`が選ばれたときだけ正式Step 1を既存gateで記録する。意味的な不足、矛盾、unknown、または検証不合格なら`executor=fresh-worker`のWork Unitへ委譲し、穴埋めした文書を有効なEvidenceとして扱わない。coordinatorによる00の記入も判断であり、Git・trusted検証・Planning Seal・独立reviewの代わりにはならない。実装前に知るべき危険変更はCandidate事前判定で止める。
   Candidate実行後は返却された`candidateWorktree`と`headSha`を次の作業の参照点に固定する。正式stagingの作成、独立reviewの`review round --init`、`candidate-adopt`、trusted検証は、そのdetached結果worktreeとそこに置いたstagingを使う。元worktreeで作ったstagingを後から手動移動したり、候補commitを元branchへ先にmergeしたりしない。必要なASC配布資産は既存の正式install/update経路で結果worktreeへ用意する。準備後に返却`headSha`とのexact HEAD一致と追跡・未追跡fileのclean状態を再観測する。準備が候補差分や封印済みstagingを変えた場合は採用・review・検証を止め、Candidate、Planning Seal、review、trusted検証の該当gateで更新をやり直す。`candidate-adopt`のpreviewを1回行い、拒否時はdiagnosticの対象だけを直す。結果worktreeのHEAD・staging・依存物を推測で再構成しない。
3. fresh workerは同じworktreeの`--plan`（alternativesを含む）でhandoffのHEAD・boundary・workUnitIdを照合し、`read.skill`の実fileへ直接進む。同じ状態の`--plan`を出力の先頭・後半に分けるために再実行しない。出力が長い場合は一度取得した結果から担当候補と`action`を選んで読む。終了時のHEAD・gate再観測は別目的なので省かない。`read.staging`はstaging相対の正式成果物pointerであり、必要節だけを読む。目的・AC・不変条件と担当する証明責務を判断し、機械観測・独立review・人間/policy authorityを自己申告で代替しない。完了済み上流判断を再推論せず、CLIの拒否・記録との矛盾・未知依存など新しい影響がある場合に上流参照を広げる。gateと独立reviewは省略しない。
4. `read.skill`がない旧handoffまたは通常contextでは、特定したStepの`.agent-skill-chain/skills/step-NN-*/SKILL.md`の実fileを読む。Step skillの読む範囲は開発ワークフロー正本の「読取と書込の量」節に従う。どのStep skillが存在するかは[Step skill利用案内](../../../.agent-skill-chain/skills/00_利用案内.md)から辿れる。この案内は索引であってStepの選択根拠にしない。
5. 選択したStep skill内の相対linkは、そのStep skillの実directoryを基点に解決する。このadapterのdirectoryを基点にしない。
6. Step契約と、そこから参照される正本・templateに従って作業する。読む量と書く量は開発ワークフロー正本の「読取と書込の量」節に従う。

host設定は既存のinstall/update lifecycleが管理する。preview後に`--apply`すればASC登録とtrusted runtimeが揃う。利用者へenv・hookの手動編集を要求しない。doctorはpostconditionを診断する。既存sessionのmodeは保持するため、更新後は新規sessionで確認する。

このadapterはhostから正本への登録口であり、Stepの順序・実行契約・成果物書式を複製しない。内容が食い違う場合は開発ワークフローと各Step skillを優先する。

`workflowReadiness.ready=false`は導入健全性とは別の配送前提不足である。欠落したverificationは利用projectの実検証commandをownerが確認して既定branchへ先行導入する。未対応のPR ruleは実観測adapterまたはpolicyの適用境界を是正する。検証宣言・rule種別を推測で書き換えず、`gh pr create`への自動迂回や`04_レビュー.md`による正式証跡の代替をしない。ユーザーがASC工程を省略した場合も、実施していない検証・承認を実施済みとして記録しない。
