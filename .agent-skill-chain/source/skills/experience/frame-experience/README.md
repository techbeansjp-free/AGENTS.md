# capability: frame-experience

**目的**: UI/UX を伴う機能について、ビジネス目的・成功基準（KPI）とユーザー・課題（誰の何の課題か・JTBD・仮説）を一人称ナラティブ＋却下案で枠づけ、02_設計.md §7.1 に記録する（体験設計フェーズ1）。

---

## 手順

1. 00_要求定義.md の `experience_surface` を確認する。値がある場合は §7.0 へ転記し、体験サーフェス定義（人間が感覚器で直接体験する出力があるか。画面に限らず CLI 出力・エラー・生成 Markdown・エージェント指示文を含む）に照らして検証する。定型理由が実態と矛盾する場合は「あり」へ倒し進行役へ差し戻す。値が無い場合はこの capability が判定し、判定結果（あり/なし＋理由 1 行）を §7.0 に記録する。
2. 判定が「なし」ならここで完了とする（後続の map-experience / detail-experience はスキップ）。
3. 判定が「あり」の場合、ビジネス目的・成功基準（KPI）を一人称ナラティブで記述する（「この機能が無ければ誰がどう困るか」を実在の一人を挙げられる粒度で書く）。
4. ユーザー・課題（ペルソナ・JTBD・仮説）を確認する（「このユーザーが最初の 5 秒で知りたいことは何か」「これはユーザーがやりたいことか、我々が作れることか」を問う）。
5. 却下案（採らなかったターゲット/目的仮説）を 1 件以上記述する。
6. 幻覚ペルソナ注意（LLM が捏造したユーザー像は実ユーザー調査の代替にならない旨）を明記する。
7. 02_設計.md §7.1 に前提ナラティブ・ペルソナ・JTBD・却下案・幻覚ペルソナ注意を記録する。

---

## 制約・禁止

- チェックボックスの列挙のみ（ナラティブ無し）で済ませない。
- 幻覚ペルソナを実ユーザー調査の代替として扱わない。
- IA・ユーザーフロー・UI 具体化に踏み込まない（map-experience / detail-experience の責務）。
- **00_要求定義.md・01_要件定義.md の目的・成功基準・ユーザーストーリーを再定義・重複執筆しない**。frame-experience は 00/01 を入力として「体験の前提」へ翻訳する役であり、要求定義の二重工数を生まない。00/01 との矛盾を発見した場合は自ら 00/01 を直さず進行役へ差し戻す（00/01 の修正は requirement-discovery 側の責務）。

---

## 成果物の形式

- **OUT**: 02_設計.md §7.0（体験サーフェス判定結果）・§7.1（前提ナラティブ・ペルソナ・JTBD・却下案・幻覚ペルソナ注意）。
- 「あり」判定時の §7.1 出力は次フェーズ map-experience の入力となる。
