# capability: detail-experience

**目的**: map-experience（フェーズ2）の流れの上で、UI・デザインシステム適用・アクセシビリティ・実装可能性を具体化し、既存デザイン資産の再利用を新規作成より優先して探索した上で、責務・API 候補を 02_設計.md §7.3 に記録し define-boundaries へ引き渡す（体験設計フェーズ3）。

---

## 手順

1. §7.2（map-experience の出力）を読み、体験の流れ（IA・ユーザーフロー・ジャーニー）を確認する。
2. UI/ビジュアル・視線誘導を検討する（観点シード:「視線誘導・操作容易性・アクセシビリティを満たすか。『格好いいが操作しづらい』案を却下したか」）。
3. **既存デザイン資産の再利用を優先順位で探索する（新規作成の前に必ず実施）**:
   1. 既存の**ページテンプレート相当**
   2. 既存の**パターン／セクション相当**
   3. 既存の**コンポーネント相当**
   4. 既存の**レイアウト相当**の組み合わせ
   5. 既存の**プリミティブ相当**
   6. それでも不足する場合のみ**新規作成**
4. デザインシステムの適用・一貫性を確認する（基礎値＝トークン相当を自由に増やさない／レイアウトを個別成果物に直接埋め込まない）。
5. アクセシビリティ（コントラスト・キーボード操作・代替テキスト等）を確認する。
6. 実装可能性・検証改善観点（体験を成立させる実装制約との矛盾の有無、どう計測・改善するか）を確認する。
7. 新規 UI 要素を作る場合は、**新規作成が正当化される条件**（すべて満たすことが望ましい）を §7.3 へ明記する: 複数箇所での再利用が見込まれる／責務が明確／既存の組み合わせで表現できない／バリアントが明示されている／アクセシビリティ要件が文書化されている／レスポンシブ挙動が文書化されている。
8. 却下案（ビジュアル洗練度優先で操作性を損なう案）を 1 件以上記述する。
9. 責務・API 候補（体験から逆算した種）を抽出し、define-boundaries へ引き渡す形で記録する。
10. 02_設計.md §7.3 に UI 具体化・**探索した既存資産の一覧**（どの層で何を探索し、再利用可否と理由）・再利用結果／新規作成の正当化根拠・アクセシビリティ・却下案・責務/API 候補を記録する。既存デザイン資産が無いプロジェクトでは「既存資産なし」と 1 行明記する。

---

## 既存資産の再利用探索順序（新規作成の前に必ず実施・ADR-8）

新規 UI 要素をいきなり作らず、次の順序で既存資産を探索する。

①既存のページテンプレート相当 → ②既存のパターン/セクション相当 → ③既存のコンポーネント相当 → ④既存のレイアウト相当の組み合わせ → ⑤既存のプリミティブ相当 → ⑥それでも不足する場合のみ新規作成

**探索一覧の提示義務**: 「探索した」という一言では Done を満たさない。§7.3 へ、どの層で何を探索し、再利用可否と理由を列挙する（検証可能な成果物形式）。既存デザイン資産が無いプロジェクトでは「既存資産なし」と 1 行明記する。

## 新規作成が正当化される条件

新規 UI 要素を作る場合、次をすべて満たすことが望ましく、§7.3 に明記する。

- 複数箇所での再利用が見込まれる
- 責務が明確
- 既存の組み合わせで表現できない
- バリアントが明示されている
- アクセシビリティ要件が文書化されている
- レスポンシブ挙動が文書化されている

## 4 原則（detail-experience の判断基準）

1. 基礎値（トークン相当）を自由に増やさない
2. レイアウトを個別成果物に直接埋め込まない
3. 既存資産を先に探索する
4. 新規作成条件を明文化する

## 技術非依存（特定フレームワーク・ディレクトリ構成を固定しない）

消費者プロジェクトが独自の階層・デザインシステム命名（Atoms/Molecules や Tokens/Primitives/Components/Layouts/Patterns/Templates/Pages 等）を持つ場合は**それを最優先で使う**。持たない場合のみ、一般化した多層構造（基礎値 → 最小部品 → 複合部品 → レイアウト → パターン → 個別成果物）を参考情報として使ってよい。**本 capability は特定フレームワーク（React/Figma 等）・特定ディレクトリ構成・特定の階層名を強制しない**。

---

## 制約・禁止

- 判断基準優先順位（skills/experience/README.md）を無視し「ビジュアルの洗練度」を上位に置かない。
- 既存資産の探索を省略し、安易に新規 UI 要素・新規トークン・ページ直書きレイアウトを増やさない。
- 幻覚ペルソナを実ユーザー調査の代替として扱わない。
- UI モックの作画（本フレームワークの除外要件）は行わない。
- architecture の責務境界を確定しない（define-boundaries の責務）。
- 特定技術スタック（React/Figma 等）や特定ディレクトリ構成を前提として固定しない（消費者の技術非依存性を壊す）。

---

## 成果物の形式

- **IN**: 02_設計.md §7.2（map-experience の出力）・消費者プロジェクトの既存デザイン資産／デザインシステム（存在すればその階層・命名を最優先で参照）。
- **OUT**: 02_設計.md §7.3（UI 具体化・既存資産の探索一覧・再利用結果／新規作成の正当化根拠・アクセシビリティ・却下案・責務/API 候補）。責務/API 候補は define-boundaries の入力となる。
