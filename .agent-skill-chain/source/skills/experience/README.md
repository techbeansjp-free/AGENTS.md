# skills/experience — 体験設計ドメイン

体験（UX/IA/UI）の観点確認を担う 3 フェーズ capability の集合。command **design-feature** の skill chain 冒頭に、体験サーフェス該当時のみ発動する条件付き工程（step0a/0b/0c）として組み込まれる。

| capability | フェーズ | 目的 |
|------------|---------|------|
| [frame-experience](frame-experience/) | 1: 体験の前提づけ | ビジネス目的・成功基準（KPI）とユーザー・課題を一人称ナラティブ＋却下案で枠づけ、02_設計 §7.1 に記録する |
| [map-experience](map-experience/) | 2: 体験の流れ | フェーズ1 の前提の上で、情報設計（IA）・ユーザーフロー・体験ジャーニーを設計し、02_設計 §7.2 に記録する |
| [detail-experience](detail-experience/) | 3: 体験の具体化 | フェーズ2 の流れの上で、UI・アクセシビリティ・実装可能性を具体化し、既存デザイン資産の再利用を優先探索した上で責務・API 候補を define-boundaries へ引き渡す |

単体で使う場合は LOAD_POLICY に従い該当 capability のみ読む。chain で使う場合は commands/design-feature.md の順序（frame → map → detail → 既存 step1-3）を守ること。

---

## 発動条件（過剰適用回避）

- 3 フェーズは 00_要求定義.md の `experience_surface` が `yes:`（値。または未記入で frame-experience の判定結果＝あり となった場合）の issue にのみ発動する。判定結果が「なし」（`no:` 明示、または未記入で frame-experience が「なし」と判定）の issue では 3 フェーズとも発動せず、02_設計 §7.0 に判定結果（なし＋理由 1 行）のみを記録する。**値語彙（`yes:`/`no:`/未記入）と判定結果（あり／なし）は別概念であり混同しない**（正本は CONCEPTS.md および 00_要求定義テンプレートの frontmatter コメント）。
- 体験サーフェスの定義は「人間が感覚器で直接体験する出力があるか」であり、画面に限らず CLI 出力・エラーメッセージ・生成 Markdown・エージェントへの指示文も含む。

## フェーズ間の委譲モデル（fresh サブ分割・規模比例統合）

- **各フェーズは都度 fresh なサブエージェントへ委譲する**（1 人のサブが要件受領から UI まで一気通貫でこなす設計にはしない）。これは既存原則 CLOSEOUT.md §fresh サブ分割（同一サブに文脈を蓄積させない）を体験設計フェーズ境界へ拡張適用したものであり、進行役は design-feature の委譲を「step 0a」「step 0b」「step 0c」「残り chain」の単位に分割して個別に委譲する。各フェーズは前フェーズの確定出力（02 §7.x）のみを引き継ぎ、会話文脈は引き継がない。委譲手順の具体形は commands/design-feature.md の「実行時の注意」を参照。
- **規模比例で統合可**: 体験サーフェスが小さい場合（例: CLI エラーメッセージ 1 行の文言）、進行役の裁量で 3 フェーズを統合し、最小 1 サブに畳んでよい。統合時は 02 §7 に「どのフェーズを統合したか」を 1 行記録する。3 フェーズの機械的な強制はしない（CONTEXT_EFFICIENCY.md §適用のスケーリング）。

## 判断基準の優先順位（ドメイン共通・8 段）

体験設計の 3 フェーズすべてが判断に迷ったときに共通で用いる優先順位。設計判断（本ドメインの各フェーズ）とレビュー判断（review-docs）の双方に同一リストを適用し、二重定義しない。

1. ビジネス目標
2. ユーザータスク（ユーザーが達成したいこと＝ユーザー体験の中核）
3. 情報階層（IA）
4. アクセシビリティ
5. デザインシステムの一貫性
6. レスポンシブ
7. 保守性
8. ビジュアルの洗練度

上位（ビジネス目標・ユーザータスク）が下位（ビジュアルの洗練度）に優先する。「格好いいが操作しづらい」（ビジュアルの洗練度がユーザータスク・アクセシビリティを上回る案）は各フェーズの却下案として明示的に却下する。

## detail-experience: 既存デザイン資産の再利用優先

フェーズ3（detail-experience）は「新規に作る」より「既存デザイン資産を再利用する」ことを優先する。新規 UI 要素の提案前に、消費者プロジェクトの既存資産を探索順序（テンプレート相当 → パターン/セクション相当 → コンポーネント相当 → レイアウト相当 → プリミティブ相当 → 不足時のみ新規作成）に沿って探索し、探索結果を 02 §7.3 に列挙する。新規作成は正当化条件（複数箇所での再利用見込み・責務明確・既存の組み合わせで表現不可・バリアント明示・アクセシビリティ/レスポンシブ挙動の文書化）を満たす場合に限る。詳細な探索順序・正当化条件・4 原則・技術非依存の扱いは [detail-experience/SKILL.md](detail-experience/SKILL.md) を参照。
