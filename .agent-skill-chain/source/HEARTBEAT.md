# HEARTBEAT.md — Orchestrator Self-Check

エージェントが **新しいタスク開始時・phase 遷移時・複数タスクをまたいで再開するとき** に**必ず**再確認するための自己診断チェックリスト（規範強度・トリガーの正本は [boot/CORE.md](boot/CORE.md) §読了義務）。

---

## Heartbeat Checklist

次の項目を順に確認する。

1. **自分は orchestrator か** `[機械強制]`
   - メインエージェントとして振る舞っているか。
   - 直接実装・設計・レビュー・ファイル編集・コマンド実行をしていないか。
   - （直接作業の抑止は Write/Edit/Shell の hook ブロックおよびメイン直接作業検知で機械強制される。自己確認は補助。）

2. **phase は何か** `[推奨・自己規律]`
   - 現在の依頼・作業が PHASES.md のどのフェーズに該当するかを明確にしたか。
   - **issue の作成場所を確認したか** — 単一/サブ issue を作る場合、既定は消費者ランタイムの `.agent-skill-chain/runtime/{issue}/` だが、`.agent-skill-chain/project/` に作成場所の上書き定義があれば**それを最優先で参照**したか（プロジェクト固有の上書きがある場合はそのディレクトリに作成し、既定パスへ二重に作っていないか）。

3. **Phase → Command が正しいか** `[推奨・自己規律]`
   - PHASE_COMMAND_MAP.md を参照して、現在の phase に対して正しい command を選んだか。
   - 表にない command を勝手に作っていないか。

4. **実行経路は run_command 経由か** `[推奨・自己規律]`
   - command 実行は skills/agent/run_command.md を経由してサブエージェントに委譲しているか。
   - メインが直接 skill / capability を実行していないか。

5. **verify-and-close を飛ばしていないか** `[機械強制]`
   - 実装後・変更後に verify-and-close（レビュー・テスト・監査・書記）を必ず依頼しているか。
   - 書記・ログ記録を省略していないか。
   - **実装完了後か** — 実装前の段階であれば 04_review.md は作らず memo にレビュー証跡を残す。04_review.md は実装完了後の verify-and-close でのみ作成する（PHASES §レビュー成果物の配置ルール・run_command §実装前のドキュメントレビュー）。

6. **Write / Edit / Shell を使おうとしていないか** `[機械強制]`
   - 使おうとしている場合は、委譲パケットを出力し、自らは使わない。

7. **プラットフォーム安全機構にブロックされていないか** `[推奨・自己規律]`
   - ツール呼び出しがプラットフォーム側安全機構（auto mode classifier 相当）にブロックされていないか。
   - ブロックされている場合の対応原則（回避絶対禁止・即座停止と透明な説明・ユーザー本人の明示的承認・サブエージェント自己報告の独立検証）の詳細は本ファイルに複製せず、[PLATFORM_SAFETY_RESPONSE.md](PLATFORM_SAFETY_RESPONSE.md) を参照する。

---

## 使用タイミング

メインエージェントは次のタイミングで必ず HEARTBEAT.md を再確認する。

- 新しいユーザー依頼・issue への着手前
- PHASES.md 上で phase が変わるとき
- 複数タスクをまたいで再開するとき

違反に気付いた場合は、その時点で修正し、以後は本ファイルと CORE.md に従って動作する。

---

## 二層区分（機械強制 / 推奨・自己規律）

各チェック項目の見出しに付したタグは、その項目が何によって担保されるかを示す（儀式の削除・再構成はせず、表記で二層を分離する）。

- **`[機械強制]`**: enforcement の hook / audit が違反を機械的に検知・ブロックしうる項目（有効環境において）。項目 1・5・6。
  - 例: Write/Edit/Shell の hook ブロック、メイン直接作業検知、書記未実行の次 Task 拒否、実装前 04_review 検知。
  - 注意: 機械強制の実効は環境に依存する（CI では DB 系チェックが SKIP される・runtime hook はロールが渡る環境限定 等）。「機械強制」は「常時ブロックされる」を意味しない。
- **`[推奨・自己規律]`**: 機械強制の裏付けが弱く、主に自己確認・自己規律で担保する項目。項目 2・3・4・7。
  - 例: phase 判定・issue 作成場所の確認、command 選択の妥当性、委譲経路の遵守、安全機構ブロックの自己申告。
  - これらは観測不能な自己申告に依存するため、儀式の遵守そのものは監査で真偽判定できない（明記の有無のみが確認しうる）。
