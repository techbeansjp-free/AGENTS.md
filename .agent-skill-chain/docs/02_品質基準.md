# 品質基準

## システム開発のテスト契約

利用側が選択した言語、runner、Gherkin方言、test layer、命名をproject policyから参照する。要求を実行可能な受け入れ例と安定IDへ結び、変更種別、risk、影響境界、要求、受け入れ条件、影響分析に応じたVerification Setと再現可能なEvidenceで合否を判定する。テスト形式、コマンド、フィクスチャー、表示言語、構造keywordは利用側が所有する。

リスクに応じて正常、異常、境界、悪用、回帰を選ぶ。パス脱出、Unicode正規化、並行、同一性誤認、秘密、TOCTOUなど、変更が触れる安全境界の反例を検証する。一時環境と模擬境界を使い、無関係なワークスペースや外部状態を変更しない。具体的な静的検査とtest suiteはproject policyのhookから選ぶ。

CIはproject policyが選択した形式、runner、layer、静的検査を実行し、未定義と失敗、追跡欠落を拒否する。汎用パッケージは特定runnerやfile名を強制しない。

PR作成とmergeは、AIの成功判断や外部commandの終了値だけで完了としない。外部副作用前のdurable intent、外部副作用後のprovider read-back、固定したrepository・PR・Issue・HEAD・base ref・closing契約との一致をEvidenceとする。timeout、通信切断、応答解釈不能など成否が曖昧な場合はcreateまたはmergeを再送せず、provider上の既存状態を照合する。一度もdispatchしていないprepared intentは、該当するPR、auto-merge、merge queue entryが存在しない決定的Evidenceを得た場合だけ同一identityで一度再試行できる。照合不能や複数候補は`reconciliation-required`として停止し、重複PR・二重mergeの可能性を推論で解消しない。

merge直前の認可は固定HEADへexactに結び付ける。PR作成時から同じbase ref上でbase SHAが通常前進すること自体は失格にしないが、providerのdefault branch tip、PR base SHA、認可に用いるtrusted policy commitを一致させ、そのcurrent baseに対してpolicy、checks、review、mergeabilityを再評価する。classic protectionの404だけで無保護とせず、exact branchへ適用されるactive rulesetを確認する。native auto-mergeはmethodとenabledAtを、merge queueはentry ID・state・時刻・head/base OIDをEvidenceとして`merge-observed`へ保存するが、いずれもmerge完了Evidenceではない。providerから同じPR・Issue・HEAD・closing契約、`merged`状態、provider mergedAt、merge commit SHAを再観測した場合だけ`outcome=merged`のStep 11成功Evidenceにする。PoCとdisabledは固定PR bindingのdigestを`outcome=pull-request`としてStep 11へ結び、authority待ちは未完了のまま残す。

provider APIがHEAD以外のPR metadataへcompare-and-setを提供しない区間は、直前二重read、HEAD CAS、保護規則、直後read-backによるdetect-onlyの残余競合として扱う。本文またはbaseの同時変更を完全予防したEvidenceと誤表示せず、事後不一致は`reconciliation-required`とsecurity記録へ送る。

設計・test gateは、project hookが供給する依存/authority/evidence graphについてcycle、self-loop、unknown nodeの反例と汎用detectorの成功を要求する。PR gateは製品・仕様・testを固定した`H_impl`とreview artifactだけを加えたcurrent `H_final`を分離する。trusted providerが`H_impl` commit author、PR head/author、Actions runの関連PR/head/conclusion、独立review commit/actorを観測する。reviewerがPR authorとobserved implementation commit authorのどちらとも異なり、同じPRへ直接関連するsuccessful CI runとexact-head reviewがcurrent `H_final`へ一致する場合だけ承認証拠にする。head変更時はstale、failed、cancelledを除外して下流証拠を再生成する。

### 既定branch追随

既定branchが動いてcandidateが取り込みを要求される場合、取り込みは**review artifact commitより前**で行う。artifactの後へmerge commitを置くと、`H_impl..current`がreview artifactだけという条件を必ず破る。artifactを一度外して取り込み、artifactを最終commitへ置き直す。

追随後の固定点は次を指す。

| 固定点 | 指し先 |
|---|---|
| `比較基点` | 取り込んだ既定branchのtip |
| `H_impl` | artifact直前の最新commit。追随merge自身とは限らず、後続の整理commitがあればそれになる |
| `H_final` | 置き直したreview artifact commit |

**個別監査表は追随前の内容を流用せず、`比較基点..H_impl`から再生成する。** 追随後の差分は「取り込んだ既定branch tipに対してcandidateが最終的に持ち込むnet delta」であり、追随前の差分とはpath集合もchange typeも一致しない。

`比較基点`と`H_impl`はいずれも申告値をそのまま使わず、commit構造から独立に導出した値との完全一致を要求する。**`比較基点`を前へ進めれば監査範囲を縮められるため、片側だけを申告値のままにしない。**

`比較基点`の正確な定義は「`H_impl`が含む最新の取り込み先branch commit」、すなわち`H_impl`と取り込み先branch tipの`merge-base`である。上の追随手順に従えば、これは取り込んだ既定branchのtipと一致する。別branch経由で間接的に取り込んだ場合も同じ値へ収束する。

導出は境界commit、つまり`H_final`を含む最初のmerge commitの第1親を取り込み先branch tipとして行う。**境界commitの親がちょうど2個の場合だけ導出できる。**取り込み先branch上のPR mergeと、CIが`pull_request`でcheckoutするmerge refがこれに当たる。導出の成否で扱いを3つに分ける。

| 状態 | 条件 | 扱い |
|---|---|---|
| 対象外 | 境界commitの親が1個。候補branch上でreview artifact commitをHEADにした場合 | 導出せず申告値を使う。この確認は取り込み先が判明する時点で成立する |
| 判定不能 | 親が2個以上で導出できない。親が3個以上でどの親が候補branchか決まらない場合、浅いcloneでfork点が取得範囲の外にある場合、`merge-base`が複数ある場合 | **拒否する。**検証すべき場所で検証できなかった状態を合格へ倒さない。親が2個でないmergeを拒否する扱いは損失検知と揃える。CIでは全履歴を取得する |
| 検証済み | 親がちょうど2個で`merge-base`が一意 | 申告値との完全一致を要求する |

**squashまたはrebaseで取り込むprojectでは、取り込み先branch上のcommitが親1個になるため、取り込み先側でこの確認は成立しない。** 取り込み前のmerge refでの確認だけが働く。

`比較基点..H_impl`に含まれるmerge commitは、両方の親が保持していた安定IDと、いずれかの親が新たに導入した安定IDを、出現位置ごとに保持しなければならない。**安定IDの意図的な削除はmerge commitでは行わず、mergeの後の通常commitで行う。** merge内の削除は衝突解消の巻き戻しと区別できないため、通常commitの差分として個別監査へ載せる。親が2個でないmerge、merge-baseが一意でないmergeは判定不能として拒否する。

## 開発契約

- UNIX: 1責務、明示的な入力・出力、合成可能、最小共有状態。
- DDD: 境界づけられたコンテキスト、ユビキタス言語、影響するモデル・不変条件を記録する。変更で発見した候補語を要求・business ruleへ結び、確定語を耐久的なドメイン用語台帳へ反映する。コンテキストをまたぐ同名語、未定義語、表記揺れ、根拠なしの意味変更をreviewする。
- BDD: 要求 → 具体例 → 受け入れ条件を実装前に確定し、business requirementと実装検証の共通契約にする。
- Evidence-driven Verification: AI推論は候補生成、反例探索、原因分析に使うが、推論自体を正しさの証拠にしない。変更種別、risk、影響境界、要求、受け入れ条件、影響分析から必要な検証集合だけを選び、再現可能なEvidenceで判定する。TDDはbug再現やcritical logicなど有効な場合に選べる技法であり、全変更の必須processではない。
- Zero Trust: 入力、リポジトリ、認証、承認、状態を書き込み直前に検証する。
- Privacy/Security by Design: 個人情報・秘密・攻撃面・保持・削除・最小権限を要求時点から扱い、ログ、例外、分析、配布物への漏えいを防ぐ。
- Secure Logging・Observability・運用可能性: 必要な信号、相関、伏字化、アクセス、保持、rotation・容量上限、監視、障害対応、復旧確認を設計する。
- Human-Centered UI/UX・アクセシビリティ: 人が触れる操作では利用状況、主要タスク、状態・エラー、支援技術、キーボード・タッチ、認知負荷を受け入れ条件へ結ぶ。
- Design System・Design/Layout Token: UI、テーマ、複数画面、レスポンシブ表示、または再利用部品がある場合、意味を持つtoken、状態、breakpoint、配置不変条件を契約化する。
- Markdown: 判断、レビュー、テスト、仕様影響、再開地点を人間が読める形で残す。

要求・要件・設計・計画・レビューは、Privacy/Security、Logging/Observability、Human-Centered UI/UX、Design/Layout Tokenをそれぞれ`applicable / not-applicable`で判定する。`not-applicable`は対象範囲を限定した理由と確認証拠を必須とし、未判定、理由なし、証拠なしを認めない。具体的なログ製品、rotation手段、UI framework、token形式、保持期間は汎用側へ固定せず、利用側のproject policyと`docs/specs/`が所有する。

Step成果物は対応する`SKILL.md`が明示したテンプレートを作業開始前に全文読み、その構造と必須欄を保持して作る。テンプレートの対応・実在・境界は機械検証し、成果物名だけからの推測を認めない。

## 有限レビュー契約

最大3ラウンド契約とexact-head独立reviewは実装後の最終レビューだけに適用する。要求・要件・設計・計画の途中確認はreadiness checkであり、成果物ごとに独立した3ラウンドreviewを連鎖させない。

すべてのラウンドで肯定・敵対の評価基準を確認する。肯定は正しさ、価値、実現可能性、整合性、保守性を確認する。敵対は反例、失敗経路、境界値、悪用、安全性、データ損失、ロールバック、範囲漏れを確認する。各項目は`pass / finding / not-applicable（理由）`で評価し、指摘なしの承認を有効とする。

ラウンド1は全評価基準で指摘を確定する。ラウンド2は未解決のCritical/High、修正差分、触れた隣接範囲だけを確認する。ラウンド3は収束を確認し、残存指摘を`valid / resolved / duplicate / false-positive / out-of-scope`へ根拠付きで分類する。Medium/Lowは記録するが、自動修正、追加ラウンド、ゲート停止を発生させない。未解決Critical/Highは、別権限者による責任者・期限・条件付きリスク受容がない限り停止する。任意の危険な範囲は除外、既定無効、ロールバック可能な安全側へ縮小する。同じ範囲の上限は3ラウンドで、自動更新しない。

## 仕様整合性

振る舞い・構造変更は`docs/specs/`を更新し、要件・変更・シナリオ・テストを追跡する。実際に文言だけの変更は、範囲を限定した`no-spec-impact`根拠により仕様ファイルを空更新せず通せる。影響不明、必要更新欠落、追跡欠落はPR作成・完了処理を拒否する。

## 検証scopeとpolicy品質

## 独立reviewが成立しない場合

外部reviewサービスの利用有無は要件ではない。要件は、PR authorとobserved implementation commit authorのどちらとも異なるreviewerによるexact-head reviewである。人がreviewerであってもよい。

**既定は停止ではなく、無記録での通過の禁止である。** 独立reviewの不在それ自体は何も壊さない。壊すのは、未reviewのまま外部へ不可逆に配布することである。したがってrisk比例型ruleに従い、強制強度を可逆性と影響範囲へ比例させる。

門を置く場所は、自動か手動かでは決めない。**止めた場合に残る状態が復旧可能であり、かつ止めることで不可逆な行為を防げるところにだけ置く。** どちらか一方でも満たさない門は、安全を足さずに流れだけを止める。

| 対象 | 止めたら残る状態 | 止めて防げる不可逆な行為 | 門 |
|---|---|---|---|
| 既定branchへのmerge | PRのまま。復旧可能 | 無い。mergeはrevertできる | 置かない |
| tag作成とRelease | tagが無い状態。復旧可能 | 無い。tagもReleaseも削除できる | 置かない |
| package registryへの公開 | tagはあるが未公開。後から公開でき復旧可能 | **ある。** 公開の取り消しは事実上できない | **置く** |

| 対象 | 独立reviewが無いとき |
|---|---|
| 実装、test、仕様の変更とcommit | 記録があれば進む |
| PR作成、既定branchへのmerge | 記録があれば進む。適用した例外の識別子と観測値をreview artifactへ残す |
| mergeを契機に自動で走るtag作成とRelease | **記録があれば進む。** 止めても不可逆な行為を防げないため門を置かない |
| package registryへの公開など、外部への不可逆な配布 | 既定は停止し、独立reviewの外部証拠を要求する。**外部reviewerが実在しない構成では例外で覆える。** ただしその宣言は不可逆性に比例して強くする |
| 削除、force push、履歴書き換え | **独立reviewの対象外。** reviewが見るのは変更であって操作ではない。preview、承認hash、authorize、branch保護の既存authority経路で守る |

記録が無い場合は、可逆な操作であっても進めない。**無音で通過させないことが目的であり、待たせることが目的ではない。**

例外を認める場合、projectは承認済み例外を正本fileへ宣言する。宣言には識別子、種別、条件、観測方法、承認元、承認者、対象scope、理由、承認日時、失効日時、満たさない要件、記録先を含める。失効日時は無期限を明示する値と未記入を区別する。**checkの結論だけを証拠にしない。** review commentとapprovalの実体を観測して未実行を判定する。

宣言の強さは不可逆性に比例させる。**永久に塞がる門を作らない。** 独立reviewerが実在しないprojectでも公開できなければ、製品として成立しない。門の目的はownerの判断を妨げることではなく、**黙って、誰の判断か分からないまま行われることを防ぐこと**である。

| 対象 | 宣言に求めるもの |
|---|---|
| 可逆な操作 | 通常の宣言。失効日時に無期限を示す値を置いてよい |
| 外部への不可逆な配布 | 対象に含める旨の明示と、**期限付きの失効日時。** 無期限を認めない |

一度書いて忘れたまま公開され続ける状態を作らない。

種別ごとに扱いが異なる。

| 種別 | 扱い |
|---|---|
| 独立reviewerが実在しない | 承認元、対象scope、失効日時を持つ宣言でだけ許可する |
| 一時的な失敗 | **例外にできない。** 再試行を既定とし、上限を超えた場合は他の種別として宣言し直す |
| 成功と表示されるがreviewが実行されていない | 実体の観測で未実行と判定し、適用したPRと観測値を記録する |

review artifactは正本の識別子を参照し、承認元、承認者、承認日時、失効日時を複製しない。

差分、risk、正確な成功証拠に基づいてtargeted検証を選び、同じ成果を重複実行しない。最終gateはfull検証と独立reviewを維持する。運用品質は待ち時間、重複、誤block、override、rollback、検出漏れを秘密なしで観測する。利用側固有の設定と証拠は汎用配布物から分離し、具体的な検証方法とbudgetはproject policyのhookから選ぶ。
