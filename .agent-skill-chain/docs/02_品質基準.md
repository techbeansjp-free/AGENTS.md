# 品質基準

## システム開発のテスト契約

利用側システム開発の単体・結合・E2Eテストはすべて、人間が読める日本語のGherkin `Feature / Scenario / Given / When / Then`で起票し、安定した一意のSCN IDを付ける。ステップ定義はその起票を実装し、結果へ同じIDを表示する。最初にシナリオの失敗を観測し、最小実装で合格させてから整理する。テスト基盤、コマンド、フィクスチャー、ステップ実装は利用側が所有し、パッケージは形式契約と検証器を提供する。

リスクに応じて正常、異常、境界、悪用、回帰を選び、安全性に関わるワークフローコードは正常系以上の失敗系を用意する。パストラバーサル・シンボリックリンク脱出、Unicode制御文字・正規化、同時作成・原子性、リモート誤認、秘密情報の伏字化、TOCTOUを検証する。テストは一時リポジトリと模擬プロバイダーだけを使い、実ワークスペース、実リモート、他のworktreeを変更しない。プロジェクトの型検査と既存テスト一式を通し、変更したシェルだけShellCheckする。

CIは`scripts/check_gherkin_format.py`を実行し、日本語説明なし、SCN ID欠落・重複、Given/When/Then欠落、単体・結合・E2E層の欠落、Node `*.test.js`起票の残存を拒否する。Cucumber実行は未定義・失敗ステップを別途拒否する。

## 開発契約

- UNIX: 1責務、明示的な入力・出力、合成可能、最小共有状態。
- DDD: 境界づけられたコンテキスト、ユビキタス言語、影響するモデル・不変条件を記録する。
- BDD/TDD: 受け入れ条件 → シナリオ → 失敗テスト → 実装 → 結果を追跡する。
- Zero Trust: 入力、リポジトリ、認証、承認、状態を書き込み直前に検証する。
- Markdown: 判断、レビュー、テスト、仕様影響、再開地点を人間が読める形で残す。

## 有限レビュー契約

すべてのラウンドで肯定・敵対の評価基準を確認する。肯定は正しさ、価値、実現可能性、整合性、保守性を確認する。敵対は反例、失敗経路、境界値、悪用、安全性、データ損失、ロールバック、範囲漏れを確認する。各項目は`pass / finding / not-applicable（理由）`で評価し、指摘なしの承認を有効とする。

ラウンド1は全評価基準で指摘を確定する。ラウンド2は未解決のCritical/High、修正差分、触れた隣接範囲だけを確認する。ラウンド3は収束を確認し、残存指摘を`valid / resolved / duplicate / false-positive / out-of-scope`へ根拠付きで分類する。Medium/Lowは記録するが、自動修正、追加ラウンド、ゲート停止を発生させない。未解決Critical/Highは、別権限者による責任者・期限・条件付きリスク受容がない限り停止する。任意の危険な範囲は除外、既定無効、ロールバック可能な安全側へ縮小する。同じ範囲の上限は3ラウンドで、自動更新しない。

## 仕様整合性

振る舞い・構造変更は`docs/specs/`を更新し、要件・変更・シナリオ・テストを追跡する。実際に文言だけの変更は、範囲を限定した`no-spec-impact`根拠により仕様ファイルを空更新せず通せる。影響不明、必要更新欠落、追跡欠落はPR作成・完了処理を拒否する。
