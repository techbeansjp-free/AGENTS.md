# 運用ポリシー

## 目的と成立条件

本システムの目的は、システム開発として正しい成果物を、AIを用いて速く作ることである。

**ここでいう正しさは、要求を満たし、品質、セキュリティ、再利用性、保守性を担保していることを指す。検査が緑であることは正しさの必要条件であって十分条件ではない。** gateを通過した事実を正しさそのものと読み替えない。

**ここでいう速さは開発速度、すなわち要求から成果物を提出するまでに要する時間の短さを指し、成果物自体の実行性能を指さない。**

正しさと開発速度はトレードオフではなく、両方が成立条件である。

- 正しさを満たしても開発速度を失った状態は、目的を達成していない。
- 開発速度を満たしても正しさを失った状態も、目的を達成していない。
- policy enforcement、gate、reviewは正しさを担保する手段であって目的ではない。**手段が開発速度を損なうとき、縮小するのは手段の側である。**

この節は目的と観測基準だけを所有し、安全条件、authority分離、fail-closed不変条件を緩和しない。開発速度を理由に必要な検証を省略する根拠として引用しない。**縮小の対象は手段の実施回数、範囲、所要時間であり、安全条件、authority分離、fail-closed不変条件に属する手段を含まない。** これらを変更する場合は個別Issueの判断ではなく本文書の改訂手続きを要する。成果物の実行性能は本節の対象ではなく、非機能要件が所有する。

### 成立条件の観測

正しさの観測は[02_品質基準.md](02_品質基準.md)が所有する。開発速度は次を観測する。

- **支援層の所要時間が成果物構築の所要時間を上回らないこと。** 上回る場合、policy enforcementは薄い支援層ではなく主経路そのものになっている。
- 同一scopeのreviewラウンドが有限であり、予算内で収束すること。
- 手段の追加を提案する前に、既存手段の縮小で目的を満たせないかを先に評価すること。
- **成果物の分量を判断の量へ比例させること。** 機械検査が要求するのは節や欄の存在であって分量ではない。判断のある箇所は具体的に書き、判断の無い箇所は書式を埋めるために語を増やさない。同じ理由で対象外になる項目が複数あるなら、項目名を列挙した1行へまとめる。**これは記録の省略を許すものではない。** 対象外である事実は必ず残し、同じ理由を複数回書き直す作業だけを止める。

## 4つの正本と記録の原則

永続的に保持する情報は、責務の異なる次の4つだけに置く。**同じ事実を2つ以上へ書かない。**

| 正本 | 何を表すか | 何を置くか | 置かないもの |
|---|---|---|---|
| Planning | 実装前の意思決定 | 要求、要件、受け入れ条件、不変条件、設計、実装計画（staging 00〜03）と計画変更記録（05） | 実装後の事実、実装に合わせた書き直し |
| Git | 実装された事実 | commit、diff、code、test、変更順序、finding是正の変更 | 同じ事実を説明し直すMarkdown |
| System Specification | 完成したシステムの現在状態 | `docs/specs/`の振る舞い・構造・データ・非機能・安全・運用の契約 | 案件の検討経緯、途中の方針変更の叙述、review記録 |
| Evidence | 正しく安全であることの証明 | exact HEAD、review sessionとfinding状態、独立性、検証結果、影響集合を構造化したdata | 自然言語の長文による証明 |

**記録の判断は次の順で1回だけ行う。**

1. Gitから分かるか。分かるなら書かない。
2. 現在のシステムの仕様か。そうなら`docs/specs/`へ書く。
3. 実装前の意思決定か。そうならPlanningへ一度だけ書く。承認後の変更は計画変更記録へ差分だけを書く。
4. 安全性や正しさの証明か。そうならEvidenceへ構造化して残す。

どれにも当たらない情報は保存しない。

**承認済みPlanningは凍結する。** 同期時点（fullはStep 8、quick・pocはStep 4）で計画文書のdigestを封印し、以後は実装結果に合わせて書き直さない。実装中に計画を変える必要が生じたら`05_計画変更.md`へ対象・変更前・変更後・理由・影響する契約・影響範囲だけを追記し、その差分だけをStep 10でreviewする。封印は記録し直せず、記録済みの計画変更は書き換えない。完成状態はPlanningではなく`docs/specs/`へ反映する。

**reviewの対象はGitとSystem Specificationであり、説明文書ではない。** reviewerは比較基点と候補HEADからGitを直接読み、実装者が変更内容を説明し直した文書を主入力にしない。round 2以降は未解決finding、前回review済みHEADからの差分、その差分の影響集合だけを見る。影響を証明できなければ全体reviewへ倒す。review結果はreview sessionの構造化dataとCLIが生成するreview証跡として残し、reviewを行った証明を長文として書かない。

**縮小するのは書類と再読込であって、安全性ではない。** 事前の要求・要件・設計review、reviewerの独立性、exact HEAD binding、Critical/Highの解消、security review、仕様適合、検証Evidence、fail-closed、追跡はいずれも維持する。

## 権限

パッケージ既定値は`delivery.stopAt=pull_request`である。これは`pr create`がmergeを同じ外部操作へ暗黙連結しないコマンド境界を表し、ASC全体の正常終了をPRへ固定する値ではない。ローカル計画にGitHubリモートは不要だが、一時ステージングを耐久化済み、同期済み、別セッションから再開可能とは報告しない。外部への書き込みには、事前表示、リポジトリ同一性、認証・権限・状態、操作単位の承認、書き込み直前の再検証を要求する。

プロジェクトのマージ方針は既定ブランチで追跡し、`disabled / assisted / automatic`から選ぶ。`assisted`はformal quality approvalとは別に、対象PR単位の`--authorize=approved`とrepository write authority照合を要求し、その後に作る`merge-prepared`を耐久的な操作承認記録とする。`automatic`は既定ブランチ上の信頼済みポリシーを耐久的な承認として扱う。対象PR自身が追加・緩和したポリシーで自己承認できない。ホストとGitHubの制御を迂回しない。

`full`と`quick`で`merge.mode=automatic`の場合、PR作成後も正常終了と報告せず、required checks、review記録、current HEAD、ruleset、mergeable状態を観測して独立した`pr merge`操作へ進む。GitHubのauto-mergeまたはmerge queueを利用できる場合は登録を正常な進行状態とし、無期限pollingを行わない。`poc`と`disabled`はPRを正式な終端とする。`assisted`で対象PR authorityが無い場合は終端化せず、PR bindingと再開条件を保持して待機する。`disabled`で終端化したfull/quickのopen PRは、後に既定branch上のtrusted policyがmerge可能なmodeへ変わった場合も自動では再開しない。repository ownerが同じPRに対する新しいdelivery判断を明示した場合だけ、旧Step 11を保存した別epochとして、現在のtrusted policy、固定PR identity、exact HEAD、checks、review、protectionを再検証してmergeへ進める。PoC、closed/merged PR、identity不一致は再開しない。

マージ承認が許可するのは`pr.merge`だけである。ブランチ削除、Issue終了、リリース、パッケージ公開、完了処理、後片付けは別の権限を要求する。

## 所有権

パッケージ所有資産は、この案内、3つの規範文書、テンプレート、ステップ0〜11のスキル契約、スキーマ、既定ポリシー、CLI、検証器、アダプターである。利用側所有資産は、プロジェクト規約・テストコマンド、Issue staging（project policyの`staging.root`、既定`.agent-skill-chain/tmp/issues/`）、`docs/reviews/`のreview証跡、`.agent-skill-chain/project-policy.json`、`docs/specs/`、将来の`docs/adr/`である。更新・アンインストールは利用側所有資産と変更済み資産を保持する。

Semantic Graphの正本はGit管理text・sourceとproviderから固定した既存耐久stateである。`.agent-skill-chain/runtime/graph/v1/`のGraphQLite extension・database・manifest・pointerは各worktreeのGit管理外派生投影であり、全削除と完全再構築が可能でなければならない。package更新・削除は利用側runtimeを暗黙に正本化または共有しない。

## role分離とmodel tier

同一scopeの工程責務は`coordinator / analyst / implementer / reviewer / verifier / finalizer`へ分離する。coordinatorはIssue分解、依存関係、割当、状態遷移、証拠集約だけを行い、product code・test・specを実装しない。implementerと最終reviewerは異なるagent identityかつ異なるcontextとする。**組織上の別人物であることは既定では要求しない。** 独立性の要求水準はproject policyの`merge.reviewIndependence`が決め、未宣言の既定は`context-isolated`（別session/context、exact HEAD固定、対象差分の非変更、肯定・敵対レビューとfinding記録）である。`actor-independent`（PR author・implementation commit authorと別のstable actor ID）は、**高リスク変更・不可逆操作・release・外部公開でproject policyが宣言して引き上げる。** **独立性はprovider名や論理tierでは判定しない。** 要求水準が不明ならPR、merge、finalizeをfail-closedで停止する。

**どこまでが機構で、どこからが記録かを取り違えない。** `merge`はtrusted policyから要求水準を解決し、`context-isolated`では保存済みreview sessionのexact `H_impl`、Step 10 bindingのround digest、`review export`が生成したtracked `H_final` review証跡のpath/digest、独立性・非変更・`approved`・未解決Critical/Highなしを照合したformal approvalを使い、`requiredReviews`が2以上なら同じHEADへのprovider approvalを追加で数える。`actor-independent`では従来どおり対象`H_final`のprovider `APPROVED` eventとPR author・`H_impl` authorからのstable actor ID分離を使う。両modeとも`H_impl`から`H_final`への差分をreview証跡1件に限定する。candidateの申告や証跡file単体はauthorityにせず、保存済みsession・tracked Git blob・trusted policyから再導出できなければ承認しない。**この区別を曖昧にしたまま「機構が保証している」と書かない。**各roleの許可path、許可操作、禁止操作、必要証拠はproject choiceで宣言し、package既定契約より弱い変更をcandidate自身の承認へ使わない。

能力tierは`routine / standard / advanced / critical`とし、risk、mode、scope、finding重大度から単調に必要tierを決める。model mapping未定義、tier不足、根拠なし降格、silent fallbackは拒否する。能力tierはfilesystem、GitHub、merge、releaseのauthorityを付与せず、操作authorityを別の信頼境界で検証する。

provider別の自律選択上限として、Codexの推論レベルは`high`まで、Claudeのmodelは`Opus`までとする。上限超過にはprovider、選択値、Issue、scope、指示者、指示日時、失効日時が完全一致する人間overrideを要求する。roleまたはAI agentによる自己発行、別Issue・別scope・失効済み証拠、alias・自動routing・fallbackによる上限回避を拒否する。人間の事業判断とrisk受容は能力tierから推測しない。

## fail-closed不変条件

- モードの根拠が不明なら`full`を選ぶ。
- リポジトリ、リモート、SHA、保護設定、検査、レビュー、仕様影響、復旧方法、権限が不明なら、それに依存する書き込みを拒否する。
- 暗黙のstash、reset、checkout、clean、worktree削除、マージ、終了、削除、リリース、公開を行わない。
- 事前確認と適用を分離する。完了処理の適用には、承認済みの最新報告ハッシュを要求する。
- アーカイブ済みハーネス、SQLite台帳、リース、UUIDによる作業調整、サブエージェント強制、無制限レビューループへ実行時依存しない。
- Graphのsource、schema、builder、固定extension、worktree identity、manifest、実投影のいずれかがdriftしたらexact Graph Evidenceを拒否する。正本とwrite authorityが健全なら人間承認待ちではなくworktree内の完全rebuildで前向きに復旧する。

上記GraphQLiteは正本または作業調整用のSQLite台帳ではなく、問い合わせのための破棄可能なRead Modelである。アーカイブ済みSQLite台帳への実行時依存禁止は維持する。

依存、authority、evidenceは有向非循環graphとして扱う。candidateによる自己評価、tracked artifactへの自己commit SHA、相互参照で成立する承認・証拠を禁止する。rollback/retryだけは、単調なrevision、実行上限、終了条件を持つ明示的な状態遷移として許可する。

ポリシースキーマと安全な既定値は`.agent-skill-chain/schemas/`と`.agent-skill-chain/policy/`に置く。利用側による上書きは、有効で追跡済みのポリシーだけに許可し、パッケージ既定値は常に安全側とする。

## conformance scopeと適用可否

project policy manifestの`conformanceScope`は、未指定を含む`repository-bound`と`package-attested`を区別する。`repository-bound`は利用projectがI1〜I12を自身のrepository実装へbindingする宣言であり、従来どおり1件以上のconformance fileを要求する。`package-attested`はpackage側で成立したI1〜I12の適合証拠を再利用し、consumer実装へのbindingをclaimしない宣言である。I1〜I12が不要または未検証という意味にはせず、conformance fileは空のinventoryにする。

project policy manifestの`verification`は、`verify run`が受理する検証commandをargvで宣言する。`fullCommand`は全体検証のargvそのもの、`targetedRunner`は影響集合のfeature pathを後ろへ並べる実行器のargvである。**値は既定branchのtrusted commitから読み、candidateの宣言は使わない。** 宣言の無いprojectでは`verify run`・`review export`・review証跡の照合を拒否する。

repository-boundのbindingはI1〜I12を各1件列挙する。`status`を省略したbindingと`applicable`はsource、enforcement point、反例SCNを必須とする。`not-applicable`は範囲を限定した理由と証拠を必須とし、source、enforcement point、反例SCNを指定しない。空配列で形式的に適用外を表現しない。module exportを持たない実行入口は、実行せず通常fileの実在だけを検証する`file-entrypoint`で宣言する。構造化checkは`ASC-`を除いたproject rule IDを小文字ハイフン化した`check-ref`で参照し、bindingへraw shell commandを書かない。

qualityのstrict型検査、lint、format、typecheck、runtime validationは、具体値または理由と証拠を持つ`not-applicable`で宣言する。`applicable` objectだけで具体値を省略しない。trustedからcandidateへの比較では、`repository-bound`から`package-attested`、binding削除、`applicable`から`not-applicable`、enforcement point・反例SCNの減少、quality具体値から`not-applicable`、禁止型の縮小を弱化として拒否する。逆方向と要素追加は強化として許可する。

**単調性契約を持つ`projectChoices.testLayers`・`projectChoices.forbiddenTestFileSuffixes`・`projectChoices.quality.forbiddenTypes`から、採用していない値を取り除く経路は存在する。** 既定branchのproject policyへ`projectChoiceShrinkProposals`を登録し、次のPRで適用する二段階の手順である（`schemas/00_利用案内.md`）。**`forbiddenTestFileSuffixes`の空配列は「この方針を持たない」の正規表現であり、検査系は禁止対象0件として扱う。** 採用していない禁止を宣言し続ける必要はない。

## risk比例型rule

強制強度は具体的なrisk、可逆性、影響範囲、authority境界に比例させる。安全・authority境界以外を一律にdenyせず、拒否時は行動可能な根拠、安全な次の行動、必要authority、rollbackを返す。candidate変更は自身へ適用するtrusted条件を緩和して自己承認できない。構造の機械正本はschema、製品仕様と追跡は`docs/specs/`、projectの選択値はproject policyへ分離する。
