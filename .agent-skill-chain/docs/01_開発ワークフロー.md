# 開発ワークフロー

## モード

既定は`full`で、`0 → 1 → … → 11`を実行する。`quick`はQ-01〜Q-08がすべて真かつ根拠付きの場合だけ許可し、`0 → 1 → 4 → 9 → 10 → 11`を実行する。偽、不明、未回答、根拠なし、プロジェクト閾値なしが1つでもあれば`full`とする。quick失格分類を発見した`quick`は`full`へ単調昇格し、`full`から途中降格しない。分類は下の「モード判定質問」の表が所有する。

`poc`は仮説検証のために明示指定し、全工程をquick相当の最小成果物・最小gateへ集約して`0 → 1 → 4 → 9 → 10 → 11`を実行する。PoC目的、repository内で実環境・実data・外部副作用から隔離した疑似project fixture、fixtureの初期化Evidence、runner IDと安全な相対path、固定argv、use case、Given・When・Thenを持つBDD scenario、各scenarioを判定する機械observable、成功・中止条件、非対象、データ・security上の制約、責任者、full昇格または廃止の判断条件を00へ記録する。要求時点では未実装fixtureのdigestを自己申告させず、実装後のexact HEAD blobからASCがfixtureとrunnerのdigestを計測する。観測期間の経過を完了条件にしない。公開API、個人情報、機密情報、外部公開、不可逆操作の各high risk条件を根拠付きで確認し、ひとつでも`あり`、不明、未確認、根拠なしの場合、または変更fileからquick失格条件を検出した場合はfail-closedで`full`へ単調昇格するか停止する。

`poc`は正式開発ではなく、PRを既定停止点とする。ASCは検証対象HEADに追跡済みでdirty・untrackedでないfixtureをHEAD blobから一時copyへ復元し、fixture内のNode runnerを宣言済み固定argvで実行する。任意shell・任意command・外部作成Evidenceは受理しない。Linuxの`/usr/bin/git`、`/usr/bin/bwrap`、`/usr/bin/prlimit`を事前条件とし、欠落・隔離失敗は観測前にfail-closedとする。bubblewrapのmount・PID・network namespaceとread-only mount、prlimit、timeout、出力上限を主境界にし、Node Permission Modelは補助防御であって単独のsecurity境界ではない。EvidenceはPoC宣言digest、ASCが計測したfixture/runner digest、scenarioごとの`exitCode=0`・`signal=null`、stdout/stderr/fileのdigest、全observableの型別exact一致、result/execution/global digest、ISO 8601 UTC観測時刻、exact HEADを必須とし、raw stdout/stderrを保存しない。`poc-observations/<headSha>.json`へHEAD別append-onlyで固定し、同一HEADの異なる内容を拒否する。Step 9以降のjournalは同じheadShaとevidenceDigestへ拘束し、review修正後の新HEADは新世代を追加して旧Evidenceを残す。Step 11後は新観測・Step 0〜10追記を拒否する。baselineからHEADまで、およびPR適用直前のprovider観測baseからHEADまでの実Git差分がfixture root内の通常fileだけであることを再計測する。release、自動merge、本番cleanupへ進めず、正式開発へ移す前に昇格根拠と`full`で不足する01要件定義、02設計、03実装計画を列挙して補完する。`full`から`poc`へ途中降格しない。

`quick`と`poc`のステップ1は目的、対象内外、影響する境界づけられたコンテキストとドメイン不変条件、受け入れ条件、最小Gherkin、確認方法を00へ集約する。全モードでP-01 worktree、P-02 Markdown、P-03 UNIX、P-04 DDD、P-05 BDD、P-06 Evidence-driven Verification、P-07 Zero Trustの証拠を残す。quickは根拠付き低risk変更を最短で完了する正式開発、pocは仮説を最速で検証してPRで停止する非正式開発であり、相互に読み替えない。

## Semantic Graphの利用

GraphはFull・Quick・PoCの別契約をそのまま投影し、Graphの導入またはquery可能性を理由にQuick・PoCを一律にFull化しない。GraphはGit・text・provider耐久stateの派生Read Modelであり、要求、要件、設計、実装計画、Finding、Evidenceの書き込み正本にしない。

影響候補はbounded BFS、依存順序とcycleはbounded Kahn法・iterative Tarjan法、説明経路はbounded BFSまたは非負重みDijkstra法で決定論的に取得する。driftのあるGraphをGateに使わず、正本が変わらない復旧は完全rebuildで行う。実装中の発見は影響する契約だけを前向きに更新し、Graph driftだけで要求から工程全体を再開始しない。観測は実日数を待たず、隔離疑似projectのモード別・通常・反例・復旧scenarioで完了する。

## モード判定質問

`quick`を選べるかは次の8問で決める。**すべて真かつ根拠付きの場合だけ`quick`を許可する。** 1問でも偽、不明、未回答、根拠なしがあれば`full`とする。

質問は1問につき1つのquick失格分類だけを問う。**すべて「真＝`quick`を選べる」向きで書かれている。** 1つの変更が複数の分類へ該当することは正常であり、その場合は該当するすべての質問を偽とする。どれか1つを選ばせない。

| 質問 | quick失格分類 | 内容 |
|---|---|---|
| Q-01 | public-api | この変更は、外部へ公開するinterface（API、CLI、配布するschema定義file、template、規範文書）とその外部観測可能な振る舞い（終了値、error、既定値、副作用、互換性）を、追加・変更・削除しないか |
| Q-02 | data-migration | この変更は、既に保存されているデータの形式、移行手順、後方非互換な読み書き規則を追加・変更・削除しないか |
| Q-03 | security-boundary | この変更は、認証、認可、信頼境界の判定に加え、秘密情報の取得、保存、伝送、表示、伏字化、破棄の扱いを、追加・変更・削除しないか |
| Q-04 | dependency | この変更は、依存package、lockfile、versionの制約に加え、実行時に必要となる外部の存在（executable、OS library、外部service、常駐process）を、追加・変更・削除しないか |
| Q-05 | infrastructure | この変更は、実行環境、CI、基盤設定、配布経路、および接続先やendpointの指定を、追加・変更・削除しないか |
| Q-06 | irreversible-operation | この変更は、削除、公開、送信など元へ戻せない操作について、認可、対象、引数、実行時期、到達性、操作手順、復旧可能性のいずれも追加・変更・削除しないか。いずれも変えない非規範的な引用だけであれば該当しない。不明な場合はfalseとする |
| Q-07 | ambiguity | 現時点の入力に、目的、対象内外、各受け入れ条件の観測方法、判定に用いる閾値、未決事項とその決定権者がすべて明記されており、目的、対象範囲、受け入れ条件、不変条件、要件のいずれのあいだにも矛盾が無いか。1つでも不足、不明、または矛盾があればfalseとする |
| Q-08 | multi-context | 影響する境界づけられたコンテキストが1つに限定でき、他コンテキストのモデルと操作へ触れないか |

この表と`src/domain/mode.ts`の`MODE_QUESTIONS`は、機械的に一致を強制される対である。**片方だけを書き換えると`conformance:check`が落ちる。** 質問文の向きが正しいかを機械は判定できないため、向きの変更が必ずこの表の差分として現れるようにしている。質問文の決定権者はpackage ownerである。

## 成果物用語と責務境界

Issue同期時のtrackerはrepositoryとIssue番号を拘束するabsolute GitHub Issue URLに限る。`#123`や`123`の短縮値は将来の再同期先を一意に復元できないため永続化しない。

### Step実施の機械記録

`workflow record`の汎用追記はStep 1〜10だけに使用する。Step 11はdelivery終端専用であり、固定済みPRまたはmerge observationからdelivery経路が記録し、genericな`workflow record --step=11`は拒否する。

Step定義の機械正本は`src/domain/workflow.ts`とし、この文書のStep表4列とモード節のStep列は`npm run workflow:check`で完全一致させる。表とモード節の一方だけを変更しない。Step 0は`00_モード判定.json`と`journal/steps.jsonl`を生成し、各Step完了時は`workflow record`で成果物と証拠を追記する。`pr create`はStep 10まで、特にStep 4と10、および`sync-verified`を検証する。quickでもStep 4は省略対象ではない。

無条件の欠落迂回を設けない。人間が欠落を明示承認する場合は対象Issue、`workflow.pr.create` scope、指示者、理由、指示日時、失効日時をjournalへ記録し、AI・roleの自己発行、別Issue、失効、欠落以外の不整合を拒否する。

HumanOverrideの承認元はcandidateの管理境界から分離し、candidate作成前から既定branch上で保護された設定、GitHubのreview・承認、またはrepository ownerが管理する認証済み外部channelに置く。candidate branch内のfileは、内容や署名欄に人名があっても承認元として扱わない。`instructedBy`と`reason`のjournal記録は事後監査の証拠にすぎず、candidateによる自己許可を防ぐ予防統制の代替にはならない。

この節を開発工程で使う統制語彙の正本とする。案件固有の業務用語・略語・ユビキタス言語は各案件の00/01と生成後の`docs/specs/01_システム概要/02_用語・略語.md`が所有し、この節の用語を別の意味へ再定義しない。

| 用語 | 定義 | 含めないもの・境界 |
|---|---|---|
| 要求 | 利害関係者が解決したい問題、実現したい価値、期待する状態を表す上流の意図 | 実現手段を要求として固定しない。ただし法令、契約、期限等の真正な制約は分離して記録する |
| 要件 | 承認済み要求を満たすためにシステムまたは開発成果が充足しなければならない、一意IDを持つ観測・検証可能な条件 | 設計案、実装task、テスト結果を要件として扱わない |
| 制約 | 法令、契約、互換性、環境、authority等によって解空間を制限する変更不能または変更権限が別にある条件 | 期待価値や未確認の前提と混同しない |
| 前提 | 計画時点で真と仮定するが、未成立なら要求・要件・設計を再評価する条件 | 検証済み事実または恒久的制約として扱わない |
| 対象外 | 今回の変更が責任を負わない範囲と、その除外理由 | 未検討、記入漏れ、将来対応という語だけで除外しない |
| 受け入れ条件 | 個々の要件が満たされたかを利害関係者の観点で真偽判定する条件 | Gherkin例やテストコードそのものではない。実行可能な受け入れ例とテスト結果を判定証拠にする |
| 設計 | 要求・要件を満たす責務、境界、依存方向、インターフェース、データ、状態、失敗、復旧への写像 | 要求・要件・受け入れ条件を下流都合で再定義しない |
| 設計判断 | 選択肢、採否、根拠、帰結を伴う具体的な選択 | 長期かつ横断的な判断だけを必要に応じてADRへ分離し、未決事項を決定済みにしない |
| 実装計画 | 承認済み設計を実現する、依存順・risk比例検証・最小変更・仕様更新・rollbackを持つ実行task列。fullは03、quickとpocは集約00が所有する | 新しい要求や設計判断を計画内で暗黙に追加しない。実装中の発見はモードが所有する実装計画へ事実・影響・判断・対処・検証・仕様更新を追記する |
| 実装 | 設計と計画を具体化するコード、設定、データ、migration等の変更 | 文書上の宣言や未実行の計画を実装済みとしない |
| システム仕様書 | 現在の対象版について、外部振る舞い、構造、データ、非機能、安全、運用等の成立中のシステム契約を保持する耐久的な正本 | 案件内だけの検討経緯、未来のtask、未採用案、実装レビュー記録を混入しない |
| 検証証拠 | 要件・受け入れ条件・仕様への適合を、対象版・SHA・コマンド・結果・観測元へ結び付けた再確認可能な記録 | 実行していない主張、別headの成功、自己申告だけを証拠にしない |
| 正本 | その情報について更新権限と競合時の優先権を持つ一意な情報源 | 同じ契約を複数文書へ複製して独立更新しない |

変更単位の成果物は`要求 → 要件・受け入れ条件 → 設計・設計判断 → 実装計画 → 実装・検証証拠 → レビュー`の順に詳細化する。システム仕様書はこの直列工程の一時成果物ではなく、承認された変更によって更新される現在状態の正本である。下流で上流の不足・矛盾・新事実を発見した場合は、その場で意味を上書きせず、事実と影響をfullは03、quickとpocは集約00へ記録して前進し、契約が変わる場合だけ所有する成果物の影響部分と追跡を再確定する。`quick`と`poc`は1ファイルへ集約しても、この論理境界と依存方向を維持する。

## ドメイン用語台帳

業務・システム固有の用語はDDDのユビキタス言語として継続管理する。現在有効な定義の正本は生成後の`docs/specs/01_システム概要/02_用語・略語.md`とし、00は変更で発見した候補語、01は要求・business ruleと対応付けて確定した用語差分を所有する。未実装の候補を現在有効な仕様へ混入させない。

- 作業開始時に既存の用語台帳を読み、既存IDを再利用する。全用語をIssueへ複製せず、追加・意味変更・改名・廃止する差分と、変更で参照する既存IDだけを記録する。
- 用語ID、標準語、定義、種別、境界づけられたコンテキスト、成立例・反例、類義語・禁止表現、根拠となる要求・business rule・一次資料、owner、状態、適用版を追跡する。
- 同じ表記でもコンテキストごとに意味が違う場合は別IDにする。複数コンテキストをまたぐ共有語は各ownerの意味と変換境界を明示し、曖昧な全体共通定義を作らない。
- 状態は`candidate / active / deprecated`とする。`candidate`は要求・要件の検討用で、実装済みの正本ではない。`deprecated`は削除せず、置換先、互換期間、廃止理由を残す。
- 設計、API・CLI、データ名、UI文言、ログ・診断、テスト、運用手順は標準語と用語IDへ整合させる。新語や意味変更を下流で発見した場合は事実と影響をfullは03、quickとpocは集約00へ記録し、影響する用語契約、business rule、仕様、実装、テストだけを再確定する。
- 実装後は用語差分を耐久用語台帳と仕様変更履歴へ反映し、レビューで未定義語、同一コンテキスト内の重複定義、根拠なしの意味変更、置換先なしの廃止、成果物間の表記揺れをfindingにする。

## ユースケース単位の設計と詳細化

この節は「どの単位で設計し、どこまで同時に詳細化するか」の正本である。Step 2、Step 5、Step 6はここへ参照する。**記入欄と、記入時に守る条件は`templates/specs/`の各categoryが所有し、この節はその本文を複製しない。** 工程の判断だけをここで決め、条件の本文が要るときは所有するtemplateを名指しする。

**全体を先に粗く揃え、今回届ける1単位だけを縦に詳細化する。** 機能、画面、バッチ、外部interface、dataの一覧と、コンテキスト境界と、横断方針を先に粗く揃える。そのうえで今回届ける業務をユースケース1件として選び、そのユースケースが通る機能、画面、ジョブ、API、dataだけを同時に詳細化して完成させる。全categoryを毎回すべて埋めない。

**ユースケースは業務の達成単位、シナリオは前提・操作・観測結果を持つ具体例である。** 両者を同義語として扱わない。ユースケース定義の正本は生成後の`docs/specs/01_システム概要/01_業務・利用者フロー.md`、ユースケースと機能・画面・ジョブの対応の正本は`docs/specs/15_要件追跡/00_追跡表.md`とし、各詳細はそこを参照する。

**詳細化する範囲は、そのユースケースが実際に通る要素に限る。** 画面を持たないsystemはAPI、CLI、イベント、時刻を起点にする。多対多の対応と条件付き適用の記入条件は`templates/specs/15_要件追跡/00_追跡表.md`が所有する。

**受付や画面操作の成功を業務完了と同一視しない。** ユースケースの事後条件は業務として成立した結果で書く。確定や配達が非同期で別のユースケースになる場合は、依存と、完了を観測する方法を明示する。

**構造妥当性と業務妥当性を別の責務へ割り当てることを、実装より前に設計で決める。** 責務の記入条件は`templates/specs/03_アーキテクチャ/00_全体構成.md`、`templates/specs/06_外部インターフェース/01_共通契約.md`、`templates/specs/14_開発・品質/01_コーディング標準.md`が所有する。

**ユースケースの対応にも、未実装を現在仕様へ混入させない既存規則を適用する。** Step 2からStep 8の時点の対応はIssue成果物が所有し、実装が成立したStep 9で`docs/specs/`の正本へ反映する。仕様更新の判定と証拠は[02_品質基準.md](02_品質基準.md#仕様整合性)が所有する。

## レビュー配置と前向きな変更処理

Step 3と7は高コストな品質レビューではなく、次工程を開始できるかを確認するreadiness checkである。未決事項、矛盾、受け入れ不能、security境界不明など次工程を成立させない事項だけをその場で修正し、exact-head、独立review、最大3ラウンドの有限レビュー契約はStep 10の実装済み差分へ一度だけ適用する。予算3ラウンドとは別枠で、収束後にHEADが動いたときの取り直しを1ラウンドだけ許す。通算4ラウンドを超える自動拡大は行わない。

**`pr create`より後に届いた外部reviewerの指摘は、条件を満たす場合に同じPRへ取り込む。**

守る性質は「**独立reviewerが確認した内容とmergeされる内容が一致すること**」である。この性質は、HEADが動いたときに同sessionの次roundで再reviewすれば保たれる。**封じていたのは記録側だけであり、性質そのものではなかった。**

取り込みは次をすべて満たす場合に限る。

1. **是正は前進commitで行う。** amendとforce pushを使わない。`review round`は前roundのcandidate HEADがancestorであることを要求するため、前進commitでのみ次roundを開ける
2. **次roundを記録して収束させる。** 予算は既存の有限レビュー契約（同一scope最大3ラウンド、収束後の取り直し1ラウンド、通算4ラウンド）をそのまま使う。**予算を超える指摘はfollow-up Issueとする**
3. **review artifactの`H_impl`を新しい実装commitへ直し、artifactだけのcommitで載せる。** `audit:check`は`比較基点..H_impl`の差分path集合と個別監査表の一致、および`H_impl..current`がreview artifactだけであることを引き続き要求する
4. **Step 10を`workflow record --step=10 --post-terminal-intake`で再記録する。** この記録はStep 11より後に置き、順序判定から外す。**記録は残す**
5. **元のPRのreviewスレッドへ判定を返信して解決する。** 指摘を無記録で通過させない

**予算を超えた場合、受け入れ条件を満たさない場合、または安全境界・authority・不可逆操作へ及ぶ場合は、follow-up Issueとする。** 新しいstagingと新しいworktreeで完全な工程を通す。元のPRのreviewスレッドへは判定と分離先を返信して解決する。

実装中に問題や新しい事実を発見しても、要求から全工程を自動的に再起動しない。契約を変えない発見は、fullは03、quickとpocは集約00へ`発見ID / 事実 / 影響 / 判断 / 対処 / 検証 / 仕様更新`を追記して実装を継続する。契約変更時は`workflow assess-discovery --input=<JSON>`に現在モード、目的・scope・AC・security境界・不可逆操作の変更、`changedContractKinds`（domain invariant、requirement、interface、data、design responsibility、non-functional、operations）、根拠付きcanonical失格条件`{ id, evidence }[]`を渡し、出力された影響成果物だけを再確定する。`full`の目的・scope変更は00と影響する01〜03、その他の契約変更は01〜03、`quick`と`poc`の通常変更は集約00だけを対象とする。quickのsecurity境界拡大・不可逆操作・失格条件は`workflow promote-full`で同じIssue・tracker・履歴を維持してfullへ単調昇格する。PoCの同じ発見では判定だけで成果物を変更せず、停止または明示的な`workflow promote-full`のどちらかを記録する。昇格時は元の`requestedMode`を保持した正規モード判定、昇格前00・モード判定、発見Evidence、full用00〜03をstagingへ保存する。staging単位の排他lockと永続transaction markerにより複数file更新を保護し、process停止後は再実行でrollbackまたはcommit確定を完了する。既同期なら`promotion-active`、未同期なら`local-active`とし、fullのStep 2〜10を補完する。Issueの再起票、変更のない成果物、完了済み調査をやり直さない。

Step 9は実装の成立状態をmerge前に`docs/specs/`へ反映する。Step 10は実装中発見記録、コード、test、システム仕様書が一致するexact-headをreviewし、session ID、latest round digest、HEADをjournalへ固定する。review後にHEADが変われば同sessionの次roundで実Gitの修正差分だけを再reviewし、新しいStep 10 bindingが無いPR作成を拒否する。reviewで修正した場合も変更範囲と隣接依存だけを再検証し、上流工程全体へ戻さない。目的または受け入れ契約が変わった場合だけ前段落の再確定を適用する。

成果物の依存方向は`要求 → 設計 → test → 実装 → review → PR`とし、設計時にtopological orderと循環反例を確認する。headが変われば、そのheadに依存するtest・CI・review・PR証拠を失効させる。修正loopは同一scope最大3 review round、単調revision、明示終了条件を持ち、以前の証拠へ逆向きに依存させない。

拡張はpreview、正確な対象、適用直前の再確認、適用、読取確認、rollbackを合成する。candidateはtrusted条件を自己緩和できない。外部障害時はlocalの安全な実装・test・記録を継続し、外部必須操作だけを保留する。詳細な構造とversion契約はschemaと`docs/specs/`を正本とし、この規範文書へ複製しない。

## ASC本体の是正を作業scopeへ入れない

**開始時に承認したcanonical Issueの目的にASC本体の保守を含まない作業では、実行中に発見したASC本体の欠陥・矛盾・使いにくさを、当該作業のscopeへ追加して是正しない。この禁止に例外を設けない。** ASC本体とは、配布される規範文書、schema、CLI、検査、template、project policy機構を指し、利用projectがASCを用いて作る成果物を含まない。scopeの拡張、candidateによる自己許可、別roleへの付け替えを例外として認めない。

**目的にASC本体の保守を含むIssueは、この禁止の対象ではない。** 対象外であって例外ではない。ASC本体の是正は、別Issueとして別scope・別履歴・owner決裁のもとで開始する。**この区別を欠くと、ASC本体を保守する手段そのものが失われる。**

**「ASCに従う」と「ASCを直す」は別である。** 前者は必須で、後者は非保守Issueのscope外である。この2つは実行中に混同されやすい。ASCに従おうとして矛盾に当たると、矛盾の解消が「従うために必要な作業」に見えるためである。次で区別する。

- **必須**: その作業の成果物をASCの契約へ合わせる。成果物が検査に落ちたら成果物を直す。
- **scope外**: ASC本体を直す。検査の側、規範文の側、機構の側を直す。

**検査を通すための変更が、検査が無ければ弁護できない変更になる場合、それは成果物側の是正ではない。** 検査を通すためだけの弱化、観測する量の置き換え、実質を持たない充足はいずれもこれにあたる。この場合は成果物を歪めず、下の経路へ入る。

ASCの欠陥で作業が進まない場合は次の順に扱う。**迂回しない。** 未許可の操作、candidateによる自己許可、別roleへの付け替え、未許可のsource編集で先へ進むことは、いずれもこの経路に含まれない。

1. **停止する。** 進まない事実を確定させ、権限外の手段で回避しない。
2. **記録する。** fullは`03_実装計画.md`、quickとpocは集約`00_要求定義.md`へ、発見として事実と影響を残す。
3. **別Issueへ分離する。** ASC本体の是正は独立した変更単位として起票する。
4. **owner決裁を仰ぐ。** 決裁が扱うのは、分離したIssueの承認・延期・却下、修正版ASCの反映後に元作業を再開すること、元作業を中止することである。**元Issueのscope内でASC本体を直す許可を含まない。**

**上の4項は禁止の例外ではない。** 禁止を保ったまま前へ進むための経路であり、非保守Issueのscope内での是正を許す条件ではない。

**作業を止めない軽微な矛盾は、記録と別Issueの起票だけを行って作業を継続する。** 進める欠陥のたびに停止してowner決裁を待つと、この規則自体が新しい作業妨害になる。停止とowner決裁は、記録と起票では進めない場合に限る。

**軽微かどうかは判断ではなく次の3条件で決める。すべて満たす場合だけ軽微とする。**

1. その欠陥を是正せずに、当該作業の受け入れ条件をすべて充足できる。
2. 充足のために成果物を歪めない。**検査を通すための弱化・観測量の置き換え・実質を持たない充足を要するなら軽微ではない。**
3. 安全条件、authority分離、fail-closed不変条件のいずれにも触れない。

**1つでも偽、または不明なら軽微としない。** 不明を軽微へ倒さないのは、ASCが他の判定で採るfail-closedと同じ理由による。判定は当該作業を実施するroleが行い、判定の根拠を記録へ残す。**判定が割れる場合は軽微としない側へ倒す。**

**ASCへの改善提案と別Issueの起票は禁止しない。** 禁止するのは非保守Issueのscope内での是正だけである。報告まで止めるとASC本体の欠陥が残り続け、同じ作業妨害が次の利用者にも起こる。

**この規則の強制はreviewが担う。** 目的にASC本体の保守を含まないIssueのPR差分にASC本体のpathが現れた場合、reviewerはそれをfindingにする。違反は差分のpath集合とIssueの目的の突合で現れ、機械による自動照合は現時点で存在しない。

この節はscopeの規律だけを所有し、[00_運用ポリシー.md](00_運用ポリシー.md)が持つ安全条件、authority分離、fail-closed不変条件を緩和しない。ASC本体の是正をscope外とすることは、それらの検証を省略してよいという意味ではない。

## 提出とライフサイクル

`workflow assess-discovery`の入力は`DISC-`で始まる安定`discoveryId`を必須とし、出力の7記録fieldへ同じIDを引き継ぐ。`workflow promote-full`は既定でpreviewし、`--apply`指定時だけ適用する。delivery stateが作成済みのstagingは昇格を拒否し、既存終端を新しいdelivery epochとして再利用しない。

createとmergeのprovider call直前に永続dispatch claimをfsyncし、claim消費後はprovider応答が不明でも再送しない。PR作成後binding前にbaseが前進した場合も既存PRのread-only照合を先に行い、一致するclosedまたはmerged PRを観測したら重複PRを作成しない。exact absenceでもbaseが固定値から前進済みなら再送せず照合待ちにする。

classic protectionの代替にrulesetを用いる場合、PR、required status checks、署名、non-fast-forward、linear historyのいずれかを拘束する規則だけを保護Evidenceにする。deletionだけのrulesetをprotectedと判定しない。

**レビュー成果物は版管理下へ置く。** 一時ステージングはStep 0の性質どおり版管理外であり、そこに置いたままではmerge認可もStep 11も成立しない。ステップ10で`04_レビュー.md`を埋めたら、`docs/reviews/`または`.agent-skill-chain/reviews/`配下へ複写し、実装commitの後にその1 fileだけをcommitして`H_final`にする。`review evidence`と履歴監査はこのcommitされたfileを読む。ステージングへ置いたままにすると、成果物が独立approverから見えず、git外で書き換えられ、同一actorの自己申告になる。

merge認可は、review artifact直前の`H_impl`、artifactだけを加えた`H_final`、artifact path/digest、PRに直接関連する成功CI run ID、`H_final`への独立approval IDを固定する。PR authorと`H_impl` commit authorのstable IDを必須とし、actorごとの最新の承認状態変更eventだけから独立approvalを選ぶ。`COMMENTED`は承認状態を変更しないため、後続コメントだけで`APPROVED`を失効させない。実装者の判定は`H_impl`のcommit authorで行い、artifact commit authorと混同しない。

Step 11 journal保存後のcrash復旧は、保存済みartifact inventoryとcontent digestが現在値に一致する場合だけstateを前向きに復旧する。未記録の改変を新しいdigestとして追認しない。

状態遷移は`ステップ10のレビュー → 仕様整合性 → PR → delivery policy判定 → mergeまたは明示停止 → 完了処理 → 後片付け`とする。`pr create`はマージ・後片付けを同じ外部操作へ連鎖しないが、ASCの進行役は`automatic`のfull/quickをPR作成成功だけで正常終了と報告しない。automaticの`pr create`は`merge_pending`を返してStep 11を未記録とする。`pr merge`はPR作成時と同じstagingを必須とする独立コマンドで、PoCを拒否し、既定ブランチ上の信頼済みポリシーとGitHubの最新状態を検証する。auto-merge要求またはmerge queue entryは`merge-observed`の進行状態として保持し、providerから`merged`とmerge commit SHAを再観測した後だけStep 11を記録する。無期限の繰り返し確認をせずGitHub標準の自動マージ・マージキューを優先する。PoCと`merge.mode=disabled`は`outcome=pull-request`のStep 11終端とする。`assisted`のauthority未成立は終端ではなく`pr-bound`の再開可能な待機であり、Step 11を記録しない。

Step 11の外部副作用は同じIssue staging内の`journal/delivery-state.json`をwrite-ahead状態として使用する。PR create intentより前にproviderのwrite authority、既定branchとtip、remote head SHAを観測し、指定repository・base、trusted policy commit、exact HEADと一致させる。その後、repository、canonical IssueとURL、head ref/SHA、base refと作成時base SHA、canonical title/body digest、本文のclosing契約digestを`create-prepared`として耐久化する。作成後のprovider read-backでrepository、PR番号・URL、canonical Issue、same-repositoryかつcross-repositoryでないhead repository、head ref/SHA、canonical title/body、base ref、closing Issue 1件を再照合し、同じidentityを`pr-bound`として固定する。通常のbase SHA前進は許容するがbase refは変えず、merge時のprovider default branch tip、PR base SHA、trusted policy commitを一致させなければならない。classic branch protectionがない場合はexact branchへ適用されるactive rulesetも読み、両方を観測できない場合はfail-closedとする。

merge直前に固定HEADへchecks・review・policy・methodを再認可し、外部merge要求より前にmethod、認可HEAD、intent IDを`merge-prepared`として耐久化する。timeout、通信切断、応答解釈不能など副作用の成否が曖昧な場合は同じ要求を再送せず、固定identityを使ったprovider read-backだけで照合する。副作用を一度も要求していないprepared intentについてprovider上の該当PR、auto-merge、queue entryが存在しないことを決定的に確認できた場合だけ、同一のimmutable intentを一度再試行できる。曖昧状態または`reconciliation-required`では再試行しない。一意に確定できなければ人へ返す。journalを先にfsyncし、そのdigestをdelivery stateへ保存する。journal保存後・state保存前に停止した再実行は、同じStep 11 entryからstateだけを前向きに復旧し、PR create、merge要求、journal追記を重複させない。delivery stateの書込先は当該projectが検証したIssue stagingだけとし、project外、別Issue、symlinkを介するstagingをprovider呼出し前に拒否する。

GitHubの通常merge APIが提供するcompare-and-setはPR HEADに対するものだけで、PR本文やbase tipを同じ要求内で固定するCASはない。ASCは外部merge直前の二重read、`--match-head-commit`、provider保護規則、直後read-backで窓を最小化するが、認可済みの別writerが最終readとprovider処理の間に本文またはbaseを変更する競合は予防できず、事後検出して`reconciliation-required`として扱う。この制約を「完全に防止した」と報告しない。

| head allowlist | PRのhead branchがmergeを許されるかの判定 | `*`をワイルドカードとする照合。`feature/*`は`feature/x`に一致する |
| 長命branchペアの判定 | baseとheadの双方が長命branchかの判定 | 完全一致 |
| 長命branch警告のbase候補 | squashまたはrebaseだけを許す設定への警告 | 完全一致。**ワイルドカードを含む要素はbaseにならないため候補から外れる** |

**主用途はhead allowlistである。** `pr merge`はheadがここに一致しないmergeを拒否するため、作業branchからmergeする運用では短命branchのpatternを列挙する。`worktree.allowedBranchTypes`と揃える。長命branchだけを列挙すると作業branchからのmergeが全て拒否される。

**長命branch警告は、ワイルドカードを含まない要素が2件以上あるときだけ発火する。** 短命branchのglobだけを列挙した構成では発火しない。squashまたはrebaseは長命branch間の親子関係を保存せずmerge-baseを進めないため、次回以降に取り込み済みの変更まで未取り込みと判定され、恒常的な全面衝突と誤った衝突解決による変更巻き戻しを招く。`branchMethods`はbase branchに一致する全entryのmethods積集合を使い、どのentryにも一致しない場合だけglobalな`merge.methods`へ戻る。branch単位指定はglobalな許可を拡大できない。

canonical Issueの受け入れ条件を完了させるPR本文は`Closes #番号`で1回だけ参照し、GitHubのmerge連動で自動closeする。後続作業または非終端の関連Issueは別Issueへ分離して`Relates to #番号`で参照し、`Close / Closed / Closes / Fixes / Resolves`を使用しない。ブランチ削除、release、package公開はroot更新、対象worktreeの後片付け、Issue自動closeと連鎖させず、それぞれの権限で実行する。

完了処理はworktree・ブランチ・基点・パス、変更済み・未追跡・stash・一時・無視対象、コミット・push・リモート、PRマージ、仕様、テスト、レビュー、復旧方法を検査する。危険または状態変化時はworktreeを保持する。

新規プロジェクトだけがコードより先に`docs/specs/`を生成できる。既存プロジェクトは明示的な導入操作を要求する。デザイン・レイアウトトークン、Mermaid図、ドメインUUIDは条件付きである。ADRは`docs/adr/`と任意の`related_adrs`という将来拡張点だけとし、サブシステムを実装しない。
