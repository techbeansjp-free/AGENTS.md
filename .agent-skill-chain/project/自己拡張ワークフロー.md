# 自己拡張ワークフロー

## 目的・前提

本リポジトリの自己拡張は GitHub Coordination Backend を使う。GitHub Issue が要求と進行の集約先、branch と PR が変更の集約先、Check Run がゲートの正本である。実行可能な規約・スキーマ・テンプレートは AGENTS.md と `.agent-skill-chain/` 配下にあり、存在しない別の asset tree は参照しない。

## Issue から PR まで

1. GitHub Issue の番号、作成日時、type、slug から `issue start` で専用 branch/worktree を作る。
2. writer lease を取得し、worktree root に `SPEC.md` を作る。checkpoint で commit/push した後、Draft PR を作成する。PR 本文には `Closes #<id>` を含める。
3. 同じ branch で `DESIGN.md` と `PLAN.md`、実装とテスト、`VALIDATION.md` を追加し、各セグメントを checkpoint する。
4. 各 Check Run の承認後に Draft PR を Ready for review にし、必要な CI が成功した PR だけを merge する。

## 記録と追跡

GitHub-native は「ローカル文書を無追跡にする」という意味ではない。このリポジトリでは、4 セグメント成果物を branch に追跡して remote push する。これにより Issue の要求、設計、実装、検証の証跡を PR と Git 履歴から復元できる。

一時メモ、ローカル editor 設定、依存ディレクトリ、ビルド済み CLI は `.gitignore` に従い追跡しない。過去の `docs/maintainer/workflow/close/` は完了済み作業の履歴であり、新規 Issue の作成場所・規範・テンプレートではない。

## close

merge により GitHub Issue が close され、branch 上の 4 成果物が default branch の Git 履歴へ入る。worktree の削除は、PR が merged で、writer lease が無く、未 commit・未 push の変更が無いことを確認してから `cleanup` を使う。close 後も必要な追跡情報は GitHub Issue、PR、main の履歴に残る。
