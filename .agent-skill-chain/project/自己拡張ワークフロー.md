# 自己拡張ワークフロー（このリポジトリ固有・最優先）

**目的**: 本リポジトリは「パッケージの正本」かつ「自己拡張（ドッグフーディング）する消費者」の二役を兼ねる。両者は git の扱いが逆になるため、名前空間を分離して二重管理・配布物汚染を防ぐ。

このファイルは `.agent-skill-chain/project/` 配下にあり、**`.agent-skill-chain/source/` および CLAUDE.md の標準フローより優先**される（[../.agent-skill-chain/project/README.md](README.md) §優先順位）。

## issue の作成場所（標準フローの上書き）

CLAUDE.md / `.agent-skill-chain/source/` の標準では issue を `.agent-skill-chain/runtime/<timestamp>_<title>/` に作るが、**本リポジトリでは下記に作成する**。

| 種別 | 作成場所 |
|------|----------|
| 単一 issue | `docs/maintainer/workflow/<timestamp>_<title>/` |
| サブ issue（PR 指摘対応等） | `docs/maintainer/workflow/{parent}/90_issues/{ディレクトリ名}/` |

- `<timestamp>` は実行環境の現在時刻（JST）。例: `TZ=Asia/Tokyo date +%Y%m%d_%H%M%S`。
- ファイルセット（`00_要求定義.md`・`01_要件定義.md`・`02_設計.md`・`03_実装計画.md`・`04_review.md` 等）は `.agent-skill-chain/runtime/templates/` の標準テンプレートに従う。
- これらは **git 追跡対象**であり、自己拡張の開発記録として残す。

## GitHub Issue 起票ゲート（具体手順）

**抽象原則（ゲートの存在・位置・強度・分岐・記録の必要性・declined バリデーション・enforcement #34）の正本は `.agent-skill-chain/source/`**（[skills/agent/run_command.md §Constraints](../source/skills/agent/run_command.md)・[commands/implement-feature.md §実行時の注意](../source/commands/implement-feature.md)・[workflow/PHASES.md §レビュー成果物の配置ルール](../source/workflow/PHASES.md)・[enforcement/README.md](../source/enforcement/README.md) #34）である。本節はそれらが委ねる**具体手順**（起票要否のユーザー確認・`gh` コマンド・title/body・frontmatter 形式・declined 記録形式・PR トレーラ・対象外環境の具体判定）のみを定義する（配置境界＝コア抽象／project 具体・02_設計 ADR-5）。

**実行主体（進行役限定）**: 本節の `gh issue create`（起票）をはじめ、`git push`・`gh pr create` 等の外部書き込みコマンドの**実行主体は進行役**である（承認の直接性を実行主体に持たせる原則。準備＝コマンド文面・body の作成はサブ、最終確認＋実行のみ進行役）。原則・対象/非対象の境界の正本は [skills/agent/run_command.md §外部書き込み操作の実行主体（進行役限定）](../source/skills/agent/run_command.md) とし、本節に原則本文を重複させない（配置境界＝コア抽象／project 具体）。

適用対象は**トップレベル issue のみ**（`90_issues/` 配下のサブ issue は対象外。親 Issue のチェックリスト/コメントに集約する・ADR-6）。**ただし、親ワークフロー自体に対応するトップレベル GitHub Issue が存在しない場合**（例: 横断的な自己点検・監査から生まれた `90_issues/` で、起点となる GitHub Issue が無いケース）は、集約先が存在しないため、サブ issue であっても本ゲート（#34）の通常手順（デフォルト起票）に従い独立して起票してよい（ADR-6 補足）。review-docs 完了後・implement-feature 委譲前に実行する。**デフォルトは起票**であり、既存 Issue が無い場合はユーザーへ起票するかを確認する。issue 化が不要とユーザーが判断した場合は起票せず、その決定と理由を記録する（免除ではなく代替記録＝記録なし・理由なしのスキップは不可・ADR-1）。ゲート通過には「実 Issue 番号の記録」または「理由付き declined の記録」のいずれかが必要（コア audit.sh #34 が理由なし declined を弾く・ADR-7）。

### 1. 既存 Issue 有無の判定（Query）

1. **第一情報源**: 対象 issue の `00_要求定義.md` frontmatter の `github_issue` キーを確認する。
   - 値が非 null（例: `"#123"` や URL）であれば既存とみなし、手順 4（記録）へ進む。**新規起票はしない。**
   - 値が `null` または欠落していれば、次のフォールバックへ進む。
2. **フォールバック（null/欠落時のみ）**: `gh issue list --repo <owner>/<repo> --search "<issue のタイトルや要求定義の主題>"` で類似 Issue の有無を照合する。一致する Issue が見つかった場合はその番号を採用し手順 4 へ進む。
3. **フォールバック（照合でも不明な場合）**: ユーザーへ「対応する GitHub Issue が既に存在するか」を確認する。既存があればその番号を採用し手順 4 へ進む。既存が無ければ手順 1.5（起票要否の確認）へ進む。

自動推測（frontmatter にもコメントにも根拠が無いのに Issue 番号を憶測する）は禁止する（02_設計 ADR-2）。

### 1.5 起票要否のユーザー確認（Query・既存が無い場合）

既存 Issue が無いと判定された場合、**デフォルトは起票**である。ユーザーへ「この issue を GitHub Issue に起票するか」を確認する。

- **起票する**（既定）: 手順 2（新規起票）へ進む。
- **起票しない**（ユーザーが「issue 化は不要」と判断）: 手順 2 を飛ばし、手順 4.5（起票しない場合の理由記録）へ進む。

判断がつかない場合は起票（既定）に倒す。無記録・無確認のまま implement へ進めてはならない（ADR-1）。

### 2. 新規起票（Command・既存が無く起票する場合のみ）

```bash
gh issue create --repo <owner>/<repo> \
  --title "<00_要求定義.md の「プロジェクト名」と同一の短い表題>" \
  --body "$(cat <<'EOF'
## 概要
<00_要求定義.md の「目的」「成功基準」を 2〜3 文で要約>

## 参照
- docs/maintainer/workflow/<issue ディレクトリ>/00_要求定義.md
EOF
)"
```

- title は 00_要求定義.md の「プロジェクト名」と一致させる（トレーサビリティ確保）。
- body に**内部パスの参照は含めてよい**（GitHub Issue 本文は本リポジトリの内部運用ドキュメントであり、PR 本文の内部参照禁止＝enforcement #6 の対象外）。
- `gh issue create` は標準出力に Issue の URL を返す。URL 末尾の数字が Issue 番号である。

### 2.5 起票直後の書き戻し（必須手順・取りこぼし防止）

**背景（事故事例）**: 進行役が実際に `gh issue create` で GitHub Issue を複数件作成した際、発行された Issue 番号のローカルへの書き戻し（`00_要求定義.md` frontmatter の `github_issue` への記録）を失念する事故が起きた。原因は「起票フォーマット」（§4 実 Issue 参照・§4.5 declined）は定義済みだったが、「起票した**直後**に、誰が・どうやって・必ずローカルへ書き戻すか」という手順そのものが明文化されていなかったことにある。以下を必須手順として明記する。

1. **起票直後の書き戻しを必須手順とする（同一タスク内で完結）**: 実際に GitHub Issue を起票した場合（`gh issue create` 等）、発行された Issue 番号/URL を、**起票と同一のタスクの中で**、当該ローカル issue の `00_要求定義.md` frontmatter の `github_issue` キー（§4 の形式 `"#<番号>"`）へ記録すること。**起票のみ行い、書き戻しを別タスク・後回しにすることを禁止する**（取りこぼし防止）。
2. **委譲の明記**: この書き戻し作業（`00_要求定義.md` の編集）は**成果物編集**であり、**メイン（orchestrator）が直接編集してはならない**。必ずサブエージェントへ委譲すること（[../source/boot/CORE.md](../source/boot/CORE.md) §メインがやってはいけないこと 準拠）。
3. **複数 issue を一括起票する場合**: 複数のローカル issue を一括して GitHub Issue 化する場合も、**1 件ごとに「起票 → 書き戻し」を完結させてから次の issue へ進む**か、**全件起票後に一括で書き戻しを行う場合は、書き戻し漏れが無いことを（発行された Issue 番号一覧）と（書き戻し後の各 00_要求定義.md frontmatter の github_issue 値）を突き合わせて検証**すること。1 件でも突き合わせが取れなければ、当該 issue の書き戻しは未完了とみなし、完了するまで次の作業（implement-feature 委譲等）へ進んではならない。
4. **機械検知の限界**: コア audit.sh #34 は「`github_issue` が空/理由なし declined でないか」は検知できるが、「実際に起票したのに書き戻しを忘れた」という手順違反そのもの（＝GitHub 側には Issue が存在するのにローカルが無記録の状態）を、そのタイミングでは検知できない場合がある（audit は implement-feature ログが記録された後に走る近似検知であり、書き戻し漏れの直後には走らない）。したがって本節の手順を遵守することが、この事故の**唯一の予防策**である。

### 3. 対応判定・到達性（Query・具体）

- `gh` の可用性: `command -v gh` で確認する。
- 認証: `gh auth status` で確認する（未認証・トークン失効時は「対象外環境」ではなく「一時障害」として §5 の手順に従う）。
- `git remote`: `git remote -v` に `github.com` を含むかで GitHub 採用を判定する（コア audit.sh #34 の SKIP 判定と同一シグナル・ADR-4）。
- 上記いずれかが「恒久的に GitHub 非採用」（`git remote` に github.com を含まない）と判定できる場合のみ、ゲートを非発火とする。`gh` 未認証・一時的な API 障害は「対象外環境」と区別し、非発火にはしない（§5 参照）。

### 4. 番号の記録（Command）

**§2.5 の必須手順（起票と同一タスク内で書き戻し・サブエージェントへ委譲）に従うこと。** `00_要求定義.md` frontmatter の `github_issue` へ、確定した Issue 番号を `"#<番号>"` 形式（例: `"#123"`）の文字列として記録する。

```yaml
github_issue: "#123"
```

- 既存にリンクした場合・新規起票した場合のいずれも、記録形式は統一して `"#<番号>"` とする（URL は記録しない。番号のみで `gh`/GitHub UI 双方から一意に解決できるため）。
- frontmatter 更新後、書記（write-workflow-log）による記録は不要（`github_issue` は成果物 frontmatter 自体が記録面であり、audit #34 がこれを直接検査する。00 の変更自体は通常の implement-feature 証跡の一部として扱う）。

### 4.5 起票しない場合の理由記録（Command・declined）

手順 1.5 で「起票しない」とユーザーが判断した場合、`00_要求定義.md` frontmatter の `github_issue` へ、**起票しない決定とその理由**を `"declined: <理由>"` 形式で記録する。

```yaml
github_issue: "declined: 設定ファイルの軽微な値修正のみで外部追跡が不要なため"
```

- `declined:` の後に、**なぜ issue 化が不要なのか**を非空の理由として書く（例: 「軽微なドキュメント typo 修正で追跡不要」「別 issue #45 に集約済み」等）。
- **理由なし（`"declined:"` のみ）・空白のみの理由は禁止**。コア audit.sh #34 がこれを FAIL として弾く（空虚なバイパス防止・ADR-7）。理由の内容妥当性は機械検知の対象外であり、AI 自律判断＋人手監査に委ねる。
- declined と記録した issue は GitHub Issue を起票していないため、後述の PR 本文 `Closes #<番号>`（§6）の対象外である（含めない）。
- frontmatter 更新後、書記による追加記録は不要（§4 と同様、`github_issue` 自体が記録面）。

### 5. API 一時障害・認証失効時の運用（確定）

- **一時障害の判定**: `gh issue create` / `gh issue list` / `gh auth status` がネットワークエラーまたは 5xx 相当で失敗した場合を「一時障害」、401/403 相当で失敗した場合を「認証失効」とみなす。
- **リトライ**: 一時障害は 30 秒間隔で最大 3 回まで自動リトライする。
- **エスカレーション**: リトライを尽くしても解消しない場合、または認証失効と判定した場合は、implement-feature への委譲を保留し、ユーザーへ「GitHub Issue 起票ゲートが API 障害/認証失効により完了できない」旨を提示して人手の判断を仰ぐ。**ロックアウト（永久に進めなくする）も黙認通過（記録せず先へ進める）もしない**。

### 6. PR 本文への Closes 埋め込み（契約）

対応 Issue 番号（`"#<番号>"` 形式）が `00_要求定義.md` frontmatter の `github_issue` に記録されている場合、当該 issue に関する PR の本文に以下を含める（GitHub 公式のマージ時自動クローズ仕様）。**`github_issue` が `"declined: <理由>"`（起票していない）の場合は対象外であり、`Closes` 行を含めない。**

```markdown
Closes #<番号>
```

- `<番号>` は frontmatter `github_issue` の値（`"#123"` → `Closes #123`）。
- CLOSEOUT の PR トレーラ規約と併記する場合、本行を他のトレーラと分けて記載してよい（内部参照禁止＝enforcement #6 は PR 本文の**リポジトリ内部パス**への言及を禁止するものであり、`Closes #<番号>` は GitHub Issue 番号でありパス参照ではないため抵触しない）。
- **この記載は enforcement #36（PR 紐づけ）で CI 検証される**。詳細な運用（許容キーワード・照合粒度・CI 限定性・本リポ CI の配線申し送り）は後述の「## ブランチ紐づけ・PR 紐づけの機械強制（具体手順）」を参照。

### 7. トークン取扱い（セキュリティ）

`gh` の認証はホスト環境の既存認証（`gh auth login` 済みの資格情報）に従う。トークンの実値を成果物・memo・`workflow.db`・ログ・本ドキュメントの記載例のいずれにも残さない。上記コマンド例に実トークンを埋め込まない。

### 8. プロジェクト全体でのゲート無効化トグル（`GITHUB_ISSUE_GATE_ENABLED`）

GitHub は使っているが Issue 運用自体を採用しないプロジェクト（GitHub 非採用環境の自動フォールバック＝ADR-4 とは別軸。`git remote` は github.com を指しているが、そのプロジェクトでは Issue トラッカーを使わない運用方針の場合）向けに、本ゲート単体をプロジェクト全体で無効化できる env `GITHUB_ISSUE_GATE_ENABLED` を用意する（02_設計 ADR-8）。

- **既定値**: `true`（ゲート有効）。未設定時は従来どおり動作する。
- **無効化**: `GITHUB_ISSUE_GATE_ENABLED=false`（`0`・`no`・`off` も同義）を設定すると、audit.sh #34 は他のどのガード（GitHub 採用環境判定・grandfather・declined 判定等）よりも先に SKIP する（最優先ガード）。
- **既存 `enforce on/off` との違い**: `enforce on/off` は enforcement 機構**全体**の opt-in/opt-out であり、本トグルは **GitHub Issue 起票ゲート（#34）単体**の無効化である。他の enforcement チェック（#29・#32 等）には影響しない。
- **設定方法**: CI 環境変数・シェル環境変数として設定する（`.env` やリポジトリ設定ファイルへの記載は本 issue のスコープ外。具体の設定手段は消費者環境に委ねる）。
- **本リポジトリでの扱い**: 本リポジトリ（AGENTS.md パッケージの正本・自己拡張元）は GitHub Issue 運用を採用しているため、**`GITHUB_ISSUE_GATE_ENABLED` は設定せず既定の `true`（有効）のままにする**。無効化は消費者ランタイム側の判断に委ねる機能である。
- **AI エージェントによる自律設定の禁止（参照）**: 本トグル（`GITHUB_ISSUE_GATE_ENABLED`）を含む enforcement ゲートの無効化 env（`*_GATE_ENABLED` 系）および grandfather env（`*_GATE_EFFECTIVE_FROM` 系）を AI エージェントが自律的に設定・変更してはならない（人間の明示指示がある場合のみ可）。正本は [../source/AGENT_CONDUCT.md](../source/AGENT_CONDUCT.md) §enforcement ゲートの自己無効化禁止。

## ブランチ紐づけ・PR 紐づけの機械強制（具体手順）

**抽象原則（紐づけの存在・記録タイミング・機械強制の存在・適用条件・grandfather）の正本は `.agent-skill-chain/source/`**（[skills/agent/run_command.md §Constraints](../source/skills/agent/run_command.md)・[commands/implement-feature.md §実行時の注意](../source/commands/implement-feature.md)・[enforcement/README.md](../source/enforcement/README.md) #35/#36）である。本節はそれらが委ねる**具体値・具体手順**のみを定義する（配置境界＝コア抽象／project 具体・02_設計 ADR-5/ADR-6/ADR-7/ADR-8）。

### 0. 作業ツリーの worktree 必須化（実装・変更作業の前提・§1 の前提条件）

本リポジトリでの**実装・変更を伴う作業**（`implement-feature` 相当、本ファイル §完了 issue の close 移動 の PR フロー、issue 文書（`00_要求定義.md`〜`04_review.md`）の新規作成・更新など、**ファイルを変更するすべての作業**）は、必ず `git worktree` で `main` から新規ブランチを切った上で行う。**メインの作業ツリー（worktree でない、通常の checkout）を直接変更してはならない。**

- **例外**: 読み取り専用の調査・レビュー（Read/Grep/Glob によるコード閲覧、PR コメントの確認等、ファイルを一切変更しない作業）は worktree 不要。基本原則は「実装・変更は必ず worktree」であり、判断に迷う場合は worktree を使う側に倒す。
- **下記 §1（ブランチ紐づけ）との関係**: worktree 作成はブランチ作成を伴うため、worktree で切った feature ブランチ名を、そのまま §1 の `branch` フィールドへ記録すればよい（worktree 用に新しい命名規則やタイミングを追加するものではなく、§1 が定義する記録対象ブランチと同一のものを指す）。§1 の「いつ記録するか」「どの値を書くか」の定義はここで重複再定義しない。
- **理由**: メインの作業ツリーを直接変更すると、複数タスクの並行実行時にチェックアウト状態が競合し、レビュー前の変更が `main` の作業ツリーに残留するリスクがある。worktree で隔離することで、常にクリーンな `main` を保ち、変更は必ず「ブランチ → レビュー → マージ」を経由させる。

### 0.1 worktree／ブランチの命名規則と配置（このリポジトリ固有・命名の正本）

worktree ディレクトリ名・ブランチ名は、命名から対応 issue（または目的）を追跡できるよう次の規則に従う。**本 issue（worktree 運用規律）完了時点以降に新規作成するものにのみ適用**し、既存のブランチ・worktree の遡及改名・移動は求めない（グランドファザリング）。

- **命名パターン**: `<type>/<YYYYMMDD_HHMMSS>-<固有名>`。
  - `<type>` は **feature / bugfix / hotfix / release / chore の 5 種**（Conventional Branch 準拠）。`<type>` と `<YYYYMMDD_HHMMSS>` の間の区切りは `/`。
  - `<YYYYMMDD_HHMMSS>` は既存のプレフィックス取得規約 `TZ=Asia/Tokyo date +%Y%m%d_%H%M%S` で得た値。`<YYYYMMDD_HHMMSS>` と `<固有名>` の間の区切りは `-`（`<YYYYMMDD_HHMMSS>` に `-` は含まれないため、最初の `-` が区切りに一意対応する。固有名内部の `-` はそのまま保持される）。
  - `<固有名>` は日本語可・パス区切り（`/`）や空白・`;`・`..`・先頭 `.`/`-`・末尾 `.lock` 等の危険文字不可・200 バイト以内（`validate_name` 相当）。
  - 例: `feature/20260716_143000-worktree運用規律`。
- **配置（`.worktree/` 一元化）**: worktree はリポジトリルート直下の `.worktree/` 配下に、ブランチ名パターンをそのままミラーした階層で作成する: `.worktree/<type>/<YYYYMMDD_HHMMSS>-<固有名>/`。
  - `.worktree/.gitignore`（`*` ＋ `!.gitignore` の 2 行）で配下の worktree 実体を追跡除外する。ルート `.gitignore` は変更しない。この雛形は `setup.sh`／`init`／`upgrade` が**未存在時のみ自動生成**する（`worktree-gitignore.template` から）。
  - 作成例: `git worktree add -b feature/20260716_143000-worktree運用規律 .worktree/feature/20260716_143000-worktree運用規律`。
- **機械強制の三層（Tier1/2/3）**:
  - **Tier1（PreToolUse hook・即時 reject）**: 作成形（`git worktree add`〈`-b` 無しの暗黙ブランチ名含む〉／`git switch -c/-C`／`git checkout -b/-B`／`git branch <name>`〈作成形のみ〉）の命名違反を hook が exit 2 で reject する（listing/削除/rename・曖昧・非 git は fail-open で通す）。正本は `enforcement/claude/PreToolUse.sh` の R7。
  - **Tier2（CI audit・事後検知）**: 全ローカルブランチ名を列挙し、grandfather baseline（`worktree-naming-grandfather.txt`）に無い非準拠名を audit #40 で FAIL する（`git branch -m` リネームや DWIM 由来等の hook 非捕捉経路のバックストップ）。
  - **Tier3（明示 allowlist で除外）**: `gh pr checkout` 由来の外部ブランチ名や既存名は grandfather baseline へ追記して救済する。plumbing 系・hook 非経由のシェル操作は完全網羅を目指さない（残余リスク）。
- **削除前 untracked 退避（C）**: `git worktree remove`（`--force` 含む）・`git clean -x/-X` の前に、hook（R8）が対象の untracked 成果物を退避先へ **copy 保全**してから削除を通す（2026-07-15 の未 commit 成果物ロスト事故の再発防止）。退避先は既定 `.claude/.worktree-trash/<YYYYMMDD_HHMMSS>_<worktree名>/`（env `WORKTREE_TRASH_ROOT` で上書き可）、保持期限は既定 14 日（env `WORKTREE_TRASH_RETENTION_DAYS`）で退避時 lazy purge する。**退避は block しない**（保全のみ・退避失敗でも WARN のみで削除は妨げない）。

**残余リスク・限界（隠さない）**:
- hook を経由しない削除経路（別プロセス・別ツール・エディタからの削除、`rm -rf`）は Tier1/退避の捕捉外。
- `validate_name` は ASCII 危険文字・制御文字のブラックリスト方式であり、Unicode 書式制御文字（ゼロ幅・双方向制御等）は通過しうる（本リポの固有名は保守者・エージェントが選ぶ値のため深刻度低と判断・スコープ外）。
- `.worktree` prune 規約（#39）は静的 grep のベストエフォート（1 行 find のみ・動的生成は検知外）。

### 0.2 `.worktree/**` 配下 close/** の deny ミラー（手動手順・自動配布されない）

`.worktree/` 配下にネストした worktree 内には、`docs/maintainer/workflow/close/**` 等の deny 対象ファイルが別経路で存在しうる。ネスト経由の deny バイパスを防ぐため、`.claude/settings.json` の `permissions.deny` に既存 `close/**` と**共存する形で**次の 3 エントリ（`close/**` のネスト部分のみに限定）を追加する。

```json
"Read(.worktree/**/docs/maintainer/workflow/close/**)",
"Grep(.worktree/**/docs/maintainer/workflow/close/**)",
"Glob(.worktree/**/docs/maintainer/workflow/close/**)"
```

- **対象をネストした `close/**` 部分のみに限定する理由**: パターンを `.worktree/**` 全体（worktree配下の全ファイル）とすると、worktree で作業する通常の subagent が正当な作業ファイルまで読めなくなる。対象を `close/**` のネスト部分のみに絞ることで、この副作用を避けつつ、ネスト経由のバイパス防止という本来の目的を達成する。トップレベルの `close/**` deny と同じく Read/Grep/Glob の3種とも対象とし、ネスト経由でのアクセス範囲をトップレベルと同一に保つ。
- **自動配布されない（重要）**: `enforce on`／`setup.sh` は `.claude/settings.json` の `permissions.deny` を管理しない（hook エントリのみ配線し、ユーザー設定は touch しない）。よってこの deny は**各採用先で手動ミラーする**必要がある（既存 `close/**` deny も同様に手動維持されている）。本リポジトリでも `.claude/settings.json` へ手で追記する。

### 1. ブランチ紐づけ（`branch` の記録手順・enforcement #35）

- **記録面**: 対象 issue の `00_要求定義.md` frontmatter の `branch` キー（新規 issue はテンプレートに既定値 `null` で用意される）。
- **いつ記録するか**: review-docs 完了後・**implement-feature 委譲前**に、この issue の実装作業に用いる feature ブランチ名を記録する。ブランチを切ってから（または切る決定をしてから）実装着手までの間に必ず書く。
- **どの値を書くか**: 実際に使う feature ブランチ名（例: `branch: "feat/some-feature"`）。値は文字列。空/`null`/`~`/キー無しは「未記録」として enforcement #35 が FAIL する。実ブランチ名との一致照合は行わない（記録の有無のみ検査。worktree・detached HEAD・CI checkout での揺れによる誤 FAIL を避けるため・02_設計 ADR-2）。
- **記録例**:

```yaml
branch: "feat/issue-branch-pr-linkage-enforcement"
```

- **書記の要否**: frontmatter 更新後、書記（write-workflow-log）による追加記録は不要（`branch` は成果物 frontmatter 自体が記録面であり、audit #35 がこれを直接検査する。00 の変更は通常の implement-feature 証跡の一部）。
- **発効日（grandfather）**: `BRANCH_LINK_GATE_EFFECTIVE_FROM`（既定 `20260713_000000`）未満の日時プレフィックスを持つ既存 issue には遡及適用しない。本 issue（`20260713_050350_...`）が適用第一号。
- **プロジェクト全体での無効化**: git ツリーでない・DB 非採用の環境では自動 SKIP する。GitHub 非採用でもブランチは成立するため github.com remote は要求しない（#34 との差分）。プロジェクト全体でゲート自体を無効化する場合は env `BRANCH_LINK_GATE_ENABLED=false`（`0`/`no`/`off` も同義・最優先ガード）。**本リポジトリでは設定せず既定 `true` のままにする**。

### 2. PR 紐づけ（PR 本文キーワード運用・enforcement #36・CI 限定）

- **記録面**: GitHub PR 本文（CI が `PR_BODY` として audit.sh へ渡す）。ローカルファイルではない。
- **何を書くか**: 対応 GitHub Issue への `Closes #<番号>` または `Refs #<番号>`（§6 の契約）。許容キーワードは `close`/`closes`/`closed`/`fix`/`fixes`/`fixed`/`resolve`/`resolves`/`resolved`/`ref`/`refs`/`references`（大小文字不問）で、直後に空白を挟んで `#<数字>` または `<owner>/<repo>#<数字>` が続く形。
- **照合粒度**: **1PR=1issue を原則**とするが、複数 issue をまとめた PR も許容し、**有効な `Closes/Refs` が 1 件以上**あれば通過する（過剰強制を避ける・02_設計 ADR-5）。
- **declined は対象外**: `github_issue` が `"declined: <理由>"` の issue は起票していないため PR 本文への記載対象外（含めない）。`github_issue` が空/`null` の issue も #36 の対象外（実 Issue 番号が無く PR で参照不能。これは #34 の責務であり #36 とは非交差）。
- **CI 限定性（ローカルと CI で挙動が異なる）**: PR 本文はローカルに存在しないため、#36 は **CI（PR イベントで `PR_BODY` が渡るとき）でのみ実行**され、ローカル実行・push イベント（`PR_BODY` 未設定）では SKIP する。この挙動差は仕様である（02_設計 ADR-4）。
- **発効日（grandfather）**: `PR_LINK_GATE_EFFECTIVE_FROM`（既定 `20260713_000000`）未満の日時プレフィックスを持つ差分内 issue は対象外。
- **プロジェクト全体での無効化**: env `PR_LINK_GATE_ENABLED=false`（既定 `true`・最優先ガード）。GitHub 非採用環境では PR イベント自体が発生せず `PR_BODY` が渡らないため自然に SKIP する。**本リポジトリでは設定せず既定 `true` のままにする**。

### 3. 本リポ CI（self-enforce.yml）への `PR_BODY` 配線（申し送り・本 issue 実装対象外）

- 消費者向けテンプレート `.agent-skill-chain/runtime/templates/github/workflows/audit.yml` は既に PR イベントで `PR_BODY: ${{ github.event.pull_request.body }}` を渡す配線を持つため、消費者環境では**追加配線なしで #36 が有効**になる。
- 一方、**本リポジトリの CI（`.github/workflows/self-enforce.yml`）は audit.sh を `continue-on-error`（非ブロッキング）で呼び、`PR_BODY` を渡していない**。このため本リポの PR では #36 は現状 inert（`PR_BODY` 未設定で SKIP）である。本リポで #36 を実効化するには self-enforce.yml への `PR_BODY` 配線とブロッキング化が必要だが、**これは本 issue のスコープ外（00 §4.2・02_設計 ADR-8）であり、将来の別 issue／ユーザー判断に委ねる申し送り**とする。#36 は `PR_BODY` 未設定時 SKIP なので、配線されるまで本リポで安全（誤 FAIL しない）である。

### 3.5 audit step 全体の非ブロッキング運用（意図的な暫定状態・申し送り）

- 本リポジトリの CI（`self-enforce.yml`）の「Enforcement audit (non-blocking)」step は、`continue-on-error: true` かつ `bash .../audit.sh . || echo "..."` により、`audit.sh` の FAIL が CI 全体のステータス（緑/赤）に反映されない。上記§3 の `PR_BODY`/#36 に限らず、audit step 全体がこの運用である。
- これは `enforcement/README.md` が謳う「CI audit は最後の砦・全ツール共通の最終強制層」という一般原則（消費者環境向けの既定挙動）と、本リポジトリの実運用が乖離しているように見えるが、以下の理由により**意図的な暫定状態**である。
  - 本リポジトリの issue は `.workflow` ではなく `docs/maintainer/workflow` 配下に置かれるため、`audit.sh` の一部チェックがそのままでは前提を満たさない。
  - さらに、workflow.db が本リポの CI では非追跡であり（別途起票・解消待ちの課題）、DB 系チェックが構造的に SKIP/FAIL し続ける状態にある。この状態のままブロッキング化すると、既存 PR フローを不必要に止める可能性が高い。
- **申し送り**: workflow.db の CI 非追跡問題が解消され、DB 系チェックが正常に機能する状態になった後、本 step の `continue-on-error` 除去（真のブロッキング化）を改めて判断する。それまでは本節の記載をもって、`enforcement/README.md` の「最後の砦」原則との文言上の矛盾は解消済みとみなす。

### 4. GitHub Issue 起票直後の書き戻し（即時自己検証・#36 とは別軸）

GitHub Issue 紐づけの実効性（起票直後の書き戻しタイミング）については、機械監査を新設せず既存 #34（implement 前に `github_issue` 非空を強制）に一本化し、起票直後の書き戻しは前述「### 2.5 起票直後の書き戻し（必須手順・取りこぼし防止）」の即時自己検証規約（人手監査＋自己検証）で補完する（02_設計 ADR-3）。本 issue で GitHub Issue 紐づけの新規 audit チェックは追加していない。

## Issue 追跡モード（`ISSUE_TRACKING_MODE`）の本リポ運用（両モード具体手順）

Issue 追跡モードの**抽象原則**（二値モード `github_native`／`local_tracked`・既定 `local_tracked`・実効モード解決の 2 因子・非 GitHub/未設定/不明値の `local_tracked` フォールバック・AI エージェントによる env 自律設定の禁止）は [../source/skills/agent/run_command.md §Constraints「Issue 追跡モード」](../source/skills/agent/run_command.md#constraints) と [../source/boot/CORE.md §完了 issue の close 分離](../source/boot/CORE.md) が正本である。本節はそれを**重複再定義せず**、本リポ固有の実効モード・両モードの起票〜完了具体手順・スイッチ投入先のみを記載する（配置境界: 抽象=source／具体=project）。

**本リポの実効モード**: 本リポは `ISSUE_TRACKING_MODE=github_native` を採用し、`git remote` に `github.com` を含む（[§3 対応判定・到達性](#3-対応判定到達性query具体) と同一シグナル）ため、スイッチ投入済みの環境では実効モードが **`github_native`** になる。スイッチ未投入（env unset）の環境では既定 `local_tracked` へフォールバックする。実効モードは `resolve_issue_tracking_mode`（`enforcement/ci/audit.sh`・**不変・参照のみ**）が env × github.com remote の 2 因子で決定論的に返す。

### 両モードの起票〜完了具体手順（分岐）

進行役は実効モードを解決したうえで、次の分岐に従う。

- **`github_native`（本リポの採用モード）**:
  - **起票**: GitHub Issue を正本とする。起票時に **00_要求定義.md の目的・成功基準・受け入れ基準（および理解に必要な全体像・フロー図）を GitHub Issue 本文へ完全転記**する（ローカルドラフトが非追跡・破棄されうるため、恒久情報を Issue 本文に自己完結させる）。AI 経路は `gh issue create --body`（[§GitHub Issue 起票ゲート](#github-issue-起票ゲート具体手順) の body テンプレート）、Web UI 手動起票は [.github/ISSUE_TEMPLATE/issue-request.yml](../../.github/ISSUE_TEMPLATE/issue-request.yml) の Forms で目的・成功基準・受け入れ基準を必須化する。
  - **作業記録**: 進捗・レビュー・チェックリストは GitHub Issue のコメント／チェックリストへ記録する。恒久的な**設計判断（ADR）**は追跡ファイル [../docs/maintainer/decisions/DECISIONS.md](../../docs/maintainer/decisions/DECISIONS.md) へ完了フェーズ（verify-and-close／04_review）で転記する（非追跡ドラフト破棄後も失われないため）。
  - **完了**: **GitHub Issue の close で完結する**（`close/` への **close 移動 PR は不要**）。ローカル 00〜04 は非追跡ドラフトであり `close/` へ移動しない。
- **`local_tracked`（既定・非 GitHub 環境等でのフォールバック）**:
  - **起票**: ローカル issue ドキュメント（00〜04）を正本とする（従来どおり）。
  - **完了**: 従来どおり `docs/maintainer/workflow/close/<issue>/` への **close 移動 PR** で確定する（詳細は下記 [§完了 issue の close 移動（上書き）](#完了-issue-の-close-移動上書き)）。close 移動は **`local_tracked` 専用**であり、`github_native` では行わない。

### スイッチ投入先（実効 `github_native` を機械的に成立させる 2 箇所）

実効 `github_native` は env `ISSUE_TRACKING_MODE=github_native` を次の 2 箇所へ配線して成立させる（02_設計 ADR-S2-3）。配布物 source（`pre-push.example`・`audit.yml` テンプレート・`audit.sh` 既定値）は**変更しない**（消費者非波及・AC8）。

- **CI（追跡・本 PR で投入）**: `.github/workflows/self-enforce.yml` の「Enforcement audit (non-blocking)」step に `env: { ISSUE_TRACKING_MODE: github_native }` を付与する。`continue-on-error: true`（非ブロッキング運用）は不変。
- **ローカル pre-push（追跡外・手動設定）**: `.git/hooks/pre-push`（未追跡・環境固有。`enforcement/ci/pre-push.example` を各自コピーして使う）内で `export ISSUE_TRACKING_MODE=github_native` を設定するか、シェルプロファイルで export する。**pre-push フック採用と env 設定は一組で行う不変条件**とする（env 未設定のまま非追跡ドラフトを作業ツリーに置いて push すると audit #28 が誤 FAIL しうる唯一の残余ロックアウト経路のため・02_設計 ADR-S2-1）。

`github_native` 実効時、audit.sh の #28（`check_issue_doc_in_gitignored_path`）と #33（`check_close_move_pending`）は冒頭 SKIP ガードにより SKIP される（非追跡ドラフト・close 未移動を FAIL 対象にしない）。`local_tracked`・非 GitHub では従来どおり検知が有効（回帰安全）。

### 非追跡化・スイッチ投入・DECISIONS 記録の正当性（人間判断のトグル運用）

### close 移動時の相対リンク補正（必須手順・移動前に完結）

本節は [../.agent-skill-chain/source/workflow/PHASES.md](../source/workflow/PHASES.md) §完了 issue の close 移動 の「移動に伴う相対リンクの深度補正」原則の**本リポ向け具体化**である（原則・検証タイミングの正本はコア、本節は具体手順）。

`docs/maintainer/workflow/<issue>/` はリポジトリルートから **4 階層下**（`docs`/`maintainer`/`workflow`/`<issue>`）だが、`close/<issue>/` へ移動すると **5 階層下**（`docs`/`maintainer`/`workflow`/`close`/`<issue>`）になる。issue ディレクトリの**外**（`.agent-skill-chain/source/`・`.agent-skill-chain/project/`・`.github/`・`README.md`・`docs/maintainer/RELEASE.md` 等リポジトリルート配下）を指す相対リンクは 1 階層深くなるため補正する。**検証・補正はすべて移動前（`docs/maintainer/workflow/<issue>/`＝読み取り制限のかからない場所）で完結させること。** `.claude/settings.json` は `close/` 配下への Read/Grep/Glob を deny しており、移動後検証に依存する手順は必ずブロックされる。

**手順（この順で厳守）**:

1. **列挙**: 元の場所（未移動）で、対象 issue 内の全ファイルの相対リンクを列挙する。例: `grep -rEon '\]\(\.\./' docs/maintainer/workflow/<issue>/`。
2. **分類**: 各リンクを次に分類する。
   - **(a) issue ディレクトリの外を指す参照**（`.agent-skill-chain/source/`・`.agent-skill-chain/project/`・`.github/`・`README.md`・`docs/maintainer/RELEASE.md` 等、リポジトリルート配下）→ **深度 +1 が必要**。
   - **(b) 同一 issue ディレクトリ内の兄弟ファイル・配下 memo への参照**（例: `./00_要求定義.md`・`./memo/...`）→ **補正不要**（深さ変更なし）。
   - **(c) 同時に close へ移動する別 issue への参照**（例: `../20260712_XXXXXX_.../00_要求定義.md`）→ 参照先も同じ深さで一緒に移動するため**補正不要**（両者の相対位置は不変）。
3. **編集**: **(a) のみ**、`../` を 1 つ追加する形で、**元の場所にいるうちに**編集する（例: `../../../../.agent-skill-chain/source/CONCEPTS.md` → `../../../../../.agent-skill-chain/source/CONCEPTS.md`）。**markdown リンク構文 `](...)` を伴わないバッククォート内・本文中の `../` の言及（過去レビュー証跡・例示等）は改変しない**（実リンクのみ対象）。
4. **移動前検証**: **元の場所にいる状態のまま**妥当性を検証する。**`close/` という文字列を含むパスを Bash コマンドの引数に一切使わない**方法で行う: 編集前のリンクと編集後のリンクを比較し、「`../` の数がちょうど 1 つ増えている」「ターゲットのファイル名部分が変化していない」ことをテキスト上で確認する（実ファイルシステムへの再アクセスは不要）。深度 +1 は移動という操作の定義そのものであり、**編集前のリンクが実在解決していれば**深度 +1 後のリンクも移動後に正しく解決することは構造的に保証される。念のため、編集前（未移動）のリンクが実在解決することを通常の Read/Grep/Glob（deny 対象外の元の場所）または `realpath -m` で確認しておくこと。**編集前のリンクが解決しない**（元から深度不足等の不備がある）場合は、単純な +1 では移動後も解決しないため、移動後に 5 階層上（`](../../../../../`）で正しく解決する深度へ**是正**してから移動する。
5. **移動**: 編集・検証が完了し確認が取れた後にのみ、`git mv`（追跡ファイル）／`mv`（`memo/` 等の非追跡ファイル）でディレクトリを `close/<issue>/` へ移動する。
6. **移動後の禁止事項**: 移動後は、`close/` 配下のファイルに対して Read/Grep/Glob（Bash 経由の `cat`/`grep`/`realpath` 等を含む）を**一切行わない**。移動成否の確認は `git status`（パス一覧のみで内容は読まない）・`git log --stat`（コミット対象パス一覧のみ）等、**ファイル内容を読まない手段**に限定する。

この手順により、以後の close で同じリンク切れ（深さ不足）が再発せず、かつ移動後の `close/` 配下への読み取りに依存しないため、環境の deny 設定（`.claude/settings.json`）に抵触しない。

## close/ 参照・deny 運用に関する方針（自己点検issue対応）

2026-07-14 fable による自己調査で検出された 3 件のサブ issue（`docs/maintainer/workflow/close/20260714_180751_自己点検issue群対応/90_issues/` 配下: `20260714_163724_close移動リンク切れとRead制限の相互作用`・`20260714_163717_close済みissue参照アンバランス`・`20260714_164034_closedeny監査手順衝突`）への対応として、close/ 関連の運用方針を以下に追記する。

### close/ の外側からの既存参照の補正（恒久ルール）

上記「close 移動時の相対リンク補正」手順は、**移動する issue 自身が持つリンク**（issue ディレクトリ内のファイルから外部・兄弟・同時移動先を指すリンク）を対象とする。これとは別に、**close/ の外側にある正本文書**（`.agent-skill-chain/project/`・`.agent-skill-chain/source/`・`README.md`・`docs/maintainer/RELEASE.md` 等）側から、移動対象 issue を指す既存参照が存在する場合がある。これは上記手順の対象外であり、放置すると移動後にリンク切れとして残る（実例: `.agent-skill-chain/project/MODEL_TIER_TABLE.md` が `docs/maintainer/workflow/20260712_120018_.../00_要求定義.md` を close 移動後も直接参照しており不達になっていた）。

今後の close 移動では、上記手順のステップ1（列挙）と同じタイミング（移動前・deny 対象外の場所にいる間）で、以下を恒久ルールとして追加実施する。

1. **外部参照の洗い出し**: `grep -rn "<移動対象issueディレクトリ名>" --include=*.md .`（またはリポジトリ全体を対象にした同等の grep）で、移動対象 issue ディレクトリ名を含む参照をリポジトリ全体から検索する。
2. **分類**: ヒットした参照のうち、移動対象 issue ディレクトリの**外**にあるファイルからの参照のみを対象とする（同時に移動する issue 同士の相互参照は既存手順の分類 (c) と同様に補正不要）。
3. **補正**: 該当する参照のパスに `close/` セグメントを挿入する（例: `workflow/<issue>/00_要求定義.md` → `workflow/close/<issue>/00_要求定義.md`）。見出しアンカー付きリンクは、アンカー先の妥当性を移動後に close/ 配下を読んで確認することができない（deny 制約）ため、移動前にアンカーの妥当性を確認できない場合はファイル全体へのリンクに簡略化してよい。
4. **同一コミット/PRで実施**: 移動と外部参照側の補正は同一のコミット・PR内で完結させる（移動後に別作業として先送りしない）。

既存の切れたリンク（約 1,060 件、fable 自己調査 2026-07-14 時点で検出）を今回全件遡及修正することは求めない（段階対応で可）。本節は**今後の新規 close 移動から適用する恒久ルール**である。

### 正本文書における close/ 参照の位置づけ（経緯・ADR 参照の扱い）

正本ドキュメント（本ファイル・`.agent-skill-chain/project/` 配下等）が close/ 配下の issue（検討経緯・ADR 等）を参照する場合、以下を方針とする。

- **正本には結論・現在の事実のみを記載する**。「なぜその結論に至ったか」の詳細な検討経緯は正本の理解に必須としない（既存の「経緯はノイズ・現在の事実のみ」原則と整合させる）。
- close/ 配下 issue への参照は、あくまで**補足情報（詳細な経緯を辿りたい場合の追加資料）**という位置づけに限定する。**読めなくても正本の本文の理解・運用に支障が出ない**ことを条件に、参照リンクを残すことを許容する。
- 具体例: 本ファイルと対をなす [MODEL_TIER_TABLE.md](MODEL_TIER_TABLE.md) §裁量禁止との整合 の「詳細な検討経緯・論拠は [...] を参照」という記載は、この方針に沿った書き方の実例である（本文の結論部分はリンク先を読まなくても完結しており、リンクは補足に留まる）。
- 上記を満たさない書き方（close/ 配下の記載を読まないと正本の結論が成立しない、close/ 配下の値そのものを正本が転記せず参照のみに依存する等）は、今後の正本執筆で避ける。

### close/ deny 設定の推奨形態（監査・調査タスクとの両立）

`.claude/settings.json` の close/ 配下 Read/Grep/Glob deny は本リポのローカル環境固有設定であり（§close 移動未実施の検知 参照）、本ファイルではこの設定自体を変更しないが、今後の設定見直しにあたっての**推奨案**をここに記録する。

- **推奨案**: Read のみ許可し、Grep/Glob および Edit/Write 系は引き続き deny する案を推奨する。close 済み issue の**意図しない変更**を防ぐという deny の主目的は Edit/Write 側の deny 維持で達成でき、Read のみの許可であれば「誤って編集してしまうリスク」を増やさずに、監査・調査タスク（過去 issue の参照、リンク切れ検証等）との両立が見込める。Grep/Glob は close/ 内の大量ファイルを横断検索してしまう操作性のため、意図しない情報の大量流入を避ける目的で当面 deny を維持する案とする。
- **audit.sh との非対称について**: `enforcement/ci/audit.sh` は close/ 配下を `find` で走査するが、これはエージェント（AI）が Read/Grep/Glob で内容を読む操作とは性質が異なる。audit.sh は**人間が事前にレビューした固定ロジックのプログラム**であり、実行のたびに恣意的な判断・誤操作のリスクを追加しない（決定論的な走査のみで、内容を「読んで判断する」ことをしない）。一方 Read/Grep/Glob はエージェントが内容を読んで自律的に判断・行動する経路であり、誤操作・誤編集の起点になり得る。したがって「機械監査（プログラム）は許容し、エージェントの読み取りは制限する」という非対称は意図的であり、解消すべき矛盾ではないと整理する。
- 上記はいずれも**推奨・提案であり、`.claude/settings.json` 自体の変更はこの節の範囲外**（同ファイルは本リポの `.gitignore` 対象・ローカル環境固有設定であり、実際に変更するかどうかは各消費者・保守者の判断に委ねる）。

## テストの tmp 隔離（必須）

何かをテスト/検証するときは、**一時ディレクトリ（`mktemp -d`）を作成してその中で検証**する。**いきなり自己インストール（本リポへの `setup.sh` 実行等）や本番ファイルへの実行をしてはならない。**

- **理由**: 破壊的影響の回避と、既存生成物との混同による「本当に正しいか分からない」状態の防止。
- **具体運用**: install / uninstall / setup / build 等の検証は `mktemp -d` ＋ `git archive HEAD | tar -x`（クリーン clone の再現）等で隔離環境を作って行う。本リポの `.agent-skill-chain/source/` `.claude/` `.cursor/` `.agent-skill-chain/runtime/` `workflow.db` を**変更・破壊しない**こと。検証後は一時環境を片付ける（`rm -rf` 等）。
- 汎用のテスト方針は [../.agent-skill-chain/source/RULES.md](../source/RULES.md) §テスト隔離 を参照（重複させず相互参照）。
