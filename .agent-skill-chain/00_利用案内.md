## 導入・更新・削除

利用者向けの公開入口はpackage runnerの`npx`である。**本packageはnpm registryへ公開しておらず、`npx`は本package自体をregistryから解決せず、Git remoteの指定でGitHubから直接取得して実行する。**

**registryを完全に使わないわけではない。** Git取得時は`prepare`が`npm run build`を実行するため、その過程でdevDependenciesをregistryから取得する。

| 用途 | command |
| ---- | ------- |
| 最新を使う | `npx github:techbeansjp-free/AGENTS.md doctor --root=.` |
| 版を固定する | `npx github:techbeansjp-free/AGENTS.md#<tag> doctor --root=.` |

`<tag>`にはreleaseのtag（`v0.3.1-beta.83`のような形）を指定する。**以降に現れる`npx agent-skill-chain <command>`は、この`npx github:techbeansjp-free/AGENTS.md <command>`の短縮表記である。**

**利用project側のpackage manager scriptを経由しない。** `package.json`の`scripts`へ登録して`npm run`や`pnpm run`から呼ぶと、package managerが本CLIへ到達する前に利用project自身の依存解決を走らせる。**その失敗は本CLIとは無関係に起動を止める。** 実際に、依存が552 packageあるprojectで`pnpm run`経由の起動だけが失敗し、同じ環境で直接起動は成功した。**本CLIはNodeとGitだけで動き、runtime依存を持たない。** 起動口は上表のcommandを直接実行する。

対象directoryを省略した場合は現在directoryを使い、`install`、`update`、`delete`は何も書き換えないpreviewを既定とする。preview結果を確認した後、同じcommandへ`--apply`を付けた場合だけ変更する。

| 操作 | preview                                  | 適用                                             |
| ---- | ---------------------------------------- | ------------------------------------------------ |
| 導入 | `npx agent-skill-chain install --root=.` | `npx agent-skill-chain install --root=. --apply` |
| 更新 | `npx agent-skill-chain update --root=.`  | `npx agent-skill-chain update --root=. --apply`  |
| 削除 | `npx agent-skill-chain delete --root=.`  | `npx agent-skill-chain delete --root=. --apply`  |
| 診断 | `npx agent-skill-chain doctor --root=.`  | 読み取り専用のため非該当                         |

`delete`はmanaged asset recordとhashが一致するpackage所有fileだけを削除し、利用project所有fileと変更済みfileを保持する。再現性のためversionを固定するときはGit remoteの指定へrelease tagを付けて`github:techbeansjp-free/AGENTS.md#<tag>`とする。**`agent-skill-chain@<version>`はnpm registry上のpackage名とversionの解決であり、本packageは未公開のため成立しない。**内部関数名と旧CLI aliasの`init / upgrade / uninstall`は新しい手順・文書・自動化へ使用しない。

**`.agent-skill-chain/managed-assets.json`（初回managed asset record）と`.agent-skill-chain/managed-assets-records/`（更新snapshot）の両方を失った場合は`update --recover-record`で復旧する。** **`--recover-record`を付けない`update`は、recordが無ければ1 fileも書かずに拒否する。** 誤った`--root`や作業directoryでの実行を防ぐためであり、**製品はfilesystemから「かつて導入した」ことを推測しない。** 初回recordは更新で置換せず、更新は内容を検証したsnapshotを追記する。snapshotだけが失われた場合は古いrecordから無音で再開せず、原因を確認して復旧する。

復旧すると、正本と一致する展開済み資産を採用してrecordを再固定し、**正本と異なる資産は上書きせず`retained`として報告する。** 報告された資産は内容を確認し、正本へ戻したい場合だけ当該fileを削除して再実行する。**`--recover-record`は未導入のdirectoryでも展開対象を配置する。** 対象directoryを確認してから付ける。dangling symlinkのrecordと壊れたrecord・snapshotは不在扱いにせず拒否する。snapshotが残り初回recordだけが欠落したときも`--recover-record`では進めず、両者を一組でバックアップから復元する。中断した書込み・hardlink確認の一時fileは正本ではなく、次回の連鎖検証を塞がない。更新後に旧CLIへ戻すと旧CLIは初回recordしか見えないため、旧版との交互運用はしない。切り戻しは利用projectのバックアップから両recordを復元する。

`install`・`update`・`delete`のapplyは`.agent-skill-chain/managed-assets-mutation.lock/`を排他的に保持する。失敗後にlockが残った場合、別の操作を直ちに再実行しない。実行中の操作がないことを確認し、初回record・snapshot連鎖・資産の実測内容を照合し、必要ならバックアップから復元してから、運用者がこのlock directoryだけを除去する。`doctor`は残存lockを不健全として報告する。

`install`と`update`は、Claude Code用`.claude/skills/asc-step/SKILL.md`とCodex用`.agents/skills/asc-step/SKILL.md`も管理する。両fileは`.agent-skill-chain/skills/asc-step/SKILL.md`と同じ内容で、hostからWorkflow・Step skill正本へ入るための登録口である。`doctor`で配置・hash・frontmatter・正本linkを確認できる。

## commandの調べ方

**必須flagを1件ずつ試す必要はない。** 任意のcommandとsubcommandへ`--help`を付けると、必須flag検証より先にusageをJSONで返す。

```
npx agent-skill-chain worktree create --help
```

usageは要約、必須flag、条件付きflagとその条件、任意flagと既定値、位置引数、実行例を含む。

必須flagが不足したまま実行した場合も、**不足を1回の実行ですべて`reasons`へ列挙する。** 1件ずつ返さない。

```
$ npx agent-skill-chain worktree create
reasons: --issue=...が必要です / --branch=...が必要です / --slug=...が必要です / --base=...が必要です / --remote-default-branch=...が必要です / --remote-default-sha=...が必要です
```

値をとるflagは`--flag=値`の形式で指定する。**空白区切りは受理しない。** 無言で未指定として扱わず、専用の診断で拒否する。

```
$ npx agent-skill-chain worktree create --branch 値
reasons: --branchは空白区切りでは受理しません。--branch=値の形式で指定してください
```

trusted boundaryの評価は必須flag検証より先に行う。境界を侵すpathを渡した場合、不足flagではなく境界違反として拒否する。

## 使い方

1. 最初にrepository直下の[AGENTS.md](../AGENTS.md)と、この索引を読む。
2. 作業規則は`docs/`、実行するStepは`skills/`、成果物の書式は`templates/`からたどる。
3. policy入力を変更するときは`schemas/`で構造を確認し、package既定値とproject選択値を分離する。
4. 仕様を作るときは[仕様template利用案内](templates/specs/00_利用案内.md)から適用categoryを選ぶ。

各Step directoryの入口はそのdirectoryの`SKILL.md`、各仕様category directoryの入口はそのdirectoryの`00_*`文書である。新しいdirectoryを追加するときは、用途を重複定義しない入口文書とdirectory案内検査の対応を同じ変更に含める。

## 補助レビュー

### 進行役からローカルLLMへのreview委譲

Step 03/07/10の進行役は、下記の`local/supplemental-review.json`が`enabled: true`なら、その設定のローカルLLMをreviewerとして呼び出す。ユーザー共通設定は`$XDG_CONFIG_HOME/agent-skill-chain/supplemental-review.json`（未指定時は`~/.config/agent-skill-chain/supplemental-review.json`）に同じJSONを置く。対象worktreeのローカル設定、主worktreeのローカル設定、ユーザー共通設定の順に採用する。先に見つかった`{"enabled":false}`は後続の設定を抑止する。どれも無ければ既存のreview経路を使い、LLMは起動しない。`--root`には対象stagingと同じworktreeのrootを指定する。

```
npx agent-skill-chain routing delegated-review-staging --root=<対象worktreeのroot> --step=3 --staging=<対象staging>
npx agent-skill-chain routing delegated-review-staging --root=<対象worktreeのroot> --step=7 --staging=<対象staging>
npx agent-skill-chain routing delegated-review-diff --root=<対象worktreeのroot> --base=<比較基点SHA> --head=<H_impl SHA> --staging=<対象staging>
```

結果は`disabled`、`degraded`、`reviewed`のいずれか。`reviewed`には肯定・敵対の評価、対象内finding、差分外指摘の除外件数、判定、入力・出力digest、modelを含む。設定済みで`degraded`ならreview完了として扱わない。これは進行役のreviewer委譲であり、個人設定だけでprojectのtrusted policyやmerge権限を変えない。従来の`routing supplemental-review-*`コマンドは追加の指摘を得る互換経路として残る。

Step 03/07/10実施時に、ローカルLLM（Ollama）へdiffまたはstaging文書を渡し、判定には使わない追加の指摘を得られる任意機能である（TERM-ASC-124）。CodeRabbit相当以上の観点（バグ・セキュリティ・パフォーマンス・保守性・機能性）でレビューするようpromptを設計している。

**Issue #1425の`modelMapping.roles.reviewer`との違い**: `modelMapping.roles.reviewer`はgit管理下・project全体共有のreviewer役割宣言であり、`mode: "supplement"`でも共有設定の上書きが必須になる。本機能はエンジニア個別のGit管理外設定であり、`modelMapping.roles.reviewer`を一切読み書きしないため、他エンジニアや`pr create`/`pr merge`/`review round`の判定に影響しない。

有効化するには、`.agent-skill-chain/local/supplemental-review.json`（既定path）を作成する。

```json
{
  "enabled": true,
  "provider": "ollama",
  "model": "qwen2.5-coder:32b",
  "endpoint": "http://localhost:11434",
  "timeoutMs": 900000,
  "promptChunkBytes": 24576,
  "maxOutputTokens": 2048,
  "profile": "chill"
}
```

`timeoutMs`の省略時は15分であり、review全体の全chunkで共有する。`promptChunkBytes`の既定値は24576（24 KiB）、`maxOutputTokens`の既定値は2048で、進行役が使う委譲reviewと補助reviewの全chunkおよび投稿前検証へ適用する。端末性能に合わせ、Git管理外の同じ設定fileで前者を16384〜1048576 byte、後者を128〜32768 tokenの範囲で変更できる。Ollamaのstream応答は有限量で統合する。`profile`は`chill`（Critical/Highだけ表示）または`assertive`（全severityを表示）を指定できる。省略時は従来互換の`assertive`である。表示から隠した候補は`suppressedFindings`に残り、差分reviewの第二passでも検証する。`firstPassFindings`が全候補の元の順序を保持し、第二passの`findingIndex`はその配列に対応する。進行役は表示候補と隠れた候補の両方を確認する。findingの`effort`は`Quick win`、`Moderate`、`Heavy lift`から選ぶ修正工数の目安である。

`endpoint`はloopback（`127.0.0.1`/`localhost`）だけを受理する。`.agent-skill-chain/local/`は本packageの`install`/`update`が管理する対象namespace（`docs`・`skills`・`templates`・`schemas`・`policy`・`hooks`）に含まれないため、**`update`を実行してもこの設定fileは上書き・削除されない。** 追加で`.gitignore`へ登録する必要はない（本packageの配布物に含まれる`.gitignore`が`.agent-skill-chain/local/`を既に除外している）。利用projectが独自の`.gitignore`を持つ場合は、同じprefixを追記する。

CLIの呼び出し方は次のとおりである。設定が無効・不正な場合はエラーにせず`{"state": "disabled"}`を返して正常終了する。

```
# Step 10相当: exact-head diffと関連ファイルをレビューする
npx agent-skill-chain routing supplemental-review-diff --root=. --base=<比較基点SHA> --head=<対象SHA>

# Step 03/07相当: staging内の要求・要件・設計文書をレビューする
npx agent-skill-chain routing supplemental-review-staging --root=. --staging=<staging path>
```

指摘は`{"state": "findings", "findings": [...], "ignoredOutOfScopeCount": 0}`のJSONで返る。差分外の別taskへの指摘は採用せず、除外件数だけを残す。 連結worktreeから既定の補助review設定を使う場合、対象worktreeに設定が無ければ主worktreeのローカル設定を参照する。`--config-path`で明示したpathにはこのfallbackを適用しない。`supplemental-review-diff`の関連file収集では、拡張子なしdotfileを検索対象から外し、変更file名のstemが10件を超えるfileに現れた場合は汎用名として関連候補を採用しない。Ollama未起動・timeout時は`{"state": "degraded", "reason": "..."}`を返し、呼び出し元（Step 03/07/10の既存実施）を妨げない。より詳細な契約（起動境界・endpoint検証・安全側への倒し方）は、利用projectが`docs/specs/`配下に持つ信頼境界仕様（本package自身の例: `docs/specs/10_セキュリティ/01_信頼境界.md`の「補助レビュー起動の境界」節）を確認する。

## Jev provider設定

### Decision Skillと有限選択判断の委譲

Step 3/7/10の進行役は、DCAND-006（finding分類記入）・DCAND-008（CodeRabbit利用枠制限判定）・DCAND-009（reviewer選定）・DCAND-010（軽微な矛盾3条件判定）という有限選択判断を、`agent-skill-chain decision invoke`（Issue #1485、Decision Skill）で行う。この4件はいずれも「呼び出し元を名指しできない」ためprose記述に留まっていたが、Decision Skill自身がその呼び出し元になる。

```
npx agent-skill-chain decision invoke --type=<DCAND-006|DCAND-008|DCAND-009|DCAND-010> --input=<file> --staging=<対象staging> --dry-run
npx agent-skill-chain decision invoke --type=<同上> --input=<file> --staging=<対象staging> --apply
npx agent-skill-chain decision types
```

解決順序はdeterministic resolverを先に試し、無ければ設定済みprovider（既定`lightweight-tier`）へ委譲する。DCAND-001〜005（既存compiled codeの判断）はdeterministic resolverとして統合済みで、既存呼び出し元（`issue.ts`・`cli.ts`等）の挙動は変えない。`--input`はJSON fileで、共通envelope`{candidateHeadSha, subjectRef, payload?, proposedValue?, confirmedBy?}`を持つ。`candidateHeadSha`は対象repositoryの実HEADと一致しない場合は拒否する（自己申告SHAを受理しない）。型別の`payload`形式と使い方は[step-10-review SKILL.md](skills/step-10-review/SKILL.md)と`.agent-skill-chain/docs/01_開発ワークフロー.md`のDCAND-008/010節を参照する。

判断の提案（`proposedValue`）がどこまで自動的に有効値（`effectiveValue`）へ反映されるかは`authorityMode`が決める。

| authorityMode | 対象 | 反映条件 |
|---|---|---|
| `authoritative` | DCAND-001〜005、DCAND-008の確定できた範囲 | 提案をそのまま反映する |
| `advisory` | DCAND-006、DCAND-008のunknown範囲 | `--input`へ`confirmedBy=<進行役識別子>`を含めて再実行するまで`effectiveValue`は`null`のまま |
| `one-way-escalation` | DCAND-010 | 安全側（`"not-minor"`）は確認なしで反映、緩和方向（`"minor"`）は`confirmedBy`が必要 |
| `constrained-choice` | DCAND-009 | `payload.candidateSet`内の値だけを反映し、候補外は`rejected`にする |

`--apply`時は判断結果を`DecisionJournalRecord`として`<primaryRoot>/.agent-skill-chain/runtime/decisions/<staging名>/events.jsonl`（`.gitignore`済みの`runtime/`配下。staging digestの対象外）へ追記する。**永続先は常にprimary worktreeであり、対象worktree（active）には書かない。** worktreeを削除しても判断記録は失われない。DCAND-006の記録は`decisionRecordId`をfindingの`decisionRef`欄へ書くことで、Step 10のreview roundが機械検証する（type・candidateHeadSha・inputDigest・provider versionのいずれかが不一致なら該当roundを拒否する）。

### 個人ローカルのJev provider設定

Jev（Decision Provider）は`decision invoke`が委譲できるprovider先の1つ。**2026-09-26時点（Issue #1486）で実HTTP dispatchが実装済みだが、常にcontinuous shadowとしてのみ動く。** `decision invoke --apply`が実際にproviderへ委譲した判断（DCAND-008のunknown分岐・DCAND-009・DCAND-010。DCAND-006はshadow対象外、後述）について、Jev設定が`enabled`ならば追加でJevへも問い合わせ、結果を`jev-shadow.jsonl`へ記録するが、**`effectiveValue`・`requiresConfirmation`・`rejected`には一切影響しない。** authorityへの昇格は[#1487](https://github.com/techbeansjp-free/AGENTS.md/issues/1487)（shadow評価の蓄積）と[#1488](https://github.com/techbeansjp-free/AGENTS.md/issues/1488)（decisionType×provider×directionごとの限定的採用）を経るまで、Jevの提案は記録専用でrouting・authorityには使われない。

#### guided setup command（config file手書きの回避）

設定fileを手書きする代わりに、guided setup commandでendpoint・model・apiKeyEnvVar（env var名。値そのものではない）を渡すと、正しいschemaの`.agent-skill-chain/local/jev-provider.json`を生成し、その場で`LocalConfigResolution`の状態を返す。

```
npx agent-skill-chain decision configure --provider=jev --endpoint=<https URL> --model=<model名> --api-key-env-var=<ENV_VAR_NAME> --dry-run
npx agent-skill-chain decision configure --provider=jev --endpoint=<https URL> --model=<model名> --api-key-env-var=<ENV_VAR_NAME> --apply
```

`endpoint`・`model`・env var名（値ではない）は非秘密情報であり、**人間が自分のAIエージェントへ自然言語で伝え、AIエージェントがこのcommandを代行実行してよい。** 出力は常に構造化されたJSON（`configPath`・`wouldWrite`・`applied`・`validationErrors`・`resolution`）で、AIエージェントが次の一手（例えば`resolution.state === "invalid"`ならreasonを人間へ伝える）を人間の追加確認なしに判断できる。

#### APIキーのshell起動fileへの追記（確認付き・値非表示）

`--shell-rc-append`を付けると、同じcommandが「config file生成」ではなく「検出した shell起動file（`$SHELL`からbash→`~/.bashrc`、zsh→`~/.zshrc`を検出。対応外shellは拒否）への`export`追記」モードへ切り替わる。

```
npx agent-skill-chain decision configure --provider=jev --api-key-env-var=<ENV_VAR_NAME> --shell-rc-append --dry-run
npx agent-skill-chain decision configure --provider=jev --api-key-env-var=<ENV_VAR_NAME> --shell-rc-append --apply --confirm=APPEND
```

**APIキーの値そのものはこのcommandの引数として渡さない。** `process.env[<ENV_VAR_NAME>]`（呼び出し時点でそのshellに既に`export`済みの値）を直接読むだけで、コマンド履歴・stdout・エラーメッセージのいずれにも値が現れない。これは、値をAIエージェントのcontext・logへ残したくない場合に、**人間が自分のshellで実行すべき正確な1コマンド（`export <ENV_VAR_NAME>=<値>`）をAIエージェントが提示し、人間自身がそれを実行する**という役割分担を可能にするための設計であり、人間がAIエージェントへ値を直接渡す選択も禁止しない（どちらを選んでも設定は完了する）。追記は`--apply`と明示確認token`--confirm=APPEND`の両方が揃わない限り行われない（無言で書き換えない）。既に同名変数の`export`行がrc fileにあれば、値を読まず常に無変更のまま返す（重複追記・既存記述の上書きを避ける）。

有効化には、`.agent-skill-chain/local/jev-provider.json`（既定path。エンジニア個別のGit管理外設定であり、`modelMapping.roles.reviewer`やtrusted project policyとは独立）が上記のいずれかの方法で存在する必要がある。手書きする場合の形式は次の通り。

```json
{
  "enabled": true,
  "apiKeyEnvVar": "JEV_API_KEY",
  "endpoint": "https://api.example-jev-provider.invalid/v1",
  "model": "jev-decision-1"
}
```

| field | 内容 |
|---|---|
| `enabled` | `true`のときだけ有効。`false`または欠落は`disabled`として扱う |
| `apiKeyEnvVar` | APIキーを保持するenv var名（`^[A-Z_][A-Z0-9_]*$`）。**値そのものはこのfileに書かない。** |
| `endpoint` | 接続先URL文字列 |
| `model` | 使用するmodel識別子文字列 |

**APIキーの値は常にprocess環境変数から取得する。** `apiKeyEnvVar`が指すenv varが実行時に設定されていない場合も、config自体は無効（後述の`invalid`）として扱う。値がこのfileや戻り値、ログへ書かれることはない。同意の単位はrepository instance／developer-local projectであり、user共通設定（`~/.config/...`）は使わない。

連結worktree（feature worktree等）から使う場合、**対象worktree（active）にこの設定が無ければ、主worktree（primary）のローカル設定を継承する。** 継承するのは「設定が無い」場合だけであり、対象worktreeで明示的に`{"enabled": false}`にした場合や、設定内容が不正な場合は主worktreeへfallbackしない（個人が明示的に無効化・記入した設定を、worktreeを越えて無視しないため）。

#### 解決状態の確認方法（state/resolutionフィールド）

補助レビュー（`routing supplemental-review-diff`等）が`{"state": "disabled"|"degraded"|"reviewed"}`を返すのと同じように、**Jev provider configが今どう解決されているかは、`decision invoke`自身の出力を読むことで確認する。** 別途の診断スクリプトは不要であり、用意もしない。

`decision invoke`の出力は常に`workspace`（`{activeRoot, primaryRoot}`）と`jevProviderConfig`を含む。`jevProviderConfig`は次の4状態（`LocalConfigResolution<T>`）のいずれかを返す。

| state | 意味 |
|---|---|
| `absent` | active worktreeにもprimary worktreeにも設定fileが無い |
| `enabled`（+`source: "active"\|"primary"`） | 有効な設定が見つかった。`source`でどちらのworktreeから継承したかが分かる。値には`endpoint`・`model`・`apiKeyEnvVar`（env var名のみ）を含み、APIキーの値は含まない |
| `disabled`（+`source`） | 見つかった設定が`enabled: false`または`enabled`欠落 |
| `invalid`（+`source`、`reason`） | 見つかった設定がJSON不正・schema不正・指定env var未設定等。`reason`に具体的な理由文字列が入る |

例えば連結worktreeで設定していないのに主worktreeのJev設定を使わせたい場合は`enabled`＋`source: "primary"`が返るはずで、代わりに`absent`が返れば主worktree側の設定を確認する、というように、この出力を読むだけで「なぜJevが使われた／使われなかったか」を追える。Jevがdispatch不可の間は、`jevProviderConfig`が`enabled`でも実際の判断は常にdeterministic resolverまたはlightweight-tier（自己申告provider）で処理され、出力の`providerNote`にその旨が明記される。

## 置かないもの

- package所有directoryへrepository固有のpackage manager、CI、言語、命名、release値を置かない。
- `project/`へpackageの汎用規則、Markdown、未列挙fileを置かない。
- templateへ完成済みproject値や実装証拠を置かない。
- `.agent-skill-chain/tmp/`、`role-log/`、`metrics/`、`local/`、`runtime/`（Decision Journal）を正本または配布物にしない。
