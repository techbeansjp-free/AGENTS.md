# hooks（強制点）

このdirectoryは、hostのtool呼び出し前に自動実行される**強制点**の正本を持つ。

## skillとの違い

**skillは呼び出されたときに読まれる登録口である。** hookは**利用者の操作なしに毎回走る。** 同じ配布機構で配るが責務が違う。

## 配られるもの

`install`と`update`は本体だけを配る。

| path | 内容 |
|---|---|
| `.agent-skill-chain/hooks/asc-contract-citation.mjs` | 正本 |
| `.claude/hooks/asc-contract-citation.mjs` | 正本からの展開 |
| `.codex/hooks/asc-contract-citation.mjs` | 同上 |

**登録は配らない。** hostの設定fileへの書き込みは、`install`の権限を「packageの資産を置く」から「以後のtool callごとに自動実行されるcodeを登録する」へ広げる。**利用者が明示的に登録する。**

`doctor`はproject-localの設定に期待するentryがあるかを**報告する**。**`healthy`は変えない。**

## asc-contract-citation.mjs が何をするか

`codex exec`を含むcommandを検査する。commandが参照する`.md`または`.txt`のfileに**範囲を狭める語**（だけ・のみ・対象外・外す・限る・含めない・実行しない）があるのに、`## 規範の引用`節の中に要件IDと`> `で始まる原文引用の両方が無ければ、起動を`deny`で拒否する。

**節の外に置いた引用やIDは数えない。**

**Node.jsで実行する。** `package.json`の`engines`が要求するNode.js 20以上で動く。**`bash`と`jq`は必要としない。**

## Claude Codeへの登録

`.claude/settings.local.json`へ次を加える。**既存の設定を消さないこと。**

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR/.claude/hooks/asc-contract-citation.mjs\"",
            "timeout": 15
          }
        ]
      }
    ]
  }
}
```

**この形式は本repositoryで実際に動作している。**

## 変更したい場合

**展開先ではなく正本を変える。** 展開先を書き換えると、`update`は利用者の変更として保持し、`delete`は削除しない。**正本と展開先が食い違ったまま残る。**

本repositoryでは実際にdriftが起きた。`.claude`側だけがIssue #1233の是正を受け、`.codex`側は古い判定のまま残っていた（2026-09-09に観測）。

## Agent Lifecycle / Handoff（Issue #1546）

`asc-agent-lifecycle.mjs`は標準のClaude Code用hookである。`install` / `update --apply`は本体・ASC所有の登録・trusted CLIを一緒に管理する。Codexへの配布・強制は未対応である。

### 登録

既存install/updateのpreviewで対象を確認し、`--apply`でASCの登録を構成する。利用者がJSONを編集する必要はない。適用後は新規sessionで開始する。`startup`または新session IDを持つ`/clear`を受理し、同じIDの`/clear`では上限をリセットしない。開始記録のない既存sessionへの途中導入はtoolを拒否する。

doctorの登録診断は静的なpostconditionである。`runtimeVerified: false`は実hostでの発火確認を意味しない。詳細は下記の標準short-lived方式を参照する。

### 強制する範囲

- `SubagentStop`でagentをclosedにする。これは返答を終えたことの観測であり、タスク成功の証拠ではない。追加修正は別ID・履歴非継承のagentで行う。同じIDへの再度の`SubagentStart`は再利用として記録し、その後のtool実行を拒否する。
- `PreToolUse`は旧`Agent` / `Task`の`resume`指定を拒否する。`SendMessage`は記録上activeで、明示的enforce時のみ上限未到達の正確なIDだけを許す。終了済みID、名前alias、別session、未知の宛先は拒否する。active agent同士の進行中の連絡は許す。
- main/subagentのtool試行を計測する。これはAPI call数やcontext量ではない。`ASC_AGENT_BUDGET_MODE`は`observe`（計測のみ）、`warn`（既定、警告のみ）、`enforce`（実験的、subagentだけ強制停止）を選べる。完了済みsubagentの再利用禁止はすべてのmodeで有効。
- `ASC_AGENT_MAX_TOOLS`（10〜1000、既定120）は警告の目安であり、この変数だけではhard stopを有効化しない。残り20%と20回の小さい方から警告する。120は実測で確定した危険閾値ではない。**mainはどのmodeでもtool数によって停止しない。**
- modeと目安は新規session開始時に固定する。compact・再開・環境変数変更で回数やclosed状態を戻さない。modeのない旧記録はwarnとして読む。subagentのclosed/exhaustedは復活させない。mainはSessionEndでpaused、SessionStart(resume)でactiveへ戻り、starts/resumeAttemptsを加算してtool数と開始時刻を保持する。旧版のmain closed/exhaustedもresumeを許す。観測寿命は休止期間を含む経過時間である。
- 実験する場合だけ、新session起動前に `ASC_AGENT_BUDGET_MODE=enforce ASC_AGENT_MAX_TOOLS=120` を明示する。subagent上限後は `continue: false` で処理loopを停止し、`SubagentHandback`による結果返却だけ許す。**状態保存完了を確認してから停止する保証はなく、DRAINING / handoff専用予算は未実装。** 本番標準にせず、tools・API calls・context max・cache_read・完了状態・handoff overheadの関係を測って判断する。Stopはblockしない。
- mainの継続・resumeを許可し、Step 8後のfresh context移行は推奨とする。conversationはなくても復旧できるが、mainで残っている会話を必ず捨てる必要はない。
- 正常な終了前、または警告期間内に、Git / staging / trackerへ現在の変更と未完了状態を固定する。次のagentはIssue → worktree → staging → `workflow advance` previewの`resume` → Step skill・必要な計画節から再開する。会話summaryをauthorityにせず、既存gateがHEAD・digest・Evidenceを検証する。reviewとverificationを省略しない。

### 強制できない範囲と回復

| host / 操作 | 対応 |
|---|---|
| Claude Codeの上記event・入力を提供するhost | hook fixtureでmode境界を検証。旧実装のClaude Code 2.1.282隔離sessionで停止信号・完了agentへのSendMessage拒否・fresh agent実行を確認済みだが、新mode設定の実機保証とは区別する。他versionでの発火は利用環境で確認する |
| `SubagentStart`そのもののblock | host仕様上不可。再利用後のtoolを拒否する |
| mainのfresh session起動 | 不可。そのためmainへtool数のhard stopを適用しない |
| 自動fresh agent dispatch・保存内容の十分性 | coordinatorと既存workflow gateが担当する。short-livedは下記のpointer dispatch制約を追加する |
| modelだけのloop、hookを通らない外部process、他hookによる許可上書き、hook無効化・timeout・runtime改ざん | このhookの保証外。hostの権限・管理設定が担当する |
| Codex / hook未登録host | 未強制。prompt規律を機械強制と報告しない |

hookは進行中processをkillせず、未commit変更を削除しない。上限に達したら旧agentへ同じ要求を再送せず、fresh agentが残作業とprocessの状態を確認して引き継ぐ。異常終了は終了eventが届かない場合があり、その記録はactiveのまま残る。時刻だけから成功やclosedを推定しない。

記録はproject rootの`.agent-skill-chain/runtime/agent-lifecycle/`に保持する。session IDをhash化したfile名を使い、symlinkとhardlinkのstate fileを拒否する。worktree単位の全session共通の短い排他とatomic renameで更新する。競合は最大約0.5秒待ち、解消しなければそのtoolを拒否する。中断でlockが残った場合、実行中processがないことを運用者が確認してから当該lockだけを除く。記録破損や欠落では旧sessionを再利用しない。残存予約は新sessionだけでは解除されないため、後述の明示復旧を先に行う。障害のためにworkflow Evidenceを緩和しない。

この記録は操作の寿命を保持する運用stateであり、Planningや品質承認の正本でも、作業割当のlease台帳でもない。削除すると旧IDの履歴を失うため、実行中sessionがある間は削除しない。別worktreeは別rootとして扱い、同一session途中で`CLAUDE_PROJECT_DIR`を切り替えない。

### 計測

```sh
CLAUDE_PROJECT_DIR="$PWD" node .claude/hooks/asc-agent-lifecycle.mjs --report
```

ID・親session・開始/最終観測/終了・終了理由・tool試行数・拒否数を出力し、promptやtool本文は保存しない。`starts`は同一IDの起動回数、`dispatchAttempts`はresume/SendMessage要求数、`resumeAttempts`は再起動・session再開・拒否したdispatch要求数であり、許可済みの再開回数ではない。`contextIsolation`はhostの`agent_type`に基づき、forkは`inherited`、観測した非fork typeは`fresh`、main・旧記録・type未観測は`unknown`とする。これはhost仕様による分類であり、会話内容を検査した証明ではない。generationとは独立した値である。generationはmainが0、coordinatorからのdispatchと結合したchildが1であり、未観測の親・generationはnullとする。mainのresumeでgenerationは変わらず、subagentの再利用は禁止する。取得できないcontext量・API call数・host versionは`null`である。

`scripts/report_session_tokens.ts`の`contextPerCall`はinput + cache creation + cache readの分布、`observedLifetimeMs`は最初と最後のAPI応答間の時間を返す。hookのtool回数や実際のspawn時刻とは区別する。v0.4.18以降の導入後に新規spawnされたかは、versionとspawn証拠を別途照合してcohortを固定する。起票時baselineのraw logは本変更に含まれず、実測Before/Afterは未実施である。

参考: [Claude Code hooks](https://code.claude.com/docs/en/hooks)、[subagent resume](https://code.claude.com/docs/en/sub-agents#resume-subagents)。auto-compact 50%の設定変更は本機構に含めない。

### 標準のshort-lived方式

`install/update --root=. --apply`で必要な設定が成立する。previewは書き込まない。適用後は新規sessionを開始する。env・event一覧・timeout・CLIの絶対pathの手設定は不要である。既存sessionの保存modeは変更しない。

`short-lived`が未設定時の既定であり、`ASC_EXECUTION_CONTEXT_MODE=compatible`は明示的な互換overrideである。ASC工程担当は`workflow advance --staging=<path>`の`agentDispatch`をAgent引数として渡す。通常taskは自然言語を使える。工程担当の起動拒否をmainによる実装代行で埋めない。

共有`.claude/settings.local.json`全体は利用者が所有する。ASCはcanonical command `node "$CLAUDE_PROJECT_DIR/.claude/hooks/asc-agent-lifecycle.mjs"`に一致するentryだけを管理する。updateは重複・部分matcher・旧timeoutを同期全対象1件、30秒へ収束させ、他hook・permissions・無関係なenvを保持する。command内にpathを含むだけのラッパーは所有を推測せず保持して診断する。deleteは変更されていないcanonical entryだけを除去する。

旧設定の冗長な`ASC_EXECUTION_CONTEXT_MODE=short-lived`と、`agent-skill-chain/vX.Y.Z/dist/bin/agent-skill-chain.js`を指す絶対pathは移行時に除去する。compatibleと任意の開発・緊急用`ASC_WORKFLOW_CLI`overrideは保持する。

CLIは`.agent-skill-chain/managed-runtime`へpackage assetsとともに配布し、既存managed record・snapshot chain・hashで管理する。PATHやhandoffから実行先を選ばず、npx cacheへの参照も保存しない。workflow検証中は既存managed mutation lockを保持し、更新による混在を拒否する。中断時は既存lock復旧手順を使い、自動期限解放しない。

doctorは登録・current runtime・hookのpostconditionを診断し、不備はinstall/update経路で修復する。変更済みmanaged assetは上書きせず不健全として報告する。`runtimeVerified: false`は実hostの発火を未観測であることを表す。global/managed/plugin側の設定やhook無効化はproject-local診断だけでは保証しない。

settingsは既存mutation lock内でatomicに公開し、公開直前にも元bytesを再照合する。失敗時は既存のrecordとlockでpartial状態を検出し、復旧して再実行する。非協調的な外部editorとrenameの最終瞬間まで完全なCASを保証するものではない。

short-livedのactive review sessionの同HEADでは、既定のCorrection pointerに加え、`workflow advance`の`handoffAlternatives`が次roundのfresh Reviewer pointerを返し、`agentDispatchAlternatives`が対応するAgent引数を返す。是正が変更不要と判断したfindingは、このpointerで独立Reviewerへ誤検知再評価を依頼できる。同じstagingのactive workerが終了するまで次workerを起動できず、finding分類・HEAD照合・収束判定は既存review sessionのgateが行う。`review round --init`の同HEAD雛形生成もshort-lived（未設定を含む）の場合に限定する。compatibleの空差分拒否と、全modeでの収束済み同HEAD拒否を維持する。


- short-livedでは`subagent_type: "fork"`をdispatch時に拒否する。`SubagentStart`でforkを観測したchildも実行させない。[Claude Code公式仕様](https://code.claude.com/docs/en/sub-agents#how-forks-differ-from-other-subagents)でforkはparent conversationを継承するため、fresh workerとして扱わない。
- 通常の単発taskは自然言語promptを受理し、複数同時に起動できる。ASC工程のHEAD/role bindingは持たず、reportでは`dispatchScope: task`とし、Step/roleはnullとする。通常taskは`subagent_type`省略も受理し、開始eventのtypeでfresh contextを確認する。type未指定のpendingがある間は、ASC工程担当との誤結合を避けるためworkflow dispatchを待つ。通常taskの結果をASCのreview承認証跡として扱わない。実装後の是正・別Issueはfresh agentへ渡す。
- ASC工程担当は`dispatchScope: workflow`とする。pointerは16KiB以下の既知fieldだけのJSONとし、単独pointerまたは`{ "handoff": <pointer>, "prompt": "担当への補助指示" }`のenvelopeを受理する。補助指示はauthorityでも保存対象でもなく、workerの実行指示は担当Stepのskillを正本とする。kindまたはhandoffを宣言した壊れた構造化入力を通常taskへ格下げしない。
- hostが発行する`tool_use_id`と`subagent_type`をpendingへ保存し、対応する`SubagentStart.agent_type`を実agent IDへ結合する。ASCの同時pendingはsessionで1件、同じstagingのactive workerも1件とする。通常taskのpendingは複数保持できる。hostの開始eventにはtool_use_idが無いため、同じtypeの通常task同士は共通のlifecycle契約へ結合し、個別promptとagent IDの対応は主張しない。通常taskとASC担当の同じtypeがpendingで重なる場合は誤結合防止のため拒否する。別typeの通常taskや開始済みASC workerは、下記のwriter境界を満たす場合に並走できる。同じtypeの通常taskが先行する場合、ASC担当の起動はそのAgent呼出し完了まで待つ。未結合childは実作業を拒否する。
- dispatch時にsession lockの外で設定済みCLIのpreviewを実行し、渡されたhandoffがrepositoryから導出した値と一致することを確認する。Step/roleの自己申告だけでは起動しない。lock内ではstateとHEAD/journal境界を再確認してから登録し、CLIの待機で別taskを塞がない。開始時にworktree、branch、HEAD、staging内のsteps journal・review sessionのdigestを照合する。各worker tool前にも境界を照合する。変更は成功ではなくstaleを意味する。新しいHEADへの変更を許す成果物作成roleでもjournal/roundを跨げない。
- Step 10 Reviewerは`Read / Glob / Grep / SubagentHandback`およびhookが開始時に示す読取専用Bash commandだけを許可し、HEADと追跡・未追跡fileの未commit変更を確認する。`verify run`と同様に`git status --porcelain=v1 -z --untracked-files=all`を用い、canonical handoffが指す現在のstaging directoryだけをliteral pathspecで除外する。dispatch時・worker実行時とも候補外の未追跡fileを拒否する。Bashは設定済みCLIの`workflow advance` previewと、SHAをliteral指定した`git diff/show/log`だけを完全一致で許可し、shell連結・外部diff・textconv・書込・MCP実行を拒否する。coordinatorが差分をstaging外へ準備し、検証とround記録を行う。readiness reviewは既存の是正責務を維持する。
- workflow writer取得時は、Reviewerと同じ`git status --porcelain=v1 -z --untracked-files=all`と現在のstaging directoryだけのliteral除外で未commit変更を拒否する。trusted CLIの検証前とworktree lock取得後、SubagentStartで確認する。完了済みtoolが残したtracked・ステージ済み・untracked変更も対象で、解消またはcommitして新しいhandoffを取得する。writer稼働中の自身の編集やSendMessageではこの取得時clean条件を再適用しない。由来を推測してdirty fileを引き継がない。
- 同一worktreeに開始待ちまたは未終了の通常taskがあれば、workflow writerのdispatchを拒否する。Reviewer・coordinator以外の工程担当は、計画文書を書くroleも含めwriterとする。逆方向では通常taskを起動できるが、writerの開始待ちから終了までRead / Glob / Grep / WebSearch / WebFetchと連絡・返却だけを許可する。Bashは読取commandを含め許可せず、未知のtoolも拒否する。tool上限到達だけでは所有を解除せず、終了eventを待つ。通常task同士の並走は維持する。書込みが必要なら担当の完了を待つか別worktreeへ隔離する。worktree共通lockの下で全sessionの既存記録から占有状態を再導出し、別sessionやcompatibleのmain・subagentもwriter以外は読取と連絡だけに制限する。mainのAgent呼出しは既存のdispatch gateを満たす場合だけ許可する。mainの書込みtoolと通常Agent呼出しは完了eventまで記録し、実行途中でwriterを開始しない。
- 通常taskのactive childへの`SendMessage`は自然言語を受理する。ASC工程担当への`SendMessage`は同一pointer JSONの再送だけを許可する。別担当はfresh dispatchとする。terminal identityの再利用拒否は既存どおり。
- boundary拒否は`continue:false`を追加せず、`SubagentHandback`を許可する。workerが検証・commit・返却した後にcoordinatorがStep/roundを記録し、保存途中に境界を動かさない。例外時は成果物とprocessを確認してfresh workerへ復旧する。coordinatorも旧bindingを書き換えて再有効化しない。
- Agent完了・失敗は同じ`tool_use_id`のpendingだけを解放する。hostが完了eventを返さないときは後述のowner停止確認・digest付き明示復旧を行ってから新sessionで再開する。pendingを時刻で消さない。

SessionStartでcoordinatorへ上記の2経路とCLIからの起動方法を通知する。dispatch拒否時も`workflow advance --staging=<path>`と`agentDispatch`、旧形式の`handoff`を`JSON.stringify`してpromptへ渡す手順を示す。ASC担当の起動拒否時に、mainによる実装・是正代行や通常taskへの格下げへ切り替えない。拒否理由を修正して再委譲し、復旧できない場合は利用者へ理由を返す。この代行禁止は指示であり、mainの任意shellや自然言語taskの意味をhookが検査して強制するものではない。

`handoff`は認可tokenではなく、runtime記録は改ざん耐性のあるauthorityではない。元のStep/round/HEAD gateを必ず通す。任意shellの内部動作・hostの暗黙context継承・hook無効化・登録漏れは本hookだけでは保証できない。最初からcontextをforkしないfresh host起動を用いる。

### 追加の観測とA/B比較

対応hostでは`PostToolBatch`にも同じcommandを任意登録できる。[公式hook仕様](https://code.claude.com/docs/en/hooks#posttoolbatch)ではtool batch終了後・次model request前のeventである。`modelCycleProxy`はその観測数だけでありAPI call数ではない。event未観測は0とせずnull。toolを使わないmodel requestやretryも数えない。本文は読取JSONから永続化しない。

reportへexecutionContextMode、結合済みagentのrole/Step/review session/round/parent/generation、freshHandoffToを追加する。親子結合とcontext継承は別概念である。既存の開始・終了・観測寿命・tool試行・resume試行・終了理由も併用する。

cross-session保護には両modeの`PostToolUse`・`PostToolUseFailure`が必要である。旧compatibleの5event設定はdoctorで不合格となるため、fragmentを併合して全hostを同じhook版へ更新し、新sessionを開始する。既存のsession記録は実行時の占有情報としてのみ使用し、承認・Planning・作業割当のauthorityへ昇格させない。

異常終了後もTTLで占有を解除しない。`--report`はsessionごとのwriterReservations・inFlightWrites・pendingDispatchesと、同じbyte列から作ったrecoveryDigestを返す。owner sessionと子processの停止を利用者が確認した後だけ、`--recover-session=<sessionId> --expected-digest=<recoveryDigest> --owner-stopped`で復旧する。停止確認は明示申告であり、hookがhostの生存を自動証明するものではない。digest不一致は拒否し、復旧した旧sessionは再開できない。新sessionを使う。記録そのものの削除や時刻だけの解除はしない。

共有lockが残った場合はreportのworktreeLockと、そのdirectoryのowner.jsonを確認する。session記録作成前の中断でreportが空なら、runtime/agent-lifecycle/worktree.lock/owner.jsonを直接確認する。全host・hook processを停止し、owner PIDが動作していないことを確認したうえで利用者がそのlockだけを除去する。PID確認なしや自動TTL解除はしない。hookを通らないTerminal操作、hook無効化・改ざん、終了後も残る外部process、event未送信、protocol不参加hostの書込みをOS境界で阻止する機能ではない。main conversation自体の自動交換も行わない。

A=`compatible`、B=`short-lived`の新session cohortを同じASC commit/Claude version・モデル・同程度のIssue構成で固定する。`scripts/report_session_tokens.ts`へmainと全child logを渡し、Issue全体のtotal/cacheRead/input/output/max context/agent数/寿命/wallClockMsを比較する。`resumeOverhead`と最初のcallのcontextは初期化・再読コストのproxyであり、handoffだけに帰属する実測ではない。hook reportのtool試行・batch proxy・freshHandoffTo件数をagent IDで照合し、review sessionのround数・correction数・verification結果・finding収束・regression・利用者介入数を別途記録する。欠測はunknownとし、効果未測定で削減率を主張しない。
