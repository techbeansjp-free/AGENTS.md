# 識別子・UUID設計ガイド

## 基本方針

ワークフローの作業調整だけを目的としてUUIDを一律必須にしない。要求、Gherkinシナリオ、レビュー指摘には、人が追跡できる安定IDを使う。既存IDがある場合は再発行せず、参照関係を維持する。

利用側ドメインで全体一意性、オフライン生成、複数ノード生成等が必要な場合はUUID等を採用できる。要件がなければ、連番、自然キー、リポジトリ内で一意な人間可読IDも比較する。

## 設計時の記入項目

| 項目 | 記入内容 |
|---|---|
| 対象 | エンティティ、値オブジェクト、文書、イベント等 |
| 採用理由 | 必要な一意性の範囲と、他方式では満たせない理由 |
| 形式 | UUID版または別形式 |
| 生成 | 生成主体、生成時点、生成ライブラリ |
| 正規形 | 文字列表現、大小文字、バイナリ・DB・JSON直列化 |
| 比較 | 同値性、並び順、索引局所性 |
| 安全性 | 列挙耐性、衝突時の扱い、時刻・ノード情報漏えい |
| 公開境界 | 外部API、ログ、画面へ公開するか |
| 移行 | 既存IDとの対応、段階移行、ロールバック |
| テスト | 固定フィクスチャー、重複、形式不正、境界値 |
