# 11 プルリクエスト事前確認

§4.1を除く全項目を満たしてから`pr create`を実行する。§4.1はPR作成後の`pr-bound`で確認する。満たさない項目は理由と次の操作を残す。

| 読者 | 読む節 |
|---|---|
| 発注・評価する人 | §5 残存リスクと次の操作 |
| 実装・レビューする人 | 全節 |
| 運用する人 | §4 Git・GitHub・権限 → §5 残存リスクと次の操作 |

## 0. 対象

- 正本Issue:
- リポジトリ:
- 基点ブランチ・SHA:
- 先頭ブランチ・SHA:
- PRで許可された停止点:

## 1. 要件と変更

- [ ] 対象内の要求・要件がすべて実装済み
- [ ] 対象外を暗黙に実装していない
- [ ] 維持対象の既存動作を確認済み
- [ ] T01〜T14等のタスク追跡が完了

## 2. テストと品質

- [ ] project policy選択の言語・runnerと汎用の安定SCN IDで受け入れ例を追跡している
- [ ] 変更種別・risk・影響境界・ACから選んだVerification Setに再現可能なEvidenceがある
- [ ] project policy選択の全test layerが合格
- [ ] 型検査と既存テスト一式が合格
- [ ] project policy選択の静的検査が合格、または対象外
- [ ] 開発専用資産が配布物へ混入していない
- [ ] 秘密情報検査が合格

## 3. レビューと仕様

- [ ] 全ラウンドで肯定・敵対の両観点を確認
- [ ] 実装中発見の事実・影響・判断・対処・検証・仕様更新が最終reviewに含まれる
- [ ] 実施した最終ラウンドで全指摘を分類（指摘なしならRound 1、Critical/High修正があれば必要な範囲だけ最大Round 3）
- [ ] 未解決Critical/Highがない、または別権限者の条件付き受容がある
- [ ] `docs/specs/`を更新して要件・変更・SCN・テストを追跡した、または`no-spec-impact`の限定的根拠を記録した
- [ ] dependency/authority/evidence graphのcycle反例とdetectorが合格
- [ ] review証跡`docs/reviews/<Issue番号>_review.json`を`review export`で生成し、`review validate --artifact=<path> --staging=<staging>`が合格した（手で書かない）
- [ ] `H_impl`が`H_final`のancestorで、その差分がreview証跡だけ
- [ ] 既定branch追随を行った場合、取り込みが証跡commitより前にあり、証跡の比較基点（`baseSha`）が取り込んだ既定branch tip、`implementationHeadSha`が証跡直前の最新commitを指すよう`review export --base`で再生成した
- [ ] reviewerが`merge.reviewIndependence`の要求水準を満たす（既定`context-isolated`はimplementerと別session/context）

## 4. Git・GitHub・権限

- [ ] 正確なリポジトリ、既定ブランチ、基点・先頭SHAを再確認
- [ ] すべてのコミットを対象ブランチへpush済み
- [ ] PR本文のIssue参照が[開発ワークフロー](../../docs/01_開発ワークフロー.md)の規約に従う
- [ ] PR作成の操作authorityがあり、automaticの場合はtrusted policyをcandidate自身が変更していない
- [ ] マージ、Issue終了、ブランチ削除、release、公開、finalize、cleanupを連鎖しない

## 4.1 PR作成後のread-back（`pr-bound`で確認する）

`pr create`の前には成立しない。作成後にproviderから観測して記録する。

- [ ] trusted providerが観測したPR head、成功CI head、独立review commitが`H_final`へexact一致
- [ ] repository、PR、Actions run、immutable review IDが一致し、runの関連PR番号が対象PRだけを指す
