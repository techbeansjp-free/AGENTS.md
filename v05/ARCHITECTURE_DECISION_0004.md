# ADR 0004: グラフ型ランタイムの考え方（ループ上限・明示的状態）は導入せず、判断点の宣言は保留する

2026-11-08。状態: 判断の記録（Issue #1648）。ownerは、隔離環境での検証と、本当に必要な場合だけ実装し、不要ならEvidenceとともに参考資料として残すことを指示した。

## 決定

グラフ型エージェントランタイム（状態・分岐・ループを持つグラフでAgentとワークフローを制御する枠組み）の考え方のうち、次のA・BをASCの製品（runtime・CLI・配布Skill）へ導入せず、Cは保留する。フレームワークへの依存も追加しない。

- **A. ループの明示的な終了条件**（実装→レビュー→是正の往復に上限と打ち切り後の遷移を置く）：上限に当たるPRが少なく、価値の条件を満たさない。上限の遷移では解決できない後半の実欠陥もあり、品質の前提条件も満たさない。
- **B. 明示的な状態**（進行状態・Evidence・owner制約を構造化stateに持ち、節目ごとに新しいContextで再開する）：実測した規模では、事前に固定した採用条件を満たさなかった。
- **C. 判断点の宣言**（owner決裁が要る地点を宣言する）：保留とする。不要な停止は実在するが、待ち時間は3週間で上限約148分（中央値2分）と小さい。約半数はHostの自動承認審査の拒否に続いて起きており、ASC側の宣言だけでは変えられない可能性がある。Phase 1の対照実験では両条件とも停止が起きず、効果を測れなかった。

判定の閾値と手順は、測定の前に[測定計画](evaluation/graph-runtime/PHASE0_PROTOCOL.md)へ固定してcommitした。結果を見た後に閾値は変えていない。

## 根拠（Phase 0：過去の実データ）

対象は、v0.5移行（2026-10-16）から2026-11-08までにmergeされたPR 44件と、同じ期間のsession 275件（Codex 259・Claude 16、総処理token約23.9億）である。集計値は[Phase 0結果](evaluation/graph-runtime/PHASE0_RESULTS.json)にある。手作業の分類は、仮説を知らない別Contextに標本を分類し直させて照合した。一致率はAが6/6、Cが22/25（88%）だった。Cの一致はc1か否かの照合であり、標本にc2は含まれない（[再分類の記録](evaluation/graph-runtime/phase0-blind-reclassification.json)）。

- **A**：是正が3ラウンド以上になったPRは、数え方によって次のとおりで、いずれも閾値の20%に届かない。
  - GitHubで見えるレビュー結果だけ：1/44（2.3%）。
  - PR本文に記録された独立レビューを加える：3/44（6.8%）。
  - PR作成後のcommitを20分超の間隔で区切った塊をすべて1ラウンドと数える：7/44（15.9%）。是正の時刻や、本文だけのowner指摘を取りこぼしても、この上限推定は小さくならない。
  - PRごとに上の2つの多い方を取る（最も甘い数え方）：8/44（18.2%）。

  3ラウンド目以降にもHigh・Medium相当の実欠陥が5件あった。そのうち1件（#1615の集計範囲の誤り）は、打ち切って分割に回しても、owner判断に回しても解決できない。反例は1件だが、上限の遷移で品質を保てるという前提が成り立たない。
- **B**：入力tokenの80%は、会話の蓄積を読み直す分だった。tokenの80%は進行役sessionが使っている。節目でContextを作り直したと仮定した反実仮想では、削減率は進行役の中央値で62%になった。ただしこの推定は、作り直しても呼出し回数は変わらないと仮定している。最大のsessionは1件で全体の65%を占め、起点の取り方で判定が反転する。開発sessionの75%に、作り直すと失われうるowner制約があった。節目はcommit・PR作成・review完了のコマンドで検出しており、コマンドが成功したかは区別していない。
- **C**：許可済みの操作で止まって確認した事例（c1）が20件（境界例を含めると29件）あった。承認なしの判断点通過（c2）は3件あったが、実害は0件である。c2は3件とも実行前に止まっている。ただし抽出は利用者の発言を起点にしている。最後の発言の後に実行されたコマンドは分類の対象外だった。利用者の発言がある進行役session 16件のうち3件で、最後の発言の後に`gh pr merge`か`git push`が実行されていた。それらがownerの常設の許可の範囲内かは確かめていないので、c2の件数は下限である。止めたのはCodexの自動承認審査が2件、ownerが1件と分類した。審査の拒否は、進行役が起動した審査用subagentに記録される。拒否を親の進行役sessionへ帰属させて日時で突き合わせると、180分以内に拒否が先行していたのは次のとおりだった。これは時間的な前後関係であり、因果は確かめていない。
  - c1：20件中10件（60分以内なら6件）。
  - c2：3件中2件。

AはPhase 1へ進めなかった。BとCは、失われうる制約の多くが許可範囲であり、どちらも同じ情報を扱う。そのため、状態ファイルに目標・許可・owner制約・進捗を持たせる1つの機構としてPhase 1で試験した。

## 根拠（Phase 1：隔離環境での対照実験）

評価用の合成fixture（`test/fixtures/complex-issues/`）を、`/var/tmp`配下のlocal repositoryで使った。remote・公開はない。Agentは既存の制限付き構成で起動した。条件はCodex CLI 0.166.0-alpha.5.1、`gpt-6.1-sol`、effort mediumで、全試行で同一である。

比べたのは次の2つである。

- **baseline**：1つの進行役sessionを段階ごとに再開して続ける。
- **state**：段階ごとに新しいsessionを起動し、状態ファイルを読み書きさせる。

3段階目でowner制約（commitの末尾に`Refs: #<Issue>`）を与え、最後まで守られるかを測った。本試行の`long` scenarioは8段階で、4段階目の後に第2の単位を新しいIssueとして渡す。順序はbaseline・state・state・baselineの2組である。

| 試行 | 所要時間 | 処理token | 進行役の呼出し | 進行役の平均入力context |
|---|---|---|---|---|
| 1 baseline | 1,510.6秒 | 11,553,299 | 108 | 82.8k |
| 2 state | 1,707.4秒 | 10,074,154 | 167 | 44.4k |
| 3 state | 1,986.8秒 | 10,982,771 | 175 | 46.4k |
| 4 baseline | 1,465.4秒 | 10,811,430 | 117 | 72.4k |

採用条件の判定は次のとおりである。

- **条件1（処理tokenの中央値がbaselineの80%以下）**：94.2%で不成立。
- **条件2（2組ともstateの方が少ない）**：2組目でstateが+1.6%となり不成立。
- **条件3（所要時間の中央値がbaselineの120%以下）**：124.1%で不成立。

品質は両条件で同等だった。

- 10種のoracleはすべて合格した。
- owner制約は全試行で6/6守られた。
- 停止・実行失敗は0件だった。
- Git管理状態の照合は全試行で一致した。
- 独立した事後レビューでは、未解決のHigh・Mediumは両条件とも0件だった。レビューは、どの試行がどちらの条件かを伏せて4試行8 copyに同じ確認を行った。確認は約90件の再現probeで、テナント越境、重複効果、共有DB、通貨の改訂、旧replayを含む。

効果が小さかった理由は、新しいContextが毎回コードと状態を読み直すことにある。1回あたりの入力contextは約半分に減ったが、進行役の呼出しは1.52倍に増えた。Phase 0の反実仮想は、この読み直しを含めていなかった。パイロット（4段階、各1回）も同じ傾向で、tokenは−11%、時間は+16%だった。

Cの「不要な停止」は、両条件とも0件だった。この試験は、許可範囲を最初に明示している。その条件では両条件とも停止が起きなかったので、許可を状態に記録する効果は分離できない。

## 外挿と限界

この試験のbaseline側の進行役contextは平均72k〜83kだった。Phase 0の進行役9件は平均60k〜336kで、tokenの約99%を占める上位6件は131k〜336kである。Phase 1で測った2つの値を使ってPhase 0の進行役9件へ外挿すると、削減は約54%になる（倍率を1.3〜1.8に変えると46〜61%、最大sessionを除くと約48%）。

- 呼出しの倍率：1.52（2組の合計342/225）。
- 1回あたりの入力：初回context＋28k。28kは、state側の呼出し加重の平均入力約45.4kと、初回context約17k（全試行で16.9k〜17.0k、`PHASE1_RESULTS.json`の`coordinatorFirstContext`）の差である。

これは2組の比率による外挿であって、その規模では測定していない。試行は2組、モデルは1種、fixtureは1種である。

## 再検討する条件

次のいずれかを示せたら、新しいIssueで導入を検討する。評価資産を出発点とし、同じ測定計画で比べる。

- baseline側の進行役の平均入力contextが130k以上になるfixtureまたは実プロジェクトで、同じ採用条件（処理token 80%以下、全組で減少、所要時間120%以下、品質の非劣性）を満たす。
- Hostの自動承認審査が利用者の許可範囲を外部の記録から受け取れるようになり、その記録によって不要な停止が減ることを実測できる（Cについて）。
- 許可を途中で与えて繰り返さない試験で、許可を状態に記録した場合に不要な停止が減ることを実測できる。かつ、不要な停止の損失が、記録を保つ費用を上回る（Cについて）。
- 是正ラウンドが3回以上になるPRが20%を超え、その後半ラウンドの実欠陥が分割やowner判断でも解決できると示せる（Aについて）。

## 評価資産

`v05/evaluation/graph-runtime/`のscriptは、ソースrepository用の評価資産である。配布物（`package.json`の`files`）には含めない。session記録は私的データのため、公開repositoryには集計値だけを置く。

```sh
D=v05/evaluation/graph-runtime
node $D/phase0-loops.mjs <out.json> [classification.json] [windows.json]                 # PRの是正ラウンド（GitHub API）
node $D/phase0-context.mjs <out.json> <sinceISO> <repoPath> <excludeId> <logDir...>      # sessionのcontext蓄積と反実仮想
node $D/phase0-decisions.mjs <out.json> <sinceISO> <log.jsonl[.zst]>...                  # 判断点の候補抽出
ASC_EVAL_MODEL=<model> node $D/phase1-run.mjs <abs-tarball> <abs-codex> baseline|state [pilot|long]
```

Phase 0のscriptはNode 24で実行した。圧縮された`.jsonl.zst`の展開に`zlib.zstdDecompressSync`を使うため、Node 20では起動しない。評価期間の終わりは実行日（2026-11-08）であり、scriptに終了日時の指定はない。後日再実行する場合は、入力するlogを期間内に限る。

`phase1-run.mjs`は、`scripts/pack-candidate.mjs`で作ったtarballと、Codex CLIの絶対pathを受け取る。記録した試行はcommit `8954e939`（パイロット）と`82b59078`（本試行）の版で、Linuxのhostモードで実行した。その後の版では、各段階の前後と最終集計の前にGit管理fileを照合する。また、Agentのcommitが要件・oracleを変えていないことも記録する。試行は1つずつ順に実行する。並行して走らせると、providerの制限を共有して所要時間が歪む。集計値は[Phase 1結果](evaluation/graph-runtime/PHASE1_RESULTS.json)にある。
