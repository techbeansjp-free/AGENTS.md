# Phase 0 測定計画（#1648）

測定前に定義・対象・判定閾値を固定する。測定後に閾値を変えた場合は、変更前の閾値による判定も併記する。

## 対象
- PR：`techbeansjp-free/AGENTS.md` で 2026-10-16（v0.5移行 db49ed04）〜2026-11-08 にmergeされたPR（44件）。
- session：同期間に本repositoryまたはそのworktreeをcwdとしたCodex rolloutとClaude Code transcript（subagentを含む）。
- 公開repositoryへは集計値だけを記録する。会話本文・利用者情報・他projectの内容は記録しない。

## A. ループの明示的な終了条件
- **是正ラウンド**：PR作成後、レビュー結果（独立レビュー・CodeRabbit・ownerの指摘）を受けて行った是正commit群を1ラウンドと数える。PRごとのラウンド数Rを数える。
- **同型の再発**：同じ欠陥の型（同じ不変条件・同じ経路への指摘）が連続する2ラウンド以上に現れたPRを数える。分類は指摘の原文に基づく。
- **超過コスト**：3ラウンド目以降の開始からmergeまでの経過時間と、その時間帯のsession token。
- **価値ありの判定**：次をすべて満たす。
  1. R≥3のPRが全体の20%以上。
  2. 3ラウンド目以降の超過コストが、期間全体のPR所要時間またはsession tokenの10%以上。
  3. 上限と打ち切り後の遷移（分割・owner判断）があれば短縮できたと原文で示せる同型再発が1件以上。

## B. 明示的な状態
- sessionごとに、model呼出し数、呼出しごとの入力context（cache readを含む）、出力、総処理token、自動compaction回数、進行役とsubagentの内訳を測る。
- **蓄積の上乗せ**：呼出しごとの入力contextから、そのsessionの最初の呼出しの入力contextを引いた量の総和。
- **反実仮想の削減量**：commit・PR作成・review完了の各時点で、5,000 tokenの構造化状態からcontextを作り直したと仮定した場合の総処理tokenの減少率。上限推定であり、作り直しで失う情報による再読込みは含まない。
- **価値ありの判定**：総処理tokenの上位で全体の過半を占めるsession群で、反実仮想の削減率の中央値が20%以上。

## C. 判断点の宣言
- session内の利用者発言から次を数える。
  - **c1 不要な停止**：既に許可された、または進行役の権限内の操作について、Agentが止まって利用者へ確認した事例。
  - **c2 判断点の通過**：merge・push・権限や規約の拡大・保護fileの変更・変更範囲の拡大を、owner承認なしに実行または実行しかけた事例。
- 各事例の損失（再開までの往復回数・経過時間、または取り消し作業）を記録する。
- **価値ありの判定**：c1とc2の合計が期間内に3件以上、または実害を伴うc2が1件以上。

## 品質側の測定（2026-11-08追記）
初版はA〜Cが無いことの費用だけを測り、導入で品質を落とす経路を測っていなかった。測定の起動後に次を追加した。Aの測定scriptの生の出力は追記の約1分前に生成されていたが、進行役はその報告を受け取っていなかった。追記はAの判定を厳しくする方向だけであり、Aは既に条件1で不成立だった。

- **A：後半ラウンドの欠陥検出量**：ラウンドごとに、指摘を「実欠陥（High・Medium、コード・契約の是正を伴う）」と「好み・誤検知・Low」に分ける。3ラウンド目以降で実欠陥を検出したPRの数と件数を数える。上限で打ち切ってその欠陥を未解決のまま受け入れることは許されない。上限の遷移先は分割またはowner判断だけとする。Aを価値ありとするには、上の3条件に加えて、3ラウンド目以降の実欠陥がすべて、その遷移先でも解決できたと原文で示せることを要する。
- **B：作り直しで失う制約**：session途中で利用者が与え、その後の作業が依拠した制約・指示の件数を数える。5,000 tokenの構造化状態に入りきらない、または節目の時点で記録されていなかった制約を「失われうる制約」とする。失われうる制約が1件以上あるsessionの割合を、削減率と並べて報告する。
- **分類の独立確認**：A・Cの手作業分類は、仮説を知らない別Contextが無作為に抽出した標本（各20%以上、最低5件）を再分類し、一致率を報告する。一致率が80%未満の分類には依拠しない。
- **Phase 1の品質条件**：品質は改善目標ではなく非劣性の制約として扱う。treatmentでoracleの不合格、または未解決のHigh・Mediumが1件でも増えたら、費用の改善量にかかわらず不採用とする。費用の比較はこの条件を満たした試行どうしで行う。

## 判定の扱い
Phase 0は相関と反実仮想による上限推定であり、因果は示さない。価値ありと判定された考え方だけをPhase 1（隔離環境での対照実験）へ進める。

## Phase 1の判定基準（2026-11-08、long scenarioの実行前に固定）
- 対象はB・Cを合わせた1機構（明示的な状態ファイルと、段階ごとの新しいContext）。Aは対象外。
- パイロット（4段階、各1回）は、効果の規模と費用の見積もりにだけ使い、判定には含めない。
- 本試行は `phase1-run.mjs` の `long` scenario（8段階、2単位目を後から渡す）。baseline・state・state・baselineの順に2組行う。モデルとeffortは全試行で同一とする。
- 品質の非劣性：stateの各試行で、oracle不合格・独立した事後レビューによる未解決のHigh・Mediumが、対になるbaselineより増えないこと。stateのowner制約の遵守率がbaselineを下回らないこと。1つでも満たさなければ不採用とする。
- 採用の条件（すべて満たす）：
  1. 処理tokenの中央値がbaselineの80%以下。
  2. 2組とも、stateの処理tokenがbaselineより少ない。
  3. 所要時間の中央値がbaselineの120%以下。
- 条件を満たさなければ不採用または保留とし、測定値を記録して製品は変更しない。
