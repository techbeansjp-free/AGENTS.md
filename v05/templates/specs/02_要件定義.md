# 要件定義（入口）

> この文書は値を書かない入口である。書く内容ごとに、`details/`の正本を示す。置き場の規則は[利用案内](00_利用案内.md#置き場の表)に従う。小さな変更は、Issue・PRに要求と受入条件を書けば足り、仕様書を作らない。

| 書く内容 | 書く場所 |
|---|---|
| 要件・根拠・状態 | [要件一覧](details/02_要件/00_要件一覧.md) |
| 適用条件・受入条件・確認方法、失敗・境界ケース（前提・操作・期待結果） | [受け入れ条件](details/02_要件/01_受け入れ条件.md) |
| 業務規則・不変条件 | [業務・利用者フロー](details/01_システム概要/01_業務・利用者フロー.md)「業務規則」。機能固有の不変条件は[個別機能仕様](details/04_機能/01_個別機能テンプレート.md) |
| 非機能要件（測定条件と閾値） | [非機能要件一覧](details/11_非機能/00_非機能要件一覧.md)の索引から、各品質特性の正本へ |
| 互換性 | [利用性・互換性・保守性](details/11_非機能/02_利用性・互換性・保守性.md)「後方互換」 |
| 顧客と合意する品質保証範囲（受託開発で、保証の基準時点・責任分界・条件が変わったときの分類を合意する場合） | [品質保証範囲](details/02_要件/03_品質保証範囲.md) |
| 権限境界（許可する主体と操作） | [信頼境界・認証認可](details/10_セキュリティ/01_信頼境界・認証認可.md)「操作と権限」 |
| 未決事項・仮定 | 未決は[システム概要](details/01_システム概要/00_概要.md)「未決事項」、仮定は[制約・前提・対象外](details/02_要件/02_制約・前提・対象外.md)の「前提」 |

受入例は既存runnerの形式を優先する。Gherkinを採用する場合は[受け入れ条件](details/02_要件/01_受け入れ条件.md)の「実行可能な受け入れ例」に従う。IDは既存の命名規則を使用する。
