# 任意の仕様書テンプレート

既存プロジェクトの書式・配置・用語・IDを優先する。以下は書式がない場合の出発点であり、全ファイルの生成・読込みを要求しない。番号は分類であり実行順序ではない。

## 構成

雛形の構成は`details/`の一つだけとする。案件の規模によらず同じ構成を使い、作るのは必要なファイルだけでよい。不要なファイルは作らない。

小さな変更は、Issue・PRに要求と受入条件を書けば足り、仕様書を作らない。仕様書を作る場合も、既存Issue・OpenAPI・テスト・設計資料が正本なら参照し、重複記述を避ける。

`01`〜`06`の6ファイルは、値を書かない入口である。書く内容ごとに、`details/`のどのファイルへ書くかを示す。入口に値を書かない。

| 書きたい内容 | 入口 |
|---|---|
| 目的・対象範囲・元要求 | [要求定義](01_要求定義.md) |
| 検証可能な条件・不変条件 | [要件定義](02_要件定義.md) |
| 責務・依存関係・設計判断 | [基本設計](03_基本設計.md) |
| API・データ・処理・例外 | [詳細設計](04_詳細設計.md) |
| 画面・操作・状態・アクセシビリティ | [画面仕様](05_画面仕様.md) |
| 検証方法・運用・移行 | [検証・運用設計](06_検証・運用設計.md) |

表の補足：

- 未決事項は、該当する文書の箇所に`OPEN-...`を書いて参照する。
- 業務規則のうち機能固有の不変条件だけは、個別機能仕様に書く。
- 一覧（`04_機能/00`、`05_画面/00`、`06_外部インターフェース/00`、`08_バッチ・ジョブ/00`）は、ID・名称・状態・個別仕様への参照など索引の列だけを持つ。`07_データ/00_データ一覧.md`は、データの索引と所有者・正本・識別子・機密区分の正本を兼ねる。
- HTTP API・CLIの共通の規則（認証方式・時刻・再試行等）は`06_外部インターフェース/01_共通契約.md`に書く。
- バックアップ対象ごとの達成値は、`11_非機能/01_性能・容量・可用性.md`の目標以内であることを示す。
- 障害時の振る舞いは粒度で分ける：コンポーネント単位は`CMP`、外部の依存先単位は`03_アーキテクチャ/01_システムコンテキスト.md`、配備ノード単位は`NODE`、システム全体の災害時は`11_非機能/01_性能・容量・可用性.md`。

表にない種類の情報は、話題が最も近い1ファイルを正本に決め、他の文書から参照する。新しく決めた種類は、プロジェクトの文書にこの表と同じ形で追記する。

## 書き方

利用時は選んだ雛形をプロジェクトが認めた場所へコピーし、以後はプロジェクトが所有する。雛形の相対リンクは同じ構成を前提とする。リンク先の正本を既存の文書で管理する場合はリンクを書き換え、正本がない場合は必要な雛形も追加する。既存文書を上書きしない。`project-assets`による標準配布先は `.agent-skill-chain/templates/specs/`。同梱本体内にも `managed-runtime/v05/templates/specs/`として保持する。初回導入用のnode_modulesは配置後の参照先ではない。自動生成・自動読込み・専用Agent起動は行わない。

`{...}`は記入例のplaceholder。未確定事項は未決として、確認先と影響を記す。提案・承認済み・実装済み・検証済みを区別し、実装に合わせて元要求を変えない。各文書の状態（提案／承認済み）と確認者・根拠は、文書の冒頭に1行で書く。雛形を埋めたことは承認・検証Evidenceではない。

不要な節は省略できるが、適用される契約は省略しない。仕様変更時は関連文書を更新し、独立レビューで元要求・実差分・文書を照合する。変更不要の専用報告書は作らない。

Gherkin・DDD・層構造・採番規則はプロジェクト契約に従う。ADRは長期的な判断理由が既存資料に残らない場合だけ使用する。旧Step・Seal・Journalは必要ない。
