# 品質保証範囲

状態: {提案 / 承認済み}（確認者: {役割}、根拠: {Issue・PR等}）

> 任意の詳細雛形。既存仕様・書式・ID・設計を優先し、必要な項目だけ利用する。全カテゴリの生成・読込みは不要。例の構成・値を未確認の確定仕様として扱わない。

顧客と合意した品質保証の範囲の正本。受託開発で、納品物の保証範囲を顧客と合意する案件で使う。他の文書はWAR IDで参照する。

この文書に書くのは、他に置き場のない情報だけとする。保証の基準時点、責任分界、条件が変わったときの分類、調査を始める条件と修正の完了条件、証跡の保存、合意の記録である。保証する値（対応環境・性能の閾値・セキュリティの合格基準・受け入れ条件等）は、[置き場の表](../../00_利用案内.md#置き場の表)の正本に書き、ここには正本のIDを書く。

契約書の条文ではない。責任の期間・通知の期間・免責の範囲は契約書が正本であり、ここには契約書の該当箇所だけを書く。法的な有効性は法務が判断する。用語は、実務上の対応を「瑕疵対応」、法律上の責任を「契約不適合責任」（2020年施行の改正民法で、「瑕疵担保責任」に代わり定められた）と書き分ける。

## 条件が変わったときの分類

次は分類の例であり、案件で合意した区分と扱いに置き換える。互換性対応から改善までは、元の設計・実装に契約不適合がない場合の分類である。契約不適合の判定で契約不適合に当たるとしたものは、瑕疵対応として扱う。

| 区分 | 該当する状況 | 扱い |
|---|---|---|
| 瑕疵対応 | 保証の基準時点の環境・条件で、合意した仕様どおりに動かない | {修正・検証・完了。費用の扱い} |
| 互換性対応 | 保証の対象外のブラウザ・OSのアップデート後に動かない | {見積・承認のうえ対応} |
| 保守・改修 | 外部APIの仕様変更、OSSのサポート終了 | {保守契約の範囲で対応 / 見積} |
| 仕様変更 | 法改正・税率の変更・業務フローの変更 | {見積・承認のうえ対応} |
| 性能・インフラの改善 | 想定したデータ量・利用者数を超えた | {見積・承認のうえ対応} |
| セキュリティの強化 | 適用した基準が改訂された | {見積・承認のうえ対応} |
| 改善 | デザインの刷新・操作性の向上 | {見積・承認のうえ対応} |
| 原因と責任による判定 | 顧客側のインフラ・設定の変更後に動かない | {原因調査のうえ判定} |
| 契約不適合の判定 | 納品時の設計の不備が後で判明した | {契約不適合責任の定めに従い判定} |

判定の流れ：

```text
問題の発生
→ この文書と参照先の正本（合意済みの仕様・保証条件）と比較する
→ 契約不適合に当たるか
   当たる：瑕疵対応（修正・検証・完了）
   当たらない：保守・仕様変更・追加開発として見積・承認
   判定できない：原因調査（費用は上の表の扱い）と双方の協議
```
