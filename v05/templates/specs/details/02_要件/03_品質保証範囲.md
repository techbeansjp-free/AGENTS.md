# 品質保証範囲

状態: {提案 / 承認済み}（確認者: {役割}、根拠: {Issue・PR等}）

> 任意の詳細雛形。既存の仕様・書式・ID・設計を優先する。必要な項目だけ使う。例の構成・値は、確認するまで確定仕様として扱わない。書き方は[利用案内](../../00_利用案内.md#書き方)に従う。

顧客との合意案と合意記録の正本。受託開発で、納品物の保証範囲を顧客と合意する案件で使う。他の文書はWAR IDで参照する。案の段階では、冒頭の状態を提案、各行の状態を提案・未決・適用外（理由）のどれかにする。承認済み・合意済みにするのは、合意者が確認した場合だけとする。そのときは「合意の記録」に行を足す。

この文書に書くのは、他に置き場のない情報だけとする。保証する値（対応環境・性能の閾値・セキュリティの合格基準・受け入れ条件等）は[置き場の表](../../00_利用案内.md#置き場の表)の正本に書き、ここには正本のID（IDのない正本はファイル・節・行）を書く。

契約書の条文ではない。契約書が仕様書に優先する。契約書に同種の定め（責任期間・免責・再発・検収合格の扱い・調査費用等）があれば、ここには条項の参照だけを書く。法的な有効性と契約上の分類は法務・契約が判断する。用語は、実務上の対応を「瑕疵対応」、法律上の責任を「契約不適合責任」と書き分ける。契約不適合責任は、2020年施行の改正民法で「瑕疵担保責任」に代わり定められた。

## 条件が変わったときの分類

社内の対応区分の例であり、法的な結論ではない。案件で合意した区分と扱いに置き換える。契約上の分類は、下の判定の流れの2で権限者が決める。

| 区分 | 該当する状況 | 扱い |
|---|---|---|
| {瑕疵対応} | {判定の流れの2で、権限者が瑕疵対応と分類したもの} | {扱い} |
| {互換性対応} | {保証の対象外のブラウザ・OSのアップデート後に動かない} | {扱い} |
| {保守・改修} | {外部APIの仕様変更、OSSのサポート終了} | {扱い} |
| {仕様変更} | {法改正・税率の変更・業務フローの変更} | {扱い} |
| {改善} | {想定を超えたデータ量・利用者数、適用した基準の改訂、デザインの刷新} | {扱い} |
| {原因の調査が必要} | {顧客側のインフラ・設定の変更後に動かない} | {扱い} |
| {権限者の判断が必要} | {検収後に、合意した仕様・条件との差異が判明した} | {扱い} |
