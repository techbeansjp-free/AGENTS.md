# create-pr-review-issue — 出力フォーマット（固定）

本 worker が指摘抽出・トリアージ・対応方針で用いる**データ形式はコード上で固定**する。AI 補助で中身を生成するが、入出力の形はこの仕様に従う。

**本ファイルの責務（単一正本）**: `Disposition`（三値）・`TriageRow`・**起票条件チェックリスト（C1〜C5）**・見送り理由・`security_flag` のデータ形式を **1 か所の正本**として固定する。command / worker README / 00_TEMPLATE_MAPPING は本ファイルを**参照**し、これらの定義を再定義しない。横断ルール（サブによる独断起票禁止・Go は進行役・進行役の直接 Edit 禁止）は本ファイルの責務外であり、`skills/agent/run_command.md` §Forbidden / Execution Path Rule・CORE / PHASES を正本とする（本ファイルでは再定義しない）。

---

## 1. ReviewFinding（1 件あたり）

| フィールド | 型 | 必須 | 説明 |
|------------|-----|------|------|
| **id** | string | 必須 | 指摘ごとの一意 ID（連番 `finding-1` または PR 側 ID を流用） |
| **file** | string \| null | 任意 | 対象ファイルパス（分かる範囲で） |
| **location** | string \| null | 任意 | 行番号やセクション（分かる範囲で） |
| **summary** | string | 必須 | 指摘内容の要約（1 文程度） |
| **raw** | string | 必須 | 元のテキスト（トレーサビリティ用） |

- 複数件は配列 `ReviewFinding[]` で扱う。
- review_comments_raw を行単位またはコメント単位で分割し、明らかに指摘でない行は除外してから各要素を上記フィールドにマッピングする。
- **本改定で ReviewFinding の形式は変更しない**（既存互換）。

---

## 2. Disposition（三値の処置・列挙）

各指摘の最終処置（disposition）は次の**三値**とする（二値にしない）。

| 値 | 意味 | 実施経路 |
|----|------|----------|
| **即時対応** | 現 PR ブランチ内で修正 | **委譲実行**（進行役は直接 Edit しない）＋テスト green 維持ゲート |
| **起票** | 非可逆的対応として追跡・起票 | 既存起票フロー（`90_issues/{ディレクトリ名}/`。§5 参照） |
| **見送り** | 対応しない | 理由（`defer_reason`）必須記録のみ |

- 「即時対応」の実施は**委譲実行**である（進行役が自らファイルを Edit しない。正本: `skills/agent/run_command.md` Execution Path Rule）。
- 起票・即時対応の実行 Go はサブではなく進行役が出す（正本: `skills/agent/run_command.md` §Forbidden「サブによる独断起票」・CORE / PHASES）。サブは提案（トリアージ表）に留める。

---

## 3. TriageRow（トリアージ表・1 指摘あたり）

ステップ 1（サブの独立技術評価）の出力は、全指摘一括のトリアージ表 `TriageRow[]` とする（列: 指摘 / 判定案 / 根拠）。指摘 1 件ごとに 3 ステップを個別往復させない。

| フィールド | 型 | NULL | 説明 |
|-----------|-----|------|------|
| **finding_id** | string | NO | 対応する `ReviewFinding.id` |
| **disposition_proposal** | Disposition | NO | サブの判定案（即時対応／起票／見送り） |
| **matched_criteria** | IssueCriterion[] | YES | 該当した起票条件（1 件以上で起票側デフォルト。空＝非該当） |
| **rationale** | string | NO | 根拠（該当した起票条件項目名／即時対応の目安充足／見送り理由）。主観語「非可逆」を判定式の語として用いない |
| **security_flag** | bool | NO | セキュリティ関連か（true なら軽微でも記録・監査必須。§4 参照） |
| **defer_reason** | string | YES | `disposition=見送り` のとき必須（例: AI 誤検知） |

- **不変条件**:
  - `matched_criteria` が空集合でない ⇔ `disposition=起票`（保守側デフォルト）。
  - `disposition=見送り` ⇒ `defer_reason` 非空。
  - `security_flag=true` ⇒ disposition に関わらず 00 へ記録・監査対象。

## 4. 起票条件チェックリスト（IssueCriterion・保守側デフォルト）

起票要否は「非可逆」の主観判定ではなく、**操作可能な代理指標チェックリスト C1〜C5（名前付き項目の closed set）**で判定する。**1 つでも該当したら `disposition=起票` に倒す（保守側デフォルト）**。本表がデータ形式の正本であり、command / README / 00_TEMPLATE_MAPPING / 各 issue ドキュメントは本表を参照する。

| コード | チェック項目 | 該当時 |
|------|----------|--------|
| **C1** | 仕様・受け入れ基準の変更を伴う（**契約/後方互換を壊す breaking change を含む**） | **1 つでも該当したら disposition=起票**（保守側デフォルト） |
| **C2** | 設計判断（02_設計 の修正）が必要 | 同上 |
| **C3** | PR スコープ外 | 同上 |
| **C4** | 複数指摘に共通する根本原因がある（個々は軽微でも合算で起票側へ） | 同上 |
| **C5** | **非可逆または破壊的な副作用を伴う、または起票要否の判定が不確実**（データ削除・スキーマ破壊的変更・データ上書き / マイグレーション・外部公開 / 送信・リリース済み成果物の変更等、取り消しコストが高い変更。判定に必要な情報が不足する場合を含む） | 同上。C5 は当初基準「非可逆」を代理指標 C1〜C4 が取りこぼさないための **fail-safe 項目**。疑わしきは起票へ倒す |

### 4.1 即時対応の許容ゲート（C1〜C5 いずれも非該当が前提）

`disposition=即時対応` は、**C1〜C5 のいずれにも非該当**であり、かつ次を満たす軽微指摘に限る。

- 現 PR ブランチ内の **1 コミットで完結**する。
- 既存テストが **green のまま**維持される。
- diff が**局所的**（typo・lint・コメント・単一関数内）。

修正が既存テストを壊す場合、**またはテストが実行不能・タイムアウト・flaky で green を確定できない場合**は、即時対応の green を確認できたとみなさず、軽微判定（即時対応）を**取り消して起票側または再評価へ回す**（不確実なら安全側へ倒す fail-safe。C5 と整合）。

### 4.2 「非可逆」と「破壊的」の振り分け

- データ削除・上書き・マイグレーション等の**破壊的操作は原則として非可逆**（実行後に元へ戻せない）であり、**C5** の中核をなす。
- 契約 / 後方互換を壊す「破壊的変更（breaking change）」は、データの非可逆性というより仕様・受け入れ基準の変更に近く **C1** で捕捉する。
- 列挙 C1〜C5 は closed set だが、C5 が「非可逆／破壊的な副作用・判定不確実」の catch-all を担うため、C1〜C4 に厳密一致しない非可逆・破壊的ケースや情報不足ケースも C5 で起票側へ回収される（原基準「非可逆」の取りこぼしを防ぐ）。

### 4.3 見送り（理由付き）

- 「見送り」は AI レビューア（CodeRabbit 等）の**誤検知**などを対応しないと決めた正式な処置カテゴリである。
- `disposition=見送り` のとき `defer_reason`（見送り理由）を**必須**記録とする。無理由の見送りは認めない。

### 4.4 セキュリティ指摘の記録・監査必須と一括承認からの分離

- `security_flag=true` の指摘は、disposition が**即時対応であっても** 00 へ記録し監査対象とする。無記録での即時対応を認めない。
- `security_flag=true` の指摘、および **C5 該当**の指摘は、トリアージ表で**視覚的に分離して提示**し、進行役の一括承認に**埋没させず個別に承認**する（効率化＝一括承認が、セキュリティ影響や非可逆な副作用を持つ指摘の無自覚な素通し＝rubber-stamp を招かないための安全策）。

## 5. strategies / disposition の 00_要求定義.md への反映

- **指摘一覧セクション**: `ReviewFinding[]` を表形式で展開する。各行に id / file / location / summary に加え、**disposition（確定値）／根拠（rationale）／該当起票条件（matched_criteria）／security** を記載する。raw は必要に応じて折りたたみで参照可能にする。記録先・列の詳細は [00_TEMPLATE_MAPPING.md](./00_TEMPLATE_MAPPING.md) を正本とする。
- **strategies（対応方針案）**: 各 `finding.id` に対応する対応方針案テキストを、当該指摘の disposition・rationale と整合する形で記述する（型は `map<finding.id, string>`。各 finding.id に key が 1 つ以上存在すること）。方向性は次のいずれか:
  - **即時対応**: どのファイルのどのルール・記述をどう修正するか（委譲実行で現 PR ブランチ内に反映）。
  - **起票**: 該当した起票条件（C1〜C5）を根拠に、どんなサブ issue を立てるべきかの概要。
  - **見送り**: 対応しない理由（`defer_reason`。例: AI 誤検知）を 1 文で。
- **一括承認ブロック**: 進行役の一括承認記録（承認者・日時・方式・個別修正した finding.id 一覧）を 00 に持たせる。マッピングの正本は [00_TEMPLATE_MAPPING.md](./00_TEMPLATE_MAPPING.md)。

## 6. エラー時フォーマット

- **指摘一覧が空**: `ReviewFinding[]` が 0 件の場合、00_要求定義.md の指摘一覧セクションに「指摘一覧が空です。手動で指摘を追加するか、review_comments_raw を再入力してください。」と記載する。`TriageRow[]` は 0 行、strategies は空の map でよい。
- **PR URL 不正**: pr_url から PR 番号を抽出できない場合、00 の参照元に「PR を一意に特定できるか不明です。有効な PR URL を確認してください。」と記載する。ディレクトリ名のプレフィックスは「PR不明」等のフォールバックを用いてよい。
- **起票条件の判定に必要な情報が不足**: 判定を保守側（起票）へ倒す（保守側デフォルト。C5 と整合）。
