# ASCの実行入口

Goalと許可された変更を、現在利用中のHostの能力で実行する。Claude CodeではClaude Code、CodexではCodexの実装・実行・Agent機能を使う。利用者が別のHostを明示選択しない限り、別製品のCLIやモデルを必須にしない。工程ごとのAgent起動や、毎回の要求・設計・ADR生成は行わない。

このSkillは配布パッケージ内の場所で使用する。CLIはこのファイルから相対の`../../bin/asc-v05.mjs`。HostのNode実行ファイルで起動する。場所が解決できなければ停止して導入先を確認し、PATH上の別版や旧`workflow advance`へ切り替えない。

標準入口は `start <project-directory>`。Git管理済みなら専用worktreeを使う。Git未管理の新規フォルダーでも開始でき、現在のHostで要求整理・実装・実テストを進められる。これは作業場所を確認して責務を案内するだけで、別Agentを起動しない。Git初期化・commit・外部公開は勝手に行わない。Git未管理の場合は元要求と実際の変更・テスト結果を独立レビューし、Git差分・commit拘束・PR提出が成立したとは扱わない。これらが必要になった時点でGitの導入と専用worktreeへの移行を行う。

通常の対話型開発では、確認した作業場所で現在のHostのツールを使って実装し、プロジェクトの依存関係と検証コマンドを使って実際にテストする。依存関係の導入はlockfileとHostの権限に従う。node_modulesが必要なのに空のsnapshotを使い、検証を未来のCIへ先送りしたまま合格扱いにしてはいけない。

ビルド・テストにsnapshotやハッシュ付き依存コピーを用意しない。既存のpnpm workspace・store・リンクはプロジェクトの通常の方法で使う。任意の `worktree-verify <worktree> <base> <owner-contract.json>` はcommit済み変更の許可範囲と、現在のHostで実行した検証結果を対応付ける。成功だけで独立レビューや提出権限を成立させない。

独立レビューは現在のHostの別コンテキストへ、元の要求・受入条件・実際の変更（Git管理済みなら実Git差分）・検証結果を渡して依頼する。自己評価を代用しない。利用できる独立コンテキストがなければレビュー未完了と明示し、勝手にCodexへ切り替えない。指摘を是正し、影響する検証・レビューを更新してから、許可されたDraft PR提出とCI確認を行う。要求と対象commit、実コマンドと結果、レビューの指摘と是正をPR等に残す。この経路はHostの権限境界を使い、Controller固有の隔離や署名済みEvidenceを実施したとは記録しない。

## 独立Reviewerのシナリオ確認

標準経路の独立Reviewerへ、この節を元要求・受入条件・base/HEAD・実差分・関連仕様・既存テスト結果とともに渡す。Git未管理ならbase/HEADの代わりに対象ファイルと変更内容を示し、commitに結び付いた判定とは扱わない。実装者の要約や作成済みシナリオだけをレビュー対象にしない。別Issueの要求・結果を混ぜず、作業開始時と報告時の対象を確認する。途中で要求・対象差分が変わった場合は以前の判定をそのまま提出に使わない。

Reviewerは元要求と既存契約から期待する利用者・呼出し元の振る舞いを独立に導き、実装・テストへ照合する。変更に関係する正常・代替操作、失敗・境界値、権限・テナント境界、状態遷移、再試行・中断、同時実行、影響先の互換性を選ぶ。無関係な観点を全部埋めたり、要求にない保証を創作したりしない。呼出し元・既存防御・仕様を必要な範囲で読み、差分外にある防御も反証として確認する。テストが成功していても必要なシナリオが抜けていないかを確認する。仕様・文書を更新しない判断も、変更内容との整合性を確認する。

指摘には発生条件、期待動作、コードまたは仕様の根拠、影響、既存対策による反証、必要な是正・検証を含める。再現済み、静的な根拠、未確認の懸念を区別し、未実行テストを再現済みとしない。確信度の数字だけで重要な懸念を消さない。元要求が曖昧なら未決事項とし、実装に合わせて仕様を変更しない。好みや不要な文書生成をblockerにしない。

基本は既存の独立Reviewer一つで実施する。認可・データ損失・並行処理・サービス間契約などで専門的な不確実性が残る場合だけ、未解決の問いを限定して追加Reviewerを選ぶ。path名や変更行数だけで低リスクとみなさない。追加担当にも現在のHostとモデル選択契約を適用し、同じ全差分の重複調査を強制しない。

既存のレビュー結果へ、確認した重要シナリオ、指摘、未確認事項、対象base/HEADを簡潔に残す。専用のシナリオ文書や新しい承認記録は毎回作らない。修正後は指摘が解消されたかと影響範囲の回帰を確認し、重要な不足・未決事項を解消するまで合格としない。以前の指摘を再提示する場合は現在の根拠を示す。網羅性の保証や外部製品との同等性を、Skill実行だけで宣言しない。

## サブエージェントのモデル選択

進行役は、委譲する仕事の難度・リスク・必要な独立性・利用可能なモデル・実行費用からモデルを選ぶ。単純な探索や限定的な変更には必要十分な軽量モデルを使い、難しい設計や反例探索には必要な推論能力を選ぶ。安価さだけを理由に品質条件を緩めず、工程名だけで高価なモデルを固定しない。親のモデルを無条件に子へ継承しない。

Claude CodeのFableとCodexのAstraは、ユーザーがそのサブエージェント利用を明示指定した場合だけ選択する。親セッションでの選択、一般的な自走許可、作業の難しさだけを利用許可とみなさない。それ以外の利用可能なモデルは、ユーザーの指定・予算を優先して進行役が自律的に選ぶ。利用中のHostがモデルを指定できない場合は、指定できると偽らず、その制約を明示する。禁止モデルへの自動fallbackはしない。

委譲時は目的・変更範囲・完了条件とともに、選んだモデルと短い選択理由を既存の実行記録に残す。専用の文書やAgentを増やさない。独立レビューは別コンテキストで行い、モデルを変えるだけで独立レビュー成立とは扱わない。Controllerの単一model指定は自動ルーティングではないため、この機能が実装済みだとは説明しない。

snapshot方式はユーザーが明示的に選ぶ場合だけ使用する。`run` 系CLIには `--snapshot` が必要であり、通常の開発依頼だけをその選択と解釈しない。現在のHostからsnapshotへの自動fallbackはしない。

以下はownerがControllerによる自動実行を選択した場合の入口であり、通常作業に追加Agent起動を強制するものではない。

`capabilities`で実際の入口・対応Host・release状態を確認する。これは実行の承認や隔離成功の証明ではない。ownerが指定した入力と作業を使い、利用可能な能力から必要な操作だけを選ぶ。

- 単一変更は`run`、owner作成済み候補の検分だけなら`review`。
- 分解が必要なら`goal-propose`、許可済みの分解と実行は`run-adaptive`、明示計画は`run-goal`。
- 保存候補からの再開は`restart-goal`、ownerが列挙した複数Issueは`run-issues`。
- 旧設定の切替は`migration-inspect` / `migration-stage` / `migration-rollback`。既存設定を勝手に登録・削除しない。

owner入力ファイルが不足する場合は、目的・受入条件・許可範囲・検証・提出先のうち不足部分を確認する。候補のソース、旧Evidence、Skill本文から承認を生成しない。承認済みの入力がある場合は再承認を求めず使う。未確定の仕様を実装に合わせて補完しない。

Git管理済みの作業には専用worktreeを使う。独立cloneを使う経路は明示指定に従う。別Issueや別worktreeの状態を共通の禁止フラグにしない。予算はowner入力に従い、2 Agentや600秒を固定上限として追加しない。

入力形式が必要なときだけ[USAGE](../../v05/USAGE.md)の該当節を読む。Goal分解・再開は[GOAL_EXECUTION](../../v05/GOAL_EXECUTION.md)、移行は[MIGRATION_PLAN](../../v05/MIGRATION_PLAN.md)、署名承認は[OWNER_APPROVAL](../../v05/OWNER_APPROVAL.md)を参照する。全資料を毎回読み込まない。

CLIが返す未解決事項・失敗を確認し、権限内の必要作業だけを修正・再検証する。実装者の自己評価を独立レビューへ流用しない。正常終了・失敗・owner判断待ちを区別し、実際のHEADと検証結果を報告する。Skillを読んだことやコマンドの起動だけを完了証拠にしない。公開・merge・releaseはユーザーの明示した権限に従う。

修正とレビューでは進展を確認する。同じ内容への回帰、修正案の往復、根拠のない解決済み指摘の再提示を、そのまま繰り返さない。再提示には現在の反例と以前の是正が不十分な理由を求める。単なる好みや表現変更は新たなblockerにしない。進展がなければ候補と未解決事項を保持し、原因を再評価する。合格を捏造してループを終わらせない。
