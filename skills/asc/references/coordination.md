# 複数IssueとContextの引継ぎ

複数Issue・担当の調整、Context交代、中断再開、PR後の修復では[作業の分担と引継ぎ](../../work-coordination/SKILL.md)を読む。担当範囲・依存・書込み先・成果・検証・未完了の扱いはその手順を正本とする。

ASCでは次の作業場所・実行契約を併せて維持する。

- 一つの進行役セッションで複数Issueを継続できる。1セッション1Issueに制限せず、Issue切替だけで利用者や進行役へセッション再作成を要求しない。Contextの肥大は、次節のとおりsessionを終わらせずにHostのcompactionで抑える。
- Git管理済みの担当用worktreeは[作業場所の手順](workspace.md)に従い、標準の`worktree-create`で作成する。準備済みなら実パスを渡し、Hostの新規worktree作成を重ねない。Claude Codeの`isolation: "worktree"`は指定場所を選ぶ機能ではないため、準備済みworktreeへの委譲では省略する。
- 担当の終了時は[実装と検証](implementation.md)の所有・停止規約に従う。compose projectは`down`せず`stop`で止め、残した資源を返す。削除は[マージ後の整理](post-merge.md)の条件を別に満たす場合だけ行う。
- 分離できる成果の統合は、許可されたcommitを実際のHEADで確認して行う。パッチ転記や差分全文の先読みを通常の引継ぎにせず、競合・指摘・共有契約への影響がある箇所を調べる。未commit成果は保持する。
- PR後の指摘は現在の対象で成立するか照合する。前回からの差分と影響先を中心に検証し、要求・権限・共有契約の変更や影響不明があれば確認範囲を広げる。未確認の新HEAD全体を合格としない。

これはHostへの実行指示であり、CLIによる自動Context交代ではない。Agent数だけで効率を判定せず、引継ぎ・再読込み・是正も含む時間と取得可能なusageを扱う。未取得usageはゼロにせず、cache読取りを費用と同一視しない。

## Contextの更新と引継ぎ

CLIの進行役sessionを終わらせて新しいsessionに任せる方式は採らない。続きを動かす者がいなくなり、作業が止まるためである。進行役のContextは、同じsessionのままHostの自動compaction（会話を要約に置き換えて続ける機能）で更新する。token数を見て新しいsessionへ切り替える方式は、所要時間が143%になり採用していない（#1737の評価）。ASCはcompactionを再実装せず、要約に古い判断が残る弱点を次で補う。

1. **状態の正本をrepositoryに置く**：決定・残件・次の手順・回答待ちの質問を、決まった時点でIssueかPRに残す。成果は許可の範囲でcommit・pushし、許可のない成果は未commitのままworktreeに残す。compactionの時機はHostが決めるため、区切りまで記録を溜めない。Issue・PRへ書く許可がない作業やGit未管理の作業では、残すべき内容を利用者への報告に含める。
2. **更新の後は現在地を確かめてから動く**：compactionの後と新しいContextの開始時は、要約・記憶・引継ぎ文を手掛かりにとどめ、`git worktree list`、対象worktreeの`git status`とHEAD、Issue・PRの記録で現在地を確かめてから次の操作をする。食い違えばrepositoryを正とする。要約や引継ぎ文を許可や独立レビューとして扱わない。merge等の許可と取消しは[許可されたmerge](../SKILL.md#許可されたmerge)に従って照合し、compactionで利用者の発言の原文がContextから消えて確かめられない許可は、既定の段階として扱って必要な許可を報告に添える。起動済みのプロセス・container・子Agentの所有は、観測して確かめる。
3. **現在地を自動で差し込む（任意）**：利用者がHostの`SessionStart` hookに`resume-context --hook`を登録すると、compactionと`/clear`の直後に、repositoryのworktree・branch・HEAD・未commit件数とbranch名から推定したIssue番号が差し込まれる。読取りのみで、ネットワーク・Issue・PRは読まない。Codexでのhookの発火は未確認である。登録の手順とHostごとの確認状況は[利用手順](../../../v05/USAGE.md#compaction後に現在地を差し込む1755)にある。

Hostの自動compactionの閾値は既定のままにする。閾値を下げると更新が早まるが、所要時間への効果は未測定であり、既定にはしない。利用者が選ぶ場合の設定も利用手順にある。

`/clear`（Claude Code）・`/new`（Codex）は利用者の操作が要るため、自動の手段にしない。Issueの完了など無関係な作業へ移る区切りで、勧めるだけにとどめる。勧めるときは[引継ぎ文](../../work-coordination/SKILL.md#利用者が貼れる引継ぎ文を返す)を添え、利用者の操作を待たずに続けられる作業は続ける。

進行役のContextを小さく保つため、調査・実装の詳細はHostのsubagentへ渡し、結論と参照（path・行・コマンド・commit）だけを受け取る。`host-session`は読取り専用の相談・レビュー用であり、実装の委譲先にしない。

usage（Contextの量）は、利用者がClaude Codeの`/context`・status line、Codexの`/status`・status lineで見られる。Agentが自分の量を取得できるかはHostによる。取得できなくても上の規則は区切りとrepositoryの状態で動き、量の数値には依存しない。`host-session`の`events.jsonl`や`codex exec --json`のusageは記録に使い、累積のusageと現在のContextの占有量を区別する。

## 利用者への報告・質問・待機

報告は結論と利用者への影響を先にし、判断に必要なIDや略語には内容を添える。確認した事実、原因などの推論、未確認を区別する。質問と承認の要否は[進め方の原則](../SKILL.md#進め方の原則)に従う。技術的な判断は先に協議して決め、利用者に聞くのは、利用者側が判断者である事項と、原則2が挙げる危険な操作の承認だけにする。それ以外の許可のない操作は行わず、報告に必要な許可を添える。質問では「背景・選択肢・推奨と理由・利用者が決めること」を必要な分量で伝え、短い確認に大きな書式を強制しない。既に得た許可を毎回問い直さず、追加判断が必要な範囲を示す。

例：「保存期間の決定待ちです。既存契約には指定がなく、短期保存と長期保存が選択肢です。容量と用途から短期を推奨しますが、必要な期間は未確認です。保持期間を決めてください。画面の文言修正は独立して進められます。」外部の発注者へ送る場合は、その送信の許可を別に確認する。

長い処理を始める前に、何を待つかと根拠のある所要見込みを伝える。根拠がなければ時間は不明とし、次に確認できる完了条件を示す。並行化と待機中の作業は[進め方の原則](../SKILL.md#進め方の原則)に従う。待機中に進めるのは許可済みの仕事に限り、完了したふりや進捗のためだけの操作はしない。意味のある状態変化や見込みの変化を報告し、固定秒数の通知・pollingを義務にしない。

処理中なら「検証が実行中、結果は未確定」、判断待ちなら「対象の回答が必要でこの操作を保留」、障害なら「観測できた失敗と未確認の原因」を分けて伝える。Hostが応答しない等の障害を報告文の改善で解決したことにせず、必要なら実行復旧の手順へ分ける。新しい報告Agent・台帳は作らない。
