# 適用条件と反例

以下は適用条件によって判断が変わる例である。特定案件での結論を、別の案件の禁止事項にしない。

| 強すぎる一般化 | 条件を残した判断 |
| --- | --- |
| コードとテストが正本なので要求と異なっていても正しい | 現在の振る舞いと、合意された期待動作を区別する。テストも誤り得るため、要求への適合を別に確認する。設計書の背景や制約まで捨てない |
| 要求から試験への一方向の対応は後戻り禁止を意味する | 目的と成果の対応を追う。試験で矛盾や不足が分かれば、必要な要求確認や設計の見直しへ戻る |
| 運用は常に一つのサービスへ集約する | 集約による負担削減と、権限分離・障害影響・移行費用を比較する。集約自体を要件にしない |
| 再発防止には必ずチェックリストと自動テストを両方追加する | 既存の強制点や手順で防げるか確認し、繰り返す失敗に効く手段を選ぶ。一度きりの作業へ無用な保守を増やさない |
| 常に旧版の操作を維持する | 移行で維持する操作と意図的に変更する要求を特定する。旧版も改善対象になり得る |
| 未検査ならすべての作業を停止する | 未検査を合格としない。必須保証が欠ける操作の有効化を止め、依存しない作業は進める |
| 根拠不足なら何も答えない | 断定を避け、分かる事実・仮説・確認方法を示す。仮説を決定へ昇格させない |
| NAT・EC2・バッチは不要 | 通信先、実行形態、必要な副作用から要否を決める。日時から表示を計算するだけなら定期更新は不要でも、期限時の通知等には別の実行手段が必要になり得る |
| マネージド基盤ならCVE対応不要 | 対象の実体、責任分界、到達可能性と公式情報を確認する。サービス名だけで非該当にせず、期限だけを理由に必要な安全確認を省略しない。残るリスクの受容は既存の承認手順に従う |
| テナントや履歴は全データに必須、物理削除は禁止 | 製品の所有・監査・保持・削除要件に従う。不要な多テナント化や無期限保持を追加しない |
| 既存システムへの影響は常にゼロ | 許可されていない影響を防ぐ。移行等の意図した影響には範囲・検証・復旧条件を持たせる |
| UIで作れないfixtureは禁止 | 利用者受入・デモでは実到達可能な状態を使う。拒否・破損・移行・障害試験では目的を明記して異常状態を作れる |
| 正常系は減らせばよい、検証は必ず10分以内 | 必須の保証と代表経路を維持する。対象リスクに見合う上限を置き、計測して短縮する |
| 未確認や保留は存在してはいけない | 完了扱いと未確認を混ぜない。必要な未決は、解消条件と有効化前の作業を具体化する |
| 共通化・拡張性は常に優先 | 実在する共通責務をまとめ、現時点の要求や具体的な変更見込みがない抽象化を増やさない |
| 並べ替えはドラッグだけ、認証切れは必ずモーダル | 既存の操作慣習、キーボード利用、回復経路、入力保持から選ぶ。過去のUI方式を唯一の手段にしない |
| 問題を見つけたら全部直し、必ずIssueを投稿する | 許可された範囲は完遂する。範囲外は影響・対応案を残し、投稿や範囲変更の権限を確認する |

## 機能設計で条件を具体化する

対象の機能を設計・レビューするときだけ使う。基盤全体の再構築や、以下の方式の一律採用を要求しない。

| 対象 | 判断と受入への接続 |
| --- | --- |
| 規約の例外 | 既存の承認手順に従い、対象・理由・代替案・期限または解消条件を限定する。チケット運用があれば対応する記録へ結び付ける。型抑制やlint除外で黙って必須保証を消さない |
| 識別子・採番 | 合算や連携の具体的な見込みがあれば、名前空間・形式・一意性・発番主体を揃える。既存IDの互換性を保ち、見込みだけで汎用採番基盤を増やさない |
| 認可 | Web/APIでは信頼できるサーバー側で一貫して判定し、許可を確認できない操作は拒否する。役割・資源の所有・操作対象の範囲を区別し、tenantがある場合は境界を含める。UIの非表示や推測困難なIDは認可の代替にしない。表示上の操作可否はサーバーと整合させる |
| 保存と証跡 | 現在値、変更履歴、所有者が必要かを業務・監査・保持要件から決める。履歴が必要なら現在フラグだけで代用せず、過去の証跡の訂正は元を残す訂正記録や版で追跡する。必要な削除や保持期限は別に満たす |
| 外に返す情報 | 応答・ログ・外部への報告は必要な項目と共有先に限定し、秘密・個人情報・内部詳細を除く。識別子の推測が脅威になる場合は推測困難性も検討するが、アクセス制御を省略しない |
| 移行の利用者負担 | 保存済み設定・認証状態・操作の継続条件を確認し、不必要な再設定を避ける。期限変更の猶予は互換性と安全要件を両立する範囲で決め、移せない秘密や失効済み資格情報を無理に継承しない |
| ログ障害と業務継続 | 監査の欠落が許容される操作かを先に決める。停止が必要な操作と継続可能な操作を分け、必要に応じて退避・再送・欠落検知を設計する。ログ失敗を無視して成功扱いにせず、全業務停止も無条件に選ばない |
| 操作の慣習と負担 | 既存製品・対象プラットフォームの操作慣習、キーボード等の代替手段を確認する。安全のために確認や制限を加える場合も、対象リスクと仕事を完了できる回復手段を示す。使えなくする制限と無根拠な防御解除を避ける |
| 異常時の表示 | 利用者がどこで何をすれば回復できるかで選ぶ。入力箇所の修正はその近くに、操作を妨げない一時通知はトースト等に、継続に必須の判断はダイアログ等に、画面自体が成立しない場合はエラー画面にする。認証切れを常にモーダルとせず、再認証と入力保持の経路を選ぶ。重要な対処を消える通知だけに置かない |
| 異常時の文言 | 原因が分かる範囲と利用者の次の行動を短く示す。原因・対処が収まれば1文にし、理解やアクセシビリティを損なう文字数制約にしない。内部エラー名を見出しにせず、入力保持・再試行・取消しと実際の副作用を一致させる |

## 判断の確かめ方

過去と同じ単語が出た際に同じ結論を出すだけでは効果の証明にならない。条件を変えた対になる例で、追加構成が本当に不要な場面と必要な場面を区別できるか確認する。利用者からの修正は、その場の前提とともに狭く反映し、一度の指摘を全案件の禁止事項へ拡大しない。

## 構造と運用の条件

- 一覧の0件と、単一資源の不存在を分け、既存API契約に従う。空の集合を異常と決めず、全応答を同じステータスへ統一しない。
- 金額は通貨・桁数・丸め・外部契約に適合する整数最小単位または正確な十進表現で扱う。固定の通貨や桁数を持ち込まない。
- 既存部品の変更では拡張点・wrapper・直接修正の影響と保守費を比較する。継承やwrapperを常に必須とせず、不具合の正本を放置しない。
- 本番調査は利用可能な証拠を保全し、許可された読取りから始める。再現手順がなくてもログや変更差分から条件を絞れる。書込み・本番データの取得は必要性と操作権限を確認し、本番データの複製を全案件の検証条件にしない。
- 切替えでは件数だけでなく、業務上の金額・関係・履歴・処理結果を照合する。切替中の更新、切替後の新規データを含む復旧可能性、判断者と実行許可を確認する。逆変換が情報を失う場合は往復一致を無理に要求せず、保存・照合・前進修復を設計する。
- 監視はエラーだけでなく、定期処理の成功が所定時間内にない状態も必要に応じて検出する。未使用の公開面は利用状況と依存を確認して縮小する。引継ぎ時の鍵・権限の回収と再発行は責任移転と脅威に合わせる。
- 暫定対応は残る問題、影響、解消条件と担当を既存の追跡先に残す。人物像の推測から本人の指示を無効化したり、未許可のIssue投稿や担当割当を行ったりしない。

- 未確定の技術前提は、影響を局所化し、差替え条件と確かめ方を示す。仮決定を業務上の合意や実行許可として扱わない。
- 資源の存在秘匿が必要なら応答コードだけでなく本文・時間差・一覧の見え方も確認し、案件のAPI契約に沿って拒否する。常に404へ統一する規則にはしない。
- 侵入後の影響範囲、検知と鍵・権限の更新手段も設計する。予防策だけで残余リスクがゼロになったと扱わない。
- 同じ業務対象の操作は慣習をそろえる。繰り返す手作業は頻度・失敗費用から機能化・自動化・手順化を比較し、取り消しが必要な操作には復旧経路を用意する。自動化やUndoを全操作の必須機能にはしない。
