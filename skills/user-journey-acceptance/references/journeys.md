# 操作・障害・証拠の取り方

## 最小の一連操作

例として「対象を登録→一覧で見つける→編集→再読込み→権限の異なる利用者から確認」がある。これは固定ケースではなく、要求にある操作へ合わせる。製品にない削除や共有機能を追加しない。API成功だけ、画面のtoastだけで保存完了と判定せず、公開された読取り操作で結果を再確認する。

初利用者の導線では、事前の設定・招待・接続・資格情報が必要かを確認する。開発者が準備した管理設定やログイン状態を、利用者自身の初回操作と混同しない。

## 失敗からの回復

連打・戻る・再読込み・取消し・期限切れ・競合などを実機能のリスクから選ぶ。入力が保持されるか、何を直せば再試行できるか、成功した副作用を重ねないかを見る。障害注入は専有fixtureまたは許可されたテスト環境だけで行う。

待機は状態・レスポンスを根拠にし、有限の上限を設ける。長い固定sleepで偶然成功する試験を作らない。異なるtenantや役割の検証には所有が明確なテスト主体を使い、UIが非表示なこととserver側拒否を別々に確認する。

## 証拠の意味

画面の操作ログや安全な画像に、対象版、開始状態、手順、期待/実際、結果の再取得を対応付ける。観測用のAPI読取りは補助証拠と表示し、UI操作の代替にしない。ブラウザーの内部状態やDBを直接書き換えた検証は、その準備条件を明記する。

console・通信記録・画像は必要箇所だけを取得し、cookie、token、メール、private URL、実データを保管しない。認証済み画面の共有には共有範囲を確認する。未実行と失敗と成功を区別する。

## 利用者に見せるデモ

実演を依頼された場合は、合意した受入条件から対象のロール・開始状態・見せる正常操作と拒否/失敗経路を選び、先に確認点を伝える。画面のない仕事へブラウザーを要求しない。全ロール・全異常系を無条件に列挙せず、必要な未確認を隠さない。

許可された既存環境を使うか、必要な場合だけ専用の環境を起動する。起動前に対象版・接続先・ポート・テスト主体・データと資源の所有を確かめ、既存の共有環境を再起動しない。コンテナを使う場合はプロジェクトのcompose命名・label規則に従う。ASCを使う場合の所有・停止規約は既存の実装手順を参照し、このデモのために別の命名規則を作らない。

利用者が見られるブラウザーで操作し、受入条件ごとに結果を示す。画像は上の証拠・秘密保護の規則に従い、安全なテストデータで撮影し、共有前に内容を確認する。「確認点／期待結果／実際／証跡／未確認理由」を短くまとめればよく、専用チェック表の保存は必須にしない。headless実行や保存済み画像だけなら、その事実を示し、可視ブラウザーで実演済みとしない。表示できない場合は実演未実施として、可能な代替と未確認を報告する。

終了・中断時は自分が起動した専有のプロセス・ブラウザーだけを止める。自分のcompose projectは起動時と同じ指定でstopし、downやvolume削除をデモ終了の既定にしない。借用した共有環境・利用者のブラウザー・永続データは保持する。利用者が継続利用を求めた資源は稼働中であることと停止方法を渡す。停止に失敗したら対象と残存状態を報告し、他の資源まで一括停止しない。
