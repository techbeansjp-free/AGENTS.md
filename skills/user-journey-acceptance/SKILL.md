# 利用者操作の受入検証

## 入口から利用者の目的までつなげる

元要求と既存の画面/API契約から、役割・開始状態・操作・期待結果を選ぶ。画面一覧を埋めるのではなく、利用開始から目的達成、失敗からの回復までを対象にする。ASCや特定ブラウザー自動化製品を必須にしない。

対象URL・稼働版・接続先・アカウント・データの所有と許可範囲を確認する。公開repoや合成データ等の再現可能なfixtureを優先するが、clone・外部接続・fork・公開の権限は別に判断する。既存アカウントや実データを勝手に変更しない。

## 実画面で確認する

[操作・障害・証拠の取り方](references/journeys.md)を読み、通常の画面入口から操作する。利用者に見える実演を求められた場合は、同referenceの「利用者に見せるデモ」を使う。必要なセットアップは明示し、直接APIやDB操作で成功状態を作ったものを「画面から完了」と報告しない。画面確認とAPIの境界試験は分ける。

保存、一覧反映、再表示、再読込み、権限切替え等を要求に応じて確認する。loading/empty、validation、denied、conflict、通信失敗、取消し、再試行で、利用者に残る状態と副作用を観測する。mockだけで実接続済みとしない。操作不能な依存があれば、その先は未検証とする。

## 問題を再現可能に返す

実行環境とfixture、手順、期待/実際、失敗した境界、保存結果を記録する。スクリーンショットだけで認可や永続化を証明しない。観測したUI症状と原因の推測を分け、秘密・個人情報・認証情報を証跡へ含めない。

検証のみの依頼では再現手順・影響・修正候補を返す。実装・修正も依頼範囲に含まれる場合は不具合を修正し、失敗した操作と影響する隣接経路を再確認する。コードを直さずリトライで不安定さを隠さない。ブラウザーや実接続を使えない場合は静的確認と区別し、未実施の実操作を合格にしない。

完了報告では実操作したケース、mock/実接続、保存・回復の結果、未確認を示す。使い捨てデータと自分の資源だけを後始末し、外部公開は別の許可に従う。
