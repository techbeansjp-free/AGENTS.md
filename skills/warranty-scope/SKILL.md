# 受託開発の保証範囲の合意

受託開発で瑕疵対応が無制限に広がらないように、保証の対象・条件・対象外と、瑕疵対応の始まりと終わりの条件を、顧客と合意する前に揃える。合意案と合意記録は仕様書の品質保証範囲に残し、後で来た不具合や依頼を合意と証跡で判定できるようにする。

中心の考え方：責任期間の長さと、保証の対象・条件・範囲を分けて扱う。責任期間が無期限でも、対象・条件・範囲は無制限にしない。期間は法務・契約の判断に残し、対象・条件・範囲を限定する案を出す。

作るのは案までとする。顧客への送信と合意の確定は権限を持つ担当者が行う。契約書の雛形や条文は作らない。法的な有効性は断定せず、論点と判断者を示す。用語と契約書との関係は雛形の冒頭に従う。

顧客に納品して保証範囲の合意が必要な案件で使う。合意の相手がいない案件（OSS・社内ツール等）や通常の開発の工程には挟まない。

## 材料と書く場所

仕様書、既存の決定（Issue・議事録等）、契約書のうち保証・検収・責任期間等の条項の所在を確かめる。既存の書式・ID・置き場があればそれに従う。

仕様書雛形を使う場合、節・列・判定の流れは雛形の`details/02_要件/03_品質保証範囲.md`、値の置き場は`00_利用案内.md`の「置き場の表」を正本とする。雛形は`project-assets`の配布先では`.agent-skill-chain/templates/specs/`、パッケージ内では`v05/templates/specs/`にある。このSkillは別の書式を持たない。

## 項目を選ぶ

[確認する項目](references/check-items.md)の核はすべて扱い、任意の項目は案件で選ぶ。扱わないものは理由を残す。

## 値は正本に置き、参照する

保証する値（対応環境の版・性能の閾値・受け入れ条件等）は置き場の表の正本に書き、品質保証範囲・未決事項・説明文には正本のIDだけを書く。IDのない正本（例：対応環境の行）はファイル・節・行で参照し、参照のためにIDを新設しない。同じ値を二か所に書くと片方だけが更新されて食い違うため、参照に値やラベルを添えない。正本に値がなければ、正本への追記を提案するか未決にする。

## 状態と判定

案の段階では、状態を提案・未決にする。合意済みにするのは合意者の確認があった場合だけとする。判定は、合意した仕様・条件との差異か（技術的な事実）を先に見て、契約上の分類は権限者（法務・契約）が決める。分類表は社内の対応区分で、法的な結論ではない。検収済みであることだけで責任を否定しない。

## 未決事項に判断者を付ける

未決事項は置き場の表の「未決事項」の正本にOPEN IDで書き、判断者を付ける。対象プロジェクトの体制を優先し、次は既定の目安とする。

| 論点 | 既定の判断者 |
| --- | --- |
| 契約書との関係（契約書がこの文書を参照するか） | 法務・契約 |
| 責任期間・通知期間・免責・みなし検収の有効性、契約不適合責任の扱い | 法務 |
| 保証の範囲・費用負担・保守契約との切り分け | 契約・営業の権限を持つ担当（提供側）と、顧客の契約担当 |
| 保証する値・測定方法・技術的な実現性 | 技術の担当 |
| 業務上必要な範囲・受け入れる残存リスク | 顧客の業務の責任者 |

判断者が決まっていない論点は、それ自体を先頭の論点にする。

## 顧客への説明文の案を作る

送信はしない。本文の先頭に「法務確認前の案」と書く。何を保証し何を保証しないか（WAR IDと正本の参照）、条件が変わったときの扱い、顧客に決めてもらう未決事項と回答の期限、法務の確認が必要な論点（結論は書かない）を含める。免責・責任制限に当たる文は、法務の確認を経るまで送らない。期間と範囲を分ける原則は、対応の範囲が明確になる顧客の利点として伝える。

## 出力

既存の記録先と書式があればそれに従う。なければ、品質保証範囲の案（雛形の節に沿う）、正本へ追記を提案する値とその文書、未決事項と判断者、説明文の案を返す。

## 扱わないこと

合意の後に来た依頼の判定と見積は[estimate-and-scope](../estimate-and-scope/SKILL.md)、保証範囲に関係しない未決事項の整理は[decision-ownership](../decision-ownership/SKILL.md)、開発基盤の先行決定は[project-foundation](../project-foundation/SKILL.md)が扱う。個別の案件の値（ブラウザの版・稼働率等）は決めない。
