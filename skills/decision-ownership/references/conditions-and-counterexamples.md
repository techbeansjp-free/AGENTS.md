# 適用条件と反例

以下は条件によって判断が変わる例である。ある案件で効いた運用を、別の案件の規則にしない。

| 強すぎる一般化 | 条件を残した判断 |
| --- | --- |
| 判断は必ず判断者に返し、提供側では何も決めない | 業務・受入・優先度の判断は返す。事実の確認、権限内の技術判断、決定済みの方針の適用は進める。返す判断と進める作業を分けて示す |
| 未決事項がある限り作業を始めない | 未決に依存する作業を止め、依存しない作業は進める。仮置き案で進めた部分は、判断が変わったときの戻し方を残す |
| やらない選択肢は毎回提案する | 要否が未確認の依頼・追加要望・対応漏れで出す。合意済みの必須要件や不具合の是正で、要否を蒸し返さない |
| 着手したタスクの優先度は変えない | 途中の差込みが品質や他の約束を損なう場合に守る。調査タスク、重大な障害、前提が崩れた場合は、影響を示して判断者が変える |
| 優先度は次の次のリリースまで決めておく | 定期的にリリースする案件で、直前の決定が情報不足で押し出される場合に使う。単発の納品では納期と範囲の合意で足りる |
| 見積は常に目安として伝える | 前後する前提を合意しておく。固定価格の契約や約束済みの納期では、目安と確約の区別を契約に合わせる |
| リリース日は曜日で固定し、金曜は避ける | 周期・締切・見直し条件を決める手段の一つである。体制・顧客の業務日・監視の有無から選び、緊急時に崩してよい範囲を先に合意する |
| 一覧の列は常に同じものを使う | 同じ種類の指摘を追う間は列を固定し、比較できる状態を保つ。対象が変われば列を見直す |
| 窓口で全部返し、実装担当には聞かない | 記録や既存機能で答えられるものは窓口で返す。実装を見ないと分からないものは、推測で返さずに実装担当へ聞く |
| 顧客の事情は全部要件に反映する | 社内調整や体制の変化は要件と日程のリスクとして扱う。品質・安全・契約に反する要望は、理由と代案を示して判断者と合意する |
| 新しい業務は断る | 引き受ける前に、誰の工数が圧迫され何が遅れるかを示す。判断者が影響を受け入れれば引き受ける |
| 人を増やせば解決する | 何を任せるかを作業単位で決める。「サポート」だけの割当ては動けない。詰まりがレビューや確認待ちなら、人よりフローを変える |
| 進行役がいる場では発言しない | 仕切りは任せ、抜けている文脈（出どころ・優先度・経緯）だけを短く補う |
| 確認事項は1件ずつ専用の場所を作る | 置き場所を1か所に集め、提供側の回答から顧客の確認までを1行で追えるようにする。既存のtrackerや資料の形式があればそれを使う |

## 運用を整えるときの目安

依頼が個別の案件ではなく、プロジェクトの運用（会議体・ルール・資料）を整えることなら、次を必要な分だけ使う。全部を新設しない。

- 目標は、特定の人がいなくても回ることである。初めて参加する人が口頭の説明なしで動ける資料を、読む人の役割（管理責任者・実装担当・技術責任者・顧客）ごとに分ける。
- ルールは通常の流れを基準にし、例外は差分だけ書く。新しいルールや管理表は、試験用の場所で試してから本番へ移す。
- 締切と例外の条件は先に合意する。緊急時に崩してよい範囲（即日リリースの可否、環境への反映順）を平時に決める。
- 定例は「前回の結果・今の進捗・次の仮決め」をまとめて扱う。決まったことと、誰がいつまでに何をするかを必ず記録する。
- 稼働の超過・不足は、提供側の内部で確認してから顧客へ伝える。監視の通知は確認した記録を残し、不要な通知は基準の見直しを提案する。
- 「どこに聞けばよいか分からない」という問い合わせはいったん受け、担当へつなぐ。
- 大きな対応は、全量を洗い出す→重要なものを絞る→工数の目安を出す→いつやるかを決める、の順に進める。調査は時間を区切り、区切りで続けるかを確認する。
- 影響が大きい変更（基盤・バージョンアップ・セキュリティ）は、レビューの回数や経過観察を増やす。
