## 1. 目的と背景

### 1.1 目的（必須、1文）

利用projectのimplementerが、`routing roles --assignments`と`routing ceiling --override`の`--help`に従ってfile pathを渡し「値が不正です (offset 0)」で止まる状態を無くし、宣言・実行例・診断が実装（inline JSON）と一致するようにする。

### 1.2 現在の課題（必須）

- 現在の状態: `src/cli-usage.ts:187`は`flag("assignments", "path", …)`、同232は`optional("override", "path", …)`と宣言し、実行例も`--assignments=./assignments.json`とfile pathを示す。実装（`src/cli.ts`の`assignmentInput`・`humanOverrideInput`）はflagの値そのものを`parseJsonStrict`へ渡す。仕様06は`<JSON>`（inline）と定めており、実装は仕様どおり、usageだけが食い違う
- 困っている利用者・運用者: 利用project（beekle-team/system-graph #48・#64）のimplementer。pathを渡して`ASC-CLI-VALIDATION-001` / `override: 値が不正です (offset 0)`で止まり、`ASC-PROVIDER-CEILING-001`の反例を立証できないとして停止した
- 発生条件と頻度: usageを信じてpathを渡した全実行。利用側で2件観測
- 放置した場合の影響: usageを読んだ利用者が必ず失敗し、診断からは「pathでなくJSONを渡せ」と分からない
- 観測した事実と推測の区別: 事実はIssue #1340の再現argvと両fileの原文。`cli.ts:6111`の`parseJsonStrict(manifestRaw, file)`はfile内容を渡しており、inline parseなのはこの2 flagだけ（2026-09-12 grepで確認）

### 1.3 期待する状態と価値（必須）

- 期待する状態: `--help`の型・説明・実行例が`<JSON>`（inline）を示し、pathらしい値（`{`/`[`で始まらない）を渡したときの診断が「inline JSONを渡す（pathではない）」という是正操作を含む。値の解釈は変えない
- 利用者価値: usageどおりに書けば初回で通る。失敗しても次の1手が診断に出る
- 運用・事業上の価値: 利用側の停止（#48・#64の同型）が再発しない
- 成功時に観測できる変化: `routing roles --help`・`routing ceiling --help`の該当flagが`<JSON>`になり、`--assignments=/tmp/a.json`の診断に「inline JSON」の案内が含まれる。inline JSONの受理は変わらない

## 2. 対象範囲

### 2.1 対象内（必須）

- `src/cli-usage.ts`の`assignments`・`override`の型を`path`から`JSON`へ、説明と実行例をinline JSONへ直す
- `src/cli.ts`の`assignmentInput`・`humanOverrideInput`で、値が`{`または`[`で始まらないときに「inline JSONを渡す（pathではない）」を含む診断で拒否する
- `.agent-skill-chain/00_利用案内.md`と`README.md`の自動生成区画を`generate_cli_usage_guide`で再生成する（usage正本の生成物）
- unit scenarioと`docs/specs/`（要件・追跡表・変更履歴）の更新

### 2.2 対象外（必須）

- file pathを読む経路の追加。読むfileの境界検証（root containment・symlink）が新たに要り、仕様06がinlineを契約しているため採らない
- `parseJsonStrict`自体の診断改善。共通libで他の呼び出し元（manifest file）へ影響するため触れない
- 他commandのflag型の見直し。inline parseなのは2 flagだけであることをgrepで確認済み

### 2.3 維持する既存動作

- inline JSONを渡す既存の呼び出しはそのまま受理される
- `ASC-CLI-VALIDATION-001`の診断構造（ruleId・reasons・next）は不変。reasonsの文言だけを具体化する
- `routing roles`・`routing ceiling`の判定logicは不変

### 2.4 権限と停止点

- 許可済みの読み取り: repository全体、Issue #1340
- 許可済みの書き込み: 専用worktree内の`src/cli-usage.ts`、`src/cli.ts`、`dist/`、`.agent-skill-chain/00_利用案内.md`と`README.md`の生成区画、`test/`、`docs/specs/`、本staging
- 別承認が必要な操作: 既定branchへのmerge（ownerが会話上で許可済み。policyは`merge.mode=disabled`でPR終端）、release、公開
- 今回の停止点: PR作成（`outcome=pull-request`）
