## 1. システム・変更概要

- 対象利用者: 利用projectのimplementer・coordinator（`routing roles`・`routing ceiling`を実行する）、ASC maintainer
- 実現する価値: `--help`の宣言・実行例・拒否診断が実装（inline JSON）と一致し、usageどおりに書けば通る。失敗時は次の1手が分かる
- 変更前の振る舞い: `--assignments=<path>`・`--override=<path>`と宣言し実行例もfile pathだが、実装は値をinline JSONとして解析する。pathを渡すと`assignments: 値が不正です (offset 0)`で終了する
- 変更後の振る舞い: 宣言と実行例が`<JSON>`（inline）になり、`{`または`[`で始まらない値は「`--assignmentsにはinline JSONを渡します（pathではありません）`」相当の診断で拒否される。inline JSONの受理と判定は不変
- 対象外: file pathを読む経路の追加、`parseJsonStrict`の共通診断、他commandのflag型（00 §2.2）

## 6. 外部インターフェースとデータ

### 6.1 外部境界

| 境界 | 方向 | 契約 | 認証・承認 | 失敗・再試行 |
|---|---|---|---|---|
| CLI `routing roles --assignments=<JSON>` | 入力 | inline JSON配列 | 不要 | 型不一致は非0。修正後再実行 |
| CLI `routing ceiling --override=<JSON>` | 入力 | inline JSON object | 不要 | 同上 |
| `--help`と生成区画（`.agent-skill-chain/00_利用案内.md`・`README.md`） | 出力 | usage正本からの生成 | 不要 | `cli:check`で一致を検証 |

### 6.2 データ要件

- データ項目と意味: role割当（role・identity・context）、人間override（provider・selection・issue・scope・instructedBy・instructedAt・expiresAt）。いずれも既存
- 検証・正規化: 先頭空白を除いた1文字で型不一致を判定し、本文の正規化は行わない
- 保存期間と削除: 保存しない
- 個人情報・秘密情報: 診断へ値本文を転記しない
- 既存データとの互換性: 不変
- 識別子方針: 既存のSCN ID体系。新規scenarioは`SCN-UNIT-JSONFLAG-<3桁>`

## 8. Zero Trustと権限要件

- 検証する入力: flag値（inline JSON）
- 検証するリポジトリ・リモート同一性: 変更なし
- 認証確認: 不要（read-only検証command）
- 操作単位の承認: 不要
- 書き込み直前に再検証する状態: 該当しない（書き込みを行わない）
- 不明時に拒否する条件: 先頭が`{`/`[`でない値は型不一致として拒否する
- 権限を分離する後続操作: なし
- authority/evidence graphの正方向と自己参照・相互参照の拒否条件: usage正本 → 生成区画の一方向。生成区画を手で編集しない
- head変更で失効する下流証拠: review・test・PR証跡（既存規則）

## 9. 受け入れ条件と実行可能な受け入れ例

| AC ID | 受け入れ条件 | 例ID | project選択test layer | 観測方法 |
|---|---|---|---|---|
| AC-01 | `routing roles --help`と`routing ceiling --help`の当該flagが`<JSON>`型で、実行例がinline JSONを含む | SCN-UNIT-JSONFLAG-001 | unit | `--help`のJSON出力 |
| AC-02 | `--assignments=/tmp/a.json`と`--override=./o.json`を渡すと終了値1で、`reasons`に「inline JSON」と「pathではない」を含む | SCN-UNIT-JSONFLAG-002 | unit | CLI `main`の終了値と出力 |
| AC-03 | 先頭空白付きを含むinline JSONは変更前と同じ判定を受ける | SCN-UNIT-JSONFLAG-003 | unit | CLI `main`の出力 |
| AC-04 | `--assignments=null`は既存の型診断（JSON配列でなければならない）で拒否され、`--assignments=[a].json`は解析errorに是正操作を併記して拒否される。どちらも値本文を転記しない | SCN-UNIT-JSONFLAG-004 | unit | CLIの終了値とreasons |

- project policyが選択した言語とrunner形式の実行可能な受け入れ例（`gherkinDialect: en`、cucumber-js、`test/features/unit/routing-json-flag.feature`）:

```gherkin
@unit
Feature: routing rolesとceilingのJSON flagは宣言・実行例・診断が実装と一致する

  Scenario: SCN-UNIT-JSONFLAG-001 helpがinline JSON型と実行例を示す
    Given routing rolesとrouting ceilingのusageがある
    When 両subcommandの--helpを表示する
    Then --assignmentsと--overrideは<JSON>型で実行例はinline JSONである

  Scenario: SCN-UNIT-JSONFLAG-002 path風の値はinline JSONを渡す案内つきで拒否する
    Given file pathをJSON flagへ渡すargvがある
    When routing rolesとrouting ceilingを実行する
    Then 両方とも終了値1でreasonsにinline JSONを渡す案内を含む

  Scenario: SCN-UNIT-JSONFLAG-003 inline JSONの受理と判定は変わらない
    Given 先頭空白付きのinline JSONをJSON flagへ渡すargvがある
    When routing rolesとrouting ceilingを実行する
    Then 変更前と同じ判定を返す

  Scenario: SCN-UNIT-JSONFLAG-004 scalarのJSONと角括弧で始まるpathは既存の型・解析診断に是正操作を併記する
    Given nullのJSONと角括弧で始まるpathをJSON flagへ渡すargvがある
    When routing rolesとrouting ceilingを実行する
    Then scalarは型診断で拒否されpathは解析診断と是正操作を併記して拒否される
```

## 10. 境界値、異常、悪用、回帰

| 観点 | 条件 | 期待する振る舞い | シナリオID |
|---|---|---|---|
| 境界値 | 先頭空白付きのinline JSON、scalarのJSON、`[`で始まるpath | 空白は受理、scalarは型診断、`[a].json`は解析診断に是正操作を併記 | SCN-UNIT-JSONFLAG-003、004 |
| 異常 | 存在するfileのpath、存在しないpath | どちらも案内つきで拒否（fileを読まない） | SCN-UNIT-JSONFLAG-002 |
| 悪用 | 値本文の診断への転記 | 転記しない | SCN-UNIT-JSONFLAG-002 |
| 回帰 | 既存のinline JSON呼び出し | 判定不変 | SCN-UNIT-JSONFLAG-003、既存role-tier scenario |
