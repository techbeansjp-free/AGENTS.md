## 1. 設計方針

### 1.0 開発考慮事項の適用判定（必須）

開発考慮事項の適用判定は00_要求定義.md §6.1と同じ

### 1.1 設計目標

- FR-01〜03、INV-01〜03を満たす。usage正本の2 flagを`JSON`型・inline実行例へ直し、入力helperの拒否診断へ是正操作を足す。値の解釈は変えない

### 1.2 設計対象外

- file pathを読む経路（root containment・symlink検証が要る新経路。仕様06がinlineを契約）
- `parseJsonStrict`の共通診断の変更（manifest読み込みにも使われる）
- 先頭文字以外の入力正規化

### 1.3 適用する原則

| 原則 | この設計での適用方法 | 証拠 |
|---|---|---|
| UNIX・単一責務 | usage正本1箇所を直し、生成区画はscriptで生成する。helperは値→構造の純関数のまま、型不一致の分岐を1つ足す | §2.2 |
| DDD | CLI adapterに閉じ、domain判定（`validateRoleAssignments`・`validateProviderSelection`）へ触れない | §2.1 |
| BDD / Evidence-driven Verification | AC-01〜03 → SCN-UNIT-JSONFLAG-001〜003。bug fix・low riskから回帰と契約検査（`cli:check`）を選ぶ | §10、§11 |
| Zero Trust | fileを読まない。診断へ値本文を転記しない | §5 |

## 2. システムコンテキストと責務

### 2.2 コンポーネント

| コンポーネント | 単一責務 | 依存先 | 外部処理 | テスト接合部 |
|---|---|---|---|---|
| `src/cli-usage.ts` `routing roles`/`routing ceiling`項 | `assignments`・`override`を`JSON`型、説明「inline JSON（pathではない）」、実行例をinline JSONにする | なし | なし | `--help`出力（SCN-UNIT-JSONFLAG-001） |
| `src/cli.ts` `inlineJsonInput`（`assignmentInput`・`humanOverrideInput`が使用） | `parseJsonStrict`の解析errorへ`--assignmentsにはinline JSONを渡します（file pathではありません）`を併記して投げ直す。正当なJSON本文は解析し、型の診断は既存検査が担う（round 1 REV-02・REV-03で先頭文字gateから変更） | `parseJsonStrict` | なし | CLI `main`（SCN-UNIT-JSONFLAG-002、003、004） |

### 2.3 依存方向と循環防止

- 呼び出し元 → 呼び出し先: `cli.ts`（handler）→ 入力helper → `parseJsonStrict`。`cli-usage.ts` → 生成区画
- 許可しない依存: helperからfilesystemへの依存
- 外部プロセスを呼べる境界: なし
- 循環を検出する方法: `architecture:check`（既存）

| node | 依存先 | authority/evidence | topological順 | cycle反例SCN |
|---|---|---|---|---|
| USAGE-SOURCE | なし | なし | 1 | SCN-UNIT-JSONFLAG-001 |
| INPUT-HELPER | PARSE-JSON | 診断 | 2 | SCN-UNIT-JSONFLAG-002 |
| GENERATED-GUIDE | USAGE-SOURCE | `cli:check` | 2 | SCN-UNIT-JSONFLAG-001 |

candidate自己評価、tracked artifact自己SHA、相互参照をedgeとして許可しない。rollback/retryはPR単位のrevert。
