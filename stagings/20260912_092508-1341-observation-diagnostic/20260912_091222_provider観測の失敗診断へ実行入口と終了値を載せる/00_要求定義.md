## 1. 目的と背景

### 1.1 目的（必須、1文）

`routing observe`が観測に失敗したとき、利用者が実行した入口（argv）と終了値を出力から特定できるようにし、`claude`に公式catalog入口が無いことを仕様の明示契約にする。

### 1.2 現在の課題（必須）

- 現在の状態: `observeProvider`（`src/adapters/provider.ts`）は非codexへ`<provider> models list --json`を渡す。`claude` CLIに`--json`は無く終了値1になるため、出力は`state: "unknown"`、`entrypoint: "claude"`、`reason: "provider実行入口のread-only観測が失敗しました"`になる。**実行したargvも終了値も出力に無い。**
- 困っている利用者・運用者: 利用project（beekle-team/system-graph #62・#63）の進行役。原因を特定するために配布物の`dist`を読む必要があった
- 発生条件と頻度: `routing observe --provider=claude`の全実行、および非codex providerでの観測失敗全般
- 放置した場合の影響: 診断が行動可能でなく、利用者がdistを読むか推測で切り分ける
- 観測した事実と推測の区別: 事実は`claude models list --json`が`error: unknown option '--json'`で終了値1になること、`routing observe --provider=claude`の出力、`provider.ts:271`の決め打ちargv。**「実装が常に`unknown`を返す」は誤り**で、catalogを解釈して`available`/`unavailable`を返す経路は存在し、成立しないのは`claude`を相手にしたときだけである（報告者も同じ訂正を本文へ記載している）

### 1.3 期待する状態と価値（必須）

- 期待する状態: 観測失敗時の`entrypoint`が実際に実行したargvを示し、`reason`が終了値を含む。仕様06が「Codex以外に公式catalog入口は定義されておらず、`claude`の観測は必ず`unknown`になる」ことと、`unknown`の`reason`が実行入口と終了値を含むことを明示する
- 利用者価値: 出力だけで「何を実行して何が返ったか」が分かり、distを読まずに切り分けられる
- 運用・事業上の価値: 「観測できない」が仕様の明示契約になり、利用側が観測不能を欠陥と誤認しない
- 成功時に観測できる変化: `routing observe --provider=claude`の出力の`entrypoint`が`claude models list --json`になり、`reason`に終了値1が含まれる。`codex`経路の出力は変わらない

## 2. 対象範囲

### 2.1 対象内（必須）

- `src/adapters/provider.ts`の`unknownObservation`へ実行argvと終了値を渡し、`entrypoint`を実際のargv文字列、`reason`を終了値つきの文言にする
- `docs/specs/06_外部インターフェース/01_コマンド・GitHub契約.md`の`provider availability`行へ、Codex以外に公式catalog入口が定義されていないこと（`claude`の観測は`unknown`になること）と、`unknown`の`reason`が実行入口と終了値を含むことを明記する
- unit scenarioと`docs/specs/`（要件、追跡表、変更履歴）の更新

### 2.2 対象外（必須）

- **`state: "unobservable"`の新設。** 仕様06が`available`・`unavailable`・`unknown`の3状態と終了値を定めており、4状態目は仕様2箇所・型2箇所・終了値表の変更を要する。かつ`resolveRouting`は`state !== "available"`で分岐するため、状態を分けても採る行動が変わらない（REQ-LC-011の「報告するがhealthyを変えない」と同じ形）。区別は`reason`と`entrypoint`で足りる
- **provider名のenum化とcapability-mappingとのcross-file一致検査。** 報告者も「可能なら」と書いており、進行役・諮問双方が別Issueと判断した。本Issueは診断の行動可能性に限る
- **`resolveRouting`のfallback条件の変更（`unknown`でfallbackしない）。** 現行の`state !== "available"`でのfallbackは本Issue以前から存在し、報告が挙げた症状でもない。変えるとrouting decisionの契約が動く
- **provider名を実行fileとして起動する設計の置き換え（adapter registry）。** 実行境界の再設計であり、報告の対応策3の範囲を超える
- `stderr`本文の転記。仕様06が禁じている

### 2.3 維持する既存動作

- `codex`経路の観測（`available`・`modelMetadata`）は不変
- `state`の値域（`available` / `unavailable` / `unknown`）は不変
- `stderr`本文を転記しない制約は不変

### 2.4 権限と停止点

- 許可済みの読み取り: repository全体、Issue #1341、諮問結果
- 許可済みの書き込み: 専用worktree内の`src/adapters/provider.ts`、`dist/`、`test/`、`docs/specs/`、本staging
- 別承認が必要な操作: 既定branchへのmerge（owner会話許可済み、policyは`disabled`でPR終端）、release、公開
- 今回の停止点: PR作成（`outcome=pull-request`）

### 5.1 機能上の期待

### 6.2 その他の制約

- 依存/authority/evidence graphのnode・edgeと正方向: 要求 → 要件・AC → unit scenario → `provider.ts` → review → PR。観測結果 → routing decisionの既存方向は変えない

- rollback/retryのrevision、上限、終了条件: PR単位のrevert。review round最大3、取り直し1

- 技術的制約: `unknownObservation`は4箇所から呼ばれる。全箇所へargvと終了値（または起動失敗）を渡す
- 期間・運用上の制約: #1350の後に進める（別fileだが同じrouting系で、mainの追随を直列化する）
- 外部サービス・組織への依存: なし。`claude` CLIを新たに必須にしない
- 前提としている事実: 仕様06が`stderr`本文の転記を禁じ、非0終了を`unknown`と定めている。`claude`に機械可読なread-only catalog入口が無いことは利用側が実測している（`--json`は存在せず、`--json`無しの出力は非決定的な生成文）
