## 1. 目的と背景

### 1.1 目的（必須、1文）

`routing tier`の利用者が、working treeを読む互換検証の結果を「trusted検査に通った」と誤読しないよう、判定の信頼源を出力へ明示し、trustedを主張する診断と仕様に無い`--provider=claude`を除く。

### 1.2 現在の課題（必須）

- 現在の状態: `src/cli.ts`の`routing tier`は`--provider`に`codex`と`claude`を受理する（`claude`は#1257で仕様外に追加された）。`codex`経路だけ`loadOperationPolicy`（既定branchをgit経由）でtrusted tierMappingを選び直し、`claude`と未指定は`loadProjectPolicySet`（working tree）の値を`validateTierSelection`へ渡す。失敗診断は「trusted project choiceへmodel mappingを定義するか…」「requiredAuthority: model mapping owner」とtrustedを主張し、成功出力は`{valid, errors, required, selected, model}`だけで信頼源を持たない
- 困っている利用者・運用者: 利用project（beekle-team/system-graph #59）の進行役とreviewer。候補branchの`development.json`へkeyを足すだけ（commit・push無し）で`valid:true`になり、それをtrusted採用の証拠と誤読しうる
- 発生条件と頻度: `--provider=claude`または未指定で`routing tier`を認可用途に使う全実行。利用側で1件観測
- 放置した場合の影響: 「検査する側の正本を検査対象が用意できる」状態がtrustedの語で覆われ、外部consumerがexit 0だけを見るconfused-deputyになる
- 観測した事実と推測の区別: 事実はIssue #1350の再現と`cli.ts`原文、諮問（codex・fable）の実測。「製品内でmerge・launchの自己承認まで成立している」は事実ではない（`routing tier`の出力を認可へ流す辺は製品内に無く、`routing launch`は別にtrusted policyを読む）。欠陥は「trustedと誤認させる表示・値」に限る

### 1.3 期待する状態と価値（必須）

- 期待する状態: `--provider`は仕様どおり`codex`だけを受理し、`claude`は`ASC-CLI-VALIDATION-001`で拒否する。未指定経路は互換検証として残し、成功・失敗の出力へ`provenance`（`source: filesystem|git`と読んだref）と`usage: "compatibility-only"`を含め、診断の`next`から「trusted project choice」の主張を外し`requiredAuthority`を「不要」にする。`codex`経路の判定は変えず、出力へ`provenance`（`source: git`、trusted commit）と`usage: "codex-adoption"`を足す
- 利用者価値: 出力だけで「どの信頼源で判定したか」「認可に使えるか」が機械的に分かる
- 運用・事業上の価値: 運用ポリシー「機構が保証していると書かない」に従い、trustedの誤読による自己承認の抜け道の見かけを閉じる
- 成功時に観測できる変化: 再現手順3（working treeへkey追加）は未指定経路で`valid:true`のまま（仕様どおりの互換検証）だが、出力に`provenance.source: "filesystem"`と`usage: "compatibility-only"`が付く。`--provider=claude`は拒否される。`--provider=codex`の判定は不変

## 2. 対象範囲

### 2.1 対象内（必須）

- `src/cli.ts` `routing tier`: `--provider=claude`の拒否、未指定経路の出力へ`provenance`と`usage`を追加、失敗診断の`next`・`requiredAuthority`から trusted の主張を除去、`codex`経路の出力へ`provenance`と`usage`を追加
- `src/cli-usage.ts`の`provider` flag説明（codexのみ）と生成区画
- unit scenario（拒否、provenance、codex経路不変）
- `docs/specs/`（06のrouting tier行、10の信頼境界、追跡表、変更履歴）

### 2.2 対象外（必須）

- `claude`経路を`loadOperationPolicy`へ通す案（Issue提案1）。仕様に無い`--provider=claude`を「trusted検査を行う正式経路」へ昇格させ、Claudeには公式観測入口が無いため片翼の対称にしかならない。fableの実測ではlocal `origin/HEAD`の捏造で通り、remote無しrepositoryでは一律停止する
- `codex`経路の`loadProjectPolicySet`先行呼び出しの除去（諮問codexの指摘）。判定に使っていない読み取りであり、問題以上の変更になる
- `routing tier legacy`等の別commandへの分離。仕様06の1行の範囲を超える
- 利用側が`valid`だけを見て認可へ使う合成の防止。製品はtrustedと書かない・認可に使わないと出力するまでで、利用側の合成は閉じられない（限界として記録）

### 2.3 維持する既存動作

- `--provider=codex`の判定logic・出力field（既存分）・診断は不変
- 未指定経路の判定logic（working treeの互換検証）は不変。出力fieldの追加のみ
- `routing launch`・`routing resolve`は触れない

### 2.4 権限と停止点

- 許可済みの読み取り: repository全体、Issue #1350、諮問結果
- 許可済みの書き込み: 専用worktree内の`src/cli.ts`、`src/cli-usage.ts`、`dist/`、生成区画、`test/`、`docs/specs/`、本staging
- 別承認が必要な操作: 既定branchへのmerge（owner会話許可済み、policyは`disabled`でPR終端）、release、公開
- 今回の停止点: PR作成（`outcome=pull-request`）

### 6.2 その他の制約

- 依存/authority/evidence graphのnode・edgeと正方向: 要求 → 要件・AC → unit scenario → `cli.ts`/`cli-usage.ts` → 生成区画 → review → PR。判定の信頼源（trusted ref／filesystem）→ 出力の`provenance`は一方向
- cycle、self-loop、unknown node、candidate自己評価、tracked artifact自己SHAを拒否する条件: candidate側filesystemの結果を認可へ流す辺を作らない（`usage: compatibility-only`で明示）。review artifactは自身のSHAを書かない
- rollback/retryのrevision、上限、終了条件: PR単位のrevert。review round最大3、取り直し1

- 技術的制約: `loadProjectPolicySet`は`provenance.source`（`filesystem`／`filesystem-legacy`）を既に返す。`loadOperationPolicy`はtrusted commitを返す。両方を出力へ写すだけで済む
- 期間・運用上の制約: #1340（同じ`cli.ts`）の後に直列で進める
- 外部サービス・組織への依存: なし
- 前提としている事実: 仕様06の`routing tier`行が`[--provider=codex]`と未指定の互換検証だけを定める。諮問2件（codex・fable）が「`claude`値の拒否」で一致
- 未確認事項: なし
