## Context

agent-skill-chain は対象リポジトリ（consumer）へ GitHub Actions ワークフローを配布する。そのうち root-cleanup ワークフローは、既定ブランチへの push を契機に、リポジトリ root 直下へ混入した Issue セグメント成果物を短命ブランチ上の削除コミット・PR・管理者権限マージで除去し、その後 root が clean であることを検証する。

このワークフローは Node.js プロジェクト専用の前提（依存導入とビルド）を無条件のステップとして持っていた。consumer は Node.js プロジェクトとは限らず、`package.json` や lockfile を持たない consumer では依存導入が必ず異常終了し、root-cleanup が push ごとに恒常的に失敗する。結果として (1) root 直下の成果物が除去されず残留する、(2) 常に失敗するワークフローが 1 本存在し後続の本物の失敗が埋没する、という 2 つの害が生じていた。

除去処理と root clean 検証はいずれも agent-skill-chain CLI への薄いラッパー経由で実行され、CLI を 3 経路（リポジトリ内のビルド成果物、依存ディレクトリ配下の実行ファイル、`PATH` 上のコマンド）で解決できなければ停止する。したがって npm 手順を単に削除・条件化するだけでは、失敗ポイントが CLI 未検出へ移動するだけである。

検討したトレードオフは次のとおり。

- 判定形の設計: 姉妹ワークフロー（PR 契機の検査ワークフロー）は同種の欠陥を先に是正しており、実行時の構成を観測して 2 つの真偽値出力を出す判定ステップと、共有 CLI 解決実装を呼ぶ CLI 保証ステップを持つ。新しい機構を発明せずこの実証済みの形を踏襲するのが妥当である。一方、姉妹ワークフローの判定述語は build 実行条件に install 前提を含めておらず、また `scripts.build` の妥当性を値の真偽値化のみで判断するため、空白のみの文字列や文字列以外の型を「有効な build script」と誤認する。前者は lockfile 不在の consumer で「依存未導入のまま build を実行して失敗する」経路を残し、失敗箇所が移動するだけで害が解消しない。
- CLI 保証ステップの配置: npm 手順より前に置くと、自リポジトリと同じ構成の consumer でもビルド成果物・依存ディレクトリの実行ファイルがまだ存在せず、`PATH` 経路も無い状態から自動導入フォールバックが起動する。自動導入は外部レジストリとネットワークに依存するため、後段であれば不要だったはずの失敗要因を持ち込む。npm 手順より後・CLI 依存処理より前に置けば、npm 前提を満たす consumer はビルド成果物で解決でき、自動導入は 3 経路のいずれも成立しない consumer に限られる。
- CLI を用意できない場合の扱い: 沈黙して後続へ進む選択肢は、除去処理の途中での不透明な失敗を招き、原因の特定を困難にする。自動導入経路そのものを本 Issue で是正する選択肢は、変更対象（ワークフロー定義）の外側にある独立した欠陥の修正を抱き込むことになる。

## Decision

root-cleanup ワークフロー（配布正本と本リポジトリの展開先の両方、常に同一内容）について次を決定する。

1. 実行時の構成を観測する npm 前提判定ステップを追加し、2 つの真偽値出力（install 可否・build 可否）を後続ステップの実行条件として用いる。判定ステップは、どの構成でも異常終了せず終了コード 0 で終わる。すべての判定は条件式の内部でのみ評価し、`package.json` が JSON として解析不能な場合も、解析コマンドの非ゼロ終了を条件値として扱うだけとする。
2. install 可否は「`package.json` が存在し、かつ `package-lock.json` または `npm-shrinkwrap.json` の少なくとも一方が存在する」で判定する。解析不能な `package.json` に対してもこの述語は変えない。解析不能な `package.json` は「npm 前提を持たない構成」ではなく壊れた Node.js 構成であり、依存導入がその場で明示的に失敗して原因が可視化されるほうが安全側であるため。
3. build 可否は「install 可否が成立し、かつ `package.json` の `scripts.build` が有効に定義されている」の論理積とする。`scripts.build` の有効性は「値が文字列であり、前後の空白を除いた結果が空でないこと」に限定し、空文字列・空白のみ・`null`・文字列以外の型・解析不能はいずれもキー未定義と同一に扱う。install 前提を合成するのは、依存未導入のまま build script を実行すると典型的に失敗し、失敗箇所が移動するだけで害が解消しないため。
4. CLI 保証ステップを、実行条件なしで、npm 手順の後・除去処理と root clean 検証の前に置く。同ステップは共有 CLI 解決実装を読み込んでその公開関数を呼び、成功時は解決した経路を 1 行出力する。CLI 解決ロジック自体は複製せず共有実装のみが持つ。
5. CLI を解決できない場合、同ステップは沈黙して続行せず、共有実装が返す非ゼロ終了コードでワークフローをその時点で失敗させる。共有実装が標準エラーへ出す失敗理由は握り潰さない。自動導入経路そのものが実環境で成立することは本決定の保証範囲に含めない。
6. 上記の振る舞いは、ワークフロー定義からステップ実行本文を機械的に取り出し、取り出し結果が取り出し元の記述と一致することを確認したうえで、模擬構成上で実行する自動テストによって固定する。

## Consequences

- npm 前提を持たない consumer で、npm 手順を理由に root-cleanup が失敗することはなくなる。npm 前提を満たす consumer（本リポジトリを含む）は従来と同じ手順が同じ順序で実行され、CLI 保証ステップはビルド成果物経路で解決するため追加導入を行わない。
- root-cleanup ワークフローの判定述語は、姉妹ワークフローの判定述語と意図的に一致しなくなる（build 条件への install 前提の合成、`scripts.build` 妥当性判定の厳格化）。この差異は本 ADR が記録する意図的な決定であり、「両者を機械的に揃える」方向の変更は、姉妹ワークフロー側を本決定の判定形へ合わせる形でのみ行うべきである。姉妹ワークフロー側の追随は本決定の対象外であり、必要なら別 Issue で扱う。
- 3 経路のいずれでも CLI を解決できず自動導入も成立しない consumer では、root-cleanup は CLI 保証ステップで明示的に失敗し続ける。害の完全な解消には自動導入経路の是正が別途必要であり、本決定はその失敗が沈黙して後続へ伝播しないことまでを保証する。
- 追加されるステップは 2 つのみで、実行契機・再帰トリガ防止・同時実行制御・権限・使用する認証情報は変更されない。新しい認証情報も追加されない。切り戻しはワークフロー定義の差分の revert で完結する。
- 判定ステップは解析不能な `package.json` に対して install 可否を「可」と出しうるため、その構成（解析不能な `package.json` と lockfile を併せ持つ consumer）では依存導入ステップが失敗し、以降の CLI 保証・除去処理・root clean 検証へ到達しない。すなわち本 ADR の Context が解消対象として挙げた 2 つの害——root 直下の成果物が除去されず残留する、恒常的に失敗するワークフローが 1 本存在し後続の本物の失敗が埋没する——と同型の状態が、この構成では残る。この割り切りを採るのは、当該構成が「npm 前提を持たない consumer」ではなく consumer 側の構成破損であり、判定ステップが破損を検知して install 可否を「不可」と偽り npm 手順を飛ばすほうが有害だからである。偽った場合、破損は root-cleanup の実行結果から見えなくなり、consumer は `package.json` が壊れていることに気付かないまま他の経路で同じ失敗を繰り返す。加えて、install 可否の述語へ独自に JSON 妥当性を加えることは要件が定める述語との乖離を生む。残る害は当該破損が是正されるまでの期間に限られ、失敗箇所と原因はその場の出力に現れる。
