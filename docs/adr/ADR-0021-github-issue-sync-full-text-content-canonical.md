## Context

### 現行の構造

agent-skill-chain は Coordination Backend として GitHub モードとローカルモードの二値を持ち、「調整状態」の正本をモードごとに一意に決めている（GitHub モード: Issue・PR・branch・Check Run／ローカルモード: `state.yaml`・`reviews/<gate>.yaml`）。二値のうち片方だけが正本であり、二重化しないことが不変条件 I6 の要求である。

この二値モデルは、これまで調整状態にのみ適用され、**成果物の中身**（`SPEC.md`・`DESIGN.md`・`PLAN.md`・`VALIDATION.md` の本文そのもの）には適用されてこなかった。成果物内容は Coordination Backend の選択に関わらず「Git 管理下ファイルのみが正本」という単一ルールに置かれている。

不変条件のうち本決定が対象とする 2 つの現行記述は次のとおりである。

| # | 現行の記述 | 現行の検査手段 |
|---|---|---|
| I1 追跡可能性 | 全変更は Issue に紐づき、要求→設計(ADR)→実装→レビューの証跡が Git 履歴に残り、現在有効な決定を指し続ける | PR に Issue 参照必須、成果物存在チェック、ADR lint（CI） |
| I3 耐久性 | 作業状態は常に Git（remote push 済み）から完全復元可能。頭の中にしか無い状態を作らない | セグメント完了ごとの commit+push、Issue resume、`durability.backend` 未設定環境では完全自走を拒否 |

一方 I2（セグメントゲート）は既に「GitHub モード: Check Run の成功状態／ローカルモード: `reviews/<gate>.yaml`」という Coordination Backend 別の条件分岐を持つ。すなわち「不変条件の要求は不変のまま、その要求を満たす場所だけがモードで変わる」という記述形式は、本システムに既存のパターンとして存在する。

### 問題

GitHub モードを採用するプロジェクトでは、GitHub の Issue ページ・PR ページを開いても、そのIssueが 4 セグメントのどこまで進んだか、各ゲートが通過済みか、何が要求され何が決定されたかが一切分からない。詳細を知るには毎回 PR の変更ファイル一覧から `SPEC.md` 等を開く必要があり、複数Issueの状況を横断的に把握する場面でこの往復がボトルネックになる。GitHub モードを選ぶプロジェクトの期待（GitHub を正本の置き場所として使う）と、成果物内容についてだけ Git ファイルへ読みに行かされる実態との間に非対称が生じている。

この問題に対して「本文へ 3〜5 行の要約とファイルへのリンクだけを同期する」という案が先行して検討され、実運用で不十分と判定されて撤回されている。要約は「機能を実装した」という一行を運べても、成果物の実体・設計判断の詳細・受け入れ基準ごとの検証結果という一次情報を運べず、読み手は結局リンク先を開くことになるためである。行数を増やす方向の改善では到達できない構造的な限界であり、必要なのは全文の同期である。

### 全文同期が正本の二重化を招かないための条件

同じ内容を 2 か所へ常時コピーするだけの設計は、更新漏れによる不整合・どちらが正本か不明・機械検査不能という 3 つのリスクを生む。これらはすべて「同じ内容について 2 つの場所が同時に正本を名乗る」ことに起因する。したがって全文同期を安全に成立させる条件は、正本がどちらか一方に一意に定まり、他方はその正本から機械的・決定的に導出される非正本の中継物である、と構造的に決着させることである。これは I6 が調整状態について既に採っている考え方と同型である。

### 本決定の直接の動機となった実例

本システムのメンテナ自身が、本提案の起票とは独立に「GitHub Issue を見ると情報が足りない。要求・要件・設計・実装計画が詳細に GitHub Issue を見ればすべて分かるようになっているべきである」と指摘した。提案が解決しようとしている問題が、提案者の固有事情ではなく本システムの通常運用でも再現することの裏付けである。

### 検討した代替案

| 代替案 | 却下理由 |
|---|---|
| 要約（3〜5 行）+ リンクのみを同期する | 成果物の実体・設計判断の詳細・検証結果の詳細が運べず、読み手は結局リンク先を開く。実運用で不十分と確認済み。 |
| 都度手動で Issue コメントへ転記する | 更新のたびに人手作業が発生し忘れられる。二重の情報源のずれを運用でカバーする案そのもので根本解決にならない。 |
| 成果物を Issue 本文へ直接書かせ、リポジトリファイルを廃止する | 行単位 diff・PR ベースのレビュー・複数ワーカーの同時編集調停という Git の機構を失う。 |
| GitHub Projects のカスタムフィールドで進捗管理する | 別画面遷移が必要で「Issue ページを見ただけで分かる」を満たさない。 |
| Check Run 名の一覧だけを本文へ貼る | ゲートの成否は分かっても成果物の内容が分からず、入口にしかならない。 |
| I1・I3 を改定せず、同期を「非公式な利便機能」として不変条件の外に置く | 正本がどちらか不明のまま 2 か所に内容が存在する状態を追認することになり、上記 3 リスクを構造的に排除できない。 |

## Decision

### D-1: I1・I3 を Coordination Backend 別の条件分岐へ改定する（採用する）

I1・I3 の改定を**採用する**。改定後の文言は次のとおりとする。要求そのもの（追跡可能であること・状態が完全復元可能であること・頭の中にしか無い状態を作らないこと）は一切緩和せず、その要求を満たす場所の記述だけをモード別に分岐させる。

- **I1 追跡可能性**: 全変更は Issue に紐づき、要求→設計(ADR)→実装→レビューの証跡が追跡可能な形で残り、現在有効な決定を指し続ける。GitHub モードで `issue_sync` を有効化した場合、証跡は Issue/PR 本文（成果物内容の正本）と Check Run に保持され、Git は同期元・版管理基盤として機能する。それ以外（ローカルモード、および `issue_sync` 無効の GitHub モード）は Git 履歴に証跡が残る。
- **I3 耐久性**: 作業状態は常に完全復元可能であり、頭の中にしか無い状態を作らない。GitHub モードで `issue_sync` を有効化した場合、復元元は Issue/PR 本文と Check Run（GitHub 側の永続化）を含む。それ以外は Git（remote push 済み）から完全復元可能。

採用の根拠は次の 3 点である。

1. I2 が既に同型の条件分岐を持つため、これは新しい記述パターンの導入ではなく既存パターンの一貫適用である。
2. GitHub モードの調整状態（Issue・PR・Check Run）は既に GitHub 側の永続化に依存しており、I6 がその依存を前提として受け入れている。本決定はその依存範囲を成果物内容へ対称に広げるものであって、依存の種類を新設するものではない。
3. 正本を一意に決めない限り、全文同期は必ず正本の二重化になる。全文同期を採るなら正本の所在を明示的に移すほかに構造的な選択肢が無い。

### D-2: 適用範囲は `issue_sync` を有効化したプロジェクトに限る

本改定は `issue_sync.enabled: true` を明示したプロジェクトにのみ適用される。既定は `issue_sync.enabled: false` であり、既定のままの GitHub モードプロジェクトでは I1・I3 の実効的な意味は改定前と同一である（証跡・復元元は Git）。ローカルモードは本決定の影響を一切受けない。

I3 の耐久性は「GitHub が消失・アクセス不能になった場合の復元可能性」という保証の性質を変える。この変化を全プロジェクトへ一律に強制しないため、適用をオプトインに限定する。

### D-3: 同期の実体（MVP スコープ）

`gate publish` が Check Run の発行に成功した直後に、Coordination Backend が GitHub かつ `issue_sync.enabled: true` の場合のみ、対象の Issue 本文（`target` 設定により PR 本文）の固定マーカー区間を機械生成内容で置換する。

- マーカーは `<!-- agent-skill-chain:issue-sync:begin (do not edit manually) -->` と `<!-- agent-skill-chain:issue-sync:end -->` の対とする。マーカー外の人間記述部分は読み取りのみ行い一切変更しない。マーカーが存在しない本文には末尾へ区間を新設する。
- 区間の内容は、対象 commit SHA、4 ゲートそれぞれの判定状態、および対象 commit に存在する `SPEC.md`・`DESIGN.md`・`PLAN.md`・`VALIDATION.md` の**全文**（要約・抽出を行わない）とする。
- 同期は一方向（Git → Issue/PR）であり、生成された区間をゲート判定・検証の入力として読み戻すことはしない。ゲート判定は引き続き commit と Check Run に基づく。
- 同期の失敗・スキップは `gate publish` 自体を失敗させない。理由を警告として出力し、Check Run の発行結果を最終的な成否とする。同期は判定に用いる正本の生成ではなく、正本から導出される一方向転記であるため、可用性を優先する。

### D-4: 未解決事項への回答（MVP での確定方針）

本決定の起点となった提案が列挙した未解決事項に対し、MVP で採る方針を次のとおり確定する。

1. **1 Issue が複数 PR に跨る場合の集約**: 対象が PR の場合、当該Issueに紐づく open な PR が一意に特定できるときのみ同期する。判定は PR 本文の close 参照（`Closes #<番号>` 等）と head ブランチ名の命名規則の 2 経路で行う。該当が 0 件または 2 件以上のときは同期をスキップし理由を出力するに留め、エラーにはしない（ベストエフォート機能であるため）。
2. **GitHub API のレート上限**: 呼び出しはゲート通過 1 回につき、対象ごとに読み取り数回と書き込み 1 回のみとする。ゲートは 1 Issue あたり 4 回（差し戻し時の再通過を含めても数回程度）しか通過しないため、高頻度呼び出しにはならない。バッチ化・呼び出し間隔制御は実装しない。大規模プロジェクトで実際に上限へ達した場合の再検討事項として記録するに留める。
3. **同時更新の競合**: 書き込み前に対象本文を読み直し、直前に観測したマーカー区間の内容と一致するかを比較する compare-and-swap 相当の検知を行う。不一致を検知した場合は 1 回だけ再取得してやり直し、それでも不一致なら書き込みを行わず警告を出力してスキップする。書き込み自体を GitHub 側で不可分にする手段は提供されていないため、検知後に失敗させるのではなくスキップする（次のゲート通過時に最新内容で再同期される）。
4. **本文上限超過時の分割**: 生成後の本文全体が上限（GitHub の本文上限 65536 文字に対し安全側の余裕を取った既定 60000 文字）を超える場合、全文を本文へ書かず、Git 側の該当ファイルを最終同期 commit で参照するよう促す短い案内文へ切り替える。専用コメントスレッドへの分割保存は本決定のスコープ外とし、将来の改善候補として記録する。
5. **既存検査スクリプトへの影響**: 成果物存在チェック等の既存検査は変更しない。同期は Git 側ファイルの存在を前提とする導出処理であり、Git 側ファイルが存在しなくなる訳ではないため、検査対象の置き換えは発生しない。
6. **既存プロジェクトの移行**: `issue_sync.enabled: false` が既定であるため移行作業は発生しない。有効化したプロジェクトでも遡及適用は行わず、有効化以降にゲートを通過したIssueから順次同期される。

### D-5: 設定項目として持つ値と持たない値

`issue_sync` に置くのは `enabled`（オプトインの可否）・`target`（Issue 本文か PR 本文か双方か）・`max_body_chars`（本文上限の安全域）の 3 項目のみとする。設定項目の追加手順が要求する「内部で固定できる値は設定に出さない」に従い、次の値は設定に出さず実装内で固定する。

- 同期対象ファイルの集合: 4 セグメントの主成果物として固定であり、プロジェクト単位で変わる余地が無い。
- Coordination Backend と成果物内容の正本の対応（GitHub モード → Issue/PR 本文、ローカルモード → Git 管理下ファイル）: 本決定が定める不変の対応関係であり、プロジェクト設定で上書きできてはならない。不変条件の上書きを試みる記述は設定エラーとして扱うという既存の優先順位規則にも反する。
- 中継元への参照の固定方法: commit SHA 固定のみを実装するため選択肢が無い。
- 上限超過時の方式: MVP は Git 参照への切り替えのみを実装するため選択肢が無い。将来 2 つ目の方式を実装する時点で設定項目を追加する。

## Consequences

- GitHub モードで `issue_sync` を有効化したプロジェクトでは、Issue ページを開くだけで現在のセグメント進捗・ゲート状態・要求・設計・実装計画・検証結果の全文が読める。PR の変更ファイル一覧を開く往復が不要になる。
- 有効化したプロジェクトにおいて、成果物内容の正本は Issue/PR 本文となり、Git 管理下ファイルは同期元・版管理基盤という位置づけへ変わる。人間が状況把握のために読みに行く先が変わるのであって、成果物が commit される場所は変わらない。diff によるレビュー・複数ワーカー間の同時編集調停は引き続き Git の機構に依存する。
- 有効化したプロジェクトでは、GitHub が消失・アクセス不能になった場合の復元可能性が、調整状態に加えて成果物内容についても GitHub 側の永続化に依存する。ただし Git 側ファイルは廃止されないため、実務上は Git 側からの復元も引き続き可能である。この依存を受け入れられないプロジェクトは既定（無効）のままにすることで従前の保証を維持できる。
- 既定が無効であるため、既存の GitHub モードプロジェクトは本機能の導入によって一切の挙動変化を受けない。Issue/PR 本文への書き込みは発生しない。
- マーカー区間は機械が排他的に書き込む領域であり、人間が編集した内容は次の同期で失われる。マーカー内に手動編集禁止である旨を明記するが、機械的な強制手段は持たない。
- 同期は失敗してもゲート通過を妨げない。したがって「同期が成功していること」は保証されず、Issue 本文が最新でない期間が生じうる。マーカー区間には最終同期 commit を必ず記録し、読み手が鮮度を判断できるようにする。
- 本文上限を超える規模の成果物を持つIssueでは、全文が本文に載らず案内文へ縮退する。この場合に限り読み手は Git 側を参照する必要があり、本決定が解こうとした問題が部分的に残る。専用コメントスレッドへの分割保存が将来の改善候補である。
- 同時更新の競合検知はスキップで終わるため、稀に同期が 1 回分行われないことがある。次のゲート通過時に最新内容で上書きされるため、恒久的な不整合にはならない。
- 本決定の適用範囲は Issue/PR 本文に限る。Slack 通知・ダッシュボード等への同期、および `docs/system-spec/`（Issue をまたいで永続するシステム仕様書）は対象外である。後者は正本の性質・ライフサイクルがIssue単位の成果物と異なる。

## accepted 後の不変項目・可変項目

| 区分 | 項目 |
|---|---|
| 不変（accepted 後は変更不可） | `id`、Context、Decision、Consequences、`supersedes` |
| 可変（ライフサイクル遷移に伴い更新可） | `status`、`superseded-by`、`deprecated-reason`、`tags` |

本文（Context / Decision / Consequences）の変更が必要になった場合は、新しい ADR を作成し `supersedes` / `superseded-by` で旧 ADR との関係を記録する。既存 ADR の本文を書き換えてはならない。

## ライフサイクル

```text
DESIGNワーカー   → ADR を proposed で作成
設計レビュア     → ADR 本文をレビュー（read-only）→ content digest を承認
進行役           → adr-finalize.sh を起動
ADR finalization → writer lease を取得 → status を accepted へ更新
ワーカー           → commit・push → content digest を再検査
```
