## Context

### 本ADRが扱う問題

agent-skill-chain（本npmパッケージ・CLI）は、導入時に対象リポジトリへ次を配置する。これが本ADRの検討対象となる現行構成である。

- `init`: `AGENTS.md`・`CLAUDE.md`・`docs/GLOSSARY.md` をリポジトリ直下へ、`standards`・`templates`・`schemas`・`config`・`adapters`・`scripts`・`ci`・`hooks` を `.agent-skill-chain/` 配下へ複製する。配置される `CLAUDE.md` は本文5行で、実体は `@AGENTS.md` の1行importである。
- `setup github`: `.github/` 配下のワークフロー同期・ラベル作成・branch ruleset適用をGitHub API経由で行う。ruleset は `main` に対し required status checks として4つのゲート名と `verify` を要求し、非fast-forward・削除を禁止する。
- `enforce on`: `.claude/settings.json` へ PreToolUse hook を配線する。hook本体は `tool_name=="Bash"` のみを検査し、(1) `cleanup` を経由しない `git worktree remove` の直接実行、(2) 命名規約に違反するブランチ作成、の2種のみを終了コード2で拒否する（それ以外はすべて通過するfail-open設計）。
- CLI本体（`bin/agents-md.js`）は約70個のサブコマンドを持つ。`issue start`・`lease acquire`・`segment start`・`gate publish`・`gate reconcile`・`pr create`・`verify *`・`lint *` 等、状態遷移1つにつき1コマンドという構成である。

この構成の特徴は、`CLAUDE.md` から `@AGENTS.md` をimportすることで、当該リポジトリの**すべてのClaude Codeセッションが常に**不変条件I1〜I8・4セグメント・4ゲート・writer lease・進行役の純粋性という規律を前提として動く点にある。ユーザーからの問題提起は次のとおりである——「このシステムは常時稼働する統制系として機能しているが、そうではなく一連の流れを必要時に呼び出せるスキルとして持たせる必要がある。開発をあまりしない利用者もいるはずだ」。

本ADRは実現可能性の調査結果を記録するものであり、実装は伴わない（由来: Issue #428）。

### 前提とする用語（本ADR内で自己完結して定義する）

- **スキル**: `SKILL.md` を必須エントリポイントとするディレクトリ。YAMLフロントマターの metadata と markdown 本文からなり、補助ファイル・実行可能スクリプトを同梱できる。AIエージェントが必要と判断した時、または利用者が `/<名前>` と入力した時に本文が文脈へ読み込まれる。
- **常時規範**: セッション開始時に無条件で文脈へ読み込まれ、以後すべての応答の前提となる指示文。Claude Code では `CLAUDE.md` および `.claude/rules/` がこれに該当する。
- **強制（enforcement）**: エージェントの判断に関わらず、機械が特定の操作を確定的に拒否・実行する層。Claude Code では hook・permission設定、GitHub側では branch ruleset・required status checks がこれに該当する。

### 調査1: Claude Codeスキル機構の技術的性質（一次情報に基づく）

参照した一次情報（2026-08-04取得）:

- Claude Code公式文書「Extend Claude with skills」 https://code.claude.com/docs/en/skills
- Claude Code公式文書「Hooks」 https://code.claude.com/docs/en/hooks
- Claude Code公式文書「How Claude remembers your project」 https://code.claude.com/docs/en/memory
- Claude Code公式文書「Extend Claude Code」 https://code.claude.com/docs/en/features-overview
- Claude Code公式文書「Create plugins」 https://code.claude.com/docs/en/plugins
- Agent Skills オープン標準 https://agentskills.io
- OpenAI Codex公式文書「Build skills」 https://learn.chatgpt.com/docs/build-skills
- Anthropic公式プラグイン集 https://github.com/anthropics/claude-plugins-official
- Superpowers（第三者OSS、スキルとして開発規律を配布する実例） https://github.com/obra/superpowers

得られた事実は次のとおり。

**(a) ロードのされ方は常時ではなく進行的開示である。** Agent Skills標準は3段階を規定する——「Discovery: 起動時にエージェントは各スキルの名前と説明のみを読み込む」「Activation: タスクがスキルの説明に一致した時、`SKILL.md` の全文を文脈へ読み込む」「Execution: 同梱コードの実行や参照ファイルの読み込みを必要に応じて行う」。Claude Code公式文書も「通常のセッションではスキルの説明のみが文脈へ読み込まれ、全文は呼び出された時にのみ読み込まれる」と明記する。`disable-model-invocation: true` を設定すると説明すら文脈へ載らず、利用者が明示的に呼び出すまで消費文脈はゼロになる。

**(b) `CLAUDE.md` は常時全文ロードであり、importでは軽くならない。** 公式文書は「`CLAUDE.md` ファイルは毎セッション開始時に文脈ウィンドウへ読み込まれ、会話と並んでトークンを消費する」「importへの分割は整理には役立つが、importされたファイルも起動時に読み込まれるため文脈は削減されない」と明記する。したがって現行の `CLAUDE.md` 1行import構成は、`AGENTS.md` 144行を全セッションへ常時載せている。

**(c) 常時規範は強制ではない。** 公式文書は「Claudeはこれらを文脈として扱い、強制された設定としては扱わない。Claudeの判断に関わらず操作を阻止するには PreToolUse hook を使うこと」と明記する。さらに「`CLAUDE.md` やスキルに書かれた『.envを編集するな』という指示は要請であって保証ではない。PreToolUse hook による阻止が強制である。規則が毎回成立しなければならないなら、指示文ではなくhookにせよ」と述べる。

**(d) スキルはhookを同梱できるが、寿命はスキルの有効期間に限られる。** 公式文書はスキル・サブエージェントのフロントマターに `hooks` フィールドを定義でき、設定ファイル記載のhookと同一の記法であり、全hookイベントを利用可能と記す。ただし「フロントマターで定義されたhookはそのコンポーネントの寿命にスコープされる——コンポーネントが有効な間だけ実行され、終了時に自動的に解除される。これはセッション全体で持続するプロジェクトレベルのhookより狭い」。すなわちスキル同梱hookは「スキルを呼び出さなかったセッション」を一切統制できない。

**(e) スキルのツール制御はターン単位であり恒久的な拒否ではない。** `allowed-tools` は「スキルを呼び出したターンの間だけ許可を与え、次のメッセージ送信時に解除される。利用可能なツールを制限するものではない」。`disallowed-tools` は「スキルが有効な間、利用可能プールからツールを除去する。次のメッセージで解除される」。恒久的な拒否は permission設定側のdenyルールが担う。

**(f) スキルはスクリプトを同梱・実行できる。** 標準は `scripts/`・`references/`・`assets/` の同梱を認め、Claude Codeは `${CLAUDE_SKILL_DIR}` 置換により、スキルがどの階層に導入されても同梱スクリプトの絶対パスを解決できる。`allowed-tools` に同じ置換を書けば許可プロンプトなしで実行できる。加えて `` !`コマンド` `` 記法は、スキル本文がAIへ渡る**前に**シェルコマンドを実行し出力を本文へ差し込む前処理を提供する。ただし `disableSkillShellExecution` 設定が真の環境ではこの前処理は無効化され、`[shell command execution disabled by policy]` に置換される。

**(g) 配布経路は4系統ある。** プロジェクト（`.claude/skills/` をバージョン管理へcommit）・個人（`~/.claude/skills/`）・プラグイン（`<plugin>/skills/`、marketplace経由で配布）・組織管理（managed settings）。プラグインは skills・agents・hooks（`hooks/hooks.json`）・MCPサーバ・`settings.json` を1単位に束ねられ、有効化中はそのhookが利用者・プロジェクトのhookと**併合**される。さらにスキルフォルダへ `.claude-plugin/plugin.json` を置くと `<名前>@skills-dir` としてプラグイン扱いになり、agents・hooks・MCPサーバを同梱できる。

**(h) 分量制約がある。** `SKILL.md` は500行以内が推奨され、`description` と `when_to_use` の合算はスキル一覧表示上1,536文字で切り詰められる。一覧全体の予算は既定でモデル文脈長の1%であり、超過時は利用頻度の低いスキルから説明が削られる。またスキル本文は一度読み込まれるとセッション中残り続け、Claude Codeはファイルを再読み込みしない。

**(i) スキルはベンダー中立の公開標準である。** Agent Skillsは「Anthropicが開発し、オープン標準として公開された」形式であり、Codex・Cursor・Gemini CLI・GitHub Copilot・OpenCode・Goose等が対応する。Codexは `SKILL.md` を `.agents/skills` 等から探索し、`scripts/` の同梱実行に対応する。本パッケージが `.agent-skill-chain/adapters/{claude,codex,human}.sh` によるベンダー中立を掲げていることと、スキル形式の採用は矛盾しない。

**(j) 「開発規律をスキル・プラグインとして配布する」実例は既に存在する。** Anthropic公式プラグイン集の `feature-dev` は、Discovery→Codebase Exploration→Clarifying Questions→…という段階分割された開発手順を、単一のコマンド文書と3つの専用エージェント定義として配布する。同じく公式の `hookify` は、`PreToolUse`・`PostToolUse`・`Stop`・`UserPromptSubmit` の4イベントに対するhookをプラグインとして配布し、利用者が書いた宣言的な規則ファイル（`event: bash` / `pattern: rm\s+-rf` / `action: block`）で操作を阻止する。第三者OSSのSuperpowersは、着想の吟味・worktree作成・計画・サブエージェント実行・テスト駆動・レビュー・ブランチ完了という7段階の規律をスキル群として配布し、Claude Codeでは公式marketplace経由で導入、他エージェントではセッション開始hookで自動有効化する。すなわち「規律のスキル配布」は既に確立した実装様式であり、本ADRの検討は前例のない試みではない。

### 調査2: 現行構成要素がスキルに収まるか

| 構成要素 | 判定 | 理由 |
|---|---|---|
| `AGENTS.md` 本体（不変条件・4セグメント・writer lease等の規範知識） | **スキルとして表現可能**（ただし性質が変わる） | 144行の指示文であり `SKILL.md` の500行推奨内に収まる。だが `CLAUDE.md` からのimportは「毎セッション必ず前提となる」のに対し、スキル化すると「AIが説明文から関連ありと判断した時、または利用者が明示的に呼んだ時のみ」前提となる。規範として同一ではなく、無視され得る規範になる。 |
| `enforce on` が配線する PreToolUse hook | **スキルだけでは代替不可能** | 公式文書が明示するとおり、指示文は要請であって保証ではなく、確定的な阻止はhookのみが行う。スキルフロントマターの `hooks` で同等のhookを同梱すること自体は可能だが、スキルの寿命に限定されるため「スキルを呼ばずに `git worktree remove` を実行する」経路を塞げない。恒久的な配線には `.claude/settings.json`（現行方式）またはプラグインの `hooks/hooks.json` が必要。 |
| branch protection ruleset・GitHub Actions（`verify` 等の required status checks） | **スキルだけでは代替不可能（原理的に）** | 強制点がGitHubサーバ側にあり、ローカルのAIエージェント設定からは到達できない。スキルは「AIエージェントが何を読むか」を変えるだけであり、`main` への直接pushやゲート未通過マージを阻止する能力を持たない。ここは `setup github` によるAPI適用以外の実現手段が存在しない。 |
| CLI本体（`bin/agents-md.js`、`issue start`・`gate publish` 等の実処理） | **スキル化する必要がなく、そのまま配布が適切** | スキルはスクリプトを同梱・実行できるため技術的には同梱可能だが、CLIは既にnpmパッケージとして版管理・テスト・型検査を備えた実行系であり、`SKILL.md` へ移せるのは「どのコマンドをどの順で叩くか」という手順記述のみ。実処理をスキルへ移す利得はなく、CLIはCLIのまま、スキルはその呼び出し手順書とするのが標準的な役割分担（公式文書のhook対skill比較が示す「hookは決定的な実行、skillは推論が要る手順」という区分に合致）。 |
| `.agent-skill-chain/scripts/` の薄いラッパースクリプト | **スキルの同梱スクリプトとして表現可能** | 各スクリプトはCLIサブコマンドへの薄い委譲であり、`${CLAUDE_SKILL_DIR}/scripts/...` として同梱し `allowed-tools` に同じ置換式を書けば、許可プロンプトなしで実行できる。ただし `disableSkillShellExecution` を組織管理設定で有効化した環境では前処理系の記法が無効化されるため、スキル本文の `` !`コマンド` `` 前処理に依存する設計は避ける必要がある。 |

### 調査3: 常時統制とオンデマンド呼び出しのトレードオフ

両者は「二者択一」ではないが、**同一の層では両立しない**。整理すると次の3層に分解でき、層ごとに答えが異なる。

1. **強制層**（hook・permission・GitHub ruleset）: オンデマンド化できない。呼ばれなかった時に効かない強制は強制ではないため、これは定義上の帰結である。ただし「導入する／しない」の粒度で軽量化することは可能であり、現に本パッケージは `init`（ローカル資産のみ）と `setup github`（サーバ側強制）と `enforce on`（hook配線）を既に分離しており、後者2つはオプトインである。すなわち強制層の軽量化は既に達成済みで、残る重さは規範層にある。
2. **規範層**（`AGENTS.md` の常時import）: ここが本問題提起の核心である。常時importは(i)全セッションで文脈を消費し、(ii)開発以外の用件（調べもの・単発の修正）にも4セグメント・writer leaseという語彙を持ち込む。スキル化すれば消費はほぼゼロになり、必要時のみ規律下へ入れる。代償は「AIが自発的に規律を読み込まないまま作業を始める」可能性であり、これはサイレントな逸脱そのものである。ただしこの代償は、強制層が独立して残っている限り**致命的ではない**——規範を読まずにブランチを切っても命名規約違反はhookが拒否し、ゲート未通過のマージはrulesetが拒否する。規範層の役割は「逸脱の防止」ではなく「逸脱の回避と手順の一貫性」であり、最後の砦は元々強制層にある。
3. **手順層**（CLIの呼び出し順序・成果物テンプレート・ゲート審査の進め方）: 本質的にオンデマンドが適する。公式文書の指針も「複数手順の手続きを3度目に貼り付けたらスキルにせよ」「`CLAUDE.md` の一節が事実ではなく手続きに育ったらスキルにせよ」であり、現行 `AGENTS.md` のうち4セグメント運用手順・ゲート審査手順・worktree操作手順はまさにこれに該当する。

したがって部分的ハイブリッドは現実的である。具体的には「強制層＝現行のまま（オプトイン）」「規範層＝不変条件など最小限のみ常時、残りはスキル」「手順層＝全面スキル」という分割が、公式文書が推奨する機構別の使い分け（常時規則は `CLAUDE.md`、path限定規則は `.claude/rules/`、手続きと参照資料はスキル、確定的強制はhook）と完全に一致する。なお `.claude/rules/` の `paths` フロントマターを使えば「特定パスのファイルを触った時だけ規範を読み込む」という中間形態も選べる。

### 調査4: 想定利用者の分類

| 類型 | 特徴 | 適合するモデル |
|---|---|---|
| 常時開発型 | 複数人・複数Issue並行、監査証跡・ゲート再通過・writer leaseによる競合制御が実利をもたらす。GitHub Coordination Backend、required status checks運用。 | 現行の常時規律モデル（`@AGENTS.md` import + `setup github` + `enforce on`）。 |
| 間欠開発型 | 単独または少人数、開発は月数回。多くのセッションは調査・小修正・文書更新であり、Issue起票からゲート4通過までの手続きが作業本体より重い。 | スキルモデル（規範は呼び出し時のみ、CLIは導入するが強制層は入れない、`coordination.backend: local`）。 |
| 非開発型 | リポジトリはあるが本パッケージの規律を必要としない。 | 導入対象外。ただし誤って `init` した際に全セッションが規律下に入ってしまう現状は、この類型にとって明確な害である。 |

両方に対応する必要がある。後者だけに絞ることはできない——現行の常時規律モデルは本リポジトリ自身の運用（自己適用）で実利を上げており、これを削れば不変条件I2・I5の検証手段が失われる。逆に前者だけに絞ると、問題提起にある「開発をあまりしない利用者」は導入自体を見送るか、`init` 後に手動で `CLAUDE.md` のimportを削るという未文書化の運用へ流れる。

### 調査5: 検討した代替案

- **(a) 完全にスキルへ置き換える**: 却下。GitHub ruleset・required status checks・恒久hookはスキルで表現できず（調査2）、不変条件I2（セグメントゲート）・I4（分離）の機械的検査手段が失われる。「機械的に検査可能」を不変条件の要件としている本システムの設計前提そのものと衝突する。
- **(d) 実現困難で見送る**: 却下。調査1(g)(j)が示すとおり、スキル・プラグインによる開発規律の配布は既に確立した実装様式であり、技術的障壁は無い。見送る理由は技術ではなく優先度になるが、間欠開発型利用者にとっての実害（調査4）は現に存在する。
- **(b) 現行モデルを維持しつつスキル版を並行提供**: 有力。導入時の選択肢（プロファイル）を増やす方向。
- **(c) 現行モデルのままハイブリッド化する（一部のみスキル化）**: 有力。全利用者に対し、手順層をスキルへ移して常時文脈を減らす方向。

(b)と(c)は排他ではない。(c)は「常時載せる分量を減らす」内部再編であり、(b)は「強制層を入れない導入形態を用意する」外部インターフェースの追加である。

## Decision

**推奨案: (b) と (c) の合成——現行の常時規律モデルを既定として維持したうえで、規範の一部をスキルへ移す内部再編（c）を先に行い、その成果を用いて強制層を伴わない軽量導入形態（b）を並行提供する。** 本ADRは調査結果としてこの方針を推奨するものであり、実装は別Issueの判断に委ねる（Issue #428のスコープは調査のみ）。

推奨の内容を具体的に示す。

1. **強制層は現状維持**: `setup github`（ruleset・Actions）と `enforce on`（PreToolUse hook）は現行のままオプトインとして残す。スキル化しない。理由は、確定的な阻止はhookとサーバ側強制でしか実現できず（調査1(c)(d)、調査2）、これらは既にオプトインで軽量導入時は入らないため、問題提起にある「重さ」の原因ではないからである。
2. **規範層の分割**: `AGENTS.md` に残す常時規範を、不変条件I1〜I8・4セグメントと4ゲートの対応・Coordination Backendの選択・writer leaseの基本規則・用語の正本という「事実と常時規則」に限定する。ゲート審査の進め方・worktree操作の手順・ADRライフサイクルの操作手順・成果物テンプレートの記入手順といった「手続き」は `SKILL.md` 側へ移す。これは公式文書の「`CLAUDE.md` の一節が事実ではなく手続きに育ったらスキルにせよ」という指針の直接適用である。
3. **スキルの粒度**: 単一の巨大スキルではなく、セグメント・役割に対応する複数スキル（例: Issue起票とworktree開始、セグメント作業、ゲート審査、PR作成とマージ、後片付け）へ分ける。理由は、スキル本文は一度読み込むとセッション中残り続け再読み込みされないため（調査1(h)）、必要な手順だけを載せる粒度が文脈効率と追随性の双方で有利だからである。各スキルは実処理を持たず、`.agent-skill-chain/scripts/` および CLI サブコマンドの呼び出し手順書として書く。
4. **軽量導入形態**: `init` に軽量プロファイルを追加し、(i) `CLAUDE.md` への `@AGENTS.md` importを行わず、(ii) `.claude/skills/` 配下へ上記スキル群を配置し、(iii) `coordination.backend: local` を既定とし、(iv) 強制層（`setup github`・`enforce on`）を実行しない構成を選べるようにする。この形態では逸脱の機械的阻止が無いことを導入時に明示する。
5. **配布形式**: スキルはまず本パッケージが `.claude/skills/` へ複製する形（プロジェクトスキル）で提供する。プラグイン化・marketplace公開は、hooks同梱による強制層の再統合（調査1(g)）という利点があるものの、Claude Code固有の仕組みであり、ベンダー中立のrole contract（`.agent-skill-chain/config/roles.yaml`）とadapter層を正本とする現行設計との整合を別途要する。`SKILL.md` 形式自体は公開標準でありCodexも解釈できる（調査1(i)）ため、まずは標準準拠のスキル群を配布し、プラグイン化は後続判断とする。

**引き続き調査・議論が必要な事項**（本ADRでは確定させない）:

- 規範層のどこまでを常時規範として残すかの正確な線引き。不変条件I5（進行役の純粋性）のように、違反が起きるのが「規律を読んでいないセッション」である種類の規則は、スキルへ移すと機能しない可能性がある。
- 軽量プロファイルにおける不変条件I2・I3の扱い。ローカルCoordination Backendでは `reviews/<gate>.yaml` と `state.yaml` が正本となるが、これらを人間・AIが自主的に書く運用で不変条件と呼び続けられるか、ガイドラインへ降格すべきかの判断。
- 既に現行モデルで導入済みのプロジェクトに対する移行手順（`upgrade` が `CLAUDE.md` を書き換えてよいか）。
- スキル一覧の文脈予算（既定でモデル文脈長の1%、調査1(h)）に対し、複数スキルの説明文が占める割合の実測。

## Consequences

- 間欠開発型利用者が、強制層と常時規範を伴わずに本パッケージの手続きだけを必要時に呼び出せるようになり、導入見送りまたは未文書化の手動改変という現状の逃げ道が解消される。
- 常時開発型利用者にとっても、手続きを常時規範から外すことで全セッションの文脈消費が減る。`AGENTS.md` の行数上限（150行）に対する圧力も緩和される。
- 一方で、規範層をスキルへ移した分だけ「AIが規律を読み込まないまま作業を始める」経路が増える。強制層を導入していないプロジェクトでは、この逸脱を検知する手段が無い。軽量プロファイルはこの性質を導入時に明示する必要があり、明示しなければ利用者は現行と同等の統制がかかっていると誤認する。
- スキル本文と `AGENTS.md`・`.agent-skill-chain/standards/` の間に内容の重複が生じ得る。本システムは成果物の自己完結性を要求する一方で参照による意味の委譲を禁じているため、スキルを「手順の正本」とし規範文書側から手順記述を削る（重複を作らない）方針を取らないと、二重管理による陳腐化が発生する。
- 配布資産が増える（`.claude/` 配下への書き込み）。現行の `init` は `.github/` を暗黙変更しない設計を明示的な利点としており、`.claude/` への書き込みも同じ扱い（明示的なオプトイン、衝突時は上書きせず日本語の理由付きエラーで停止）とする必要がある。`.claude/` は本リポジトリ自身では追跡対象外に設定されているため、consumerプロジェクトでの追跡方針も決める必要がある。
- 本ADRは調査結果の記録であり、実装を承認するものではない。`init` のプロファイル追加は設定項目の追加ではなく導入手順そのものの分岐であり、実装に着手する場合は本ADRとは別に、対象範囲・受け入れ基準・移行手順を持つIssueを起票する必要がある。
