## Context

`.agent-skill-chain/` 配下のシェルスクリプトのうち54本（`scripts/` 直下40本、`ci/` 配下12本、`adapters/` 配下2本）は、agent-skill-chain CLI サブコマンドへの薄いラッパーであり、いずれも同一の3経路解決ブロック（`bin/agents-md.js` → `node_modules/.bin/agent-skill-chain` → PATH上の `agent-skill-chain`）を自ファイル内にコピーして保持していた。3経路のいずれでも解決できない場合、これら54本は日本語エラーを出して即座に `exit 1` するだけで、CLIの自動導入は行わなかった。

一方、配布用CIワークフローテンプレートの「Ensure agent-skill-chain CLI」ステップには、同じ3経路で解決できない場合に `npm install -g agent-skill-chain@latest` を実行する自動導入フォールバックが既に実装されていた。この修正はワークフロー1箇所にのみ適用され、共通化されていないローカル用スクリプト側へは横展開されなかった。結果として、テンプレート一式のみを導入しCLI本体を未導入の consumer プロジェクトでは、CIでは自動導入されて処理が続行するのに対し、ローカルで同じ処理を直接実行すると即座に失敗するという挙動乖離が生じていた。乖離そのものよりも、ロジックが55箇所（54本＋ワークフロー）へ分散していて今後の変更が必ず横展開漏れを起こすという構造が本質的な問題である。

検討したトレードオフは次のとおり。

- **重複排除の代償としての単一障害点**: 55箇所の重複を1箇所へ集約すると、その1ファイルの欠落・破損が54本すべての起動不能へ直結する。重複を残したまま「変更時は全箇所を更新する」という規律で運用する案は、本Issueの発生経緯（規律が実際に破れた）がその実効性を否定している。
- **共有実装の配置先**: 専用ディレクトリを新設する案は名前空間として明快だが、パッケージ同梱設定・展開対象の名前空間一覧・導入時の所有権記録・アンインストール対象・アップグレード時の削除候補判定という複数機構の同時更新を要し、いずれか1つの漏れが「consumer 展開物に共有実装だけが含まれない」という最悪の退行を生む。
- **自動導入の既定値**: グローバル領域への `npm install -g` は可逆でない副作用を持つ。同意確認を必須にする案は安全側だが、非対話環境（CIランナーおよび開発端末上でフック・親スクリプト・エージェントから配管越しに起動された場合）では同意を得る手段が無く、「CIとローカルの挙動を揃える」という本Issueの要求そのものと両立しない。
- **並行実行への対処**: 複数のラッパーが同時にCLI未解決状態から起動されると、グローバル導入が並行実行され、途中結果（部分的に配置され実行可能でない実体）が観測されうる。相互排他による直列化はこれを防ぐが、ロックファイルの残留・異常終了時の後始末という新たな失敗モードを持ち込む。
- **呼び出し形態の差**: 対象54本のうち52本は直接実行されるが、`adapters/claude.sh`・`同 human.sh` の2本は他スクリプトから `source` されて関数群を提供する形で使われ、内部に `_asc_cli` 関数を持つ。直接実行される側は失敗時に `exit` で自プロセスを終了させる必要があり、`source` される側で `exit` を使うと呼び出し元シェルを巻き添えに終了させる。両者を1つの契約・1つのテキストで扱おうとすると、この停止手段の非両立がそのまま設計の矛盾になる。

## Decision

1. **3経路解決と自動導入フォールバックを、単一の bash ライブラリ `.agent-skill-chain/scripts/cli-resolve.sh` へ集約する。** 公開契約は関数 `asc_resolve_cli`（戻り値0のとき、かつそのときに限り配列変数 `ASC_CLI` にCLI起動用 argv の前置部分が設定される）のみとする。ライブラリは標準出力へ何も書かず、メッセージと自動導入コマンドの出力はすべて標準エラー出力へ出す。呼び出し元のカレントディレクトリに依存せず、自身の位置からリポジトリルートを算出する。

2. **配置先を既存の配布対象ディレクトリ `.agent-skill-chain/scripts/` 内に限定する。** 専用ディレクトリは新設しない。これにより、パッケージ同梱・展開・所有権記録・アンインストール・アップグレードの各機構を一切変更せずに、共有実装が consumer へ確実に配布される。

3. **読み込み方式は `source` とする。** 解決結果が複数要素の argv（第1経路では `node` と JS ファイルの絶対パスの2要素）であり、子プロセスの標準出力経由で文字列として返すと引用・空白の復元が呼び出し元の再解析に依存して壊れるため。ラッパー1回あたりのプロセス生成を増やさない利点も伴う。

4. **対象54本を呼び出し形態により2つの契約へ明示的に分ける。** 直接実行される52本（`scripts/` 直下40本・`ci/` 配下12本）を契約W、他スクリプトから `source` されるアダプタ2本（`adapters/claude.sh`・`同 human.sh`）を契約Aとする。両者を単一の契約へ押し込むことはしない。失敗時の停止手段が両立しないためである——契約Wは `exit` で当該プロセスを非ゼロ終了させる必要があり、契約Aで `exit` を用いると呼び出し元シェルを巻き添えに終了させてしまうため `return` で非ゼロを返す必要がある。直接実行時と `source` 時で自動的に振る舞いが変わる単一記述（`return … || exit …` の類）は採らない。当該記述の挙動が bash の版・実行形態に依存し、依存が破れた場合に「エラーを出したまま処理が継続して委譲へ到達する」という最も重い失敗形へ倒れるためである。

5. **共有実装を読み込む前文を、終了形を表す語（契約Wは `exit`、契約Aは `return`）を除いて54本で文字単位に同一とし、自己位置の算出手段を `${BASH_SOURCE[0]}` に固定する。** 対象54本はすべて `.agent-skill-chain/<ディレクトリ>/<名前>.sh` という同一の階層深さにあるため、共有実装への相対的な位置関係も同一である。算出手段に `$0` を用いてはならない。契約Aの2本は `source` されて使われ、その文脈で `$0` は呼び出し元のパスを指すため、`$0` 基準では当該2本が誤った基準ディレクトリから共有実装を探して解決に失敗する。前文は「共有実装パスの算出 → 読み取り可能性検査 → `source` の成否検査 → 公開関数の定義有無検査」の3段検査を行い、いずれか1つでも成立しなければ探索パスを含む日本語エラーを標準エラー出力へ出して非ゼロで停止する。前文は3経路解決に関する判定を一切含まない（インライン再実装を禁じ、重複の再導入を構造的に排除する）。前文はマーカーコメントで囲み、機械的な抽出・同一性検証と対象集合の列挙の双方をこのマーカーで行う。

6. **解決関数 `asc_resolve_cli` の呼び出しを前文に含めない。** 呼び出し位置は、契約Wでは前文の直後（トップレベル、起動時）、契約Aでは `_asc_cli` 関数の本体とする。契約Wで起動時に解決を済ませるのは、引数や分岐に依存して解決・自動導入分岐へ到達しない実行経路を作らないためである（当該経路が生じると、全数を対象とする受入判定が引数の選び方に依存してしまう）。契約Aで同じことをしないのは、`source` された時点で副作用が発火するためである。前文に含めると、契約Aのアダプタが `source` された時点で——`_asc_cli` を一度も呼ばない呼び出し元に対しても——自動導入分岐へ到達し、`npm install -g` という不可逆なグローバル副作用が発生しうる。加えて `_asc_cli` 本体でも同じ関数を呼ぶため解決手続きが二重に走る。呼び出しを前文から外すことで、副作用の発火点は契約Wでは委譲直前、契約Aでは `_asc_cli` の呼び出し時の各1回だけとなり、利用者の同意を求める手段（対話確認・オプトアウト）と発火点が一致する。契約Wの外部から観測できる挙動はこの変更で変わらない。

7. **契約Aに対する全数判定の実施手順を、呼び出し元スクリプト（driver）経由と定める。** 契約Aの2本は直接実行を想定した実体ではなく固定の委譲先サブコマンドも持たないため、「1本実行する」の意味を確定させなければ全数判定が実施不能になる。driver は対象アダプタを `source` し `_asc_cli` を所定の引数列で1回呼び、その戻り値を自身の exit code とする。後方互換の判定では、委譲先サブコマンド名の一致を「記録された引数列の先頭要素の一致」として評価する。共有実装を解決できない状態の判定では、前文の `return` により `source` が非ゼロで打ち切られ `_asc_cli` が未定義のまま残ることを経て、driver の非ゼロ exit code をもって「非ゼロ終了」と判定する。併せて、アダプタを `source` するだけでは自動導入コマンドが一度も実行されないことを表明する。

8. **自動導入の既定を「試行する」とし、無効化は環境変数 `AGENT_SKILL_CHAIN_AUTO_INSTALL` の値が厳密に `0` の場合に限る。** 未設定・空文字列・`false`・`no` その他の任意の値はすべて既定（試行する）として扱い、警告もエラーも出さない。非対話環境では確認を求めずに試行し、対話環境（標準入力と標準エラー出力の双方が端末に接続されている場合）では試行前に確認を求める。確認を拒否された場合は自動導入コマンドを実行せず、拒否を理由として明示した日本語エラーで非ゼロ終了する。「確認も自動導入も行わずに即座に失敗する」経路は持たない。

9. **第3経路の採用条件に「ファイル単位検査」と「起動可能性検証」の双方を常時課し、相互排他は導入しない。** 第3経路（PATH上の実体）は、`command -v` で発見できただけでは採用しない。「実体が存在し、実行可能で、サイズが0でない」というファイル単位検査に加え、当該実体を `--help` で1回起動して exit code 0 を確認する起動可能性検証を、自動導入の有無にかかわらずすべての解決で行う。いずれかに不合格の場合は当該経路を採用せず「未解決」として扱い、オプトアウト判定・自動導入分岐へ進む。起動可能性検証を自動導入直後の1回に限定する案は採らない。限定すると、他プロセスがグローバル導入を進行中で「実体は配置済みだが依存パッケージが未配置」という状態を、自ら自動導入を行わないプロセスが第3経路で拾った場合に検出できず、委譲先CLI自身のエラーによる終了——本決定が定める2挙動のいずれでもない終了形——が生じるためである。代償として、第1・第2経路の実体がいずれも存在せず第3経路が採用される構成では、ラッパー1回の起動につき `--help` のプロセス生成が1つ増える。実行時間は本Issueのいずれの受入条件にも拘束されない一方、並行実行時の2挙動への収束は受入条件であるため、正しさを優先する。

10. **配布用CIワークフローテンプレートの「Ensure agent-skill-chain CLI」ステップも同じ共有実装を読み込む形へ統一する。** これにより、リポジトリ全体で3経路解決を記述する箇所は共有実装1つだけになる。ワークフローはリポジトリを checkout した状態で当該ステップを実行するため、共有実装は当該時点で必ず利用可能である。

11. **重複の再導入を機械的に検出する不変条件を定める。** `.agent-skill-chain/` 配下の `*.sh` 全件を走査し、(a) 3つの literal（`bin/agents-md.js`・`node_modules/.bin/agent-skill-chain`・`command -v agent-skill-chain`）が連続12行の窓に同居するファイルの集合が `{共有実装}` の部分集合であること、(b) literal `node_modules/.bin/agent-skill-chain` を含むファイルがちょうど1件で、それが共有実装であること、(c) 共有実装が3つの literal をすべて含むこと（行間距離は問わない）、をいずれも自動テストで表明する。(a) を「ちょうど1件」ではなく部分集合とするのは、窓幅12という定数を共有実装の記述スタイルへ結合させないためである。共有実装の第3経路判定は Decision 9 の2検査を含むため3 literal 間の距離が12行を超えうるが、その場合でも重複が存在しない正しい実装が誤って不合格になってはならない。共有実装が3経路解決を保持し続けていることは、窓幅に依存しない (b)(c) が担保する。コメント行の除外という前処理は行わない（前処理自体が「どこからがコメントか」の解釈を持ち込み、判定を再び実装依存にするため）。

12. **前文の同一性と契約割当も機械的に表明する。** 対象54本からマーカーコメント間の前文ブロックを抽出し、行頭空白の除去と `return`→`exit` の正規化の後に全件が文字単位で一致することを自動テストで表明する。併せて、正規化前に `exit` 形であるファイルがちょうど52件、`return` 形がちょうど2件であり、後者が `adapters/claude.sh`・`同 human.sh` に一致することも表明する。全数の起動を検証するテストだけでは、前文が個別に書き換えられていても偶然すべて動作する限り検出できず、Decision 5 が置く同一性の不変条件が無検証のまま残るためである。

13. **第3経路の起動可能性検証が前提とする「健全なCLI実体は `--help` に対し exit code 0 を返す」を、実CLIに対する回帰表明で守る。** 本決定の時点で実CLIの入口実装は、引数が空・`-h`・`--help` のいずれかであれば使用方法を標準出力へ書いて 0 を返す。この前提が破れると、グローバル導入のみで運用する構成で第3経路が恒久的に採用されず、自動導入が成功しても毎回「再解決不能」で非ゼロ終了する。テスト用スタブは `--help` に必ず exit code 0 を返すため、スタブのみを用いる自動テストでは前提の破綻を検出できない。したがって実CLI実体に対して `--help` を実行し exit code が 0 であることを表明する回帰テストを設ける。前提を意図的に変える場合は、起動可能性検証の判定条件を同じ変更で設計し直すことを要求する。

14. **委譲の記述形は3種を認め、既存の関数境界を保つ。** 対象54本の内訳は、末尾 `exec` で1回だけ委譲する薄いラッパー49本（契約W）、`_cli` 関数を保持し同一プロセス内でCLIを複数回呼ぶスクリプト3本（契約W。`scripts/worker-launch.sh`・`同 worker-launch-verify.sh`・`同 gate-launch-reviewer.sh`）、`_asc_cli` 関数を保持するアダプタ2本（契約A）である。後者2種では関数を廃止せず、本体だけを `"${ASC_CLI[@]}" "$@"` の実行へ置き換える。当該5本は関数の戻り値で分岐する記述を複数持ち、関数を廃止すると呼び出し側の記述を広範に書き換えることになるためである。契約Wの3本については、CLIが解決できない場合の失敗が「最初の関数呼び出し時点」から「起動時点」へ早まる挙動変化を受け入れる。いずれも日本語エラー＋非ゼロ終了であり、CLIが解決できる場合の引数透過・標準出力・exit code は変わらない。

15. **契約Aの呼び出し元は `source` の戻り値を明示的に検査する。** `set -e` の有無に依存してはならない。本リポジトリ内で唯一アダプタを `source` するスクリプトは `-e` を含まない設定で動作しており、検査が無ければ、共有実装を解決できない状態でも処理が継続して後続の関数呼び出しが「コマンドが見つからない」というシェル既定のエラーで終わる（日本語メッセージも探索パスも伴わない）。本決定に伴う変更には、当該呼び出し元への戻り値検査の追加を含める。

## Consequences

- **利点**: CLI解決に関する今後の変更（フォールバック方式の変更、経路の追加、メッセージの改善）が1ファイルの修正で54本とCIワークフローへ同時に反映される。本Issueの発生原因である横展開漏れが構造的に発生しなくなる。CIとローカルの挙動乖離が解消され、CLI未導入の consumer でもローカル実行が自動導入を経て続行する。ラッパー1本あたりの記述量が減り、新しいラッパーの追加時に3経路解決を書き写す必要がなくなる。
- **欠点・受け入れたリスク**: 共有実装1ファイルが単一障害点になる。緩和は3層（54本全数の起動を毎回検証する自動テスト、本リポジトリ自身のCIが `ci/` 配下12本を実際に実行すること、共有実装が壊れても無言終了ではなく探索パス付きの日本語エラーで停止する定型前文の3段検査）で行うが、リスクを0にはできない。
- **並行導入への帰結**: 第3経路の採用条件に起動可能性検証を常時含めるため（Decision 9）、bin エントリの実体は配置済みだが依存パッケージが未配置という中間状態も、自ら自動導入を行わないプロセスが第3経路で拾った場合を含めて検出され、当該経路は採用されない。したがって並行導入下でも各プロセスは「解決したCLI実体へ委譲する」か「日本語エラーで非ゼロ終了する」かのいずれかへ収束し、部分配置状態の実体で委譲先サブコマンドが実行されることはない。相互排他を導入しない代わりに支払うのは、第3経路が採用される構成での `--help` 起動1回分のコストであり、未検出の中間状態ではない。ただし、採用判定の直後から `exec` による委譲までの極小時間に他プロセスが実体を破壊する事象までは、いかなる事前検査でも排除できない。これは並行導入固有ではなくあらゆる委譲に共通する時間差であり、本決定が禁じる「部分配置状態の実体を採用して委譲する」（採用時点の状態に対する規定）には該当しない。
- **2契約に分けたことの帰結**: 対象54本は単一の契約では扱われず、契約W（直接実行52本）と契約A（`source` される2本）が並存する。ラッパーを新設する者は、その呼び出し形態に応じてどちらの契約に従うかを選ぶ必要がある。可変部分は前文の終了形（`exit`／`return`）と解決呼び出しの位置だけであり、共有実装のパス算出と3段検査は両契約で同一テキストである。契約の割当（52件と2件、および `return` 形の割当先）は自動テストが表明するため、誤った契約でラッパーを追加すると検出される。
- **`source` 時の副作用の不在**: アダプタは `source` されただけではCLI解決も自動導入も行わない。解決と自動導入は `_asc_cli` が呼ばれた時点で初めて起こる。したがってアダプタの関数群のうちCLIを必要としないものだけを使う呼び出し元は、グローバルnpm環境の変更を誘発しない。代償として、`_asc_cli` が1プロセス内で複数回呼ばれる場合は解決手続きが呼び出しごとに走る（公開契約が結果をキャッシュしないため）。同一プロセス内で環境が変化した場合に古い結果を返さないための意図的な選択であり、収束先の挙動（委譲成功か日本語エラー＋非ゼロか）は呼び出し回数によらず同一である。
- **既知の限界（自動導入の版指定）**: 自動導入は `@latest` を使うため、consumer が導入済みのテンプレート版とグローバル導入されるCLI版が乖離しうる。乖離時の期待挙動は本決定では定義しない（既存のCIワークフローの挙動と同一であり、本決定の前後で変化しない）。版整合ポリシーはCI側の挙動も同時に変える別論点であり、必要なら別の決定として扱う。
- **利用者から見た新しい観測可能な副作用**: CLI未導入の環境でラッパーを実行すると、グローバルnpm環境が変更されうる。対話環境では確認を挟み、非対話環境では `AGENT_SKILL_CHAIN_AUTO_INSTALL=0` で事前に無効化できる。この挙動と無効化手段は共有実装のヘッダコメントと README に記載する。
- **フォローアップ事項**: `.agent-skill-chain/hooks/` 配下および `adapters/codex.sh` は3経路解決のコード片を保持しないため本決定の対象外である。将来これらがCLIを解決する必要が生じた場合は、インラインで書き起こさず共有実装を利用する。

## accepted 後の不変項目・可変項目

| 区分 | 項目 |
|---|---|
| 不変（accepted 後は変更不可） | `id`、Context、Decision、Consequences、`supersedes` |
| 可変（ライフサイクル遷移に伴い更新可） | `status`、`superseded-by`、`deprecated-reason`、`tags` |

本文（Context / Decision / Consequences）の変更が必要になった場合は、新しい ADR を作成し `supersedes` / `superseded-by` で旧 ADR との関係を記録する。既存 ADR の本文を書き換えてはならない。
