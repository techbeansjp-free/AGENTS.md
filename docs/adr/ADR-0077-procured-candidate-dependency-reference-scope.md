## Context

ローカルゲートレビューの準備段は、protected default branch の base SHA を checkout した隔離 clone を作り、隔離 clone の外にある配布パッケージの実体を検証して隔離 clone 配下へ複製し、その実体でレビュアを起動して verdict を証跡へ記録する。この隔離は「verdict を記録する実行コードが審査対象（target SHA の Issue worktree）のコードではないこと」を担保する仕組みである。

調達する実体の由来は 2 つの手段で担保していた。第一に、候補の実体パスが本リポジトリの linked worktree のうち protected base worktree 以外の配下にある場合、当該候補を採用しない。第二に、候補の内容から算出した正準ツリー digest が、base SHA のコミット内容に含まれる導入マーカーの期待値と一致する場合にのみ採用する。

しかしこの 2 つを通過しても、実行時に読み込まれるコードが審査対象由来になる経路が残る。正準ツリー digest はパッケージ root 配下の通常ファイルを対象とし、依存モジュールのディレクトリ配下を対象から除く。したがって、候補パッケージ root 直下の依存ディレクトリ、または候補と同じ親の依存ディレクトリへ、依存と同名の参照経路（symbolic link）を置いて審査対象の Issue worktree 配下の実体へ向けても、候補の digest は変わらない。候補の実体パス自体は linked worktree の外にあるため第一の判定も通過する。調達後、依存には実体を複製せず参照経路のみを与えるため、この参照経路がそのまま実行時の module 解決に使われ、審査対象が用意した実体が prompt 生成・verdict 記録を行うプロセス内で読み込まれる。すなわち、実行コードの実体だけを照合する設計では、審査対象からの分離という目的が達成されない。

検討したトレードオフは次のとおりである。

- 候補の実体パスだけを照合し、依存は照合しない案（変更前の状態）: 実装は最小だが、上記の反例により目的が破れる。採らない。
- 依存閉包を再帰的に解決して全て照合する案: 束縛は強くなるが、閉包の大きさと形は導入経路ごとに変わり、走査コストと、任意のパッケージが正当に持つ参照経路による停止が実行のたびに増える。審査対象以外から供給される依存閉包の供給網の完全性は別の脅威モデルであり、Issue #772 が扱う。本決定は境界を移さない。
- 依存の実体を隔離 clone 配下へ複製する案: 依存の配置と版が導入経路ごとに変わるため期待値が環境ごとに一致せず、ADR-0072 が正準ツリー digest の対象範囲を定めた際に排した問題へ戻る。採らない。
- 正準ツリー digest の対象範囲へ依存ディレクトリ配下を含める案: 同じ理由で期待値が環境ごとに一致しなくなる。加えて、候補の内容が同一でも依存の配置差だけで完全性検証が失敗する。採らない。
- 参照経路を作る直前にだけ照合する案: 除外の判断が採用後になるため、「候補全体として採用も実行もしない」という要求を満たせない。採らない。
- 実行時に読み込まれた依存の実体パスを観測し、審査対象配下なら実行を中止する案: 観測が判定の入力になるため、観測が無効・失敗した実行では排除も働かない。安全側ラチェット（不変条件 I8）に反する。採らない。

## Decision

1. **調達候補は、次の 2 つのパス条件をいずれも満たす場合にのみ採用する。** 第一に、候補の実体パスが本リポジトリの linked worktree のうち protected base worktree 以外の配下にないこと。第二に、候補が依存を解決する供給元に置かれた参照経路を全て解決した後の実体パスが、いずれも当該 linked worktree の配下にないこと。いずれかを満たさない候補は候補全体として採用せず実行もしない。

2. **第二の条件の照合対象は、供給元 2 か所とその直下エントリに限る。** 供給元は、候補パッケージ root 直下の依存ディレクトリと、候補パッケージ root の親が依存ディレクトリである場合の当該親ディレクトリである。この 2 か所それぞれについて、ディレクトリ自身とその直下の全エントリを対象とし、名前がスコープ名（`@` で始まる）のエントリはその直下の各エントリを対象とする。第一の条件で照合済みの候補パッケージ自身は重ねて数えない。

3. **解決先の照合はそこから先の依存閉包へ再帰しない。** 複製先パッケージ root を基点とする実行時の module 解決が最初に到達する依存ディレクトリは決定 2 の 2 か所だけであり、審査対象配下の実体を依存として解決させる参照経路はこの 2 か所にしか置けないためである。

4. **参照経路は途中のディレクトリを含めて全て解決し、実体パスまで到達させる。** 解決できない場合（リンク切れ・権限不足・循環）は候補を除外する。解決できない参照先について審査対象の配下でないことを示せないためである。

5. **linked worktree 配下か否かの判定は、候補の実体パスに用いるものと同一の 1 つの判定とする。** 候補用と依存用に判定を分けない。分けると片方だけが更新されて食い違い、その食い違いが検出されないためである。

6. **2 条件の判定は候補の採用前、正準ツリー digest の算出より前に行う。** 除外した候補には複製も参照経路の付与も行わない。

7. **参照経路を付与する対象集合は、決定 2 の照合対象と同一の列挙規則で決める。** さらに付与の直前に同じ照合を再度行い、条件を満たさないものが 1 つでもあれば付与せず非0終了する。採用の判定と付与の間に参照先が差し替えられた場合に安全側へ倒すためである。

8. **除外により採用候補が残らない場合は、除外した候補の識別子、どちらの条件で除外したか、検査した参照経路、解決後の実体パス（解決できなかった場合はその旨）、該当した linked worktree のパスを含む日本語メッセージを出して非0終了する。** どこを検査して何が該当したかを示さない診断は、無言の劣化と同じく原因の特定を実行者へ委ねるため採らない。

9. **実行時に解決された依存の実体パスを観測できる出力点を CLI 側へ置く。** 環境変数が与えられたときに限り有効とし、未設定時は何も出力せず解決の順序・結果・失敗時の挙動を変えない。観測結果は判定の入力にしない。排除の責務は決定 1 の除外規則が持ち、観測点は結果を実行時の値として外から確認できるようにするだけである。

## Consequences

- 利点: 候補の内容（正準ツリー digest）を変えずに依存の参照先だけを審査対象へ向ける経路が、採用前に閉じる。実行コードの実体を検証しても依存が未検証なら目的が破れる、という穴のうち、審査対象からの分離に当たる部分が塞がる。
- 利点: 判定を 1 つに統一したため、候補と依存で linked worktree の判定が食い違わない。
- 利点: 照合対象の列挙規則と参照経路を付与する対象集合が同一であるため、照合を経ないまま到達可能な依存が残らない。
- 利点: 除外理由が診断へ出るため、consumer の実行環境で候補が採用されない場合に原因を特定できる。
- 欠点: 候補ごとに供給元 2 か所の直下エントリ数に比例した参照経路の解決が増える。候補が採用されるまでの処理時間が導入形態に応じて延びる。
- 欠点: 依存の供給元にリンク切れのエントリを持つ実行環境では、審査対象と無関係であっても候補が除外され、ローカルゲートが実行できない。安全側だが、正当な実行環境が止まりうる。
- 欠点: 決定 3 により、解決先のパッケージが更に読み込む依存（依存閉包の 2 段目以降）は本決定の照合対象に含まれない。
- フォローアップ: 審査対象以外から供給される依存閉包の供給網の完全性（由来・完全性の積極的な検証と証跡への記録）は Issue #772 の射程とする。本決定は審査対象からの分離だけを扱い、当該 Issue が扱う境界を先取りしない。
