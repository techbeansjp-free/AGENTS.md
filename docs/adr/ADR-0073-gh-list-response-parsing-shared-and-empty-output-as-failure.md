## Context

ゲートは GitHub の一覧 API を `gh api` で取得する。全ページ取得に用いている `--slurp` は gh 2.63.0 で追加されたオプションであり、それより古い gh は未知フラグとして非 0 終了で拒否する。LTS ディストリビューションの標準パッケージがこれより古い gh を配る場合があり、配布先の gh バージョンは制御できない。実測では gh 2.45.0 が該当し、`--slurp` を含む起動は標準エラー出力へ `unknown flag: --slurp` を出して失敗する。

`--slurp` を外すと、gh の標準出力は取得先によって形が変わる。配列応答は `--paginate` のみで全ページを平坦化した単一の JSON 配列として得られるが、オブジェクト応答は空白区切りで連結された複数の JSON 文書として得られ、単一文書としては解釈できない。`--slurp` を与えた場合はいずれも各ページを要素とする配列になる。したがって解釈側は 3 つの出力形を扱う必要がある。

現行実装では、この解釈が 12 箇所の呼び出し側に個別に書かれている。配列を一段平坦化するもの、先頭要素が配列かどうかで分岐するもの、ページ属性を取り出すもの、呼び出し側で直接 `JSON.parse` するものが混在し、失敗時の扱いも停止・空集合・偽値と揃っていない。

加えて、一覧応答の標準出力が空（0 バイト）または空白のみである場合の扱いが定義されていない。これを要素 0 件として扱う設計と、解釈失敗として扱う設計の 2 案がある。前者は実装が単純だが、gh が出力を produce できないまま終了コード 0 を返した場合と、一覧が実際に空である場合を区別できなくなる。本 Issue が除去しようとしている症状は、まさに取得失敗が空の結果と区別できないまま正常終了することである。

なお gh の最低バージョンを検査して満たさなければ起動時に停止する案は、`SPEC.md` で不採用としている。古い gh の環境でゲートを一律に利用不能にするためである。

## Decision

1. gh の一覧応答の解釈を単一の共有モジュールへ集約する。呼び出し側は gh の標準出力を直接 `JSON.parse` しない。
2. 共有パーサは、単一の JSON 文書、空白区切りで連結された複数の JSON 文書、各ページを要素とする配列の 3 形を受理する。
3. 単一の JSON 文書として解釈できる標準出力は、その解釈結果を用いる。文書境界を求める走査は、単一文書として解釈できない場合にのみ行う。
4. 標準出力に JSON 文書が 1 つも存在しない場合（0 バイト、または空白文字のみ）は解釈失敗とする。要素 0 件として扱わない。要素 0 件は JSON 文書が実在しその内容が空である場合にのみ成立する。
5. 共有パーサは解釈失敗時に専用の例外を送出するのみとし、空集合・既定値へ自らフォールバックしない。失敗をどう提示するかは呼び出し側が決める。
6. 共有パーサは gh の起動を行わず、実行系にも cli 層にも依存しない純関数として置く。

## Consequences

- 3 つの出力形の判別が 1 箇所に集まるため、`--slurp` の有無による差が呼び出し側から消える。`--slurp` を持つ gh と持たない gh のどちらでも同じ要素集合が得られ、gh のバージョン差が挙動差として表面化しなくなる。
- 決定 3 により、`--slurp` を用いていた従来の出力形は変更前と同じ解釈経路を通る。新たに導入する走査の影響は、単一文書として解釈できない出力に限定される。
- 決定 4 により、取得結果が空であることは「空の JSON 文書が返ってきた」という積極的な証拠を要求するようになる。空出力は失敗として呼び出し側へ伝わり、失敗が空の結果と区別できないまま正常終了する経路が塞がれる。現行実装も空文字列に対して例外を投げるため、この決定は既存の安全側挙動を明文化するものであり、挙動を後退させない。
- 決定 5 により、失敗時に何をするかは呼び出し側の責務として残る。既存の 3 種の写像（停止、理由付きの取得不能、検証不成立）はそのまま維持でき、共有化によって失敗時の強さが一律に弱まることはない。一方で、新しい呼び出し側を追加する際には失敗の提示を毎回決める必要がある。これは意図した負担であり、既定で空集合へ倒れる設計に比べて無言の劣化を作りにくい。
- 決定 6 により、共有パーサは文字列を入力とする純関数となり、gh を起動せずに 3 形すべてを自動検証できる。実行環境の gh を差し替える必要がなくなる。
- 連結文書の分割を自前で行うため、文字列リテラル内の括弧を誤って数えると文書境界がずれ、要素の欠落や重複を生む。レビュー本文には括弧を含む文字列が頻繁に現れるため、走査は文字列リテラルとエスケープを認識する必要がある。この誤りが生む影響は共有化によって 1 箇所へ集約され、そこを検証すれば全経路が担保される。
- gh が将来 `--paginate` の出力形を変更した場合、影響範囲は共有モジュールに限定される。追随は 1 箇所の変更で済む。
