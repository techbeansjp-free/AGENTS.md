## Context

worktree 削除コマンド（`agent-skill-chain cleanup <issue_id>`）は、削除前に「未pushのcommitが無い」ことを検査する。この検査の目的は、worktree を削除しても復元できない作業——ローカル限定 commit——を巻き添えで失わせないことである。ローカル限定 commit とは、その変更内容が実 remote 上のいずれの ref からも到達できず、かつ統合先ブランチにも取り込まれていない commit を指す。

当初の実装は、Issue ブランチ先端の commit SHA・祖先関係・tree 一致のいずれかが統合先ブランチとの間で成立することを保全の根拠にしていた。squash merge は複数 commit を統合先上の1つの新しい commit へ置き換えるため SHA も祖先関係も保存されず、統合先が分岐後に前進していれば tree も一致しない。その結果、作業が完全に保全されているにもかかわらず削除が拒否される誤検知が発生した。

この誤検知を解消する過程で、保全の根拠として採用しうる情報源が複数存在することが分かった。実 remote への問い合わせが返す head、ローカルの remote-tracking ref とその reflog、Coordination Backend が保持する位置（GitHub の完了済み PR の head SHA、ローカルモードの Integration Record が記録する SHA）、および commit が触れた path の内容が統合先の現在内容と一致するという事実である。これらは強度が異なり、無差別に採用すると逆方向の欠陥——保全されていない commit を保全済みと誤判定し、削除で作業を失う——を生む。実際に、最終差分が空になる構成、統合済み path を変更して直後に取り消す構成、pathspec magic と同名のファイルを追加する構成、未 push の位置が記録された Record を用いる構成という複数の反例が、実装中に順次発見された。

誤検知（保全済みなのに拒否する）と取りこぼし（未保全なのに削除する）は等価ではない。前者は運用上の不便であり利用者が理由を読んで対処できるが、後者は復元不能な作業消失である。したがって根拠ごとに採否の条件を定め、条件を満たさない場合は保全済みと判定しないという規則が必要になった。根拠の採否を実装の都度の判断に委ねると、反例が見つかるたびに規則が場当たり的に緩められ、同じクラスの欠陥が再発する。

## Decision

保全判定の根拠を、次の規則で採否する。

1. **到達可能性を主根拠とする。** ある commit が、統合先ブランチ、実 remote の head、または記録済み push 位置のいずれかから到達可能であれば保全済みとする。記録済み push 位置とは、実 remote 上のいずれかの ref から到達可能であることが確認済み、または確認済みであったと Git 上の証跡で裏付けられる commit SHA である。判定の単位はブランチ全体ではなく、分岐点からブランチ先端までの commit 1件ずつとする。

2. **内容一致は一方向の補助根拠に限る。** commit が触れた path の内容が統合先の現在内容と一致する場合に限り保全済みと確定させ、一致しない場合は何も確定させない（他の根拠が無ければ未保全側へ倒れる）。適用は記録済み push 位置が1つ以上存在する場合に限る。push 実績が皆無の状態で内容一致だけを根拠にすると、push 済みで統合されたものと、一度も push されておらず内容がたまたま一致するものを区別できないためである。比較に用いる path は commit 由来の信頼できない文字列であるため、pathspec の特殊構文として解釈される経路を残さない。

3. **Coordination Backend 由来の位置は裏付けを経てから採用する。** ローカルモードの Integration Record が記録する SHA は、現在も到達元集合から到達可能であるか、統合完了を記録した時点の確認結果を固定する検証 ref がその SHA を指している場合にのみ採用する。記録された位置を無検証で採用すると、記録時点で push も統合もされていない位置を起点に「自分は自分の祖先である」という自己参照が成立し、ローカル限定 commit を保全済みと誤判定する。GitHub の完了済み PR の head SHA は、GitHub が PR ごとに remote 上へ保持する PR head ref が指す SHA であり、head ブランチの ref が削除された後もこの ref は残るため、追加の裏付けを求めずに採用する。

4. **reflog 由来の過去 push 位置は採用しない。** remote-tracking ref の reflog に残る push 記録は、現在の実 remote head の祖先であれば判定力を追加せず、祖先でなければ force-push により捨てられ現在の remote 上のどの ref からも到達できない位置である。追加の判定力を持つ唯一の場面が同時に唯一の危険な場面であるため、根拠として採らない。

5. **根拠の不足は拒否条件ではない。** 特定の根拠を得られないことは、判定への入力が1つ減ることとしてのみ扱い、独立した削除拒否の理由に昇格させない。拒否は「ローカル限定 commit が確定的に存在する」か「保全済みかを確定できない」のいずれかに限る。後者の場合は確定できなかった事由を日本語で出力する。

6. **確定できない場合は常に削除を拒否する。** 判定に必要な情報を取得できない状態を保全済みとして扱わない。

## Consequences

- 利点: 根拠の強度に応じた採否条件が明文化され、反例が見つかるたびに規則を場当たり的に緩める余地が無くなる。判定単位を commit ごとにしたことで、ブランチ全体の差分では消えてしまう中間の変更（追加後に取り消した path など）を取りこぼさない。誤りの方向は常に削除拒否側であり、作業消失を伴わない。
- 欠点: 実 remote への問い合わせが失敗するオフライン環境では判定不能となり、統合済み worktree の削除が一時的にできない。また、記録済み push 位置より後に作られ、同一 path を複数 commit で更新した中間 commit は、内容一致では保全済みにできず削除が拒否される。中間状態そのものは統合先に存在しないため、これは保全済みの定義に照らして正しい帰結である。
- フォローアップ: ローカルモードの検証 ref はローカルの ref のみを拠り所とするため、remote へ push 済みであることを復元元とする耐久性より弱い保証にとどまる。この保証の強化方式は本決定の対象外とし、別 Issue で検討する。
- 影響範囲: 未push判定を共有する他用途（期限切れ writer lease の回収可否判定、lease 再取得時の残作業判定）は、Coordination Backend 由来の位置を受け取らない呼び出しのまま据え置く。これらの用途では保全済みの worktree も未保全側として扱われるが、いずれの経路も lease・worktree・commit を削除せず人間判断へ昇格するのみであるため、作業消失は生じない。
