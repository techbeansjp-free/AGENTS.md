## Context

4セグメント（spec・design・implementation・validation）の作業ワーカーを起動する実行系アダプタは、設定の正本にある単一のスカラー値でしか指定できず、セグメントごとに変えられなかった。加えて、codex アダプタが使うモデル名と reasoning effort はアダプタ内のフォールバック値を環境変数で上書きする経路しか持たず、環境変数はセッション限りで消えるため、プロジェクトの恒久的な既定値として記録できなかった。

この状態を解消するにあたり、次の判断が必要だった。

第一に、モデルをどう指定するか。設定に具体的なモデル文字列を書けば単純だが、モデル世代が変わるたびに設定ファイル・スキーマ・導入済みの各プロジェクトを追随させる必要が生じる。一方、抽象名（ティア）で設定を書けば、追随は具体名を保持する側の更新だけで済む。

第二に、その具体名をどこに保持するか。本リポジトリには既に、コア独立レビュー用の codex モデル文字列と reasoning effort が登録済みプロジェクトポリシー（`.agent-skill-chain/project/manifest.yaml` の `model_selection.core_review`）として宣言されており、`src/lib/model-selection.ts` の読み取り関数がスキーマ検証を伴って読み出している。さらに `.agent-skill-chain/schemas/project-policy.schema.yaml` は同じ値を `const` として固定し、`src/lib/model-selection.ts` の型と `src/lib/bootstrap-ledger.ts` の実行時検証も同じ値を固定している。これらの固定は単なる重複ではなく、コア監査レビュアのモデルが無断で差し替えられていないことを検証するための機構であり、attestation 用の環境変数と対になっている。ワーカー用に同じ文字列を別のファイル（たとえばアダプタの bash 側）へ書き写せば、モデル世代更新時の更新箇所がさらに1つ増え、片方だけ古い値が残る不整合が起こり得る。

第三に、ティア語彙をどう扱うか。既存のコア独立レビュー契約は `frontier_coding`（モデル能力の要求水準）と `maximum_reasoning`（推論強度の要求水準）というティア語彙を持つ。ただしこれらは要求水準の宣言であり、照合される期待値として使われる。ここで注意が必要なのは、claude アダプタがティアから具体モデル名を導く対応表を持っているわけではない点である。claude アダプタは、渡されたティア名が期待値と一致するかを検証し、具体モデル名は別の環境変数から受け取るだけであり、ティアから具体名を解決する対応表は本リポジトリのどのアダプタにも存在しない。つまりティア語彙は既にあるが、ティアから具体名を解決する仕組みは本決定が初めて導入する。

第四に、恒久設定を更新する操作をどうするか。設定ファイルの直接編集と、設定を書き換える専用コマンドの新設という2案がある。ここでは「進行役が読み書きするのは調整状態のみであり、成果物の著述・内容の取り込みを行わない」という不変条件と、「調整状態は Coordination Backend のプリミティブにのみ存在する」という不変条件の両方を侵さないことが制約になる。設定ファイルは Git 管理下の正本アセットであって調整状態ではない。

第五に、設定スキーマの版数をどう扱うか。項目追加の手続きはスキーマ更新を必須とするが、「スキーマ定義の更新」と「スキーマ版数の引き上げ」は同義ではない。版数は設定ファイル側の値と一致必須であるため、引き上げれば導入済みのすべての設定ファイルが即座に不正となる。

第六に、解決結果をワーカー起動ラッパーからアダプタへどう渡すか。既存の経路は、起動ラッパーが CLI から解決結果を受け取り、アダプタを選び、環境変数を介して実行系固有の値を渡す形になっている。codex アダプタには既にテスト用の完全上書き環境変数と、モデル・reasoning effort の個別上書き環境変数があり、これらの優先順位を壊さないことが要求される。

## Decision

セグメントごとの上書きを設定の正本へ `worker.segment_overrides.<segment>` として追加し、値は `adapter`・`model_tier`・`reasoning_effort` の3つの任意項目に限定する。既存のスカラー指定は「セグメント別上書きが無いセグメントの既定アダプタ」として維持し、未設定時の最終フォールバックは従来どおり `human` とする。

モデルはティア抽象化で指定する。設定ファイルと設定スキーマには具体的なモデル文字列を置かない。ティア `highest_capability` の具体モデルは、登録済みプロジェクトポリシーのコア独立レビュー契約が宣言する codex モデルを唯一の出所として解決する。解決は既存の読み取り関数を読み取り専用で再利用して行い、コア独立レビューの契約・スキーマの固定値・attestation 検証・トリガー・レビュア選定には一切手を加えない。これにより、具体モデル文字列の出現箇所は本決定によって増えず、モデル世代の更新はプロジェクトポリシーの宣言値の更新で完結する（同じ値を固定している attestation 機構の固定値は、無断の差し替えを検出するために意図的に多重化されたものであり、モデル世代更新時に同一変更で更新されるべきものとして残す）。

ティア解決の責務はアダプタに置く。codex アダプタは、ティア名から具体モデル文字列を得る単一の解決定義を持ち、その定義は値を自前で保持せず、読み取り専用の CLI サブコマンド `worker model-for-tier` の出力を用いる。起動ラッパーと `worker context` はティア名をそのまま扱い、具体モデル文字列を扱わない。これにより、モデル文字列が現れる実行経路は codex アダプタの1経路に限定され、起動ラッパーと解決結果出力はベンダー中立に保たれる。

ティア語彙は既存の `frontier_coding` を再利用せず、`highest_capability` を用いる。`frontier_coding` はスキーマで `const` に固定された attestation 機構の語彙であり、同じ名前を設定側の「選択の指示」へ流用すると、照合される期待値と解決される選択値が同名になり、検証側と選択側の区別が名前から付かなくなる。語彙は2つ並立するが、指す具体モデルは同一の宣言から解決されるため値は分岐しない。ティア語彙自体の統合はコア独立レビューの契約表現に影響するため本決定の範囲外とする。

解決不能な場合は推測しない。未知のティア名、プロジェクトポリシーの不在、codex 用モデルの未宣言、CLI 呼び出しの失敗はいずれも、既定モデルへ暗黙に倒さず、writer lease 取得後の blocked 報告・lease 解放・0 でも 3 でもない終了コードという既存のフェイルセーフ経路へ倒す。

恒久設定の更新は、設定ファイルの直接編集で行う。設定を書き換える CLI サブコマンドは新設しない（本決定が追加するのは読み取り専用の解決サブコマンドのみである）。実行主体は writer lease を保持するセグメント作業ワーカーであり、タイミングは当該変更を扱う Issue の実装セグメントである。進行役は設定ファイルを編集しない。進行役の関与は、対話で受けた指示内容を Issue へ記録し、通常どおりワーカーを起動することに限る。設定ファイルは調整状態ではなく Git 管理下の正本アセットであるため、進行役による直接編集は「成果物ブランチへの commit をしない」「成果物を著述しない」という不変条件に抵触する。書き換えコマンドを設ければ、CLI を実行できる進行役がその境界を越えられてしまい、統制が運用依存になる点も採らない理由である。

設定スキーマの版数は `agent-skill-chain/config/v1` のまま据え置く。追加はすべて任意項目であり、旧形式の設定は無変更で妥当かつ同一挙動を保つ。版数を引き上げるのは、必須項目の追加・許容値の削除・既存項目の意味変更といった破壊的変更に限る。したがって migration は不要（no-op）であり、変換処理は追加しない。既定値は「セグメント別上書き無し」であり、その場合の解決結果は従来と同一である。

解決結果の伝達は、`worker context` にセグメントを任意引数として受け取らせ、解決した `adapter`・`model_tier`・`reasoning_effort` を `KEY=VALUE` 形式で返す形とする。未解決のキーは行そのものを出力しない。セグメントを渡さない従来の呼び出しは従来どおりの3行を返し、無変更で動作する。起動ラッパーは解決できた値だけを、ベンダー中立な `ASC_WORKER_MODEL_TIER` および `ASC_WORKER_REASONING_EFFORT` として export する。既存のワーカー・レビュア起動が使う環境変数と同じ名前空間に揃え、アダプタ固有の上書き変数とは名前空間を分ける。

codex アダプタにおけるモデルおよび reasoning effort の決定順序は、(1) 起動コマンド全体を差し替える上書き、(2) アダプタ固有の個別上書き、(3) 設定由来のティア・reasoning effort、(4) 従来のフォールバック値、とする。テスト用の完全上書きが最優先であるという既存規則を維持し、ティア指定が無い場合の結果は本決定の適用前と一致させる。

## Consequences

モデル世代の更新に対する追従コストが、ワーカー用途については宣言データ1箇所へ集約される。設定ファイルと設定スキーマは具体的なモデル名を持たないため、モデル名の変更が導入済みプロジェクトの設定書き換えを要求しない。一方で「1箇所に集約された」と言えるのはワーカー用のティア解決経路に限る。リポジトリ全体では、コア独立レビューの attestation 機構が同じ値をスキーマの `const`・型・実行時検証へ意図的に固定しており、これは無断の差し替えを検出する目的の機構であるため集約できない。本決定はその箇所を増やさないことをもって重複の抑制を果たす。

ワーカー用途がコア独立レビューの宣言を読み取ることで、両者は同じ値に結び付く。読み取りは一方向であり、コア独立レビュー側が新設側へ依存することはない。ただし、将来「コア監査に使うモデル」と「実装ワーカーに使う最高能力モデル」が別物になる要件が生じた場合は、プロジェクトポリシーへワーカー用の宣言を独立に設ける変更が必要になる。その時点までは、両者が同一であるという前提が成立している。

ティア語彙は `frontier_coding` 系と `highest_capability` の2つが並立する。前者は要求水準の照合、後者は選択の指示という役割の違いがあるが、初見の読者には重複に見える。役割の違いは規範文書と設計成果物で説明するに留まり、機械的に区別を強制する仕組みは設けない。

既存の設定ファイルは無変更で従来どおり動作し、移行作業は発生しない。許容するティア名・reasoning effort の値はスキーマの enum に列挙されるため、値を増やすときはスキーマの変更が必要になる。これは変更がレビューを通ることを意味し、意図しない値の混入を防ぐ側の効果として受け入れる。

`model_tier` や `reasoning_effort` を解釈しないアダプタと組み合わせた設定は、スキーマの条件制約により設定エラーとして拒否される。指定が黙って無視される状態を作らない代わりに、将来 claude 側がティアを解釈するようになった時点で制約の緩和が必要になる（緩和は後方互換な変更である）。

恒久設定の更新を設定ファイルの直接編集に限定したため、更新は必ず Issue・ブランチ・PR・ゲートという既存の統制を通る。即時性は下がるが、恒久的な方針変更が証跡なく入る経路を作らない。進行役は設定ファイルを編集できないため、対話で受けた指示は Issue への記録とワーカー起動という形でのみ反映される。

設定ファイルはパッケージへ同梱され、導入時に複製される。さらに更新コマンドは `.agent-skill-chain/` 配下の正本アセット（設定を含む）を衝突検知なしの無条件上書きで同期し、不可侵なのはプロジェクトポリシーと展開済みの GitHub 資産だけである。したがって本リポジトリ自身の運用上の選択（実装セグメントを codex・`highest_capability`・`high` にすること）は新規導入プロジェクトの初期値となり、導入先が当該上書きをローカルで削除しても次回の更新コマンド実行で必ず復活する。設定ファイルに対する恒久的なオプトアウト手段は現時点で存在しない。codex CLI を導入していない、またはティアの参照先を宣言していない導入先では、更新のたびに実装セグメントが blocked（人間確認が必要な停止）へ倒れ続ける。

これは意図された挙動である。実装セグメントを最高能力の実行系で走らせることを全体既定として強制するという所有者の明示的判断に基づく。「既定は常に安全側」という原則との緊張関係は認識している——導入先の環境で成立しない既定値を配ることは、導入先にとって安全な既定とは言えない。それでもこの判断を採る根拠は3点ある。第一に、失敗の現れ方が誤った成果物ではなく停止であり、危険側へ黙って倒れないという安全側ラチェットの主眼は保たれる。第二に、更新コマンドは人間が明示的に実行する操作であり、実行によって正本アセットが同期されることは既に規範文書が述べている。第三に、導入先には、更新の影響を受けないプロジェクトポリシーの層で自プロジェクトのティア参照先を宣言するという恒久的な手段がある。

配布既定値と本リポジトリ自身の運用設定を分離すること、および更新コマンドが設定ファイルのローカル変更を保護する方式（マージ・不可侵化・オプトアウト表現の導入）は、いずれも本決定の範囲外のフォローアップ事項として残る。
