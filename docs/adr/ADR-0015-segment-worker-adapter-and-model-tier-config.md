## Context

4セグメント（spec・design・implementation・validation）の作業ワーカーを起動する実行系アダプタは、設定の正本にある単一のスカラー値でしか指定できず、セグメントごとに変えられなかった。加えて、codex アダプタが使うモデル名と reasoning effort はアダプタ実装内のフォールバック値を環境変数で上書きする経路しか持たず、環境変数はセッション限りで消えるため、プロジェクトの恒久的な既定値として記録できなかった。

この状態を解消するにあたり、次の判断が必要だった。

第一に、モデルをどう指定するか。セグメント別の設定に具体的なモデル文字列を直接書けば単純だが、モデル世代が変わるたびに全セグメント分の記述を追随させる必要が生じる。抽象名（ティア）で書けば、追随は対応表の値の更新だけで済む。

第二に、その具体名をどこに保持するか。候補は3つあった。(a) アダプタのソース（bash）に書く、(b) 本リポジトリに既存のコア独立レビュー用モデル宣言（登録済みプロジェクトポリシー）を再利用する、(c) 設定ファイル自身に構造化データとして持つ。ここで、既存のコア独立レビュー用宣言について事実を確認する必要がある。当該宣言のモデル文字列と reasoning effort は、プロジェクトポリシーのスキーマで定数として固定されている。これはコア監査レビュアのモデルが無断で差し替えられていないことを検証する attestation 機構であり、導入先が自分の都合でこの値を変える余地は無い。さらに、モデル世代が変わる場合はこの宣言だけでなく、スキーマの固定値・関連する型・コア監査証跡の実行時検証も同時に更新しなければ動作が壊れる。したがって (b) は「1箇所の更新で追従できる」という前提が成立せず、加えてワーカーのモデル解決をコア監査の分類・判定経路と結合させる副作用を生む。(a) は具体的なモデル文字列をコードへ埋め込むことになり、値の更新にコード変更とリリースを要する。

第三に、ティア語彙をどう扱うか。既存のコア独立レビュー契約は `frontier_coding`（モデル能力の要求水準）と `maximum_reasoning`（推論強度の要求水準）というティア語彙を持つ。ただしこれらは要求水準の宣言であり、照合される期待値として使われる。ここで注意が必要なのは、claude アダプタがティアから具体モデル名を導く対応表を持っているわけではない点である。claude アダプタは、渡されたティア名が期待値と一致するかを検証し、具体モデル名は別の環境変数から受け取るだけであり、ティアから具体名を解決する対応表は本リポジトリのどのアダプタにも存在しない。つまりティア語彙は既にあるが、ティアから具体名を解決する仕組みは本決定が初めて導入する。

第四に、恒久設定を更新する操作をどうするか。設定ファイルの直接編集と、設定を書き換える専用コマンドの新設という2案がある。ここでは「進行役が読み書きするのは調整状態のみであり、成果物の著述・内容の取り込みを行わない」という不変条件と、「調整状態は Coordination Backend のプリミティブにのみ存在する」という不変条件の両方を侵さないことが制約になる。設定ファイルは Git 管理下の正本アセットであって調整状態ではない。

第五に、設定スキーマの版数をどう扱うか。項目追加の手続きはスキーマ更新を必須とするが、「スキーマ定義の更新」と「スキーマ版数の引き上げ」は同義ではない。版数は設定ファイル側の値と一致必須であるため、引き上げれば導入済みのすべての設定ファイルが即座に不正となる。

第六に、解決結果をワーカー起動ラッパーからアダプタへどう渡すか。既存の経路は、起動ラッパーが CLI から解決結果を受け取り、アダプタを選び、環境変数を介して実行系固有の値を渡す形になっている。codex アダプタには既にテスト用の完全上書き環境変数と、モデル・reasoning effort の個別上書き環境変数があり、これらの優先順位を壊さないことが要求される。

## Decision

セグメントごとの上書きを設定の正本へ `worker.segment_overrides.<segment>` として追加し、値は `adapter`・`model_tier`・`reasoning_effort` の3つの任意項目に限定する。既存のスカラー指定は「セグメント別上書きが無いセグメントの既定アダプタ」として維持し、未設定時の最終フォールバックは従来どおり `human` とする。

具体的なモデル文字列は、同じ設定ファイルに新設するティア対応表 `worker.model_tiers` に保持する。構造はティア名をキーとし、その値は実行系アダプタ名をキーとする具体的なモデル文字列の集合とする。これが具体的なモデル文字列を保持する唯一の場所であり、セグメント別上書き・設定スキーマ・起動ラッパー・アダプタのソースには置かない。設定スキーマはモデル値を定数ではなく通常の文字列として検証する。これにより、モデル世代の更新は対応表のエントリの値を書き換えるだけで完結し、スキーマ・CLI・起動ラッパー・アダプタのコード変更を要さない。

コア独立レビュー用のモデル宣言と attestation 機構は再利用しない。参照も変更もしない。結果として同一のモデル文字列がリポジトリ内に2系統で独立して存在するが、これは意図的である。ワーカー用は「起動時に選ぶモデルの指示」であって利用者が変更してよい値であり、attestation 用は「レビュアのモデルが差し替えられていないことの照合値」であって変更されたら検出されなければならない値である。両者を1つの宣言へ相乗りさせると、モデル選択を変えるためにセキュリティ機構の固定値を触ることになり、さらにワーカーのモデル解決がコア監査の分類・判定経路と結合してしまう。

ティア解決は CLI 側で完結させる。`worker context` が設定を読み、ティア対応表を引いて具体的なモデル文字列まで解決し、`KEY=VALUE` 形式で返す。起動ラッパーとアダプタはティア名から具体名を導く処理を持たない。アダプタは解決済みの値を環境変数から受け取り、そのまま codex CLI 起動コマンドへ反映する。

ティア語彙は既存の `frontier_coding` を再利用せず、`highest_capability` を用いる。`frontier_coding` はスキーマで固定された attestation 機構の語彙であり、同じ名前を設定側の「選択の指示」へ流用すると、照合される期待値と解決される選択値が同名になり、検証側と選択側の区別が名前から付かなくなる。語彙は2つ並立し、値は独立に保持される。ティア語彙自体の統合はコア独立レビューの契約表現に影響するため本決定の範囲外とする。

解決に失敗した場合は推測しない。ティア対応表に該当エントリが無い、当該アダプタ用のモデルが無いといった場合は、`worker context` が日本語の理由付きで失敗する。この失敗は writer lease 取得前に起こるため、起動ラッパーは既存の「まだ何も起動していない段階の error（0 でも 3 でもない終了コード）」として返す。報告のためだけに lease を取得することはしない。未知のティア名は設定スキーマの列挙により設定ファイルの段階で拒否される。加えてアダプタ側に防御的検査を置き、ティアが指定されているのに解決済みモデルが届いていない場合は従来フォールバックへ黙って落ちず、既存の blocked フェイルセーフ経路へ倒す。

恒久設定の更新は、設定ファイルの直接編集で行う。設定を書き換える CLI サブコマンドは新設しない。実行主体は writer lease を保持するセグメント作業ワーカーであり、タイミングは当該変更を扱う Issue の実装セグメントである。進行役は設定ファイルを編集しない。進行役の関与は、対話で受けた指示内容を Issue へ記録し、通常どおりワーカーを起動することに限る。設定ファイルは調整状態ではなく Git 管理下の正本アセットであるため、進行役による直接編集は「成果物ブランチへの commit をしない」「成果物を著述しない」という不変条件に抵触する。書き換えコマンドを設ければ、CLI を実行できる進行役がその境界を越えられてしまい、統制が運用依存になる点も採らない理由である。

設定スキーマの版数は `agent-skill-chain/config/v1` のまま据え置く。追加はすべて任意項目であり、旧形式の設定は無変更で妥当かつ同一挙動を保つ。版数を引き上げるのは、必須項目の追加・許容値の削除・既存項目の意味変更といった破壊的変更に限る。したがって migration は不要（no-op）であり、変換処理は追加しない。既定値は「セグメント別上書き無し・ティア対応表無し」であり、その場合の解決結果は従来と同一である。

解決結果の伝達は、`worker context` にセグメントを任意引数として受け取らせ、`adapter`・`model_tier`・`model`・`reasoning_effort` を返す形とする。未解決のキーは行そのものを出力しない。セグメントを渡さない従来の呼び出しは従来どおりの3行を返し、無変更で動作する。起動ラッパーは解決できた値だけを、ベンダー中立な `ASC_WORKER_MODEL`・`ASC_WORKER_REASONING_EFFORT`・`ASC_WORKER_MODEL_TIER` として export する。既存のワーカー・レビュア起動が使う環境変数と同じ名前空間に揃え、アダプタ固有の上書き変数とは名前空間を分ける。アダプタ固有変数を起動ラッパーが直接設定する案は、起動ラッパーがベンダー固有の変数名を知る必要が生じること、および明示的な上書きと設定由来の値が同じ変数に混ざって優先順位を機械的に区別できなくなることから採らない。

codex アダプタにおけるモデルおよび reasoning effort の決定順序は、(1) 起動コマンド全体を差し替える上書き、(2) アダプタ固有の個別上書き、(3) 設定由来の解決済み値、(4) 従来のフォールバック値、とする。テスト用の完全上書きが最優先であるという既存規則を維持し、ティア指定が無い場合の結果は本決定の適用前と一致させる。

## Consequences

モデル世代の更新に対する追従は、ワーカー用途については設定ファイルのティア対応表1箇所の値の変更で完結する。スキーマがモデル値を定数として固定しないため、値を変えてもスキーマ変更は生じない。設定ファイル自体が配布物であるため、更新は導入先へもそのまま行き渡る。

同一のモデル文字列がリポジトリ内に2系統（ワーカー用のティア対応表と、コア独立レビュー用の attestation 機構）で独立して存在する。モデル世代が変わる場合、両系統をそれぞれ更新することになる。ワーカー用は設定値1箇所、attestation 用は当該機構が定める複数箇所である（固定値の性質上まとめられない）。この重複は上記の理由により意図的に受け入れる。本決定は attestation 用の箇所を増やしも減らしもせず、読み取りもしないため、コア監査の判定経路に副作用を持ち込まない。

ティア語彙は `frontier_coding` 系と `highest_capability` の2つが並立し、現時点では同じモデルを指す。値は独立に保持されるため、片方の更新が他方へ自動的には波及しない。役割の違い（要求水準の照合と、選択の指示）は規範文書と設計成果物で説明するに留め、機械的に区別を強制する仕組みは設けない。

既存の設定ファイルは無変更で従来どおり動作し、移行作業は発生しない。許容するティア名・アダプタ名・reasoning effort の値はスキーマの列挙に載るため、これらを増やすときはスキーマの変更が必要になる。モデル文字列の変更とは異なりレビューを通ることになるが、語彙の追加は本来レビューされるべき変更であるため受け入れる。

`model_tier` や `reasoning_effort` を解釈しないアダプタと組み合わせた設定は、スキーマの条件制約により設定エラーとして拒否される。指定が黙って無視される状態を作らない代わりに、将来 claude 側がティアを解釈するようになった時点で制約の緩和が必要になる（緩和は後方互換な変更である）。

恒久設定の更新を設定ファイルの直接編集に限定したため、更新は必ず Issue・ブランチ・PR・ゲートという既存の統制を通る。即時性は下がるが、恒久的な方針変更が証跡なく入る経路を作らない。進行役は設定ファイルを編集できないため、対話で受けた指示は Issue への記録とワーカー起動という形でのみ反映される。

設定ファイルはパッケージへ同梱され、導入時に複製される。さらに更新コマンドは `.agent-skill-chain/` 配下の正本アセット（設定を含む）を衝突検知なしの無条件上書きで同期し、不可侵なのはプロジェクトポリシーと展開済みの GitHub 資産だけである。したがって本リポジトリ自身の運用上の選択（実装セグメントを codex・`highest_capability`・`high` にすること）とティア対応表の内容は新規導入プロジェクトの初期値となり、導入先がこれをローカルで削除・変更しても次回の更新コマンド実行で必ず配布時の内容へ戻る。設定ファイルに対する恒久的なオプトアウト手段は現時点で存在しない。codex CLI を導入していない導入先では、更新のたびに実装セグメントが blocked（人間確認が必要な停止）へ倒れ続ける。

これは意図された挙動である。実装セグメントを最高能力の実行系で走らせることを全体既定として強制するという所有者の明示的判断に基づく。「既定は常に安全側」という原則との緊張関係は認識している——導入先の環境で成立しない既定値を配ることは、導入先にとって安全な既定とは言えない。それでもこの判断を採る根拠は2点である。第一に、失敗の現れ方が誤った成果物ではなく停止であり、危険側へ黙って倒れないという安全側ラチェットの主眼は保たれる。第二に、更新コマンドは人間が明示的に実行する操作であり、実行によって正本アセットが同期されることは既に規範文書が述べている。導入先が恒久的にオプトアウトする手段は無い。

配布既定値と本リポジトリ自身の運用設定を分離すること、および更新コマンドが設定ファイルのローカル変更を保護する方式（マージ・不可侵化・オプトアウト表現の導入）は、いずれも本決定の範囲外のフォローアップ事項として残る。
