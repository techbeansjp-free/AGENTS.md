## Context

4セグメント（spec・design・implementation・validation）の作業ワーカーを起動する実行系アダプタは、設定の正本にある単一のスカラー値でしか指定できず、セグメントごとに変えられなかった。加えて、codex アダプタが使うモデル名と reasoning effort はアダプタ内のフォールバック値を環境変数で上書きする経路しか持たず、環境変数はセッション限りで消えるため、プロジェクトの恒久的な既定値として記録できなかった。

この状態を解消するにあたり、4つの判断が必要だった。

第一に、モデルをどう指定するか。設定に具体的なモデル文字列（例: `gpt-5.6-sol`）を書けば単純だが、モデル世代が変わるたびに設定ファイル・スキーマ・導入済みの各プロジェクトを追随させる必要が生じる。一方、抽象名（ティア）で書けば、追随はアダプタ内の対応表1箇所の更新で済む。既に claude アダプタは、モデルと推論強度をティア名で表して具体名を実行系側に閉じ込める方式を採っている。

第二に、恒久設定を更新する操作をどうするか。設定ファイルの直接編集と、専用の CLI サブコマンドの新設という2案がある。ここでは「進行役が読み書きするのは調整状態のみであり、成果物の著述・内容の取り込みを行わない」という不変条件と、「調整状態は Coordination Backend のプリミティブにのみ存在する」という不変条件の両方を侵さないことが制約になる。設定ファイルは Git 管理下の正本アセットであって調整状態ではない。

第三に、設定スキーマの版数をどう扱うか。項目追加の手続きはスキーマ更新を必須とするが、「スキーマ定義の更新」と「スキーマ版数の引き上げ」は同義ではない。版数は設定ファイル側の値と一致必須であるため、引き上げれば導入済みのすべての設定ファイルが即座に不正となる。

第四に、解決結果をワーカー起動ラッパーからアダプタへどう渡すか。既存の経路は、起動ラッパーが CLI から解決結果を受け取り、アダプタを選び、環境変数を介して実行系固有の値を渡す形になっている。codex アダプタには既にテスト用の完全上書き環境変数と、モデル・reasoning effort の個別上書き環境変数があり、これらの優先順位を壊さないことが要求される。

## Decision

セグメントごとの上書きを設定の正本へ `worker.segment_overrides.<segment>` として追加し、値は `adapter`・`model_tier`・`reasoning_effort` の3つの任意項目に限定する。既存のスカラー指定は「セグメント別上書きが無いセグメントの既定アダプタ」として維持し、未設定時の最終フォールバックは従来どおり `human` とする。

モデルはティア抽象化で指定する。設定とスキーマには具体的なモデル文字列を一切置かず、ティア名から具体モデル文字列への対応は codex アダプタ内の単一のマッピング定義だけが持つ。本決定で定義するティアは `highest_capability`（初期値の対応先は `gpt-5.6-sol`）のみとする。より高性能なモデルへの追従は、このマッピングの値の更新だけで完結させ、設定・スキーマ・CLI・起動ラッパーの変更を要求しない。未知のティア名が渡された場合は既定値へ推測で倒さず、writer lease 取得後の blocked 報告・lease 解放・0 でも 3 でもない終了コードという既存のフェイルセーフ経路へ倒す。

恒久設定の更新は、設定ファイルの直接編集で行う。設定を書き換える専用の CLI サブコマンドは新設しない。実行主体は writer lease を保持するセグメント作業ワーカーであり、タイミングは当該変更を扱う Issue の実装セグメントである。進行役は設定ファイルを編集しない。進行役の関与は、対話で受けた指示内容を Issue へ記録し、通常どおりワーカーを起動することに限る。設定ファイルは調整状態ではなく Git 管理下の正本アセットであるため、進行役による直接編集は「成果物ブランチへの commit をしない」「成果物を著述しない」という不変条件に抵触する。書き換えコマンドを設ければ、CLI を実行できる進行役がその境界を越えられてしまい、統制が運用依存になる点も採らない理由である。

設定スキーマの版数は `agent-skill-chain/config/v1` のまま据え置く。追加はすべて任意項目であり、旧形式の設定は無変更で妥当かつ同一挙動を保つ。版数を引き上げるのは、必須項目の追加・許容値の削除・既存項目の意味変更といった破壊的変更に限る。したがって migration は不要（no-op）であり、変換処理は追加しない。既定値は「セグメント別上書き無し」であり、その場合の解決結果は従来と同一である。

解決結果の伝達は、`worker context` にセグメントを任意引数として受け取らせ、解決した `adapter`・`model_tier`・`reasoning_effort` を `KEY=VALUE` 形式で返す形とする。未解決のキーは行そのものを出力しない。セグメントを渡さない従来の呼び出しは従来どおりの3行を返し、無変更で動作する。起動ラッパーは解決できた値だけを、ベンダー中立な `ASC_WORKER_MODEL_TIER` および `ASC_WORKER_REASONING_EFFORT` として export する。既存のワーカー・レビュア起動が使う環境変数と同じ名前空間に揃え、アダプタ固有の上書き変数とは名前空間を分ける。

codex アダプタにおけるモデルおよび reasoning effort の決定順序は、(1) 起動コマンド全体を差し替える上書き、(2) アダプタ固有の個別上書き、(3) 設定由来のティア・reasoning effort、(4) 従来のフォールバック値、とする。テスト用の完全上書きが最優先であるという既存規則を維持し、ティア指定が無い場合の結果は本決定の適用前と一致させる。

## Consequences

モデル世代の更新に対する追従コストがアダプタ内の1箇所へ集約される。設定ファイルとスキーマは具体的なモデル名を持たないため、モデル名の変更が導入済みプロジェクトの設定書き換えを要求しない。

既存の設定ファイルは無変更で従来どおり動作し、移行作業は発生しない。一方で、許容するティア名・reasoning effort の値はスキーマの enum に列挙されるため、値を増やすときはスキーマの変更が必要になる。これは変更がレビューを通ることを意味し、意図しない値の混入を防ぐ側の効果として受け入れる。

`model_tier` や `reasoning_effort` を解釈しないアダプタと組み合わせた設定は、スキーマの条件制約により設定エラーとして拒否される。指定が黙って無視される状態を作らない代わりに、将来 claude 側がティアを解釈するようになった時点で制約の緩和が必要になる（緩和は後方互換な変更である）。

恒久設定の更新を設定ファイルの直接編集に限定したため、更新は必ず Issue・ブランチ・PR・ゲートという既存の統制を通る。即時性は下がるが、恒久的な方針変更が証跡なく入る経路を作らない。進行役は設定ファイルを編集できないため、対話で受けた指示は Issue への記録とワーカー起動という形でのみ反映される。

設定ファイルはパッケージへ同梱され、導入時に複製され、更新時にはミラー更新される。したがって本リポジトリ自身の運用上の選択（実装セグメントを codex・`highest_capability`・`high` にすること）は、新規導入プロジェクトの初期値となり、既存導入プロジェクトの設定も更新時に同じ内容へ揃えられる。codex CLI を持たない導入先では実装セグメントが blocked へ倒れる（誤った結果ではなく停止として現れ、当該上書きの削除または `adapter` の変更で復旧できる）。配布既定値と本リポジトリ自身の運用設定を分離すべきかどうかは本決定の範囲外であり、別 Issue として扱うフォローアップ事項として残る。
