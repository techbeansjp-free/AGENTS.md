## Context

ゲートレビュアは呼び出し元の資格情報を持ち込まない隔離サブプロセスとして起動する。隔離サブプロセスへ
与える環境は `env -i` で構成した固定の基底集合であり、設定ディレクトリは隔離領域内の制御されたパスへ
向けられる。Claude Code CLI が認証を成立させられる認証情報の所在は、環境変数（分類A）、設定ディレクトリ
配下の通常ファイル（分類B）、外部資格情報ストア限定（分類C。macOS Keychain 等）の3分類に限られる。
分類Aと分類Bは隔離領域へ持ち込めるため既に成立しているが、分類Cは資格情報ストアが呼び出し元の
ログインセッションに紐づくため隔離サブプロセスからは参照できず、ゲートレビューが常に人間判断へ倒れる。

同種の不具合は3度繰り返されている。過去2回の修正はいずれも、継続的インテグレーション環境で表現できた
構成のみを回帰テストの対象とし、分類Cを対象集合へ入れなかった。したがって本決定では、分類Cの成立自体に
加えて、模倣に依存する部分と実機でしか確認できない部分の境界を明示することが要件になる。

分類Cを成立させる手段として検討した選択肢とトレードオフは次のとおり。

- 呼び出し元の `HOME` や利用者識別情報を隔離サブプロセスへ渡す案: CLI の設定探索先が呼び出し元の実設定
  ディレクトリとなり、呼び出し元由来の設定・hooks・外部サーバ定義・権限設定がゲートレビュアへ適用され
  得る。レビュアの独立性と read-only 性を損ない、隔離方針そのものの変更にあたるため採らない。
- 認証情報を用意できないときに設定ディレクトリの指定自体を外す案: 指定を外すと CLI の探索先が呼び出し元
  ホーム配下へ後退し、上と同じ露出が生じる。指定先に認証情報が無いことと指定そのものが有害であることは
  別であり、指定先へ資格情報を配置すれば成立することは分類Bが同一経路で実証している。
- 取得結果をシェル変数へ取り込んでから書き出す案: 変数への代入はシェルのトレース出力に値がそのまま
  現れる。またコマンド引数として渡す実装はプロセス起動列へ値を露出させる。いずれも資格情報の実値を
  環境変数・プロセス起動列・診断・ログへ出さないという要件と両立しない。
- 取得結果を一時ファイルへ落としてから移送する案、およびパイプ経由で分岐させる案: 隔離領域外の一時
  ファイルは新たな残存経路になる。分岐は呼び出し元へ届く標準出力・標準エラーへ実値を流す経路を作り得る。
- 時間上限を外部の時間上限コマンドへ委ねる案: 当該コマンドは主要な分類C環境である macOS に既定で存在
  しない。存在時のみ上限を課す従来の書き方は、継続的インテグレーション環境と実機で異なる経路を走らせる
  ことになり、過去2回の失敗と同じ構図を再生産する。
- 取得の可否をもって認証の成否を判定する案: 認証の判定点が隔離環境の認証確認と取得可否の2つに分かれ、
  取得できた資格情報が実サービスで無効な場合の扱いが両者で食い違う。
- 取得した資格情報を1回のゲートレビュア起動内で再利用（キャッシュ）する案: 隔離サブプロセスは1回の起動で
  2回構成され、各回が独立した隔離領域を持つ。再利用のためには隔離領域の外へ資格情報を置く必要があり、
  新たな残存経路を作る。

加えて、資格情報ストアが返す値の全体構造・末尾の付随出力・対話的承認要求の有無は、macOS と設定済みの
資格情報ストアを備えたホストでしか確認できない。これらを確定した前提として実装へ埋め込むと、前提が
外れた場合に沈黙して誤った結果へ倒れる危険がある。

## Decision

claude アダプタのゲートレビュア起動経路について次を決定する。

1. 分類Cの資格情報の取得は呼び出し元プロセス上で行い、取得コマンドの標準出力をシェルのリダイレクトで
   隔離設定ディレクトリの認証ファイルのみへ接続する。取得結果を保持する変数・コマンド引数・隔離設定
   ディレクトリ外のファイル・分岐を伴うパイプ中継を設けない。取得コマンドの標準エラーは破棄する。
2. 取得の時間上限は本アダプタ内の監視プロセスで強制する。外部の時間上限コマンドの有無で経路を分けない。
3. 取得は分類Aと分類Bのいずれからも認証素材を用意できなかった場合に限り行う。取得の結末は
   未実施・取得手段なし・時間上限超過・取得失敗・形式不適合・配置済みの6状態として記録する。
4. 取得直後の検査は値を出力しない構造検査に限る。認証の成否の判定点は隔離環境の認証確認1つとし、
   取得の可否を判定点にしない。
5. 取得コマンドと取得の時間上限は呼び出し元環境の変数で上書き可能とし、上書き値を隔離サブプロセスの
   環境変数として渡さない。
6. 取得した資格情報を隔離領域の外へ複製・保存・再利用しない。
7. 自動テストが模倣する前提を識別子付きで列挙した対応表と、分類C経路を変更する Issue に対する実機確認の
   実施時期・実行者・記録先の規約を、配布対象の標準文書へ置く。

## Consequences

- 資格情報の実値が通る経路は取得コマンドの標準出力から隔離設定ディレクトリの認証ファイルまでの1本だけに
  なる。シェルのトレースを有効にしても値は現れず、プロセス起動列・環境変数・診断・ログのいずれにも
  実値が入り得ない。実値非露出の検証は、この1経路以外に実値が現れないことの確認へ単純化される。
- 取得コマンドの標準エラーを破棄するため、資格情報ストア側の失敗理由は呼び出し元へ伝わらない。原因の
  切り分けは、取得結果状態に基づくアダプタ自身の診断（取得手段なし・時間上限超過・取得失敗・形式不適合・
  取得できたが認証確認が不成立）に依存する。
- 時間上限を自前で強制するため、継続的インテグレーション環境と実機が同じ経路を走る。対話的承認を要求する
  環境では上限で打ち切られ、待ち続ける状態にはならない。一方で監視処理の実装量は増える。
- 分類Aの環境変数トークンが設定されているが実サービスで無効な場合、資格情報ストアへは問い合わせない。
  この構成は隔離環境の認証確認で不成立となり診断へ倒れる。利用者は診断を見て環境変数を外す必要がある。
- 資格情報ストアの取得は1回のゲートレビュア起動につき2回行われる。承認を毎回求める設定の環境では
  承認要求も2回生じる。
- 資格情報ストアが返す値の形式が前提と異なる場合、構造検査または隔離環境の認証確認で不成立となり、
  誤った成功へは倒れない。前提そのものの確定は実機確認の記録に委ねられ、確定するまで分類Cの成立は
  自動テストだけでは保証されない。
- 主要な分類C環境以外（既定の取得手段を持たないホスト）では取得手段なしと解決され、分類Cは従来どおり
  成立しない。別の資格情報ストアへの対応は上書き変数による運用か、後続の決定を要する。
- 模倣前提の対応表と実機確認の規約を配布対象の標準文書へ置くため、消費側リポジトリにも同じ規約が配布
  される。Issue 単位の成果物は Issue 完了後に既定ブランチ直下へ残らないため、規約の所在としては
  Issue 単位の成果物より持続的である。
