## Context

ゲートレビュアにはツール呼び出しが一切許可されておらず、判定プロンプトへ文字列として展開された内容
だけを検証できる。ところが判定プロンプトは、gate_id によらず上流成果物として要求仕様の成果物だけを
展開し、憲法文書を一切展開せず、成果物が事実主張の根拠として名指しするリポジトリ内ファイルも展開して
いなかった。この結果、実物を確認できないことを理由にレビュアが判定を保留し安全側ラチェットにより
人間判断へ倒れる事象と、比較対象が無いため反例探索そのものが空振りし、実在した設計と実装の乖離が
指摘ゼロで通過する事象が、同時に発生していた。いずれも成果物側の欠陥ではなく入力側の欠落に起因する。

検討した選択肢とトレードオフは次のとおり。

- 成果物側へ実物の原文引用を義務づける案: 運用として既に適用済みだが、引用の忠実性と網羅性そのものが
  検証できないため保留を解消しない。原文引用を追加した後もレビュアが反証を完了できなかった実例がある。
- 事実主張の検証を後段セグメントへ委譲する案: 比較対象が無いまま承認を導出することを追認する。承認済み
  の決定と実装が矛盾したまま通過した実例があり、追跡可能性の実効的な破れを固定化する。
- レビュアへ read-only のファイル読み取りを与える案: 隔離条件と証跡の再現性の再設計を伴い、変更の範囲が
  レビュア権限モデル全体へ広がる。
- 実行時にレビュアの必要に応じて展開対象を増減させる案: 同一入力に対する生成物が揺れ、証跡照合の前提で
  ある生成の決定性を失う。

展開対象を増やすと入力量が増える。受け渡しは argv を経由しないため引数長上限は制約にならないが、
レビュアモデルの文脈長は制約になり、超過は入力の末尾側が読まれないという無言の形で現れうる。この
無言の劣化こそが本決定が解こうとしている欠陥そのものであるため、量の扱いを決めずに展開対象だけを
増やすことはできない。量の上限に達したとき、必要な入力の省略と黙った末尾落ちは判定材料を欠かせる。
全文と超過通知を出して成功させる案も、モデルが末尾まで読める保証にならず、本決定の目的と両立しない。

## Decision

1. 判定プロンプトへ展開する入力は gate_id ごとの固定表で定め、実行時の裁量で増減させない。
2. 固定表の列は 2 種類とする。展開対象列（判定対象成果物・上流の承認済み成果物・憲法文書）は展開する
   パスを直接列挙し、抽出元列は展開対象を列挙せず根拠ファイルを導出するための入力を指定する。
3. 根拠ファイルは、抽出元列が指定する成果物の本文と target SHA のツリーのみから導出する。導出は 1 段に
   限り、根拠ファイル本文・憲法文書本文・差分本文からの再導出を行わない。
4. 展開は固定順序（判定対象成果物、上流の承認済み成果物、憲法文書、根拠ファイル）の順序付きリストとして
   構築し、同一パスは最初に現れた位置で 1 回だけ展開する。
5. 完成した判定プロンプト全体の UTF-8 バイト長に単一の上限を設け、固定の指示区間・見出し・フェンス・両一覧・
   展開された全内容を残らず算入する。対象外の区間を設けないのは、内容バイトだけを数えて一覧を対象外に置くと、
   多数の小さな根拠ファイルを名指しする target SHA で一覧が件数に比例して増大し、内容バイトが上限内のまま
   プロンプト全体が文脈長を超えるためである。
6. 上限の正本は設定項目 `review.prompt_max_input_bytes` とし、その値を target SHA の設定ファイル blob から
   解決する。作業ツリーの設定も導入済みパッケージ側の設定も読まない。blob もキーも無い場合の既定値は
   1500000 バイトとし、観測されている最大の生成物である ISSUE-733 implementation の完全レンダー
   1042451 バイト（現行生成物 839397 バイトと本決定が追加する必須入力 203054 バイトの和）を上回らせる。
7. 判定対象の差分と展開対象列を必須入力とし、一覧の予約とあわせて予算による省略の対象にしない。必須区間の
   レンダー長と全候補分の一覧予約長の和が上限を超える場合は、切り捨ても省略もせず生成を非 0 終了で失敗させる。
   根拠ファイルの予算は上限からこの和を引いた残余とし、走査順の先着適合で展開する。非テキストの根拠ファイル、
   および予算に収まらない根拠ファイルは全文を展開せず、走査は打ち切らない。
8. 展開対象列と根拠ファイルの全展開パスを含む展開済み一覧、省略した根拠ファイルの一覧（パス・バイト長・
   内容 digest・省略理由）、および適用した上限・必須区間のレンダー長・一覧の予約長・予算を本文へ出力し、
   ハルシネーション防止の指示は両一覧を判別手段として参照する。
9. 判定プロンプトの生成経路を 1 つに保ち、標準出力へ出す生成物とレビュー証跡照合が用いる期待値を同一の
   実体から得る。

## Consequences

- レビュアは、判定対象・照合基準・成果物が根拠として名指しした入力を同一プロンプト内で参照できる。
  実物が無いことだけを理由とした保留と、比較対象の不在による反例探索の空振りが、いずれも解消する。
- 入力集合が固定表と 1 段の導出規則で決まり、上限値も target SHA から解決されるため、同一の target SHA に
  対する生成物は未コミットの作業ツリー変更や実行環境によって揺れない。証跡照合が前提とする決定性を保てる。
- 量の上限に達した場合の帰結が、無言の劣化から明示的な失敗へ変わる。既定値は観測済みの最大ゲートの完全
  レンダーを上回るため、同規模の既存ゲートを失敗側へ変えない。超過時の対処は対象 Issue の分割、または設定値の
  引き上げだが、値を target SHA から解決する以上、commit して新しい target SHA で再実行するまで効かない。
- 根拠ファイルの導出に部分文字列一致を用いるため、短いパスが散文中に偶然現れると過剰に抽出される。
  過剰分は予算により展開量が抑えられ、省略一覧へ記録されるため無言の劣化にはならない。
- 判定プロンプトの内容が変わるためプロンプト digest が変わり、既存の golden fixture は再生成を要する。
  過去に記録済みのレビュー証跡の再検証は本決定の対象に含めない。
- フォローアップとして、上限の既定値の妥当性は実運用の生成サイズを観測して見直す。見直しは設定値の
  変更で完結する。
