## Context

ローカルゲートレビューの準備段は、protected default branch の base SHA を checkout した隔離 clone を作り、その中で無条件に依存導入と build を行ってから、隔離 clone 内の実行コードでレビュアを起動し verdict を証跡へ記録する。この隔離は「verdict を記録する実行コードが審査対象のコードではなく保護された base のコードであること」を担保する仕組みである。

しかし build は実行対象リポジトリの build script が定義する任意の処理であり、agent-skill-chain の CLI 生成とは無関係でありうる。配布先（consumer project）には agent-skill-chain 本体のソースもビルド定義も配布されないため、consumer の隔離 clone で走る build は consumer 自身の build であり、CLI を生成しない。実測では、build が非0終了する Node 構成と、`package.json` を持たない非 Node 構成の双方で、レビュア起動段へ到達できないことが確認されている。すなわち配布先では 4 ゲートすべてがローカルで実行できない。

準備段を通しても、証跡へ記録する launcher digest の算出対象に配布集合外の project policy 文書が含まれており、consumer では全件取得に失敗して証跡投稿が成立しない。したがって「準備段のビルド前提」と「launcher digest の算出対象」は同じ Issue で扱う必要がある。

一方、隔離 clone に CLI 実体が無い状態で外部の実体を使えば、実行コードの由来が未検証のまま verdict を記録でき、隔離の目的そのものが破れる。配置先が隔離 clone 配下であることは由来の検証にならない。したがって、外部から持ち込む実行コードには由来と完全性の検証が要る。検証には「審査対象が変更しうる情報源に依存しない期待値」が必要であり、その供給元をどこに置くかが本決定の中心である。

検討したトレードオフは次のとおりである。

- 隔離 clone を廃して審査対象の作業ツリーのコードをそのまま実行する案: 準備段の問題は消えるが、進行役の純粋性（不変条件 I5）と証跡の意味を同時に失う。採らない。
- consumer でも build を試み、失敗したら続行する案: 失敗を握り潰すため、build 生成物の有無が実行の可否と無関係になり、何が実行されたかが実行環境によって変わる。安全側ラチェット（不変条件 I8）に反する。採らない。
- CLI の実行コードを配布集合へ加え、隔離 clone 内に常に存在する状態にする案: 調達が不要になり検証も要らなくなる。しかし配布集合はソースを持たない consumer へ配る asset の集合であり、ビルド生成物を全 consumer のリポジトリへ commit させることになる。版の追随・差分の肥大・生成物と資産の混在という恒久的な負債を配布先へ課すため採らない。
- 期待値を調達元パッケージ自身が同梱する値から取る案: 改変された実体は自身の期待値も同時に書き換えられるため、検証として成立しない。採らない。
- 期待値をレジストリ等ネットワーク上の情報源から取る案: ゲートの実行可否がネットワーク到達性に依存し、かつ base SHA との対応を持たない。採らない。
- 期待値を配布集合の内側のファイルへ置く案: 配布集合は全 consumer へ同一内容が配られる集合であり、consumer ごとに異なる「導入時に実際に用いた配布物」の digest を持てない。加えて、配布集合に属し隔離 clone から読まれる asset は launcher digest の算出対象へ含める要求（本 Issue の要件6 が定める下限）が生じ、当該要素を含まない過去の base SHA に対する算出が停止して既存 PR の証跡投稿と過去反復の再検証が一斉に止まる。採らない。
- 調達した CLI の依存モジュールも隔離 clone 配下へ複製し、その閉包まで期待値で束縛する案: 束縛は強くなるが、依存の実体は導入経路（グローバル導入・プロジェクト依存・一時実行キャッシュ）ごとに配置と版が変わり、同一版の CLI でも期待値が一致しない環境が生じる。実行時に解決される依存閉包の束縛は Issue #772 が別途扱うため、本決定では境界を移さない。

## Decision

1. **信頼実行環境の調達方式を 2 つの調達モードに分ける。** 隔離 clone に agent-skill-chain 自身のソースとビルド定義が存在する場合は隔離 clone 内で CLI を生成する（`clone_build`）。存在しない場合は隔離 clone の外にある配布パッケージの実体を検証して隔離 clone 配下へ複製する（`package_copy`）。

2. **調達モードの判定入力は、隔離 clone に checkout された base SHA のコミット内容だけとする。** 作業ツリーの状態・環境変数・実行環境の構成を判定入力にしない。判定が確定しない場合は `package_copy` とする。

3. **`package_copy` では準備段が npm による依存導入と build script の実行を行わない。**

4. **調達実体の期待値の供給元を、base SHA のコミット内容に含まれる導入マーカー `.agent-skill-chain/.trusted-cli.json` だけに限定する。** 当該マーカーは配布集合の要素とせず、`init`・`upgrade` が生成し `uninstall` が撤去する。読み取りは SHA を明示した Git オブジェクト参照で行い、作業ツリー上のファイルを読まない。

5. **調達候補は期待値と一致した場合にのみ採用する。** 一致する候補が無い場合、および期待値を取得できない場合は、レビュアを起動せず、審査対象の実行コードへフォールバックせず、前提と是正手段を含む日本語メッセージを出して非0終了する。当該メッセージには、列挙した候補の識別子と実際に探索したパスを全件含める。どこを探して見つからなかったかを示さない診断は、無言の劣化と同じく原因の特定を実行者へ委ねるため採らない。

6. **調達した実体の照合に用いる digest は、配置場所・導入経路・時刻に依存しない正準ツリー digest とする。** 対象はパッケージ root 配下の通常ファイルとし、依存モジュールのディレクトリと Git メタデータを除く。除外を適用した後の対象範囲内に symbolic link がある場合は算出しない。除外された範囲にある symbolic link はこの中止条件に該当しない。決定 7 が定める依存への参照経路は、この除外範囲の内側にのみ置く。

7. **依存モジュールの実体を隔離 clone 配下へ配置しない。** 隔離 clone 配下へ配置するのは調達したパッケージ自身のファイルに限り、依存は参照経路のみを与える。参照経路は、複製先パッケージ root の外か、複製先パッケージ root からの相対で依存モジュールのディレクトリ配下にのみ置く。これにより決定 6 の算出と両立する。

8. **調達モード・調達元識別子・調達実体の digest を、準備段が生成する既存の一回限りの受け渡し経路へ載せ、証跡へ記録する。** 証跡のスキーマ識別子は据え置き、当該記録は任意フィールドとして加える。証跡投稿時には、実行中の CLI が隔離 clone 配下にあること、および `package_copy` では実行中の実体の digest が base SHA の期待値と一致することを、記録側が独立に再検査する。

9. **launcher digest の算出対象から配布集合外の project policy 文書 2 件を除き、レビュア起動スクリプトが読み込んで実行する共有 CLI 解決実装を加える。** 結果として算出対象は 10 要素の固定列挙となり、実行環境や実行時の解決結果によって変動しない。算出対象のいずれかを trusted base SHA から取得できない場合に部分集合で算出しない現行挙動は維持する。導入マーカーは配布集合の外にあるため算出対象へ含めない。

10. **隔離環境の健全性は、処理の実行ではなく状態の観測で確定する。** 隔離 clone に登録された remote が 1 件も存在しないことを積極的に検査する。

## Consequences

- 利点: consumer project のローカルゲートが、consumer 自身のビルド構成・ビルド成否・依存導入成否から独立して成立する。非 Node 構成でも実行できる。
- 利点: 期待値の供給元が base SHA のコミット内容 1 か所に限定されるため、由来検証が空洞化する経路（自己申告・環境変数・審査対象側のファイル）が設計上存在しなくなる。
- 利点: 調達の失敗がすべて非0終了に倒れるため、実行された verdict 記録コードが未検証であるまま証跡が残る状態が生じない。
- 利点: 導入マーカーを配布集合の外に置いたことで、launcher digest の算出対象へ新しい必須要素を加えずに済み、過去の base SHA に対する算出停止が起きない。
- 欠点: consumer は CLI の版を更新した際に更新操作を行い、その結果を default branch へ反映しなければ、期待値の不一致でゲートが止まる。これは版の取り違えを実行前に止める意図した挙動だが、更新手順を 1 段増やす。
- 欠点: launcher digest の算出対象を変更するため、同一の base SHA に対しても digest 値が変更前後で変わる。変更前に投稿済みの証跡は変更後のコードでは検証済みとして扱われず、過去反復を用いるラウンド計数が利用不能へ倒れる。承認済みゲートの判定記録そのものは Issue と PR に残る。
- 欠点: 調達モードが 2 つあるため、準備段の経路が 1 本ではなくなる。判定入力を base SHA のコミット内容へ限定してもなお、2 経路それぞれの検証が必要になる。
- 欠点: 依存モジュールの実体は隔離 clone の外に残るため、実行時に解決されるコードのうち依存閉包は本決定の束縛対象に含まれない。
- フォローアップ: 実行時に解決される依存閉包の由来・完全性の束縛は Issue #772 の射程とする。本決定は隔離 clone 配下へ配置する範囲と検証対象を一致させることで、当該 Issue が扱う境界を先取りしない。
