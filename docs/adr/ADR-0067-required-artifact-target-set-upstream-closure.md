## Context

必須成果物検査は、あるセグメントが「開始済み」と判定された場合にのみ、そのセグメントの必須成果物の存在を検査する。開始済みの判定根拠は、そのセグメントに対応する成果物がブランチ差分に現れることだけである。したがって、成果物が1つも作られていないセグメントは開始済みと判定されず、検査自体が実行されない。成果物が欠けている場合こそ検査が必要であるにもかかわらず、欠けていること自体が検査をスキップさせる構造になっている。

実運用で、quick 免除の解除条件（変更差分がスキーマ定義を含む）に該当し設計・実装計画セグメントの成果物が必須であったにもかかわらず、その成果物が両方とも存在しなかったために当該セグメントが検査対象にならず、欠落したまま CI が成功した事例が発生した。欠落を発見したのは独立検証セグメントのレビュアであり、レビューは GitHub Coordination Backend ではガイドラインであって自動強制を持たない。結果として、影響の大きい変更に通常フローを強制するための解除条件そのものが機械的強制を失っていた。

検討したトレードオフは次のとおり。

- 開始済みセグメント判定の根拠を変更し、成果物の有無に依存しない別の入力（Coordination Backend 上の進行状態など）から導く案: 判定入力を新設することになり、開始済みセグメント判定を利用する他の検査（要求・要件の記述充足検査、設計の図示要否検査、受入条件の対応検査）の分岐条件まで一斉に変わる。影響範囲が本欠陥の是正に必要な範囲を大きく超えるため採らない。
- 全セグメントを無条件に検査対象とする案: 要求・要件セグメントだけを開始した段階の PR や、コード変更を伴わない文書のみの Issue が一律に失敗する。作業を小さなバッチで段階的に進める運用そのものを壊すため採らない。
- 成果物の存在判定規則（成果物存在述語）を厳格化する案: base 側に残存する同名ファイルによる偽陽性の充足は解消するが、成果物ファイルの削除自体を目的とする Issue を自己言及的に失敗させるなど、本欠陥とは独立の副作用を持ち込む。本欠陥の原因は述語ではなく検査対象集合の側にあるため採らない。

もう1つの論点は、quick 免除の可否を決めるシグナル（GitHub モードでは Issue ラベル、ローカルモードでは Issue 状態ファイル）を取得できない実行環境の扱いである。現行の判定はシグナル取得の失敗を「quick が要求されていない」と同一の結果へ畳み込んでおり、免除の可否だけを問う限りこの畳み込みは安全側で正しい。しかし対象集合を拡張すると、「解決できたうえで未要求」と「解決できない」で検査の強さが分岐するため、両者の区別が必要になる。本リポジトリは他リポジトリへ配布される資産であり、配布先の CI がシグナルを取得できる保証は無い。取得の一時障害（API エラー・レート制限）と恒久的な未付与（権限・トークン未設定）は、観測側から区別できない。

## Decision

必須成果物検査を適用するセグメントの集合を、次の規則で導出する。

- 開始済みセグメント集合が空であれば、対象集合も空とする。検査は1回も実行せず、成果物の欠落を理由に失敗しない。
- 開始済みセグメント集合が空でなく、かつ後述の閉包追加条件を満たす場合、セグメントの連鎖順序上で開始済み集合の最も下流の要素より前に位置し、開始済み集合に含まれず、かつ閉包追加除外集合に属さないセグメントを対象集合へ加える。
- 閉包追加除外集合は「実装」と「独立検証」の2つとする。実装セグメントを除外するのは、その必須成果物が差分そのもの（コード変更・テスト変更）であり、コード変更を伴わない文書のみの Issue には産出物が原理的に存在せず、強制すると正当な Issue を失敗させるためである。独立検証セグメントの除外は、現行のセグメント定義の下では結果に影響しない。独立検証が閉包追加対象になるのは開始済みセグメント集合に独立検証より下流の要素が含まれる場合であり、連鎖上で独立検証の下流にあるのは終端の要素だけだからである。終端の要素はセグメント定義に要素として存在せず連鎖の行き先としてのみ現れるため必須成果物を持たず、成果物の出現を根拠に導出される開始済みセグメント集合へ入ることがない。それでも規則として明記するのは、将来セグメント定義が延長され独立検証の下流に必須成果物を持つ要素が置かれた場合にも、独立検証を閉包追加しない意図を規則側へ残すためである。
- セグメントの連鎖順序は、セグメント定義の連鎖から導出する。実装側に固定列として再定義しない。

現行のセグメント定義（要求・要件、設計・実装計画、実装、独立検証の4要素）の下では、上記の除外集合による定義によって実際に閉包追加されうるのは要求・要件セグメントと設計・実装計画セグメントの2つだけであり、対象を肯定的に列挙する定義と同値である。両者が食い違うのはセグメント定義が延長された場合に限られ、そのときは除外集合による定義が「新設要素を既定で閉包追加対象に含める」という安全側の帰結を与える。

閉包追加条件は「quick シグナルを解決できた、かつ quick 免除を適用しない」の連言とする。すなわち次のように振る舞う。

- quick 免除が有効な場合は閉包追加を行わず、対象集合は開始済みセグメント集合と等しくする。免除対象の成果物を要求しない現行の挙動も維持する。
- quick 免除が解除された場合（quick が要求されているが、リスク区分が normal でない、または変更差分がガードレール対象を含む場合）は閉包追加を行い、解除理由を提示する。
- quick シグナルを解決できない場合は、免除を適用せず、かつ閉包追加も行わない。対象集合は開始済みセグメント集合と等しくなり、本決定の適用前と完全に同一の判定になる。解決できなかった旨と、そのため免除も閉包追加も適用しない旨を提示する。取得の一時障害と恒久的な未付与は区別せず、同一の劣化挙動をとる。

対象集合の導出は、単体テストから直接呼び出せる実行可能アセット側の、外部入出力を持たない関数として実装する。CI ワークフロー定義のシェル記述へ上流判定・閉包追加対象の判定を埋め込まない。CI ワークフローは、必須成果物検査を実行する段へ Issue ラベルを取得できる権限とトークンを与える。この権限とトークンの付与が本決定の実効化スイッチであり、与えない環境ではシグナルが解決できず、判定は本決定の適用前と同一になる。

開始済みセグメント集合を導出できない場合は判定不能として失敗させ、その失敗を空の開始済みセグメント集合として読み替えない。空の集合は「どのセグメントも開始されていない」という判定結果であり、「判定できなかった」こととは意味が異なる。両者を同一の値へ畳み込むと、判定不能がそのまま無検査の成功として現れ、本決定が塞ごうとしている穴と同種の経路が残る。この読み替えの解消が新たな失敗を生まないよう、CI ワークフローは開始済みセグメント集合を導出する段より前に、履歴を切り詰めないリポジトリ取得と base ブランチの明示取得を行い、この2点と展開結果の同一性を静的検査で保証する。この前提の下では導出の失敗そのものが起きないため、読み替えを解消しても本決定の適用前に成功していた PR が失敗へ変わることはない。

欠落による失敗メッセージには、セグメント名と欠落した成果物名を含める。閉包追加によって対象集合へ加わったセグメントについては、当該セグメントが開始されていないこと自体が失敗理由であると読み取れる情報を併せて示す。

## Consequences

- 利点: 成果物が1つも存在しないセグメントが検査対象から外れるという構造的な穴が塞がる。下流セグメントを開始した時点で、その上流の要求・要件セグメントと設計・実装計画セグメントの成果物が機械的に要求されるようになる。
- 利点: 対象集合の導出が外部入出力を持たない関数として独立するため、CI を起動せずに単体テストから直接検証できる。同種の欠陥が CI ワークフロー定義のシェル記述の中に潜伏して再発することを防げる。
- 利点: 権限とトークンの付与という単一の設定が実効化スイッチになるため、問題が生じた場合はコードを戻さずに設定の取り消しだけで従来の判定へ復帰できる。
- 欠点・トレードオフ: quick シグナルを解決できない実行環境では穴が開いたままになる。これは強制を強める方向ではなく弱める方向の既定であり、agent-skill-chain の通常の安全側既定とは逆向きである。それでもこの向きを選ぶのは、(a) 強制が有効になる条件（シグナルを解決できること）が CI ワークフロー定義の内容として静的に検査でき、どの環境で強制が効くかを配布物の側で確定できること、(b) 本検査は成果物作成の規律に関するものでセキュリティ低下やデータ喪失には関与せず、シグナル取得の一時障害だけで無関係な PR を失敗させる不利益（強制への信頼低下と迂回の誘発）が穴を一時的に残す不利益を上回ること、(c) 解決不能時の対象集合が適用前と完全に同一になるため、閉包追加そのものによって新たに失敗する PR は存在しないこと、による。ただし開始済みセグメント集合の導出失敗を空集合へ読み替えない変更については、「本決定によって新たに失敗する PR は存在しない」と言えるのは、本決定が定める前段（履歴を切り詰めないリポジトリ取得と base ブランチの明示取得）を保つワークフロー定義を用いる環境に限られる。当該前段を保証する静的検査は本リポジトリの自動テストとして実行され、配布物には含まれず配布先では実行されない。また展開結果と配布テンプレートの同一性検査は、配布先では配布先ローカルの2つの複製どうしを突き合わせるため、双方を整合的に改変した状態を検出しない。したがって配布先が base 取得段を双方から取り除いた環境では、従来は空の開始済みセグメント集合として成功していた PR が失敗へ変わりうる。この範囲について本項の言明は成立しない。要求側もこの範囲を非退行保証の対象外として明記しており、配布物のワークフロー定義それ自体を配布先が改変していない環境に対してのみ非退行を保証するという前提で、本項の成立範囲と一致している。
- 欠点・トレードオフ: 上流セグメントの成果物を用意しないまま下流セグメントだけを開始した PR は、シグナルを解決できる実行環境では失敗するようになる。これは本決定が塞ぐ対象の穴そのものであり意図した挙動変更である。該当する PR は、上流成果物を作成するか、quick 免除の条件を満たすことで解消できる。
- 欠点・トレードオフ: 必須成果物検査を実行する段へ Issue ラベルを取得できる権限とトークンを与える結果、CI 上で quick 免除が初めて実効化する。現在 CI で失敗している quick 免除有効の PR が成功へ変わりうるが、これは quick 免除を規則どおり機能させるという意図した効果である。
- 欠点・トレードオフ: 成果物存在述語は変更しないため、base 側に同名の成果物ファイルが残存している場合は、当ブランチで一切作成していなくても存在すると判定され欠落が検出されない。閉包追加された設計・実装計画セグメントで実効的に強制されるのは、リポジトリ水準の判定を持つ ADR を除いた2つの成果物ファイルである。
- フォローアップ: 実装セグメントの成果物欠落は閉包追加除外集合により検出対象外のまま残る。文書のみの Issue を失敗させないための意図した除外だが、コード変更を伴うことが確定している Issue に限って実装セグメントも要求する余地はある。必要になった場合は別 Issue で扱う。

## accepted 後の不変項目・可変項目

| 区分 | 項目 |
|---|---|
| 不変（accepted 後は変更不可） | `id`、Context、Decision、Consequences、`supersedes` |
| 可変（ライフサイクル遷移に伴い更新可） | `status`、`superseded-by`、`deprecated-reason`、`tags` |

本文（Context / Decision / Consequences）の変更が必要になった場合は、新しい ADR を作成し `supersedes` / `superseded-by` で旧 ADR との関係を記録する。既存 ADR の本文を書き換えてはならない。
