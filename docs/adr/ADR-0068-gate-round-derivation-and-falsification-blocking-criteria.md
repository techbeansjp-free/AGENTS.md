## Context

ゲートレビュアへ渡す判定プロンプトの反証ルーブリックは、反例を能動的に 1 件以上探索することだけを命じ、探索を打ち切ってよい条件を与えていない。立証側は「全 AC-ID が充足されていれば合格」という到達条件が一意に定まる一方、反証側には対応する到達条件が無い。その結果、同じ品質の成果物でもレビュアが反例を 1 件構成できれば不合格、できなければ合格になる。実測では ISSUE-733 の要求・要件ゲートが 9 反復、ISSUE-692 の実装ゲートが 10 反復、ISSUE-680 が 13 反復を要し、ISSUE-692 では同一の finding code が 6 反復連続で再提出された。投入資源の大半がゲート通過そのものへ費やされている。

停止性を与える機構は、軽量プロファイルの再是正ラウンド計数として既に 1 つ存在する。ADR-0031 はこの計数の格納先を Issue ごとの調整状態ディレクトリ配下の判定記録ファイルとし、GitHub モードでは一時領域へ置くことを、恒久ストア新設のコストに見合わないトレードオフとして確定させた。しかし本件で必要な停止性は Standard・Strict を含む全プロファイルに及び、かつ GitHub モードが本リポジトリの実運用そのものであるため、一時領域に依存する計数では毎回 0 に戻り打ち切りが一度も発火しない。これは本 Issue の要求（有限反復での承認または人間判断への到達）を直接無効化する。

検討したトレードオフは次のとおりである。

- ラウンド番号のための恒久ストアを新設する案: 停止性は最も素直に得られるが、Coordination Backend へ新しい状態を持ち込み、その耐久性・整合性・移行を新たに設計・検証しなければならない。一方で、各ラウンドのレビュア証跡は既に PR のレビューとして投稿され、反復識別子・slot・profile・target_sha・verdict 全体を保持したまま残っている。新設せずに既存の耐久記録から数えられるため採らない。
- ラウンド番号を証跡の件数から数える案: 実装は最も単純だが、Strict は 1 反復につき 2 件の証跡を残すため、ラウンド番号がレビュア体数に比例して整数倍にずれる。閾値の意味がプロファイルごとに変わってしまうため採らない。
- 高ラウンドの限定を「blocking の 3 条件のうち目的阻害性の 1 条件へ切り替える」形にする案: 「絞る」という意図に反し、到達可能性・責務内是正可能性の 2 条件が外れることで blocking の適用範囲がむしろ広がる。限定前後で受入条件が同時に充足できない状態にもなるため採らない。
- ラウンド番号を導出できない場合に人間判断へ倒す案: 停止性の形は整うが、差し戻し・是正・再レビューという既存のゲート反復そのものが消滅し、導出できない環境（ローカルモード等）のすべての不合格が人間へ流れる。既存運用の破壊であり採らない。
- 打ち切りの判定不能表明をレビアへの指示として与える案: レビュアの自然言語判断の当否は検証できないという本件の前提の下では、指示が守られたか否かを機械的に確認できず停止性が保証されない。採らない。
- severity をテキスト照合で機械的に書き換える案: ADR-0031 が誤検知と見落としの双方を理由に採らないと確定させている。本 ADR はこの判断を継承する。

## Decision

1. **ラウンドの単位はゲート反復とし、反復識別子の相異なる個数で数える。** 同一 Issue・同一ゲートについて、耐久記録に現れるレビュア証跡のうち、schema 版・Issue 識別子・ゲート識別子が一致し、投稿主体が登録済みの trusted recorder actor であり、反復識別子を取り出せるものを取り、その反復識別子の相異なる個数をラウンド番号とする。初回は 0 とする。証跡の件数からは数えない。target_sha では絞り込まない（是正のたびに target_sha は変わるが同一の系列に属する）。trusted recorder actor 以外の投稿を数えないのは、証跡と同形の本文を投稿できる主体がラウンド番号を押し上げると、限定閾値の早期到達を通じて blocking の適用範囲が狭まり、承認の敷居を下げる経路になるためである。反復識別子を取り出せない証跡を落とすとラウンド番号は小さくなり、限定も打ち切りも遅れる安全側へ倒れる。

2. **導出元は既存の耐久記録に限り、新規の永続ストアを設けない。** GitHub モードでは PR へ投稿されたレビュー証跡がこれに該当する。ADR-0031 が定めた軽量プロファイルの再是正ラウンド計数は、単位・格納先・用途のいずれも本ラウンド番号とは別の量であり、本 ADR はこれを変更しない。両者は併存し、軽量プロファイルが適用されたゲートでは、いずれかの打ち切りが成立した時点で人間判断へ移る。

3. **当該反復自身の反復識別子を計数から除外する。** ラウンド番号は 1 回のゲート反復の中で 4 回導出される（slot ごとの判定プロンプト生成、slot ごとの証跡投稿時の prompt digest 再計算、証跡検証時の期待 prompt digest 生成と打ち切り判定）。反復の進行中に耐久記録へ加わる証跡はすべて当該反復の反復識別子を持つため、これを除外すれば計数対象の集合は反復の開始から検証まで変化せず、4 時点の導出結果が同値になる。除外しない設計では、slot 1 の証跡投稿を境に slot 1 と slot 2 のプロンプトが食い違い、既存の prompt digest 一致検査が必ず失敗する。導出時点間で値が食い違った場合は、当該一致検査が証跡を受理せず人間判断へ倒れる。承認が黙って記録される経路は生じない。

4. **高ラウンドの限定は、blocking の 3 条件を維持したうえで実証性を加える真部分集合とする。** 目的阻害性・到達可能性・責務内是正可能性の 3 条件はラウンド番号によらず常に必要条件である。ラウンド番号が限定閾値以上のとき、blocking として提出してよい反例を「3 条件をすべて満たし、かつ実証性（反例が成立する経路を、当該ラウンドの判定対象成果物の記述を引用して具体的に示せること）を満たすもの」に限定する。3 条件はいずれも取り除かない。限定により blocking から外れた反例は warning 以下として記録する。あわせて、ラウンド番号やレビュープロファイルを理由に、データ喪失・セキュリティ低下・既存機能の回帰・当該 Issue の目的の未達という区分そのものを blocking の対象から除外しない。

5. **閾値は設定で与え、下限と順序関係を設定エラーとして強制する。** 限定閾値は 1 以上、打ち切り閾値は 2 以上とし、限定閾値は打ち切り閾値より真に小さくなければならない。等号を含めこれを満たさない設定は、設定の読み込み時に日本語の理由を付けて拒否する。限定閾値の下限が 1 であるのは、0 だと限定閾値未満のラウンドが存在せず、限定が真に狭める操作であることを機械的に検証できないためである。等号を許さないのは、限定が初めて効くラウンドと打ち切りが発火するラウンドが一致し、限定が承認率を引き上げる機会を一度も持たないまま判断が人間へ流れるためである。既定値は限定閾値 2・打ち切り閾値 4 とする。収束した実測例（ISSUE-721 実装ゲート 1 反復、ISSUE-729 要求・要件ゲート 4 反復）を打ち切らず、発散した実測例を 5 反復で止める最小の値として選ぶ。

6. **打ち切りの判定不能は trusted な処理が機械的に設定し、差し戻し判定より先に評価する。** 判定に使うラウンド番号が打ち切り閾値に達し、かつ未解消の blocking finding が残る場合、verdict を受け取って記録する処理が判定不能を設定し、既存の最終判定導出を経由して人間判断とする。承認は自動的に記録しない。証跡検証経路の既存導出は blocking の有無を判定不能表明より先に評価するため、打ち切りの判定はその前段に置く。レビュア自身が申告した判定不能と blocking が同時に立つ場合の既存の評価順序は変更しない。

7. **ラウンド番号を導出できない場合は、限定と打ち切りだけを止め、差し戻しの反復を維持する。** 導出できない場合に禁じるのは、限定を適用すること（安全側）と、打ち切りを理由に承認を記録することの 2 点だけである。未解消の blocking が残る場合は通常どおり差し戻しとし、是正・再レビューの反復を継続する。各ラウンドの帰結は、導出可否によらず承認・差し戻し・人間判断のいずれかである。判定プロンプトでは「過去ラウンドが無い（初回）」と「取得できなかった」を別の文言で展開する。取得失敗を初回と同一に扱うと、実際には過去ラウンドが存在するのに過去ラウンドが無いと展開され、蒸し返しの抑止が黙って無効になるためである。

## Consequences

- 利点: 停止性の保証が、一時領域に依存しない既存の耐久記録から得られる。セッションをまたいでも、是正のたびに target_sha が変わっても、ラウンド番号は 0 へ戻らない。
- 利点: 打ち切りが既存の最終判定導出（判定不能なら人間判断）を再利用するため、最終判定の意味論を増やさずに済み、進行役の差し戻し判断への影響が無い。
- 利点: ラウンドの単位がゲート反復であるため、閾値の意味が Standard と Strict で同一になり、プロファイルごとに閾値を分ける必要が無い。
- 利点: 導出時点間の同値性が崩れた場合の帰結が、既存の prompt digest 一致検査により人間判断へ倒れる。新しい失敗経路を作らずに検出できる。
- 欠点: ラウンド番号を導出できない環境（ローカルモード、PR 番号を伴わない呼び出し、trusted recorder actor の登録が無い consumer project）では有限性が保証されない。差し戻しの反復は維持されるが、打ち切りは発火しない。導出不能な環境そのものを解消する手段は本決定の対象外とする。
- 欠点: 判定プロンプトの内容が変わるため、本決定の適用時点で進行中のゲート反復は、投稿済み証跡の prompt digest が期待値と一致しなくなりやり直しになる。やり直さない場合の判定は人間判断へ倒れる。
- 欠点: 過去ラウンドの展開により判定プロンプトが伸びる。1 finding あたりの根拠要約と節全体の双方に文字数上限を置き、超過時は古いラウンドから省略して省略した旨を残すが、上限に触れた場合は古い論点の再提出を抑止する力が弱まる。
- 欠点: 進行役が Issue コメントで行った severity の降格は耐久記録に現れないため、過去ラウンドの展開には降格前の severity が現れる。finding 台帳の永続化は Issue #745 の射程であり、本決定では扱わない。
- 欠点: 既定値の限定閾値 2・打ち切り閾値 4 は実測に基づく仮の値であり、収束した実測例と発散した実測例の比較のみを根拠に設計時点で確定した。運用実績が蓄積した段階で見直しが必要になる可能性がある。値の変更は設定で行え、コード変更を要しない。
- フォローアップ: 軽量プロファイルの再是正ラウンドの打ち切りは、GitHub モードでは verdict 結線経路にしか実装されておらず実質的に作用しない。本決定の打ち切りが後備として働くため実害は生じないが、当該経路の欠落自体の是正は別 Issue とする。
