## Context

ゲートレビュアはツール呼び出しを一切許可されておらず、判定に使える情報は判定プロンプトへ文字列として展開済みの内容だけである。従来の判定プロンプトは conformance の判定軸を `SPEC.md` から抽出した受入条件の識別子（以下 AC-ID）に固定しており、AC-ID を抽出できない場合は「conformance は inconclusive とし人間判断へ倒すこと」という指示を出力していた。

一方で本システムの憲法は、作業規模を quick と指定した Issue について `SPEC.md`・`DESIGN.md`・`PLAN.md`・`VALIDATION.md` の作成義務を免除する。免除は、リスク分類が normal であり、かつ変更差分が `docs/adr/`・`.agent-skill-chain/config/segments.yaml`・`AGENTS.md`・`.agent-skill-chain/schemas/` を含まない場合にのみ成立する。免除に従って成果物を作らなかった Issue は AC-ID を抽出できないため、成果物の品質と無関係に conformance が確定せず、どのゲートも構造上 `approved` に到達できない。免除を活かすには、免除下で AC-ID 全件網羅に代わる判定軸（当該 Issue 本文に記載された要求・期待する挙動・受入基準。以下 代替判定基準）を判定プロンプトへ実体として展開する必要がある。

ここで 2 つの設計上の危険が生じる。

第一に、判定軸を可変にすると、判定プロンプト内で「判定軸を指示する記述」と「判定対象の成果物の内容」が混ざり、どちらの区間の内容がどの入力で決まるのかが不明確になる。従来の判定プロンプトは、判定軸を述べる節（適用対象の AC-ID）と conformance ルーブリックが別々の節に分かれており、ルーブリック本文には「全 AC-ID が充足されているか」という判定軸そのものが固定的に書き込まれていた。判定軸を切り替えると、この 2 箇所が同一プロンプト内で矛盾する。また区間の境界が見出し文字列でしか識別できないため、成果物本文に同じ見出しが現れると境界が一意に定まらない。

第二に、そして重大なことに、代替判定基準の実体をどこから取得するかが自己承認の可否を決める。判定を受ける側であるセグメント作業ワーカーが判定軸の実体を供給できるなら、緩い受入基準相当の記述を自分で書いて自分で通過でき、不変条件 I8（安全側ラチェット、silent pass 禁止、昇格は人間の明示行為のみ）が quick 経路に限って実質的に無効化される。憲法の役割・権限は、セグメント作業ワーカーへ自ブランチへの commit / push、Draft PR 作成、Issue コメントを与えている。したがってブランチ上のファイル・PR 本文・Issue コメントはいずれもワーカーが内容を制御できる経路である。

さらに見落としやすい経路がある。GitHub モードでは、ゲート通過ごとに 4 成果物の全文とゲート状態を Issue 本文の固定マーカー区間へ一方向転記する機能が既定で有効である。転記を実行するのは trusted な発行経路だが、転記される内容の著述主体はセグメント作業ワーカーである。免除は成果物の作成を免除するだけで禁止はしないため、ワーカーが `SPEC.md` だけを著述して `DESIGN.md`・`PLAN.md` を作らない状態は正当に成立し、その状態で先行ゲートを通過させると `SPEC.md` 全文が Issue 本文へ入る。以降のゲートで代替判定基準として Issue 本文全体を採ると、ワーカー著述の成果物全文が判定軸の実体になる。憲法自身も「転記結果をゲート判定の入力として読み戻すことはしない」と定めている。

検討したトレードオフは次のとおりである。判定軸の実体をブランチ上の成果物や PR 本文からも採れば、Issue 本文が薄い Issue でも判定軸を実体化でき、免除下のゲートが通りやすくなる。しかしそれは上記の自己承認経路をそのまま開く。逆に代替判定基準を一切導入せず免除下のゲートを常に人間判断へ倒せば安全だが、免除の意義（成果物作成の負担軽減）が失われ、進行役が毎回判定を上書きする運用が残る。区間の境界を見出し文字列のままにすれば実装は小さいが、成果物本文に同じ見出しを書くだけで境界を偽装でき、区間が重ならないという性質そのものをワーカーが破れる。

## Decision

1. **判定プロンプトを判定対象区間と判定軸区間の 2 つの区間へ明示的に分離する。** 判定対象区間はレビュアが読むべき成果物の内容または存在しない事由を提示し、判定軸区間は conformance を何によって判定するかを指示する。conformance ルーブリックの本文は「何によって判定するか」の記述そのものであるため判定軸区間に含める。反証ルーブリック・最終判定の扱い・出力形式の契約・ハルシネーション防止の指示は、いずれの区間にも属さない中立域に置く。

2. **区間の境界は、判定プロンプトの本文としては意味を持たない一意な標識行で表す。** 見出し文字列を境界に流用しない。さらに、成果物本文・変更差分・Issue 本文を判定プロンプトへ展開する際、標識と同一の文字列が含まれていれば無害な表記へ置換する。この無害化が無ければ、成果物ファイルへ終了標識を書き込むだけで区間を早期に閉じ、以降の内容を別の区間の側へ見せかけられる。

3. **代替判定基準の実体は、リポジトリの default branch を保護された基点として実行される起動経路が、Coordination Backend の一次情報から取得した Issue 本文のみに由来させる。** GitHub モードは Issue 本文取得、ローカルモードは Issue 状態ファイルの要求内容フィールドを取得元とし、呼び出しの基点は共通（メイン）作業ツリーのルートとする。ブランチ上の成果物ファイル・PR 本文・Issue コメント・ワーカーが作成した本文の写しは、当該記述がそこに存在するか否かによらず一切読まない。

4. **取得した Issue 本文から、成果物全文の一方向転記区間を除去したうえで代替判定基準を抽出する。除去範囲は、開始マーカーの最初の出現と終了マーカーの最後の出現を基準として一意に定める。** 開始マーカーがあり、その最初の出現より後に終了マーカーがあるならば、最初の開始マーカー行から最後の終了マーカー行まで（両マーカー行を含む）を除去する。開始マーカーのみが存在する場合はその最初の出現以降のすべてを、終了マーカーのみが存在する場合は先頭から最後の終了マーカーまでを除去する。マーカーの片側が失われた状態でも転記内容が残らない側へ倒す。除去後に残った本文へ開始・終了いずれかのマーカーと同一の行がなお含まれる場合、その行自体も捨てる。**最初ではなく最後の終了マーカーまでを除去するのは、上記 2 と同型のマーカー偽装の無害化である**——作業規模を quick と指定した Issue でも成果物の作成は禁止されないため、成果物本文の中へ終了マーカーと同一の行を書き込む入力は正当に到達可能であり、除去を最初の終了マーカーまでとすると、埋め込まれたマーカー以降の著述内容が本文に残って判定軸の実体へ流入する。転記側の実装は転記区間を組み立てる際にマーカーと同一の文字列を無害な表記へ置換しているが、本決定は抽出側の除去規則だけで偽装が成立しないことを要求し、転記側の無害化に依存しない。

5. **抽出は、転記区間を除去した本文のうち、見出しが要求記述節ラベルへ一致する節からのみ行う。** 除去後の本文を先頭から 1 度走査して囲み区間（fenced code block・HTML コメント。終了記号が現れないまま本文が尽きた場合は開始位置から本文末尾まで、先に開始した種別を優先）を特定し、その内部の行を見出し行として扱わずに ATX 見出し行で節へ分割する。正規化（前後の空白・強調記号・末尾コロンの除去、英字の小文字化、全角英数字と全角空白の半角化）した見出しテキストが、実装のコード上に固定列挙された要求記述節ラベル（課題・目的、要求、要件、期待する挙動、受入基準、完了条件、およびそれらに相当する英語表記）へ完全一致する節を要求記述節とする。要求記述節の内容を空行区切りのブロックへ分割し、空白のみ・HTML コメントのみ・水平線のみ・記入省略表現のみ（`無し`・`未定`・`TBD` 等の固定列挙との完全一致）のブロックを捨てる。残ったブロックを全要求記述節にわたって原文順に連結し、空白文字を除いた総文字数が実質性下限（40 文字。コード上の固定定数）以上である場合にだけ展開可能として当該ブロックを原文順に判定軸区間へ書き出す。総文字数が下限未満の場合、要求記述節が 1 件も無い場合、本文自体を取得できない場合、および抽出規則を一意に適用できないその他の入力は、いずれも展開不能とし判定軸を判定不能の指示へ倒す。**すなわち展開可能と判定してよい条件を網羅的に定め、それ以外はすべて展開不能へ倒す（安全側の既定）。** **空でないブロックを内容によらず採用する規則を採らないのは**、管理上の記述だけが書かれた本文でも展開可能となり、要求でも期待する挙動でも受入基準でもない文字列が唯一の判定軸として置かれるためである。そのときレビュアは実質的な判定軸を持たないまま立証観点を判定させられる。**管理上の記述を列挙の拡充ではなく実質性下限で排除するのは**、記入省略表現の言い換え（`担当者: 未定` のように語を含むが完全一致しない 1 行）が有限個の列挙では閉じず、列挙を増やすたびに列挙外の表現が残るためである。下限は列挙に載る表現をすべて包含する。下限を設けた副作用として、下限未満の実質的な要求も展開不能となりうるが、その誤りは判定不能の指示を経て人間判断へ倒れるだけであり `approved` を導出しない。**囲み区間の内部を見出し検出から除くのは**、コード例や記入案内として本文に含まれる `# 要求` 等の行が要求記述節の見出しとして一致し、その配下の記述が判定軸の実体になる経路を閉じるためである。**ラベル・記入省略表現の列挙と実質性下限を設定・環境変数・成果物から与えないのは**、判定を受ける側が採否を変えられないようにするためである。節の分割を上記 4 の除去より後に行うのは、転記された成果物本文が同じラベルの見出しを含むためである。Issue のタイトル、実装差分、テスト実行結果、継続的統合の結果は代替判定基準に含めない。

6. **判定対象の成果物と、`SPEC.md` から抽出した AC-ID 集合は、上記 3 の限定の対象外とする。** これらはワーカーが著述するが判定対象そのものであり、判定対象区間へ展開すること、および AC-ID 集合を判定軸区間へ書き出すことは限定に反しない。限定するのは代替判定基準の実体の取得経路だけである。

## Consequences

**利点。** 判定を受ける側が判定軸の実体を供給できる経路のうち、判定機構の側から閉じられるものはすべて閉じる。ブランチ上の成果物ファイル・PR 本文・Issue コメント・ワーカーが作成した本文の写しに置いた記述、および一方向転記によって Issue 本文へ入り込んだ成果物本文は、いずれも判定軸の実体にならない。ワーカーが制御できるのは「どちらの判定軸が適用されるか」に限られ、しかもその切替は進行役だけが書き込める免除シグナルが成立している場合にのみ起きる。切替先の内容は進行役側が管理する Issue 本文に由来するため、切替によって判定軸の信頼度が下がらない。区間の分離により、判定軸を観測する検証と判定対象の提示を観測する検証が同一の観測位置を争わなくなり、同一入力に対して 2 つの相反する期待結果が定まる状態（実装不能）が構造的に排除される。標識の無害化により、区間が重ならないという性質そのものが埋め込み内容から独立する。憲法が定める「転記結果をゲート判定の入力として読み戻さない」規定が、判定プロンプト生成の側でも機構として担保される。

**欠点・制約。** Issue 本文そのものへの書き込みは、本決定の射程外に残る。役割・権限はセグメント作業ワーカーへ自ブランチへの commit / push、Draft PR 作成、Issue コメントのみを与えており、Issue 本文の編集は運用規約として禁止されている。しかし本決定の時点で、その禁止に機構上の保証は無い——ワーカーを起動するアダプタの実行制約は実行コマンドを網羅的に限定しておらず、ワーカーへ渡す資格情報も Issue 本文の編集だけを除いて絞られていない。したがって規約に違反して Issue 本文を直接書き換えるワーカーは、判定軸が代替判定基準となる入力において判定軸の実体を供給しうる。本決定はこれに対する検知機構も遮断機構も導入せず、**運用規約による禁止はあるが機構上の保証は無い残存リスク**として記録する。是正するならば手当てはゲート判定機構ではなくワーカー起動基盤の側（実行コマンド制約の統一、または資格情報の権限分離）にあり、別の決定が扱う。

代替判定基準は Issue 本文の記述の質に完全に依存する。本文が薄い Issue では判定軸が粗くなり、本文が実質的に空である場合、要求記述節の見出しを持たない場合、および要求記述節の内容が実質性下限に達しない場合は、判定軸を実体化できず判定不能の指示へ倒れる。これは免除下の Issue が通過するために、Issue 本文へ要求記述節の見出しとその内容を書く運用を要求することを意味する。配布される Issue テンプレートは全 6 種が同一のフォーム項目を持ち、Issue フォームは各項目のラベルを見出しとして本文へ書き出すため、テンプレート経由で起票された Issue の主経路では見出しの表記が揺れない。見出しを持たない本文で展開不能へ倒れることは `approved` を導出しない側の誤りであり、是正は本文へ見出しを 1 行加えるだけで足りる。また Issue 本文・ラベル・変更差分の取得可否は target SHA に固定されないため、同一 target SHA でも判定プロンプトが起動ごとに変わりうる。判定プロンプトの digest を再計算して証跡と照合する自動検証経路が将来再導入された場合、成果物に欠陥が無くても照合が不一致となり人間判断へ倒れうる。この影響を抑えるため、Issue 本文の取得は免除が成立し判定軸の切替が必要な入力に限る。判定プロンプトの決定性の保証と入力の固定は本決定の対象外であり、別途扱う。

**今後のフォローアップ。** 判定軸が判定不能の指示である attempt から `approved` が導出されないことを、レビュアの指示遵守に依存せず trusted 側の値だけで機械的に抑止するかは本決定の対象外である。判定プロンプト生成時点の入力を保存し、後日その判定を再生成して照合する機構も本決定の対象外である。一方向転記のマーカー文字列の形式が将来変わる場合は、代替判定基準の除去規則を同じ変更で追随させる必要がある。追随を怠ると転記された成果物全文が判定軸へ再び混入するため、マーカー定義は転記側と除去側で単一の定義を共有する。

## accepted 後の不変項目・可変項目

| 区分 | 項目 |
|---|---|
| 不変（accepted 後は変更不可） | `id`、Context、Decision、Consequences、`supersedes` |
| 可変（ライフサイクル遷移に伴い更新可） | `status`、`superseded-by`、`deprecated-reason`、`tags` |

本文（Context / Decision / Consequences）の変更が必要になった場合は、新しい ADR を作成し `supersedes` / `superseded-by` で旧 ADR との関係を記録する。既存 ADR の本文を書き換えてはならない。
