## Context

`agent-skill-chain upgrade` は配布元の正本アセット（root直下の追跡対象ファイル・`.agent-skill-chain/` 配下の名前空間ディレクトリ群・展開済みテンプレート）を導入先へミラーコピーするが、配布元で廃止（リネーム・統合・削除）されたファイルを導入先から削除する処理を持たない。導入先には過去に書き込まれた古い内容のファイルが残り続け、`grep`・IDE補完・AIエージェントの参照先探索で古い内容がヒットし、実行可能スクリプトであれば古い挙動のまま呼び出され続けるリスクもある（Issue #492 SPEC.md）。

単純に「ファイル名が既知パターンに一致すれば削除する」方式は、過去に別Issueで発生した「パッケージ所有と判定した名前を中身の由来を検証せず削除し、ユーザーが同名で配置していた無関係な自作ファイルを誤って消去した」事故と同種のリスクを再発させる（Issue #492 SPEC.md 背景）。安全に削除するには、(a) 過去に本パッケージ自身が当該パスへ書き込んだことが記録により確認でき、(b) 導入先での内容が本パッケージが最後に書いた内容から変更されていないことの両方を機械的に確認できる場合に限る必要がある。

検討した実現アプローチ：

- (a) 導入先ファイルシステムに、バージョンごとに「そのバージョンで本パッケージが書き込んだファイルパス一覧とその内容ハッシュ」を記録する専用の所有権記録ファイル（`.agent-skill-chain/.owned-files.json`）を新設し、`init`/`upgrade` の書き込み完了ごとに更新する（本決定で採用）: 判定に必要な「過去に本パッケージが書いたか」「その後内容が変わっていないか」の両方を、導入先のファイル内容自体の解析や外部システムへの問い合わせなしに、導入先リポジトリ内だけで完結して判定できる。ファイル名パターンにのみ依存せず、内容ハッシュの一致という機械的に検証可能な条件を必須にすることで、無関係な自作ファイルを誤って対象にする事故を構造的に防げる。
- (b) 配布元パッケージの過去バージョンをすべて保持し、導入先の `.installed_version`（導入時点のバージョン）からの差分で削除対象を都度算出する: 配布元パッケージ自体が全バージョンの完全なファイル一覧を恒久的に保持し続ける必要があり、パッケージのリリース運用（過去バージョンの取得可否）に強く依存する。導入先が独立して復元可能であるべきというI3の趣旨（作業状態は常に完全復元可能）にも反し、導入先のファイルシステムだけで判定が完結しない。
- (c) 削除候補をファイル名（既知の廃止パスの固定リスト）で判定する: SPEC.mdが明示的に禁止した過去の事故と同種の再発リスクを持つため採らない。内容の由来・変更有無を一切確認できず、パッケージが一度も書いていない同名ファイルを誤検知しうる。

## Decision

`.agent-skill-chain/.owned-files.json` を新設し、`init`・`upgrade` の書き込み完了ごとに「その時点で本パッケージが導入先へ書き込んだファイルの相対パスと内容ハッシュ（SHA-256）」の一覧として更新する。このファイルは `NAMESPACED_ENTRIES`（`.agent-skill-chain/project/` を含まない既存の構造的境界）と同様の性質を持つ内部マーカーファイルであり、配布元から導入先へミラーコピーされる対象そのものには含めない（`.installed_version` と同じ扱い）。

`upgrade` は、直前の所有権記録に含まれるパスのうち今回の配布元には存在しないものを削除候補とし、各候補を導入先ファイルシステム上で分類する：ファイルが物理的に存在しない場合は削除操作もエラーも警告も発生させず記録から除去する（目的状態が既に達成されているとみなす）。読み取り自体がENOENT以外の理由で失敗する場合、または通常ファイルでなくなっている場合は、削除せず警告を提示し記録にエントリを保持する。内容ハッシュが記録済みハッシュと一致する場合のみ削除し（非dry-run時）、記録から除去する。一致しない場合は削除せず警告を提示し記録にエントリを保持する。削除操作（syscall）自体が権限不足・I/Oエラー等で失敗した場合は、当該ファイルを削除失敗として扱い、削除に成功したファイルとは区別して記録からは除去せずエントリを保持する（読み取り失敗時と同じ、次回実行での再試行可能性を保つ設計思想）。この削除失敗は削除実行時のエラーとして非ゼロ終了の対象に含める。`.agent-skill-chain/project/` 配下は構造的に所有権記録へ現れないことに加え、判定ロジック内でも防御的に除外する。`--dry-run` は同一の候補計算ロジックを用い、削除の実行と記録の更新のみを行わない。削除実行時のエラーは個々のファイル単位で扱い、成功した他の結果を先に標準出力へ出力してから、失敗ファイルを明示した非ゼロ終了で応答する。

## Consequences

- 利点: ファイル名パターンに依存せず、「過去に本パッケージが書いたか」と「その後変更されていないか」の両方を機械的に検証してからでなければ削除しないため、無関係な自作ファイルの誤削除事故（過去の類似事故）を構造的に防止できる。判定は導入先リポジトリ内で完結し、配布元パッケージ側に過去バージョンの保持を要求しない。
- 欠点・フォローアップ: `.agent-skill-chain/.owned-files.json` 導入以前に `init`/`upgrade` を実行済みの既存導入先には所有権記録が存在しないため、初回の `upgrade` 実行では削除候補が0件になる（記録が無いパスはAC-4により削除要否判定の対象外）。以降のアップグレードから徐々に記録が蓄積され、廃止ファイルの検知が有効になる。この移行期間中の遡及適用は本Issueのスコープ外（SPEC.md スコープ外）。`uninstall` は本Issueで変更しないため、`.agent-skill-chain/.owned-files.json` は `uninstall` 実行後も導入先に残存する（次Issueでの解消検討対象）。
- スコープ外の扱い: `uninstall` コマンド自体の削除ロジックの変更、`detectLegacyAssets` が検知する所有権記録導入以前の旧世代アセットの一括削除、GitHub workflow（`.github/`）配下の同期・削除、ファイル権限（実行ビット等）のメタデータ差異の検知・警告は本決定の対象外とする（SPEC.mdスコープ外）。
