# Issue 1509 現行Skillの反復レビュー実測

## 対象と判定方法

対象は `60d68920d3f925ede528993c44bd4bd67fc795e6` の現行ASC・変更レビューSkill。旧Controllerの16 roundや撤去済み診断器の再現ではない。製品機構・Skillの変更は行わず、追加の永続台帳・専用Agent・固定round上限を先に導入しない。

3軌跡の初回／変更後を各1回、計6回、同じCodex Hostで別のephemeral contextとして測る。モデルは `gpt-6.1-sol`、reasoning effortは `medium`。各起動の実引数と時刻・所要秒・CLIのusage・欠測は `measurements.json`、全JSONLと入力・出力は `traces/` に保持する。既存の認証を使い、起動元のみHostの許可で実行し、子CLIは `-s read-only -a never`、外部検索無効とする。`--ignore-user-config` を用い、会話のresume/forkは使わない。変更後のcontextには当該軌跡の初回の出力だけをレビュー履歴として渡す。

Git未管理の合成fixtureを `/tmp/asc-1509-review-fixtures/` に置いた。レビューのために実製品をsnapshot化したものではない。各対象の元要求、変更前後のmodule、既存テストは `fixtures.json` と現行の `prepare.mjs` で再現できる。元測定時にはPython版 `prepare.py` を用いた。評価者がCLI起動前に `oracle.json` とfixture・Skillのhashを `frozen-manifest.json` へ凍結した。oracle・生成元・他試行・集計はReviewerに渡さず、参照しないよう指定した。oracleにある期待指摘そのものはpromptに含めていない。元要求には失敗時の契約等を明示しており、これは正解の秘匿とは区別する。

- 認可欠陥 → 完全修復：他組織の更新を許す欠陥を、更新前の組織照合で修正する。解消した認可指摘の再提示を調べる。
- 正常private helper → 説明コメントのみ：唯一の公開呼出側で入力を検証している。private helperへの二重防御要求を調べる。初回から正常であり、実質的な修復ではない対照である。
- 保存欠陥 → 不完全修復：保存失敗時のlive record変更とretryKey消費がある。後者だけを修正する。現在も成立する前者の再指摘は正当で、解消済み後者の再提示は不要と扱う。

不要再提示は「前回の指摘と同じ文字列」ではなく、解消した不変条件の違反を現在の根拠なく再要求することと定義する。正常対象への要求外の修正要求はfalse positive、残る違反の指摘欠落は見逃しとする。初回の保存欠陥は2個の既知違反として数え、1件にまとめて報告された場合でも各違反が説明されていれば検出とする。集計は実出力とoracleを評価者が照合するもので、確信度や指摘件数だけによる棄却機構ではない。

## 実体の検証

元測定時にはPython版 `verify.py` で6対象を実行し、oracleと6/6一致した。Node移植後も `node docs/evidence/1509-review-repetition/verify.mjs` で同一の6反例と既存テストを再実行し、すべて元の観測値と一致した。元結果は `behavior-verification.json`、Node再検証は `node-behavior-verification.json` に分けて保持した。`behavior-verification.json` は実コマンド・終了コード・観測値を含む。認可初回では他組織が200で更新でき、修復後は403で状態不変。private helperは両対象で不正値を拒否し状態不変。保存初回は503でもnote変更・key消費、変更後はkey消費だけ解消してnote変更が残る。既存の正常系テストは6対象ともexit 0であり、成功テストだけでは欠陥を検出しない構成とした。

## 観測結果と判断

現行Skillのまま、解消対象2違反の不要再提示は0、残る違反への正当な再指摘は1、既知違反4 instancesの見逃しは0だった。正常private helperの2 contextに不要な二重検証要求はなかった。保存初回では2違反を1指摘にまとめていたが、live record変更とretryKey消費の両方を再現・説明しており両検出とした。変更後はkey消費の解消を明記し、live record変更だけを再指摘した。分類根拠と元出力の対応は `assessment.json` にある。

| 対象 | 初回の判定 | 変更後の判定 | 初回秒 | 変更後秒 |
| --- | --- | --- | ---: | ---: |
| 認可 | 組織境界違反を再現、High 1件 | 解消、指摘なし | 40.590 | 47.276 |

適合6起動のwall timeは合計 **231.135秒**、観測inputは **593,620 tokens**（cached input **496,384**を含む）、outputは **8,597 tokens**。reasoning outputの報告値は494で、outputと別加算しない。6起動はすべてexit 0・turn.completedがあり、usage欠測なし。起動失敗3件の既知20.192秒を含めると全試行の既知wall timeは **251.327秒**で、失敗側のtokensは欠測のままである。CLIは `0.164.0-alpha.11.1`。認可の変更後起動ではモデル一覧refreshのtimeoutがstderrに1件あるが、指定モデルのturnはexit 0で完了してusageも得られた。この待ち時間もwall timeに含み、純粋な推論時間とは扱わない。

この選択した小規模軌跡では、既存の指示で解消済み指摘と正当な再指摘を区別できた。実測費用はあるが、同義指摘による追加往復は観測していないため、**追加機構を導入しない**。長い実開発での頻度は未測定であり、既存指示が常に防げるとの結論にはしない。新たに現在の反例のない再提示が実業務で記録された場合は、対象・指摘履歴・所要時間・usageを同じ形で照合してから変更の必要を判断する。旧16 roundの原因解決や削減率は主張しない。

## 起動の失敗と逸脱

測定前に3件の起動失敗がある。これらを成功6試行へ混ぜず、`startup-failures/` に保持した。いずれもtoken usageは欠測であり0に換算しない。

1. `-a never` を `exec` の後へ置いた引数エラー：0.017秒、exit 2、turn未開始。
2. 制限内の既存CODEX_HOMEでapp-server初期化がread-only filesystemにより失敗：0.296秒、exit 1、turn未開始。
3. 一時CODEX_HOMEへ認証の読取りリンクを置く方法を試したが、上位の変数再割当て禁止に適合しないため撤回：19.879秒、workspace routing discovery失敗、exit 1、turn未完了。認証リンクは削除した。これは権限に適合する測定として受理しない。以後、既存認証で起動元の許可を得る方法へ変更し、子CLIのread-only制限を維持した。

失敗の既知wall timeは計20.192秒。起動失敗の自動再試行は行わず、原因を確認して明示的に起動方法を訂正した。3件目のtransport内の自動reconnectは当該失敗traceにそのまま残っている。

## 再現

このEvidenceを含み、元のSkill hashに一致する専用worktreeを用意し、既存のCodex CLI認証・モデル利用権を使う。repo rootから以下を実行する。6 CLIは費用を伴う。CLIの外側にHost実行の許可が必要な環境では、既存認証で起動できる許可を得る。HOME・CODEX_HOMEを再割当てしない。

```sh
node docs/evidence/1509-review-repetition/prepare.mjs
node docs/evidence/1509-review-repetition/verify.mjs
node docs/evidence/1509-review-repetition/measure.mjs /tmp/asc-1509-new-measurement
```

`prepare.mjs` は保存済みの `fixtures.json` を元に同一内容だけをmaterializeし、異なる既存内容を上書きしない。元のoracle・凍結manifestは再生成せずhashを維持する。`measure.mjs` はfixtureとSkillの凍結hashを照合してから実行し、新規出力directoryだけを受理する。途中で最終出力が欠けた場合や起動失敗・timeoutは記録して停止する。CLIの上限は600秒で、timeout時はprocess groupへSIGTERMを送り5秒後も残る場合はSIGKILLする。fixture検証だけではSkill hashを必須にせず、モデル再測定時には元のSkill hash一致を要求する。既存の失敗ログは自動再生成せず保存資料である。実コマンドは各測定の `argv` とpromptを正本とする。時刻と絶対path・thread IDは実行ごとに変わる。

## 成果物の自己確認

fixture実動作、凍結hash、6件のthread IDの独立性、全JSON/JSONLのparse、usageとwall timeの集計一致を確認した。全contextで3本の必須レビュー参照を実際に読んだcommand traceがあり、oracle・生成元の読取りはtrace上認められない。指摘分類は最終出力・実反例・oracleを人手で照合した。元のPython runner3本は初回測定時に構文確認したが、現行のsource validatorがdocs内のPython sourceも拒否する契約に適合させるためNodeへ移植した。現行Node4本は構文確認、source validator成功、fixture再検証6/6一致。Nodeのtimeout処理はSIGTERMを無視するローカル子processをSIGKILLして回収し、存在しない実行fileの起動失敗も確認した（`node-harness-verification.json`）。制限内での初回Node検証は子processのstdoutが空になり未完了だったため、Hostで実行許可を得た再実行の結果だけをNodeの合格Evidenceとした。`git diff --cached --check` は成功。変更はEvidenceだけであり、製品コード・Skill・テスト定義は変更していない。製品全体の `npm run quality` と独立レビューは統合担当が提出対象に対して確認する。

## 実測runnerと移植版の区別

保存した6つのCodex CLI実測は、commit `7d60ca568c0354723db35abd596feb08a0d21135` にあるPython版 `prepare.py`・`measure.py`・`verify.py` を用いたもの。現行Node版によるCodex CLI再測定は実行していない。元Python sourceはそのGit commitから参照でき、検査回避の拡張子変更ではなくNodeへ実装を移した。元の `frozen-manifest.json`・`measurements.json`・trace・oracleを変更せず保持した。`node-harness-hashes.json` は移植版4本と元凍結manifestのhashを別記し、Nodeのfixture検証成功を元のモデル測定runnerの実績と取り違えない。

## 判断の限界

これは課題を意識して作った、短いコードと明示した要求を用いる合成fixtureである。Reviewerへ履歴再検証と既存防御の確認を明示しており、課題誘導がある。各条件1回で確率・分散・実業務での発生頻度は推定できない。比較対象のSkillなし条件・旧版・永続状態機構は実行していないため、改善率や機構の優劣は示せない。正常対照の2回目は実験者が指定した再提出であり、Skillが再レビューを要求した結果ではない。この費用をSkill起因の不要往復とは扱わない。正常対照は実質変更がなく、実際の誤指摘を修正して再発する軌跡を代表しない。独立contextは一方で履歴の持ち越しを限定し、長い会話や多数の相互依存文書で生じるchurnの負荷は扱わない。

CLIのusageはツールを挟むturn全体で報告された入力・出力で、初回promptのユニークtoken数ではない。cached inputはinputの内数であり別加算しない。各試行でcache利用量も異なり、同条件の費用比較ではない。価格計算や金額換算はしない。wall timeはCLI subprocessの開始から終了までで、fixture準備・人手評価・既存テストを除く。新しい機構の導入費用や運用効果は測っていない。
