## 結論

- 判定（規則1）：**不合格**。g1-maintenance-answerは8/9で水準7/9を満たした。ただし、調査の前の無償の約束の目印が1件（C-m-r1-3の`free-before-check`）当たった。この件数は、判定の規則に従い、中身を確かめる前に`runs.json`の`markerDeductions`から数えた。
- 当たった1件は、回答の「今は『無償で直します』とも『有償です』とも答えません。まず原因を調べます。」の引用の部分だった。統括が回答を読んだところ、無償の約束はしていなかった。これは固定した判定の外で行った確認であり、合否は変えない。この1件の他の観点（WAR ID・合意の版・調査）はすべて合っていた。
- `judge.json`の全体の判定は`not-judged`になった。共通の仕組みの`judge.mjs`が条件を2つと決めて読むため、条件が1つのこの設定では、試行の無い条件`undefined`ができ、その条件の「有効な試行が無い」で判定しなかった。Cの`perCondition`は`meets-levels`で、規則2の「判定不能」の条件（未完了、有効な試行が0件の依頼、置き換えの欠け、失敗の率）は、Cには当たらない。仕組みの直しは別のIssueで扱う。
- 合意の版：m-r1・m-r2・m-r7の9試行すべてで、回答に例の形「合意の版1.0」が現れた（統括がtraceの文字列で確かめた。合否には使わない）。
