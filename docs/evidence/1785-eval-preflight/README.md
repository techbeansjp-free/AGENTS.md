## 費用管理の確認

- **API課金とsubscription**：この環境では区別できなかった（API keyは未設定、認証の方式は未確認）。過去の評価も、値はHostの報告値（`total_cost_usd`、`subagent_tokens`）だった。課金額は全て欠測である。推定で確定値にしていない。
- **少数試行の費用**：Cの見積りに含めた（下表）。
- **並列の予約・確定・未確定**：
  - Agent toolの並列起動（#1767は7件、#1774は3件を同時に起動）では、tokenは完了通知の時点でしか分からない。実行中の費用は未確定で、1件ごとの金額の上限も無い（`execution-budget.mjs`は回数と時間だけを扱う）。

  - 以上から、予約・確定・未確定を区別する台帳は不要と判断した。計画に上の算術を書けば足りる。
- **timeout・通信断・rate limit・中断**：R68・HSとも1回だけ起動し、失敗を記録して止まった（代役の起動回数で確認）。HSのtimeoutは`--timeout-ms`、R68は600秒である。通信断はrate limitと同じ`is_error`の経路と推定するが、代役では再現していない（欠測）。
- **費用上限と停止条件が未確定の有料実験**：本Issueの実モデル検査は、EVAL_PLANの上限（8回・1.00 USD）を実行前にcommitしてから行った。
- **AI採点器**：対象の評価はどれもAI採点器を使っていない。S67・S74は決定論である。ただし#1774の`runs.json`は、操作者が回答をgoldの項目に対応付けたもので、その対応付けの一致率は測っていない（欠測）。

A＝現行（実際の結果）、B＝事前検査を追加、C＝Bに少数試行を追加。tokenはsubagent tokensで、I8（processed tokens）は単位が違うので合計から分けた。

- I1の1試行の平均は49,175 token（688,452÷14）。観測した失敗率は7/14＝0.5である。

## 採否

EVAL_PLANの基準に、Bが防いだ分だけで当てはめた。
- **既存手段で十分**：該当しない。既存の採点器（S67・S74）は、8種を全ては区別しない。
- **限定改善候補**：条件を満たさない。次の3つの条件は満たす。
  - Bは、過去の基盤の不備を1件以上（I2・I6）、モデル呼出し0回で再生した。
  - 採点器・goldを変えない。
  - 採点精度・独立性を下げない。
  - しかし準備時間の条件を満たさない。Bの準備（初版で約2分＋実行、計画外の追加を含めて約7分）は、Bで防げるI2の再実行（約105秒）を上回る。I1はBで防げないので、比較に含めない。
- **不採用**：「Bの準備の費用が、防げる無効試行の費用を上回る場合」に当たる。
  - 測った費用は時間だけで、時間ではBが上回る。ただし両側とも下限同士の比較である。Bの準備は計画のcommitから数えた（scriptは全て計画のcommitの後に書いた）。I2の側は、Phase 1cの3回を順に実行したと仮定した再実行の時間で、原因の調査とfixtureの修正の時間は記録に無く含めていない。
  - tokenではBが有利（モデル呼出し0回、対してI2は192,794）である。しかし親sessionのtokenが欠測なので、費用での判定はできない。
  - 計画は「費用」の内訳を時間に限っていない。そのため、測れた時間で判定した。

**結論：不採用。** Bを評価の標準の工程として足さない。CはBに条件付きで加える案だったため、Bと同じく足さない。新しい機構も導入しない。

経緯：初版（commit `9ed3e6fa`）は「限定改善候補」と判定した。独立レビューの指摘（Bで防げないI1まで比較に含めていた）を受けて、Bが防いだ分だけで当て直し、不採用とした。

この判定は、計画の時間の基準によるものである。Bに効果が無いという判定ではない。結果を見た後で基準を変えると計画に反するので、基準は変えない。

再利用できるもの（採用ではない。評価を行う人が任意に使う）：
- `preflight.mjs`の8種の区別と、3点の較正。既存の採点器を再利用する前に、変更なしで実行できる。較正が見る軸はrecallと検出数だけである。
- P3の起動設定。goldを隠す必要がある評価で使う。前提は、goldがcwdと`--add-dir`の外にあることと、事前にmarkerの反例で確かめることである。
- 並列の費用は算術で予約する（「費用管理の確認」）。

## 欠測・限界

- 課金額、cacheの内訳、親sessionのtoken（調査・作成・採点の分）は欠測である。
- 準備時間は、commitとfileの時刻から求めた。作業の中断や、並行する別作業の影響を分けていない。
- 有効性の比較は、過去の事象を記録値で再生したものである。同じ評価を、A・B・Cで新たに実行して比べてはいない。Cの効果は推定である。実モデルでのI1の再現はしていない。原因の依頼文が記録に無く、同じ条件を作れないためである。
- I2・I6の再生は、原因を知った後に書いた検査によるものである。未知の不備を本試行の前に見つける能力は、測っていない。
- I3・I4は過去の記録に依っており、今回は再実行していない。I5・I7は、検査を実装していないので「見込み」にとどまる。
- `goldPrecondition`は、#1774の規模fixtureに固有の静的規則（POST routeかseedの有無）である。一般のfixtureには、そのまま使えない。
- 変異は作業者が作った6種だけで、網羅的な変異試験ではない。
- 隔離の反例は、1つのHostの版・1つのmodel・macOSの1環境で、各1回だけ行った。Agent toolのsubagentは測っていない。親sessionの権限を継承するので、P3と同じ限定はできないと判断したが、未検証である。
- 通信断は、代役で再現していない。R68のtimeoutは、代役が模したものである。
- 標本は過去の評価5件の記録だけである。記録されていない無効試行は数えていない。
