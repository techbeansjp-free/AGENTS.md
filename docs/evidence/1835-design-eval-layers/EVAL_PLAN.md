# #1835 評価計画（有料の実行の前に固定する）

開発時の検証資料であり、配布対象に含めない。通常のASC実行時に読み込ませない。

Issue：[#1835](https://github.com/techbeansjp-free/AGENTS.md/issues/1835)。ownerの決定は同Issueのコメント（2026-11-27）にある。

## 1. 層の定義

3層は1つの総合点にまとめず、層ごとに別々に報告する。

| 層 | 問い | 正解の作り方 | 言えること | 言えないこと |
| --- | --- | --- | --- | --- |
| 1 適合性の下限 | 依頼の必須情報が初期表示にあるか。axeのserious・criticalがあるか。横scrollがあるか | 機械判定（`harness/`） | 不合格は限られた範囲での反証 | 合格しても「使いやすい」とは言えない |
| 2 評価者の校正 | 評価者と評価方式が、既知の劣化を見分けるか。差の無い組に差を付けないか | 元の画面と、1か所だけを変えた劣化版の組 | 感度と再現性 | 良い案どうしの優劣、人との一致 |
| 3 人の判断 | 自然な案どうしで、どちらが依頼に合うか | ownerが条件名を伏せて一対比較する | 「ASCとしての基準」との一致 | 一般の利用者・顧客の正解 |

## 2. 対象の画面（新たな生成はしない）

- **ケース：** #1804の ui02-exhibition・ui03-dashboard・ui08-existing-ds。依頼文は#1804の`cases/`を使う。
- **層3の自然な案：** ケースごとに3画面。#1804の A-r1・D-r1・E-r1 を使う。比べる組は3組で、3ケース合わせて9組になる。
- **層2の元の画面：** A-r1。`harness/degrade.mjs`の版（定義はREADMEと`manifest.json`）のうち、次の6版を使う。
  | 版 | 強さ | 期待 |
  | --- | --- | --- |
  | `hierarchy-weak`・`hierarchy-strong`（依頼で最も重要なまとまりを1つ下・最下段へ） | 弱・強 | 層1を通る見込み |
  | `spacing-weak`・`spacing-strong`（見出しの下の余白48px・128px） | 弱・強 | 層1を通る見込み |
  | `contrast-strong`（本文のコントラスト比1.6） | 強 | 層1で検出される。天井・層1との重なりの対照 |
  | `control-attr-order`（属性の並びの反転。描画はpixelで同一） | — | 陰性対照 |
  元の画面と各版の6組×3ケース＝18組。層2の結果は、実際の層1の結果（合格・不合格）で分けて報告する（ui08の`hierarchy-strong`のように、層1を通る見込みでも不合格になる版がある）。
- **使わない版：** `inconsistency-*`（ui08では描画の崩れ、ui03では状態の表示と読まれ得て、「悪い」と言い切れない）、`contrast-weak`・`pushout`（層1で検出され、`contrast-strong`と役割が重なる）、`control-whitespace`（陰性対照は1つで足りる）。
- **描画の幅：** ui02は390×844と1440×900、ui03は800×1280（依頼文と#1815の狭幅）と1440×900、ui08は390×844と1440×900（`render.mjs`の幅の表の都合で#1804の1280から変わる）。ui02・ui08の時計（`fixedNow`）は作業者が決めた値で、依頼文に根拠は無い。
- **評価者に渡すもの：** 依頼文と、各画面の2幅のscreenshotだけ。HTMLは渡さない（劣化の箇所が推定できるため）。
- **変換できない画面：** manifestに理由を記録して除外し、残りで判定する。ケースごとに層2の組が半数未満になったら、そのケースの層2は未判定とする。

## 3. 評価者と評価方式

- **評価者：** Fable（Claude Code `claude -p --model fable`）とCodex（`codex exec`）。ownerの決定による。
  - Fableは、読取りだけのtoolと作業directoryの限定（`--restricted`）で起動する（#1815のhost-sessionの限定と同じ）。tool呼出しの記録を残し、渡した画像をすべて読んでいない呼出しは欠測とする。
  - Codexは`-s read-only`で起動する。これは読取りの範囲を限らないため、実行中は対応表（key）とownerの対応表を読めなくする（`--lock`）。実行の記録で束の外を読んだ呼出しは、隔離違反として欠測とする。Codexのmodelは、#1815段階3でownerが答えた`gpt-6.2-sol`を使う。
- **評価の軸（ownerの決定）：** 「依頼の利用者・目的に、どちらが合っているか」の1軸だけ。
- **画面ID：** 乱数で付ける。対応表は採点の後に照合する。表示順は2回の採点で変える（1回目と再採点）。
- **方式：** どの呼出しも、会話の履歴を持たない独立した呼出しにする。画面は乱数IDのscreenshotだけで渡し、file名・path・metadataから条件や版が分からないようにする。
  | 方式 | 何をするか | 呼出しの単位 |
  | --- | --- | --- |
  | D 直接の順位付け | ケースごとに、層2の6画面（元の画面と、陰性対照を除く5版）と層3の3画面を別々の群として順位付けし、組の優劣を順位の比較で決める。同順位は無いので、陰性対照の組はDから除き、Dの誤検出は測らない | ケースごとに1回 |
  | P 一対比較 | 1組の2画面を見せ、「A・B・同等」から答える。1回目と再採点で左右を入れ替え、組ごとに左右の偏りが出ないようにする | 組ごとに1回 |
  | F FLR | (1) 画面ごとに、他の画面を見せずに講評（自由文）を書かせる。(2) 別の呼出しで、講評1件だけを固定した5段階の基準文（`anchors.json`）に照らして1〜5で採点する。組の優劣は点で決め、同点は「同等」とする | 講評・採点とも画面ごとに1回 |
  | S SSR | Fの講評を、ローカルのembeddingで基準文と照らして期待値を出す。差が0.1未満なら「同等」とする。式は論文の p_r=(s_r−min s)/Σ(s_j−min s)。基準文は3組の平均 | 有料の呼出しは0回 |
- **F・Sの解釈の限定：** F・Sは画面ごとの絶対評価で、組の中の微差を直接比べる方式ではない。講評の生成の揺れも誤検出に含めて数える。
- **SSRのembedding：** `intfloat/multilingual-e5-large`（Qdrantが変換したONNX版を`fastembed` 0.9.1・`onnxruntime` 1.23.2で動かす）をローカルに取得して使う。取得は受信だけで、画面や講評は送らない。modelのsnapshotのhashを記録する。依存はscratchのvenvにだけ置く。
  - 推奨の例だった`multilingual-e5-small`から変えた。理由：このHost（macOS x86_64）では、PyTorchが2.2.2までしか入らず、`sentence-transformers`が動かなかった。fastembedが日本語に対応して用意しているe5はlargeだけだった。
  - 事前の観測：否定だけが違う文の対（「対処が必要な項目が最上部にある／ない」）のcos類似度は0.966。無関係な文（「画面全体の配色が題材に合っている」）でも0.861だった。否定の区別が弱いことは、固定の前から観測されている。
- **基準文の固定：** 基準文（`anchors.json`）は、評価対象の画面を見る前に、依頼の軸だけから書いて固定する。

## 4. 否定の反例（テキストのみ）

- 「〜が初期表示にある／ない」「対処が必要な項目が最上部にある／ない」など、否定だけが違う講評の文の対を10対、事前に書いて固定する（`negation-pairs.json`）。
- SとFの採点に通し、否定側が肯定側より低くなるかを見る。
- 有料の呼出しはFの採点だけで、テキストのみの安価なものである。

## 5. 反復と費用

- **反復：** 各方式×各評価者で2回採点する（IDと左右・表示順を変える）。Fの講評も2回とも書き直す。
- **費用の上限：** 30 USD（ownerの決定。当初は20 USDで、本番の前の試行の実測を受けて2026-11-27に変更。下の「試行の結果と上限の変更」）。Fableの、Hostが計算した値で数える。Codexは費用の報告が無いため、tokenと時間を記録して別枠とする。
- **出力の上限：** 呼出しごとの出力の長さとturnの上限を、固定の時に決める。
- **予算の守り方：**
  1. 本番の前に、Fableで各方式を1回ずつ試し（P 1組、Fの講評と採点 1画面、D 1ケース）、1回あたりの費用を測る。この試行の費用も上限に含める。
  2. 見込みが線（当初18 USD、変更後28 USD）を超える場合は、次の順に削る。
     - 採否の対象外のDを外す。
     - それでも超えるなら、層1と重なる`contrast-strong`の組を外す。
     - それでも超えるなら、本番を始めずに「予算の見込みで未判定」として止める。
     狭い幅のscreenshotと「弱」の劣化は削らない（依頼の利用環境と、採否の条件3に要るため）。
  3. 台帳の合計が上限に達したら止め、残りは未判定とする。
- **試行の結果と上限の変更（2026-11-27）：** 固定（`91e8cbd0`）の後の試行（Fable、各方式1回、計1.32 USD、4回とも有効で渡した画像をすべてRead）の1回あたりの費用は、D 0.832・P 0.228・F講評 0.212・F採点 0.045 USDだった。見込みは、全部で34.3、Dを外して29.3、Dとcontrast-strongを外して26.4 USDで、当初の規則（18 USD）では止まる。ownerの判断（「推奨どおり30USDで進めて」）により、上限を30 USD、見込みの線を28 USDに改め、2の削り方の結果として**Dとcontrast-strongの組を外して**本番を行う。Codexも同じ範囲で行う。試行で見たのは費用と読取りの記録だけで、評価の結果（回答の中身）は採否の規則の変更に使っていない。
- **Codexの本番のやり直し（2026-11-27〜28）：** 採否の規則は変えていないが、Codexの呼出しの手順を本番の途中で2回直し、Codexの P・F講評・F採点を全件やり直した。やり直さなければ、Codexは「中心の仕組みが動かなかった」で未判定となり、F・Sの結論も未判定だった。
  1. **1回目（無効）：** 共通の冒頭文がcommandの実行を禁じていたため、Codexは束の画像を開けなかった（stderrに「unable to process image」が57回。回答を「画像を見られない」と書いているかで数えると、P 47/48・F講評 44/48）。回答は、画像を見たかを確かめる範囲で読んだ。選択や点は集計も比較もしていない。この回の記録はすべて外し（scratchの`void-codex1/`）、Codex用の冒頭文（`prompts/common-head-codex.txt`：作業directoryの中を読む読取りだけのcommandを許す）と、画像を見なかった呼出しを欠測にする判定（`run-eval.mjs`の`checkCodexImagesViewed`）を加えた（e7e21240）。否定の反例は画像を使わないので、1回目の結果を使った。
  2. **2回目（途中で停止）：** 判定の正規表現が、有効な講評（画面の一部の状態について「画像からは確認できませんでした」と書いたもの）を欠測と判定しうることを、その1件の本文を読んで見つけた。実行を止めて正規表現を狭め、その文を誤判定しない試験を加えた（dd255c38）。止める前に終わっていたPの3件は外した（scratchの`void-codex2/`）。
  3. **3回目（本番）：** 2の後の道具で、P・F講評・F採点の144回を最初から実行した。既にあった`status.json`の分類を後から書き換えたものは無い。

## 6. 指標

| 指標 | 内容 |
| --- | --- |
| 層1 | 全画面の判定結果。陰性対照が元の画面と同じ結果になること |
| 層2の感度 | 劣化の種類×強さごとに、元の画面を選んだ割合 |
| 層2の誤検出 | 陰性対照の組で「同等」以外を答えた割合。Dは同順位が無いので対象外とし、その旨を記録する |
| 再現性 | 層2と層3の全組で、1回目と再採点の判断（A・B・同等）が一致した割合 |
| 層3の一致 | ownerの選択と一致した割合。ownerが「同等」「判断しない」とした組は分母から除く |
| 評価者間の一致 | FableとCodexの判断が一致した割合（方式ごと） |
| 費用 | token・時間・USD（方式・評価者ごと） |

## 7. 採否の規則（固定の後は変えない）

F・Sのそれぞれを、Pを基準に、評価者ごとに判定する。

**有効の条件：** 次のどれかに当たる評価者・方式は、その評価者について「未判定」とする。

- 分母が0、または欠測がある。
- 中心の仕組みが動かなかった（例：embeddingを取得できなかったときのS）。
- 予算で止まった。

**最低の基準（Pとは別）：** 次を満たさない方式は、その評価者について「不採用」とする。

- 層2の強い劣化（層1を通った版）で、元の画面を選んだ組が有効な組の3分の2以上。
- 再現性が0.5以上（#1807の分析規則で「採点の揺れ」とした境）。

**評価者ごとの判定：** 有効で最低の基準を満たした場合に、次の1〜4がすべて成り立てば「合格」、1つでも成り立たなければ「不合格」とする。

1. 再現性がP以上。
2. 層3の一致がP以上（同等・判断しないを除いた分母で）。
3. 層2で、強の感度が弱の感度以上であることが、全種類で成り立つ。さらに、弱の感度がP以上。どちらも、最低の基準と同じく層1を通った版だけで数える。
4. 否定の反例で失敗が0件。

**費用：** 方式ごとに、Fableについてだけ判定する。Pの2倍以内（Sは、Fの講評の費用を含める）。Codexは費用を判定しない。

**方式の結論：** この評価は、規模が9組・18組と小さい探索的なものである。そのため、結論はIssueの「採用（評価実験での補助）」を、次の意味で使う。

- **採用：** 両方の評価者が合格し、費用の条件を満たす。今回の結果だけでは評価の判定に使わない。次のデザイン評価で追加の標本により確かめるまでは、「採用候補」と記録する。
- **不採用：** 両方の評価者が、不合格か、最低の基準で不採用。
- **未判定：** それ以外。例えば、評価者で結論が分かれた、片方が未判定、費用の条件だけを満たさない、その評価者でP・F・Sの弱の感度がすべて100%で天井に達した、層3のownerの判断が無い。

**記録の仕方：** どの指標も、百分率だけでなく件数と分母を記録する。感度・一致は「1組×1回」を1件として、2回分を合わせて数える。層3は分母が最大18（1件5.6%）、層2の種類×強さは最大6（1件16.7%）である。

Dも同じ指標で記録する（現行の#1807方式の対照）が、採否の対象にはしない。この結果は統計的な差の証明ではなく、その旨を記録する。

## 8. 層3の手順（owner）

- ケースごとに3組、合わせて9組を、乱数のIDと順序で並べた比較用のページで示す。各組で「A・B・同等・判断しない」から選んでもらう。
- 条件名と、評価者の判断は見せない。
- 評価者の採点が済む前でも、後でもよい。ownerの判断は、評価者の結果を見る前に記録する。

## 9. 3層の手順を続けるかの規則

- **続ける：** 層2で、評価者または方式の間に差が出た場合。差とは、感度か再現性の差、または最低の基準で外れる評価者が見つかったことを指す。続ける場合は、`docs/evidence/shared-harness/README.md`に、この手順（本directory）への参照の段落を足す。これで、Issueの完了の基準「共通測定基盤から参照できる」を満たす。道具をshared-harnessへ移す（統合する）かは、別のIssueでownerが判断する。
- **保留：** どれも無い場合。「今回の劣化では情報が得られなかった」と記録し、劣化の設計を見直すことを条件に、続けるか保留するかをownerが決める。
- 配布物は、どの結果でも変えない。
