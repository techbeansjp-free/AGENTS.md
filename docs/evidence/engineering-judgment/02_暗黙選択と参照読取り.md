従来の回答比較は本文を指定して読ませており、自動選択を検証していなかった。今回初めて、Skill名を含めない自然文から、配布入口→正本本文→必要referenceの読取りをCodex CLIの実行ログで確認した。対象sourceは `95512507b892ca8d546ac008e27e70d2d4bc3879`。この測定で製品本文・descriptionは変更していない。

## 方法と証跡

- `codex-cli 0.164.0-alpha.11.1`、`gpt-6.1-sol`、reasoning medium、各依頼独立したephemeral session、read-only sandbox。最大2プロセス、各300秒上限。
- `/tmp`に空のGit repositoryと専用worktreeを作り、対象sourceの `node bin/asc-v05.mjs project-assets <fixture> --register-skill --apply` で14 Skillの入口と正本を配置した。fixture作成時の通常repo拒否とsandbox内のpatch準備失敗は、隔離worktreeと承認された配布実行で解消した。これらをSkill未発火として数えていない。
- 利用者configは `--ignore-user-config`、同名個人版は実行単位の `skills.config` overrideで無効化。個人ファイル・設定は変更していない。Host既定の指示や他のグローバルSkillは完全隔離していない。
- 最初の設計依頼は動作確認として単独実行、残る7依頼は期待Skill/referenceをcaseファイルへ記録してから実行した。全8依頼を各1回実施し、失敗を選別して再試行したものではない。設計依頼のpromptは完了後に同じcase一覧へ統合した。
- 生成側へ渡したのは自然文promptだけ。期待Skill名や読取り合格条件は渡していない。
- `item.completed` のcommand、exit=0、aggregated_output内の対象ファイル全文を照合した。使用宣言だけでは合格にしない。各sessionの `turn.completed` も確認。空repoに対する `rg` のexit=1は検索一致なしであり、Skill読取り失敗ではない。
- [依頼](routing/cases.json)、[集計](routing/results.json)、[配布済みファイルhash](routing/installed-sha256.json)、各case名のJSONLに実行証跡を保存。JSONLのfixture絶対パスのみ `<FIXTURE>` に正規化している。設計smokeの壁時計時間は未記録、残る7件は5.28〜72.84秒。各turnのtoken使用量は集計に保持し、課金額とは解釈しない。
- 独立ContextのReviewerがraw traceを読み、読取り完了・実内容・製品sourceとのbyte一致・負例のコマンド未実行を確認した。

## 再実行

対象sourceの配布コマンドで空の専用worktreeへ登録後、[reproduce.py](routing/reproduce.py)を実行する。Codexの既存認証を使用し、認証情報をfixtureへコピーしない。ネットワークとプロセス実行は環境の承認条件に従う。

```sh
python3 docs/evidence/engineering-judgment/routing/reproduce.py \
  --fixture /absolute/path/to/isolated-worktree \
  --output /tmp/asc-routing-rerun \
  --disable-skill /absolute/path/to/personal/engineering-judgment/SKILL.md
```

再実行scriptはログを取得するだけで自動採点しない。結果は実ファイルの内容とcommand出力を照合する。期限超過・実行エラー・turn未完了は欠測として記録し、負例の成功にしない。

## 限界と残件

これは単一CLI版・単一モデル・空fixture・各1回の疎通観測である。全14 Skill、曖昧な境界依頼、複数回のばらつき、個人版との共存、IDE固有context、Claudeは未検証。本文を読めたことは意味的に適用できたことや回答品質の保証ではない。画面受入も計画依頼であり実ブラウザー操作の成功を意味しない。「発火率100%」「常に適切に読まれる」とは主張しない。

PR #1634のCIではHost・Linux・worktree検査は成功したが、base validatorによる品質契約事前登録検査が失敗した。`package.json`全体が保護対象であり、配布filesへの3件追加にもbase側のversioned staged proposalが必要になる。この読取り検証によってCI失敗が解消されたとは扱わない。保護を緩めず、事前登録と承認の順序を満たすまでPRはDraftで維持する。
