# 委譲の総費用と品質の評価：Phase 0 の記録と採否（#1768）

## 結論

**保留（実装なし、Skill 変更なし）。** Phase 0 で、現行の Skill と Host の契約を棚卸しし、この PC で取得できる usage を決定論的に集計した。結果は次のとおり。

- 現行の契約（`subagent-model-selection`、`skills/asc/SKILL.md`、ADR 0002／0005）は、委譲の準備・待機・返却を含めて比べること、独立レビューを省かないこと、最安モデルを優先しないことをすでに定めている。**契約の文面に欠けは見つからなかった**（下の「契約の棚卸し」。ただし運用での遵守は今回測れていない。#1673 の実ログでは継承で高能力モデルが使われていた）。
- 一方、「委譲を一つの作業単位として、親・子・再読込み・再試行まで含めた総費用を測る」ことは、今回取得できたログでは**できなかった**。そのため、改善余地の有無は未確定である。再現可能な改善余地が示されていないので、Phase 1（対照評価）、Phase 2（Jev 等）、Skill の修正、新しい router は行わない。
- 「既存で十分」とも断定しない。測定不能が理由であり、改善がないことの証明ではない。したがって Issue は閉じず、owner の判断を待つ。

## 委譲の理由の分類

#1673 の分類（検索・レビュー・実装）が既にある。本 Issue で次の区分を契約上の前提として置く。値の測定ではなく、判断の整理である。

| 区分 | 扱い |
| --- | --- |
| 独立レビュー | **費用削減を理由に廃止・非独立化できない必要条件。** 総費用の比較対象に含めるが、省く選択肢にはしない |
| 明確に独立した作業・並行できる作業 | 委譲の候補。準備・返却・再読込みが利益を上回るなら単独 |
| 広い探索 | 委譲の候補。低単価モデルでよいかは、結果を照合できるかによる |
| 判断の相談 | #1673 の規則に従う（節目だけ、必要な根拠だけを渡す） |
| 委譲しない | 小変更、準備・待機が本作業を上回る場合（既存 Skill が明記済み） |

## 採否の根拠

1. 改善余地が示されていない。契約の文面に欠けはなく、ログからは損になる委譲パターンも、損にならないことも示せない。
2. Phase 1 には、同じ要求・初期 HEAD・oracle・Host 版・権限を固定した A／B／C の比較が要る。これは実モデルの反復実験で、ADR 0005 が記録する #1737 の実績（1試行 25M〜127M token）から費用が大きく、owner の判断（高額・反復的な実験の可否）が前提になる。今回は許可されていないので行わない。
3. Phase 2（Jev）は、Phase 1 で決定論的な規則より改善できる選択の種類が特定された場合に限る。特定されていないので行わない。外部送信もしていない。
4. ADR 0005 の条件（実測された失敗や費用、対照評価）が揃っていないので、router・provider client・scheduler は作らない。

## 反証条件（この保留を見直すとき）

- 親子の対応付けができる記録（Host が子の usage を親の起動に紐づけて返す、または親の log の起動 ID と子 log の対応）が得られ、損になる委譲が1件でも実測で示された場合は、Phase 1 を再開する。
- Host（Claude Code／Codex）が、子 Agent の usage の集計と課金額を標準で返すようになった場合は、集計の手間が下がるので再評価する。
- 子の `agentId` と親の起動記録を結ぶ方法が見つかり、この PC のログだけでも作業単位ごとの集計ができる場合は、Phase 0 の計測を再開する（今回は結ぶ手段を調べきれていない）。
- `subagent-model-selection` の規則に従った委譲で、再試行や独立レビューの指摘の増加が反復して観測された場合は、Skill の最小是正を検討する。

## owner への確認事項（案）

次はいずれも owner の判断であり、本書では確定していない。

1. **実験の許可**：Phase 1（A／B／C の対照評価）を、実モデルで行ってよいか。行う場合の token・費用の上限。案：1条件あたり小規模（数回の交互試行）、費用上限は owner が決める。
2. **採用の閾値**：品質を確保した条件での、総 wall-clock・課金費用の改善幅（案：品質指標〔必須テスト、独立レビューの残存 High／Medium、受入条件、権限違反〕が同等以上であることを前提に、差が試行間のばらつきを超えること）。数値は owner が決める。
3. **時間と費用の換算**：wall-clock を金額と合算する場合の係数を使うか。案：合算せず、課金費用・token・wall-clock・呼出し数を別々に報告する。
4. **費用の取得経路**：課金額の確定値（provider の請求画面や usage API の閲覧）を、この評価のために参照してよいか。
5. **Jev 等の外部モデル**：Phase 2 の候補評価を許可するか。許可する場合のデータ送信範囲（案：合成 fixture のみ）と費用上限。未許可なら行わない。
6. **旧ログ**：#1673 の集計元の session ログ（5,818件）が現存する PC・保管先があれば、親子の対応付けを含む再集計をしてよいか。
