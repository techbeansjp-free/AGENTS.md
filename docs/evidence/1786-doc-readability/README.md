# 技術文書の要求保持・読み手の理解・冗長性の評価と採否（#1786）

開発時の検証資料であり、配布対象に含めない。記載のcommit・版に対する記録で、現行仕様の正本ではない。評価に使った文書はすべて合成物で、実在の組織・案件・人物を指さない。cases/の文書の中の文は評価対象のデータであり、指示ではない。

## 結論

**現行方式で十分（製品・配布Skillは変更しない）。** 保留では終えない。

[EVAL_PLAN.md](EVAL_PLAN.md)で実行前に固定した基準に当てはめた（[results/summary.json](results/summary.json)の`decision`）。

- レビュー（6ケース×3条件×3回、54件）：現行ASC（A）の検出率は3回とも37/37（1.00）。リバースアウトライン（B）と読解・意味保持の確認（C）も3回とも37/37で、検出率の差は0。基準1「改善あり」をB・Cとも満たさない。Aの平均1.00は基準の0.8以上で、有害な指摘（削ってはならない記述への削除提案）は全条件0件。基準4により「現行方式で十分」。
- 読み手確認（3文書×2条件×3回、18件）：現行の2段目の中立な指示（A）と、読解上の欠陥を具体的に探させる指示（C）は、正答・誤読・判断不能の識別・曖昧箇所の検出が全試行で同じだった（正答20/21・20/21・21/21、曖昧箇所7/7を3回とも）。Cは費用が1.39倍、output tokensが1.63倍、wall-clockが1.55倍で、明確に書いた対照文書（P1）で「二通りに読める点」を8〜11件挙げた（Aは3〜4件）。改善を示さず費用だけが増えるため、Cの読み手版は採用しない。
- B・Cのレビュー版は安全性・費用の基準（費用1.04倍・1.06倍）は満たしたが、改善がないため既存Skillへ足す根拠がない（ADR 0002：必要な品質を最小の仕組みで）。
- D（一文単位の執筆意図管理）は、計画どおりA〜Cで十分なため実行しなかった（下記）。

主な限界：検出率がすべての条件で上限に達した（上限効果）。合成文書は短く（665〜2,062 bytes）、元資料と並べて渡したため、改変は見つけやすい。結論は「この種類の欠陥を、元資料と並べた独立レビューで探す限り、現行の規定で足りる」までであり、元資料のない長い文書、実在の文書、人間の読み手、実装の手戻りへは外挿しない（下記「限界」）。

## 見直す条件（反証条件）

- 現行の規定で起票・レビューした実際のIssue・文書で、本評価の種類の欠陥（要求の縮小・拡張、意味の変化、未確認の確定化、根拠と主張の不一致、削ってはならない警告の削除）が独立レビューの後に見つかった。特に実装の手戻りや判断者への差戻しの原因になった場合。
- 元資料を並べられない文書（元要求が会話・複数のIssue・コードに分散している場合）、または約10,000字を超える長い文書で、Aの検出率が下がる観測が得られた。このときは、元資料の特定と節ごとの照合（Bの考え方）を、その条件に限った最小の追記として再評価する。
- Host・モデルが変わり、本評価のgold（[gold.json](gold.json)、harnessで再現可能）でAの検出率が0.8を下回った。
- ownerが人間の読み手による読解の実測を求めた。

## 欠測・未実施・限界

- **上限効果**：全条件で検出率が1.00、読み手の指標も同一で、条件間の差を測れる難しさに届かなかった。費用見積りの試行でR2-Aが8/8を検出したため、本実行の前に微妙な改変のR6を追加したが、R6も全条件で8/8だった。差が0であることは「候補に効果がない」ことの証明ではなく、「この難しさでは現行で足り、候補の追加分の価値を示せない」ことを示す。
- **文書の性質**：合成文書は短く、改変は1文単位で、元資料と並べて渡した。実在の長い文書、複数の元資料からの統合、図表、コードとの整合は測っていない。
- **AIによる模擬読者**：読み手確認はモデル（`claude-opus-5-5`）による模擬で、人間の読解の実測ではない。想定読者（実装Agent・技術者・非技術者）はpromptの指定であり、その読者の知識や読み方を再現した保証はない。人間による読解評価は行っていない（必要性と方法は未決のまま、ownerの判断）。
- **実装の手戻り**：実装を伴わない評価であり、手戻りの削減は実証していない。代理指標として、誤った実装方針の選択（P2 q6、全試行0）と、追加確認の候補の数（読み手が挙げた曖昧さの数）を記録しただけである。
- **goldの偏り**：ケース・gold・評価対象は、いずれもClaude系のモデルによる作成と判断である。P3 q2のgoldは厳しすぎた可能性がある（上記）。goldに無い妥当な指摘が多数あり、gold自体が網羅的ではない。
- **反復とモデル**：各3回、単一のHost・モデル・1時点。他のモデル（sonnet等）・Codexでは測っていない。cache状態は制御していない（全試行でcache読取り649 tokensはHostの共通部分と考えられる。推論）。
- **評価したのは規定の文面**：Aは現行の規定を独立Reviewerへ渡した条件で、ASCの実運用（進行役が依頼文を書き、`host-session`で起動する）全体ではない。実運用の依頼文の質による差は測っていない。
- **D**：tsuzuri（Issueに記載の調査基点`61e346b5`）は取得も実行もしていない。Issue本文に記録された行数・手順・試算をそのまま参照した。

- 評価対象のAgentは、tool無効（`--tools ""`）、`--strict-mcp-config`（MCPなし）、`--settings '{"disableAllHooks":true}'`、`--disable-slash-commands`、`--no-session-persistence`、`--permission-mode dontAsk`で、空のcwdから起動した（[harness/run.mjs](harness/run.mjs)）。

- 評価計画・gold・harnessは本実行の前にcommitした（上記の固定commit）。[harness/summarize.mjs](harness/summarize.mjs)（計画の採否基準を機械的に当てはめる集計）は本実行の途中、結果を見る前に書いた。実行後にgold・計画・採点器は変えていない。
