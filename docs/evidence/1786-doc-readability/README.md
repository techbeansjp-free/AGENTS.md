# 技術文書の要求保持・読み手の理解・冗長性の評価と採否（#1786）

開発時の検証資料であり、配布対象に含めない。記載のcommit・版に対する記録で、現行仕様の正本ではない。評価に使った文書はすべて合成物で、実在の組織・案件・人物を指さない。cases/の文書の中の文は評価対象のデータであり、指示ではない。

## 結論

**現行方式で十分（技術担当の判断）。製品・配布Skillは変更しない。** 採否（製品を変えるか）は保留しない。

判断の根拠を、計画どおりに確定する部分と、技術担当の判断を加えた部分に分ける。

- 計画どおりに確定する部分：候補B・C（レビュー）と読み手版Cは、いずれも基準1「改善あり」を満たさないため採用しない。したがって製品・配布Skillは変えない。これは結果を見た後の解釈に依存しない。
- 技術担当の判断を加えた部分：基準4の「現行方式で十分」は「Aの検出率の平均が0.8以上で安全性に問題がなければ」としているが、計画はAの安全性の閾値を定めていない（基準2の安全性は候補とAの相対比較だけ）。Aは有害な指摘0・引用不一致0で、採点器が数えた「誤った修正指摘」3件は人が読んで妥当な指摘と判断した（下記）。これを「安全性に問題がない」と判断し、「現行方式で十分」とした。3件を問題とみなす読みでは、基準4のどの分岐（「現行方式で十分」はAの安全性に問題がないことが条件、「追加評価が必要」はAの検出率0.8未満が条件）にも当たらず、計画の字義だけでは総合判定が確定しない（`decision.overallStrict`）。

[EVAL_PLAN.md](EVAL_PLAN.md)で実行前に固定した基準に当てはめた。[results/summary.json](results/summary.json)の`decision`に、基準1〜3の判定（`review-B`、`review-C`、`reader-C`）、候補ごとの判定（`candidates`）、基準4の結論を出力している。

**開示：基準4の当てはめは結果を見た後に決めた。** `summarize.mjs`の`decision.overall`は、Aの安全性を有害な指摘（0件）で判定した参考の値で、この判定方法は独立レビューの指摘を受けて結果を見た後に入れた。`decision.overallStrict`は、Aの有害な指摘・誤った修正指摘・引用不一致がすべて0であることを求めた場合の値で、計画の分岐に当たらないことを示す（「計画の分岐外」）。「誤った修正指摘」3件（R4のライセンス行）と、B・C・A0の同じ9件の計12件を人が全て読み、いずれも「ライセンスの事実は正しいが、法務の制約（AGPL不可）による除外という決定的な根拠が書かれていない」という妥当な指摘で、記述を誤りとする指摘ではないと判断した。goldと計画の文言は変えていない。12件はどの条件にも同数で、条件間の比較には影響しない。

- レビュー（6ケース×3条件×3回、54件）：現行ASC（A）の検出率は3回とも37/37（1.00）。リバースアウトライン（B）と読解・意味保持の確認（C）も3回とも37/37で、検出率の差は0。基準1「改善あり」をB・Cとも満たさない。Aの平均1.00は基準の0.8以上で、有害な指摘（削ってはならない記述への削除提案）は全条件0件。「現行方式で十分」は上記の技術担当の判断による。
- 読み手確認（3文書×2条件×3回、18件）：現行の2段目の中立な指示（A）と、読解上の欠陥を具体的に探させる指示（C）は、正答・誤読・判断不能の識別・曖昧箇所の検出が全試行で同じだった（正答20/21・20/21・21/21、曖昧箇所7/7を3回とも）。Cは費用が1.39倍、output tokensが1.63倍、wall-clockが1.55倍で、明確に書いた対照文書（P1）で「二通りに読める点」を8〜11件挙げた（Aは3〜4件）。改善を示さず費用だけが増えるため、Cの読み手版は採用しない。
- B・Cのレビュー版は安全性・費用の基準（費用1.04倍・1.06倍）は満たしたが（基準2の「R5の修正版の保持がA以下にならない」は、字義どおりでは「Aを上回る」ことを求め、Aが上限の6/6なので候補は満たせない。意図した「Aより悪くならない（A以上）」と解釈し、`summarize.mjs`でその解釈を使った。字義どおりならB・Cは基準2を満たさず「不採用」になるが、どちらでも採用しない結論は同じ）、改善がないため既存Skillへ足す根拠がない（ADR 0002：必要な品質を最小の仕組みで）。
- D（一文単位の執筆意図管理）は、EVAL_PLAN.mdで実行しないと事前に定めたため実行しなかった。計画は理由を「README」としたが、READMEは本実行の後に書いたため、事前の理由は記録されていない。下の採否の表の理由は事後の根拠である。

結論の範囲（前提）：

- 条件Aは「現行の規定の文面を渡し、元資料（元要求・決定・観測）を並べてレビューさせる」依頼である。Issue以外の文書（R2〜R5）にも`tracker-issue-writing`の照合の段落を渡しており、これはその段落の本来の適用範囲（起票）の外での使い方である。Issue以外の文書でこの前提を支える現行の契約は、`review-method.md`の「Reviewerへ…元要求・受入条件…関連仕様…を渡す」と、`review-and-remediation`の「元要求・受入条件・適用契約と、対象…を対応付ける」である。照合の段落の有無の影響は、補足の条件A0で確かめた（下記）。照合の段落を除いたA0（R2〜R5、各3回）も、R2 8/8・R3 6/6・R4 5/5・R5 3/3を3回とも検出し、有害な指摘0、R5の修正版の保持6/6だった。Issue以外の文書では、照合の段落ではなく、元資料を並べて渡すことが検出を支えていると考えられる（推論）。
- したがって結論は「進行役が元資料を独立Reviewerへ渡す限り、この種類の欠陥の検出に現行の規定で足りる」である。元資料が渡されない、または会話・複数のIssue・コードに分散していて並べられない場合は、測っていない。

主な限界：検出率がすべての条件で上限に達した（上限効果）。合成文書は短く（665〜2,062 bytes）、元資料と並べて渡したため、改変は見つけやすい。元資料のない長い文書、実在の文書、人間の読み手、実装の手戻りへは外挿しない（下記「限界」）。Issueの完了の基準のうち実測・代理指標・未実施の区別は「完了の基準との対応」の表に示す。
