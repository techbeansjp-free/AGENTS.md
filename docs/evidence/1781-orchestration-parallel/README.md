# 高能力モデルの統括と並列実行の評価（#1781）

## 結論

**既存 Skill の限定改善（採用）。** `skills/subagent-model-selection/SKILL.md` に1段落を追加した。新しい runtime・router・scheduler は作らない。保留では終えない。

判定は、測定の前に固定した [EVAL_PLAN.md](EVAL_PLAN.md) の規則による。Host は Claude Code 2.1.323、親は全条件で `claude-opus-5-5`。課題は3つ（P1・P2・P3）、条件は5つ（A〜E）、各3回で計36件、全件で独立レビューを行った。

- **E（opus 親が sonnet の子を並列に起動）だけが、現行（A）より良い条件に当たった。** P1（独立3単位）の時間は E が 103〜107秒、A が 120〜160秒で、範囲が重ならない。費用は E が 0.363〜0.454 USD、A が 0.406〜0.475 USD で、範囲が重なる（同程度）。P2（依存を含む）は「差が不明」で、「損」ではない。P3（1単位を書込み不可にした失敗注入）は3回とも合格した。品質は全件 oracle 合格、独立レビューの High は0件だった。
- **A は、ASC の抜粋（並行を検討する、モデルを明示する）を与えても、6回とも委譲しなかった。** 現行の文面だけでは E の構成は起きない。規則1（限定改善）の条件をすべて満たした。
- **変更した文面の受入確認（A2、6件）にも合格した。** P1 で3回中2回、親が sonnet の子3つを1メッセージで同時に起動した。P2 では3回とも自分で行った（依存を含む Goal で、文面の除外条件どおり）。費用・時間とも A に対して「損」はなく、oracle は全件合格、High は0件。
- **効果を分けると、時間を縮めたのは並列化で、費用を下げたのはモデル分離だった。** モデル分離（C 対 B、E 対 D）は P1・P2・P3 のすべてで「改善あり（費用）」。並列化（D 対 B、E 対 C）は、時間の範囲が重ならずに短い組（P1）もあったが、費用の最大が基準を上回るため、規則上は「差が不明」。同じ opus を子に使う B・D は費用が A のほぼ2倍で「損」。sonnet の子でも1つずつ動かす C は、P2 で時間の「損」。
- **限界：** 小さな合成 fixture、n=3、1時点、親は opus だけ。同じ機械で他の作業（load average 7〜537）が並行していた。時間の改善幅は約13秒以上と小さく、大きな repo・長い作業・他のモデル組へ外挿しない。Fable は使っていない。Claude Code Projects は CLI から使えず cloud session が要るため、測っていない。

## 採用した変更

`skills/subagent-model-selection/SKILL.md`「仕事に必要な能力を選ぶ」の末尾に、次の1段落を追加した。

> 仕様と検証手段が単位ごとに確定し、書込み先が分かれた実装単位が3つ以上あるGoalで委譲が許可されている場合は、進行役は実装を抱えず、依存しない単位ごとのサブエージェントを1回の指示で同時に起動し、実装には成果物と検証で照合できる範囲で親より低費用のモデルを明示する。共有契約に依存する単位は、契約の単位が検証を通ってから起動する。進行役は全体の検証と統合後の受入を自分で行う。#1781の評価では、この構成が単独の実行より所要時間を短くし、費用は同程度だった。子に親と同じ高能力モデルを使うと費用が増え、1つずつの委譲は時間が延びた。単位が少ない、または小さい作業には適用せず、自分で行う。

- 根拠：E の P1 の「改善あり（時間）」、P2・P3 で損や失敗がないこと、A が自発的にこの構成を選ばないこと、モデル分離が費用を下げること（C 対 B、E 対 D）。
- 受入条件と結果：[EVAL_PLAN.md の追補](EVAL_PLAN.md#追補限定改善の受入確認36件の判定の後a2-の実行の前に固定)で固定した3条件をすべて満たした（下の「A2」）。
- 変えないこと：委譲の許可（この段落は許可を与えない）、独立レビューの Context 分離、Fable・Astra の明示許可の契約、モデル名を品質の証拠にしない規則、小変更は単独で行う規則、#1768 の結論（小さい単一の委譲は損）。ASC 本体・`work-coordination`・ADR は変えていない。

公式文書（Claude Code docs の `claude-projects`・`sub-agents`・`headless`・`agent-view`・`agent-teams`・`worktrees`・`cost-tracking`・`cli-reference`）を確認した。

| --- | --- | --- |
| Claude Code Projects（public beta） | 1つの coordinator 会話がタスクごとに thread（主に cloud session）を起こし並列に進め、結果を検証する。Coordinator と Threads のモデルを別々に設定できる（既定は両方 Opus、thread は effort medium） | Web・desktop・mobile の機能で CLI の起動手段がなく、thread は cloud session を要する。Pro／Max／Ultra 向けで Team・Enterprise は対象外。本評価は外部送信を行わない条件のため測っていない。CLI で同じ「統括＋役割別モデル＋並列」を再現できる Agent tool で代替した |

結論：講演の運用（高能力モデルが統括し、別モデルの実装 thread を並列に動かす）は、Host の標準機能（Projects、または Agent tool のモデル指定と同時起動）だけで実現できる。ASC 側に runtime・scheduler・router を足す必要はない（ADR 0005 の「汎用の Subagent runtime は Host の責務」と一致）。

## 対照評価の設計（要約）

詳細は [EVAL_PLAN.md](EVAL_PLAN.md)。課題は #1768 で不足していた条件から選んだ。小規模変更と単一の複数ファイル変更は #1768 で評価済みのため再実験していない。

- P1：独立した3単位（`csv`・`duration`・`semver`）を仕様書から実装し、単位ごとに test を追加する。
- P2：共有契約 `money` と、それに依存する3単位（`invoice`・`split`・`report`）。
- P3：P1 と同じで、`duration` の file と directory を書込み不可にした。特定の子の失敗を環境要因で起こし、依存しない作業が続くかを見る。
- 条件：A＝現行 ASC の通常実行（親が選ぶ）、B＝opus 子の逐次、C＝sonnet 子の逐次、D＝opus 子の並列、E＝sonnet 子の並列。B〜E では親は実装せず、子の後に自分で test を実行し、失敗した単位は1回だけ新しい子へ差し戻す。全条件で同じ ASC の抜粋を system prompt に足した。
- 品質：隠し oracle（参照実装で全件合格を確認済み）と、session 自身の test 一式。独立レビューは条件を知らせない新しい Context（`host-session`、`--tools Read,Glob,Grep`、sonnet）で全件に行った。
- 実行：36件を直列に、反復ごとに条件を回す順序で実行した。費用は Host の `total_cost_usd`（client 側の推定で請求額ではない）、時間は wall-clock。時間と費用は合算しない。

### 読み取れること

- **品質**：42件すべてが oracle に合格した。隠し test の失敗は0件（P3 の `duration` は書込み不可にした単位で、失敗が期待どおり）。独立レビューの High は0件。Medium は P2 に多い。`money` の小数 ratio や半端な丸めでの浮動小数点の扱いの指摘が主で、A も含めて全条件に出た（P2 の Medium 合計：A 6、B 4、C 3、D 4、E 3、A2 5）。oracle の範囲外の弱点で、条件による差は見られない。
- **A の選択**：A は6回とも委譲しなかった。ASC の原則3（並行を検討する）とモデル選択の規則を与えても、この大きさの課題では親が自分で実装した。

## 採否の根拠（規則の当てはめ）

1. 品質の必要条件：A〜E の全セルが oracle 3/3 合格、High は全条件で0。
2. E は P1 で A に対し「改善あり（時間）」、P2 で「差が不明」（損でない）、P3 で3/3 合格。A はこの構成を0/6回しか選ばなかった。これは規則1（既存 Skill の限定改善）に当たる。
3. B・C・D は、P1 か P2 の少なくとも一方で A に対し「損」だった。そのため、規則2（不採用）の「B〜E のすべてが損」には当たらない。
4. 規則1により、課題種別に限った短い規則を、既存のモデル選択 Skill へ最小差分で加えた。受入確認（A2）の3条件を満たしたので、変更を採用した。
5. Host 標準機能（Agent tool のモデル指定と同時起動）だけで実現でき、新規実装は不要（ADR 0005 の例外条件の検討に進まない）。

## 反証条件（この採用を見直すとき）

- 大きな実 repo・長い作業・単位が4つを超える Goal で、この構成が単独の実行より時間で劣るか、費用で「損」になる反復観測が得られた場合。その場合は段落を取り消すか、適用条件を狭める。
- この段落に従った委譲で、独立レビューの High、統合の競合、差し戻しの増加が反復して観測された場合。
- 子のモデルの費用・能力の関係が変わり、親と同じモデルの子でも費用が増えない場合や、低費用のモデルで oracle の合格率が下がる場合。この段落はモデル名を固定していないが、根拠の数値は改める。
- A2 の受入確認では、P1 の1回（3回中）で親が「各単位が小さい」と判断して自分で実装した。除外条件の解釈が揺れるため、利用者の Goal で構成が起きない反復が観測された場合は、条件の書き方を見直す。
- Host が Projects 等で、統括と並列実行のモデル分離を CLI でも標準で提供した場合は、Skill の段落をその手段の参照に置き換える。

## 隔離の確認（測定の前と途中）

測定の前に反例 probe（`PROBE`、sonnet 親・haiku 子）で確かめた。目印 file は fixture 外に置いた乱数の token で、probe の後に session log と run の出力全体を grep して token が現れないことも確かめた。

| 確認 | 結果 |
| --- | --- |
| Read・Glob・Grep で fixture 外の目印を読む | 拒否（`--restricted` の作業 directory 制限）。子 Agent も拒否 |
| Write で fixture 外へ書く | 拒否。子 Agent も拒否 |
| Bash で `cat <目印>`、`node -e` | 拒否（dontAsk） |
| test wrapper 内の test code から目印を読む・`/w` へ書く・`1.1.1.1:443` へ接続 | `ENOENT`（mount していない）・`EROFS`・`ENETUNREACH` |

測定の途中で、wrapper 以外の Bash（`ls`・`cat`・`head`・`find`・`grep` 等）が実行されていることに気づいた。Claude Code は dontAsk でも、作業 directory 内の読取り専用の command を自動で許可する。そこで2つ目の反例 probe（`PROBE2`）で、fixture 外の目印への `cat`（相対 path を含む）・`head`・`ls`・`grep -r`・`find`・`cd && wc`、fixture 外への `touch`・リダイレクト書込み、`curl`・`git ls-remote`（127.0.0.1 宛て）、`python3`、fixture 内へのリダイレクト書込みを試した。すべて拒否され、許可されたのは `node --version` だけだった。子 Agent も同じだった。36件の全 session log を [harness/bash-audit.mjs](harness/bash-audit.mjs) で監査した結果、wrapper 以外で実行された Bash は30件ですべて読取り専用（`cat`・`ls`・`head`・`find`・`grep`・`sed`・`echo` の組合せ）、fixture 外の path を指すものは0件、拒否されたものは10件だった。隔離の合格条件（fixture 外を読めない・書けない、外部 network なし）は満たしたと判断し、結果を使う。全条件に同じ Host の振る舞いが適用されるため、条件間の比較の公平性も保たれる。計画の「Bash は wrapper 1つだけ」は、読取り専用 command の自動許可の分だけ実際より狭く書いていた（記録の訂正）。

## harness の不具合と再実行（記録）

- pilot（P1-D、判定に使わない）で、session log の1つの tool 呼出しが streaming で複数行に記録され、Agent 起動数を二重に数える不具合を見つけ、tool の id で重複を除いた（commit `498bcab`）。
- 測定の6件目（P2-A-1）の採点で、P2 に存在しない `duration` の file を読んで harness が落ち、Host の出力（費用・時間）を保存できなかった。採点の前に Host の生出力を保存するよう直し（commit `adab7be`）、P2-A-1 を再実行した。同時に実行中だった P2-B-1 は停止して再実行した。落ちた P2-A-1 と停止した P2-B-1 の費用は欠測（36件の集計に含めない）。試行の失敗ではなく harness の失敗なので、計画の「失敗は再実行しない」には当たらないと判断した。
- 2つ目の隔離 probe の追加（commit `2f7b25c`）は probe の分岐だけを変え、測定条件は変えていない（差分で確認）。
- 採否の規則と課題・条件・oracle は、測定の開始後に変えていない。

## 限界

- 合成 fixture の小さな課題（1単位あたり数十行）で、n=3、1時点、親は opus だけ、子は opus と sonnet だけ。haiku の子・sonnet の親・Fable は評価していない（haiku の子は #1768 で評価済み）。
- 時間の改善は P1 の約13秒以上（範囲の端どうしの差）で、P2 では観測されなかった。大きな repo・長い作業・単位の多い Goal へ外挿しない。
- 同じ機械で他の Issue の評価が並行し、load average は 7〜537 と大きく変動した。条件を反復ごとに回したため、偏りは条件間に分散するが、取り除けてはいない。時間は主に API の待ち時間で決まった（子を使わない A と逐次の B では、Host の `duration_api_ms` が wall-clock の約8〜9割。並列の条件では子の API 時間が重なるため、wall-clock を上回る）。
- 費用は Host の推定（`total_cost_usd`）で、請求額ではない。cache の状態は制御していない。
- A2 は36件より後の時点に実行した。受入確認は「損にならない」ことと、文面がその構成を引き出すことの確認にとどめた。36件の判定は置き換えていない。
- 独立レビューは sonnet の1系統で、指摘の真偽を個別には検証していない。品質の主な根拠は oracle である。
- 失敗の注入は書込み不可の環境要因だけで、子の process の停止は試していない。
