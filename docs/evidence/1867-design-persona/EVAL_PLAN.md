## 判定

設定は`config/`の下に置き、計画とともに固定する（`config/decision-criteria.md`の冒頭の一覧。`conditions.json`の`fixedExtra`で`fixation.mjs`の対象に入れる）：生成（`cases.json`・`conditions.json`・`release.json`・`run-order.json`）、門の数え（`config/layers/gate-count.json`・`gate-count-prompt.md`）、層1（`config/layers/layer1-cases.json`・`layer1-gold.json`）、層2・層3（`config/layers/eval.json`）。

1. **工程が使われたか（門）：** Sの試行で、`design-creation`の`SKILL.md`が読まれ、デザインの記録に利用者の像（根拠と仮説の区別つき）と、判断と利用者の対応がある試行を数える。ケースごとに3回中2回以上なら、そのケースは判定できる。判定できるケースが3未満なら、全体を「未判定」とする。
   - 記録の中身は、次の2つが両方ある場合に「ある」と数える。(a) 利用者の像があり、その項目の**すべて**に根拠（出典）か仮説かが付いている。(b) デザインの判断のうち3つ以上に、どの利用者のどの要求・状況から選んだかが書かれている。
   - 数えるのは、会話を引き継がない新しいcontextとする。modelは`opus`、Hostは`asc host-session claude`（読取りのみ：Read・Glob・Grep、起動先を束のdirectoryに閉じる）。promptは`config/layers/gate-count-prompt.md`で固定する。
   - 入力は24試行（B・S）のデザインの記録（`out/DESIGN-NOTES.md`）だけとし、画面は渡さない。条件名・ケース名・試行名を伏せ、乱数のIDと順序で渡す（`harness/gate-packet.mjs pack`、回ごとにseedを変える）。記録の本文は変えないので、Sの記録に工程の名前（「確認の時点」等）やSkill名が出れば条件が分かる。伏せ方は完全にはできない。
   - 出力は、試行ごとに(a)・(b)の可否と、該当する箇所の引用とする（promptの形）。
   - 独立に2回数える（別のcontext、別のseed）。(a)・(b)それぞれ、2回とも「ある」なら「ある」とし、割れたら「無い」とする。回答の無い回・読めない回は「無い」とする（回答が無いときだけ、新しいcontextで1回やり直してよい）。まとめは`harness/gate-packet.mjs combine`で行う。
   - Bの結果は報告だけに使う。数えた結果（IDごとの可否と引用）は、層3のownerの回答と層2の結果を開く前にcommitする。IDと試行の対応表は、ownerの回答の記録をcommitした後に開く。
   - 機械の部分（`SKILL.md`のRead）は共通の仕組みが数える（`decision-criteria.md`）。Skill toolで`design-creation`を呼んでも、読み込まれるのはClaude Codeの薄い入口（本文を読むよう指示する数行）だけで、本文は読み込まれない（導入した`.claude/skills/design-creation/SKILL.md`で確かめた）。そのため、Skill toolの呼出しは本文の読込みに数えない（#1815・#1840と同じ）。
2. **層1（機械の判定）：** #1835の層1の道具（`run-layer1.mjs layer1`、`--cases config/layers/layer1-cases.json --gold-add config/layers/layer1-gold.json`）で、全24試行の元の画面を両幅で判定する。画面は`harness/layer-pages.mjs`が生の記録から並べる（記録のfileは写さない）。
   - 数える単位は**試行**（ケース・条件ごとに3回中の数）。項目は#1835の4つ（`answerInitialView`・`noOverflowX`・`axeNoSeriousCritical`・`noExternalRequests`。どれも両幅で合格が条件）。
   - 記録するもの：ケースごとに、層1の不合格（どれかの項目が不合格、または測れなかった）の試行の数をS・Bで数え、SがBより多いケースを記録する（判定には使わない）。
   - **害：** `axeNoSeriousCritical`が不合格の試行の数（3回中）を、ケースごとにS・Bで数える。SがBより多いケースが2つ以上なら「不採用」とする。測れなかった試行は不合格として数える。
   - lp-newの設定：幅はui02と同じ（狭幅390×844、広幅1440×900）。初期表示の項目は、サービス名「ひだまりスマホ相談」と、電話（`tel:`のリンク）か申込み（`#apply`へのリンク）のどちらか（依頼の目的：申し込みか問合せ）。必須項目（`layer1-gold.json`、記録だけ）は依頼文の「このページに必ず載せる」の項目。時計は2027-03-01。
3. **層3（ownerの盲検の比較）：** ケースごとに、Sの3回×Bの3回の9組、計36組をownerが比べる（`config/layers/eval.json`の`layer3.pairs`）。手順は#1852と同じ：
   - #1835の`owner-page.mjs --config config/layers/eval.json --seed 18670003`で、1枚のローカルHTMLを作る。見せるのは各画面の狭幅・広幅のscreenshotと依頼文だけで、`DESIGN-NOTES.md`・条件名・評価者の判断は見せない。組の順番・ID・左右（A/B）は乱数で決まる。ownerの対応表（`owner-key.json`）はownerに渡さない。
   - 選択肢は、A・B・同等・判断しない（対応表でS側・B側に直す）。同等と判断しないはnから除く。
   - ownerの回答（`owner-answers.json`）は、記録した時刻とともにcommitする。そのcommitより後に、層2の結果と、門の数えの対応表を開く。
   - ownerがSかBを選んだ組（n）で、Sを選んだ数をk、片側の二項検定（偶然0.5、α 0.05）をかける。p ≤ 0.05なら効果あり。
   - **nとkは、門で判定できたケースの組だけで数える。** nの下限は「24×（判定できたケースの数）/4」とし、端数は切り上げる（4ケースなら24、3ケースなら18）。nが下限に届かなければ「未判定」。
   - **害の確認（全4ケースに当てる。門で判定できないケースも含む）：** 業務の画面の各ケース（ui03・ui08）で、ownerがBを選んだ組がSを選んだ組より多ければ「不採用」とする。1対0（他は同等・判断しない）でも当たる、感度の高い規則である。業務の画面で悪くならないかを重く見るために、このままにする。
   - 同じ回の画面が複数の組に入るので、組は独立ではない。p値は目安として扱い、その旨を報告する。
4. **結論：** 次の順に当てはめ、最初に当たったものを結論とする。害の確認（層1・層2・層3）は全4ケースに当てる。
   0. 次のどれかなら「未判定」：共通の仕組みの判定（`judge.json`）が`not-judged`（失敗した試行の率が上限を超えた、必須の置き換えが無い等）。生成が停止の線に達した。層2が欠けた（評価者・回・組のどれか1つでも、有効な判断が無い）。費用が上限を超える見込みになった（下の「費用」）。
   1. 門で「未判定」なら、「未判定」（工程が使われていないので、他の層の結果を工程の効果とみなさない）。
   2. 層1・層2・層3のどれかで害（「不採用」の条件）に当たれば、「不採用」。
   3. 層3でnが下限に届かなければ、「未判定」。
   4. 層3で効果ありなら、「採用」。効果が無ければ、「不採用」。
   - 配布するかはownerが決める。

## 層2（一対比較P）：明らかな差の警報

ownerの決定で使う。Pは良い案どうしの優劣を判定できない（#1852）。一方、片方に既知の種類の明らかな劣化があれば見分ける（#1835、強い劣化10/10）。そこで、Pを「明らかな差の警報」として使い、害は層3のownerの回答で確かめる。

- ケースごとに、同じ回のSとBの組（r1・r2・r3の3組）、計12組をPに比べさせる（`config/layers/eval.json`の`pPairs`。#1835の`make-packets.mjs --config config/layers/eval.json --seed 18670002`はこの12組だけPの束を作る）。評価者はFableとCodex（#1835と同じ。依頼文の冒頭・Pの依頼文は#1835の`prompts/`のまま。sha256を`eval.json`に記録した）。各組を2回、IDと左右を変えて比べる。FableとCodexを並行して動かすときは、keyとownerの対応表を両方の実行で`--lock`する（#1860の直しがmainに入っている：`221283eb`）。
- **警報：** ある組で、両評価者が2回とも同じ側を選んだら、その組を「警報」とする。
- **確かめられた害：** 警報がBを選び、かつownerもその組（同じ回のS-ri対B-ri。層3の9組に必ず含まれる）でBを選んだ組。
- **害の判定：** あるケースで、確かめられた害の組が3組中2組以上なら、そのケースで害ありとして「不採用」とする。全4ケースに当てる。
- 警報だけの件数（Bを選んだ警報、Sを選んだ警報。ownerが選ばなかったもの・同等としたものを含む）は報告する。Sを選んだ警報は、効果の根拠には使わない（効果は層3で判定する）。
- Pの結果は、ownerが層3の回答を記録してcommitした後に開く。
- **誤った警報の率（#1852の記録からの見積り）：** #1852でownerが「同等」とした11組のうち、両評価者が2回とも同じ側を選んだ組は6組（0.55）だった（`docs/evidence/1852-p-good-pairs/results/result.json`の`perEvaluator.*.pairs`と`ownerByItem`）。差の無い組でも、半数ほどで警報が出る。片側（B）への誤った警報は、その半分の約0.27と見る。そのため、警報だけでは害としない。ownerが優劣を付けた25組では、警報が17組で出て、14組はownerと同じ側、3組は逆の側だった。

## 「指摘ありの1例」を行わない理由

Issueの手段の案には「指摘ありの場合は、別に1例だけ示す」がある。この評価では行わない。

- Issueの手段の案は要求ではなく、完了の基準にも入っていない。

## この評価で確かめられないこと

- 生成者にbrowserが無いため、Skillの6節のうち「描画して確かめる」部分は動かない。この部分の効果は未判定として報告する。

- 実際の利用者の反応（CVR等）は確かめない（Issueの対象外）。
