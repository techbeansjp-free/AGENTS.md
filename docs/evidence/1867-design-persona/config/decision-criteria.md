# 判定の規則（#1867。モデル実行の前に固定）

対象：#1867の評価。ペルソナ調査の工程を持つデザイン作成Skillの候補（`design-creation`、[../candidate/design-creation/](../candidate/design-creation/)）を入れると、入れない場合より、ownerが良いと判断するデザインになるか。業務の画面で悪くならないか。

正本は評価の計画（[../EVAL_PLAN.md](../EVAL_PLAN.md)）である。この文書は計画の判定を、共通の測定の仕組み（[../../shared-harness/](../../shared-harness/)）の設定として書き直したもので、計画と食い違う場合は計画が正しい。評価結果を見た後に、この規則・[cases.json](cases.json)・[conditions.json](conditions.json)・[release.json](release.json)・[run-order.json](run-order.json)・共通の仕組みのmoduleを変えない。

## 判定（計画の「判定」と「層2」）

### 1. 工程が使われたか（門）

> Sの試行で、`design-creation`の`SKILL.md`が読まれ、デザインの記録に利用者の像（根拠と仮説の区別つき）と、判断と利用者の対応がある試行を数える。ケースごとに3回中2回以上なら、そのケースは判定できる。判定できるケースが3未満なら、全体を「未判定」とする。（計画）

数え方を、機械で数える部分と人が数える部分に分ける。

- **機械（共通の仕組み）：** Sの各試行で、`SKILL.md`（`^\.agent-skill-chain/(managed-runtime/)?skills/design-creation/SKILL\.md$`）のRead（結果がerrorでないもの）があるか（`cases.json`の`expectReads`、`runs.json`の`expectReadsAll`）。ケースごとの数は、`judge.json`の`perCondition.S.checks.gate-read-<ケース>`（水準`2/3`）に出る。この水準に届かないケースは、記録の中身によらず判定できない。
- **人（統括または親）：** `SKILL.md`が読まれたSの試行について、`collect.mjs`の後に、その試行の`out/DESIGN-NOTES.md`（手元の`work/`の写し）を読み、次の2つが両方あるかを試行ごとに数える。
  1. 利用者の像があり、その項目が根拠（出典）のあるものか仮説かを区別して示している。
  2. デザインの判断と、それをどの利用者（の要求・状況）から選んだかの対応がある。
  - 数えた結果（試行ごとの可否と、該当する記録の箇所）は、判定の前に記録としてcommitする。条件名は伏せずに数える（Sの試行だけを数えるため）。
- ケースは、「`SKILL.md`が読まれ、1と2が両方ある」試行が3回中2回以上なら判定できる。判定できるケースが3未満（4ケース中）なら、全体を「未判定」とする。
- 共通の仕組みの`perCondition.S.verdict`（`meets-levels`）は、4ケースすべてが機械の部分を満たしたことだけを示し、門の結果ではない。
- Bの水準（`perCondition.B`）は計算されるが使わない。Bは`design-creation`を持たないので、読込みは構造上0件である。
- 報告するだけのもの（判定に使わない）：referenceの読込み（`reference-read`）、成果物と記録の両方を書いた試行（`written-<ケース>`、`writeOk`）、各試行の`report`（入口・本文・各referenceの読込み、ascの本文の読込み、lp-newの`inquiries.md`の読込み、書いたfileの一覧）、`writesReport`（記録に「仮説」「根拠・出典」「ペルソナ・利用者の像」の語があるか。人が数えるときの手掛かりで、門ではない）。

### 2. 層1（機械の判定）

> #1835の層1の道具で、全試行の画面を判定する。Sの不合格の数が、ケースごとにBより多いケースがあれば記録する。axeの重大・深刻な違反が、Bより多いケースが2つ以上あれば「不採用」とする。（計画）

- 共通の仕組みの外で、[#1835の層1の道具](../../1835-design-eval-layers/README.md)を使う（モデルを呼ばない）。対象は各試行の画面（ui02・lp-new・ui03は`out/index.html`、ui08は`app/billing.html`）。

### 3. 層2（一対比較P）：明らかな差の警報

> ケースごとに、同じ回のSとBの組（r1・r2・r3の3組）、計12組をPに比べさせる。評価者はFableとCodex。各組を2回、IDと左右を変えて比べる。ある組で、両評価者が2回とも同じ側を選んだら、その組を「明らかな差」とする。あるケースで、Bを選んだ「明らかな差」の組が3組中2組以上あれば、そのケースで害があるとして「不採用」とする。Sを選んだ「明らかな差」は、効果の根拠には使わない。件数は報告する。Pの結果は、ownerが層3の回答を記録した後に開く。（計画の要約。Codexの実行中はkeyとownerの対応表を`--lock`で閉じる）

- 共通の仕組みの外で、#1835・#1852の道具を使う。費用は生成の台帳に入らないので、生成の後に、上限20 USDから生成の台帳の合計を引いた残りを層2の上限とする。

### 4. 層3（ownerの盲検の比較）

> ケースごとに、Sの3回×Bの3回の9組、計36組をownerが比べる（条件名を伏せる）。ownerがSかBを選んだ組（n）で、Sを選んだ数をk、片側の二項検定（偶然0.5、α 0.05）をかける。p ≤ 0.05なら効果あり。nが24未満なら「未判定」。業務の画面の各ケース（ui03・ui08）で、ownerがBを選んだ組がSを選んだ組より多ければ「不採用」とする。同じ回の画面が複数の組に入るので、組は独立ではない。p値は目安として扱い、その旨を報告する。（計画）

### 5. 結論

> 門を通り、層1・層2で不採用にならず、層3で効果あり、かつ害が無ければ「採用」。層3で効果が無ければ「不採用」。上の未判定の条件に当たれば「未判定」。配布するかはownerが決める。（計画）

## 完了と費用

- `maxFailureRate`（失敗した試行の率の上限0.1）、必須の置き換え（失敗した試行1件につき1回）、停止の線は、共通の仕組みの`order.mjs`の規則のまま。停止の線に達したら、その時点の記録で判定し、足りない試行を報告する。
- 該当しない依頼（negative）は置かない（計画に無い）。共通の仕組みが「該当しない依頼の有効な試行が無い」ことで未判定にしないよう、`rule.negativesRequired`を`false`にした（共通の仕組みの#1867の変更）。
- 生成の台帳の合計と、層2の費用の合計が20 USDを超える見込みになれば、止めて未判定とする（計画の「費用」）。

## この測定で確かめられないこと

- 生成者にbrowserが無いため、Skillの6節のうち「描画して確かめる」部分は動かない。この部分の効果は未判定として報告する。
- networkが無いため、根拠は依頼文と置いた資料（lp-newの`inquiries.md`、ui03の`data.json`、ui08の既存のfile）に限られる。
- 読取りはfileの単位で数え、`SKILL.md`のどの節まで読んだかは確かめない。
