# 利用者を決めてからデザインする

デザインの無いページを作るとき、先に「誰が、何のために、どんな状況で使うか」を根拠から決め、その結果からデザインの判断を導く。工程はAIが最後まで進める。人はどの段階でも指摘・指示でき、指摘・指示が無ければAIの案のまま進む。

中心の考え方：利用者の像は、根拠のある事実と仮説を分けて持つ。根拠の無い属性（名前・年齢・趣味等）を作り込まない。デザインの判断に効かない設定は書かない。

## 1. ページの種類を決める

依頼から、ページが次のどちらに近いかを決め、調べる項目を選ぶ。両方の性質があれば両方の項目を使う。

- **公開ページ（LP・案内・紹介）：** 不特定の見込み客が、行くか・申し込むか・読むかを決める。[公開ページの項目](references/public-page.md)
- **業務の画面（管理画面・ダッシュボード・入力画面）：** 役割の決まった担当者が、作業を速く正しく終える。[業務の画面の項目](references/business-screen.md)

## 2. 根拠を集める

依頼文、渡された資料・データ、既存の画面・デザインシステム、利用できる範囲の公開情報から、利用者と使い方についての記述を集める。出典ごとに、何が書いてあったかを短く残す。調べられなかった範囲（networkが無い、資料が無い等）も書く。実在の個人の情報は集めない。

## 3. 利用者の像を作る

項目ごとに、値と「根拠（出典）」か「仮説」かを書く。像の数は、デザインの判断が分かれる単位（例：スマートフォンの家族連れと、英語で情報を探す観光客）に限る。仮説がデザインを大きく左右する場合は、その仮説と、外れたときに変わる判断を書く。

## 4. 確認の時点

利用者の像と、そこから導く主な判断を短くまとめて示す。

- 対話できる場合は、まとめを示して返事を受け付ける。指摘・指示があれば反映する。指示が無ければAIの案で進む。
- 対話できない実行（自動の生成等）では、待たずにAIの案で進み、その旨を記録に残す。

## 5. デザインの判断を利用者に結び付ける

情報の順序、構図、密度、配色、書体、操作の置き方などの主な判断ごとに、どの利用者のどの要求・状況から選んだかを書く。どの利用者にも結び付かない判断は、依頼の制約か作り手の判断かを書く。

## 6. 利用者の立場で点検する

完成した画面を、像ごとに、その利用者の目的・環境（画面の幅・急ぎ方・言語・支援技術等）で見直す。目的の情報や操作にたどり着けない、見落とす、誤る箇所を直す。描画して確かめられるなら、狭い幅と広い幅で確かめる。確かめられなかったことは書く。

## 出力

依頼の成果物（画面のfile）に加えて、デザインの記録を1つ残す。依頼が記録の場所を指定していればそこに、なければ成果物の隣に置く。記録には、ページの種類、集めた根拠と調べられなかった範囲、利用者の像（根拠と仮説の区別）、確認の時点の扱い、判断と利用者の対応、点検の結果を書く。長さは依頼の規模に合わせる。

## 扱わないこと

画面から一連の操作を完了できるかの実操作の確認は[user-journey-acceptance](../user-journey-acceptance/SKILL.md)、設計案の採否の比較は[engineering-judgment](../engineering-judgment/SKILL.md)が扱う。実際の利用者への調査・A/Bテストは行わない。必要なら、その必要と確かめたい仮説を記録に書く。
