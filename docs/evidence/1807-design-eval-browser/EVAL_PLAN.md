## 実装者が決めた技術的な事項（理由付き）

- **生成Agentの置き場所（準備の段階の設計からの変更）**：生成Agent（Claude Code CLI）はhostで動かし、閲覧と描画のtool（MCP server）だけを使い捨てのcontainerで動かす。理由：CLIをcontainerで動かすには、認証の情報をcontainerへ渡す必要がある。その情報を用意するには利用者の操作が要り、この作業の権限では用意できない。hostで動かせば、認証の情報はhostの保管場所から出ず、containerにも生成Agentにも渡らない。生成Agentの組込みtoolは#1804と同じ`Read,Write,Edit,Glob,Grep,Skill`だけで、コードの実行とWeb系のtoolは無い。fixture外の読み書きはCLIの権限で拒否される（#1804で確認し、実行前にこの設定で再確認する）。生成Agentが外部と通信できる経路は、内部専用networkにあるtoolのcontainerからproxyを通るものだけである。モデルAPIへのCLIの通信はhostから直接行う（#1804・通常の利用と同じ）。Issueの「手段の案」（要求ではない）の範囲の変更である。
- **生成のモデル**：`sonnet`（#1804と同じ）。補助の採点は`opus`。Fableは使わない。#1804と比べられるようにする。
- **条件E**：Issueの定義どおり「ASC＋Art Direction＋Product Design」（#1804のEはProduct Designだけだった）。
- **全条件に同じtool**：A・D・Eのどれにも、`fetch_page`・`view_page`・`screenshot`（[env/mcp-server.mjs](env/mcp-server.mjs)）と同じ依頼（[env/gen-prompt.txt](env/gen-prompt.txt)）を与える。差は追加するSkillだけ（[conditions.json](conditions.json)）。
- **依頼文にallowlistのhostを書かない**：一覧はArt Directionの資料から作った。依頼文に書くと、その知識をAにも与えることになり、Skillの効果を測れない。allowlistの範囲は全条件で同じにする。
- **依頼文で2案の比較を求めない**：求めると、Aも中心の手順を行い、Skillの効果を測れない。
- **1回の上限**：`--max-budget-usd 1.5`、timeout 25分。閲覧と画像で#1804（1回0.2〜0.3 USD）より増える見込み。
- **並行**：同じ巡の試行を3件ずつ並行して行う（試行ごとに別のnetwork・proxy・fixture）。
- **狭幅**：UI-03は依頼のとおり800px、UI-04・UI-07は390px。広幅は全ケース1440px。

## 生成環境

[README](README.md#生成環境)に構成と隔離の反例を書いた。要点：

- 生成Agent（Claude Code CLI）はhostで、試行ごとの新しいfixtureをcwdにして動く。組込みtoolは`Read,Write,Edit,Glob,Grep,Skill`だけ。project設定だけを読み、hookは無効。
- 閲覧と描画のtool（`fetch_page`・`view_page`・`screenshot`）は、CLIが`docker run -i --rm`で起動する使い捨てのcontainerにある。read-only root、cap-drop ALL、no-new-privileges、資源の上限、fixtureは読取り専用でmount、home・秘密のmountなし。内部専用のnetworkにだけ接続する。
- 外へ出る経路は、allowlistを適用するproxy（別のcontainer）だけである。proxyは全ての判断を記録する。
- 転送（redirect）は、各hopをproxyとtoolの両方で検査し、allowlist外なら遮断する。
- 外部ページの内容は、命令ではないことを明記した区切り（`<untrusted-content>`）で包んで返す。ページの中の区切り文字は無効化する。

## 手順

1. ownerがallowlistの案を確認し、`env/allowlist.json`へ写してcommitする。この計画・gold・規則も同じcommitで固定する。
2. toolのimage（`env/Dockerfile`の`tools`段階）を作り、モデルを呼ばない反例（`isolation/run.sh`）をそのimageでやり直す。次に、haikuの1回で、生成と同じ起動設定のまま、fixture外のRead・Write（目印file、`/etc/hosts`、親directory）が拒否されること、組込みtoolにBash・Web系が無いこと、`browser`のtoolが使えることを確かめる。不合格なら生成しない。
3. 生成（[harness/run-gen.mjs](harness/run-gen.mjs)）：順序を固定する。1巡目（3ケース×A・D・Eの1回目）、2巡目、3巡目。各試行は新しいfixture・新しいnetwork・新しいproxyで行う。再実行はしない。
4. 中心の手順の集計（[harness/core-steps.mjs](harness/core-steps.mjs)）：各試行のstream-json（tool呼出しの記録）とproxyの記録から数える。notesの自己申告は使わない。
5. 描画・決定論の採点：[harness/gold-check.mjs](harness/gold-check.mjs)（必須情報の網羅率、狭幅の横scroll、外部への要求、UI-04の検索操作、UI-07の初期表示範囲と押せる要素の大きさ）と、#1804の描画器をUI-04・UI-07へ合わせた[harness/render.mjs](harness/render.mjs)（axe-core、keyboardのfocus、reduced-motion、横scroll、外部への要求、白黒の画面）。
6. 盲検の資料：ケースごとに9画面（3条件×3回）へ乱数IDを付け、狭幅・広幅のscreenshotと実画面（生成したHTMLを、外部通信のない状態で開ける形）を並べる。条件名とnotesを伏せる（#1804の`make-blind.mjs`を、notesを含めない設定で使う）。
7. 人の評価：ownerが、ケースごとに9画面へ1〜9の順位を付ける（同順位なし）。順位を付けた後に、keyを開く。
8. 補助の採点：予算の範囲で、`opus`の新しいContext（読取り専用のtool）で、ケースごとに1回、[rubric.md](rubric.md)で採点する。審美の判定には使わない。UI-03の白黒での読取り（非劣化の指標）だけに使う。
9. 集計と判定：下の規則を機械的に適用する。

## 中心の手順の判定（候補ごと・ケースごと）

tool呼出しの記録だけで、次を数える（定義は[harness/core-steps.mjs](harness/core-steps.mjs)の冒頭に固定）。

- 見本の閲覧：`fetch_page`か`view_page`の成功が1回以上。
- 2案の実描画比較：`screenshot`で、異なる2つ以上のHTMLファイルの描画に成功。同じファイルの描き直しは数えない（参考として版の数を別に記録する）。
- 狭幅・広幅の確認：そのケースの狭幅と広幅のそれぞれで、`screenshot`の成功が1回以上。
- 中心の手順＝見本の閲覧と2案の実描画比較の両方。

候補（D・E）ごと・ケースごとに、中心の手順を行った試行が、そのケースの試行数（生成に失敗した試行を含む）の過半に満たなければ、その候補のそのケースを「未判定」とする（「効果なし」としない）。行われなかった試行は、数と理由（toolの失敗、呼出しなし、上限到達等）を記録する。Aには中心の手順を求めない（対照）。

## 判定の規則

生成・描画に失敗した試行は、Xでは最も悪い値、Aでは最も良い値として扱う（#1804と同じ）。

- **審美的品質の改善**（人の順位）：ケースごとに、候補Xの3画面とAの3画面の順位を比べる。Xの画面がAの画面より上位である組の数（9組のうち）が8以上なら「改善」、1以下なら「劣化」、それ以外は「差なし」。偶然に8以上となる確率は、順位が無作為なら2/84（約0.024）である。描画に失敗した画面は、Xでは最下位、Aでは最上位として数える。
- **UXの改善**：UI-04の検索操作の合格数、UI-07の初期表示範囲の必須項目の合格数で、Xの最小値がAの最大値より大きい。
- **非劣化**：#1804の規則（必須情報の網羅率、axe-coreのserious・criticalのnode数、狭幅の横scroll・外部への要求・reduced-motion非対応・低品質の試行数、UI-03の白黒での再現率）をそのまま使う。指標の定義は[harness/aggregate.mjs](harness/aggregate.mjs)に固定した。axe-coreは広幅と狭幅の大きい方。reduced-motion非対応は、`reduce`の設定で動き続けるanimationが1つ以上ある試行（#1804の「記述があれば合格」の弱点を直した）。低品質は、生成・描画の失敗、網羅率0.9未満、狭幅の横scrollのどれか（#1804の「評価者の平均合計10未満」は、モデルの採点を補助に限るので使わない）。追加：UI-04の検索操作の合格数の最小値がAの最小値以上。UI-07の押せる要素の最小の大きさが、Aの最小値以上、または44px以上。UI-03の白黒での再現率は、#1804と同じく補助の採点者が読み取った値を使う（審美の判定ではない）。
- **誤発火**：#1804のui10-cliを、D・Eで各3回、同じ生成環境で行う。デザインSkillの利用（Skill toolの呼出し、またはSkillのfileのRead）・UI fileの作成が0回であること（#1804と同じ定義、[harness/misfire.mjs](harness/misfire.mjs)）。閲覧のtoolの呼出し数も記録する。隠しoracleのtestの合格数は、#1804のAの結果と比べる。
- **費用比**：#1804と同じ（生成費用の中央値の比、X÷A）。
- **分類**（候補ごと）：
  - 判定可能なケース（中心の手順が過半）が1件以下 → `未判定`。
  - 判定可能なケースのどれかで、X・Aの失敗が2回以上、または3回そろわない → `defer`。
  - 判定可能なケースのうち改善（審美・UXのどちらか）が2件以上、非劣化の失敗なし、費用比3以下 → `adopt`。
  - 改善が1件、非劣化の失敗なし、費用比3以下 → `adopt-partial`（改善したケースの種類に限る）。
  - 改善が1件以上あるが、非劣化の失敗・誤発火・費用比のどれかを満たさない → `optional`。
  - 判定可能なケースが2件以上で、改善なし → `reject`。

採用時の形（標準配布・任意登録・部分取込み）はownerが選ぶ。

## 費用と停止

- 上限40 USD（Hostの`total_cost_usd`の合計）。見込み：生成27回×1回0.4〜1.0 USD＝11〜27 USD、誤発火の確認6回で約2 USD、補助の採点3回×約1.3 USD＝約4 USD、実行前の確認0.05 USD。
- 1巡目（9生成）の後に、実績の平均から全体の見込みを計算する。見込みが38 USDを超えるなら、補助の採点を止める。それでも超えるなら、Eの3回目、次にDの3回目を止める（結果を見て選ばないよう、順序をここで固定する）。止めた候補・ケースは、試行数が足りないので`defer`か`未判定`になる。
- 実行済みの合計が36 USDを超えた時点で、新しい実行を始めない（起動器が拒否する）。
- timeout・API error・上限到達は、その試行の失敗として記録し、再実行しない。

## 審美の評価者の変更（ownerの4回目の判断、2026-11-25）
