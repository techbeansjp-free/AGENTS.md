# 設計メモ

## 情報の優先順位
利用者（シフト責任者）は数秒で「対処が必要か」を判断する。そのため上から順に次のとおり並べた。

1. **最終更新時刻**（ヘッダー右、大きめ）：常時表示の画面では「この値はいつのものか」が最初の信頼の根拠になるため。
2. **対処が必要な件数と一覧**（帯）：しきい値超過のKPI・レーンと、取得失敗のデータ源を1か所に集約。各項目から該当箇所へリンクする。超過がなければ緑の「対処が必要な項目はありません」に切り替わる。現データでは4件（遅延率、B01、C02、温度センサー）。
3. **データ取得の失敗**：失敗の事実、最後に成功した時刻（10:42、最終更新の3時間50分前）、再試行ボタンを同じ枠にまとめた。温度センサーの停止は冷蔵レーン（B01）の遅延と並んで見えるよう、KPIより上に置いた。
4. **KPI 6項目**：値を大きく、目標としきい値を小さく添える。
5. **レーン 8件**：超過レーンを先頭に並べ、遅延件数・進捗・締切を1行に収めた。担当者と注文参照（長いID）は行を開くと出る（超過レーンは最初から開く）。依頼の「必要ならレーンの詳細を見る」に対応。

## 色だけに頼らない識別
赤は「超過」にのみ使う。併せて、記号（▲／✓）、文字（上限超過・下限割れ・遅延超過）、位置（帯・レーン一覧の先頭）、形（KPIは太い枠、レーンは左の太い帯）を使う。グレースケールでも識別できる。取得失敗は琥珀色の枠＋▲＋文言で、赤（業務のしきい値超過）と区別した。

## 配色
紙のような薄い灰緑の地（#eff1ee）、墨色の文字（#17212b）、進捗バーは落ち着いた青灰（#3b5870）。通常時は彩度を抑え、赤（#b3261e）が出たときだけ目立つようにした。常時表示で長時間見るため、暗い背景ではなく明るい背景とした。文字と背景のコントラストは主要な文字で4.5:1以上を想定している（計測ツールでの確認はしていない）。

## 書体
`FONTS.md`の範囲で Noto Sans CJK JP のみ。数値は `tabular-nums` で桁を揃える。見出しの強弱は太さとサイズだけで付け、大文字ラベルや装飾書体は使っていない。KPIの数値は38px、巡回中のタブレットでも読める大きさにした。

## 構図
- PC（1440px）：KPIは6列1行、レーンは5列の表形式。
- タブレット（800px）：KPIは3列2行。レーンは2段組みに切り替えるが、情報は減らさない。
- 長いID：折り返し（`overflow-wrap:anywhere`）で全文を表示し、切り詰めない。レイアウトは崩れない。

## 判断が必要だった点
- 「しきい値を超えた」は、KPIは`threshold`の`min`/`max`に従い、レーンは`lane_delay_threshold`（8）を**超えたもの**（遅延が9件以上）とした。B02（5件）は範囲内。
- 出荷済み件数は`threshold`が`null`なので、超過判定はせず、目標に対する進み具合のバーだけを付けた。
- 「締切超過・残n」は`data.json`の締切と最終更新時刻から計算した補助表示で、しきい値超過とは扱わない。九州便（C01）は締切13:30を過ぎて9件が残っている。依頼にない項目だが、判断の材料になると考えて入れた。不要なら削除してよい。
- 再試行ボタンは、押すと「受け付けました」を表示するだけで、再取得はしない（依頼どおり）。

## 参考・確認範囲
- 外部の資料やデザインは参照していない。
- 確認したのは、データの数え上げ（KPI6・レーン8・データ源3）と、しきい値の判定をコードの上で追ったことまで。**ブラウザーでの表示確認（1440px・800px）は行っていない**。実機で見た目と折り返しの確認が必要。
