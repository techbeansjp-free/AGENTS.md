# 設計メモ

## 情報の優先順位と構図（上から順に）
1. **状況サマリー**（「▲ 対処が必要：4件」＋内訳）。利用者は数秒で「対処が必要か」を知りたいので最上段に置いた。
2. **取得失敗のデータ源**（原因・最後に成功した時刻・経過時間・「再試行」ボタン）。冷蔵庫温度センサーが10:42から止まっており、冷凍レーン（B01）の判断に響くため、KPIより先に見せる。正常なデータ源は小さく1行にまとめた。
3. **KPI 6項目**（PC幅は6列1行、タブレット幅は3×2）。数値を大きくし、目標と基準を小さく添える。
4. **レーン8件の表**。「要対応」を上に並べ替えた（B01、C02）。詳細（担当者・遅延件数・締切・注文参照）は巡回時に読む情報なので、サマリーの下に常時表示した。クリックで開く操作は省いた。

## 色だけに頼らない識別
- 超過したKPI・レーンには「▲ 基準超過」「▲ 要対応」の文字と記号を付け、枠線を太くし、レーンは行の左端に太い帯を付ける。正常側は「✓ 正常」。
- 色は赤（超過）と中立のグレー・青（通常）に絞った。白黒印刷や色覚差でも文字と位置で区別できる。

## しきい値の判定
- KPIは `threshold.type` に従い、`max` は「値 > 基準」、`min` は「値 < 基準」で超過とした。該当は出荷遅延率（12.4% > 5%）のみ。出荷進捗率は目標64%に届かないが、基準58%は上回るので正常とした。
- レーンは `lane_delay_threshold`(8) に対し「遅延件数 > 8」で超過とした（B01=61、C02=9）。「8件ちょうど」の扱いは依頼に明記がなく、ここは私の仮置きなので、運用側で確認してほしい。現データには8件のレーンがなく、結果は変わらない。

## 書体
- 本文は Noto Sans CJK JP（閲覧環境にある書体）。常時表示の遠目でも読めるよう、数値は 34px の太字、`tabular-nums` で桁をそろえた。
- `lane.id` と `order_ref` は DejaVu Sans Mono。英数字の判別がしやすく、長いIDの照合に向く。`overflow-wrap:anywhere` と固定レイアウトの表で、長いIDが折り返されて崩れない。外部の書体は読み込まない。

## 時刻
- 最終更新は右上に表示した。時刻はデータの値をそのまま表示し、閲覧端末のタイムゾーンで変換しない。
- 「最終更新から何時間前か」は、現在時刻ではなく `updated_at` を基準に計算した（画面を開く時刻に依存させないため）。

## 実装上の判断
- 単一HTML、外部通信なし。データはファイル内の `DATA` に埋め込み、表示はすべて `textContent` で出力した。
- 再試行ボタンは押下で受付メッセージ（`aria-live`）を出し、3秒間無効にして連打を防ぐ。実際の再取得は行わない。
- 幅1440pxと800px前後で崩れないように、グリッド列数と表の列幅を切り替えた。ボタンは高さ44px、キーボードのフォーカス枠を付けた。
