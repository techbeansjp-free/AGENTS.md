# Context読込み選択の不足の実測と採否（#1767）

開発時の検証資料であり、配布対象に含めない。通常のASC実行時に読み込ませない。

## 結論

**追加実装不要（Phase 1へ進まない）。** 現行の規則と既存Host手段で足りないことを示す実測は得られなかった。新しい候補ランキング、索引、確率的selector（Jev等）は試作していない。外部へのrepository内容の送信、実モデル実験、費用の発生は無い。

ただしこれは「不足が無いと証明した」のではない。**必要情報のrecall・miss率は、実行ログだけからは測れない**（下記）。測定できない範囲は欠測とし、再開条件を末尾に置く。

### 適用規則の選択と、コード・根拠の内容選択は別である

`projectContext`は、変更pathのprefixと祖先の`AGENTS.md`／`CLAUDE.md`から、規約ファイルのpath・SHA256・byte数を返す決定論的な処理で、本文もコード断片も返さない。コードやテストの関連度を順位付けする機構ではなく、`authority`欄も選択が意味的遵守を示さないと明記する。したがってコード・根拠の内容選択は、現状はHostの検索と`implementation.md`の規則が担う。この責務分担は評価の前提であって、不足の証拠ではない。

`implementation.md`は、検索で位置を絞ってから必要範囲だけ読む、`gh --json/-q`で項目を絞る、巨大出力を避けて全文をworktree外へ保存する、広い調査はsubagentへ渡し結論と参照だけを返させる、を既に要求している。SKILL.md原則1も再読込みの削減を挙げている。

読取れること（観測）：
- 検索系の呼出し（343）はReadの2倍近く、Readは範囲指定なしが77%。検索で位置を絞る運用は行われているが、全文Readも多い。
- 巨大結果（20K超）は30 sessionで16件にとどまり、tool結果の中心はBash出力である。
- 再読込み25件は、編集後の確認Readなど正当なものを含み得る。必要性は区別していない。

**読取れないこと（欠測）**：
- 「結果的に必要だったfile」「読み落としによる手戻り」は、元要求・差分・テスト・独立レビューから独立に決める必要があり、ログだけでは判定できない。したがってrecall・miss率・手戻りは**欠測**で、0としない。
- input/output/cache tokens、API費用、wall-clock、再試行の費用は今回集計していない（欠測）。文字数はtokenや費用の代用にしない。
- 標本は小さく、1人の1台のログで、作業種類（認可・migration・UI連携・複数worktree等）の偏りを制御していない。結果を一般化しない。

### 追加機構なしの改善余地

観測された改善候補は、新機構ではなく既存規則の運用の範囲にとどまる。(1)範囲指定なしのReadのうち、大きなfileの全文読取り、(2)Bash出力の絞り込み（`--json/-q`、行範囲）。いずれも`implementation.md`に既にあり、規則の追加や変更が必要と示す測定は得ていない。規則の文面を増やすと通常実行の読込みが増えるため、実害の測定なしに足さない。

## Phase 1以降を実施しない理由

Phase 1の前提は「Phase 0で測定可能な実害・費用と改善余地がある場合」である。今回は、必要情報の取りこぼしも、再読込みや巨大出力による有意な費用も、実測では示されなかった。ADR 0002の機構追加審査が求める「具体的な失敗」と「既存手段では足りない根拠」も無い。ADR 0005により、実測の価値と対照評価なしに新runtimeを採用しない。以上から、A/B/Cの対照評価、決定論的scorer、Jev等のshadow評価は行わない。何も変更しないため、Phase 2の境界（`project-context.mjs`の契約、正本性、秘密の扱い）は維持される。

| 案 | 判定 | 根拠 |
| --- | --- | --- |
| A：現行Host＋ASC | 維持（追加実装不要） | 不足が実測されない |
| B：既存検索の順序・構成の最小改善 | 規則は既にある。変更しない | 追加の実害測定なし |
| C：優先順位付け（Jev等を含む） | 未着手 | 前提のPhase 0条件を満たさない。送信許可・費用もowner確認事項 |

## 再開条件と、ownerへの確認事項（案）

次の場合に、新しいIssueまたはこのIssueの再開で、Phase 1へ進む。
- 実セッションで、必要fileの読み落としによる手戻りが、独立に判定できる形で複数件記録された。
- または、同種の大きな読込み・再読込みが総費用の目立つ割合を占めると、tokenまたは課金の実測で示された。

測定前に固定する基準の**案**（ownerが決める。独断で確定していない）：
1. 必須根拠のrecallは100%を条件とし、security-critical（認可・検証・規約）の欠落は1件でも不採用。
2. 品質（受入条件・テスト・独立レビュー指摘）が基準以下に落ちたら、費用が下がっても不採用。
3. 費用の優位は、同条件の反復の揺れを上回る場合だけ採用候補とする。反復数と費用上限はowner指定が必要。
4. 外部のselector・モデルを使う評価は、データ送信先・課金・契約の承認後にのみ行う。

ownerへの確認事項：上記の採用閾値と反復数、費用上限、Jev等の外部評価を将来行う場合の送信許可。現時点で回答は不要（実施しないため）。

## 限界

- ログは1台のlocal記録で、標本が小さい。Codex等の別Hostは調べていない。
- 本資料は実行ログの件数集計であり、品質・費用の対照実験ではない。
- 「不足が測れなかった」ことは「不足が無い」ことを意味しない。
