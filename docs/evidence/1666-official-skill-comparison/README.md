# 公式Skillとの匿名比較と、ASC Skillの是正（#1666）

## 判断

- Anthropic・OpenAI の公式 Skill のうち、ASC と領域が重なる3つを比べた。公式 Skill の本文は取り込まない。同じ課題で、ASC と Skill なしより点が低かった。
- 比較で見つかった ASC の弱点2つを、1文ずつ直した。
  - `execution-recovery`：無出力で止まった実行は、原因に対処した後、再発時に有限時間で止まるよう job・test の上限時間を提案する。共有の workflow 等の変更は許可を確認する。
  - `review-and-remediation`：是正後の再確認でも、レビューのみと同じく対象を編集せず、成立する指摘と必要な修正を返す。
- このディレクトリは開発時の検証資料であり、配布対象に含めない。公式 Skill の本文は再配布しない。

## 比較した組

| ASC | 公式（ライセンス） | 課題 |
| --- | --- | --- |
| `review-and-remediation` | OpenAI `review-agent`（Apache-2.0） | R1 欠陥の仕込まれた差分、R2 是正後の再レビュー、R3 指摘のない改名 |
| `execution-recovery` | OpenAI `gh-fix-ci`（Apache-2.0） | C1 CI だけで落ちる日付テスト、C2 無出力で止まった CI、C3 再実行で通った e2e |
| `user-journey-acceptance` | Anthropic `webapp-testing`（Apache-2.0） | U1 会員登録の実操作、U2 mock での顧客デモ、U3 ボタンの色だけの変更 |

公式 Skill の取得元 commit と、評価に使った本文の hash は [source-hashes.json](source-hashes.json) にある。

## 方法

- 課題：架空の9件（[cases.json](cases.json)）。実在の顧客・人物・案件を含まない。
- 観点：課題に仕込んだ事実から41観点を作り、回答の生成前に固定した（[rubric.json](rubric.json)）。Skill の章立てや語彙からは作っていない。範囲外の行為・実施していない確認の主張・指摘の捏造を別に記録した。
- 生成：Claude Code のサブエージェント（sonnet）。条件ごとに2回、各回は会話を継承しない別 Context。9件を各600字以内で回答させ、実作業・外部操作はさせていない。
  - Skill なし：Skill を読ませない。
  - ASC：組ごとに ASC の SKILL.md を読み、本文の指示で reference を読む。
  - 公式：組ごとに公式の SKILL.md を読み、指示されたファイルを読む。
- 識別情報：回答に Skill 名・条件名を書かせず、生成後に機械的に確認した（該当0件）。
- 採点：opus の別 Context 2系統に、課題・観点・匿名回答だけを渡した。対応キーは採点後に照合した。

## 結果

C1-1 は課題の欠陥のため除外した（後述）。2回分の合計で、80点満点。

### 初回（[first/](first/)）

| 条件 | 採点1 | 採点2 |
| --- | --- | --- |
| Skill なし | 73 | 72 |
| ASC（是正前） | 74 | 74 |
| 公式 | 65 | 65 |

- ASC だけが満たした観点：R2-3（前回の指摘が現在の対象で成立するかを確かめる。`Number('')` は `0` で、前回の指摘はもともと成立していなかった）。満たしたのは ASC の2回のうち1回だけ（両系統。再採点でも同じ）で、Skill なしと公式は0回。
- ASC だけが2回とも落とした観点：C2-5（再発時に早く止まる timeout の提案）。Skill なしと公式は2回とも満たした。
- 範囲外の行為：ASC の1回が、再レビューで「削除したテストを正しい形で戻します」と書いた（採点者1系統が判定）。
- 指摘の捏造：ASC 1件、公式 1件。どちらも R2 で「空白だけの文字列は NaN」とした（実際は `Number(' ') === 0`）。
- 公式が落とした観点：C1-3（基準のタイムゾーンの確認）、C2-4（他人の run に触れない）、U1-5（通信失敗・二重送信）、U2-4（顧客への伝え方を利用者に残す）など。手順の指示（`gh` の操作、Playwright の書き方）が中心で、判断の観点が少ない。

### 是正後（[rescore/](rescore/)）

是正した本文で ASC の回答を新たに2回生成した。初回の6回分は凍結して再利用し、8回分をまとめて新しい匿名 ID に置き換え、新しい2系統で採点した。

| 条件 | 採点1 | 採点2 |
| --- | --- | --- |
| Skill なし（凍結） | 73 | 72 |
| ASC 是正前（凍結） | 73 | 73 |
| ASC 是正後 | 73 | 74 |
| 公式（凍結） | 69 | 71 |

- C2-5：是正前 0/2 → 是正後 2/2（両系統）。
- 範囲外の行為：是正後は0件。是正前の1件は、再採点でも両系統が判定した。
- 是正後に下がった観点：C2-1（runner の割当て待ちではなく実行中の停止だと区別する）が 1/2 → 0/2、C1-2・C1-3 が 2/2 → 1/2。C2-1 で落とした回答は、どちらも無出力をハングと断定していない。既存の reference の「出力がないこととハングは同じではない」に沿った書き方だが、追加した1文の影響かどうかは未確認（推論）。C1-2・C1-3 の低下は、追加した1文と関係のない課題（日付の整形）で起きており、生成のばらつきと考えている（推論）。合計は同等であり、是正による悪化とは判断していない。
- 採点者のばらつき：同じ凍結回答の再採点で、公式は 65→69・71、ASC 是正前は 74→73 と動いた。

## 独立レビューで直さなかった点

- `review-and-remediation` の「是正後の再確認」が、是正担当が自分の修正を確かめる工程と紛れうる（Low）。同じ本文が先に「どれを依頼されたか確認する」としているので、依頼された役割として読める。評価した本文の hash を保つため、文言は変えていない。
- `execution-recovery` の追加文の後半（共有の workflow 等の変更は許可を確認する）は、同じ節の「共有環境や他作業へ影響する処置は別に許可を確認する」と重なる（Low）。矛盾はなく、追加文単独で読んでも許可の要否が分かるよう残した。

## 課題の欠陥

C1 は「手元（日本時間）では通り、CI（UTC）で落ちる」としたが、`toISOString` は実行環境のタイムゾーンによらず UTC を返すため、前提が矛盾する。全条件の回答がこの矛盾を指摘した。原因をタイムゾーン差と特定する観点 C1-1 は無効として集計から除いた。

## 限界

- 課題は作成者の架空のもので、各条件2回の比較にすぎない。統計的な差や、未見の実務課題への汎化の証明ではない。
- 回答だけの評価で、script の実行、実際のブラウザ操作、実際の CI での効果は測っていない。公式 Skill は実行手順（同梱 script など）に価値が寄っており、この方法では不利に働く。
- 1つの Context で3組の Skill を続けて読ませた。
- ASC と Skill なしの差は採点者のばらつきと同程度で、回答だけの評価では3つの ASC Skill の効果を確認できなかった。
- 暗黙選択（Skill 名を含まない依頼で入口が選ばれるか）は測っていない。今回の変更は description を変えていない。
