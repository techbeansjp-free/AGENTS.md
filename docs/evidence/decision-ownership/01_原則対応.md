# 原則対応表

原資料は、ある実務者のPM・ディレクション・PMOの判断基準を記した引継ぎメモと、その実務での振る舞いを観察した個人用Skillである（非公開、再配布しない）。原資料の各項目を、配布版のどこへ反映したか、または反映しなかった理由に対応付ける。`SKILL`は`skills/decision-ownership/SKILL.md`、`REF`は同`references/conditions-and-counterexamples.md`を指す。

## 前提

| 原資料の要点 | 反映先 |
| --- | --- |
| あやふやな部分も決めきる。判断できなければ判断者を明確にして決めてもらう | SKILL 冒頭・「判断者を割り当てる」 |
| 他の人の仕事と思考のノイズを減らす | SKILL「相手に合わせて渡す」（実装担当） |
| 実装担当には作ることに集中してもらい、届く問いを少なく明確にする | SKILL「相手に合わせて渡す」、REF「窓口で全部返し…」 |
| 言われたことをそのまま流さず、要否・目的・既存機能・別案を一度挟む | SKILL「依頼の背景と要否を確かめる」 |
| 進まない原因は判断者の不在であることがある | SKILL「判断者を割り当てる」末尾 |
| 判断を代わりに決めない（決めた本人に判断が残る） | SKILL 冒頭、REF「判断は必ず返し…」で適用範囲を限定 |

## PM

| 原資料の要点 | 反映先 |
| --- | --- |
| 優先度を次の次のリリースまで仮決めする | REF 表（定期リリースの案件に限定） |
| 着手したタスクの優先度は原則変えない（調査は例外） | REF 表（例外条件を明記） |
| 依頼総量が超えたら優先度を付け直してもらう | SKILL「先に伝えるべきリスク」 |
| リリースは周期・締切・見直し条件の3点で設計する | REF 表（曜日固定の行） |
| 緊急時の動き方を平時に決める | REF 表・「運用を整えるときの目安」 |
| デモ等の日程を早めにリリース計画へ入れる | SKILL「先に伝えるべきリスク」 |
| 新しい業務を引き受ける前に、誰の工数が圧迫され何が遅れるかを出す | SKILL「先に伝えるべきリスク」、REF「新しい業務は断る」 |
| 人を増やすときは任せることをタスク単位で決める | REF「人を増やせば解決する」 |
| ボトルネックはレビューと確認待ちに出る | SKILL「先に伝えるべきリスク」、REF「人を増やせば解決する」 |
| 稼働の超過・不足や請求影響を数字で早めに出す | SKILL「先に伝えるべきリスク」末尾 |
| 影響が大きい変更はレビュー・経過観察を増やす | REF「運用を整えるときの目安」 |
| 調査は時間を区切る | REF「運用を整えるときの目安」 |
| 大きな対応は全量→絞る→工数→時期の順 | REF「運用を整えるときの目安」、SKILL「仮置き案を添える」 |
| 見積は目安として出し、前後する前提で合意する | SKILL「先に伝えるべきリスク」、REF 表（固定価格契約の例外） |
| 共有ルート（経営判断・契約変更は経営層、工数・請求は経理） | SKILL 判断者の表（契約・費用の行）。組織固有の部署名は一般化 |
| 顧客側の事情もリスクとして見る | SKILL「先に伝えるべきリスク」 |
| 売上やスピードにどう効くかの観点で提案する | 不採用。判断者の整理という本Skillの範囲を超え、提案方針は`engineering-judgment`・`estimate-and-scope`の範囲 |
| 体制変更は早めに伝え、引継ぎ計画を添える | 不採用（引継ぎは`work-coordination`が扱う） |

## ディレクション

| 原資料の要点 | 反映先 |
| --- | --- |
| まず「なぜ必要か」「今どうやっているか」を聞く | SKILL「依頼の背景と要否を確かめる」 |
| 新しく作る前に既存機能で足りないか確認する | 同上 |
| 「やらない」も選択肢に出す。対応漏れも「そもそも対応する？」から | 同上、REF「やらない選択肢は毎回提案する」で適用範囲を限定 |
| やるか・リリースしてよいか・完了かは顧客が決める。先に進めるなら理由を残す | SKILL 判断者の表・本文 |
| 判断材料は工数感・影響範囲・やらない場合のリスクのセット | SKILL「仮置き案を添える」 |
| 数が多いものは全量を見せて重要なものを絞る | SKILL「仮置き案を添える」 |
| 現行フローと新フローを並べて差分ですり合わせる | 不採用（要件定義の手法であり、`engineering-judgment`の要求確認で扱える） |
| 確定と「できたら入れたい」を混ぜない | SKILL「確定と未確定を分ける」 |
| 顧客の社内事情を素直に反映し、押し通さない | SKILL「相手に合わせて渡す」、REF「顧客の事情は全部要件に反映する」 |
| 画面は1画面で終われるか・迷わないか | 不採用（UI設計の基準であり本Skillの範囲外） |
| 指摘は列を固定した一覧で管理する | SKILL「仮置き案を添える」、REF 表 |
| 提供側の回答→顧客の確認を1行で追えるようにする | REF「確認事項は1件ずつ…」 |
| 文言・翻訳を画面・ファイル・キーまで紐づける | 不採用（個別の管理手法） |
| 要件定義に要る情報を聞かれる前に取りにいく | SKILL「依頼の背景と要否を確かめる」に包含 |
| 確認事項はまず窓口で返し、実装が要るものだけ開発に聞く | SKILL「相手に合わせて渡す」、REF 表 |
| その場で返したものは記録に残りにくい | SKILL「確定と未確定を分ける」（口頭の決定） |

## PMO

| 原資料の要点 | 反映先 |
| --- | --- |
| 人がいなくても回ることを目標にする。口頭説明なしで動ける資料 | REF「運用を整えるときの目安」 |
| 資料を読む人の役割ごとに分ける | 同上 |
| ルールは通常を基準に、例外は差分だけ書く。検証用の場所で試してから移す | 同上 |
| 締切を曜日で固定し、例外条件と緊急時の範囲を先に合意する | 同上、REF 表 |
| 稼働の超過・不足は内部→顧客の順で共有。アラートは見た記録を残す | SKILL「先に伝えるべきリスク」、REF「運用を整えるときの目安」 |
| デイリー・定例の進め方、決まったこととアクションを残す | REF「運用を整えるときの目安」 |
| 「どこに聞けばいいか分からない」はいったん受けてつなぐ | 同上 |

## 振る舞いの型・出力

| 原資料の要点 | 反映先 |
| --- | --- |
| 先回り→仮置き→決定権を返す | SKILL「仮置き案を添える」・冒頭 |
| 思考の途中をメモとして早めに出す | 部分対応。SKILL「仮置き案を添える」で仮置きと明記して出すことだけを扱う。途中経過の共有の習慣は規定しない |
| 顧客との間にフィルターと窓口を作る（見せる基準、確認事項の置き場所、前倒しの確認、起票前の確認） | REF 表（確認事項の置き場所）。案件固有の基準・ステータス名は不採用 |
| 型は横展開し、中身は相手次第 | REF 冒頭（ある案件の運用を別案件の規則にしない） |
| 進行役がいる場では文脈だけ補う | SKILL「相手に合わせて渡す」、REF「進行役がいる場では発言しない」 |
| 判断者が空いていれば、依頼された役割を超えて実質PMとして動く | 不採用。役割の拡張は権限の判断であり、本Skillは判断者の不在を論点として示すまでに留める |
| 依頼には期限と重さを添え、順番を示し、受け手の負荷を守る | SKILL「相手に合わせて渡す」末尾 |
| 出力の型（要点・確認したいこと・未決と判断者・リスク・仮置き案・渡し方） | SKILL「出力の形」（任意の例として） |
| 材料が少なければ判断に必要な問いを返す／事実は答え、不明は要確認 | SKILL 冒頭 |

## 配布しないもの

- 実在の人物名、案件名、組織の略称、顧客・同僚の発言の引用、個人への評価。
- 特定の人物の口調・語尾の再現（個人版の「文体」）。配布版は口調を規定しない。
- 新しい立場で前提を聞きに行く「ポジション取り」等、人物像からの推論。
- 原資料が前提とする、配布物に存在しない個人用Skill（議事録整形・チケット文面作成）への参照。配布版は既存の`work-coordination`・`tracker-issue-writing`等へ振り分ける。
