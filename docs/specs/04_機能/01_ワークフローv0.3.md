# v0.3 ワークフローの振る舞いと追跡

## 一時stagingの完了条件

Issue stagingは生成時の`local-active`から、quick・pocではStep 4、fullではStep 8の耐久トラッカー書き込み後再読取一致によってだけ`sync-verified`へ進む。Step 4同期済みquick/pocのfull昇格はtrackerと旧同期証拠を保持した`promotion-active`となり、同じIssueをStep 8で再同期すると`sync-verified`へ進む。`promotion-active`はPR-readyでもcleanup-readyでもない。利用projectの保持期限を経過すると`deletion-ready`になり、専用previewと承認済みhashによるapply後に`deleted`となる。同期証拠不明、mode別成果物不足、内容変更、legacy成果物ありは`retained`であり、年齢だけでは遷移しない。

## Step強制機構

Step 0〜11の機械定義は`src/domain/workflow.ts`の`WORKFLOW_STEPS`、`MODE_STEP_SEQUENCES`、`NEVER_SKIPPABLE_STEPS`を正本とする。`quick`と`poc`でもStep 0、1、4、9、10、11は省略できない。規範文書の表とモード列は`workflow:check`で完全一致を検査し、片側だけの変更をbuildとprepackで拒否する。

Step 0はQ-01〜Q-08の回答・根拠と判定結果を`00_モード判定.json`へ正準JSONで保存し、Step実施は`journal/steps.jsonl`へ行順で追記する。再実行による同一Stepの重複は最後の行を採用し、時刻順では判定しない。モード変更はquickまたはpocからfullへの単調昇格だけを許可する。昇格前に完了したStep 0・1は継承するが、旧modeのStep 4・9はfullの完了証拠にはせず再実施する。full補完中の`upToStep`より後ろにある昇格前履歴だけを順序違反へ数えず、通常fullの未来Stepは除外しない。補完したStepの最新行が以後の順序証拠になる。

`pr create`はStep 10までのjournal、Step 4と10、`sync-verified`を外部操作前に検証する。欠落時はStep番号、skill ID、単一責務を返し、quickのStep 4が省略不能であることを明示する。無条件bypassは持たず、対象Issue、scope、指示者、理由、指示日時、失効日時へ拘束した有効なHumanOverrideだけをjournalへ追記して欠落を受容できる。PoCと`merge.mode=disabled`は、成功したPR作成を`outcome=pull-request`のStep 11終端Evidenceとする。`assisted`のauthority待ちは`pr-bound`のまま再開条件を返し、Step 11を追記しない。full・quickの`automatic`ではPR作成後を`merge_pending`とし、Step 11は追記しない。別操作の`pr merge --staging=<PR作成時と同じstaging>`がPoC禁止とworkflow前提を再検証し、auto-mergeのmethod・requestedAtまたはmerge queueのentry ID・state・requestedAt・head/base OIDを`merge-observed`として保持する。providerから同じPRの`merged`状態、provider mergedAt、merge commit SHAを再観測した後だけ`outcome=merged`のStep 11を追記する。

PR作成前の`create-prepared`はrepository、canonical IssueとURL、head ref/SHA、base refと作成時base SHA、canonical title/body digest、closing契約digestを保持する。作成後read-backをsame-repository headと同じcontentを含むidentityへ照合した`pr-bound`だけがmergeへ進める。merge直前のexact-head再認可後、外部副作用より前にmethod、認可HEAD、intent IDを`merge-prepared`へ保存する。通常のbase SHA前進は許容するがbase refは固定し、provider default branch tip、PR base SHA、current trusted policy commitを一致させる。曖昧な外部結果は副作用を再送せずprovider read-backで解決し、確定不能なら`reconciliation-required`へ進む。一度もdispatchしていないprepared intentは、provider上の対応するPR、auto-merge、queue entryが存在しない決定的Evidenceがある場合だけ同一intentを1回再試行できる。Step 11 journalを先にfsyncし、そのdigestとoutcome・evidence IDをdelivery stateへ保存する。その間の停止は同じcommandからstateだけを復旧する。これらの状態は同じproject・Issue stagingだけに保存する。

## ドメイン不変条件

一時ステージングは正本ではない。`quick`は根拠付きで8問すべて真の場合だけ許可し、必要時は`workflow promote-full`で同じIssueと履歴を維持して`full`へ単調昇格する。`poc`は観測期間を待たず、隔離疑似project fixture、runner ID・path・固定argv、use case・BDD scenario・機械observableを持つ完全なPoC宣言と根拠付きhigh risk不在確認がある場合だけ許可する。要求時点で未実装digestを要求せず、ASCが実装後のexact HEAD blobからfixtureを復元し、固定Node runnerをLinuxのbubblewrap・prlimit・timeout・出力上限下で隔離実行してprocess終了値とdigestを測定する。任意shell・外部Evidenceは受理しない。Evidenceは`poc-observations/<headSha>.json`へ世代別append-onlyで固定し、Step 9以降を同じheadSha/evidenceDigestへ拘束する。review修正は新HEAD世代を追加し、旧世代を残したまま前進する。baselineおよびprovider観測baseからHEADまでの実Git差分がfixture root外なら拒否する。公開API、個人情報、機密情報、外部公開、不可逆操作があれば停止するか明示的に`full`へ昇格する。`poc`はPRで停止し、release、自動merge、本番cleanupを拒否する。正式開発への昇格では01/02/03を補完する。Step 3・7はreadiness check、Step 10はexact-headの有限reviewとする。実装中発見は契約を変えない限り記録して前進し、契約変更時も影響成果物だけを再確定する。最終レビューは肯定・敵対の両観点を必要とし、Medium/Lowは自動反復を起こさない。full/quickのdelivery、candidate policy自己承認防止、cleanup前提は各専用契約に従う。

依存グラフ、authority、evidenceの循環は汎用validatorで拒否し、各projectが実ソースからgraphを収集するadapterを所有する。このrepositoryは`architecture:check`をCIとprepackで常時実行し、仕様記載だけを循環防止の証拠にしない。

内容成果物を作るStep skillは正確なtemplate path、作業開始前の全文読取、正規成果物を自身の契約に持つ。同期など直接templateを使わないStepは非適用理由を持つ。全12 skillのfrontmatter、対応集合、実在・containmentはbuild gateで検証し、AIのファイル名推測へ依存しない。

Package lifecycleの公開入口はpackage runnerの`npx`とし、**取得元はnpm registryではなくGit remoteである**（`npx github:<owner>/<repo>`。版の固定は`#<tag>`）。公開commandは`install`、`update`、`delete`、`doctor`である。文書中の`npx agent-skill-chain <command>`はGit remote指定の短縮表記であり、registryの解決を意味しない。変更系3 commandは無指定をpreviewとし、`--apply`がある場合だけ書き込む。旧`init / upgrade / uninstall`は既存呼出しを壊さない互換aliasに限定し、help、利用案内、新規自動化では公開しない。package名・bin、help、中央利用案内、仕様の一致をbuild gateで検査し、E2Eはnetworkに依存しないlocal bin解決を介して実際の`npx`経路を検証する。

`install`は共通host skill登録アダプターをClaude Codeの`.claude/skills/asc-step/SKILL.md`とCodexの`.agents/skills/asc-step/SKILL.md`へ配置し、managed asset記録へhashを保存する。全書込先は適用前に対象root内へ解決し、親symlinkによる境界外移動を拒否する。`update`は管理中の一致hashだけを更新し、未管理でもpackage正本とbyte一致する同名fileは`adopted`として採用し、異なる内容は`retained`として保持する。`delete`は管理hashが一致する2fileだけを削除し、同じhost directory内の他skillを削除しない。`doctor`は全managed assetと、正本、両host file、managed hash、frontmatter、Workflow・Step正本linkを検証し、不一致pathを含む診断でunhealthyを返す。現行Codex adapterだけを含む`.agents`はlegacyとしない。

## merge完了フロー

merge後にlocal processが残らない経路を通常系として扱い、`worktree survey`が登録済みworktreeを事後走査する。純粋な分類はprimary、未mergeのin-progress、merge済みで安全条件を満たすcleanup-ready、保持理由が1件以上あるretainの順で判定する。未知・不正入力はentry単位でerrorへ分離し、正常entryの判定を継続する。走査と`doctor`は報告だけを担い、削除責務を持たない。削除は既存`worktree finalize`の単一対象evidence経路へ分離し、`worktree hygiene`の登録済みworktree除外を維持する。

cleanup-readyとfinalizeは`assessWorktreeRemovalSafety`の判定を共有する。ignore対象はpackage既定の`node_modules/`・`dist/`とtrusted project policyの安全なdirectory prefixだけを再生成可能とし、それ以外または種別不明をpath付き保持理由にする。追跡対象変更、未追跡file、stash、未push・remote branch、merge、復旧到達性、`.worktrees/`直接の子という条件は共通判定で維持し、allowlist内の生成物だけを理由から除く。

`worktree finalize --complete`は、`merge-confirm`、`root-update`、`cleanup-preview`、`cleanup-apply`、`post-verify`の順に進む。merge未確認またはroot更新拒否ではcleanupへ進まない。root更新が成功または既に同じmerge SHAであればcleanup previewまで進み、対象のcanonical pathとbranchの完全一致、安全条件、最新digest、cleanup専用authorityを順に検証する。

cleanup authorityがない場合はroot更新済みでも`pending`とし、対象worktreeを保持する。digest不一致、状態変化、cleanup失敗、root SHA・対象path・他worktreeの事後確認不一致は`completed`とせず、root更新済みの範囲と未完了phaseを`partially-completed`として返す。対象が既に削除済みなら再削除せず、事後確認が一致した時点で冪等に`completed`へ収束する。

## risk比例型policy enforcement

Ruleは`ruleId / purpose / riskClass / scope / enforcement / activation / owner / targetLayer / evidence / remediation / overridePolicy / rollback`を持つ。`active deny`は安全境界だけをblockし、`staged deny`は計測可能なpending、`disabled`はrecordへ縮小する。機械diagnosticを言語非依存の判断正本とし、caller/project adapterがproject choiceの`language`で表示する。組込みの`messageJa`は表示adapterがない場合の非authority fallbackであり、許可・拒否判断には使わない。根拠、確認、dry-run修正候補、最小authority、rollbackは機械fieldとして保持する。

Policy migrationはtrustedとcandidateを分離し、`policy / schema / runtime / CI / template`を同じplanでpreviewする。正当なstaged追加は許可し、trusted ruleの削除・弱化・non-override緩和は候補自身の条件として有効にしない。

## Agent Routing機能

role解決はscope、coordinator identity、reviewer identityとproject choiceを入力に、coordinator、implementer、reviewerのidentityとproviderを返す。既存routing形式のfallbackがClaude coordinatorをimplementer候補へ解決しても、role operation契約はcoordinatorによるproduct実装を許可せず、独立implementerへ再割当するまで停止する。implementerとreviewerが同一identityまたはcontextへ解決する設定・reviewも拒否する。Step 6、9、10は6 role、許可path・操作、必要証拠、能力tier、provider上限、fallback、独立性証拠を入力契約として持つ。

model解決はtrusted provider capability mappingがcoding能力と`provider_recommended_default`選択元を許可していることを確認し、Codex公式`model/list`のpicker-visible一覧から`isDefault=true`かつreasoning effort high対応のmodelを一意に選ぶ。recommended defaultが0件または複数、high非対応、観測不能ではCodexの順位を推測せず、`routeMode=fallback`、`provider=claude`、`modelSelection=project_default`としてClaude実装へ切り替える。standard speedはmodel選択と独立にservice tier defaultへ解決し、実行直前の再検証または実行提案で値が変われば開始を拒否する。project mappingも汎用機能も個別model slugを保持しない。
