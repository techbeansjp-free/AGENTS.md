# グラフ投影実装計画

## 文書の責務

本書は`REQ-GR-001`〜`REQ-GR-014`を具体化する**詳細設計**と**実装計画**を所有する。要求・要件・受け入れ条件は`../02_要件/05_グラフ投影要件.md`を正本とし、本書が新しい要求を暗黙に追加しない。

## 目的

本計画は、`REQ-GR-001`〜`REQ-GR-014`を、ASCの開発速度を落とす新しい同期Gateにせず実装・検証・deliveryする順序を定める。計画の完了は実日数の経過ではなく、隔離疑似projectを含む定義済みEvidence Setとexact-head reviewで判定する。

## 完了状態

完了時には次が成立する。

1. Git/text/providerの耐久事実が正本、GraphQLite v0.6.1 databaseがworktree固有の破棄可能な派生投影である。
2. Node.js 22.13.0以上で、固定digestのGraphQLite extensionを明示的にinstallできる。
3. 同じ意味sourceからcanonical hashが同じGraphを完全再構築できる。
4. manifestと実databaseのread-backでdriftを検出し、stale Graphをexact Evidenceへ使わない。
5. bounded BFS、Kahn、iterative Tarjan、BFS/Dijkstraが決定論的な部分結果とcounterを返す。
6. Graph EvidenceはGateの構造証拠として使われ、AI推論・inferred edge・不完全探索をPASS根拠にしない。
7. Full、Quick、PoCの別modeを維持した疑似projectで、通常・境界・失敗・復旧を待機なしに観測できる。
8. Graph破損、schema mismatch、builder mismatch、source前進、別worktree混入から人間質問なしで安全にrebuildできる。

## 実装原則

- **正本を増やさない:** Graph writeはcanonical snapshotの全置換だけにし、Graph内でRequirementやFindingを独立編集しない。
- **Domainをstorageへ依存させない:** node・edge、validator、hash、algorithm、drift判定はGraphQLiteをimportしない。
- **full rebuild first:** incremental updateより先に、完全再構築・決定性・worktree isolationを完成させる。
- **query before inference:** 確定sourceから得られるedgeを先に使い、推論edgeはcandidateへ分離する。
- **hard bound first:** timeoutだけに頼らず、入力規模とoperationの上限をDomainで数える。
- **Evidence before PASS:** AIの説明ではなく、再実行可能なtest・hash・read-back・CI・reviewをGateへ使う。
- **forward-only discovery:** 実装中の事実はdiscovery recordへ追加し、契約を変えない限り要求から全工程を再起動しない。
- **small commands:** install、rebuild、status、impact、path、orderを分離し、read-onlyとwrite authorityを混ぜない。

## WP-02 Repository projectorを実装する

### 変更

`src/adapters/repository-graph.ts`へ、repositoryの意味sourceをcanonical snapshotへ投影するbuilderを実装する。

### 入力

- `git ls-files -co --exclude-standard -z --`で得るtracked・untracked・not ignored file
- `.md`、`.json`、`.yaml`、`.yml`、`.ts`、`.mjs`、`.feature`の有限集合
- GitのHEAD、tree、absolute git directory、repository root、origin identity、dirty state
- Git管理されたtrace table、review artifact、policy・workflow・Evidence manifest
- provider事実は既存stateへ耐久化済みのものだけ。projectorがnetworkでproviderを再探索しない

### 投影規則

1. source pathを検証・辞書順化し、fileごとにsize・SHA-256・stateを記録する。
2. source集合のcontent digest、HEAD、tree、dirty、worktree IDを構築前に計算する。
3. repository、worktree、commit、file nodeを生成する。
4.正式IDのRequirement、Acceptance Criteria、Scenarioをsource line付きnodeへ変換する。
5. architecture文書、review artifact、tracked implementation fileをnodeへ変換する。
6. trace tableの1行ごとにRequirement→AC→Scenario→Feature→Implementationを直接edge化する。Feature単位の共有からScenarioごとのimplementationを推測しない。
7. TypeScript ESM import、type import、re-export、dynamic import、CommonJS requireの静的に確定するrelative依存だけを`imports`へ投影する。
8. 不確定なsymbol resolutionやcaller/calleeをdeterministic edgeとして捏造しない。
9. 構築後にsource集合とidentityを再観測し、1件でも変化したらsnapshotを破棄する。

Domainのnode・edge kind一覧は拡張可能なschema vocabularyであり、Repository Projectorの実装済み能力ではない。`REPOSITORY_GRAPH_PROJECTOR_CAPABILITY`を現行builderのmachine-readable正本とし、materialized node kindはrepository、commit、requirement、acceptance-criteria、design、file、scenario、review、worktree、edge kindはcontains、imports、references、has-acceptance-criteria、verified-by、satisfied-by、supported-byだけとする。projectorはこの集合外を生成した場合に失敗し、未実装のADR、symbol、test、finding、evidence、provider node等を能力表示へ含めない。

trace tableのbacktick pathはsource集合との完全path一致を要求する。存在しないFeatureまたはImplementation path、または生成前のedge endpoint不足をfilter・skipせず、`trace-endpoint-missing`または`edge-endpoint-missing`、trace source path・line、対象endpointを含むstable diagnosticで完全構築をfail closedにする。

### 資源上限

- 1 source fileの上限: 4 MiB
- source集合: 128 MiB
- ECMAScript import scan: lock済みTypeScript 5.9.3 compilerとlicense・third-party noticeをbuild時に固定SHA-256検証して`dist/vendor`へcopyし、Graph操作時だけlazy loadする。1 fileあたり250,000 tokenかつ250,000 AST nodeを上限とし、parse diagnostic、parser stack/resource failure、上限超過はsource path付きでfail closedにしてASTは再帰せず明示stackで走査する
- NULを含むbinaryはcontentをparseせずfile metadataだけを扱う
- directory walkでrepository外、ignored runtime、他worktreeを探索しない

### Test

- 同じclean commitを2 worktreeでbuildしcontent hash一致
- 片方だけdirtyにしてSource Identityとsnapshot差分を検出
- rename、delete、untracked、ignored、symlink、NFC、path traversalの反例
- import alias、複数行import・re-export、dynamic import、require、`index.ts`解決とcomment・string・regex・JSX textを越える偽陽性の拒否、malformed sourceとparser resource境界のfail closed
- trace rowのScenario別implementation mapping
- Requirement→AC→Scenario→Feature/Implementationをedge kind限定のbounded traversalで到達確認
- schema vocabularyとRepository Projector capabilityの非同一性、およびsnapshot kindがcapability内であること
- 存在しないtrace Feature/Implementation endpointのstable diagnostic
- build前後のTOCTOU source変更

### 完了Evidence

同一fixtureの繰り返しbuildでcanonical snapshotが一致し、malformed sourceは理由付きfail closedとなり、実repository外をread/writeしない。

1. canonical snapshotを再検証し、200,000 node、1,000,000 edge上限を確認する。

## WP-04 決定論的bounded algorithmを実装する

GraphQLiteはstorage・parameterized Cypher queryへ使う。Gateに用いる探索はDomainでcanonical snapshotを読み、ASCのbudgetとtie-breakを適用する。GraphQLite builtin algorithmは、この契約との同値性を独立に証明するまでGate結果に用いない。

### 共通budget

| field | 既定値 | 算入対象 |
|---|---:|---|
| `maxDepth` | 64 | startからのedge深度 |
| `maxVisitedNodes` | 20,000 | startを含む確定訪問node |
| `maxVisitedEdges` | 100,000 | 列挙・検査した対象edge |
| `maxResults` | 10,000 | 返却node、componentまたはpath node |
| `maxOperations` | 250,000 | 初期化、heap、edge処理等の明示counter |

すべて正の整数を要求する。operation数の完全なmachine instruction一致は要求せず、同じ実装・入力で再現するDomain operation単位を定義する。

query budgetの前段に、共通Domain定数`MAX_SEMANTIC_GRAPH_NODES = 200_000`と`MAX_SEMANTIC_GRAPH_EDGES = 1_000_000`によるinput/projection envelopeを置く。公開Domain入口、GraphQLite Store、repository projectorは同じ定数を使用し、raw `length`をO(1)で確認してからvalidation、canonicalization、hashまたはiteratorへ進む。上限ちょうどは許可し、上限+1は入力内容へ触れずfail closedにする。

BFS・Dijkstraは第一層で上限化されたeligible edgeを一度だけ`O(E)`でunsorted adjacencyへ分類する。query counterにはfilter後に実訪問するadjacencyだけを算入し、訪問listが残budgetを超える場合はsort前に`budget-exceeded`とする。Kahn・TarjanはGraph全体が探索対象なので、node・eligible edgeのindex追加をoperationへ算入し、上限到達前に停止する。

### BFS

- 複数startをdedupe・辞書順化し、start自身をnode・result・operationへ算入する。
- outgoing・incoming adjacencyをedge kindとcertaintyでfilter後にcanonical順化する。
- FIFO queueをcursor indexで実装し、`shift()`による二次コストを避ける。
- depth上限の先に未訪問neighborがある場合は`budget-exceeded`とする。
- 不完全結果は上限以内のnode列とcounterを返す。

### Kahn

- すべての対象edgeを一度走査してindegreeを作り、edge・operation budgetへ算入する。
- indegree 0のnodeをbinary min-heapへ入れ、stable ID順にpopする。
- 完全orderが得られなければ残GraphをSCCへ渡す。
- arrayの先頭削除・反復全sortを避け、基準計算量を`O((V+E) log V)`にする。

### iterative Tarjan法

- recursive callではなくexplicit frame stackを用いる。
- index、lowlink、active stack、on-stack集合を保持する。
- component内ID、component列を辞書順化する。
- self loopをcycleとして別途保持し、1 node SCCを欠落させない。
- node・edge・result・operation上限到達時は完全SCCと報告しない。

### 最短経路

- edgeにweightが1件もなければlayered BFSを使う。
- weightがあれば全対象weightの非負・有限を確認後、binary min-heap Dijkstraを使う。
- state優先度をdistance、canonical path key、node IDの順にする。
- same distance時もpredecessorとheap stateをcanonical tie-breakで更新する。
- 到達不能、invalid、budget exceededを別statusにする。

### テスト

`test/features/unit/semantic-graph.feature`の`SCN-UNIT-SEMGRAPH-002`〜`019`を主Evidenceとし、挿入順を変えたdifferential test、dense・deep・self-loop・parallel edge・negative weightを反例にする。

### 完了Evidence

- すべての部分結果とcounterが指定budget以内である。
- 同値Graphの異なる挿入順でresultが一致する。
- Kahnのedge制約、SCC partition、shortest distanceを小規模reference実装とdifferential比較する。
- mutationでtie-break、budget check、self-loop判定、負weight検査を外すと対応scenarioが失敗する。

## WP-05 drift、CLI、Evidence Gateを統合する

### 鮮度判定pipeline

1. projectorで現在Source Identityをread-only構築する。
2. GraphQLite asset version・digestをplatform catalogから解決する。
3. pointer、database manifest、database snapshotを順に読む。
4. snapshotをcanonical化してhashと件数を再計算する。
5. expectedとobservedを`assessGraphFreshness`へ渡す。
6. 複数drift reasonをstable順で返す。
7. exact Evidenceは理由0件の場合だけ許可する。

### CLI command一覧

| command | write | 主な結果 |
|---|---|---|
| `graph install --dry-run\|--apply` | applyのみ | asset identity、配置先、preview/present/installed |
| `graph rebuild --dry-run\|--apply` | applyのみ | Source Identity、snapshot件数・hash、generation、manifest |
| `graph status` | なし | fresh、exact Evidence可否、reason、recovery |
| `graph impact --start=...` | なし | direction、node列、counter、status、reason |
| `graph path --from=... --to=...` | なし | algorithm、path、distance、counter、status |
| `graph order --edge-kinds=...` | なし | order、SCC、counter、status |

### Gate契約

Graph query Evidenceへ次を保存する。

- source identityの完全値
- schema・builder・extension identity
- graph content hash、node・edge count、generation
- command・query input・edge kind・direction・certainty policy
- 全budget
- status、result、counter、reasonの完全値
- 実行HEADとEvidence artifact digest

Gateはfresh + exact evidence allowed + deterministic only + completeを構造Evidenceの必要条件にする。これを満たしても、Executable Test、Static、Type、Contract、CI、独立review等の該当Evidenceを省略しない。

Graph Evidence envelopeの権限値は固定で`authority: none`、`mergeAuthorization: false`、`modeAuthorization: false`とする。Graph freshnessや到達性はmode、release、provider write、mergeのauthorityへ変換せず、既存workflow mode・delivery Gateの入力を補助するだけとする。

### 復旧

- read-only command: drift reasonと`graph rebuild --apply`を返して停止する。
- apply authorityのある自走経路: recoverable driftなら完全rebuildし、read-back後に元queryを1回だけ再試行する。
- unsupported asset、sourceの継続変化、権限不足、path境界違反: 自動で推測・権限拡張せず、再開条件を返す。

### 完了Evidence

CLI usageと実装flagが双方向一致し、read-only commandでfilesystem・network writeが0件、injection反例が固定parameter queryを逸脱せず、stale・inferred・budget exceededがGate PASSを拒否する。

### Review観点

| 観点 | 主な反例 |
|---|---|
| 正本境界 | Graphだけに存在するRequirement・Finding・Evidence |
| supply chain | unpinned latest、digest不足、symlink extension、mirror fallback |
| injection | 任意Cypher公開、文字列連結、unknown parameter黙認 |
| isolation | shared DB、別worktree pointer、root外runtime |
| determinism | timestamp/path混入、unordered adjacency、unstable tie-break |
| completeness | malformed inputを空Graph化、不完全探索をcomplete化 |
| drift | manifestだけの照合、実DB hash未検証、stale exact Evidence |
| availability | pending generation公開、破損時の人間質問、rebuild不能 |
| resource safety | wall timeoutだけ、start/baseline operation未算入、上限超過後check |
| mode | Graphを理由に一律Full、PoCを正式Evidenceへ昇格 |
| speed | 全変更で無条件rebuild、同じscopeの上流review反復、実日数の観測待ち |

### Delivery

1. exact implementation HEADを固定する。
2. final review artifactだけを加え、実装・仕様・testを変更しないfinal HEADを作る。
3. PRへ要件、主要設計判断、Evidence、Graph runtimeをGit管理しないこと、非Graph Node 20互換とGraph Node 22.13境界を記載する。
4. required CIと独立approvalを同じHEADへ結び付ける。
5. merge前にprovider read-backでhead、base、checks、review、mergeabilityを再検証する。
6. merge後はmain側GraphDBをbranch DBとmergeせず、main sourceからrebuildする。

## Riskと対処

| Risk | 兆候 | 予防・検出 | Recovery |
|---|---|---|---|
| GraphQLite releaseの互換性 | load failure、wrong result | version/commit/asset固定、actual smoke、round-trip | adapterを無効化しSource of Truthから再評価。Domain契約は維持 |
| extension supply-chain汚染 | size/digest不一致 | HTTPS公式URL、固定size + SHA-256、symlink拒否 | fileをcurrentにせず再取得 |
| projection stale | source/manifest/hash差 | build前後identity、実DB read-back | complete rebuild |
| worktree汚染 | worktree ID不一致 | root containment、absolute git dir digest | 対象worktreeでrebuild |
| query資源枯渇 | dense/deep Graph | 全hard budget、iterative Tarjan、min-heap | budget-exceededとして部分Evidenceを返す |
| 非決定結果 | 挿入順で差 | canonical ordering、tie-break、differential | Gate利用停止、algorithm修正 |
| false negative impact | incompleteを影響なし扱い | statusをEvidence契約へ含める | budget拡大または別Evidence |
| Graphを新正本化 | Graph-only edit/CRUD | replace-only Port、runtime ignore | Graphを破棄し正本からrebuild |
| 開発速度低下 | 全commandでrebuild | status first、必要時だけrebuild、targeted test | 計測からbottleneckを限定最適化 |
| runtime境界の混同 | package全体をNode 22.13へ上げる、Node 20でGraph adapterを静的loadする | package engineはNode 20を維持し、Graph commandだけguard後にdynamic import | Node 20配布bin smokeとNode 22.13 Graph suiteを再実行 |

## 最適化の有効化条件

Base Graph、worktree delta、incremental update、shared read-only cacheは本実装の完了条件ではない。次のすべてを満たす別変更でだけ有効化する。

1. ASC規模または代表疑似projectでfull rebuildが測定上のbottleneckである。
2. 完全rebuildとのdifferential testでcanonical hash、node、edge、query resultが一致する。
3. cache keyがrepository、commit/tree、schema、builder、source digest、platform contractを包含する。
4. worktree間write共有がなく、poisoned cacheを検出・破棄できる。
5. cacheなしの完全rebuild fallbackを維持する。
6. 最適化失敗がGateのfalse PASSを生まない。
