# 信頼境界

- パス、Unicode、シンボリックリンク、Git remote、repository、branch、HEAD SHA、認証、認可、外部観測状態を信頼しない。
- 読み取り結果だけに依存せず、書き込み・削除直前に対象と状態を再検証する。
- 候補PR内のpolicy変更は当該PRのmerge判断に使用しない。
- review、test、spec証拠は同じHEAD SHAへ結び付ける。
- merge、Issue close、branch削除、release、cleanupを別操作として認可する。

## project choice差分の信頼境界

trusted側に`projectChoices`がある場合、candidateとの差分はfield単位で次の3分類へ分ける。object全体のfingerprint不一致だけを理由に一律拒否しない。

| 分類 | 対象 | 判定と処置 |
|---|---|---|
| authority | `release`、`ci` | 値の変更をASC-TRUST-001で拒否し、既定ブランチのproject policy ownerによるtrusted側の先行更新とauthority fieldの復元方法を案内する |
| 弱化 | test層、禁止test suffix、禁止型、strict型検査、capability、補助言語宣言の単調性違反、および未知field・型不正 | 検証の縮小、`applicable`の格下げ、宣言削除をASC-TRUST-001で拒否し、弱化の取消しまたは強化方向への変更を案内する |
| 許可 | authority境界外の既知field、説明・証拠、`modelMapping`、検証の拡大 | 変更field pathを記録して拒否しない |

test層、禁止test suffix、禁止型の追加、`not-applicable`から`applicable`への変更、補助言語宣言の追加は検証強化として許可する。`modelMapping`をlegacy文字列から検証済み構造化値へ変更するなど、authority境界外の変更は、ほかのpolicy・品質条件を満たす限り正当な拡張経路として通過する。未知fieldおよびobjectでない入力は、型定義の拡張を黙って自己適用しないようfail-closedで弱化へ分類する。

| 脅威 | 予防 | 検知・復旧 |
|---|---|---|
| パス走査・Unicode偽装 | NFC正規化、基準内解決、制御文字拒否 | 副作用前に拒否 |
| repository誤認 | URL構文解析とowner/name完全一致 | 外部書込を行わず診断 |
| 部分書込 | 隣接一時領域と原子的rename | 未公開一時物を除去し既存状態を保持 |
| TOCTOU | 適用直前の再検証と最新状態hash | 不一致時に拒否し再計画 |
| 秘密混入 | 引数配列、伏字化、配布許可リスト | CIの配布物検査 |
| 候補policy自己緩和 | default branchのtrusted ruleと強度・activation・overrideを比較 | ASC-TRUST-001でnon-override拒否しcandidate差分をrollback |
| project choiceによるauthority変更・検証弱化 | trustedとcandidateの差分をauthority、弱化、許可へfield単位で分類 | authority fieldをtrusted値へ復元し、弱化は取消しまたは強化方向へ変更する。許可差分はfield pathを記録して継続 |
| 品質validator自己変更 | base validatorでprotected file・package fieldのbefore/after SHA-256と品質契約versionを比較する。同一PRで追加したproposalはauthorityにせず、baseに既存の`staged` proposalとの完全一致だけを許可する | 未登録、部分一致、proposal削除・変更、version飛越しを拒否し、protected差分を適用しない |
| override逸脱 | target ruleId、expected ruleId、override record ruleIdの三者、およびIssue、scope、actor、理由、期限、SHAの完全一致 | cross-rule再利用を監査記録なしで拒否しowner authorityを診断 |
| trusted ref不明 | origin/HEADをcommit SHAへ固定できなければauthority operationを停止。PR CIはtrusted GitHub providerが観測したexact repo/PRのdefault base ref/OIDとhead OIDを明示入力へ拘束する | candidate/worktree/package install元floorへfallbackせずremote構成またはprovider入力を修復 |
| provider capability mappingの自己適用 | provider能力、公式選択元、project choice、conformance bindingはtrusted refのGit objectから読み、candidate worktreeの同名資産を読まない。具体的model slugとrankはmappingへ保存しない | candidate headをtrusted refとして使う評価と固定slug・手動rankの持込みをpendingにし、mapping ownerによるtrusted側更新を要求 |
| routing評価器の自己評価 | candidateが`src/domain/routing.ts`または`src/domain/routing-independence.ts`を変更した場合はevaluatorRefを記録し、candidate headの評価結果をauthorityにしない | evaluatorRefがtrusted refと一致する評価だけで再開する |

`providerFiles`、`project/providers/`、構造化`modelMapping`はtrusted policy loaderの入力文法を拡張するため、同じcandidateで文法追加とproject設定activationを完結させない。第1段階はlegacy文字列と既存inventoryを保持したままschema・validator・runtimeだけを追加し、mainのtrusted validatorでcandidate全体を検証する。第2段階は第1段階のbranchまたはmerge済みcommitをtrusted baseとしてproject mappingを有効化する。同一PRで追加した入力文法をcandidate自身のauthorityとして使う構成は拒否する。
| routing evidenceへの秘密混入 | 入力を未知field拒否の保存許可listで検証し、credential、prompt、メールアドレス、stderr本文を保存しない | 不正なfield、識別子、容量超過を副作用前に拒否する |
| role設定による自己review | reviewerへimplementerと異なるidentityという独立性制約を必須化し、同一providerかつ同一論理tierへ解決する設定を設定検証時に拒否する | BR-836-12の拒否診断を返し、実装とreviewを開始しない |
| fallbackのrole混同 | Codex preferred routeではcoordinatorとimplementerを分離し、Claude fallback routeだけでcoordinatorをimplementerへ昇格する。両routeでreviewerはimplementerと異なるidentityを必須とする | routeMode、modelSelection、routingReason、identityをevidenceへ拘束し、route不一致を実行直前に拒否する |

Non-override対象は秘密保護、Git内部領域、remote/worktree同一性、不可逆操作、成果物汚染、候補自身の承認防止である。環境変数や無期限flagはoverride authorityにならない。

Agent Routingの信頼方向は、trusted ref側のproject choiceとprovider capability mapping、およびprovider実行入口のread-only観測からrouting decisionへ、routing decisionからrouting evidenceと実装差分へ向かう一方向とする。candidateが変更したmapping、choice、resolver、独立性validator、conformance bindingを同じcandidateの選択・review・merge authorityへ使わず、completion recordやreview判定からrouting decisionへ戻る辺も認めない。
