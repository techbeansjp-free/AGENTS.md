# 信頼境界

- パス、Unicode、シンボリックリンク、Git remote、repository、branch、HEAD SHA、認証、認可、外部観測状態を信頼しない。
- 読み取り結果だけに依存せず、書き込み・削除直前に対象と状態を再検証する。
- 候補PR内のpolicy変更は当該PRのmerge判断に使用しない。
- 候補PR内の`issueProject`追加・変更は、当該PRのProject item追加またはStatus更新authorityに使用しない。trusted default branchの設定だけを使い、未設定ならproviderを呼ばない。
- review、test、spec証拠は同じHEAD SHAへ結び付ける。
- context-isolatedのformal approvalは保存済みreview session・Step 10 binding・tracked H_final artifactの再照合からだけ導出し、candidate申告やartifact本文単体をauthorityにしない。actor-independentはprovider APPROVEDとstable actor分離を維持する。
- context-isolated admin mergeはformal approvalと操作authorityを分離し、GitHub `BLOCKED`自体を許可根拠にしない。repository ADMIN、許可rule閉集合、全check成功、未解決thread 0件、MERGEABLE・exact HEADをproviderから二重観測し、1つでも不明ならadmin dispatchを拒否する。candidate policyからこの許可集合を拡張できない。
- merge、Issue close、branch削除、release、cleanupを別操作として認可する。
- `.gitignore`を再生成可能性の根拠にせず、trusted project policyとpackage既定値から解決したfinalize ignore allowlistだけを削除可能な生成物境界として扱う。

本repositoryの`merge.mode=assisted`への変更も候補による自己適用を許さない。当該policy変更PRは変更前のtrusted policyに従い、repository ownerがGitHubの通常の保護・独立review・CIを満たして既定branchへ取り込む。admin bypassやcandidate側policyをauthorityにせず、既定branchで信頼済みとなった後の対象PRについてのみ、PRごとの明示指示をmerge authorityとして扱う。

## 隔離copy検査のtrust anchor

Gitに依存する隔離copy検査のtrust anchorは、candidateの外部で検査前にrepository・ref・commitを固定し、Git metadataをread-onlyで供給する。candidate内で生成した`.git`、origin、commitはauthorityに使わない。この外部anchorを建てられないときは、検査対象自身のGit状態へfallbackせずfail closedとする。これをTERM-ASC-110およびREQ-SQ-028とし、SCN-1344-001とSCN-1344-002で追跡する。

## deliveryのpackage floor入力

`createPullRequest`へ`trustedPolicy`を供給するcallerは、candidateの有無、preview/applyの別にかかわらず有効な`packageFloor`を型とruntimeで要求される。省略、`undefined`、`null`、不正構造、空の`rules`はprovider呼出し前に固定errorで拒否し、raw入力を診断へ含めない。復旧には`loadEffectiveTrustedPolicySet`が返す`packageFloor`をcandidateから独立して供給する。candidateやそのruleからfloorを導出しない。構造がvalidな偽floorの真正性をdomain単独で証明せず、真正なauthorityの供給はtrusted callerが負う。非trusted previewと共通`resolveEffectivePolicy`のextension合成契約は維持する。

CLIはtrusted loader出力を`commonInput.packageFloor`へ渡し、preview、事前検証、dispatchの3呼出しで同じ入力を使う。正規floorを供給しても、無提案・無sourceの削除は拒否し、trusted提案とsourceが一致する二段階廃止およびpackage floor保護を維持する。

## project choice差分の信頼境界

trusted側に`projectChoices`がある場合、candidateとの差分はfield単位で次の3分類へ分ける。object全体のfingerprint不一致だけを理由に一律拒否しない。

| 分類 | 対象 | 判定と処置 |
|---|---|---|
| authority | `release`、`ci` | 値の変更をASC-TRUST-001で拒否し、既定ブランチのproject policy ownerによるtrusted側の先行更新とauthority fieldの復元方法を案内する |
| 弱化 | test層、禁止test suffix、禁止型、strict型検査、capability、補助言語宣言、tier引き下げ、および未知field・型不正 | 検証の縮小、`applicable`の格下げ、宣言削除をASC-TRUST-001で拒否し、弱化の取消しまたは強化方向への変更を案内する |
| 許可 | authority境界外の既知field、説明・証拠、検証済み`modelMapping`の追加・強化、検証の拡大 | 変更field pathを記録して拒否しない |
| 弱化 | test層、禁止test suffix、禁止型、strict型検査、quality command、capability、補助言語宣言の単調性違反、および未知field・型不正 | 検証の縮小、具体値から`not-applicable`、`applicable`の格下げ、宣言削除をASC-TRUST-001で拒否し、弱化の取消しまたは強化方向への変更を案内する |
| 許可 | authority境界外の既知field、説明・証拠、`modelMapping`、検証の拡大 | 変更field pathを記録して拒否しない |

test層、禁止test suffix、禁止型の追加、`not-applicable`から`applicable`への変更、補助言語宣言の追加は検証強化として許可する。test層、禁止test suffix、禁止型の**縮小**は、既定branch側のproject policyの`projectChoiceShrinkProposals`へ登録した提案とchoices fragment fileのraw byteが完全に一致する場合だけ受理する。提案は既定branch側からのみ読み、候補branch側へ置いた同形の宣言を受理判断に使わない。提案が無い縮小、対象3 field以外の縮小、raw byte列を取得できない経路はfail-closedで拒否する。`modelMapping`をlegacy文字列から検証済み構造化値へ変更するなど、authority境界外の変更は、ほかのpolicy・品質条件を満たす限り正当な拡張経路として通過する。未知fieldおよびobjectでない入力は、型定義の拡張を黙って自己適用しないようfail-closedで弱化へ分類する。

| PoC観測の自己申告・fixture逸脱 | 観測期間の主観報告やcaller作成Evidenceを使わず、repository内の隔離疑似project、runner ID・path・固定argv、use case・BDD scenario・observableをPoC宣言へ固定する。ASCは任意shellを受理せず、HEAD blobから復元したfixtureの固定Node runnerだけをLinuxのbubblewrap・prlimit下で実行する。namespace、read-only mount、timeout、出力上限を主境界とし、Node Permission Modelは補助防御とする | dirty/untracked、symlink・hardlink・特殊file、digest、process終了値、全observable、exact HEAD、baseline/provider baseからのfixture-only実Git差分を再検証する。EvidenceはHEAD別append-only、Step 9以降はdigest bindingとし、同一HEAD差替え、外部path書込、非正常終了、不一致、tool欠落を外部副作用前に拒否する |

Non-override対象は秘密保護、Git内部領域、remote/worktree同一性、不可逆操作、成果物汚染、候補自身の承認防止である。環境変数や無期限flagはoverride authorityにならない。

Agent Routingの信頼方向は、trusted ref側のproject choiceとprovider capability mapping、およびprovider実行入口のread-only観測からrouting decisionへ、routing decisionからrouting evidenceと実装差分へ向かう一方向とする。candidateが変更したmapping、choice、resolver、独立性validator、conformance bindingを同じcandidateの選択・review・merge authorityへ使わず、completion recordやreview判定からrouting decisionへ戻る辺も認めない。

## project rule廃止の信頼境界

project rule廃止提案（TERM-ASC-095）はtrusted側の`projectRuleRetirementProposals`だけから読む。候補側の提案をauthorityへ使わず、effective合成でもtrusted時だけcarryする。固定trusted commitのmanifest、rules、rawEntriesの対応からsourceを導出し、rule IDとraw UTF-8のbefore SHA-256が完全一致する削除だけを承認済みrule廃止（TERM-ASC-096）として返す。reasonとownerは監査入力であり認証に使わず、比較診断にも転記しない。

| 境界 | 拒否条件 | 復旧 |
|---|---|---|
| JSONから提案 | 未知field、非配列、17件以上、exact duplicate、rule ID不正、大文字等のSHA不正、空値・制御文字 | 最大16件の有効な提案をownerが先行登録する |
| trusted sourceから比較 | 欠落、重複、manifest/rule/raw対応不明、ID・hash不一致 | 固定commitを再読取し、観測SHAで提案を更新する |
| trustedからcandidate | 候補自己承認、部分弱化、未提案ruleの便乗削除 | 削除を戻すか各ruleを個別に先行承認する |
| project extensionからpackage floor | 最後のproject ruleを除いてもpackage floorを削除しない。operationの対象rule不在は拒否する | fragmentとmanifest参照を復元する |

validate、file migration、deliveryは同じmatcherへtrusted sourceを配送する。sourceを持たないlegacy monolith経路は全削除拒否を維持する。提案の撤回は別PRとし、自動消費しない。詳細手順は`.agent-skill-chain/schemas/00_利用案内.md`を参照する。

## Git metadataの追加書込境界

追加権限は明示されたworkspace-writeに限定する。rootの通常`.git`directoryはGit出力2件と同一であることを要求する。linkedの`.git`fileはcommon directory直下の`worktrees/<name>`を指し、その`gitdir`はrootの`.git`を、`commondir`は同じcommon directoryを指すことを要求する。common directoryも通常の非bare primaryの`.git`であることをGitで確認し、separate-git-dirを許可しない。

各path componentを正規化前に検査してsymlinkを拒否し、通常file・directory、canonical path、metadataの有限サイズと単一行を確認する。Git管理path・configを上書きする`GIT_*`環境変数も拒否する。provider観測後にdevice/inode、種別、metadata内容とGit topologyを再検証し、変化時はdispatchしない。Git照会は固定argv、各10秒・64KiB上限でありraw出力を公開しない。

common directoryには他branchのrefs等も含まれる。追加許可をGit操作単位の認可とは扱わない。再検証とspawnの間の並行writerを原子的に排除するものではなく、Git/Codexの実行結果と既存のfailed/unknown契約を維持する。

## Codex自動起動の境界

`routing launch`は`loadOperationPolicy`がorigin/HEADの既定branchから固定したpolicyだけを採用判定に使う。candidate worktreeの新しいtierMapping keyは同candidateの認可根拠にしない。**`routing tier`のprovider未指定経路は候補側worktreeのproject choiceを読む互換検証であり、認可に使わない。** 出力の`provenance`と`usage`が判定の信頼源と用途を示し、診断はtrusted側の定義を要求しない。`--provider`は`codex`と`claude`だけを受理する。provider別`provider_recommended_default:high:default` selectorは既存の非空key→tier契約内の採用条件であり、schema fieldの追加や入力文法の自己拡張を必要としない。Claudeの公式initialize応答はrequest ID、成功envelope、model entry、逐語解決ID、effortを厳密に検証し、不明・重複・不一致を安全側で拒否する。keyの配送と当該実行への適用を分離し、起動直前にtrusted commitが変化していないことを再検証する。

公式catalogの観測ではconfig/readで`model_catalog_json`を検査し、選択関連設定だけを固定する。利用者の認証・安全設定全体を消さない。実行argvは固定し、任意model/provider/shell/危険flagを受け取らない。promptはroot内の通常fileをcontainment、symlink、size、open前後のfile identityで検証してstdinへ渡す。promptとraw stdout/stderrを結果証跡へ転記しない。selector採用tierはsandboxやGitHub操作のauthorityを与えず、hostの既存制御を迂回しない。

## ローカルLLM reviewer起動の境界

`routing review-launch`は`implementer`向け`routing launch`（`launchCodex`）とは独立したdispatch経路であり、`src/domain/routing.ts`・`src/adapters/codex-launch.ts`・`src/adapters/codex-execution.ts`へ依存しない（INV-05）。`launchReview`は`loadOperationPolicy`がorigin/HEADの既定branchから固定したtrusted policyだけを採用判定に使い、**dispatch前に再取得したcommit SHAが変化していないことを再検証し、dispatch後（ローカルLLM応答待ちの間）にも同じ再検証を行う。** dispatch前の検証だけでは、ローカルLLMの応答待ち（既定最大5分）の間に発生したtrusted policyの変更を見逃す。

reviewer役割の解決は`resolveReviewRouting`が担う。`modelMapping.roles.reviewer`が`mode`fieldを持つ場合だけローカルLLM providerとして扱い、`provider`が`DISPATCHABLE_REVIEWER_PROVIDERS`（`src/domain/reviewer-provider.ts`）に登録済みで、`PROVIDER_AUTONOMOUS_CEILINGS`の対応entryに`model`が含まれ、`endpoint`がloopbackであることを要求する。いずれか1つでも満たさない場合は`rejected`とし、Codex/Claude向けの既存reviewer形状（`logicalTier`/`reasoningEffort`/`speed`を持つ）は従来どおり`validateRoleConfigurationIndependence`の対象になる。**`DISPATCHABLE_REVIEWER_PROVIDERS`は2026-09時点で`ollama`だけを含む。** 別のローカル実行runtime、または将来の外部SaaS reviewerを追加する場合は、この集合と`src/adapters/reviewer-executors.ts`のREVIEWER_EXECUTORS表へ登録するだけで済むよう、`resolveReviewRouting`・`launchReview`はprovider名の文字列比較を分岐条件に埋め込まない。`implementer`向け`resolveRouting`/`launchCodex`（`codex`/`claude`固定）は本抽象化の対象外であり、変更しない（Issue #1425の範囲外）。`resolveReviewRouting`はさらに、coordinatorとreviewerの同一identityも拒否する（`validateRoleAssignment`はimplementer/reviewerの独立性しか見ないため、ここで個別に補う）。

実行（`executeLocalLlm`）はOllama互換HTTP APIへの単一POSTに限定し、`child_process.spawn`によるCodexのような外部process起動を行わない。有限timeout・有限出力上限を`executeCodex`と同水準（既定5分・8MiB）で実装し、上限到達・不正応答・接続不可・stream読取中のtimeoutはいずれも`succeeded`を騙称せず`unknown`または`failed`として安全側に倒す。**`succeeded`時は応答本文を`output`として返す。** ローカルLLMが実際に何を指摘したかを呼出し元へ伝えるために必須であり、破棄すると本機能はreviewer役割の指摘内容を一切利用者へ届けられない。prompt本文は結果証跡へ転記しない。

`replace`モードの採用可否はtrusted policy（git管理下）の`modelMapping.roles.reviewer.mode`宣言だけで決まり、`routing review-launch`のCLI flagには`mode`を上書きする入力経路が無い。candidateがgit管理外の個人設定でreviewer役割の正式な充足条件を変更することはできない。

`replace`モードでdispatchが`succeeded`した場合、`launchReview`は`output`を`evaluateLocalLlmReview`（`src/domain/review-verdict.ts`）へ渡し、reviewer役割の正式な充足条件（FR-107）をこの判定結果で満たす。同関数はLLM出力から**主観的な評価部分**（`round`・`developmentConsiderations`・`affirmative`/`adversarial`評価・`findings`・`tests`・`specConsistency`）だけを取り出し、既存`evaluateReviewJudgment`（`src/domain/review.ts`。Claude/Codexレビューと同一のCritical/High findings blocking判定）へ渡す。**既存`evaluateReview`は使わない。** 同関数の`validateImmutableCandidateEvidence`は「GitHub上で実際にreviewがapprovedとして提出された」という外部事実の存在を要求しており、これから判定しようとしている対象には適用できない。ローカルLLMにこの外部事実（headSha・PR番号・CI run ID・reviewer actor ID等）を自己申告させると、この関数が守るべき「外部の実在するreviewだけが承認を与える」という前提を、まさにこの経路で崩す。`evaluateLocalLlmReview`はLLM出力からこれらのkeyを一切採用しない（含まれていても無視する）。**`findings[].riskAcceptance`も個別に剥奪する。** これは「人間の権限者がこのリスクを受容した」という承認の主張であり、主観的な評価とは性質が異なる。LLM応答にそのまま含めさせると、Critical/High findingを`status: "valid"`のまま自分自身の`riskAcceptance`で`acceptedRisks`側へ動かし`blocking`を回避できてしまう（自己承認）。`replace`モードのローカルLLM経路からはriskAcceptanceを一切成立させず、受容が必要な指摘は常に`blocking`として安全側に倒す。`supplement`モードではこの判定を行わず、`launchReview`の結果に`verdict`を含めない（FR-106のとおり既存reviewの充足条件を変えない）。
