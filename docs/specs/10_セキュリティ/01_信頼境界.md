# 信頼境界

- パス、Unicode、シンボリックリンク、Git remote、repository、branch、HEAD SHA、認証、認可、外部観測状態を信頼しない。
- 読み取り結果だけに依存せず、書き込み・削除直前に対象と状態を再検証する。
- 候補PR内のpolicy変更は当該PRのmerge判断に使用しない。
- review、test、spec証拠は同じHEAD SHAへ結び付ける。
- merge、Issue close、branch削除、release、cleanupを別操作として認可する。
- `.gitignore`を再生成可能性の根拠にせず、trusted project policyとpackage既定値から解決したfinalize ignore allowlistだけを削除可能な生成物境界として扱う。

## project choice差分の信頼境界

trusted側に`projectChoices`がある場合、candidateとの差分はfield単位で次の3分類へ分ける。object全体のfingerprint不一致だけを理由に一律拒否しない。

| 分類 | 対象 | 判定と処置 |
|---|---|---|
| authority | `release`、`ci` | 値の変更をASC-TRUST-001で拒否し、既定ブランチのproject policy ownerによるtrusted側の先行更新とauthority fieldの復元方法を案内する |
| 弱化 | test層、禁止test suffix、禁止型、strict型検査、capability、補助言語宣言、tier引き下げ、および未知field・型不正 | 検証の縮小、`applicable`の格下げ、宣言削除をASC-TRUST-001で拒否し、弱化の取消しまたは強化方向への変更を案内する |
| 許可 | authority境界外の既知field、説明・証拠、検証済み`modelMapping`の追加・強化、検証の拡大 | 変更field pathを記録して拒否しない |
| 弱化 | test層、禁止test suffix、禁止型、strict型検査、quality command、capability、補助言語宣言の単調性違反、および未知field・型不正 | 検証の縮小、具体値から`not-applicable`、`applicable`の格下げ、宣言削除をASC-TRUST-001で拒否し、弱化の取消しまたは強化方向への変更を案内する |
| 許可 | authority境界外の既知field、説明・証拠、`modelMapping`、検証の拡大 | 変更field pathを記録して拒否しない |

test層、禁止test suffix、禁止型の追加、`not-applicable`から`applicable`への変更、補助言語宣言の追加は検証強化として許可する。`modelMapping`をlegacy文字列から検証済み構造化値へ変更するなど、authority境界外の変更は、ほかのpolicy・品質条件を満たす限り正当な拡張経路として通過する。未知fieldおよびobjectでない入力は、型定義の拡張を黙って自己適用しないようfail-closedで弱化へ分類する。

`providerFiles`、`project/providers/`、構造化`modelMapping`はtrusted policy loaderの入力文法を拡張するため、同じcandidateで文法追加とproject設定activationを完結させない。第1段階はlegacy文字列と既存inventoryを保持したままschema・validator・runtimeだけを追加し、mainのtrusted validatorでcandidate全体を検証する。第2段階は第1段階のbranchまたはmerge済みcommitをtrusted baseとしてproject mappingを有効化する。同一PRで追加した入力文法をcandidate自身のauthorityとして使う構成は拒否する。
| routing evidenceへの秘密混入 | 入力を未知field拒否の保存許可listで検証し、credential、prompt、メールアドレス、stderr本文を保存しない | 不正なfield、識別子、容量超過を副作用前に拒否する |
| role設定による自己review | reviewerへimplementerと異なるidentityという独立性制約を必須化し、同一providerかつ同一論理tierへ解決する設定を設定検証時に拒否する | BR-836-12の拒否診断を返し、実装とreviewを開始しない |
| legacy fallbackのrole混同 | 既存routing形式がcoordinatorをfallback implementer候補へ解決しても、新しいrole契約はcoordinatorのproduct実装を許可しない | routing decisionを実行authorityにせず、独立implementerへ再割当してrole operationを再検証する |
| role兼務・自己承認 | coordinatorのproduct実装、同一scopeで同一identityまたはcontextのimplementer・reviewer兼務、reviewerによる対象差分変更を禁止する | role・操作・path・必要証拠が不明ならPR、merge、finalizeを拒否し、独立したidentity・contextへ再割当する |
| model tier降格 | risk、mode、scope、finding重大度から必要tierを単調に決め、model mapping未定義と選択tier不一致を拒否する | scope縮小、mapping ownerによるtrusted更新、または必要tier以上への再選択で復旧する。tierからauthorityを付与しない |
| provider上限回避 | Codexはhigh、ClaudeはOpusを自律選択上限とし、alias、自動routing、silent fallbackも実際の選択値で判定する | 上限内へ戻すか、provider・選択値・Issue・scope・指示者・日時・失効条件へ拘束された人間overrideを提示する。AI自己発行と再利用を拒否する |
| Step欠落の無条件迂回 | `pr create`でStep 10まで、特にStep 4・10と同期状態を外部操作前に検証し、無条件のbypass flagを設けない | 対象Issue、`workflow.pr.create` scope、指示者、理由、指示・失効日時が有効なHumanOverrideだけを欠落Stepのjournal行へ記録する。AI・role自己発行、別Issue、失効、未知field、欠落以外の不整合を拒否する |
| PoC観測の自己申告・fixture逸脱 | 観測期間の主観報告やcaller作成Evidenceを使わず、repository内の隔離疑似project、runner ID・path・固定argv、use case・BDD scenario・observableをPoC宣言へ固定する。ASCは任意shellを受理せず、HEAD blobから復元したfixtureの固定Node runnerだけをLinuxのbubblewrap・prlimit下で実行する。namespace、read-only mount、timeout、出力上限を主境界とし、Node Permission Modelは補助防御とする | dirty/untracked、symlink・hardlink・特殊file、digest、process終了値、全observable、exact HEAD、baseline/provider baseからのfixture-only実Git差分を再検証する。EvidenceはHEAD別append-only、Step 9以降はdigest bindingとし、同一HEAD差替え、外部path書込、非正常終了、不一致、tool欠落を外部副作用前に拒否する |

Non-override対象は秘密保護、Git内部領域、remote/worktree同一性、不可逆操作、成果物汚染、候補自身の承認防止である。環境変数や無期限flagはoverride authorityにならない。

Agent Routingの信頼方向は、trusted ref側のproject choiceとprovider capability mapping、およびprovider実行入口のread-only観測からrouting decisionへ、routing decisionからrouting evidenceと実装差分へ向かう一方向とする。candidateが変更したmapping、choice、resolver、独立性validator、conformance bindingを同じcandidateの選択・review・merge authorityへ使わず、completion recordやreview判定からrouting decisionへ戻る辺も認めない。
