# GitHub連携要件

### REQ-GH-001 GitHub操作を単一adapterと再読取で制御する

Issue同期、PR作成、review証拠、policy authority、mergeは完全repository同一性・base/head SHA・認証・権限を事前検証し、適用直前に再検証し、適用後に再読取する。candidate policy、自己申告metadata、stale/failed証拠をauthorityにしない。PR作成後のjournal記録が失敗しても作成済みURLと記録だけを再実行する復旧方法を返し、非0終了で成功と区別する。

- 受け入れ条件: AC-GH-001
- 根拠: Issue #824、#829、#834
- 実装: `src/adapters/github.ts`

**Issue本文の更新前状態を読む経路をadapterとCLIへ持つ。** `issue sync`は本文を全面置換するため、既存のチェックリストや進捗記録を保全するには更新前本文が要る。skillは`gh`の直接呼び出しを禁じており、**読み取り経路が無いと保全と禁止が両立しない。** `issue read`は本文と`bodySha256`を返し、**書き込みを行わないため`repository read`で成立する。**

**CI runの観測は成否で絞り込まず、拒否診断へ配送状態を含める。** 成功したrunだけを問い合わせると、run未生成・実行中・失敗がすべて同じ「該当0件」へ潰れ、待つべきか人を呼ぶべきかを判定できない。**遅延を不達と誤診して不要な人間対応を要求した実例がある**（Issue #969）。head SHAとPR番号と起動イベントで該当runを数え、イベント時刻からの経過が猶予時間の内側なら`pending`、超えていれば`undelivered`、該当runがあれば成否を問わず`delivered`とする。**判定は永続状態もpollingも新しい門も持たない純関数とし、拒否そのものは従来どおりとする。** 診断には配送状態・該当run件数・head SHA・イベント時刻・観測時刻・経過・猶予時間に加え、**次に採る行動を含める。** `undelivered`を人間へ上げる唯一の条件とし、`pending`では人間を呼ばない。イベント時刻はASCが固定した時刻を使い、commit時刻や汎用のPR更新時刻で代用しない。**この不変条件を強制するのは`SCN-UNIT-CIDEL-001`から`SCN-UNIT-CIDEL-007`である。**

### REQ-GH-002 手動releaseを段階制御する

手動dispatchはversion一致・単調増加・tag不在・既定branch・必須gateを検証し、dry-runを安全な既定値とする。tagとGitHub Releaseを独立stage・authority・再読取へ分離し、途中失敗の完了範囲と復旧を返す。**npm公開stageを持たない。** owner決裁でnpm registryへ公開しないことが確定しており、`package.json`の`private: true`により`npm publish`は必ず失敗する。stageを残すと方針上あってはならない経路を計画が宣言し続ける。**`publish_npm`入力と`npm publish` stepの存在をworkflow検証が拒否する。**

- 受け入れ条件: AC-GH-002
- 根拠: Issue #826
- 実装: `src/domain/release.ts`

### REQ-GH-003 配布digestで自動releaseを判定する

`npm pack --dry-run --json --ignore-scripts`のpathとversionだけを正規化した内容hashから配布digestを算出し、直近release tag内容の再計算値と比較する。差分時だけtag・Releaseを冪等作成する。**npm公開経路は存在しない。**

**releaseは既定branchへ書き込まない。** version bump commit、bump PR、そのadmin mergeを持たない。**versionの正本はGit tagであり、`package.json`はreleaseに追随しないsentinelを持つ。** 現在versionは既存tagから導く。sentinelのprereleaseを剥いだcoreはpolicy schema versionと一致しなければならず、**policy schemaが上がるときはsentinelのcoreを上げるcommitが既定branchへ入る。** 消えるのはprerelease番号のbumpだけである。

**公開経路が存在しないため、公開用のversion注入も存在しない。** `scripts/prepare_release_bump.ts`の`canonicalBumpDiff`は、正規bump差分（TERM-ASC-081）の定義元としてのみ残る。

**運用設計の権限境界表は、release workflowが定義するjob集合と一致しなければならない。** 廃止したjobが文書へ残る形と、新設したjobを文書へ書き忘れる形の**両方を拒否する**。片方向だけでは、文書を空にすれば通ってしまう。判定するのは名前の集合一致だけであり、権限や開始条件の記述内容は判定しない。**job IDはGitHub Actionsの文法（英字または`_`で始まり、英数字・`-`・`_`）で読む。** 狭めると両方の集合から同時に落ちて検出できない。**走査は権限境界表の節の中に限る。** 文書全体を走査すると他の表の1列目をjob名と誤認する。**行末のYAMLコメントを許す。** `jobs: # …`も`validate: # …`も正当なYAMLであり、許さないとコメントを付けたjobが集合から落ちて未記載を検出できない。**ただし値を持つkeyはjobとして拾わない。****`docs/`は配布境界に入るため、存在しない経路を運用者へ提示しない。**

**push起点のrunは、重い導入と品質gateより前に停止条件を評価する。** trigger SHAがremote既定branch tipと異なるrun、およびtrigger commitの親が2つでないrunは停止する。**tag書き込みの直前にも同じremote tip再読取を行う。** 検証通過後に別のPRがmergeされた場合に、古いtreeへtagを付けないためである。

**bump経路は廃止した。** release bump基準SHA（TERM-ASC-080）からbump branchを作り直す手続きは、既定branchへ書き込まなくなった時点で実行経路から外れている。`scripts/prepare_release_bump.ts`は残すが、**release経路のためではなく`canonicalBumpDiff`の提供元としてだけ残す。** **同関数を呼ぶrelease経路は存在しない。** 正規bump差分（TERM-ASC-081）の定義は、将来の判定のための語彙として残す。

- 受け入れ条件: AC-GH-003
- 根拠: Issue #861、#869、#879、#1051、#1184、#1191
- 実装: `src/domain/release.ts`、`scripts/plan_release.ts`、`.github/workflows/release.yml`（`scripts/prepare_release_bump.ts`は`canonicalBumpDiff`の提供元としてのみ参照する）

### REQ-GH-004 branch関係からmerge方式を解決する

base branchに一致する`branchMethods`全entryのmethods積集合を使い、global許可を拡大しない。base/head双方が長命branchならmergeだけを許可し、squash/rebaseを診断付きで拒否する。**adapterはmerge方式の既定値を持たない。** `merge`と`rebase`以外の値を受け取ったら例外にし、squashへ倒さない。既定値をsquashにすると、値を解決できなかった場合に取り込み先branch上のcommitの親が1個になり、**`比較基点..H_impl`と`H_impl..H_final`の2区間を導出できなくなって`audit:check`が成立しない。** **配布するpolicy雛形は`methods`へ`merge`だけを宣言する。** squashを含む雛形を配らない。**`merge.branches`はhead allowlist、長命branchペアの判定、長命branch警告のbase候補の3役を兼ねる。** head allowlistは`*`をワイルドカードとして照合し、長命branchペアの判定とbase候補は完全一致で扱う。**ワイルドカードを含む要素はbaseにならないためbase候補から外し、残りが2件以上のときだけ警告する。**

**baseにできるbranchは、trusted policyの`merge.branches`へ完全一致で宣言されたものと既定branchである。** wildcardを含む要素はbaseにしない。**Git revision syntaxもbaseにしない。** `main~1`は`*`を含まないが`refs/remotes/origin/main~1^{commit}`が親commitへ解決されるため、branch tipでないcommitをbaseにできてしまう。`~`・`^`・`..`・`@{`・`:`・空白を含む値、`HEAD`、`refs/`前置、`-`始まりを拒否し、**baseとして受理してよい形を狭く列挙する。****policy authorityとbase authorityは別である。** trusted policy自身は常にprovider default branchのtipから読み、baseの選択には依存させない。両者を1つの等式へ潰すと、宣言の正本を候補branch側から差し替える経路が生まれる。既定branch以外をbaseにする場合は、trusted policyの観測と、その branch のprovider観測tipへの一致、基点commitとの完全一致を要求する。

- 受け入れ条件: AC-GH-004
- 根拠: Issue #875、#1139（#1179で再実施）
- 実装: `src/domain/delivery.ts`、`src/domain/policy.ts`、`src/domain/worktree.ts`

### REQ-GH-005 Git履歴からreview境界を監査する

**`H_impl`は`H_final`で終わるartifactだけの第1親suffixを遡って決める。** `HEAD^`へ固定すると、review artifactの帳簿合わせのたびに`H_impl`が動き、記載した`H_impl`と個別監査表の追随が要る。**その追随commitがまた`H_impl`を動かすため、有限レビュー予算がreviewの実質ではなく帳簿合わせで消える。** 2026-09-06のIssue #980では予算3のうち2ラウンドがこれに費やされた。

**遡るのはartifact 1 fileだけを変えるcommitに限る。** 他pathを含むcommit、merge commit、artifactを2件以上同時に変えるcommitで止める。**止められない場合は`HEAD^`と同じ結果へ戻るため、判定が緩む方向へは動かない。** 起点は`HEAD^`のままである。起点を`HEAD`にすると、review headがartifact以外を含む場合に`H_impl..current`が空になり、「artifact以外のfileが含まれています」を検出できなくなる。これを強制するのは`SCN-UNIT-AUDITSEL-015`〜`018`である。

review artifactはfile名順でなくcommit構造と差分path 1件から選び、推定`H_impl`と本文SHAを二重確認する。正規release bumpはsubject、変更path、`package.json.version`限定の3条件を全て満たす場合だけ監査差分から除外し、直線・merge履歴の通常変更を除外しない。

**除外はcutoff commitのancestorに限る。** releaseが既定branchへbump commitを push しなくなったため（REQ-GH-003）、除外は移行前に実在した旧bumpのためだけに残す。**cutoff以後のbump形式commitは通常の変更として監査する。** cutoffを解決できない履歴では、除外の可否を判定できないものとして監査を停止する。**「解決できないので除外しない」も「解決できないので除外する」も採らない。** 前者はcutoffを消すだけで除外を止められ、後者は浅い履歴で移行後のbump形式commitを素通しできる。

**版管理下の生成物`dist/`も個別監査の対象から外す。** sourceから決定的に導出され、承認機構つき環境でも即実行できるよう版管理下に置いたものである（REQ-SQ-005）。1行ずつ書かせても確認対象は同じsourceであり、**表が生成file行で埋まって本来確認すべき変更が埋没する。** 導出の正しさは、buildの後に作業treeがcleanであることを要求するCIが見る。

- 受け入れ条件: AC-GH-005
- 根拠: Issue #873、#892、#1184
- 実装: `scripts/check_file_audit.ts`
