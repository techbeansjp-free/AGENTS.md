# プロジェクトライフサイクル要件

### REQ-LC-001 package資産を安全に導入・更新・削除する

`install`、`update`、`delete`はpreviewを既定とし、`--apply`時だけpackage所有の通常fileを変更する。利用者文書、project policy、仕様、staging、他tool、symlink、変更済み資産を保持し、hash・containment・TOCTOUを各write前に検証する。部分失敗はremoved・pending・recoveryを返す。

- 受け入れ条件: AC-LC-001
- 根拠: Issue #828
- 実装: `src/domain/lifecycle.ts`

### REQ-LC-002 host skill adapterを管理する

共通`asc-step`正本をClaude CodeとCodexの所定pathへ配置しmanaged hashへ登録する。未管理で正本とbyte一致するfileは採用し、異なる利用者fileと他skillは保持する。doctorはfrontmatter、正本link、hash、配置を検証する。正本はStep skill一覧への相対linkを持ち、そのlinkは正本と配置先の双方で解決する形にする。正本の`description`は各Stepの開始時の起動を促す単一行とし、正本はStep skillの実名を列挙しない。

- 受け入れ条件: AC-LC-002
- 根拠: Issue #847
- 実装: `src/domain/lifecycle.ts`

### REQ-LC-003 隔離worktreeを非破壊で作る

repository直下`.worktrees/`の規定名、許可branch type、Issue・slug一致、remote default branchの完全SHAを要求する。絶対・親・nested・非NFC・制御文字・case/Unicode衝突・symlink脱出・Git内部領域を副作用前に拒否し、作成元statusを不変にする。作成は明示承認を要し、`--dry-run`と`--apply`のどちらか一方の指定を必須とする。`--dry-run`は同一の検証規則を通したうえでworktreeもbranchも作らず計画だけを返す。

- 受け入れ条件: AC-LC-003
- 根拠: Issue #824、#831
- 実装: `src/domain/worktree.ts`

### REQ-LC-004 workspace一時物を安全に整理する

空directoryと既知一時fileだけをread-only previewし、決定的report hash、明示operation、再preview一致後に非再帰で除去する。Git領域、root、home、root外、symlink、`node_modules`、内容のある利用者資産、登録済みworktreeをoverride不能に保持する。

- 受け入れ条件: AC-LC-004
- 根拠: Issue #833
- 実装: `src/domain/hygiene.ts`

### REQ-LC-005 root更新・Issue参照・cleanupを分離する

merge後のcleanなroot既定branchだけを検証済みmerge SHAへfast-forwardし再読取する。canonical Issueだけを終端keywordで1回参照し、後続Issueは`Relates to`とする。cleanup対象はpath・branch完全一致の対象PR worktree 1件とし、branch削除・release・公開を連鎖しない。

- 受け入れ条件: AC-LC-005
- 根拠: Issue #829
- 実装: `src/domain/finalize.ts`

### REQ-LC-006 merge完了をphase化して収束させる

`merge-confirm → root-update → cleanup-preview → cleanup-apply → post-verify`の順で進め、cleanup専用authorityと最新digestを要求する。dirty・未push・未merge・復旧不能・unknownでは削除0件とし、途中失敗は`partially-completed`として再実行で収束させる。

- 受け入れ条件: AC-LC-006
- 根拠: Issue #856
- 実装: `src/domain/finalize.ts`

### REQ-LC-007 stagingを同期証拠に基づき削除する

staging recordのmode別checkpoint、artifact inventory、content digest、tracker再読取、owner、保持期限をすべて満たす場合だけ削除候補にする。legacy成果物、未知状態、symlink、root外、plan変化を保持し、部分失敗を成功にしない。

- 受け入れ条件: AC-LC-007
- 根拠: Issue #860
- 実装: `src/domain/staging.ts`

### REQ-LC-008 worktreeを読み取り専用で走査する

登録済みworktreeをprimary、in-progress、cleanup-ready、retainへ順序付き分類し、保持理由を全件日本語で返す。不正entryを分離して正常entryの判定を継続し、候補の存在だけで非0にせず、走査・doctor・削除の責務を分離する。

- 受け入れ条件: AC-LC-008
- 根拠: Issue #883
- 実装: `src/domain/worktree-survey.ts`

### REQ-LC-009 ignore対象を安全に判定してworktreeを後片付けする

finalize ignore allowlistはpackage既定の`node_modules/`と`dist/`、およびtrusted project policyの安全なdirectory prefixだけを受理し、schemaとruntimeで同じ入力集合を検証する。候補側は削除可能範囲の拡大を自己承認できない。surveyとfinalizeは同じ純粋な安全判定を使い、allowlist内のignore対象だけを再生成可能として保持理由から除く。allowlist外・種別不明のignore対象はpathと日本語理由を返し、未commitの追跡対象file、未追跡file、stash、未push・到達不能commit、remote branch不明、PR未merge、復旧不能、`.worktrees/`の直接の子でない配置を従来どおり拒否する。cleanup計画の配列・boolean観測が不正または不明な場合は、他の観測から安全状態を推定せずretainとする。buildとgateで生成したallowlist内資産は、survey、finalize preview、authority・digest付きapplyの順で後片付けする。

- 受け入れ条件: AC-LC-009
- 根拠: Issue #894
- 実装: `src/domain/worktree-removal-safety.ts`、`src/domain/finalize.ts`、`src/domain/worktree-survey.ts`、`src/domain/worktree.ts`、`src/domain/policy.ts`、`src/cli.ts`、`.agent-skill-chain/schemas/project-policy-manifest.schema.json`、`.agent-skill-chain/schemas/project-policy.schema.json`

### REQ-LC-010 worktree名の時刻と作成後の命名整合性を検証する

`worktree create`はCLI層で取得した現在時刻をdomainへ必須入力として渡す。directory名の`YYYYMMDD_HHMMSS`をlocal timeとして解釈し、未来または現在時刻から10分を超えて古いtimestampを副作用前に拒否する。明示pathではGit内部侵入などのtrusted boundaryをdirectory名・timestamp・Issue番号・slugより先に評価する。`--path`省略時は同じ現在時刻、Issue番号、slugから`.worktrees/{timestamp}-{issueNumber}-{slug}`を構成する。現在時刻の未指定・不正値はtimestamp検証を省略せず拒否する。`worktree survey`はdirectory名とbranch名のIssue番号・slugの不一致を`reasons`へ報告するが、分類または削除判断を変更せず、既存directoryを改名しない。

worktree作成契約は配布物の`.agent-skill-chain/docs/01_開発ワークフロー.md`へも届ける。**同じ事実を二度書かない。** 正本は`src/domain/worktree.ts`の`WORKTREE_NAME_FORMAT`と`WORKTREE_TIMESTAMP_MAX_AGE_MINUTES`であり、配布文書の該当区画は`scripts/generate_worktree_contract.ts`が正本から生成する。`conformance:check`は生成区画が正本の描画結果と一致することだけを検証し、一致しない場合は生成commandの実行を求める。正本が述べる書式をruntimeの`WORKTREE_NAME`が受理することも同時に検証する。

- 受け入れ条件: AC-LC-010
- 根拠: Issue #893
- 実装: `src/domain/worktree.ts`、`src/domain/worktree-survey.ts`、`src/cli.ts`

### REQ-LC-011 製品自身のlifecycle健全性をCIで検証する

CIは`build`の後に製品自身のrepositoryへ`install --apply`でhost skill登録アダプターを展開し、`doctor`が`healthy: true`かつ`installed: true`を返すことを要求する。`healthy: false`はCIを失敗させる。展開先の`.claude/`と`.agents/`、および`.agent-skill-chain/managed-assets.json`は`.gitignore`の対象とし、展開後も`git status --porcelain`が空であることを同じCIで確認する。`doctor`は既定branchへmerge済みで後片付け可能なworktreeを件数と個別pathで報告するが、削除は行わず`healthy`も変えない。削除は`worktree finalize`と`worktree hygiene`のpreview・承認hash経路に限る。`.codex/`はhost skill登録アダプターの対象ではない。Codexの登録口は`.agents/skills/asc-step/SKILL.md`である。

- 受け入れ条件: AC-LC-011
- 根拠: Issue #882、#847、#856、#883
- 実装: `.github/workflows/ci.yml`、`.gitignore`、`src/domain/lifecycle.ts`
