### REQ-SQ-015 独立reviewが成立しない場合をrisk比例で扱う

外部reviewサービスの利用有無は要件ではない。要件はPR authorとobserved implementation commit authorのどちらとも異なるreviewerによるexact-head reviewであり、人がreviewerであってもよい。**既定は停止ではなく無記録での通過の禁止とする。** 門を置く場所は自動か手動かでは決めず、**止めた場合に残る状態が復旧可能であり、かつ止めることで不可逆な行為を防げるところ**にだけ置く。mergeとtag作成とReleaseは止めても不可逆な行為を防げないため門を置かない。実装・test・仕様の変更、PR作成、既定branchへのmergeは記録があれば進む。mergeを契機に自動で走るtag作成とReleaseはmergeの判断に従う。package registryへの公開など外部への不可逆な配布は既定で独立reviewの外部証拠を要求するが、外部reviewerが実在しない構成のために例外で覆える。**永久に塞がる門を作らない。** ただし不可逆な配布を対象に含める宣言は、対象に含める旨の明示と期限付きの失効日時を必須とし、無期限を認めない。削除、force push、履歴書き換えは独立reviewの対象外とし、preview・承認hash・authorize・branch保護の既存authority経路で守る。記録が無い場合は進めない。

承認済み例外は`.agent-skill-chain/review-exceptions.json`を正本とし、識別子、種別、条件、観測方法、承認元、承認者、対象scope、不可逆な配布を対象に含めるか、理由、承認日時、失効日時、満たさない要件、記録先を必須とする。失効日時は無期限を示すnullとkey省略を区別する。種別は独立reviewerの不在、一時的な失敗、成功表示だが未実行の3種とし、**一時的な失敗は例外として宣言できない。** 再試行を既定とし、上限超過時に他の種別へ宣言し直す。checkの結論を証拠にせず、review commentとapprovalの実体を観測する。review artifactは正本の識別子を参照し、承認元・承認者・承認日時・失効日時を複製しない。

- 受け入れ条件: AC-SQ-015
- 根拠: Issue #921、#906
- 実装: `src/domain/conformance.ts`、`.agent-skill-chain/review-exceptions.json`、`.agent-skill-chain/schemas/project-review-exception.schema.json`

### REQ-SQ-016 契約の正本を1箇所に保つ

同じ契約を複数箇所へ記述することを禁じ、正本以外は参照だけを持つ。**検査するのは参照の存在であり、記述内容の一致ではない。** 内容一致を検査する設計は一致を保つ責務を新たに生み、複製問題を機械化しただけになるため採らない。規範文の自動判定も、判定が曖昧で誤検出が避けられないため採らない。

契約IDごとに正本pathと検出tokenを宣言する契約正本registryを置く。検出tokenは人が明示登録した語だけとし、規範性を推測して拡張しない。走査範囲は規範を宣言するlocation、すなわち`.agent-skill-chain/docs/`、`.agent-skill-chain/templates/`、`docs/specs/`のMarkdownに限る。証跡、一時ステージング、実装は規範を宣言せず規約を引用・記録・例示するため範囲外とする。**範囲を限定することで、規約を述べる記述と使う記述の判別に規範性の推測を要さない。**

正本自身は検出対象にしない。「正本への参照」は正本pathを指すMarkdown linkの存在をもって成立し、path文字列の言及だけでは成立しない。registryが無い、読めない、構造が不正、宣言されていないtop-level fieldを持つ、契約IDが重複、正本pathが規範宣言location外または不実在の場合はfail-closedで拒否する。**registryの不在を適合として扱わない。** ruleの`scope`と実装の走査locationが食い違う場合も拒否し、同じ事実の二重宣言が黙って分岐しないようにする。

**機構には限界がある。** 検出tokenを含まない言い換えによる複製は捉えられない。捉えるには規範文の自動判定が必要であり、それ自体を採らないため両立しない。人手のreviewが担う。

### REQ-SQ-018 既定branch追随をH_impl不変条件と両立させ、監査範囲内mergeの内容消失を検出する

PR gateは`H_impl..current`をreview artifact 1件に限る。一方、既定branchが動いたPRは追随しなければmergeできない。取り込みのmerge commitがreview artifactより後に来ると、この2つの強制は同時に満たせない。`H_impl`を追随merge側へ動かすと今度は`比較基点..H_impl`へartifact自身が入り、個別監査表と一致しなくなる。

**解決は検査の緩和ではなく手順の固定で行う。** 取り込みをreview artifact commitより前に置き、artifactを最終commitへ置き直す。追随後は`比較基点`を取り込んだ既定branch tip、`H_impl`をartifact直前の最新commitとする。**個別監査表は追随前の内容を流用せず`比較基点..H_impl`から再生成する。** 追随後の差分は既定branch tipに対するnet deltaであり、追随前とはpath集合もchange typeも一致しないためである。この手順は既存の判定ロジックを変更せずに成立する。

追随時の衝突解消は、検査で捉えられない巻き戻しを生む。実測では`-X theirs`による解消が既定branch側の1行を落とし、テスト814件と型検査が通過し衝突markerも残らず、tree突合だけが検出した。そこで**監査範囲`比較基点..H_impl`に含まれるmerge commitについて、両方の親が保持していたtokenと、いずれかの親が新たに導入したtokenを、出現位置ごとに保持することを要求する。** 片方の親だけがmerge-baseから削除したtokenは対象外とする。意図的な削除はmergeではなく後続の通常commitで行い、通常差分として個別監査へ載せる。

観測対象は損失検知tokenとする。安定IDを包含し、`SHA-256`のようなID以外のtokenも含む。散文の言い換え、順序変更、書式変更は検出対象にしない。**「両側の意図が失われていない」ことの一般的証明は機械的に不可能であるため、対象をtokenへ縮小する。** repository全体のtoken集合では、同じtokenが別fileに残っていれば当該fileでの消失を隠せるため、判定は出現位置ごとに行う。

対象path集合は**rename検出を無効にして**列挙する。rename検出を有効にすると移動元pathが列挙から落ち、両親が保持していたtokenをrename時に落としても移動先では両親が不在となり、保持必須集合が空になって合格する。

判定不能は合格へ倒さない。親が2個でないmerge、merge-baseが一意でないmerge、内容を観測できないpath、rename移動先が一意に定まらないpath、一部の親でだけ移動先を特定できたpath、1つのmerge内で複数の出現位置が同じ移動先pathへ潰れたpathは、いずれも拒否する。潰れる形は「異なる移動元が同じ移動先へ解決される」と「移動先がmerge結果に残る別の要求元そのものである」の2つであり、いずれも移動先の1個のtokenで複数の出現位置を保持したと誤認する。ただし保持必須集合が空の移動元は衝突として数えない。数えると正当なrenameを誤検出する。内容の観測は「存在して取得成功」「存在しないことを確認」「観測失敗」の三値とし、**観測失敗を空集合として扱わない。** 空集合として扱うと保持必須集合が縮み、損失を合格させ得るためである。

release bump除外は損失検知へ適用しない。除外は`H_impl..current`のpath差分に対する処理であり、損失検知とは責務が異なる。両者を混ぜると除外条件を満たすmergeが検査を素通りする。

**走査範囲の選択に使う`比較基点`は申告値であり、独立導出されない。** `比較基点`を前へ進めれば損失mergeを範囲外へ追い出せる。これは既存gateの構造的弱点であり本要件が導入したものではないため、Issue #966へ分離した。

- 根拠: Issue #962
- 実装: `src/domain/merge-integrity.ts`、`scripts/check_file_audit.ts`、`.agent-skill-chain/docs/02_品質基準.md`、`.agent-skill-chain/templates/issue/04_レビュー.md`、`.agent-skill-chain/templates/issue/11_プルリクエスト事前確認.md`
### REQ-SQ-019 一時ライフサイクル領域の宣言を単一正本から導出し、利用箇所の分岐を検出する

一時ライフサイクル生成物の領域は、実行ログと開発計測を含む再生成可能な出力の置き場である。この分類は複数の機構が使う。追跡可否、配布対象からの除外、package資産の禁止entry、SCN配置検査の除外範囲である。

**分類が箇所ごとに独立して書かれると黙って分岐する。** 2026-08-26の実測では、`.gitignore`だけが`tmp/`しか登録しておらず、`role-log/`と`metrics/`が追跡され得る状態だった。この非対称は無関係な検査の設計判断まで歪めた。さらに実装中、起票時点で把握していた3箇所に加えて4箇所目の独立宣言が見つかった。

そこで**領域一覧を分類の唯一の正本とし、領域判定をそこから導出する。** 利用箇所は一覧を複製せず、導出するか照合される。

無視設定の検証は版管理への問い合わせで行い、`.gitignore`の文字列一致で代替しない。否定patternや後続行による打ち消しを見落とすためである。**一致したpatternが領域そのものを指すdirectory patternであることと、一致元がrepositoryで追跡されるroot `.gitignore`であることの双方を要求する。** 浅い位置と深い位置の双方で同じpatternに一致することも要求する。領域内の一部だけを無視する設定、否定patternで一部を再許可する設定、cloneへ伝わらないexclude fileへの退避を、いずれも合格させないためである。

無視設定に加えて追跡状態も検査する。`git check-ignore`は既定で追跡済みfileを対象にしないため、無視設定だけでは既に追跡されている生成物を見逃す。

判定不能は合格へ倒さない。問い合わせの失敗、追跡fileの列挙の失敗、解決されたrepository rootの不一致をすべて拒否する。**版管理への問い合わせは、repositoryとindexの選択へ影響する環境変数を除去した実行環境で行い、解決されたrootが指定rootと一致することを確認する。** 環境変数で別repositoryやindexへ向けられると、違反のあるrepositoryを違反のないrepositoryとして判定し得る。

- 受け入れ条件: AC-SQ-019
- 根拠: Issue #959
- 実装: `src/domain/staging.ts`、`scripts/check_conformance.ts`、`scripts/check_package_contents.ts`、`.gitignore`

### REQ-SQ-020 配布準備工程と配布前品質検証を分離し、gate集合を保持したままconsumerのinstallを成立させる

package managerはgit依存のinstallで準備工程を実行する。**npmは`prepare`だけを実行し、pnpmは`prepare`があっても`prepack`を実行する。** この差により、準備工程へ品質gateを置くと配布経路が成立しない。2026-08-27の実測では、`prepack`が品質gateを持つ形で`npm install`はexit 0を返しながら`dist/`も実行fileも作らず、pnpmはexit 1で失敗した。**npmの側は失敗が表面化しないため、壊れた配布が成功として観測される。**

そこで**準備工程は構築だけを行い、配布前品質検証は独立した入口が持つ。** 準備工程は`prepack`と`prepare`の双方が同じ構築commandであることを要求する。片方だけを軽くすると、一方のpackage managerだけが直り他方が壊れたまま残るためである。

**gate集合は減らさない。** 配布前品質検証の入口は、従来の準備工程が実行していたgate列と**順序を含めて完全一致**することを要求する。集合としての包含では不十分である。実測では、gate名がすべて揃い先頭も一致したまま早期終了commandを挿入でき、以降のgateが成功扱いで省略された。順序の入れ替え、任意commandの追加、コメントによる無効化も同じ理由で拒否する。

移行期は従来の形と新しい形の双方を受理する。検査自体が保護fileにあり、保護fileの変更は既定branch側の事前登録済みproposalによる段階移行を要するためである。**移行の各段階で、その時点の既定branch側validatorが候補を検査できなければ段階を提出できない。** 従来の形での準備工程の自己緩和は、移行の前後いずれでも拒否する。

**準備工程の形を変えるだけでは足りない。** `prepack`は形によって意味が変わる。全gateを持つ形では`npm run prepack`が配布前品質検証そのものだが、構築だけへ移した形では構築と等価になる。release workflowが`npm run prepack`を呼び続けたまま中身だけを軽くすると、**workflowもrelease契約検査も変わらないまま、不可逆なnpm公開の直前検証が消える。** そこで準備工程の形とrelease workflowが呼ぶ入口の一致を要求し、片方だけの変更を双方向で拒否する。判定不能は合格へ倒さない。

- 受け入れ条件: AC-SQ-020
- 根拠: Issue #965、#978
- 実装: `scripts/check_project_quality.ts`、`scripts/check_conformance.ts`、`package.json`、`.github/workflows/release.yml`

### REQ-SQ-022 PR本文をtemplate構造へ拘束する

`pr create`はPR本文とタイトルを受け取る経路を持たなかった。本文は[開発ワークフロー](../../../.agent-skill-chain/docs/01_開発ワークフロー.md)が定めるIssue参照のlink行だけが内部生成され、タイトルはIssue番号だけの固定文字列であった。**step-11のtemplate契約は「見出し構造と必須欄を使って本文を作成する。自由形式の本文で代替しない」と要求しているが、契約を満たす本文がGitHubへ到達する経路が存在しなかった。** 契約は構造的に充足不能であり、違反した成果物が`waiting_for_human_review`という成功状態で報告されていた。

`--body-file`を必須flagとして受け取り、本文が配布templateの構造を満たすことを検証する。満たさない本文は`--dry-run`を含めてGitHub操作前に拒否し、成功として報告しない。タイトルは`--title`で明示でき、省略時は本文のH1見出しから導出する。**導出したH1行は本文から除く。**PRのタイトルが本文の先頭へ重複しないためである。

必須見出しは配布template`11_プルリクエスト本文.md`から導出し、一覧を実装へ書き写さない。書き写せばtemplateと独立に古くなり、同じ規則が複数箇所へ複製される。**見出しに条件を書いた節は必須にしない。** 条件を満たさない変更でPRを作れなくなり、充足不能な受け入れ条件になるためである。

検証は構造の存在確認に限る。内容品質、記述量、空欄の一律禁止は判定しない。未実施のラウンドは空で正しい。Issue参照規約は[開発ワークフロー](../../../.agent-skill-chain/docs/01_開発ワークフロー.md)が所有し、本節は複製しない。構造検証と参照検証の双方を満たす本文だけを受理する。

- 受け入れ条件: AC-SQ-022
- 根拠: Issue #951
- 実装: `src/domain/issue.ts`、`src/domain/delivery.ts`、`src/adapters/github.ts`、`src/cli.ts`、`src/cli-usage.ts`
