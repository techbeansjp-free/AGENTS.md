# 仕様・品質管理要件

### REQ-SQ-001 安全境界をfail-closedにする

path、Unicode、symlink、repository、remote、branch、SHA、秘密、identity、authority、外部状態を信頼せず、形式・意味・権限・最新性を副作用前に検証する。秘密・個人情報・stderr本文を診断、例外、証拠、配布物へ複製せず、不可逆操作はoperation単位の明示authorityへ分離する。

- 受け入れ条件: AC-SQ-001
- 根拠: Issue #824、#834
- 実装: `src/lib/security.ts`

### REQ-SQ-002 risk比例型policyと不変条件を強制する

ruleのrisk、enforcement、activation、owner、target layer、evidence、remediation、override、rollbackを検証し、active denyを安全境界へ限定する。I1〜I12の安全・所有・追跡・独立性・同一性・証拠・transaction・配布・offline・非循環・診断・project choice分離をconformance正本へ一意にbindingする。

- 受け入れ条件: AC-SQ-002
- 根拠: Issue #834
- 実装: `src/domain/enforcement.ts`

### REQ-SQ-003 project choice差分を分類する

trusted/candidateの差分をfield単位でauthority、検証弱化、既知の許可・強化へ分類する。release・CI authority変更、層・禁止suffix・禁止型・strict・capability・補助言語・role・tier・applicabilityの弱化、未知field・型不正を拒否し、許可差分のpathを返す。

- 受け入れ条件: AC-SQ-003
- 根拠: Issue #840
- 実装: `src/domain/project-choice-diff.ts`

### REQ-SQ-004 project rule台帳を全enforcementへ結ぶ

manifest inventoryとrule filesを完全一致させ、各ruleへ安定ID・目的・owner・scope・enforcement・test evidenceを要求する。3規範、schema、runtime、CIのcoverage matrixでorphan ruleを拒否し、CI最小権限、npm lockfile、Node互換、配布境界を自己適用する。

- 受け入れ条件: AC-SQ-004
- 根拠: Issue #832
- 実装: `src/domain/conformance.ts`

### REQ-SQ-005 配布品質gateを維持する

利用者向けREADMEを非規範入口として現行CLI・Node・npm・host adapter・正本linkへ一致させる。project data、role log、metrics、fixture、秘密をpackageから除外し、CI・prepackは全Gherkin、lint、format、typecheck、source、build、docs、trace、architecture、conformance、package検査を既存script値で実行する。

- 受け入れ条件: AC-SQ-005
- 根拠: Issue #824、#834、#858、#869
- 実装: `scripts/check_package_contents.ts`

### REQ-SQ-006 TypeScript品質と入力検証を維持する

製品実装をTypeScript strictへ統合し、明示・伝播`any`と未宣言のPython・shell sourceを拒否する。lint、非破壊format check、typecheck、source品質を独立gateにし、外部JSONは`unknown`から入力種別別validatorで未知field・型不正を拒否する。品質契約変更はtrusted proposalの二段階適用に限定する。

- 受け入れ条件: AC-SQ-006
- 根拠: Issue #834
- 実装: `scripts/check_source_quality.ts`

### REQ-SQ-007 製品仕様を自己検証する

`validateSpecs`で製品自身の必須仕様を検証する。要件ID定義をrepository全体で一意にし、索引表と定義見出しの独立列挙を双方向突合する。追跡表の未解決参照、15だけの本文、未追跡要件、孤立SCN・実装、配置外定義を拒否する。graphは完全pathをnodeにし、Set/Mapとqueueの不動点到達判定を`O(F+B+V+E)`で行う。

- 受け入れ条件: AC-SQ-007
- 根拠: Issue #881
- 実装: `scripts/check_trace.ts`

- 受け入れ条件: AC-SQ-008

### REQ-SQ-010 品質契約の保護対象からpackage自身のversionを除く

`package-lock.json`はtrusted品質契約の保護対象fileである。保護の目的はdependency構成とintegrityの自己緩和を防ぐことであり、package自身のversionはその目的に含まれない。保護snapshotを算出する前に、lockfile最上位の`version`と`packages`の空keyのentryの`version`だけを取り除く。`lockfileVersion`、dependencyのversion、`resolved`、`integrity`、dependencyの追加・削除は取り除かず、従来どおり事前登録済みstaged proposalを要求する。`package.json`の`version`が保護package fieldでないことと扱いを一致させる。

- 受け入れ条件: AC-SQ-010
- 根拠: Issue #913
- 実装: `scripts/check_project_quality.ts`

### REQ-SQ-011 test fixtureを実時計・実repository状態から切り離す

`test/steps/`配下での`Date.now()`、引数なしの`new Date()`、`Math.random()`の直接使用を拒否する。時刻を要するfixtureは`test/support/fixture-instant.ts`が1度だけ取得する基準時刻からの相対値を使い、絶対時刻をhardcodeしない。基準時刻は`ASC_FIXTURE_BASE_INSTANT`で注入できる。`test/steps/`から`package.json`、`package-lock.json`、`.agent-skill-chain/project/`配下への相対path accessを拒否し、dogfoodingとして必要なものだけを理由付きで`REPOSITORY_READ_EXCEPTIONS`へ宣言する。宣言が使われなくなった場合も拒否する。

- 受け入れ条件: AC-SQ-011
- 根拠: Issue #888、#830、#857、#866、#877
- 実装: `scripts/check_test_determinism.ts`、`test/support/fixture-instant.ts`

### REQ-SQ-012 登録済み品質proposalの契約fieldを不変にする

trusted registryへ登録済みのproposalは、`proposalId`、`status`、`fromVersion`、`toVersion`、`targets`を契約fieldとして不変にする。削除も拒否する。`owner`、`rationale`、`rollback`は記述fieldとし、値の更新だけを許可する。削除と空文字列化はregistry schemaが拒否し、`rationale`と`rollback`は12文字以上を要求する既存制約を維持する。記述fieldを不変にすると、実行不可能なrollback手順が正本へ残ったまま訂正できなくなる。

- 受け入れ条件: AC-SQ-012
- 根拠: Issue #920、#913、#882
- 実装: `scripts/check_project_quality.ts`
