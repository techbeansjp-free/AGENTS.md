# 移行・廃止方針

v0.3は、旧harnessを意図的に削除した`renewal_v0.3.0`を基点に独立実装する。旧`.agents/`、`.workflow/`、hooks、commands、enforcementを無条件に復元せず、doctorで残存を報告するだけとする。

`init`は新規導入、`upgrade`はpackage所有資産だけの更新、`uninstall`はmanaged hashが一致する資産だけの削除を担う。利用側所有の仕様、project policy、変更済み品質文書、一時stagingを保持する。

ロールバックはv0.3実装コミットを戻し、旧harness削除済みの基点へ戻す。package公開、release、既存利用者への自動移行は今回の範囲外である。

製品versionの正本は`package.json.version`とし、同じ`package.json`の`agentSkillChain`が現行・互換project policy schema versionを宣言する。今回の製品versionは`0.3.1-beta.1`、現行project policyは`v0.3.1`、互換入力は`v0.3.0`である。runtimeとlifecycleはpackage metadataを読み、schemaとの不一致はbuild gateで拒否する。

Project policy `v0.3.0`は互換入力として診断できる。`v0.3.1`への移行対象はpolicy、schema、runtime、CI、templateの所有pathだけに限定し、manifestへpath、kind、順序、before/after hashを固定する。各artifactは復旧内容そのものを持つdurableな`before` content snapshot、path/kind/source/after hashの参照、owner、retention期限または破棄条件を持つ。dry-runで差分とcompatibilityを確認し、applyは最初のwriteより前に全artifactを含むdurable journalを保存し、各write直前のbefore hash、atomicな単一file write、read-after-writeを順に記録する。複数file全体を不可分とは主張せず、partial applyやrollback中断は次回実行時に`artifacts[].before` contentを復旧正本として全targetを回復し、before/after hashは内容のintegrity検証に使うcrash-recoverable transactionとする。apply、rollback、retry、recoverはcall-siteから独立して渡されたapproved plan hashとexpected revisionを必須とし、state内の同名fieldをauthorityとして再利用しない。retryはさらにtrusted/candidate/manifestから再導出したplan IDが一致する場合だけ許可する。

Project policy setは`.agent-skill-chain/project-policy.json`をentrypointとし、choices、rules、conformanceの全fragmentをmanifestへ列挙する。trusted setは既定ブランチを最初にcommit SHAへ固定し、default、manifest、全fragmentを同じSHAから読む。candidate fallback、orphan/missing fragment、duplicate JSON key、absolute/parent/symlink/gitlink/executable path、case・Unicode衝突を拒否し、manifestを含むpathとraw bytesからset hashを作る。legacy monolithはproject directoryが完全に存在しない場合だけ読み、混在を拒否する。

Fragmented setの移行manifestはentrypointと全choice/rule/conformance fragmentをcandidateのraw inventoryと完全一致させ、assembled monolithをentrypointへ書くことを拒否する。trustedまたはrootがfragmentedならplain candidateを拒否する。apply後にfilesystem loaderで全setを再読込し、candidate set hashとsemantic policy hashの両方をread-after-write gateで確認する。回復失敗は復旧に必要なjournal/manifest/artifactを保持し、別reportへdiagnosticを記録する。

未知versionと未知fieldを黙殺せず、破壊的risk不明ならapplyを拒否してstagingまでに制限する。

旧harness、旧skill、旧hook、旧enforcementは移行元runtimeとして扱わず、復元も依存もしない。
