# 移行・廃止方針

v0.3は、旧harnessを意図的に削除した`renewal_v0.3.0`を基点に独立実装する。現行のCodex登録口`.agents/skills/asc-step/SKILL.md`を除く旧`.agents/`、`.workflow/`、hooks、commands、enforcementを無条件に復元せず、doctorで残存を報告するだけとする。

公開入口は`npx agent-skill-chain`とし、`install`は新規導入、`update`はpackage所有資産だけの更新、`delete`はmanaged hashが一致する資産だけの削除、`doctor`は読み取り専用診断を担う。利用側所有の仕様、project policy、変更済み品質文書、一時stagingを保持する。`update`で新しいpackage pathが追加されたとき、旧managed asset記録にない同名のconsumer fileはpackage正本とbyte一致する場合だけ採用し、異なる場合は上書きせず保持する。これにより、手動作成済みの同一`asc-step` adapterを安全にmanaged assetへ移行できる。内部関数名と旧CLI aliasの`init / upgrade / uninstall`は互換入力に限定し、新規利用手順へ公開しない。

ロールバックはv0.3実装コミットを戻し、旧harness削除済みの基点へ戻す。既存利用者への自動移行は行わない。release対象のmain mergeではGit tagとGitHub Releaseを自動作成する。**npm package公開の経路は存在しない。** 配布はGitのtag参照だけで行う。

## releaseとversion方針

自動release triggerの`push.paths` allowlistと、domainの`RELEASE_PATH_PREFIXES`、`RELEASE_PATHS`、`isReleasePath`は廃止する。移行後は`main`の全pushを起動対象とし、実際の`npm pack`配布境界から算出した配布digestが`v${package.json.version}` tagの再計算値と異なる場合だけreleaseへ進む。これにより既存の手書きpathへ配布対象を追加する移行作業は不要になる。ロールバックでは自動releaseを停止してtag・Releaseの実状態を確認し、漏れを再導入するpaths proxyへ戻さない。

製品versionの唯一の正本は`package.json.version`とする。自動release時に同versionのtagがなければversionを書き換えず、main merge SHAへtagとReleaseを作成する。同versionのtagが既に存在する場合、prereleaseは末尾のnumeric identifierを1つ上げ、prereleaseでないversionはpatchを1つ上げる。候補は`src/lib/version.ts`の`isPackageVersion`を満たす0.3.xだけとし、numeric prereleaseを解決できない場合や範囲外では停止する。

**version bump経路は存在しない。** `release/bump-v<version>` branch、`[skip ci]`付きcommit、PR、`RELEASE_MAIN_PAT`によるadmin merge、mainへの反映のいずれも行わない。**versionの正本は既存のGit tagであり、`package.json`はrelease番号を持たないsentinelを保持する。** 既定branchへは書き込まず、release候補SHAへ直接tagを作成する。

**versionの正本は既存のGit tagである。** `package.json.version`はrelease番号を持たないsentinelであり、release lineの検証にだけ使う。手動releaseは、入力versionが`package.json`の宣言するrelease line（prereleaseを剥いたcore）と一致し、直近の有効なrelease tagからSemVer順で単調増加し、同名tagが存在しない場合だけ本実行できる。**完全一致は要求しない。** dry-runでversion、tag、release note、`npm pack`対象を確認した後、別runで`dry_run=false`を明示する既存手順を維持する。

Git tagとGitHub Releaseは独立した状態として扱う。途中失敗では完了済みstage以降を自動継続せず、実状態を確認する。GitHub Release、続いてtagを必要な範囲だけ削除して再計画する。npm公開済みversionは削除による利用者影響を避け、`npm deprecate`で理由と代替versionを通知する。release workflow自体を戻しても既存のtag、Release、packageは消えないため、外部資産の復旧は別authorityと記録を伴う手動操作とする。

製品versionの正本は`package.json.version`とし、同じ`package.json`の`agentSkillChain`が現行・互換project policy schema versionを宣言する。今回の製品versionは`0.3.1-beta.1`、現行project policyは`v0.3.1`、互換入力は`v0.3.0`である。製品versionはSemVer 2.0.0としてpatchとnumeric prereleaseの不正な先頭ゼロ、空identifierを拒否し、build metadataを受理する。比較基点に実在する過去の誤表記`v0.3`は正式schema enumへ含めず、`deprecatedPolicySchemaAliases`のown propertyである場合だけ`v0.3.0`へ正規化するmigration専用入力として扱う。runtimeとlifecycleはpackage metadataを読み、schemaとの不一致はbuild gateで拒否する。

Project policy `v0.3.0`は互換入力として診断できる。`v0.3.1`への移行対象はpolicy、schema、runtime、CI、templateの所有pathだけに限定し、manifestへpath、kind、順序、before/after hashを固定する。各artifactは復旧内容そのものを持つdurableな`before` content snapshot、path/kind/source/after hashの参照、owner、retention期限または破棄条件を持つ。dry-runで差分とcompatibilityを確認し、applyはcall-siteのdurable journal保存関数を必須とし、最初のwriteより前に全artifactを保存できなければ何も変更しない。各write直前のbefore hash、atomicな単一file write、read-after-writeを順に記録する。複数file全体を不可分とは主張せず、partial applyやrollback中断は次回実行時に`artifacts[].before` contentを復旧正本として全targetを回復し、before/after hashは内容のintegrity検証に使うcrash-recoverable transactionとする。apply、rollback、retry、recoverはcall-siteから独立して渡されたapproved plan hash、expected revision、durable journal保存関数を必須とし、state内の同名fieldをauthorityとして再利用しない。retryはさらにtrusted/candidate/manifestから再導出したplan IDが一致する場合だけ許可する。

Project policy setは`.agent-skill-chain/project-policy.json`をentrypointとし、choices、rules、conformanceの全fragmentをmanifestへ列挙する。trusted setは既定ブランチを最初にcommit SHAへ固定し、default、manifest、全fragmentを同じSHAから読む。candidate fallback、orphan/missing fragment、duplicate JSON key、absolute/parent/symlink/gitlink/executable path、case・Unicode衝突を拒否し、manifestを含むpathとraw bytesからset hashを作る。legacy monolithはproject directoryが完全に存在しない場合だけ読み、混在を拒否する。

Fragmented setの移行manifestはentrypointと全choice/rule/conformance fragmentをcandidateのraw inventoryと完全一致させ、assembled monolithをentrypointへ書くことを拒否する。trustedまたはrootがfragmentedならplain candidateを拒否する。apply後にfilesystem loaderで全setを再読込し、candidate set hashとsemantic policy hashの両方をread-after-write gateで確認する。回復失敗は復旧に必要なjournal/manifest/artifactを保持し、別reportへdiagnosticを記録する。

未知versionと未知fieldを黙殺せず、破壊的risk不明ならapplyを拒否してstagingまでに制限する。

## Node.js 22.13.0限定Graph機能への移行

`node:sqlite`のextension load APIを使うGraph subcommandはNode.js 22.13.0以上に限定する。packageの最低runtimeはNode.js 20のままとし、CLIはGraph commandのversion guardが成功した後だけGraphQLite adapterをdynamic importする。Node 22.13.0未満はnetwork・filesystem・extension loadの前に拒否し、非Graph CLIはNode 20で従来どおり実行する。

GraphQLite databaseは移行対象の耐久データにしない。既存projectは固定assetのinstall preview/apply後、各worktreeのGit・text・provider耐久stateから新generationを完全構築する。旧database、他worktree database、branch間binaryを取り込まない。rollbackはGraph adapterの無効化と`.agent-skill-chain/runtime/graph/v1/`の破棄で行い、Git・text・provider正本を戻さない。

記録fileのない既存Issue stagingはlegacyとして保持し、年齢やdirectory名だけで移行・削除しない。通常fileの成果物がある対象は、ownerが成果物とGitHub trackerを再照合して新形式の記録を作成し、mode別最終checkpointを再確認してから専用previewへ進める。通常fileが0件の空または空directoryだけは、同期対象が存在しない限定候補として明示できる。このlegacy例外を無効化するロールバックでは全legacyを保持へ戻す。

旧harness、旧skill、旧hook、旧enforcementは移行元runtimeとして扱わず、復元も依存もしない。
