# 運用保守設計

公開操作は`npx agent-skill-chain install`、`npx agent-skill-chain update`、`npx agent-skill-chain delete`、`npx agent-skill-chain doctor`で行う。`doctor`はpackage所有資産、設定、旧runtimeの残存を読み取り専用で診断する。`install`、`update`、`delete`は無指定をpreviewとし、`--apply`が明示された場合だけ書き込む。内部関数名と旧CLI aliasの`init / upgrade / uninstall`を利用手順へ公開しない。

| 事象 | 確認 | 対応 | 保持する証拠 |
|---|---|---|---|
| CI失敗 | 失敗SCN・job・HEAD SHA | 同じscopeの原因だけ修正 | workflow runとtest出力 |
| GitHub書込失敗 | 認証、repository、対象状態 | 再認証または再計画 | 伏字化済み診断 |
| update競合 | managed hashと現ファイル | 利用側変更を保持 | retained一覧 |
| delete部分失敗 | managed record、削除済み一覧、未処理一覧、権限 | managed recordを保持し、権限と未処理対象を確認して同じ隔離先で`delete --apply`を再実行する | removed、pending、recovery |
| finalize拒否 | dirty、push、merge、復旧参照、報告hash | 不足条件を満たして再検証 | read-only report |
| network障害 | gateごとのexternal dependency | localを継続しexternalだけpending | local証拠とpending一覧 |
| workspace衛生の部分失敗 | 承認済みreport hash、削除済み・未処理path、Git HEAD・refs・status・worktree list | その場で停止し、未追跡fileをbackupから復元し、必要な空directoryを再作成してから新しいpreviewを取得する | preview report、削除済み・未処理一覧、復旧後のGit状態 |
| policy誤block | rule ID、risk、scope、falseBlock計測 | 独立reviewで観測・scope・diagnosticを修正しstaged移行。安全・authority境界、秘密、Git内部、identity、不可逆操作、artifact汚染、candidate自己承認のnon-override denyは弱めずfail closedを維持 | trusted policy、diagnostic、独立review、rollback history |
| provider停止・公式推奨不定 | provider実行入口、availability、recommended default、対応reasoning effort、scope、trusted mapping | Codexの値を推測せず、project choiceで設定したClaude coordinatorのproject defaultへ切り替える。発行済みevidenceがある中断ではcompletion recordへinterruptedを追記し、fallback routeの新evidenceを発行する | routing decision、routing evidence、completion record |
| routing evidence完了 | evidence ID、Issue、scope、実装head | evidence本体を変更せずcompletion recordを1件追記する | routing evidenceとcompletion record |
| 外部review指摘 | 指摘本文、現コードでの再現手順と再現結果 | 再現結果を記録してからresolved、rejected等へ分類し、再現なしの分類を拒否する | 指摘、再現手順、再現結果、分類 |
| release計画拒否 | version、tag、ref、SHA、必須gate、actor | 外部更新を開始せず、具体的な拒否理由を解消して新しいrunで再計画する | release計画JSONとworkflow summary |
| release途中失敗 | tag、GitHub Release、npm registryの実状態 | 完了済みstageと未完了stageを分離し、下記のstage別復旧を行う | 各jobの読取確認結果とworkflow summary |

## 手動release

`.github/workflows/release.yml`は`workflow_dispatch`だけで開始し、通常の`main` pushでは開始しない。実行者は`version`を必須入力とし、`dry_run=true`、`publish_npm=false`を安全な既定値とする。release対象は既定branchのdispatch時SHAだけであり、入力versionは`package.json.version`と一致し、直近の有効な`v0.3.x` tagよりSemVer順で大きくなければならない。これにより、tagが指すcommitとnpm packageのversionを一致させ、runner内だけでversionを書き換えた配布物を作らない。

検証jobは依存を固定導入し、`npm run prepack`で全Gherkin、lint、format、strict型検査、source契約、build、package contents、追跡、architecture、conformanceを検証する。その後、純関数のrelease計画を作り、version、`v${version}` tag、各stageの有効・無効と理由、release note候補、`npm pack --dry-run`の対象fileを`$GITHUB_STEP_SUMMARY`へ記録する。`dry_run=true`では`validate`だけを完了とし、Git tag、GitHub Release、npm公開のjobを開始しない。

本実行は`dry_run=false`を明示した場合だけ進む。Git tag、GitHub Release、npm公開を別jobとし、各操作後に外部状態を読み直して`state`を確定する。先行stageが失敗または読取確認できない場合、後続stageを成功扱いせず未完了として停止する。npm公開はさらに`publish_npm=true`、Git tagとGitHub Releaseの成功、保護environment `npm-production`の明示承認を要求し、`npm publish --provenance --access public`を使う。credentialはstepの`env`だけで渡し、計画、command、summaryへ出力しない。

### 権限境界

| job | 開始条件 | 権限 | 外部更新 |
|---|---|---|---|
| `validate` | 手動dispatch | `contents: read` | なし |
| `tag` | `ready`かつ非dry-run | `contents: write` | 検証済みSHAへの注釈付きGit tag |
| `github_release` | tagのremote読取確認成功 | `contents: write` | 検証済みtagのGitHub Release |
| `npm_publish` | 明示入力、先行2stage成功、environment承認 | `contents: read`、`id-token: write` | provenance付きnpm package |

### 途中失敗時の復旧

| 確認済み状態 | 成功として記録する範囲 | 復旧 |
|---|---|---|
| tag未確認 | `validate`まで | remoteに同名tagがないか確認し、原因を解消して新しいrunで再計画する |
| tag作成済み、GitHub Release未作成 | `tag`まで | ReleaseがないこととtagのSHAを確認し、remoteとlocalのtagを削除して再計画する |
| GitHub Release作成済み、npm未公開 | `github_release`まで | Releaseを削除し、npm未公開を確認後、必要ならtagを削除して再計画する |
| npm公開済み | `npm_publish`まで | 公開済みversionを削除せず、`npm deprecate`で理由と代替versionを案内する |

復旧操作も一括実行せず、GitHubとnpmの実状態を読み直してから対象ごとに行う。削除やdeprecateはこのworkflowが自動実行せず、repository maintainerとregistry ownerの別authorityで実施する。

## workspace衛生

`worktree hygiene --root=<repository root>`は、空directory、既知の未追跡一時生成物、未登録かつ空の`.worktrees/`直下containerを検査する。既定はread-only previewであり、候補path、理由、owner、削除可否、除外pathと理由、および決定的なSHA-256 report hashをJSONで返す。previewでは外部writeも削除も行わない。

applyは同じcommandへ`--apply --approved-hash=<64桁hex> --operations=<kind,...>`を明示した場合だけ行う。repository同一性、承認済みhash、全候補の再preview、対象operationを副作用前に検証し、stale preview、hash不一致、TOCTOUではremoveを一度も呼ばない。fileは非再帰の`rm`、空directoryは非再帰の`rmdir`に相当する処理だけを使い、広域の再帰削除を行わない。

`.git`、Git common directory、object、ref、reflog、worktree metadata、repository root、filesystem root、home、親参照、未解決env、glob、symlink、root外path、`node_modules`はoverride不能な除外境界である。内容のある`memo/`とfileは保持し、その配下で内容を持たないdirectoryだけを深い側から候補にする。登録済みworktreeは本commandで削除せず、対象PR単位の別の完了処理がGit公式`worktree remove`を使う。

apply前後でGit HEAD、refs、repository root、status、worktree listを読み直す。HEAD、refs、root、worktree listは不変、statusは削除対象だった未追跡一時生成物の消失だけを期待差分とする。removeの例外またはGit状態不一致では成功を返さず、削除済みpath、未処理path、backupからのfile復元、空directory再作成、Git状態再確認を復旧情報として報告する。
## lifecycleの隔離検証と復旧

導入・更新・削除の検証は、実workspace、実remote、他worktreeから分離した一時directoryだけで行う。隔離先にはpackage管理資産と同時に、他toolのskill、利用者文書、editor設定、symlink、Unicode正規化の異なるpath、読み取り専用file、Gitのdirty・untracked状態、project policy、project inventory、一時stagingを配置する。`install`はpackage配布物だけを追加し、`update`はmanaged recordに記録されたhashと一致する通常fileだけを更新し、`delete`はpackage所有path・containment・hashを全件検証した通常fileだけを削除する。

managed recordの不正JSON、objectでない`files`、不正hash、絶対path、親directory参照、Unicode非NFC path、重複するportable pathは、削除開始前にfail closedで拒否する。symlinkは管理hashと一致しても削除対象にせず、symlinkによる境界外移動は拒否する。preview後と各削除直前に通常fileとhashを再確認し、変更済み資産は`retained`へ移して削除しない。

削除途中で失敗した場合は`applied=false`とし、完了した`removed`、未完了の`pending`、再実行手順の`recovery`を返してmanaged recordを保持する。運用者は利用側資産を移動せず、pendingのpathと親directory権限を確認して同じrootへ`delete --apply`を再実行する。managed recordが既にない2回目の削除は未導入として停止し、外部pathを探索・削除しない。

## Secure Logging・Observability

診断と監査記録は目的と利用者を明示し、秘密、credential、個人情報、不要な識別子を記録しない。外部値はredactionし、権限のあるactorだけが参照でき、改ざんや証拠の差し替えを検出できる形式にする。保持期間、rotationまたは容量上限、削除・失効条件を出力先ごとに定め、無制限に蓄積しない。

このCLIは永続log基盤を自身で運用せず、構造化したredacted diagnostic、migration journal、metrics、GitHubのCI/review証拠を境界とする。journalはplanの完了・rollback・自動失効後に廃棄できるようにし、CI artifactの保持と容量上限はrepositoryのworkflow設定が所有する。監視はwait、duplicate、falseBlock、override、rollback、missとCI失敗を対象にし、安全gateを無効化せずに改善する。

## Agent Routingのroleとauthority

| Step | role・identity契約 |
|---:|---|
| 0、1、2、4、5、6、8 | coordinatorが進行、要求・設計・計画・同期と証拠集約を担う |
| 3、7、10 | reviewerが対象成果物の作成者と異なるidentityで肯定・敵対reviewと検証結果を作る |
| 9 | implementerが専用worktreeで失敗test、product code、test、system spec更新を担う |
| merge以降 | 人間だけがapproval、merge、Issue終了、release、cleanupのauthorityを持つ |

reviewerのproviderは固定しない。成果物の作成者がcoordinatorならcoordinator以外、作成者がimplementerならimplementer以外のidentityへ解決することだけを条件とする。AI reviewの成果物は指摘と検証結果であり、AIはapprovalを発行しない。PR approvalとmergeは人間のauthorityで行う。

## routing evidenceの保持と削除

本repositoryはproject choiceでstore rootを`docs/evidence/routing/`、保持期間を30日、1 Issueあたりの上限を20件、1 recordあたりの上限を65536 byte、rotation条件を`oldest_first`、削除方法を`preview_then_explicit`として所有する。汎用packageはこれらの具体値を既定せず、store rootまたは保持方針の5項目が欠ける場合は保存も削除も行わない。

routing evidence本体は排他的かつ原子的に1件発行し、issued後は書き換えない。終了はcompletion record、supersededとinvalidatedはEvidenceStateRecordとして追記し、有効状態は最後の状態recordから算出する。head変更ではrouting evidenceを失効させず、そのheadに依存するcompletion record、test、CI、review証拠を失効させる。

rotationのpreviewは保持期限超過、Issue単位の件数超過、容量超過を判定し、削除対象IDの字句順一覧と保持方針を含むdigestを返すだけで物理削除しない。削除applyは同じ対象一覧と承認済みdigest、および`--authorize=approved`を要求する。PruneAuditRecordを書いて再読取した後、各対象のtombstoneを先に耐久化してからrouting evidence、completion record、状態recordを物理削除し、対象ごとの成否をauditへ追記する。途中失敗時は同じPruneAuditRecord、tombstone、成功済みoutcomeから未完了対象だけを冪等に再開する。

## provider停止時のfallbackと再開

Codexを利用できる場合はCodexをimplementerへ決定的に割り当てる。Codex実行入口がunavailableまたはunknown、利用可能modelが空、公式recommended defaultが0件または複数、high非対応、trusted mappingとの不一致の場合は、Codexのmodelを推測せずClaude実装へ切り替える。fallbackはproject choiceの`when=implementer_unavailable / role=coordinator / modelSelection=project_default`を満たす場合だけ解決し、`routeMode=fallback`、切替理由、Claude identityをrouting decisionとevidenceへ記録する。

fallback後も実行直前に同じdecisionを再検証し、reviewerはClaude implementerと異なるidentityへ解決する。Codexが回復した新scopeまたは再割当ではpreferred routeを再解決できるが、進行中scopeを無告知で切り替えない。model slug台帳の定期更新は不要とし、Codex公式recommended defaultの変更へ実行時に追従する。旧evidenceが発行済みなら中断のcompletion recordを保持して旧evidenceをsupersededとし、新しいrouting evidenceを発行してから再開する。

今回作成するPRはmerge・後片付けを行わず、branchと専用worktreeを保持する。

本repositoryはproject固有policyで通常staged追加と自己緩和拒否をdogfoodし、migrationのapply、rollback、retryを隔離projectで再現する。metrics budget超過は改善対象でありsecurity gate無効化には使わない。

新設ruleはこのcandidate自身で`active`へせず、まず`staged`のままmergeして既定branch上のtrusted setにする。既定branchでproject CI hook、反例test、誤block・検出漏れの観測が成功した後、意味、scope、enforcement、overrideを変えず`activation`だけを昇格する別PRを作り、trusted-vs-candidate比較と独立reviewを通す。初回mergeまでのbootstrap期間はcandidate所有workflowだけをauthority正本にせず、固定した`H_impl`全差分の個別監査、外部providerが観測したexact-head CI、実装者・PR authorと異なるreviewerの承認を必須とする。

project policyの新しいfragment種別またはproject choice型を導入するときも二段階にする。基盤PRではmainが理解できるlegacy inventory・legacy値を維持して前方互換validatorを追加し、activation PRでは基盤PRのexact headをtrusted baseとして新fragmentと構造化値を追加する。提出前にはcandidateの`prepack`だけでなく、mainまたは対象base checkoutの`check_project_quality.ts`と`check_source_quality.ts`をcandidate rootへ実行し、trusted workflowと同じ方向の検証を記録する。

このrepository固有のCI、lint、format、typecheck、runner、validator、依存版を変更する場合は、最初のPRで`.github/trusted-quality-proposals.json`へ現在version、次version、owner、根拠、rollback、全対象のbefore/after SHA-256を`staged`登録する。このPRではprotected対象と`package.json.agentSkillChain.qualityContractVersion`を変更しない。登録が既定branchのtrusted baseになった後、次のPRでproposalと完全一致する対象だけを適用しversionを1だけ進める。既存proposalの変更・削除、同一PRで登録したproposalの利用、部分適用、未登録差分は拒否する。
