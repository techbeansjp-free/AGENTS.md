## merge後の終端処理

worktree directory名のtimestampは`YYYYMMDD_HHMMSS`を実行環境のlocal timeとして解釈する。明示pathは現在時刻以前かつ10分以内だけを許可し、未来は差が1秒でも拒否する。10分はCLI入力の確認とprocess起動の遅延を吸収しつつ、人またはAIが丸めて手入力した数時間前・翌日の値を排除する運用境界である。通常は`--path`を省略し、CLIが取得した同一の現在時刻、Issue番号、slugからpathを構成する。domainへ現在時刻が渡らない場合は検証を省略せず作成を拒否する。

GitHub標準の自動マージ・マージキュー、web UI、他者または別processによるmergeでは、完了時点にlocal processが存在しない。そのため後片付けをmerge sessionへ連鎖させず、事後のlocal `worktree survey`を正規の発見経路とする。走査は登録済みworktreeを読み取り専用で分類・報告するだけであり、削除は対象を明示して再検証する既存`worktree finalize`のevidence経路だけが行う。`worktree hygiene`は引き続き登録済みworktree本体を対象にしない。

`worktree survey`は、規定書式で解析できるdirectory名とbranch名のIssue番号またはslugが異なる場合、そのずれをentryの`reasons`へ追記する。追記は`disposition`決定後に行い、cleanup-ready、retain、in-progress、primaryの分類と削除判断を変えない。登録済みworktreeのdirectoryは改名せず、通常の後片付けまで保持する。

`worktree finalize --update-root --merge-sha=<40桁SHA>`は、PRのmerge成功をread-after-writeで確認して得た完全なmerge SHAだけを入力にする。対象repositoryのroot worktreeがcleanな既定branchで、未追跡fileがなく、upstreamが既知であり、upstream SHAとremote既定branch SHAとmerge SHAが一致し、local HEADからfast-forward可能な場合だけ、rootで`git merge --ff-only <merge SHA>`相当の処理を行う。適用後は`HEAD`を読み直し、merge SHAとの完全一致を成功条件にする。既に同じSHAなら書き込みを行わない冪等な完了とする。

rootがdirty、未追跡あり、非既定branch、upstream不明、remote同一性不一致、merge SHA不正・不一致、divergedのいずれかなら、root HEADを変更せず、理由と安全な復旧手順を構造化診断で返す。remote追跡参照の更新が必要な場合も、rootのlocal条件とremote merge SHAの同一性を先に確認する。GitHub Actionsはremote側の検証と通知だけを担い、利用者のlocal filesystemを更新済みとは報告しない。

worktree cleanupは、対象PR専用worktreeのpathとbranchに完全一致する登録がちょうど1件あり、PRがmerge済み、worktreeがclean、branchがpush済み、復旧参照へ到達可能、利用者所有資産が0件の場合だけreadyとする。prefix一致、大小文字を無視した一致、重複登録は一致として扱わない。適用はその1件へのGit公式`worktree remove`だけとし、他Issue・他agent・他利用者のworktree、他branch、prunable metadata、root以外の任意directoryを探索または削除しない。

通常のmerge後運用は`worktree finalize --complete --dry-run`でphaseとpreview digestを確認し、root／finalize authorityを示す`--authorize=approved`とは別に、cleanupを許可する場合だけ`--cleanup-authority --approved-digest=<preview digest>`を付けて`--apply`する。authorityなしでも安全なroot更新までは適用し、その後は`pending`として対象pathと再実行方法を返す。merge authorityをcleanup authorityへ読み替えない。

root更新後にcleanupが拒否または失敗した場合は`partially-completed`であり、branch削除、prune、手動の広域削除へ進まない。対象worktreeのpath、branch、status、upstream、復旧参照、利用者所有資産、最新digestを再確認し、同じ`--complete`入力でpreviewから再実行する。対象が既に削除済みなら再削除せず、root SHA、対象path不在、他worktree不変を再確認して完了へ収束する。

対象削除後はrepository直下`.worktrees/`だけを確認する。実在するsymlinkでない空directoryなら、workspace hygieneの`completed-worktree-container` operationと明示path `.worktrees`で非再帰除去する。非空、symlink、root外、読取不能では保持し、他containerを同時に削除しない。

canonical Issueを完了させるPR本文は`Closes #番号`で1回だけ参照し、merge時のGitHub標準動作で自動closeする。後続作業と非終端Issueは`Relates to #番号`だけで関連付ける。canonical Issue以外への`Close / Closed / Closes / Fixes / Resolves`はPR作成前に拒否する。branch削除、release、package公開はこの終端処理のoperation集合に含めず、個別authorityとread-after-writeを持つ別操作とする。

## 自動・手動release

`.github/workflows/release.yml`は、pathで限定しない`main`への全`push`と、既存の`workflow_dispatch`で開始する。自動経路は`npm run prepack`後の`npm pack --dry-run --json --ignore-scripts`が列挙する配布物をdigest化し、配布対象外の`docs/`、`memo/`、`test/`、`.github/`だけの変更では計画を停止する一方、配布対象の`README.md`や将来`package.json.files`へ追加されるfileの変更へ自動追随する。`package.json.version`を唯一のversion正本として`v${version}`のGit tagと同名GitHub Releaseを作成し、自動経路ではnpm公開を行わない。

自動release計画は既定branch、head commit message、現在version、既存tag、現在と前回の配布digestを外部処理なしで判定する。entrypointは`RELEASE_CURRENT_VERSION`が明示された場合にその値を現在versionとして使用し、省略された場合は従来どおり`package.json.version`を使用する。workflowはこの環境変数を渡さず、製品versionの正本を`package.json`に維持する。比較対象はtagのsort結果ではなく必ず`v${currentVersion}`とし、このtagがなければdigest比較を省略してmerge SHAをrelease対象とする。同名tagがある場合はtagをdetachした一時worktreeで依存導入とbuildを行い、配布digestを再計算する。現在digestを算出できなければ停止し、前回digestを算出できなければ取りこぼしを避けてfail-openし、digest一致時だけ停止する。差があればnumeric prereleaseは末尾番号、通常versionはpatchを0.3.x内で1つ上げ、`release/bump-v<version>` branchの`[skip ci]`付きcommitからPRを作成し、`RELEASE_MAIN_PAT`でadmin mergeする。mainへ直接pushせず、merge後のmain SHAとversionを読み直してrelease対象commitを解決し直す。

配布digestはpathと正規化後内容hashの組をUnicode codepoint順に並べたstable JSONのSHA-256とする。`package.json`のtop-level `version`、`package-lock.json`のtop-level `version`と`packages[""].version`だけを除外し、version bumpによる自己差分を判定へ混入させない。workflow summaryには現在digest、比較tagと前回digest、配布file件数、release要否と理由を残す。GitHub Release本文のdigestは参考情報であり、判定の正本はtag内容からの再計算である。

再帰triggerは、bump commitの`[skip ci]`、自動`validate` jobのhead commit message guard、`main-mutator` concurrencyによる直列化の複数機構で防ぐ。tagはremoteの同名refと対象SHAを作成前後に確認し、GitHub Releaseは同名Releaseを作成前後に読み直す。同じversion・SHAの再実行は既存資産を成功として扱い、異なるSHAまたはRelease名の衝突は上書きせず停止する。

手動経路は`version`を必須入力とし、`dry_run=true`、`publish_npm=false`を安全な既定値として維持する。release対象は既定branchのdispatch時SHAだけであり、入力versionは`package.json.version`と一致し、直近の有効な`v0.3.x` tagよりSemVer順で大きくなければならない。`dry_run=true`では検証だけを行い、外部更新を開始しない。

検証jobは依存を固定導入し、`npm run prepack`で全Gherkin、lint、format、strict型検査、source契約、build、package contents、追跡、architecture、conformanceを検証する。その後、純関数のrelease計画を作り、version、`v${version}` tag、各stageの有効・無効と理由、release note候補、`npm pack --dry-run`の対象fileを`$GITHUB_STEP_SUMMARY`へ記録する。`dry_run=true`では`validate`だけを完了とし、Git tag、GitHub Release、npm公開のjobを開始しない。

`bump_version` jobは、`npm run project:quality`、`npm run quality`、`npm run build`、`npm run docs:format`、`npm run test:format`、`npm run trace:check`、`npm run architecture:check`、`npm run conformance:check`、`npm run package:check`を順に実行する。この構成は`prepack`から`audit:check`だけを除いた品質gateである。`audit:check`は、review headのcommit構造から推定した実装commit `H_impl`との差分がreview artifact 1件だけであることを確認し、artifact本文の`H_impl`と二重確認するPRレビュー契約である。file名の番号やdirectory内の辞書順は選択へ使用しない。review artifactを持たず`package.json`と`package-lock.json`を機械生成するbump commitには適用せず、3条件を満たすrelease bumpは差分判定から除外する。`validate` jobと手動dispatch経路は引き続き`npm run prepack`を実行する。また、`.github/workflows/ci.yml`は`pull_request` triggerの品質jobで`npm run audit:check`を実行するため、通常PRの監査強度は維持する。

手動本実行は`dry_run=false`を明示した場合だけ進む。Git tag、GitHub Release、npm公開を別jobとし、各操作後に外部状態を読み直して`state`を確定する。先行stageが失敗または読取確認できない場合、後続stageを成功扱いせず未完了として停止する。npm公開jobは`github.event_name == 'workflow_dispatch'`かつ`inputs.publish_npm == true`を必須条件とし、さらにGit tagとGitHub Releaseの成功、保護environment `npm-production`の明示承認を要求する。自動push経路では条件が偽になるため`npm publish`へ到達しない。credentialはstepの`env`だけで渡し、計画、command、summaryへ出力しない。

### 権限境界

| job | 開始条件 | 権限 | 外部更新 |
|---|---|---|---|
| `validate` | release対象のmain push、または手動dispatch | `contents: read` | なし |
| `bump_version` | 自動計画が`bump-then-release` | `contents: write`、`pull-requests: write` | bump branch、PR、admin merge。mainへの直接pushは行わない |
| `tag` | 自動`release`またはbump成功、または手動`ready` | `contents: write` | 検証済みSHAへの注釈付きGit tag |
| `github_release` | tagのremote読取確認成功 | `contents: write` | 検証済みtagのGitHub Release |
| `npm_publish` | 手動dispatch、明示入力、先行2stage成功、environment承認 | `contents: read`、`id-token: write` | provenance付きnpm package。自動経路は非対象 |

### 途中失敗時の復旧

| 確認済み状態 | 成功として記録する範囲 | 復旧 |
|---|---|---|
| bump PR未merge | `validate`まで | bump branchとPRを読み直し、同じversionのopen PRを再利用してadmin mergeを再実行する |
| tag未確認 | `validate`または`bump_version`まで | remoteに同名tagがないか確認し、原因を解消して新しいrunで再計画する |
| tag作成済み、GitHub Release未作成 | `tag`まで | tagが対象SHAなら削除せず、同じrunを再実行してRelease作成だけを続ける。異なるSHAなら上書きせず停止する |
| GitHub Release作成済み、npm未公開 | `github_release`まで | tagとRelease名が一致すれば削除せず成功として扱う。自動経路ではnpm公開せず完了する |
| npm公開済み | `npm_publish`まで | 公開済みversionを削除せず、`npm deprecate`で理由と代替versionを案内する |

復旧操作も一括実行せず、GitHubとnpmの実状態を読み直してから対象ごとに行う。削除やdeprecateはこのworkflowが自動実行せず、repository maintainerとregistry ownerの別authorityで実施する。

## workspace衛生

`worktree hygiene --root=<repository root>`は、空directory、既知の未追跡一時生成物、未登録かつ空の`.worktrees/`直下containerを検査する。既定はread-only previewであり、候補path、理由、owner、削除可否、除外pathと理由、および決定的なSHA-256 report hashをJSONで返す。previewでは外部writeも削除も行わない。

applyは同じcommandへ`--apply --approved-hash=<64桁hex> --operations=<kind,...>`を明示した場合だけ行う。repository同一性、承認済みhash、全候補の再preview、対象operationを副作用前に検証し、stale preview、hash不一致、TOCTOUではremoveを一度も呼ばない。fileは非再帰の`rm`、空directoryは非再帰の`rmdir`に相当する処理だけを使い、広域の再帰削除を行わない。

`.git`、Git common directory、object、ref、reflog、worktree metadata、repository root、filesystem root、home、親参照、未解決env、glob、symlink、root外path、`node_modules`はoverride不能な除外境界である。内容のある`memo/`とfileは保持し、その配下で内容を持たないdirectoryだけを深い側から候補にする。登録済みworktreeは本commandで削除せず、対象PR単位の別の完了処理がGit公式`worktree remove`を使う。

apply前後でGit HEAD、refs、repository root、status、worktree listを読み直す。HEAD、refs、root、worktree listは不変、statusは削除対象だった未追跡一時生成物の消失だけを期待差分とする。removeの例外またはGit状態不一致では成功を返さず、削除済みpath、未処理path、backupからのfile復元、空directory再作成、Git状態再確認を復旧情報として報告する。

## 一時ステージング・ライフサイクル

`issue staging --root=<repository root>`は`.agent-skill-chain/tmp/issues/`直下だけを有限走査し、既定ではread-only previewを返す。previewは候補と除外のexact相対path、kind、owner、理由、content digest、filesystem fingerprint、tracker、同期時刻、checkpoint、およびroot・候補・除外から決定的に算出したSHA-256 report hashを含み、fileを変更しない。

applyは`--apply --approved-hash=<64桁hex>`を同じcommandへ指定した場合だけ行う。root、plan自身のhash、承認hash、保持期間、全stagingの再plan hashを副作用前に完全一致させる。対象ごとに`.agent-skill-chain/tmp/issues/`直下、symlinkでない通常directory、realpath containment、Git内部領域不在を再確認してから、安全に検査した通常fileとdirectoryだけを深い側から削除する。ひとつでも事前条件が不明なら0件で`rejected`にする。

削除中の例外または削除後も対象が存在する場合は、その場で停止して`partially-completed`とし、削除済み、失敗対象、未処理、同期前対象を分けて返す。運用者は手動の広域削除へ切り替えず、残存内容と権限を確認して新しいpreview hashを取得する。fresh previewで対象が0件なら冪等な`completed`とする。

保持期限超過は診断条件であり、未同期stagingの削除authorityではない。記録のないlegacyは、通常fileの成果物が0件である空または空directoryだけの対象を除いて保持し、記録作成と再同期を案内する。workspace hygiene、package update、package deleteは`.agent-skill-chain/tmp/`、`role-log/`、`metrics/`を専用証拠なしに一般的な空directoryや一時生成物として削除しない。
## lifecycleの隔離検証と復旧

導入・更新・削除の検証は、実workspace、実remote、他worktreeから分離した一時directoryだけで行う。隔離先にはpackage管理資産と同時に、他toolのskill、利用者文書、editor設定、symlink、Unicode正規化の異なるpath、読み取り専用file、Gitのdirty・untracked状態、project policy、project inventory、一時stagingを配置する。`install`はpackage配布物と両host skill登録アダプターだけを追加し、`update`はmanaged recordに記録されたhashと一致する通常fileだけを更新する。新規package pathに同一内容の手動adapterがあれば管理対象へ採用し、異なる内容は保持する。`delete`はpackage所有path・containment・hashを全件検証した通常fileだけを削除する。

managed recordの不正JSON、objectでない`files`、不正hash、絶対path、親directory参照、Unicode非NFC path、重複するportable pathは、削除開始前にfail closedで拒否する。symlinkは管理hashと一致しても削除対象にせず、symlinkによる境界外移動は拒否する。preview後と各削除直前に通常fileとhashを再確認し、変更済み資産は`retained`へ移して削除しない。

削除途中で失敗した場合は`applied=false`とし、完了した`removed`、未完了の`pending`、再実行手順の`recovery`を返してmanaged recordを保持する。運用者は利用側資産を移動せず、pendingのpathと親directory権限を確認して同じrootへ`delete --apply`を再実行する。managed recordが既にない2回目の削除は未導入として停止し、外部pathを探索・削除しない。

## worktreeの作成と完了後cleanup

通常の実装worktreeはrepository rootの`.worktrees/`直下だけへ作成する。directory名は`YYYYMMDD_HHMMSS-<Issue番号>-<slug>`、branch名は`<type>/<Issue番号>-<slug>`とし、`type`はproject policyの`worktree.allowedBranchTypes`から選ぶ。project policyに`worktree`がない既存projectでは、packageの安全側既定値を使用する。`.worktrees/`は`.gitignore`でGit管理対象外とし、npm packageは`package.json.files`の許可listに含めない。

作成直前にrepository root、origin repository、`origin/HEAD`が示すremote default branch、取得済みremote tracking refの40桁SHA、指定baseの解決SHA、登録済みworktree一覧、作業元statusを検証する。baseはremote default branch SHAと完全一致させ、local branch名だけでは作成しない。絶対path、親参照、nested path、Unicode制御文字、非NFC、symlinkで移動した`.worktrees/`、Git内部領域、同一Issue・branch・pathとcase・Unicode正規化衝突を作成前に拒否する。作成後に作業元statusが変化した場合は自動削除せず、両worktreeを保持して復旧情報を返す。

testは`mktemp`配下に作成した隔離repositoryだけを使用し、製品repositoryの`.worktrees/`、他Issue・他agentのworktree、branch、prunable metadataを変更しない。merge後cleanupは、登録済みworktreeのcanonical pathとbranchが対象PRの記録済みpath・branchへ大文字小文字も含めて完全一致する場合だけ対象にする。prefix一致、case-insensitive一致、Unicode正規化だけの一致を対象にせず、他worktree・branch・metadataを暗黙に削除しない。worktree削除後、`.worktrees/`自体が空であることを再確認した場合だけ空rootを削除できる。

## Secure Logging・Observability

診断と監査記録は目的と利用者を明示し、秘密、credential、個人情報、不要な識別子を記録しない。外部値はredactionし、権限のあるactorだけが参照でき、改ざんや証拠の差し替えを検出できる形式にする。保持期間、rotationまたは容量上限、削除・失効条件を出力先ごとに定め、無制限に蓄積しない。

このCLIは永続log基盤を自身で運用せず、構造化したredacted diagnostic、migration journal、metrics、GitHubのCI/review証拠を境界とする。journalはplanの完了・rollback・自動失効後に廃棄できるようにし、CI artifactの保持と容量上限はrepositoryのworkflow設定が所有する。監視はwait、duplicate、falseBlock、override、rollback、missとCI失敗を対象にし、安全gateを無効化せずに改善する。

## routing evidenceの保持と削除

本repositoryはproject choiceでstore rootを`docs/evidence/routing/`、保持期間を30日、1 Issueあたりの上限を20件、1 recordあたりの上限を65536 byte、rotation条件を`oldest_first`、削除方法を`preview_then_explicit`として所有する。汎用packageはこれらの具体値を既定せず、store rootまたは保持方針の5項目が欠ける場合は保存も削除も行わない。

routing evidence本体は排他的かつ原子的に1件発行し、issued後は書き換えない。終了はcompletion record、supersededとinvalidatedはEvidenceStateRecordとして追記し、有効状態は最後の状態recordから算出する。head変更ではrouting evidenceを失効させず、そのheadに依存するcompletion record、test、CI、review証拠を失効させる。

rotationのpreviewは保持期限超過、Issue単位の件数超過、容量超過を判定し、削除対象IDの字句順一覧と保持方針を含むdigestを返すだけで物理削除しない。削除applyは同じ対象一覧と承認済みdigest、および`--authorize=approved`を要求する。PruneAuditRecordを書いて再読取した後、各対象のtombstoneを先に耐久化してからrouting evidence、completion record、状態recordを物理削除し、対象ごとの成否をauditへ追記する。途中失敗時は同じPruneAuditRecord、tombstone、成功済みoutcomeから未完了対象だけを冪等に再開する。

## provider停止時のfallbackと再開

Codexを利用できる場合はCodexをimplementerへ決定的に割り当てる。Codex実行入口がunavailableまたはunknown、利用可能modelが空、公式recommended defaultが0件または複数、high非対応、trusted mappingとの不一致の場合は、Codexのmodelを推測しない。既存fallback形式をrouting decisionへ記録してもcoordinatorのproduct実装authorityにはせず、独立implementerへの再割当、scope縮小、または人間への移管を選ぶ。role operationと必要tierを再検証するまで実装を開始しない。

fallback後も実行直前に同じdecisionを再検証し、reviewerはClaude implementerと異なるidentityへ解決する。Codexが回復した新scopeまたは再割当ではpreferred routeを再解決できるが、進行中scopeを無告知で切り替えない。model slug台帳の定期更新は不要とし、Codex公式recommended defaultの変更へ実行時に追従する。旧evidenceが発行済みなら中断のcompletion recordを保持して旧evidenceをsupersededとし、新しいrouting evidenceを発行してから再開する。
