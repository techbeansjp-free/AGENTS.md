複数ファイルのstagingと仕様初期生成は、一時隣接ディレクトリへ完成させてから原子的に公開する。

Policy migration stateはplan ID、from/to version、適用前snapshot、candidate、compatibility、history、artifact owner、retentionを持つ。durable journalは復旧contentとartifact参照を全て含めて最初のwrite前に耐久化する。Override監査は対象rule・expected rule・recordのrule ID完全一致、Issue、scope、actor、理由、期限、SHAだけを保持し、秘密値を含めない。開発計測はgateWaitMs、duplicate、falseBlock、override、rollback、missの集計値を扱う。

`.agent-skill-chain/project-policy.json`、`.agent-skill-chain/tmp/`、role log、開発計測、test fixture、秘密情報は利用側・開発用データでありnpm packageへ含めない。

## モード判定成果物とstep journal

`00_モード判定.json`は`.agent-skill-chain/schemas/workflow-mode-decision.schema.json`に従い、`mode / requestedMode / answers / reasons / decidedAt`を持つ。`answers`はQ-01〜Q-08を全件持ち、poc判定時は`PocDeclaration`と起票時`baselineHeadSha`を必須とする。PoC宣言は期間と未実装digestを持たず、隔離fixtureのID・root・隔離/初期化Evidence、runnerのID・相対path、1件以上のuse case、各use caseを参照するBDD scenario・固定argv、各scenarioを参照する機械observableを保持する。IDは用途別prefixへ拘束し、配列内の重複と参照切れを拒否する。判定は既存`classifyMode`だけが行い、成果物処理で再実装しない。

`poc-observations/<headSha>.json`は`.agent-skill-chain/schemas/poc-observation.schema.json`に従うASC実測Evidenceであり、同じPoC宣言のSHA-256、exact HEAD、UTC観測時刻、HEADから計測したfixture・runner digest、scenarioごとの`exitCode / signal / executionDigest`、宣言順の全observable resultを持つ。各resultはobservable/scenario/kind/target/expected/actual/statusと自己を除く正準JSONのSHA-256を持ち、全体も`evidenceDigest`自身を除く正準JSONのSHA-256を持つ。全scenarioが`exitCode=0`・`signal=null`かつ全resultが`passed`の場合だけ有効である。raw stdout/stderrを保存しない。staging inventory/digestへHEAD別append-onlyで含め、同一HEADの異なる内容を置換せず、Step 9以降のjournal bindingから参照する。

`journal/steps.jsonl`の各行は`.agent-skill-chain/schemas/workflow-step-journal.schema.json`に従い、`step / skillId / mode / recordedAt / artifacts / evidence`を必須とする。未知field、空artifact、空evidence、Stepとskill IDの不一致を拒否する。Step 10だけは`reviewSession` objectの`sessionId / roundDigest / headSha`をすべて必須とし、他Stepでの使用を拒否する。HumanOverride行だけは対象Issueとscopeへ拘束した`humanOverride`を追加できるが、Step 10を補完できない。検証はJSONLの行順だけを使用し、`recordedAt`の前後を実施順判定へ使用しない。

`review-session.json`は`agent-skill-chain/review-session/v1`で、scope ID、Acceptance Criteria ID、domain invariant ID、Git基点、初回HEAD、初回差分digestからsession IDを再導出する。roundは1から連番で、直前round digest、candidate HEAD、実Gitの修正path、Graph Evidence digest付き隣接path、findingのadmission、blocker、record-only、round digestを保持する。Graph Evidenceの実照合が未実装の間、隣接pathは記録だけに使用し、current blockerのadmission authorityにしない。読取り時は各roundを先頭から再評価し、保存済みadmission・blocker・digest・statusの自己申告をauthorityにしない。`active / converged / budget-exhausted`のみを許可する。`converged`後は前roundと異なるcandidate HEADと実Gitの空でないfixed diffがあるround 2/3だけを同digest chainへ追記できる。同じHEAD、空fixed diff、`budget-exhausted`後、round 1 reset、anchor変更、previous blocker脱落を拒否する。

## delivery状態

squash/rebaseのsource commit数は固定base..headの線形historyから導出し、squashは単一結果、rebaseは導出件数の1-parent chainとして検証する。sourceが1件でprovider requestが消失したときは、固定methodは保持しつつsquash/rebaseの結果同値性を明示する。

`journal/delivery-state.json`は`.agent-skill-chain/schemas/delivery-state.schema.json`に従い、未知fieldと重複JSON keyを拒否する。repositoryとGitHub URLは正準化し、Git OID、SHA-256 digest、UTC時刻、Issue・PR番号を厳密に検証する。共通の前半は`create-prepared → pr-bound`とする。PoCとdisabledはそこから`step11-recorded(outcome=pull-request)`へ進み、automaticのmerge経路は`pr-bound → merge-prepared → merge-observed → step11-recorded(outcome=merged)`へ進む。assistedのauthority待ちは`pr-bound`に残る。外部結果を確定できない場合は`reconciliation-required`を使用し、revisionは各遷移で単調増加する。

`create-prepared`はrepository、canonical Issueと絶対URL、head ref/SHA、base ref、作成時base SHA、canonical title/bodyの`pullRequestDigest`、closing契約digest、準備時刻、nullableな`dispatchClaimedAt`を持つ。`dispatchClaimedAt=null`だけがprovider create未dispatchを表し、時刻が入った後は応答の成否にかかわらず同じ要求を再送しない。`pr-bound`はprovider read-backしたPR番号・URLを加え、repository、PR、Issue、same-repository HEAD、canonical title/body、base ref、closing契約を以後変更できない。作成時base SHAは監査値として保持するが、同じbase ref上の通常の前進を禁止しない。base前進後も固定identityへ一致する既存OPEN PRのread-only復旧は許可する一方、固定intentによる新規createの再試行は認めない。新しいprovider tipでのcreateには別の明示されたworkflowと新規intentが必要である。CLOSEDまたはMERGEDの一致PRを観測した場合は新しいPRを作らない。merge認可時にはprovider default branch tip、current PR base SHA、current trusted policy commitを一致させる。

`merge-prepared`はmethod、認可HEAD、認可base ref/SHA、trusted policy commit、H_impl、review artifact path/digest、対象PRのsuccessful CI run ID、actor別の最新状態から採用した独立review ID、それらの正規`reviewEvidenceId`、intent ID、準備時刻、nullableな`dispatchClaimedAt`をprovider mergeより前に保持する。`dispatchClaimedAt=null`だけが未dispatchを表し、時刻が入った後は再送しない。`merge-observed`は同じrepository、PR、Issue、HEAD、closing契約、provider状態、観測時刻、merge commit SHAから決定する観測digestを持つ。`providerRequest`は観測できた場合に限り、auto-mergeで`kind / requestedAt / method / headSha / baseSha`、merge queueで`kind / requestId / requestedAt / queueState / headSha / baseSha`を持つ。local claim時刻とprovider時刻の大小は因果Evidenceにせず、同じprovider clockのrequest時刻とmerged時刻だけを順序検査する。要求またはqueue登録だけでは`step11-recorded`へ進まず、`merged`・merge commit SHA・method別の親・期待tree・既定branch ancestryを再観測した場合だけStep 11のjournal digestと結び付ける。初回read-back前にrequestが消えた即時完了は`providerRequest=null`のままresult Evidenceで確定する。merge照合の`reconciliation-required`は失敗前に確定した`providerRequest`を含むobservationを保持でき、公開schemaも同じ状態を受理する。`step11`は`outcome / recordedAt / journalDigest / evidenceId`を持ち、outcomeと状態の不整合を拒否する。曖昧な`create-prepared`・`merge-prepared`・`reconciliation-required`からの再開はprovider read-backを先に行い、外部create/mergeを再送しない。一度もdispatchしていないprepared intentは対応するprovider副作用のexact absenceと現在の認可tupleを決定的に確認できた場合だけ、`reconciliation-required`から前向き復旧して同一immutable intentを1回再試行できる。Step 11 journalとdelivery stateの間のcrash windowは、復旧判定前に実artifact一覧とcontent digestを保存済みstaging recordへ照合し、その後に既存journal entryのdigest、outcome、evidence IDを検証してstateだけを前向きに復旧する。

## 一時staging記録

Issue stagingのdir名は`YYYYMMDD_HHMMSS_<slug>`とし、prefixは同じ作成instantに対する日本標準時（Asia/Tokyo、UTC+09:00）を使う。host timezoneが異なっても同じ識別名になり、`createdAt`とモード判定の`decidedAt`は同じinstantをISO 8601で保持する。

`staging-record.json`は`.agent-skill-chain/schemas/staging-record.schema.json`に従い、未知fieldと重複JSON keyを拒否する。`schemaVersion`、`mode`、字句順かつ重複なしの相対`artifacts`、成果物ごとのSHA-256から決める`digest`、既知`owner`、`createdAt`、`state`を必須とする。同期前の`tracker`、`checkpoint`、`syncedAt`、`syncDigest`、`readBackDigest`は`null`である。

quickとpocはStep 4、fullはStep 8のGitHub Issue書き込み後再読取が成功し、期待body digestと再読取digestが一致した場合だけ、同期5項目を同時に保存して`sync-verified`へ遷移する。trackerはrepositoryとIssue番号を再構成できる`https://github.com/<owner>/<repository>/issues/<number>`形式の絶対URLだけを保存し、`#123`または`123`の短縮形をwriter、parser、schemaのすべてで拒否する。成果物追加後はinventoryとcontent digestを同期記録時に更新する。本文、credential、秘密は記録せず、trackerとdigestだけを保持する。

Step 4で`sync-verified`になったquickまたはpocをfullへ昇格すると、`mode=full / state=promotion-active / checkpoint=4`へ単調遷移する。tracker、syncedAt、syncDigest、readBackDigestは昇格前の再現可能な履歴として保持し、昇格後成果物の現行同期Evidenceとは扱わない。昇格前00とモード判定、発見判定を別artifactへ保存し、元の`requestedMode`と発見Evidenceからfullを再現する正規mode decision、full用00〜03、更新後content digestを記録する。staging外writer lockとstaging内transaction markerは実行中だけ存在し、通常の成果物一覧には残さない。markerを除外した最終artifact一覧・digestをrecordへ書いて全fileとdirectoryを耐久化した後にmarkerを削除する。昇格後Step 4は同じIssueへの同期だけを許可して記録を変えず、Step 8で同じIssueを再読取確認した後だけ`checkpoint=8 / state=sync-verified`へ進む。未同期quick/pocの昇格は同期fieldをnullのまま`mode=full / state=local-active`とする。

保持日数は利用projectが操作入力として所有する。`sync-verified`かつ`createdAt`から保持期限を経過した対象だけを`deletion-ready`にする。`local-active`、`promotion-active`、成果物不足、digest不一致、部分的な同期証拠、未知ownerは年齢にかかわらず保持する。記録fileのないlegacy directoryは自動移行せず、通常fileの成果物が1件以上あれば保持する。空、または空directoryだけで通常fileの成果物が0件の場合に限り、同期対象が存在しない限定的なlegacy候補として`deletion-ready`にできる。
