# 管理データ

| データ | 正本 | 所有者 | 保持・更新 |
|---|---|---|---|
| Issue本文 | GitHub Issue #824 | リポジトリ所有者 | GitHub上で耐久化し、同期後に再読取する |
| Issue作成前staging | `.agent-skill-chain/tmp/issues/` | runtime・利用側 | Git管理外。正本ではなく、同期確認と利用projectの保持期限を満たすまで保持する |
| staging記録 | 各Issue staging直下の`staging-record.json` | runtime・project owner | 原子的に生成・更新し、削除と同時に破棄する |
| モード判定成果物 | 各Issue staging直下の`00_モード判定.json` | runtime・change owner | Step 0で正準JSONとして生成し、stagingと同じ期間保持する |
| step journal | 各Issue staging直下の`journal/steps.jsonl` | runtime・change owner | 1行1entryで追記し、stagingと同じ期間保持する。現在時刻はcallerが供給する |
| project policy | 既定branchの`.agent-skill-chain/project-policy.json` | プロジェクト所有者 | 候補PR側の変更をmerge判断へ使用しない |
| system specification | `docs/specs/` | 利用側 | 初期生成後はupgradeで上書きしない |
| review・test証拠 | HEAD SHAに結び付いたJSONとPR/Issue記録 | 実行主体 | PR判断時にSHA一致を検証する |
| managed asset記録 | `.agent-skill-chain/managed-assets.json` | lifecycle | 中央資産と両host skill登録アダプターのhashを保持し、hash一致したpackage所有物だけ削除対象にする |
| migration復旧artifact | durable journal内のbefore contentとpath/kind/source/before-after hash参照 | project policy owner | first-write前に保存し、transaction完了と外部証拠確認まで保持する。rollback/recovery不能時は破棄せずownerへ引き継ぐ |

複数ファイルのstagingと仕様初期生成は、一時隣接ディレクトリへ完成させてから原子的に公開する。

Policy migration stateはplan ID、from/to version、適用前snapshot、candidate、compatibility、history、artifact owner、retentionを持つ。durable journalは復旧contentとartifact参照を全て含めて最初のwrite前に耐久化する。Override監査は対象rule・expected rule・recordのrule ID完全一致、Issue、scope、actor、理由、期限、SHAだけを保持し、秘密値を含めない。開発計測はgateWaitMs、duplicate、falseBlock、override、rollback、missの集計値を扱う。

`.agent-skill-chain/project-policy.json`、`.agent-skill-chain/tmp/`、role log、開発計測、test fixture、秘密情報は利用側・開発用データでありnpm packageへ含めない。

## モード判定成果物とstep journal

`00_モード判定.json`は`.agent-skill-chain/schemas/workflow-mode-decision.schema.json`に従い、`mode / requestedMode / answers / reasons / decidedAt`を持つ。`answers`はQ-01〜Q-08を全件持ち、poc判定時は`PocDeclaration`を必須とする。判定は既存`classifyMode`だけが行い、成果物処理で再実装しない。

`journal/steps.jsonl`の各行は`.agent-skill-chain/schemas/workflow-step-journal.schema.json`に従い、`step / skillId / mode / recordedAt / artifacts / evidence`を必須とする。未知field、空artifact、空evidence、Stepとskill IDの不一致を拒否する。HumanOverride行だけは対象Issueとscopeへ拘束した`humanOverride`を追加できる。検証はJSONLの行順だけを使用し、`recordedAt`の前後を実施順判定へ使用しない。

## 一時staging記録

`staging-record.json`は`.agent-skill-chain/schemas/staging-record.schema.json`に従い、未知fieldと重複JSON keyを拒否する。`schemaVersion`、`mode`、字句順かつ重複なしの相対`artifacts`、成果物ごとのSHA-256から決める`digest`、既知`owner`、`createdAt`、`state`を必須とする。同期前の`tracker`、`checkpoint`、`syncedAt`、`syncDigest`、`readBackDigest`は`null`である。

quickとpocはStep 4、fullはStep 8のGitHub Issue書き込み後再読取が成功し、期待body digestと再読取digestが一致した場合だけ、同期5項目を同時に保存して`sync-verified`へ遷移する。成果物追加後はinventoryとcontent digestを同期記録時に更新する。本文、credential、秘密は記録せず、trackerとdigestだけを保持する。

保持日数は利用projectが操作入力として所有する。`sync-verified`かつ`createdAt`から保持期限を経過した対象だけを`deletion-ready`にする。`local-active`、成果物不足、digest不一致、部分的な同期証拠、未知ownerは年齢にかかわらず保持する。記録fileのないlegacy directoryは自動移行せず、通常fileの成果物が1件以上あれば保持する。空、または空directoryだけで通常fileの成果物が0件の場合に限り、同期対象が存在しない限定的なlegacy候補として`deletion-ready`にできる。
