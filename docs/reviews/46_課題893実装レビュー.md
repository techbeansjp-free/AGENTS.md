## 真因

`WORKTREE_NAME`はtimestampを捕捉群として取り出しているが、**コード中で一度も使われていなかった。**

```text
const WORKTREE_NAME = /^(\d{8}_\d{6})-(\d+)-([a-z0-9][a-z0-9-]*)$/u;
                        ↑ directory[1] が未使用
```

検証されるのは`directory[2]`（Issue番号）と`directory[3]`（slug）だけで、**書式が合っていればどんな日時でも通っていた。**

実測。

| directory名のprefix | 実際の作成時刻 | ずれ |
|---|---|---|
| `20260826_010000` | 2026-08-25 15:59 JST | **翌日の日付** |
| `20260825_233000` | 2026-08-25 15:18 JST | 8時間 |
| `20260825_230000` | 2026-08-25 16:11 JST | 7時間 |

全worktreeのprefixが`230000`、`220000`、`010000`のように**30分・1時間の丸い値**である。実時刻がこうなることはない。人またはAIが手で書いた値がそのまま通っていた。

**同じ情報を2回受け取り、片方だけを検証に使っていた。** timestampだけは他に照合先が無いため検証されないまま残った。しかし照合先はある。実際の作成時刻である。

これは#879、#892、#894と同じ構図である。

## 検証順序の回帰を是正した

実装中、`SCN-E2E-RISK-007`が失敗した。

```text
AssertionError: assert.ok(result.stdout.includes("ASC-GIT-INTERNAL-001"))
```

このtestは`.git/<name>`というGit内部pathへのworktree作成を試み、Git内部境界での拒否を期待する。しかし`.git/<name>`は`{timestamp}-{issueNumber}-{slug}`書式ではないため、**追加したtimestamp検証がより先に反応し、より重い違反が隠された。**

**#831で一度是正した回帰と同型である。** 当時も配置検証がtrusted境界検証より先に実行され、`ASC-GIT-INTERNAL-001`が失われた。

trusted boundary検証をtimestamp検証より先に評価する順序へ復元した。

さらに**他の重い違反が隠されていないかを全件確認した。**

| 項目 | 結果 |
|---|---|
| Unicode制御文字 | 隠蔽なし。制御文字違反が命名違反より先 |
| NFC非正規化 | 隠蔽なし |
| 親参照 | 隠蔽なし。親参照 → 配置 → 命名の順 |
| 絶対path | 隠蔽なし。repository相対path → 配置 → 命名の順 |
| 登録済みworktree衝突 | 隠蔽なし。命名違反と衝突理由の両方を報告 |

回帰を防ぐ反例として`SCN-UNIT-WTTS-009`と`SCN-UNIT-WTTS-010`を追加した。

### 敵対観点の残論点

**10分という許容範囲に根拠の幅がある。** CLI入力確認やprocess起動の遅延を吸収する目的だが、遅い環境では不足しうる。範囲を定数として定義し仕様へ明記したため、実績を見て調整できる。

**local time解釈は環境依存である。** 異なるtime zoneの開発者が同じrepositoryで作業すると、directory名のtimestampが互いにずれて見える。既存directoryがlocal timeで作られているため互換のためにこの解釈を採ったが、UTC固定のほうが曖昧さは少ない。移行するなら既存directoryの扱いを決める必要がある。

**既存worktreeのずれは解消しない。** 検出して報告するに留める。後片付けの過程で自然に消える。
