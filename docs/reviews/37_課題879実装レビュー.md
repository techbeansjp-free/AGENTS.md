## 真因の特定

`on.push.paths`はnpm配布境界のproxyである。`package.json`の`files`と同じ「配布物の境界」を二重に表現し、一方を手で維持する。

実際にずれた。#858で`README.md`を`files`へ追加したとき`paths`は更新されず、**README単独の変更がreleaseされない状態が続いた。** `paths`を配布境界へ揃え直しても、次に配布対象が増えたとき同じ穴が開く。

`paths`はproxyとして不正確でもある。`scripts/`を変更しても`dist/`の出力が同一なら配布物は変わらないが、旧allowlistはreleaseしていた。

したがって是正は「`paths`の内容を直す」ではなく「proxyを持たない」である。判定を`files`から導出すれば、`files`が単一の正本になる。

## 設計判断

| 判断点 | 採用 | 理由 |
|---|---|---|
| 比較対象tagの解決 | `v${currentVersion}` | このrepositoryには`v20260720.060726`、`apm-v0.1.1`など旧体系tagが248件あり、semver sortは誤った対象を選ぶ。自動releaseの流れによりmainのversionは常に直前releaseのversionと一致する |
| `version` fieldの扱い | digestから除外 | 除外しないとbumpのたびにdigestが変わり、判定が常に「変化あり」となって無意味になる |
| 前回digestの保存 | 保存しない | 保存fileの更新commitが新たなchurnを生み、改竄可能な状態が増える。tagから再計算する |
| digest算出失敗時 | fail-openしrelease | 取りこぼしより余分な版が1つ増えるほうが害が小さい。releaseは可逆でないが、配布物が同一の版は無害である |
| 並行merge | 対応不要 | 各runは「前回releaseした配布物」と比較する。concurrencyで中間runがcancelされても後続が累積分をまとめて検出する |

### 敵対観点の残論点

**`paths`廃止によりCI時間が増える。** 配布物が変わらないmerge（`docs/specs/`のみの変更など）でも`npm run prepack`が先に走り、そののちskipと判定される。judgeを`prepack`より前へ置けば`npm run build`だけで短絡できるが、job順序の再構成を要するため本変更には含めない。実害は待ち時間のみであり、release自体は正しく抑止される。

**前回tagのbuild失敗がfail-openで版を増やす。** 各pushでrelease 1回に限られ、bump commitは`[skip ci]`で再帰しないため無限loopにはならない。ただし旧tagのbuildが恒常的に失敗する状況では、配布物が同一でも版が増え続ける。旧tagはすべてv0.3.x系であり現時点で成立するが、Node major更新時には再評価が要る。

**配布fileをutf8として読む。** 現在の配布物は`.js`、`.d.ts`、`.map`、`.md`、`.json`のみで、すべてtextである。将来binaryを配布対象へ加える場合はbufferでのhash算出へ変更する必要がある。
