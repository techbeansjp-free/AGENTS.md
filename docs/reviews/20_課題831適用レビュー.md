## allowedBranchTypesの根拠

実在するbranch名から、`{type}`パターン（`^[a-z][a-z0-9-]{0,31}$`）とIssue番号付きの命名に適合するtypeを採用した。

| type | 実在例 |
|---|---|
| `feature` | `feature/826-release-workflow` |
| `fix` | `fix/readme-uninstall-doctor-mismatch` |
| `bugfix` | `bugfix/840-project-choice-diff-classification` |
| `refactor` | `refactor/822-minimal-local-issue-flow` |
| `test` | `test/828-lifecycle-isolation-tests` |
| `docs` | `docs/310-...` |
| `chore` | `chore/root-cleanup-...` |
| `process` | `process/786-gate-round-budget-remediation-policy` |

`release/*`（`release/bump-v0.2.138`等）はIssue番号を持たず`{type}/{issueNumber}-{slug}`へ適合しないため、allowlistへ含めていない。releaseは別authorityの操作であり、実装worktreeの命名規則の対象外である。

### 敵対観点の残論点

`allowedBranchTypes`へ`bugfix`と`process`を含めたことで、package既定（`feature` / `fix` / `refactor` / `test` / `docs` / `chore`）より許可typeが広い。これは実在branchとの整合のためであり、type自体はauthorityを付与しない。allowlistの拡大は`classifyProjectChoiceDiff`の対象外（`policy.worktree`はprojectChoicesではない）だが、schemaのpattern制約とIssue番号必須の命名規則は維持される。
