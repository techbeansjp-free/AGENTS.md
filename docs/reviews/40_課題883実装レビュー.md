## 真因

規範`.agent-skill-chain/docs/01_開発ワークフロー.md`の状態遷移は「merge → 完了処理 → 後片付け」を一連に見せている。しかし同じ行が`pr merge`へ「GitHub標準の自動マージ・マージキューを優先する」と指示している。

**自動マージとマージキューはmerge完了時点にlocal processが存在しない。** web UIでのmerge、他者によるmerge、`gh pr merge`も同様である。したがって後片付けを連鎖させることは設計上できず、事後のlocal走査でしか起動できない。

その走査経路が無かった。**製品が推奨する経路を使うほど残骸が増える構造である。**

## 保持側へ倒す判定

判定は次の順序で評価し、**保持側を既定とする。**

1. `isPrimary` → `primary`
2. `mergedIntoDefault`が偽 → `in-progress`（**merge判定が保持判定より先**。未mergeかつdirtyは`in-progress`）
3. `dirty` / 未追跡file / 未pushのcommit / `recoveryReachable`が偽のいずれか → `retain`（該当理由をすべて列挙）
4. どれにも該当しない → `cleanup-ready`

`retain`の各entryは必ず理由を持つ。**「なぜ消せないか」が分からない報告は役に立たない。**

実repositoryでの走査結果は cleanup-ready 19件、retain 5件、in-progress 1件であった。21件のmerge済みのうち2件は保持理由を持つと判定されている。

### 敵対観点の残論点

**`doctor`の`healthy`に含めていない。** 後片付け漏れは導入の健全性とは別軸であり、進行中の作業を`unhealthy`と誤報告する害のほうが大きいと判断した。ただしこの選択により、CIで`doctor`を実行しても後片付け漏れではCIが赤にならない。検出は報告に留まる。強制へ引き上げるかは運用実績を見てから判断する。

**`unpushedCommits`はupstream未設定時に0とする。** upstreamが無いbranchは「未pushのcommitが0件」と扱われ、他の保持理由に該当しなければ`cleanup-ready`になりうる。理由へ「upstreamが設定されていません」を加えているが、判定自体は保持側へ倒していない。upstream未設定を保持理由へ格上げするかは、誤検出の実績を見てから判断する。

**走査は実行時点の観測である。** 走査後にworktreeの状態が変わっても検出されない。削除は`worktree finalize`のevidence経路が直前に再検証するため、TOCTOUによる誤削除は防がれる。
