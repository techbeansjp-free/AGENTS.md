## 2. 受け入れ条件の確認

### 2.0 実装中に発見した事実と前向きな対処

**(1) 既存fixtureが空のclosing索引を返していた。** `SCN-INT-GITHUB-005`のstubは`closingIssuesReferences`が空配列であり、**settleを入れると読み戻し回数が増えてgh呼び出し列の完全一致assertionが壊れる。** ASC経由で作るPRは作成前に本文の終端keywordがcanonical Issue 1件だけであることを検証されるため、**空を返すfixtureは実PRの契約と食い違っていた。** canonical Issue 1件を返すよう是正した。

**(2) 当初の設計案に穴があった。** 私は「照合はloopの後に1回だけ置く」と書いていた。**独立reviewer（codex）が、1回目のidentity不一致が2回目の正常な観測で洗い流される経路を指摘した。** 待機中は認可済みの別writerがtitleやbodyを変更しうる。**自分では見つけていなかった。** INV-03として要件化し、各観測で照合する形にした。

**(3) 待機の実在を測るassertionが、待機ではなくsubprocess起動コストを測っていた。** 経過時間の下限を1回測る形にしたところ、**「待機を全く行わない」変異と「待機を1/10へ縮める」変異の双方が生存した。** 読み戻しは`gh`のsubprocessを起動するため、待機なしでも経過は数十から数百msになる。同じ観測列を待機0と待機1000msで流して差を測る形へ組み直した。

**(4) その差分測定も1度は不安定だった。** 差分300msでは他scenarioの負荷に埋もれて変異が生き延び、逆に1回目のcold startが大きいと正しい実装でも差分が縮んだ。**warm-upを1回捨ててから比べ、余裕を6割へ広げた。** baselineの合格と変異のkillをそれぞれ3回連続で実測した。
