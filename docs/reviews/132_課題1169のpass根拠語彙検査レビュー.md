## 2. 受け入れ条件の確認

### 2.0 実装中に発見した事実と前向きな対処

**実装中の発見が5件ある。**

**DISC-001。併記の判定が緩すぎた。** 行全体でbacktickを数えていたため、個別監査表のpath列（`` `src/a.ts` ``）だけで受理された。**登録語彙を含むcellと同じcell内へ限定した。** 変異M3でkillされる。

**DISC-002。変異M2（判定列の特定を外す）が等価だった。** `verdictIndex`が-1のとき`cells[-1]`は`undefined`になり直後のpass判定で必ず弾かれる。**私は等価性を確認する前に反射的にfixtureを足していた。** 追加したscenarioは契約testとして残し、等価である事実をコードコメントへ記録した。

**DISC-003。「原理的に塞げない」という当初の結論は広すぎた。** 正確には「意味的真偽の完全自動判定はできないが、**未検証の主張が黙って`pass`根拠になる経路は塞げる**」である。諮問で訂正された。

**DISC-004。`stash pop`での追随は commit の親を付け替えない。** `origin/main`がancestorでない状態を作り、`review round`と`audit:check`が落ちた。`rebase --onto`で是正した。

**DISC-005。追随時に`package.json`のversion巻き戻し（`beta.72 → 71`）が差分へ混入した。** `git checkout origin/main --`で除去した。**`git diff --name-only origin/main..HEAD`を先に見れば即座に分かるものだった。**

**DISC-006。rebase後のreview証跡は再固定も追加roundもできない。** `origin/main`が`7a0fff67`へ動いたため`pr create`より先に`rebase --onto`を行ったところ、証跡を新headへ移す2経路がいずれも塞がった。`review reanchor`は完全diffのsha256一致を要求するため（`src/domain/evidence-reanchor.ts:70-78`）、`audit:check`の要求でrebase後に必ず変わる`比較基点`・`H_impl`行を持つartifactには使えない。収束後の取り直しroundも`observeReviewDiff`が前roundのcandidate HEADをbaseに取るため、`review diff baseがcandidate HEADのancestorではありません`で拒否される（`src/adapters/review-diff.ts:35`）。**是正はrebaseの取り消しである。** `pr create`が要求するのは`git fetch`後にprovider既定branch tipとlocalのtrusted policy provenanceが一致することであって、branchのbaseが最新であることではない。**rebaseは不要だった。** `pr create`を先に済ませ、そのあとでrebaseした。
