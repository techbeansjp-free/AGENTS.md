## 3. 肯定的評価

- **親Issueの要求のうち、実装するとfail-openになる部分を実装しなかった。** 例外宣言は候補側project policyに置かれ、schemaの`approvalSource`・`approver`・`scope`は自由文字列である。非空検査だけで受理すると**候補が同一PRで独立review要求を自己解除できる。** 諮問でも同じ結論が出た。
- **規範の違反箇所を絞り込んだ。** 「永久に塞がる門を作らない」に対して破れているのは拒否そのものではなく回復経路の不記載である。`authorizeMerge`の拒否17経路のうち`Diagnostic`を持つのは1経路だけだった。
- **判定を1文字も変えていない。** `SCN-INT-MERGE-016`が独立approvalあり・なしの双方で`allowed`と`operations`を照合する。
- **沈黙した上書きを可視化した。** `requiredReviews: 0`を宣言しても下限1が適用される事実は、これまで応答のどこにも現れなかった。
- **assertionが診断文言を名指しする。** `diagnostic !== undefined`だけでは`requiredAuthority`を空にする変異が生存する。9変異すべてを個別のassertionが殺す。
- **到達不能な経路へ検証できない実装を足さなかった。** 到達不能性を実測で確かめ、診断は到達する側へ与えた。

## 4. 敵対的評価

- **本変更は#1036を解決しない。** 独立reviewerが不在のrepositoryでは、依然として`pr merge`が通らない。**変わったのは「なぜ通らないか」と「誰なら通せるか」が応答に出ることだけである。** `requiredAuthority`が名指しする「対象PRへ独立approvalを与えられるreviewer」が存在しないrepositoryでは、診断は回復経路を示していない。**この場合に残る正規経路はowner決裁（#1036）だけであり、本変更はそれを作っていない。**
- **診断の文言は自由文字列であり、機械が検証していない。** `next`と`requiredAuthority`が実際に有効な操作と権限主体を指しているかは、test fixtureが期待文字列と照合しているだけである。**文言が現実と乖離しても検査は通る。**
- **`checks`欄の2文は実装の説明であり、実行された検査の記録ではない。** 「最新状態へ畳み込んだ」「PR author等を除外した」は`authorizeMerge`の既存logicの説明で、診断生成時に再確認しているわけではない。**判定logicが将来変わると、この説明だけが取り残される。**
- **本変更は信頼境界を強くしない。** 追加したのは報告だけである。`src/domain/delivery.ts`は保護対象ではなく、同一PRで診断ごと削除できる。担保するのは偶発的劣化の回帰検出である。
- **到達不能分岐を残した。** `assisted`固有のメッセージは出力されない。判定へ影響しないが、読み手には`assisted`に固有の扱いがあるように見える。**除去を対象外にしたのは受け入れ条件の膨張を避けるためであり、正しさの判断ではない。**
- **残る14の拒否経路は依然として回復経路を示さない。** 本Issueが直したのは独立review不足の1経路だけである。同型の欠陥は残っている。
