## 経緯

Issue #928の配布物影響調査で検出した。**製品が配る要件ID体系を、製品自身が使っていない。**

| 側 | 体系 |
|---|---|
| 配布template | `FR-001` / `NFR-001` / `AC-001` |
| 本repository | `REQ-WF-001` / `AC-WF-001`（38件） |

Issue #881で、Issue番号に紐づく要件fileを廃し、変更頻度と所有責務が安定した境界づけられたコンテキストを表すID体系へ移行した。**その判断を配布templateへ反映していなかった。**

## どちらへ寄せるか

#881の判断理由は利用projectにも同じく当てはまる。`FR-001`という連番は、**どの境界づけられたコンテキストに属するかを表さない。** したがって配布template側を`REQ-{domain}-{3桁}`へ寄せた。

domain名は本repositoryの`WF`・`LC`・`GH`・`SQ`とは異なるため、templateではplaceholderとした。

## 対処

配布template 5 fileの識別子を変更した。

| file | 変更 |
|---|---|
| `02_要件/00_要件一覧.md` | `FR-001`・`NFR-001` → `REQ-{domain}-001`・`REQ-{domain}-002`。domainの決め方の節を追加 |
| `02_要件/01_受け入れ条件.md` | `AC-001`・`FR-001` → `AC-{domain}-001`・`REQ-{domain}-001` |
| `11_非機能/00_非機能要件一覧.md` | `NFR-001`〜`NFR-010` → `REQ-{domain}-001`〜`010`。機能要件と連番空間を共有する旨を追記 |
| `15_要件追跡/00_追跡表.md` | `FR-001`・`AC-001` → `REQ-{domain}-001`・`AC-{domain}-001` |
| `04_機能/01_個別機能テンプレート.md` | 関連要件の記法を`REQ-{domain}-...`へ |

domainの決め方は`00_要件一覧.md`へ書いた。**Issue番号をIDに使わないこと、変更頻度と所有責務が安定する単位で切ること、廃止した連番を再利用しないこと**を明記している。

## 検査の設計

**体系の定義を二重に持たない。** 正規表現の構成要素を`scripts/check_requirement_id_scheme.ts`の1箇所へ置き、そこから妥当な形と検出対象の両方を組み立てる。

配布template 5 fileを走査し、要件IDらしきtokenと受け入れ条件IDらしきtokenを抽出して、規定体系に合わない語を拒否する。

- `FR-`・`NFR-`で始まる旧体系を拒否する
- domainのない`AC-001`を拒否する
- 連番のない`REQ-WF`は**context略号そのものを指す散文参照として許可する**
- 連番位置のplaceholder（`{3桁連番}`、`...`）を許可する
- domainの決め方の記述欠落を拒否する

## 実測

templateを旧体系へ戻すと拒否される。

```
.agent-skill-chain/templates/specs/02_要件/00_要件一覧.mdの要件IDが規定体系ではありません: FR-001。
REQ-{domain}-000の形式にしてください
```

**製品自身の`docs/specs/02_要件/00_要件一覧.md`が同じ検査に合格することも固定した**（SCN-UNIT-REQID-007）。片側だけの体系変更が通らない。
