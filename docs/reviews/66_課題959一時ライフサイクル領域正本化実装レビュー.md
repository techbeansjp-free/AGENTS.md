### CodeRabbitの指摘

**`isExecutionEntry`の正規化不足は実害のある指摘だった。** symlink経由で起動すると`import.meta.url`は実体path、`process.argv[1]`はsymlink pathになり、完全一致比較が偽となる。判定を誤ると**検査が黙って走らず、`package:check`が何も検証しないまま成功する。** 本Issueが持ち込んだtop-level guardが、そのまま無言のno-op gateになり得た。双方をrealpathへ正規化し、SCN-UNIT-LIFEIGNORE-012で固定した。変異試験で正規化を外すと同scenarioが落ちる。

### 既定branch追随

**本Issueの実装完了後に既定branchが3回動いたため、#962で定めた手順で3回追随した。** これは同手順の最初の実運用である。

2回目の追随（#957のmerge後）では`scripts/check_conformance.ts`が衝突した。**衝突解消が関数を途中で切断していた。** `checkModeQuestionText`の`return errors;`と閉じ括弧が失われ、その直後から本Issueの関数定義が続く形になっていた。型検査が構文errorとして捕捉したため気付いたが、**切断が構文的に妥当な位置であれば、戻り値が失われたまま通過していた。** #962の損失検知は安定IDを見るため、この領域のようにIDを含まないcodeの切断は捉えられない。

あわせて、`modeQuestionGit`と`isolatedGit`が近似した2つのgit helperとして並ぶ状態になったため、前者を後者へ委譲させて統合した。片方だけが強化されて宣言が分岐することを避けるためである。

3回目の追随は自動releaseによるversion bumpだけだった。**`gh pr update-branch`で済ませようとしたが`audit:check`が落ちた。** `isReleaseBumpSide`が親1個のcommitしか受け付けず、自動releaseがPR merge commitとして着地する形を認識しないためである。除外機構が実際の着地形を想定していない。Issue #975 として分離し、本Issueでは#962の手順で追随した。

手順そのものは次のとおり。

1. review artifact commitを一旦外す
2. `git merge origin/main`で取り込む。`docs/specs/`の3 fileが衝突したため、**どちらの側も捨てずに両方を保持して解消した**
3. `比較基点`を取り込んだ既定branch tip `016f830d`、`H_impl`を追随merge commit `2a8a0ccd`とする
4. 個別監査表を`比較基点..H_impl`から再生成する
5. review artifactを最終commitへ置き直す

`audit:check`は#962で追加した損失検知を実行し、追随mergeが両親の損失検知tokenを失っていないことを確認している。`npm test` 884 scenario全通過。

### 実装担当が自ら検出した空振り

**ラウンド1の指摘に応じて追加した2件が、変異試験で空振りだった。** いずれも置き換えた。

- 「版管理commandが必ず失敗する」testは`rev-parse`で早期returnするため`ls-files`分岐へ到達していなかった。
- 「`core.worktree`注入」testは、実測で`check-ignore`の判定を変えないため空振りだった。実測で効果のある`GIT_CONFIG_PARAMETERS`経由の`core.excludesFile`注入へ置換した。

**変異試験を行わなければ、緑のまま何も検証しないtestが2件残っていた。**

### 実装中に判明した上流の誤り

**Issue起票時点で3箇所と認識していた宣言が、実際には4箇所だった。** `scripts/check_conformance.ts`の`FORBIDDEN_PACKAGE_ENTRIES`が`role-log`と`metrics`を独立に列挙していた。00と01へ反映し、当該一覧を分類正本の展開へ置き換えた。
