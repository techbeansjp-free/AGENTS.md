## 4. 敵対的評価

### 4.1 受理集合が意図より広がっていないか

拒否側に留まることを実測した入力: `a/../b`、`a/./b`、`/absolute`、`C:/outside`、`C:\outside`、`""`、`../x`、`./x`、`a//b`、`a/`。
新たに受理される入力: `a\..\b`、`a\.\b`、`\absolute`、`\\server\share`、` a `、`é.txt`。
**後者はいずれもPOSIXで実在しうるfile名である。** `\absolute`はrepository相対の1 fileであり、`/absolute`とは別物である。

### 4.2 述語側で新たな問題が起きないか

観測層が渡す文字列は入力そのものになった。述語のうち`isIssueStagingPath`と`isStagingLifecycleScanPath`は`staging.ts`の`slash()`を通すが、POSIXでは恒等変換である。**述語側の判定を変えていない。**

### 4.3 拒否条件そのものが空洞化していないか

B1〜B4（空segment・現在参照・親参照・drive修飾の各検査の削除）がすべてkillする。**歯止め4件それぞれに反例がある。**

### 4.4 拒否条件を位置や文字種で狭める変異が生存しないか

**ラウンド1では生存した。** drive修飾を大文字だけに、親参照をindex 1以上だけに、空segmentを先頭だけに狭める3変異がいずれも9 scenario緑のまま通った。**分類ごとに1件の反例では、条件を狭める変異を1つも捕まえない。** 先頭・中間・末尾と大小文字を並べた15入力へ広げ、3件すべてがkillすることを実測した。

### 4.5 `path.sep`という選択を検査が強制しているか

**していない。** §2.0(4)のとおりA2・A3がPOSIXで等価変異になる。強制しているのはA1（backslash固定へ戻す）だけであり、これは「実行OSの区切り以外を解釈しない」という条項の反対側を塞ぐ。**「POSIXで`/`以外を区切りとして解釈しない」ことは強制できるが、「Windowsで`\`を解釈する」ことはこの環境では強制できない。**

### 4.6 支援層が製品を超えている

製品14行に対し支援層317行、比は**22.6倍**である。**ラウンド2で117行増えた。** 運用ポリシーの命題に照らして縮小可否を評価した。
- SCN-006（受理・述語ごとの判定差）とSCN-007（拒否）は片方だけでは受理集合の両端を固定できない。統合すると、片側を落とす変異が生存する。
- SCN-008（理由codeの列挙）はAC-04の唯一の担保であり、型を通じてunionの増加を`npm run typecheck`へ落とす。
