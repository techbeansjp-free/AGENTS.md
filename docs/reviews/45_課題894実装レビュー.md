## 真因

`worktree finalize`は`ignoredArtifacts`の**個数が0でなければ拒否**していた。内容を一切見ていない。

**gateを回すにはworktree内で`npm run build`が必須である。** `dist/`はgitignore対象なので、build後は必ず`ignoredArtifacts`が非空になる。

つまり**規範どおりの手順を踏んだworktreeは、構造的に一度もfinalizeできなかった。**

21件のworktreeが蓄積した原因は、#883で扱った「検出経路が無い」だけではなかった。**削除経路が最初から塞がっていた。**

## `.gitignore`では判別できない

`.gitignore`は「追跡しない」を表すだけで「再生成可能か」を表さない。本repositoryでは両方が混在している。

| entry | 種別 |
|---|---|
| `node_modules/`、`dist/`、`.worktrees/` | 再生成可能 |
| `.agent-skill-chain/tmp/`、`/issues/`、`/memo/`、`.claude/` | **利用者所有** |

**一律に無視すると利用者のデータを消す。** package既定allowlistは`node_modules/`と`dist/`のみとし、利用者所有物を1件も含めていない。

## 二段階分割が必要であった

当初の単一PRはCIで拒否された。

```text
Error: project policy manifestが不正です: manifest.policy…未知fieldです
  at requireManifest → loadProjectPolicySet → checkSourceQuality
```

base validatorは**baseのvalidatorでcandidate全体を検証する。** したがってmanifestの新fieldはbaseへ先に入っていなければならない。

schema・runtime検証・判定moduleをPR #901で先行させ、本PRは接続と宣言だけを行う。同型の分割は#832と#846でも必要であった。

## candidateによる拡大を拒否した

契約では「利用projectが追加できる」とだけ指示したが、implementerは**candidate policyによるallowlist拡大をauthority緩和として拒否**する実装を選んだ。

`enforcement.ts`の既存の「candidate自己緩和の禁止」と整合する。**削除範囲の拡大をPRで自己承認できない。** 不可逆操作の境界として正しい判断である。

## surveyとfinalizeの判定を共有した

`assessWorktreeRemovalSafety`を両者が呼ぶ。**判定定義を二重化していない。**

これは#879（`paths`と`files`）、#892（差分と連番）、#893（実作成時刻とdirectory名）と同型の「同じ事実を2箇所で別々に判定する」状態であり、そのまま残してはならなかった。

## CodeRabbitの指摘による是正

外部reviewから2件の実欠陥が指摘され、是正した。

### 1. schemaとruntimeの入力契約が一致していなかった

coordinatorが実証した。

```text
値              schema   runtime
"./"            true     false    ← 食い違い
"cache/./"      true     false    ← 食い違い
"dist/"         true     true
"../"           false    false
```

**schemaを通過した値がruntimeで弾かれる。** 同じ制約を2箇所に書いて突合していない、本repositoryで繰り返し発生している欠陥類型である。

schemaへ`(?!.*(?:^|/)\.(?:/|$))`を追加し、**schema fileからpatternを読み取ってruntime述語と全件突合するtest**を加えた。入力25件（受理6・拒否19）で全件一致、mismatch 0件。

testへ正規表現をhard codeしていない。hard codeするとschemaが変わってもtestが追随せず、検証の意味が失われる。

### 2. 不正な観測値が「安全」側へ倒れていた

指摘は`planWorktreeCleanup`の`temporaryArtifacts`だったが、**同型の穴を洗い出したところ9箇所あった。**

| 箇所 | 元の挙動 | 是正 |
|---|---|---|
| `registered ? []` | 不明を空扱い | 拒否 |
| `temporaryArtifacts ? []` | 指摘箇所 | 拒否 |
| `ignoredArtifacts ?? []` | 不明を空扱い | 未加工で共通判定へ |
| `untracked ?? consumerAssets` | `null`まで代替へ逃げる | `undefined`のみ |
| `trackedChanges ?? clean` | **不正値から安全を推定** | `undefined`のみ |
| `ignoredPathAllowlist ?? default` | 不正値を既定値へ変換 | 未指定時のみ既定値 |
| `stashes ?? []` | 不明を空扱い | 削除 |
| `remoteBranch ?? pushed` | **push済みからremote有りを推定** | 削除 |
| `targetAbsent`・`clean`・`consumerAssets` | 不正な型を無視 | 明示検証 |

**`trackedChanges ?? clean`と`remoteBranch ?? pushed`は、不正な観測値から「安全」を推論していた。** 削除は不可逆であり、重い欠陥である。

`assessWorktreeRemovalSafety`側は既にfail-closedであり、変更不要と判定した。

反例として`SCN-UNIT-FINALIGN-018〜029`を追加した。

### 敵対観点の残論点

**allowlistはdirectory prefixで判定する。** `dist/`を許可すると`dist/`配下のすべてが削除対象になる。利用者が`dist/`配下へ手作業の成果物を置いた場合、それも消える。`dist/`が生成物であることは`.gitignore`と`package.json`の`files`から自明だが、**機械的な保証はない。**

**利用projectのallowlistは人間が宣言する。** package既定を超える範囲を許可するかは利用project側の判断であり、誤った宣言を製品は防げない。candidateによる拡大は拒否するが、default branch上のpolicyを直接編集する経路は残る。

**現存する20件の後片付けは本PRでは行っていない。** 判定の是正までとし、実削除はcoordinatorがmerge後に製品の経路で実施する。
