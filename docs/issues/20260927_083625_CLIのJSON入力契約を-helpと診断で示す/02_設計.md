## 1. 設計方針

### 1.0 開発考慮事項の適用判定（必須）

| ID | 考慮事項 | 判定 | 理由 | 設計・検証証拠 |
|---|---|---|---|---|
| DC-PRIVACY | Privacy/Security by Design | not-applicable | 変更は`--help`の静的な項目一覧と入力検証の診断文言に限られ、秘密情報・認証・信頼境界を扱わない | 診断はfield名・添字・finding ID・受理値だけを組み立て、入力値を連結しない設計にする（§3） |
| DC-OBSERVABILITY | Secure Logging・Observability・運用可能性 | not-applicable | log・metrics・保持・監視の仕組みを変えず、既存の診断出力の文言だけを変える | 既存のerror→JSON診断の経路をそのまま使う（§9） |
| DC-UX | Human-Centered UI/UX・アクセシビリティ | not-applicable | 変更対象はNode CLIのJSON出力であり、GUIやWeb UIを提供しない | package.jsonのbinとCLI contract |
| DC-TOKENS | Design System・Design/Layout Token | not-applicable | 画面レイアウトと視覚コンポーネントを所有しない | projectKind=cli、UI sourceなし |

### 1.1 設計目標

入力契約の項目定義を検証側（domain）に1つだけ置き、`--help`（`src/cli-usage.ts`）はそれをimportして`inputContract.fields`へ載せる。検証の診断は、未知・欠落を一括で、enum違反は受理値付きで返す。

### 1.2 設計対象外

受理する入力の変更、他commandの入力契約。

### 1.3 適用する原則

| 原則 | 適用 | 根拠 |
|---|---|---|
| UNIX・単一責務 | 項目定義はdomainが所有し、usageは表示だけを担う | §2.2 |
| DDD | CLI入力契約コンテキストだけを変える | §2.1 |
| BDD / Evidence-driven Verification | AC-01〜03をSCN-UNIT-CLIINPUT-001〜003で検証する | §10 |
| Zero Trust | 検証の厳格さは変えない | §5 |

## 2. システムコンテキストと責務

### 2.1 境界づけられたコンテキスト

CLI入力契約。review判定・Verification Set選定・発見判定の意味は変えない。

### 2.2 コンポーネント

- `src/domain/agile-verification.ts`: Verification Set入力と実装中発見入力の項目定義（export）と検証。`exactInputObject`は未知と欠落を1件のerrorへまとめ、enum違反へ受理値を添える
- `src/domain/review-convergence.ts`: review round入力の項目定義（export）と検証。`exactObject`・`parseAnchor`を同様にし、`oneOf`の違反へ受理値を添え、findingのlabelへIDを添える
- `src/cli-usage.ts`: `UsageInputContract`へ任意の`fields`を追加し、3コマンドへ設定する

### 2.3 依存方向と循環防止

`src/cli-usage.ts` → `src/domain/*`の一方向。domainはcli-usageを参照しない。`architecture:check`で確認する。

### 2.4 図表の判断

不要。3 fileの一方向依存であり図で答える問いが無い。

## 3. 操作と入出力

- `--help`: `inputContract.fields = [{path, required, type, values?}]`
- 診断: `<label>の未知fieldを拒否しました: a, b。必須fieldがありません: c, d`、`<label>.<field>が不正です（受理値: x|y|z）`、`review round.findings[5]（id=REV-06）...`

## 4. ドメインモデルとデータ

### 4.1 モデル

`InputFieldSpec {path, required, type, values?}`。

### 4.2 識別子・UUID（必要な場合だけ）

不要。

### 4.3 データ整合性

項目定義を検証が直接使うため、helpと検証は構造上一致する（INV-02）。

## 5. 信頼境界、安全性、権限

診断へ入力値を連結しない。受理・拒否の条件は変えない（INV-01）。

## 6. 失敗、復旧、ロールバック

変更は提示と文言だけであり、revertで戻せる。

## 7. 外部インターフェース（該当時）

| API・CLI・ファイル・イベント | 契約 | 入力検証 | 認証・承認 | タイムアウト・再試行 |
|---|---|---|---|---|
| 3コマンドの`--help` | `inputContract.fields`を追加 | 従来どおり | なし | なし |

## 8. UIと表示契約（該当時）

該当しない（CLIのJSON出力）。

## 9. 観測可能性

既存のerror→JSON診断の経路を使う。新しいlogは無い。

## 10. テスト戦略と接合部

unit: usageの`fields`と検証定義の一致、診断文言（未知と欠落の同時列挙、受理値、finding ID、入力値の非複写）。既存の入力拒否scenarioで回帰を確認する。

- 未決事項: なし
