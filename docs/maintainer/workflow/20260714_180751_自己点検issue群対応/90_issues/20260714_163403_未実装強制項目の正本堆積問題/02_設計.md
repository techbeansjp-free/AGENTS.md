## 2. 本 issue 固有の設計差分

### 2.1 統制語彙の分類根拠（本 issue の責務）

| 分類 | 対象 | 根拠 |
| ---- | ---- | ---- |
| `未実装（人手監査）` | #22/#23/#24/#30 | 許可確認の有無・指示文案だけ返したか・高リスク確認の有無・進捗実証の質は、成果物・git 差分・ツールメタデータに痕跡を残さず**機械検出が本質的に不能**（README §「自立進行ルール違反の検出」・AGENT_CONDUCT §機構的強制の非対象）。 |
| `未実装（抽象仕様のみ・将来hook）` | 系統A/C/E | 抽象仕様（対象・fail-open 方針・false positive 回避方針）のみ確定済みで、hook スクリプト実体は将来の別 issue（README §系統A/C・§系統E に明記済み）。 |

`未実装（人手監査）` と `未実装（抽象仕様のみ・将来hook）` を分けるのは、前者が「機械実装が原理的に困難で人手監査に委ねる恒久的分類」、後者が「実装予定はあるが未着手（将来 hook 化の土台として抽象仕様のみ正本化）」という**将来見通しの違い**を保存するため。単純な二値 `実装済み/未実装` でも区別可能化の最低要件は満たすが、この 2 分類で誤認リスク（「いつか実装される」vs「人手に委ねる」）をより正確に伝える。
