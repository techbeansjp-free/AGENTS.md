# 設計書: review-docs の表外必須ゲートという自己矛盾

> **用語**: [.agent-skill-chain/source/CONCEPTS.md §用語規約](../../../../../../.agent-skill-chain/source/CONCEPTS.md#用語規約) を参照。

## 1. 設計概要

### 1.1 設計方針

コード実装を伴わない**規約ドキュメントの再構造化**である。「重複禁止・正本 1 か所」の既存原則（[01_設計原則.md](../../../../../../.agent-skill-chain/source/spec/01_設計原則.md)）に従い、review-docs の位置づけ（横断的必須ゲート）の定義を PHASE_COMMAND_MAP.md 側に一本化し、PHASES.md からは参照のみに簡素化する。

### 1.2 設計原則（本プロジェクトで適用するもの）

- **単一責務 / 明確な境界**: 「表＝フェーズ遷移コマンドの起動経路の正本」と「横断的必須ゲートの分類・review-docs の位置づけの正本」を PHASE_COMMAND_MAP.md 内の別々の節に分離する。PHASES.md は自身の責務（フェーズ順・成果物・DoD）を保ちつつ、位置づけの説明は重複させず参照する。
- 他の設計原則（CQRS・イベント駆動・UNIX 哲学の残り観点等）はドキュメント整合性の修正には非該当。

## 2. アーキテクチャ設計

### 2.1 責務・境界・参照関係

#### 2.1.1 責務一覧

| コンポーネント | 責務（1 文） |
| --- | --- |
| `PHASE_COMMAND_MAP.md` | phase → command の起動経路の唯一の正本、および「横断的必須ゲート」という分類・review-docs の位置づけの正本 |
| `PHASES.md` | フェーズ順・成果物・DoD の正本。review-docs の位置づけ自体は再定義せず PHASE_COMMAND_MAP.md を参照する |

#### 2.1.2 境界

- **入力**: 既存の PHASE_COMMAND_MAP.md・PHASES.md の現行記述（but 書きが分散した状態）。
- **出力**: 「表の範囲」と「横断的必須ゲート」を分離して明示した PHASE_COMMAND_MAP.md、および重複説明を削除し参照のみにした PHASES.md。
- **他責務との境界**: review-docs command 自体の処理内容（commands/review-docs.md）・enforcement #32 の判定ロジックは本 issue の変更対象外（参照先の記述のみ整理し、義務・検知ロジックの正本は変更しない）。

#### 2.1.3 参照関係

- `PHASES.md` §レビュー成果物の配置ルール → `PHASE_COMMAND_MAP.md` §横断的必須ゲート（新設節）。
- 循環参照は持たない。既存の enforcement/README.md・skills/agent/run_command.md への参照はそのまま維持する。

### 2.2 横断設計判断（ADR）

#### ADR-1: review-docs の位置づけの正本をどちらに置くか

- **コンテキスト**: review-docs の「表に載らない理由」「必須ゲートである根拠」の説明が PHASE_COMMAND_MAP.md（表側）と PHASES.md（フェーズ順側）の両方に、内容の異なる文面で重複していた。1 箇所に修正が入ってももう一方に反映されず、but 書きが増殖する構造になっていた。
- **検討した選択肢**:
  1. PHASES.md 側を正本にし、PHASE_COMMAND_MAP.md は参照のみにする。
  2. PHASE_COMMAND_MAP.md 側を正本にし、PHASES.md は参照のみにする。
  3. 両ファイルに要約を残しつつ内容を完全一致させる運用ルールを追加する（重複を許容）。
- **決定**: 選択肢 2（PHASE_COMMAND_MAP.md を正本にする）。
- **根拠**: 「表に載らない」という事実自体が PHASE_COMMAND_MAP.md（表の定義ファイル）の話であり、「なぜ表に載らないのに必須なのか」という説明も表の適用範囲の定義の一部である。PHASES.md はフェーズの順序・DoD が責務であり、review-docs の分類定義を持つ必然性がない。00_要求定義.md §7.1 の対策方針（「表＝フェーズ遷移の経路」「横断ゲート＝別カテゴリ」の概念分離）とも整合する。evidence_source: `existing_code`（両ファイルの既存責務定義を実際に読んだ上での判断）。
- **帰結**: PHASE_COMMAND_MAP.md に「横断的必須ゲート」という見出し付きの節を新設し、review-docs の分類・必須性・「唯一の経路」禁止規定との関係をそこに集約する。PHASES.md §レビュー成果物の配置ルール の該当箇所は、その節への参照 1 行程度に短縮する。選択肢 3（重複許容）は今回の課題そのもの（but 書きの増殖）を継続させるため採用しない。

#### ADR-2: 「本表が唯一の経路」という文言をどう扱うか

- **コンテキスト**: PHASE_COMMAND_MAP.md の禁止事項「本表が phase → command の唯一の経路である。本表にない command の起動は禁止。」は無限定の宣言であり、これと矛盾しないために別途「補助手順は対象外」という注記が必要になっていた。
- **検討した選択肢**:
  1. 禁止事項の文言自体は変えず、注記のみで対応する（現状維持）。
  2. 禁止事項の文言に適用範囲（フェーズ遷移コマンドの起動経路としての唯一性）を組み込み、そもそも矛盾が生じない表現にする。
- **決定**: 選択肢 2。
- **根拠**: 文言自体のスコープを明示すれば、以後「これは matches するか」を都度注記で説明する必要がなくなる。00 の対応方針で採用した「スコープを明示した表現に修正」に対応する。evidence_source: `existing_code`。
- **帰結**: 「本表は phase → command（フェーズ遷移コマンドの起動経路）の唯一の経路である。フェーズ判定後に本表にない command を選ぶことは禁止。」に修正し、横断的必須ゲートの節への参照を括弧で添える。

### 2.3 コンポーネント構成・データフロー・API・UI・データ設計

該当なし（コード実装を伴わないドキュメント整合性修正のため、コンポーネント構成・データモデル・API・UI 設計は対象外）。

## 3. 機能設計

### 3.1 機能 1: PHASE_COMMAND_MAP.md の再構造化

#### 3.1.1 概要

既存の 2 つの長い inline 注記（補助手順の注記・必須ゲートとしての位置づけの注記）を、1 つの見出し付き節「## 横断的必須ゲート」に統合し、禁止事項の文言にスコープを明示する。

#### 3.1.2 処理フロー

該当なし（ドキュメント編集のみ、実行時処理フローは無し）。

#### 3.1.3 入力・出力

- **入力**: 現行の PHASE_COMMAND_MAP.md（Phase → Command 一覧、note 2 件、Rule 節の禁止事項）。
- **出力**: 横断的必須ゲート節を新設し、禁止事項の文言を修正した PHASE_COMMAND_MAP.md。

#### 3.1.4 エラーハンドリング

該当なし。

### 3.2 機能 2: PHASES.md の重複記述の簡素化

- **概要**: §レビュー成果物の配置ルール の review-docs 該当箇所を、PHASE_COMMAND_MAP.md §横断的必須ゲート への参照 1 行に短縮する。GitHub Issue 起票ゲートの記述（別項目）はそのまま維持し、変更しない。
- **入力・出力**: 現行の長文注記 → 参照リンク主体の短い記述。
