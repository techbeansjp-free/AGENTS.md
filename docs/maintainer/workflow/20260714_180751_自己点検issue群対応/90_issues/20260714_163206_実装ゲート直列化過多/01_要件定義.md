# 要件定義書: 実装着手前ゲートの直列化過多（quick モード免除）

**プロジェクト名**: 実装着手前ゲートの直列化過多
**作成日**: 2026 年 07 月 14 日
**最終更新**: 2026 年 07 月 14 日

> 用語・思想の正本は [.agent-skill-chain/source/CONCEPTS.md §用語規約](../../../../../../.agent-skill-chain/source/CONCEPTS.md#用語規約)、実行モードは [RULES.md §実行モード](../../../../../../.agent-skill-chain/source/RULES.md) を参照。

---

## 1. 概要

### 1.1 システム概要

実行モード（quick / standard / full）と実装着手前ゲート群（review-docs #32／GitHub Issue 起票 #34／branch 紐づけ #35）の適用条件を整合させる。ユーザー判断（00 §ユーザー判断）に基づき、**quick モードは #32・#34 を免除し、#35 は規模に関係なく維持する**。full/standard は現行どおり全ゲート適用。免除は「記録省略」ではなく「規模に応じた手続きの軽量化」とし、quick でも記録（変更理由・設計メモ・workflow.db 証跡）は残す。

### 1.2 用語集

| 用語 | 定義 |
|------|------|
| 実行モード | quick / standard / full の 3 区分（RULES.md §実行モード）。要求の規模に応じて選ぶ。 |
| mode 信号 | 実行モードを機械可読にするための 00_要求定義.md frontmatter `mode:` キー（値: quick/standard/full）。**本 issue で新設する単一正本**。 |
| #32 review-docs ゲート | design-feature 完了後・implement-feature 着手前の実装前ドキュメントレビュー必須ゲート。 |
| #34 GitHub Issue 起票ゲート | review-docs 完了後・implement-feature 着手前の GitHub Issue 記録ゲート（デフォルト起票＋理由付き declined）。 |
| #35 branch 紐づけゲート | implement-feature 着手前の feature ブランチ名記録ゲート。規模・モードに関係なく維持。 |
| 免除（軽量化） | 当該ゲートの手続き（review-docs 反復・GitHub Issue 起票）を省く一方、記録自体（変更理由・設計メモ・workflow.db）は残すこと。記録省略ではない。 |

---

## 2. 機能要件

### 2.1 ユーザーストーリー

- **US-1（進行役）**: 進行役として、軽微な 1 ファイル修正を quick モードで回すとき、review-docs 反復・GitHub Issue 起票を省いて手続きコストを下げたい。ただし変更理由と workflow.db 証跡は残したい。
- **US-2（進行役）**: 進行役として、full/standard の作業では従来どおり全ゲートを適用し、品質担保（レビュー・追跡可能性）を維持したい。
- **US-3（監査／CI）**: CI として、quick モードの issue で #32・#34 を FAIL させず、full/standard の issue では従来どおり FAIL させたい。かつ #35 はモードに関係なく検査したい。
- **US-4（規約読者）**: 規約読者として、RULES.md／run_command.md／PHASES.md／enforcement/README.md を読んだとき、「どのモードで何が免除されるか」が一意に読み取れ、記述間に矛盾がない状態にしたい。

### 2.2 BDD ユースケース

```gherkin
ユースケース: quick モードでの実装前ゲート免除
  シナリオ: quick モードの issue は review-docs ゲート(#32)で FAIL しない
    Given 00_要求定義.md frontmatter に mode: quick が記載された issue
    And その issue に implement-feature の workflow_log がある
    And review-docs の workflow_log は 0 件
    When audit.sh の #32 チェックを実行する
    Then その issue は SKIP され FAIL しない

  シナリオ: quick モードの issue は GitHub Issue 起票ゲート(#34)で FAIL しない
    Given 00_要求定義.md frontmatter に mode: quick が記載された issue
    And その issue に implement-feature の workflow_log がある
    And github_issue が null（未記録）
    When audit.sh の #34 チェックを実行する
    Then その issue は SKIP され FAIL しない

  シナリオ: quick モードでも branch 紐づけゲート(#35)は適用される
    Given 00_要求定義.md frontmatter に mode: quick が記載された issue
    And その issue に implement-feature の workflow_log がある
    And branch が null（未記録）
    When audit.sh の #35 チェックを実行する
    Then その issue は FAIL する（#35 は mode を参照しない）

  シナリオ: full/standard モードは全ゲートが従来どおり適用される
    Given 00_要求定義.md frontmatter に mode: standard（または full・mode 欠落）の issue
    And その issue に implement-feature の workflow_log がある
    And review-docs ログ 0 件かつ github_issue 未記録
    When audit.sh の #32・#34 チェックを実行する
    Then その issue は両方とも FAIL する

  シナリオ: mode 欠落時は standard とみなし免除しない（fail-safe）
    Given 00_要求定義.md frontmatter に mode キーが無い issue
    When audit.sh の #32・#34 チェックを実行する
    Then 免除は適用されず（standard 相当）従来どおり判定される
```

### 2.3 ビジネスルール

- **BR-1**: quick モードの単一正本は 00_要求定義.md frontmatter の `mode:` とする。二重管理を避け、機械監査・人間判断の双方が同じ 1 か所を参照する。
- **BR-2**: `mode:` が未記載・不明値の場合は **standard** とみなす（RULES.md §実行モードの既定と一致）。免除は quick 明示時のみ。
- **BR-3**: 免除は #32・#34 のみ。#35（branch）はモードに関係なく維持する（記録コストが低いため）。
- **BR-4**: quick モードでも変更理由・設計メモ（RULES quick 最小セット）と workflow.db 証跡は残す。免除は手続きの軽量化であり記録省略ではない。
- **BR-5**: 免除は遡及適用可（relaxation のため grandfather 不要）。既存の grandfather 発効日・既存 frontmatter を破壊しない。

## 3. 非機能要件

### 3.1 パフォーマンス要件

- 該当なし（audit.sh に issue あたり 00 frontmatter 1 read が加わる程度）。

### 3.2 セキュリティ要件

- 該当なし。

### 3.3 ユーザビリティ要件

- 規約 4 ファイル（RULES／run_command／PHASES／enforcement/README）で「モード別のゲート適用条件」が一意に読み取れること。「全 issue 一律・免除なし」という断定を、モード別の適用条件へ改める。

### 3.4 可用性要件

- fail-open を維持する。mode 判定不能・DB 不在・非 git は従来どおり SKIP／standard 相当にフォールバックし、ロックアウトしない。

---

## 4. 外部インターフェース要件

### 4.1 API 要件

- 該当なし（新規 API なし）。ゲート判定の入力に 00_要求定義.md frontmatter `mode:` が追加される。

### 4.2 データ形式要件

- `mode:` の値は `quick` / `standard` / `full` のいずれか（小文字）。クオート有無いずれも許容。欠落は standard 扱い。

---

## 5. 制約事項

- 既存 enforcement（#32/#34/#35）との後方互換を維持する。既存 issue（mode 欠落）は standard 扱いで挙動が変わらない。
- ゲート定義と実行モード定義の二重管理を避け、正本を 1 か所（RULES.md §実行モード＋00 frontmatter `mode:`）に保つ。
- コアに具体閾値を増やさない。既存の per-gate トグル・grandfather の設計方針を踏襲する。
