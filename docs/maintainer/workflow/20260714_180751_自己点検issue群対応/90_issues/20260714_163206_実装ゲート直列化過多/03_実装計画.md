## 1. 実装概要

### 1.1 実装方針（必須）

02 §2.1 の責務表に沿って、(A) mode 信号の正本を確立し、(B) 規約ドキュメント 5 ファイルを mode 別適用へ整合し、(C) enforcement レジストリと audit.sh に mode ガードを入れる。#35（branch）は触らない。正本 1 か所（RULES.md §実行モード＋run_command §Constraints）に定義を集約し、他ファイルは参照・整合記述に留める。

### 1.2 実装順序（必須: 1 件以上）

1. **T-A テンプレート＋mode 正本**: RULES.md §実行モードに mode 別ゲート適用と mode 信号定義を追記。00_要求定義.md テンプレートに `mode:` フィールドを追加。
2. **T-B 規約ドキュメント整合**: run_command.md #47/#48/#49、PHASES.md #65/#66、PHASE_COMMAND_MAP.md §横断的必須ゲート、design-feature.md #61/#73 を mode 別適用へ改訂。
3. **T-C enforcement レジストリ**: enforcement/README.md 失敗条件レジストリ #32/#34 に quick SKIP 条件、#35 に「mode 非参照」を明記。
4. **T-D audit.sh mode ガード**: `check_reviewdocs_before_implement`（#32）・`check_github_issue_before_implement`（#34）に mode:quick SKIP を追加。#35 は無変更。
5. **T-E テスト＋検証**: mktemp 隔離で BDD テストを作成・実行し（T-1〜T-6）、ドキュメント整合の残存断定を grep で確認。

> 実装は worktree（main から新規ブランチ）で行う。実装着手前に 00 frontmatter `branch`（記録済み: 本 issue の worktree ブランチ）を確認する（#35 は本 issue 自体にも適用される）。**本 issue 自体は standard モードで進める**（frontmatter `mode: standard`。ゲート免除の対象外）。

## 2. タスク分解

### 2.1 タスク 1（T-A）: mode 正本とテンプレート

- **対象**: `RULES.md` §実行モード（L7-19 付近）、`.agent-skill-chain/runtime/templates/00_要求定義.md` frontmatter。
- **内容**:
  - RULES.md quick 行の必須行為に、実装前ゲートの mode 別適用（quick は #32/#34 免除・#35 維持・免除は軽量化で記録は残す）を明記。表の下に「実行モードの機械可読な正本は 00_要求定義.md frontmatter `mode:`（欠落時 standard）」の 1 文を追加。
  - 00 テンプレート frontmatter に `mode: standard`（既定）＋コメント（値域・免除の意味・#35 は非対象）を追加。既存キー（document_id/issue_id/branch）の順序・意味は変えない。
- **テスト観点**: RULES.md に quick 免除・#35 維持・「記録は省略しない」の 3 点が読み取れること。テンプレートに `mode:` が存在すること。

### 2.2 タスク 2（T-B）: 規約ドキュメント整合

- **対象**: `run_command.md`（#47/#48/#49）、`PHASES.md`（#65/#66）、`PHASE_COMMAND_MAP.md`（§横断的必須ゲート）、`design-feature.md`（#61/#73）。
- **内容**: 02 §3.1 の各差分に従い、「全 issue 一律・（規模比例の）免除なし」の断定を「full/standard 必須・quick 免除」へ改める。正本は run_command §Constraints、他は参照・整合記述。#49（branch）は「モードに関係なく維持」の明文化のみ（挙動不変）。
- **テスト観点**: 5 ファイル間で review-docs／GitHub Issue ゲートの適用条件が一致（quick 免除・full/standard 必須）。branch は全ファイルで「モード非依存で維持」。旧断定文言が意図外の箇所に残らないこと。

### 2.3 タスク 3（T-C）: enforcement レジストリ

- **対象**: `enforcement/README.md`（失敗条件レジストリ表 #32/#34/#35 行、および §失敗とみなす条件一覧の #32/#34 説明）。
- **内容**: #32/#34 の SKIP 条件（強制レベル列・説明）に「当該 issue の 00 frontmatter `mode: quick` は SKIP（免除）。full/standard/mode 欠落は従来どおり」を追記。#35 行に「mode は参照しない＝quick でも発火（規模非依存で維持）」を明記。共通前提ノート（grandfather・トグル）との非交差性を保つ表現にする。
- **テスト観点**: #32/#34 行に quick SKIP、#35 行に mode 非参照が記載され、audit.sh 実装（T-D）と一致していること。

### 2.4 タスク 4（T-D）: audit.sh mode ガード

- **対象**: `enforcement/ci/audit.sh` の `check_reviewdocs_before_implement`（#32・L978-1015）、`check_github_issue_before_implement`（#34・L1085-1151）。`check_branch_linkage_before_implement`（#35）は**変更しない**。
- **内容**:
  - 共通ヘルパー（または各関数内インライン）で、指定した `00_要求定義.md` パスから frontmatter `mode:` を抽出する処理を用意する。抽出は既存 #34 の frontmatter awk（`NR==1 && $0=="---"{p=1;next} p && $0=="---"{exit} p`）＋ `grep -m1 -E '^mode:'` ＋ `sed` トリム＋クオート除去＋小文字化を流用。
  - **#32**: per-issue ループの grandfather 判定直後に、`${issue_dir}/00_要求定義.md`（存在すれば）から mode を読み、`quick` なら `continue`。00 不在・mode 無し・不明値は非 quick 扱い（従来判定）。
  - **#34**: per-issue ループ（走査対象が既に `00_要求定義.md`＝`$f`）の grandfather 判定直後に、`$f` から mode を読み `quick` なら `continue`。冒頭の `GITHUB_ISSUE_GATE_ENABLED` トグル SKIP は不変。
  - fail-open/fail-safe を維持（判定不能は従来判定へ）。DB/FS への書き込みは一切しない（Query/read のみ）。
- **テスト観点**: T-1〜T-6（01 §2.2・02 §6.1）。特に mode 欠落・不明値で従来 FAIL が維持されること（fail-safe）、#35 が mode:quick でも FAIL すること。

### 2.5 タスク 5（T-E）: テストと整合検証

- **対象**: audit.sh のテスト（既存テストハーネスがあれば追記、無ければ mktemp 隔離スクリプト）、ドキュメント整合の grep 検証。
- **内容**: mktemp -d に最小 workflow.db（sqlite3 で workflow_log を作成し implement-feature/review-docs 行を投入）＋ issue ツリー（00/03 と frontmatter）を再現し、#32/#34/#35 の各シナリオを実行。BDD インラインコメント（ユースケース・シナリオ・Given/When/Then）を必須で付す（TEST_BDD_FORMAT）。
- **テスト観点**: T-1〜T-6 が全て期待どおり。回帰（grandfather/トグル SKIP）維持。

## テスト観点

- 正常系: quick → #32/#34 SKIP。standard/full → #32/#34 FAIL（未実施時）。
- 異常系/境界値: mode 欠落・空・不明値・大文字（`QUICK`）→ 小文字化後 quick 判定 or standard 扱いの境界を明確に検証。クオート付き `"quick"` も許容。
- 回帰: 既存 grandfather（EFFECTIVE_FROM）・トグル（GITHUB_ISSUE_GATE_ENABLED/BRANCH_LINK_GATE_ENABLED）・close/templates/90_issues 除外が mode ガード追加後も従来どおり。
- 非対象: #35 は mode:quick でも FAIL（branch null 時）。

## 単体テスト

- audit.sh 各 check 関数を mktemp 隔離の擬似リポジトリに対して実行し、標準エラー出力の FAIL/SKIP 文言と EXIT_CODE を検証する。

## BDD

- 01 §2.2 のシナリオ（quick 免除 #32・#34、#35 維持、full/standard 適用、mode 欠落 fail-safe）をテストコードのユースケース・シナリオ・Given/When/Then として記述する。

## 5. リスク管理

### 5.1 実装リスク

| リスク | 対策 |
|--------|------|
