## 2. タスク分解

### 2.1 タスク 1: check_25 の時系列突合ロジック実装

#### 2.1.1 概要（必須）

対象差分（GIT_RANGE）が成果物変更を含む場合、`git log --format=%cI $GIT_RANGE` の最終行（最古コミット）の日時を `ts_to_epoch()` で epoch 化し、`oldest_commit_epoch - MAIN_WORK_GATE_TOLERANCE_SECONDS`（既定 172800 秒）を閾値とする。workflow_log の対象 command の `MAX(ts_utc)` を同様に epoch 化し、閾値未満なら FAIL とする。

#### 2.1.2 実装内容（必須: 1 件以上）

- `.agent-skill-chain/source/enforcement/ci/audit.sh` の `check_25_main_did_real_work()` を書き換え、以下を追加:
  - `git -C "$PROJECT_ROOT" log --format=%cI $GIT_RANGE | tail -1` で最古コミット日時を取得。
  - 取得失敗・`ts_to_epoch` 変換失敗時は従来の件数（COUNT）判定にフォールバック。
  - `MAIN_WORK_GATE_TOLERANCE_SECONDS`（既定 172800）による閾値計算。
  - `workflow_log` の `MAX(ts_utc)` 取得・`ts_to_epoch` 変換・閾値比較による FAIL 判定。
  - 判定不能な ts_utc（解析不能）は fail-open（既存 #33 と同型）。
- ファイル冒頭のチェック一覧コメント（#25 の説明行）と「失敗とみなす条件」コメントブロックに時系列突合の説明を追記。

#### 2.1.3 テスト観点（必須）

##### 単体（本タスクの具体ケース・必須 1 件以上）

- 対象 command ログが皆無 → FAIL（既存動作の回帰確認）。
- 対象差分の最古コミットが「今」で、workflow_log に 30 日前のログのみ → FAIL（新規検知・旧実装の恒久 PASS バグの再現防止）。
- 対象差分の最古コミットに近い時刻のログがある → FAIL しない（正常フロー）。
- 許容窓超のログ（3 日前）は既定（48h）で FAIL し、`MAIN_WORK_GATE_TOLERANCE_SECONDS=604800`（7日）で FAIL しない（env 上書きの確認）。
- 非 git ツリー・workflow.db 不在は従来どおり SKIP（回帰なし）。

##### 結合/API（本タスクの具体ケース・該当時は必須 1 件以上）

- tmp 隔離 git+sqlite3 環境で `audit.sh` をフル実行し、上記の単体ケースを実際のスクリプト実行として検証する（`test/test-audit.sh` に追加、下記実施結果参照）。

##### E2E/受け入れ（本タスクの具体ケース・未達時は理由記載）

- 実 CI（GitHub Actions）上での確認は未達。理由: A-2（workflow.db が gitignore 対象で CI に存在しない）により、CI では本チェック自体が SKIP される（00 §4.1 制約・本 issue のスコープ外）。ローカル実行時の tmp 隔離検証で代替した。

##### バリデーション（該当する場合の具体ケース）

- 該当なし。

#### 2.1.4 単体テスト仕様（BDD）（必須）


**テストコード例（bash・実施結果を記録）**:

```bash
# Given: 成果物変更ありの git tree（コミットは「今」）、workflow_log に 30 日前の implement-feature ログのみ
S25_2_OLD_TS="$(date -u -d '30 days ago' +%Y-%m-%dT%H:%M:%SZ)"
sqlite3 "$DB" "INSERT INTO workflow_log VALUES ('e1','implement-feature',NULL,'$S25_2_OLD_TS');"
# When: audit.sh を実行する
AUDIT_GIT_RANGE='HEAD~1..HEAD' bash audit.sh "$TREE"
```

## テスト観点

本実装の中心的なテスト観点は「(a) 対象差分と無関係な古いログのみでは FAIL する（旧実装の恒久 PASS バグを解消）」「(b) 対象差分に対応する直近ログがあれば FAIL しない（正常フローの回帰無し）」「(c) 許容窓の既定値・env 上書きが両方向で機能する」「(d) コミット日時取得不能・DB/git 不在時は既存の fail-open 挙動を維持する」の 4 点。各タスクの §2.x.3 に具体ケースを記載した。

## 5. リスク管理

### 5.1 実装リスク

- **リスク**: 許容窓（既定 48h）が短すぎる/長すぎることで、正当な作業を誤 FAIL させる、または不正な直接編集を見逃す。
  - **対策**: 環境変数 `MAIN_WORK_GATE_TOLERANCE_SECONDS` で消費者側が調整可能にした（02_設計 ADR-2）。既定値は本リポジトリの運用速度を踏まえた初期値であり、将来的な見直しの余地を残す。
- **リスク**: GIT_RANGE のコミット日時取得ロジック追加により、既存の GIT_RANGE 検証（オプション注入対策）と二重に評価される箇所で予期しない挙動が発生する。
  - **対策**: 新規の `git log` 呼び出しは既存の検証済み `$GIT_RANGE` 変数をそのまま使うのみで、追加の検証ロジックは持ち込んでいない。既存の GIT_RANGE 注入対策テスト（GR_TREE 系）が全 PASS のまま回帰していないことを確認済み。
