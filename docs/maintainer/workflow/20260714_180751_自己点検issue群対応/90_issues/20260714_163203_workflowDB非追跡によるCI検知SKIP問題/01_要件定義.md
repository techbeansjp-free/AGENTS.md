# 要件定義書: A-2（workflow.db 非追跡による CI 側 DB 系チェックの構造的全 SKIP）

> **用語**: [.agent-skill-chain/source/CONCEPTS.md §用語規約](../../../../../../.agent-skill-chain/source/CONCEPTS.md#用語規約) を参照。

## 1. 概要

### 1.1 システム概要

workflow.db は Git 非追跡（設計上の必須ルール）であり、CI のクリーンな checkout には実体が存在しない。`audit.sh` の DB 系チェック（`#3`、`#8`–`#25`、`#29`、`#31`–`#35`）は sqlite3/DB 不在時に fail-open（SKIP）する設計のため、これらは CI 上で構造的に常に SKIP される。00 のユーザー判断材料の検討の結果、**workflow.db 自体を CI 上で再構築する方針は採用しない**（ローカル作業の実施証跡が CI 側に存在しない以上、原理的に正当な再構築ができないため）。代わりに、(a) この構造的 SKIP を正本ドキュメントに明記し実効的な検知経路（ローカル pre-push）を明示すること、(b) CI ログ上で SKIP であることを明示的に可視化すること、の 2 点を対応範囲とする。

### 1.2 用語集

| 用語 | 説明 |
| --- | --- |
| DB 系チェック | `audit.sh` の失敗条件のうち、workflow.db（sqlite3）の存在を前提とする一群のチェック（`#3`、`#8`–`#25`、`#29`、`#31`–`#35`）。 |
| 構造的 SKIP | 環境の不備や設定ミスではなく、設計（workflow.db を Git 非追跡とする方針）そのものから必然的に生じる SKIP。 |
| SKIP-SUMMARY | 本 issue で追加する、audit.sh 実行冒頭に 1 行で DB 系チェックの SKIP 状況を要約表示するログ行。 |
| pre-push フック | `git push` 実行前にローカルで audit.sh を実行するフック。ローカルの workflow.db をそのまま参照できるため、DB 系チェックが実効的に発火する数少ない経路。 |

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: CI ログ上での構造的 SKIP の可視化

- **As a** 本リポジトリの保守者
- **I want to** CI（`self-enforce.yml`）や pre-push でローカル実行する `audit.sh` のログを見た際に、DB 系チェックが SKIP されたことと、その理由が一目でわかってほしい
- **So that** 「audit.sh が何も出力せず静かに通っている」ことを「DB 系チェックが正常に PASS した」と誤解しない

**受け入れ基準**:

- workflow.db が存在しない、または sqlite3 コマンドが利用できない場合、`audit.sh` の実行冒頭に `SKIP-SUMMARY:` で始まる 1 行が出力され、影響を受けるチェック番号（`#3`、`#8`–`#25`、`#29`、`#31`–`#35`）とその理由（DB 非追跡・累積型ローカルストア）が明記されていること。
- workflow.db が存在し `workflow_log` テーブルもある場合は、`SKIP-SUMMARY:` は出力されず、代わりに DB 系チェックを評価する旨の `INFO:` 行が出力されること。
- 個別の DB 系チェック（`#3`、`#8`、`#9`、`#11`、`#29`、`#31`–`#35`）についても、それぞれの SKIP 発生時に `SKIP: #<番号> ...` の形式で個別行が出力されること。

#### ストーリー 2: 正本ドキュメントでの構造的 SKIP の明記と実効的な検知経路の明示

- **As a** 本リポジトリの保守者・本フレームワークの消費者
- **I want to** `enforcement/README.md` を読めば、DB 系チェックが CI で構造的に SKIP されること・その理由・実効的な代替の検知経路（ローカル pre-push）が説明されていてほしい
- **So that** 「CI が通っている＝DB 系の絶対強制項目もすべて機能している」という誤解を防ぎ、実効性を担保する手段（pre-push 導入）を把握できる

**受け入れ基準**:

- `enforcement/README.md` の「workflow.db の扱い」節に、CI のクリーンな checkout には workflow.db が存在しえないこと・DB 系チェックが構造的に SKIP されること・その理由（累積型ローカルストアである workflow.db を CI 上でゼロから正当に再構築することは原理的にできない）が明記されていること。
- 同節に、実効的な検知経路がローカルの pre-push フックであること、その導入手順（`ci/pre-push.example` を `.git/hooks/pre-push` へコピー）、および pre-push フック自体は任意導入であり `--no-verify` で迂回できるという限界が明記されていること。
- 本リポジトリで実際に pre-push フックが導入されているかを確認し、未導入であればその事実を申し送り事項として記録すること（pre-push フックの必須化自体は 00 の除外要件によりスコープ外）。

### 2.2 BDD ユースケース

#### ユースケース 1: DB 不在時の SKIP-SUMMARY 出力

```gherkin
Feature: audit.sh の SKIP-SUMMARY 表示
  Scenario: workflow.db が存在しない場合
    Given workflow.db が存在しない最小 issue ツリー（tmp 隔離）
    When audit.sh <tmp> を実行する
    Then 標準エラーに "SKIP-SUMMARY: workflow.db が見つかりません" を含む行が出力される
    And 出力に影響を受けるチェック番号（#3, #8-#25, #29, #31-#35）が含まれる
```

#### ユースケース 2: DB 存在時の INFO 表示（誤検知なし）

```gherkin
Feature: audit.sh の SKIP-SUMMARY 表示
  Scenario: workflow.db が存在し workflow_log テーブルもある場合
    Given workflow.db（workflow_log テーブルあり）を含む最小 issue ツリー
    When audit.sh <tmp> を実行する
    Then 標準エラーに "[audit] INFO: workflow.db が見つかりました" を含む行が出力される
    And "SKIP-SUMMARY:" は出力されない
```

#### ユースケース 3: 個別チェックの SKIP 明示

```gherkin
Feature: 個別 DB 系チェックの SKIP 明示
  Scenario: workflow.db が存在しない場合の個別チェック
    Given workflow.db が存在しない最小 issue ツリー
    When audit.sh <tmp> を実行する
    Then 標準エラーに "SKIP: #29" および "SKIP: #31" 等、個別チェック番号を含む SKIP 行が出力される
    And 既存の FAIL メッセージ文字列と重複するテキストを含まない（既存回帰テストの grep パターンと衝突しない）
```

### 2.3 ビジネスルール

- 既存の DB 系チェックの**判定ロジック自体**（FAIL/SKIP の判定条件）は一切変更しない。本 issue は「SKIP であることの可視化」と「ドキュメントの明記」のみを対象とし、判定ロジックの二重化・変更は行わない。
- 追加する SKIP メッセージの文言は、既存の FAIL メッセージの部分文字列と一致してはならない（`test/test-audit.sh` の既存回帰テストが FAIL メッセージを grep で検出しているため、文言が重複すると既存テストが誤って失敗する）。
- workflow.db の CI アーティファクト化・CI 内再構築は採用しない（00 §制約・本要件の前提）。

## 3. 非機能要件

### 3.1 パフォーマンス要件

- 追加する判定（`command -v sqlite3` と `[[ -f ... ]]` の 1 回の評価、既存コードのファイル存在確認の使い回し）はごく軽量であり、audit.sh 全体の実行時間に有意な影響を与えない。

### 3.2 セキュリティ要件

- 該当なし。新規の外部入力・外部呼び出しは追加しない。
- `.github/workflows/self-enforce.yml` へのコメント追記は、CI 定義コメントの外部参照禁止規約（章節番号・追跡番号・仕様ドキュメント名の直書き禁止）に抵触しないよう文言を選定する。

### 3.3 ユーザビリティ要件

- CI ログ・ローカル実行ログの両方で、DB 系チェックが SKIP されているか評価されているかを、ログを最後まで読まなくても検索（grep）1 回で判別できること（`SKIP-SUMMARY` または `SKIP:` で検索可能）。

### 3.4 可用性要件

- 該当なし。

## 5. 制約事項

- workflow.db の Git 非追跡ルール自体は維持する（00 §2.1 既存機能の維持）。
- pre-push フックの必須化・自動配備は本 issue のスコープ外（00 §5 除外要件）。
- A-1（CI audit 非ブロッキング化問題）との対応順序: 本 issue は A-1 の非ブロッキング運用（`self-enforce.yml` step 7 の `continue-on-error`）を前提として、そのコメント記述のみ更新する。A-1 自体の方針変更（ブロッキング化の要否判断）は対象外。
