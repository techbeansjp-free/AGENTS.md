# 要件定義書: enforce を新規セットアップ既定 on 化し「絶対強制」の実態を記述と一致させる

**プロジェクト名**: enforce off が既定状態であり「絶対強制」の実態が宣言のみ
**作成日**: 2026年07月14日
**最終更新**: 2026年07月14日

> **用語**: [.agent-skill-chain/source/CONCEPTS.md §用語規約](../../../../../../.agent-skill-chain/source/CONCEPTS.md#用語規約) を参照。

## 1. 概要

### 1.1 システム概要

本パッケージの enforcement 機構は「絶対強制」「例外なく拒否」を謳うが、実際に PreToolUse hook がライブでブロックする経路（Layer2 runtime reject）は、**`.claude/settings.json` に enforcement 配線がある場合にのみ**有効になる。現状 `init`/`setup` はこの配線を書き込まず（既定 off・opt-in）、hook 配線は利用者が任意で `enforce on` を実行して初めて有効化される。加えて本リポジトリ CI（`self-enforce.yml`）は非ブロッキング運用であり、workflow.db が CI 非追跡のため DB 系チェックは構造的に SKIP される。結果として 4 層強制のうち新規消費者環境で常時効いているのは Layer3 wrapper と Layer4 CI の一部（DB 非依存チェック）・人手レビューのみで、「絶対強制」という強い表現と実態が乖離している。

00 に記録されたユーザー判断（フック修復バッチ 1〜3 完了後に enforce を実際にブロックする状態＝既定 on へ切り替える）を受け、本 issue で **(A) 新規セットアップ時の enforcement 既定を on 化する**設計・実装と、**(B) enforcement/README.md の各層・各ツールの強制力区分を実態どおり明記する**記述整合を行う。

### 1.2 用語集

| 用語 | 説明 |
| --- | --- |
| enforce on/off | `.claude/settings.json` に enforcement 配線（`hooks.PreToolUse`/`PostToolUse`・`env.AGENT_ROLE` 等）を着脱する CLI サブコマンド。正本テンプレートは `.agent-skill-chain/source/platforms/claude/settings.enforce.json`。 |
| 配線（wiring） | `.claude/settings.json` の `hooks` に PreToolUse.sh/PostToolUse.sh を結線し、`env` に managed キーを設定した状態。これが無い環境では PreToolUse は起動されない。 |
| ASC_MODE | `setup.sh` が `check_package_manifest` から得る配備判定（`own`＝パッケージ自身への自己適用／`new`＝新規配備／`match`＝既存の再配備／abort＝衝突中止）。 |
| 既定 on（default on） | 新規配備（`ASC_MODE=new`）時に、`init`/`setup` が enforcement 配線を自動でマージする挙動。opt-in（利用者が明示的に `enforce on` を実行）と対置される。 |
| 層の強制力区分 | 各強制点が「runtime 強制あり（その場で exit 2 ブロック）」「CI のみ（事後 reject）」「advisory のみ（物理ブロックなし）」のいずれか。enforcement/README.md §ツール別強制力マトリクスの 3 区分。 |

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: 新規消費者環境で enforcement が既定で効く

- **As a** 本パッケージを新規導入する消費者
- **I want to** `init`/`setup` を実行しただけで PreToolUse enforcement 配線が `.claude/settings.json` に入り、orchestrator の直接実作業がその場でブロックされる状態になってほしい
- **So that** 「絶対強制」の宣言どおり、追加の opt-in 操作を忘れても機械強制が最初から効く

#### ストーリー 2: 既存環境と自己適用リポは影響を受けない

- **As a** 既にパッケージを導入済みの消費者 / 本パッケージ自身の保守者
- **I want to** `upgrade`・再 `init`（`ASC_MODE=match`）や本リポジトリへの自己適用（`ASC_MODE=own`）では `.claude/settings.json` を勝手に書き換えないでほしい
- **So that** 意図的に `enforce off` した設定や、ローカル固有の settings.json が upgrade のたびに再有効化・破壊されない

#### ストーリー 3: 各強制点の実態が記述から一意に読み取れる

- **As a** enforcement 機構を運用・監査する保守者
- **I want to** enforcement/README.md と SETUP.md を読めば、各層（Layer1〜4）・各ツール（Claude/Cursor/CI 等）が「既定 on の runtime 強制」「opt-in」「advisory のみ」「CI のみ」のいずれで、どの条件下でブロック/FAIL するかが一意に分かるようにしてほしい
- **So that** 「絶対強制」の強い表現を、実際に機械強制されている範囲にのみ整合的に使える

### 2.2 受け入れ基準（Acceptance Criteria）

| # | 受け入れ基準 | 判定方法 |
| --- | --- | --- |

## 3. 非機能要件

### 3.1 互換性

- 既存の `enforce on`/`off`/`status` CLI サブコマンドの契約・挙動は不変（既定 on は「新規配備時に enforce on 相当の配線を自動実行する」ものであり、enforce コマンド自体の意味を変えない）。
- 既存導入済み環境（`ASC_MODE=match`）・本リポ自己適用（`ASC_MODE=own`）には影響しない（後方互換）。

### 3.2 セキュリティ / 安全性

- 既定 on により新規環境で PreToolUse がライブになるため、orchestrator の allowlist がハーネス組み込みツール（`Agent`・`AskUserQuestion` 等）を網羅していないと自己ロックアウトが起こりうる（過去に `Agent` で発生）。復旧経路（`!enforce off`）を SETUP.md で目立つ形で案内すること。
- 無効 JSON への書き込みは Claude 起動時エラーを招くため、既定 on 配線も既存 enforce on と同じ「無効 JSON 時は中止」を厳守する。

### 3.3 保守性

- 既定 on の判定は既存の `ASC_MODE`（`check_package_manifest`）を再利用し、新たな「fresh 判定」ロジックを二重実装しない。
- setup.sh（bash）と `src/agents-md.ts`（TS）が init 経路を二重に持つため、既定 on 配線も両者で同一挙動になるよう単一の enforce on 相当ロジックを呼ぶ形にし、パリティテストで担保する。

## 4. 制約条件

- 本リポジトリ自身の `.claude/settings.json` は `.gitignore` 対象・ローカル環境固有であり、配布パッケージに非含有・他消費者に非継承（[.agent-skill-chain/project/自己拡張ワークフロー.md](../../../../../../.agent-skill-chain/project/自己拡張ワークフロー.md) §settings.json のローカル固有性 参照）。このファイルへの実際の enforce on 適用は本 issue の実装スコープ外とし、別途ユーザー許可を得て orchestrator が手動実行する。
- 本リポ CI（`self-enforce.yml`）の非ブロッキング運用・workflow.db 非追跡は別 issue（`20260714_163129_CIaudit非ブロッキング化問題`・`20260714_163203_workflowDB非追跡によるCI検知SKIP問題`）の担当であり、本 issue では CI のブロッキング化自体は扱わない（記述整合の範囲でのみ言及）。

## 5. 除外要件

- CI（`self-enforce.yml`）のブロッキング化・workflow.db の CI 追跡化の実装（別 issue）。
- 本リポ自身の `.claude/settings.json` への enforce on 適用（別途ユーザー許可・手動）。
- Cursor/Gemini/Copilot/Codex への runtime 強制の新規実装（advisory のまま。記述整合の対象にはする）。
- orchestrator allowlist にハーネス組み込みツールを追加する作業自体（既に別バッチで対応済みの前提。本 issue はその完了を前提に既定 on を成立させる）。
