## 1. 設計概要

### 1.1 設計方針

本件は、モデルティア選定の「規約ドキュメント構造」をどう設計するかの判断である。[spec/01_設計原則](../../../../../.agent-skill-chain/source/spec/01_設計原則.md) の **単一責務・明確な境界**、および [spec/06_設計判断の優先順位](../../../../../.agent-skill-chain/source/spec/06_設計判断の優先順位.md) の **「再利用性より責務の明確さ」「再利用のために責務を曖昧にしてはならない」** を最上位の判断軸として、折衷案の採否と配置境界を確定する。

### 1.2 設計原則（本プロジェクトで適用するもの）

- **単一責務**: 1 ファイル 1 責務。抽象原則（core）／PF 固有推奨デフォルト（platforms/claude）／本リポ固有 ADR 運用（project）を**責務で分離**し、同じ対応表・原則を重複記載しない（BR-3・01 §2.3）。
- **明確な境界**: 「PF 中立なコア本体」「PF 限定名前空間 platforms/&lt;pf&gt;/」「project 固有」の 3 境界を明示し、それぞれに何を置き何を置かないかを定義する（§2.1）。
- **UNIX 哲学**: 各ファイルは小さく 1 つのことをうまくやる。推奨デフォルトは「役割→抽象ティア」の最小形に留め、モデル ID 解決や本リポ固有運用は他ファイルに委ねる（陳腐化耐性・00 §3.4）。
- **AI フレンドリー設計**: 意図が分かる命名（`MODEL_TIER_RECOMMENDED.md`）・小さなファイル・浅い構造。

- **入力**: サブ委譲時の「役割」（設計/レビュー/監査/実装/書記 等）と実行ランタイム（ティア選択可否）。

### 2.5 横断設計判断（ADR）

> 本節が本 02 の中心。各 ADR は [EVIDENCE_POLICY.md](../../../../../.agent-skill-chain/source/EVIDENCE_POLICY.md) の形式（コンテキスト・選択肢・決定・根拠[evidence_source]・帰結）で記録する。evidence_source 分類は [CONCEPTS §外部根拠の必須化](../../../../../.agent-skill-chain/source/CONCEPTS.md#外部根拠の必須化external-anchor)。

#### ADR-A: 折衷案の採否（**条件付き採用**）

- **コンテキスト**: ユーザー（メンテナ）から「Claude をオーケストレータとして使う場合の推奨デフォルト・モデルティア表を `source/platforms/claude/` に置く」折衷案の提案があった（[00 §1.2](./00_要求定義.md)）。現状は 2 層（core 抽象原則／project 固有表）で、`MODEL_SELECTION §汎用/固有境界` は「対応表はコアに置かない（PF 中立性）」と規定する（[MODEL_SELECTION.md:57](../../../../../.agent-skill-chain/source/MODEL_SELECTION.md)）。採否が未確定（AC-1）。
- **検討した選択肢**:
  1. **不採用（2 層維持）**: 採用先は各自 project/ に表を用意すればよい。core は抽象原則のみ。
  2. **無条件採用**: platforms/claude に推奨デフォルトを置き、モデル ID まで含めて手厚く配布。
  3. **条件付き採用（本決定）**: platforms/claude に置くが、(i) 役割→**抽象ティア**水準に限定（モデル ID を焼き込まない）、(ii) **一般推奨のみ**（本リポ固有 ADR 運用を除外）、(iii) 優先順位を明示 3 層化＋表なし時フォールバック接続、(iv) §汎用/固有境界と platforms/README スコープを明示更新（暗黙例外を残さない）、の 4 条件を満たす場合に限り採用。
- **決定**: **選択肢 3（条件付き採用）**。4 条件（i〜iv）を実装フェーズの完了条件に組み込む。
- **根拠**:
  - PF 中立性との整合（論点 a）は成立する。`platforms/claude/` は当該 PF 利用時のみ有効な**限定名前空間**であり、他 PF（Cursor/Gemini/Copilot/Codex）へ Claude 固有表を強制しない。「対応表はコアに置かない」の**趣旨（PF 中立性）**は限定名前空間で保たれる。実際、`platforms/claude/` には既に PF 固有具体値（settings.enforce.json・plugin.json）を置く前例が存在する（`evidence_source: existing_code` — [platforms/claude/settings.enforce.json](../../../../../.agent-skill-chain/source/platforms/claude/settings.enforce.json)・[plugin.json](../../../../../.agent-skill-chain/source/platforms/claude/plugin.json) の実在）。
  - 無条件採用（選択肢 2）を退ける理由: モデル ID を core（配布物）に焼き込むと世代交代（Opus 4.8 / Sonnet 5 / Haiku 4.5 の世代交代は既発生）のたびに本体再配布が必要（制約 1）。抽象ティア水準に留めることで更新点を 1 ファイルに局所化できる（ADR-B）。
  - 前例との**非同一性**（AC-2-3）を認めたうえでの採用: settings/plugin は Claude が動作するための**機構上の必需物（mechanical necessity）**であるのに対し、ティア表は**助言的（advisory）**である。両者は同カテゴリではない。したがって前例は採用の**十分条件ではなく**、採用は限定名前空間による中立性保持と導入利便性という**独自の根拠**による。この非同一性はむしろガードレールとして働き、「advisory ゆえに一般推奨に厳格限定し、必須運用に偽装しない」（ADR-D の除外基準）を要請する（`evidence_source: existing_code`＋`inference_only`）。
  - **採否の望ましさ（導入利便性が構造追加コストに見合うか）の最終判断は inference_only を含む価値判断**であり、[EVIDENCE_POLICY §4](../../../../../.agent-skill-chain/source/EVIDENCE_POLICY.md) に従い **メンテナの承認（human_decision）を要する（＝要人間確認）**。本 02 は 4 条件を満たせば技術的整合が成立することを existing_code で示すに留め、最終 Go はメンテナ判断に委ねる。
- **帰結**: 採用時、新設 1 ファイル＋既存 4 ファイルの境界更新が実装フェーズの対象になる（§3・03）。条件 i〜iv を欠くと不採用と同等の整合破綻（陳腐化・重複・暗黙例外・優先順位不定）を招くため、4 条件は完了条件として不可分。**不採用（選択肢 1）を選ぶ場合の帰結は ADR-E に記載**（01 シナリオ 6 対応）。

#### ADR-B: 推奨デフォルトの抽象度（**役割→抽象ティア水準に限定・モデル ID を焼き込まない**）（論点 c の陳腐化面・AC-6-2）

- **コンテキスト**: `platforms/claude/` は core（配布物）の一部。具体モデル ID を置くと世代交代のたびに本体再配布が必要（制約 1・[00 §4.1](./00_要求定義.md)）。
- **検討した選択肢**: (a) 役割→モデル ID（世代付き）まで記載、(b) 役割→**抽象ティア**（opus/sonnet/haiku のティア呼称）に留め、モデル ID 解決は project/ またはランタイム既定に委ねる。
- **決定**: **(b)**。推奨デフォルトは「役割→抽象ティア呼称」まで。世代付きモデル ID（例 `claude-opus-4-8-…`）は記載しない。
- **根拠**: ティア呼称（opus/sonnet/haiku）は世代 ID より安定であり、更新点を局所化する（`evidence_source: existing_code` — MODEL_SELECTION は既に「上位ティア/安価ティア」の抽象語で記述、[MODEL_SELECTION.md:25,41](../../../../../.agent-skill-chain/source/MODEL_SELECTION.md)）。ティア呼称が改称された場合でも更新は当該 1 ファイルに閉じる。世代付き ID の解決責務は project/ 側（コスト実測・降格判断と同じ層）に残す（`evidence_source: existing_code` — [MODEL_TIER_TABLE.md 書記行の model 実例参照](../../../../../.agent-skill-chain/project/MODEL_TIER_TABLE.md)）。
- **帰結**: 推奨デフォルト表の列は「役割｜推奨ティア｜適用条件（一般）」に固定。モデル ID 列は持たない。陳腐化耐性の評価軸（AC-6-2）を満たす。

#### ADR-C: 優先順位規約の 3 層整合（論点 b・AC-3）

- **コンテキスト**: `project/README.md §優先順位` は「project > source の 2 層」を一般規約として規定（[project/README.md:15-20](../../../../../.agent-skill-chain/project/README.md)）。採用時は tier ドメイン内で 3 者（MODEL_TIER_TABLE / platforms/claude 既定 / MODEL_SELECTION 抽象原則）の順序が要る（制約 4）。
- **検討した選択肢**: (a) project/README の一般 2 層規約を「3 層」に書き換える、(b) 一般 2 層規約は**維持**し、tier ドメイン内の 3 層順序は tier ドキュメント側（platforms/claude 既定ヘッダ＋ §汎用/固有境界）を正本とし、README には「source 内部に PF 限定名前空間のサブ層があり得る／project はその全 source に優先する」旨の**明確化注記のみ**を加える。
- **決定**: **(b)**。
- **根拠**: `platforms/claude/` と `MODEL_SELECTION` は**いずれも source 配下**である。ゆえに「project > platforms/claude > MODEL_SELECTION」は既存の「project > source」と**矛盾せず、その内部詳細化**にすぎない（project は両 source ファイルに優先する）。README の一般規約を tier 特化 3 層に書き換えると、README が tier ドメイン知識を抱えて**単一責務を侵す**（spec/06「再利用のために責務を曖昧にしない」）。tier 固有順序は tier ドキュメントに置くのが責務整合（`evidence_source: existing_code` — [project/README.md:15-26](../../../../../.agent-skill-chain/project/README.md) の規約が「同名/同目的の一般規則」である事実）。
- **帰結（AC-3-1/2/3 充足）**:
  - AC-3-1: 実行時ティア解決の順序 = **MODEL_TIER_TABLE（project）> platforms/claude 推奨デフォルト > MODEL_SELECTION 抽象原則** で一意（§2.2.2 図・platforms/claude 既定ヘッダに明記）。
  - AC-3-2: **どこにも表が無い**環境（project にも platforms/claude にも表なし）は **MODEL_SELECTION §1 のティア選択不能環境＝ランタイム既定動作**に接続（既定ヘッダに明記）。
  - AC-3-3: README への明確化注記追加を**完了条件に含める**（03 タスク 4）。一般 2 層規約は維持されるため、2 層規約との重複・矛盾は生じない（platforms/claude は source 層の一部＝project がなお優先、と矛盾なく説明）。

#### ADR-D: 一般推奨と本リポ固有 ADR 運用の切り分け（論点 c・AC-4）

- **コンテキスト**: `project/MODEL_TIER_TABLE.md` は本リポ固有 ADR 運用（opus 要否先行検討＝ADR-1 の順序規定・fable 原則禁止・書記=haiku 固定・降格手続き）を含む（[MODEL_TIER_TABLE.md:11-14,20-22](../../../../../.agent-skill-chain/project/MODEL_TIER_TABLE.md)）。これらは「Claude 採用先なら誰でも当てはまる一般推奨」とは性質が異なりうる（制約 2）。1 ファイル 1 責務・重複禁止（BR-3）を守る必要。
- **検討した選択肢（区別基準 AC-4-1）**: 「**誰にでも当てはまるか（一般）／本リポの運用文脈・ADR に依存するか（固有）**」で二分。
- **決定・切り分け**:
  - **platforms/claude 推奨デフォルト（一般・include してよい）**: 役割→抽象ティアの**方向性**のみ。すなわち「品質ゲート直結役割（設計・レビュー・監査）は上位ティア」「実装は中位ティア＋複雑作業は上位へエスカレーション」「ログ記録専任（書記）は軽量ティア」。これらは Claude 採用先一般に当てはまる助言。
  - **platforms/claude に include してはいけない（固有・除外基準 AC-4-3）**: (1) **fable 原則禁止**（本リポの運用ポリシー）、(2) **opus 要否先行検討という順序規定**（「sonnet デフォルト→複雑時格上げ」の逆順を禁ずる ADR-1 の非裁量手順）、(3) 降格の**計測閾値・承認フロー・対応表更新手順**、(4) 世代付きモデル ID（ADR-B）。
  - **重複回避の正本配置（AC-4-2）**: 一般ティア方向性の**正本は platforms/claude**。`MODEL_TIER_TABLE` は一致する行を**再掲せず参照**し（例: 「設計・レビュー・監査=opus は推奨デフォルトと同じ。本リポでも格下げしない」）、その上に本リポ固有の**上書き/追加**（ADR-1 の順序規定・fable 禁止 等）だけを記す。
- **根拠**: 除外対象はいずれも「本リポ固有 issue の決定（ADR-1）」または「本リポの運用ポリシー」に由来し、一般採用先には当てはまらない（`evidence_source: existing_code` — [MODEL_TIER_TABLE.md:32-36](../../../../../.agent-skill-chain/project/MODEL_TIER_TABLE.md) が ADR-1 を本リポ固有として明記）。一般方向性（品質ゲート役割は上位ティア）は MODEL_SELECTION §3 品質ゲート最上位固定という**PF 非依存原則の自然な具体化**であり、一般推奨として妥当（`evidence_source: existing_code` — [MODEL_SELECTION.md:23-25](../../../../../.agent-skill-chain/source/MODEL_SELECTION.md)）。
- **帰結**: platforms/claude 表は「役割｜推奨ティア｜一般適用条件」の 3 列・助言ラベル付き。MODEL_TIER_TABLE は推奨デフォルトを参照しつつ固有上書きのみ保持し、重複記載が消える（BR-3 充足）。

#### ADR-E: 本検討と ADR-1 の関係（**独立決定**）＋不採用時の帰結（AC-5・01 シナリオ 6）

- **コンテキスト**: ADR-1 は「opus 要否先行検討＝ティア選定の非裁量化」という**選定ロジック**の決定（[MODEL_TIER_TABLE.md:20-34](../../../../../.agent-skill-chain/project/MODEL_TIER_TABLE.md)）。本検討は「推奨デフォルトの**配置・抽象度・境界・規約整合**」という配置・境界の決定。両者の関係と、不採用を選ぶ場合の要件を確定する必要（AC-5・00 §4.4）。
- **決定**:
  - 本検討は ADR-1 の**拡張ではなく独立の決定**である（スコープが「どのティアを選ぶか」ではなく「推奨デフォルトをどこに・どの抽象度で置き・規約とどう整合させるか」）。ただし ADR-1 の**成果を変更せず前提として温存**する（ADR-1 の選定ロジックは project 側に残る）。
  - **不採用（選択肢 1）を選ぶ場合の帰結**: MODEL_SELECTION の「対応表はコアに置かない」は現行文言のまま維持。採用先は各自 `project/` に表を用意する（現行 2 層で運用は成立している）。この場合 §汎用/固有境界・platforms/README・README・MODEL_TIER_TABLE の更新は不要。導入利便性は得られないが、単一責務・陳腐化耐性・優先順位単純性は現状のまま最大化される。
- **根拠（AC-5-1/2）**: 本検討スコープ（配置・境界）と ADR-1 スコープ（選定ロジック）は明確に別レイヤ（`evidence_source: existing_code` — MODEL_TIER_TABLE は選定手順、本検討は配置規約）。採用（ADR-A）・不採用いずれでも MODEL_TIER_TABLE の既存記述（ADR-1 の順序規定）と矛盾しない：採用時は ADR-D により推奨デフォルトが ADR-1 順序規定を含まないため衝突せず、不採用時は現状維持のため衝突しない。
- **帰結**: 決定系譜が「ADR-1（選定ロジック）」と「本検討 ADR-A〜E（配置・境界）」に分離され、二重管理・矛盾を回避（効果 3・SC-6 充足）。

#### ADR-F: MODEL_SELECTION §汎用/固有境界の更新方針（論点 a・AC-2）

- **コンテキスト**: 現行 §汎用/固有境界は「**対応表はコアに置かない（PF 中立性）**」と規定（[MODEL_SELECTION.md:54-57](../../../../../.agent-skill-chain/source/MODEL_SELECTION.md)）。採用時、platforms/claude に条件付き推奨表を置くことが、この文言と矛盾しないか。矛盾を残さないため文言更新が要るか（暗黙例外の排除）。
- **検討した選択肢**: (a) 文言を更新しない（限定名前空間だから矛盾しない、と暗黙運用）、(b) §汎用/固有境界に**明示の但し書き**を追加：「対応表はコアに置かない」の『コア』は **PF 中立なコア本体（全 PF 共通）**を指し、**PF 限定名前空間 `platforms/<pf>/` への、当該 PF 利用時のみ有効な推奨デフォルト（advisory・抽象ティア水準）は例外的に許容**する。ただし本リポ固有運用は含めない、と明記。
- **決定**: **(b)**。加えて `platforms/README.md` の記載スコープ 1 行（現行「スキル形式・配備・ツール別設定のみ」[platforms/README.md:3](../../../../../.agent-skill-chain/source/platforms/README.md)）に「PF 固有のモデルティア推奨デフォルト」を対象として明記し、新設ファイルが未記載の暗黙例外にならないようにする。
- **根拠（AC-2-1/2/3）**:
  - AC-2-1（見立ての真偽）: 「限定名前空間ゆえ中立性に反しない」は**真**。ただし現行文言は『コア』を無限定に書いており、**暗黙の例外を残す**。→ 明示化が必要（`evidence_source: existing_code` — 現行文言 [MODEL_SELECTION.md:57](../../../../../.agent-skill-chain/source/MODEL_SELECTION.md) が限定名前空間を区別していない）。
  - AC-2-2（追記要否）: **追記は必要**。BR-2（既存原則を暗黙に骨抜きにしない）に従い、例外は明文化する（選択肢 a を退ける理由）。
  - AC-2-3（前例と同列か）: ADR-A のとおり settings/plugin（機構上の必需物）とティア表（advisory）は**非同一**。§汎用/固有境界の但し書きには「advisory 推奨デフォルトに限る／本リポ固有運用は含めない」を明記し、前例の必需物ロジックを流用しない。
- **帰結**: §汎用/固有境界に但し書き 1 段落、platforms/README にスコープ 1 行を追加（03 タスク 2・4）。これにより「置いてよい根拠」がコア規約側に明文化され、暗黙例外が消える。
