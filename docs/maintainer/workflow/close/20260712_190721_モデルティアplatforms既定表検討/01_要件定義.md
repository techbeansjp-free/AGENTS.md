# 要件定義書: Claude 向け推奨デフォルト・モデルティア表を source/platforms/claude/ に置く折衷案の評価

**プロジェクト名**: モデルティア推奨デフォルトの platforms 配置検討
**作成日**: 2026 年 07 月 12 日
**最終更新**: 2026 年 07 月 12 日

> **重要**: 本 01 は、[00_要求定義.md](./00_要求定義.md) の目的・制約・成功基準を受け、**設計フェーズ（design-feature）が折衷案の妥当性判断と具体設計を行えるようにするための、ユーザーストーリー・受け入れ基準・BDD シナリオ**を確定する。本 issue の成果物は「判断基準・要件」であり、推奨表の中身や実装ではない（00 §5 除外要件）。
>
> **用語**: [.agent-skill-chain/source/CONCEPTS.md §用語規約](../../../../../.agent-skill-chain/source/CONCEPTS.md#用語規約) を参照。

## 1. 概要

### 1.1 システム概要

本パッケージ（AGENTS.md）のモデルティア選定は現状 2 層で構成される。

- **コア（PF 中立の抽象原則）**: `source/MODEL_SELECTION.md`。適用条件・ティア明記義務・品質ゲート最上位固定・裁量禁止・§汎用/固有境界（「対応表はコアに置かない」）。
- **project（本リポ固有の具体対応表）**: `project/MODEL_TIER_TABLE.md`。役割→ティアの具体対応。ADR-1（opus 要否先行検討）に基づく運用判断。

本要件は、ユーザー提案の折衷案「**Claude 向け推奨デフォルト・ティア表を `source/platforms/claude/` に置く**」を評価・意思決定するための要件を定義する。実際の表の中身確定と実装は後続フェーズに委ねる。

### 1.2 用語集

| 用語 | 説明 |
| ---- | ---- |
| 抽象原則層（コア） | `source/MODEL_SELECTION.md`。PF 中立のティア選定原則のみ。対応表を持たない。 |
| project 固有表 | `project/MODEL_TIER_TABLE.md`。本リポ固有の役割→ティア具体対応。ADR に基づく運用判断。 |
| platforms/claude 推奨デフォルト | 本折衷案で新設を検討する「Claude 採用先一般に向けた推奨デフォルト・ティア表」。`source/platforms/claude/` に置く候補。 |
| PF 中立性 | パッケージが特定プラットフォームに依存しない設計原則。「対応表はコアに置かない」で表現される。 |
| ティア選択不能環境 | ティア選択の概念が無い/解決できないランタイム。MODEL_SELECTION §1 によりランタイム既定動作に従う。 |
| ADR-1 | 「モデルティア選定方針の project 化」issue の決定。opus 要否先行検討＝ティア選定の非裁量化。本リポ固有運用判断。 |

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: 折衷案の採否を判断基準に基づいて決定する

- **As a** 本パッケージのメンテナ（意思決定者）
- **I want to** 「Claude 向け推奨デフォルト・ティア表を `source/platforms/claude/` に置く」折衷案を、明文化された判断基準で採用/不採用/条件付き採用と決められる
- **So that** 感覚や裁量ではなく、PF 中立性・陳腐化耐性・責務分離という既存原則に照らした一貫した意思決定ができる

**受け入れ基準**:

- AC-1-1: 折衷案の採否を評価する判断軸が列挙されている。少なくとも (i) PF 中立性との整合、(ii) 具体モデル名焼き込みによる陳腐化リスク（制約 (1)）、(iii) 本リポ固有 ADR 運用判断との責務重複（制約 (2)）、(iv) 優先順位規約の整合コスト（制約 (4)）を含む。
- AC-1-2: 各判断軸は○/× または「充足/未充足/条件付き」で評価できる形で書かれている。
- AC-1-3: 「不採用（2 層のまま維持）」も選択肢として明示され、その場合の帰結（現状維持で足りる理由の要件）が示されている。

#### ストーリー 2: MODEL_SELECTION の「汎用/固有境界」節の更新要否を判断する（論点 a）

- **As a** メンテナ
- **I want to** `source/MODEL_SELECTION.md §汎用/固有境界`（「対応表はコアに置かない（PF 中立性）」）の記述を、折衷案採用時にどう更新するか（またはしないか）の基準を持つ
- **So that** コアの原則文言と実際の配置（platforms/claude に条件付き推奨表を置く）が矛盾しない

**受け入れ基準**:

- AC-2-1（論点 a）: 「`source/platforms/claude/` は**プラットフォーム限定の名前空間**であり、そこへの Claude 条件付き推奨デフォルト配置は §汎用/固有境界の『対応表はコアに置かない』と矛盾しない」という見立ての真偽を判定する基準が示されている。
- AC-2-2: 矛盾しないと判断する場合でも、§汎用/固有境界に「**PF 限定名前空間（platforms/<pf>/）への PF 条件付き推奨デフォルトは例外的に許容する**」旨の追記が必要か否かの判断基準が示されている（暗黙の例外を残さない）。
- AC-2-3: 既存前例（`platforms/claude/settings.enforce.json`・`plugin.json` が「Claude 固有の具体値をコアに置く」を許容している事実）と、本件（ティア表）を同列に扱ってよいかの評価基準が示されている。

#### ストーリー 3: 優先順位規約を 2 層のまま扱うか 3 層へ整合させるか判断する（論点 b）

- **As a** メンテナ
- **I want to** `project/README.md` の優先順位規約（project > source の 2 層）を、折衷案採用時に 3 層（project > platforms/claude > MODEL_SELECTION 抽象原則）へどう整合させるか、または 2 層のまま扱うかの基準を持つ
- **So that** ティア選定時にどの表が優先されるかが一意に決まり、解釈揺れ・二重管理を防げる

**受け入れ基準**:

- AC-3-1（論点 b）: 折衷案採用時の優先順位の並びが一意に定義できる基準が示されている（候補: project の MODEL_TIER_TABLE > platforms/claude 推奨デフォルト > MODEL_SELECTION 抽象原則）。
- AC-3-2: 対応表が**どこにも無い**環境（project にも platforms/claude にも表が無い）の扱いが、MODEL_SELECTION §1 適用条件の「ティア選択不能環境＝ランタイム既定動作」と接続されている。
- AC-3-3: 3 層化する場合、`project/README.md`（現状 2 層記述）の更新が完了条件に含まれることが明記されている。逆に 2 層のまま扱うと決める場合、platforms/claude をどの層に位置づけるか（例: source 層の一部として project がなお優先）が矛盾なく説明されている。

#### ストーリー 4: 一般推奨デフォルトと本リポ固有 ADR 運用判断を切り分ける（論点 c）

- **As a** メンテナ
- **I want to** `source/platforms/claude/` の推奨デフォルトの中身が、`project/MODEL_TIER_TABLE.md` の本リポ固有 ADR 運用判断（fable 原則禁止・opus 要否先行検討 等）と重複・矛盾しないための切り分け方針を持つ
- **So that** 1 ファイル 1 責務・重複禁止（spec/01）を保ち、採用先が誤って本リポ固有運用を一般推奨と取り違えない

**受け入れ基準**:

- AC-4-1（論点 c）: 「Claude 採用先一般に当てはまる推奨（platforms/claude）」と「本リポ固有 ADR 運用判断（MODEL_TIER_TABLE）」を区別する基準（誰にでも当てはまるか/本リポの運用文脈に依存するか）が示されている。
- AC-4-2: 重複が生じうる項目（例: 役割→ティアの一般的対応）について、正本をどちらに置き他方は参照で委ねるか（重複記載しない）の方針基準が示されている。
- AC-4-3: 本リポ固有の運用判断（fable 原則禁止、opus 要否先行検討という**順序規定**）を platforms/claude の一般推奨に混入させないための除外基準が示されている。

#### ストーリー 5: 本検討と既存 ADR-1 の関係を明確化する

- **As a** メンテナ
- **I want to** 本検討が ADR-1（選定ロジックの非裁量化）の拡張なのか、独立した配置・境界の決定なのかを判断する基準を持つ
- **So that** 決定の系譜が追え、既存 ADR との二重管理・矛盾を避けられる

**受け入れ基準**:

- AC-5-1: 本検討のスコープ（配置・抽象度・境界・規約整合）が ADR-1 のスコープ（どのティアを選ぶかの選定ロジック）と区別されて記述されている。
- AC-5-2: 「拡張」と判断するか「独立決定」と判断するかの基準が示され、いずれであっても MODEL_TIER_TABLE.md の既存記述と矛盾しないことが確認できる。

#### ストーリー 6: 制約 (1)〜(4) を前提として設計判断に引き渡す

- **As a** 設計フェーズ担当（design-feature）
- **I want to** 00 の制約 (1)〜(4) が BDD の Given として固定されている
- **So that** 妥当性判断・具体設計をこれらの前提の上で一貫して行える

**受け入れ基準**:

- AC-6-1: 制約 (1) 陳腐化リスク、(2) 性質差、(3) PF 中立性、(4) 優先順位多層化 の 4 つが BDD シナリオの Given に反映されている。
- AC-6-2: 陳腐化耐性の評価軸（推奨を「モデル名」水準にするか「抽象ティア」水準に留めるか）が受け入れ基準として存在する。

### 2.2 BDD ユースケース

#### ユースケース 1: 折衷案の採否判断（論点 a/b/c を統合）

このユースケースは、設計フェーズが折衷案を評価するときに満たすべき判断プロセスを定義する。

**シナリオ 1: PF 中立性との整合を検証する（論点 a）**

```gherkin
Feature: 折衷案のPF中立性整合検証
  Scenario: platforms/claude への配置がコア中立性原則と矛盾しないか判定する
    Given MODEL_SELECTION §汎用/固有境界 が「対応表はコアに置かない（PF中立性）」と規定している
    And source/platforms/claude/ には既に settings.enforce.json・plugin.json という Claude 固有具体値の前例がある
    And 制約(3) として「platforms/claude はPF限定名前空間なので条件付き配置はPF中立性に反しない」という見立てがある
    When 設計フェーズが折衷案のPF中立性整合を評価する
    Then その見立ての真偽を判定する基準（AC-2-1）が適用される
    And §汎用/固有境界に「PF限定名前空間へのPF条件付き推奨は例外許容」の追記要否（AC-2-2）が判断される
    And 前例(settings/plugin)とティア表を同列に扱えるかの基準（AC-2-3）が適用される
```

**シナリオ 2: 優先順位規約の整合を決める（論点 b）**

```gherkin
Feature: 優先順位規約の層構成整合
  Scenario: 2層規約を3層へ整合させるか2層維持かを一意に決める
    Given project/README.md が「project > source の2層」優先順位を規定している
    And 折衷案採用時は project > platforms/claude > MODEL_SELECTION抽象原則 の3層になりうる（制約(4)）
    And MODEL_SELECTION §1 は対応表不在環境を「ティア選択不能＝ランタイム既定動作」と規定している
    When 設計フェーズが優先順位の並びを決定する
    Then 優先順位が一意に定義される基準（AC-3-1）が適用される
    And 対応表がどこにも無い環境の扱いが §1適用条件と接続される（AC-3-2）
    And 3層化する場合は project/README.md 更新が完了条件に含まれ、2層維持なら platforms/claude の層位置が矛盾なく説明される（AC-3-3）
```

**シナリオ 3: 一般推奨と本リポ固有運用を切り分ける（論点 c）**

```gherkin
Feature: 一般推奨とリポ固有運用の責務分離
  Scenario: platforms/claude推奨とMODEL_TIER_TABLEのADR運用判断を重複・矛盾なく分離する
    Given project/MODEL_TIER_TABLE.md は本リポ固有ADR運用判断（fable原則禁止・opus要否先行検討）を含む
    And これらは「Claude採用先なら誰でも当てはまる汎用推奨」とは性質が異なりうる（制約(2)）
    And 1ファイル1責務・重複禁止（spec/01）を守る必要がある
    When 設計フェーズが platforms/claude 推奨デフォルトの責務範囲を決める
    Then 一般推奨と固有運用を区別する基準（AC-4-1）が適用される
    And 重複項目の正本をどちらに置き他方を参照委譲するか（AC-4-2）が決まる
    And 本リポ固有運用（fable禁止・opus要否先行の順序規定）を一般推奨に混入させない除外基準（AC-4-3）が適用される
```

#### ユースケース 2: 陳腐化耐性と既存 ADR 関係の確定

**シナリオ 4: 具体モデル名焼き込みの陳腐化リスクを緩和する（制約 (1)）**

```gherkin
Feature: 推奨デフォルトの陳腐化耐性
  Scenario: コア配布物に具体モデル名を焼き込むリスクを評価し抽象度を決める
    Given モデル名・世代は頻繁に変わる（Opus 4.8 / Sonnet 5 / Haiku 4.5 の世代交代が既に発生）
    And source/platforms/claude/ はコア（配布物）の一部であり、具体モデル名を置くと世代交代のたびに本体再配布が必要になる（制約(1)）
    When 設計フェーズが推奨デフォルトの抽象度を決定する
    Then 推奨を「役割→抽象ティア」水準に留めるか「具体モデル名」まで書くかの評価軸（AC-6-2）が適用される
    And 具体モデル名を書く場合の更新点局所化・再配布コストが判断材料に含まれる
```

**シナリオ 5: 本検討と ADR-1 の関係を明示する**

```gherkin
Feature: 既存ADRとの関係明確化
  Scenario: 本検討が拡張か独立決定かを判定し二重管理を防ぐ
    Given ADR-1 は「opus要否先行検討＝ティア選定の非裁量化」という選定ロジックの決定である
    And 本検討は「推奨デフォルトの配置・抽象度・境界・規約整合」という配置・境界の決定である
    When 設計フェーズが両者の関係を判定する
    Then 本検討スコープとADR-1スコープが区別される（AC-5-1）
    And 「拡張」か「独立決定」かの判断基準が適用され、いずれでもMODEL_TIER_TABLE.md記述と矛盾しないことが確認される（AC-5-2）
```

**シナリオ 6: 不採用（2 層維持）という結論も許容する**

```gherkin
Feature: 現状維持の選択肢保持
  Scenario: 折衷案を採用しない判断も基準に基づいて選べる
    Given 現状は MODEL_SELECTION(抽象原則) と MODEL_TIER_TABLE(project固有表) の2層で運用できている
    When 設計フェーズが折衷案の採否を評価する
    Then 「不採用＝2層維持」も明示された選択肢として評価対象になる（AC-1-3）
    And 不採用と決める場合、現状2層で足りる理由（採用先は自前でproject表を用意すればよい等）が要件として示される
```
