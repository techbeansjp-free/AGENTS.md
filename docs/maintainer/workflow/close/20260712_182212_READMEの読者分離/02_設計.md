## 1. 設計概要

### 1.1 設計方針

README.md を「利用者（採用先）が導入・運用に必要な情報だけ」で構成し、開発者・自己拡張・メンテナ向け情報は単一の入口ファイル（ルート新設 `CONTRIBUTING.md`）へ集約する。詳細は既存 `docs/maintainer/` 文書に一本化し、README と CONTRIBUTING は**要約＋リンク**に徹する（既存の README→`docs/maintainer/RELEASE.md` 分離パターンの踏襲）。

### 1.2 設計原則（本プロジェクトで適用するもの）

- **単一責務**: README＝利用者向けマニュアル、CONTRIBUTING＝開発者・メンテナ向け入口、`docs/maintainer/*`＝各詳細正本。1 ファイル 1 読者・1 責務に整理する。
- **明確な境界**: 「利用者向け操作」と「開発者・メンテナ向け導線」を見出し階層で物理的に分離する。利用者向け操作節を開発者見出しの配下にネストさせない。
- **AIフレンドリー設計**: 小さく責務の明確なファイル・意図の分かる見出し。README を縮小し、参照は 1 リンクで委譲する（深いネスト・重複を排除）。
- **UNIX哲学**: 「要約＋リンク」で組み合わせ可能にし、詳細は各 `docs/maintainer/*` に一本化して重複を持たない（DRY）。

（[.agent-skill-chain/source/spec/01_設計原則.md](../../../../../.agent-skill-chain/source/spec/01_設計原則.md) を参照し、上記を適用。CQRS・イベント駆動はドキュメント再編のため非該当。）

### 2.5 横断設計判断（ADR）

#### ADR-1: 分離先ファイルはルート新設 `CONTRIBUTING.md`

- **コンテキスト**: 開発者・自己拡張・メンテナ向け情報を集約する単一入口が必要。README から 1 リンクで到達でき、発見性が高い場所を選ぶ。
- **検討した選択肢**:
  - (A) ルート新設 `CONTRIBUTING.md`。
  - (B) `docs/maintainer/` 配下に入口ファイルを新設（例 `docs/maintainer/README.md` / `developer.md`）。
  - (C) 既存 `docs/maintainer/*` のいずれかへ折り込み（新設なし）。
- **決定**: (A) ルート `CONTRIBUTING.md`。
- **根拠**: `CONTRIBUTING.md` は GitHub 標準の貢献者入口（issue/PR 作成画面やリポジトリ UI から自動的に導線が張られ発見性が高い）。既存の詳細群は既に `docs/maintainer/`（RELEASE.md・adapters.md・apm-package.md・claude-hook-e2e.md）に存在し（evidence_source: existing_code、`ls docs/maintainer/` で実確認）、CONTRIBUTING はそれらへの入口として要約リンクで委譲すれば重複が生じない。(B)(C) はルートの発見性で劣り、(C) は複数詳細文書へ分散して単一入口の要件を満たさない。ルートに `CONTRIBUTING.md` は未存在（evidence_source: existing_code、`ls CONTRIBUTING.md` で不在確認）。
- **帰結**: README は `CONTRIBUTING.md` へ 1 リンク委譲。CONTRIBUTING は要約＋リンクに徹し、`docs/maintainer/*` を詳細正本として維持。CONTRIBUTING は本リポ開発用ドキュメントであり採用先へ配備される成果物ではない（`docs/maintainer/` と同じ位置づけ）。

#### ADR-2: 管理サブコマンドは README に残し、呼び出し形は `npx github:…` を維持

- **コンテキスト**: サブコマンド表・ピン留め・アンインストール・enforcement opt-in（現 §1 配下）は利用者向け操作だが、呼び出し例が `npx github:techbeansjp-free/AGENTS.md <cmd>` 形式であり、主推奨の `apm install` と表記が食い違う（00 §2.3 の設計論点）。
- **検討した選択肢**:
  - (A) `npx github:…` 形式を維持し、README の独立節「配備後の管理（CLI）」として残す。
  - (B) 例を `apm` 形式へ置換する。
  - (C) 両形式を併記する。
- **決定**: (A) `npx github:…` 形式を維持し、開発者見出しから切り離して独立トップレベル節へ再配置する。
- **根拠**: 管理サブコマンド（uninstall/doctor/enforce/upgrade/version 等）は `agents-md` CLI（`bin/agents-md.js`）が提供し、その配布経路は `npx github:…`（GitHub 直接参照）である。`apm install` は skills プリミティブと参照コンテキストを展開するのみで CLI バイナリ（bin）を導入しない（evidence_source: existing_code、README L63-69 の apm 展開内容に bin 生成の記載なし。CLI bin は L73 の `prepare` フックで npx 経路のみ生成）。したがって例を `apm` 形式に置換（B）すると事実に反し、併記（C）は「apm でも同コマンドが使える」という誤解を生む。呼び出し形は事実として `npx github:…` のままとし、「GitHub 直接参照（開発者・自己拡張向け）」という**読者を限定する枠付けだけ**を外す。
- **帰結**: 利用者は README の「配備後の管理（CLI）」節で uninstall/doctor/enforce/upgrade を `npx github:…` で実行できる。開発者向けの「GitHub 直接参照での**配備（init）**」導線のみ CONTRIBUTING へ移す（管理 CLI と初期配備 init を責務で切り分ける）。

> **補足（as-built・2026-07-13、本 issue のスコープ外の後続修正）**: 上記コンテキストが前提としていた「主推奨の `apm install`」は、別issue「apm/npx skill重複解消」の D1（apm から個々の skill 個別配布を外す設計変更）に伴うユーザー判断により、一般利用者向け推奨導線が `apm install` から `npx github:techbeansjp-free/AGENTS.md init` へ変更された（apm は skills のバンドル参照・複数ツール横断配布向けの副導線という位置づけに変わる）。ADR-2 本体の決定（管理サブコマンドの呼び出し形は `npx github:…` を維持し、`apm` 形式へ置換しない）はこの変更の影響を受けず、むしろ npx が推奨導線になったことで一貫性が増す。README §導入 lede・見出し・CONTRIBUTING.md 側の「開発者・自己拡張向け」という読者限定枠は、この補足に沿って README 側のみ本 issue のブランチ上で as-built 同期済み（CONTRIBUTING.md 自体の見出し文言の見直しは本 issue のスコープ外）。

#### ADR-3: 導入配下の導線見出しから数字接頭辞（0./1./2./3.）を除去

- **コンテキスト**: 現 README は導入配下を「### 0. apm」「### 1. GitHub 直接参照」「### 2. marketplace」「### 3. ローカル」と番号付けしている。§1 の削除で番号が不連続になる。
- **検討した選択肢**: (A) 数字を除去し内容名の見出しにする。(B) 残る 3 節を 0./1./2. へ振り直す。
- **決定**: (A) 数字接頭辞を除去。
- **根拠**: 番号は優先度・順序を誤って含意し、節の増減で振り直しが必要になる（変更容易性・可読性で劣る。spec/06 の可読性最優先）。これらの見出しを指す外部アンカー参照は存在しない（evidence_source: existing_code、`grep -rn "README.md#"` で §導入 以外の被参照なしを実測）。
- **帰結**: 「### apm 経由（バンドル参照・複数ツール横断配布向け）」「### Claude marketplace 経由」「### ローカル配備」。将来の導線増減でアンカー・番号の再調整が不要になる（見出し名は【as-built・2026-07-13】ADR-2 直後の補足を参照）。

#### ADR-4: 外部アンカー保全は §導入 見出し固定で担保し、参照元 2 ファイルは変更しない

- **コンテキスト**: `.agent-skill-chain/source/SETUP.md:191` と `docs/maintainer/claude-hook-e2e.md:14` が `../../README.md#導入プロジェクトへ配備するとき` を参照する（実測 2 箇所、evidence_source: existing_code）。再構成でこのアンカーを壊さないことが 00 成功基準・01 §5 の必須制約。
- **検討した選択肢**:
  - (A) `## 導入（プロジェクトへ配備するとき）` 見出しを一字も変えずアンカーを保全し、参照元 2 ファイルは変更しない。
  - (B) 参照元 2 ファイルのリンク先を `CONTRIBUTING.md` の GitHub 直接参照節へ張り替える。
- **決定**: (A)。§導入 見出しを固定してアンカーを保全し、SETUP.md・claude-hook-e2e.md は変更しない。
- **根拠**: (1) GitHub のアンカー生成規則で `## 導入（プロジェクトへ配備するとき）` は全角括弧が除去され `#導入プロジェクトへ配備するとき` を生成する。既存参照アンカーと一致しており（evidence_source: existing_code、見出し・参照双方を実読して一致確認）、見出しを変えない限り解決し続ける。(2) これら 2 参照は本リポ内前提のパッケージ相対リンク（`../../README.md`）であり、採用先では相対解決先が異なる既存事情がある。`CONTRIBUTING.md` は採用先へ配備されないため (B) は採用先文脈で解決先を悪化させうる。(3) §導入 lede に「開発者向け GitHub 直接参照配備は CONTRIBUTING.md 参照」の一文を置くため、§導入 に着地した読者は 1 ホップで移設先へ到達でき、参照元の文言変更なしに意味的整合を保てる。
- **帰結**: 編集対象は `README.md`・`CONTRIBUTING.md`（新規）・`docs/maintainer/RELEASE.md`（後方参照 2 行）の 3 ファイルに限定される。SETUP.md・claude-hook-e2e.md は不変。§導入 アンカーは恒久保全。
