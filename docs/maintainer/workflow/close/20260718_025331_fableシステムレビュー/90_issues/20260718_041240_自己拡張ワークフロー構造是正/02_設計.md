### G-3: ADR 参照の一意化

**問題の実体（実測）**: bare `ADR-1`〜`ADR-8` は「02_設計 ADR-n」形式で参照されるが、(1) どの issue の 02_設計 かが未明示、(2) 番号が issue 横断で衝突（`ADR-4`/`ADR-5`/`ADR-2` が別決定を指す実例）、(3) 参照先の大半が `close/`（deny）で読解不能、を実確認。一方 `ADR-132-2`・`ADR-137-1/137-4`・`ADR-S2-1/S2-3/S2-4` は既に **issue 名前空間付き**で一意（衝突なし）。

**方針（確定・2段構え）**:

1. **命名規約の確立と改称**: bare `ADR-n` を、既存先例（`ADR-<issue識別子>-<n>`）に倣い **issue 名前空間付き ID** へ改称する。識別子は当該決定を下した issue の GitHub Issue 番号または issue ディレクトリの短縮名を用いる（例: GitHub Issue 起票ゲートの決定なら `ADR-<起票ゲートissue番号>-5`）。実装時に各 bare 参照の定義元 issue を特定して付番する。**定義元が close/ で特定困難な場合は下記2を適用**。
2. **close/ 依存の切断（load-bearing の解消）**: 本ファイル自身の方針（行375「close/ 配下への参照は補足情報に限定し、読めなくても本文の理解・運用に支障が出ないこと」）を全 ADR 引用に適用する。**各 ADR 引用は本文で結論を言い切った後の括弧内トレーラ**（例: 行36「自動推測…は禁止する（02_設計 ADR-2）」）であり、既に本文だけで運用可能な構造になっている。この性質を保証するため、実装時に各引用箇所で「引用を削除しても本文の規範が成立するか」を確認し、成立するもの（大半）は **`（詳細な検討経緯は <一意ID> を参照）`** の補足参照に統一、成立しないもの（結論が引用先の値に依存）があれば**本文へ結論を1行インライン化**してから参照を補足化する。

**確定理由**: 分割・機構変更を伴わず本ファイル内で完結。既存の名前空間付き ADR という先例に合わせるため一貫性が高く、close/ が読めない現実にも耐える（本文が自己完結）。

**要ユーザー確認ではない**が、実装時の**申し送り**: 各 bare ADR-n の定義元 issue 番号の確定には、起票ゲート／ブランチ・PR紐づけを設計した元 issue の特定作業が要る（close/ 内のため、git log や 90_issues.md 等の追跡側メタ情報から辿る）。
