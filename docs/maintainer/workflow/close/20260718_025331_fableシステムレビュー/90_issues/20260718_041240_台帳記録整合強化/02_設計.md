## 0. 全体像と設計の骨子

本パッケージの中核テーマは **契約層（「必須」「絶対」）と機械強制層（実制約・実検査）の乖離是正**（総括D）である。19 件は次の 4 系統に整理できる。

1. **entry_hash チェーンの実効化**（D-1, E-2, E-3）— 改ざん検知の骨組みを「宣言」から「検証可能」へ。**破壊的マイグレーションを伴う最重要論点**。
2. **正本一元化・矛盾記述の解消**（D-2, D-3, D-4, D-7, D-13, D-18 の一部）— schema.sql / schema.md を単一正本にし、CONTRACT・README・写しの食い違いを参照へ縮退。
3. **ポリシー間の板挟み解消**（D-9, D-10, D-14, D-16）— レビュー規約・ノイズ規約・コメント規約の相互矛盾／幽霊参照／ドッグフーディング漏れの是正。
4. **儀式総量の二層化・スクリプト堅牢化**（D-5, D-6, D-15, E-10, E-14, E-20）— 機械強制/推奨の明示化とスクリプトのデッドコード・防御的エスケープ・DBパス宣言の是正。

**所有権の範囲**: 本パッケージが変更するのは 00 が列挙する 15 ファイルのみ（下表「対象ファイル」参照）。検証側の実装（`enforcement/ci/audit.sh` のチェーン検証チェック、doctor/verify スクリプト新設、`scripts/export-ndjson.sh` の全カラム出力）は**本パッケージの所有物ではない**ため、本書では「算出側の正本（アルゴリズム・バージョン規約）」のみ確定し、検証側は §5 のクロスパッケージ依存として明記する。

## 2. 「要ユーザー確認」論点

要設計判断 8 件のうち 4 件（**D-6, E-2, E-3, E-10**）に、推奨案は提示済みだが人間の最終確認を要する論点が残る。残り 4 件（**D-4, D-5, D-15, E-20**）は本設計で確定した（推奨案を採用、下記に非採用案も明記）。

### 論点1: E-2 / E-3 — entry_hash 破壊的マイグレーションの移行方針【推奨: 案B（バージョン列・新規行のみ）】

- **論点**: 生成式変更は既存 workflow.db のチェーン全行を無効化する。既存行をどう扱うか。
- **推奨（案B）**: `hash_version` 列を追加し、**既存行は v1（旧 14 フィールド式）のまま検証対象外に近い扱い、新規行のみ v2** を適用（詳細 §3）。切替時点以降が改ざん耐性チェーンになる。
- **非採用（案A: 全行再計算）**: 追記専用台帳に UPDATE を要し、原本ハッシュを消去（移行と攻撃が区別不能）、環境ごとに非追跡な DB の一斉再計算は協調不能。
- **確認事項**: (1) 破壊的（既存チェーンを遡及的には強化しない）点の承認、(2) v2 の対象フィールドを「entry_hash 以外の全カラム＋prev_hash」とする範囲の承認、(3) §5 のクロスパッケージ companion 変更（export-ndjson 全カラム化・検証スクリプト新設）を同一リリースで揃える方針の承認。

### 論点2: E-10 — DBパス上書きのハードニング要否【推奨: ドキュメント修正のみ、機能制限なし】

- **論点**: `WORKFLOW_DIR=/tmp/x` 等で canonical DB を回避し「記録済み」と偽れる（§3.2 セキュリティ）。resolve-wf-db.sh の明示ヒント分岐（38 行）は sentinel ガードを通らない。
- **推奨**: 本パッケージでは**宣言文の正確化のみ**（override は worktree 横断のため維持）。
- **確認事項**: 明示ヒント分岐にも sentinel 検査を課す／enforcement 側で「書込が canonical DB に着地したか」を検証する、というハードニングを**別パッケージ（enforcement）で行うか**。推奨は「本パッケージは宣言是正に留め、ハードニングは enforcement 側 follow-up」。

### 論点3: D-6 — dod_met 自己申告への根拠パス必須化の要否【推奨: 正直な明記のみ、新規ハード制約は追加しない】

- **論点**: dod_met=1 に根拠パスを必須化し audit で実在検査するか。
- **推奨**: 全 command 一律のハード制約は追加しない（requirement-discovery 等・既存行を壊す）。「audit は明記の有無のみ検査」と正直に記述し、既存の command 別必須（implement=changed_files, verify=review_path/parent）で実質担保。
- **確認事項**: implement-feature/verify-and-close に限り「dod_met=1 なら changed_files_json/review_path 必須」を明文化する（現状ほぼ既成事実）に留めるか、より踏み込むか。

### 参考: 本設計で確定した要設計判断項目（非採用案の明記）

- **D-4**: ドキュメント修正のみで確定（DB 制約・監査強化は不要。正規経路は既に素の INSERT）。
- **D-5**: CHECK 維持＋記述再定義で確定（列削除・複数値化は非採用。不変条件保護を壊すため）。

## 3. entry_hash v2 設計（E-2 / E-3 / D-1 の技術詳細）

### 3.1 アルゴリズム

- **v2 の対象**: `workflow_log` の **entry_hash を除く全カラム**（entry_id, parent_entry_id, document_id, ts_utc, created_at, actor_role, delegated_by_role, command, issue_id, review_id, issue_path, review_path, document_path, changed_files_json, summary, dod_met, model_tier, tier_rationale, tier_exception, **prev_hash**）を schema.sql のカラム順で対象とする。
- **枠付け（E-3 解消）**: 各フィールドを **`LC_ALL=C` 下のバイト長プレフィックス**付きで連結する（例: 各フィールド `f` を `printf '%s:%s' "${#f}" "$f"` として連結）。長さプレフィックスにより、値に `|`・改行・制御文字が含まれても連結文字列は**単射**となり、フィールド境界の衝突（E-3）が原理的に発生しない。連結結果を `sha256sum` の先頭語とする。
- **NULL 正規化**: DB の NULL 値は**空文字列**として枠付けする（ラッパーが空文字から NULLIF で NULL 化するのと逆写像。検証側も同一規則を用いる）。
- **v1 は不変**: 既存 `gen_entry_hash`（14 フィールド `|` 連結）は**1 文字も変更しない**（既存行の false positive 回避）。v2 は新関数 `gen_entry_hash_v2` として追加する。

### 3.2 スキーマ変更（`hash_version` 列）

- schema.sql に `hash_version INTEGER NULL` を追加（NULL=レガシー v1、2=v2）。**DEFAULT は付けず、ラッパーが新規行に必ず `2` を明示 INSERT** する（新規 DB と移行 DB で挙動を一致させ、DEFAULT 分岐差を排除）。
- **ensure_column による移行整合**: 既存 DB へは ensure_column が `hash_version` を `TEXT NULL`（≒INTEGER 親和）で追加、旧行は NULL のまま＝v1 判定。
- **再作成 heredoc の追随（自己レビューで検出）**: write-workflow-log.sh の review-docs/create-pr-review-issue 用テーブル再作成 heredoc（350-382 の CREATE、383 の INSERT ... SELECT）に **`hash_version` を必ず追加**する。追加漏れは再作成時に列消失を招く。

### 3.3 チェーン意味論と改ざん耐性

- v2 行は prev_hash をハッシュ入力に含むため、**行の削除・並べ替え・prev_hash 書換のいずれも entry_hash 再計算なしには検証を通過できない**（E-2 の攻撃シナリオを封鎖）。
- 境界行（最初の v2 行）の prev_hash は最後の v1 行の entry_hash を指すため、切替後に v1 末尾行を削除すると境界行の prev_hash 検証が壊れる。
- **正直な劣化境界の明記**: v1 区間の内部行は個別（14 フィールド）検証は可能だが**チェーン保護されない**（削除・並べ替えを個別ハッシュだけでは検知不能）。schema.md にこの劣化境界を明記する（D-1 の「誤った安心感」是正）。

### 3.4 gen-entry-hash.sh ヘッダの追随
