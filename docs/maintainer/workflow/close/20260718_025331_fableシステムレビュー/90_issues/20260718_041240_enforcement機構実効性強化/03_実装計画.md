## 2. 指摘ID別 実装内容

### C-1（high・ユーザー承認済み）enforcement 正本ファイル自体の保護 × ドッグフーディング両立

- `PreToolUse.sh` に **R1B** を新設。対象: `.agent-skill-chain/source/enforcement/**`・`.agent-skill-chain/project/orchestrator-allowlist.txt`・`.agent-skill-chain/project/settings.enforce.json`・`.scribe-nonce`（basename 一致）への `Edit`/`Write` を全 ROLE で block。
- `ASC_ENFORCEMENT_SELF_DEV`（非空かつ `"0"` 以外）設定時のみ解除し、`_wt_record_bypass_warn` と同型の `[enforcement:warn]` を stderr へ出力（監査痕跡）。
- `audit.sh` に **#42 `check_enforcement_diff_has_evidence`** を新設。対象差分が上記パスに触れる場合、`workflow_log` に `implement-feature`/`design-feature`/`verify-and-close`/`review-docs`/`create-pr-review-issue` のいずれかの記録が1件以上あることを要求。
- `PROTECTED_PATHS.txt` に上記4パスを参照用リストとして追記。
- `README.md`・`DESIGN.md` に設計意図・残余リスク受容根拠を記載。

### C-2（high）audit ゲートの env 無効化耐性

- `audit.sh` に `AUDIT_STRICT`（既定 `0`）を追加。`1`/`true`/`yes`/`on` 系の値で strict モードに入り、`GITHUB_ISSUE_GATE_ENABLED`・`BRANCH_LINK_GATE_ENABLED`・`PR_LINK_GATE_ENABLED`・`MODEL_TIER_GATE_ENABLED`・`MAIN_WORK_GATE_TOLERANCE_SECONDS`・`WORKFLOW_DIRS` の指定を無視して既定値を強制し、無視した事実を `[audit] WARN:` として stderr へ出力。
- `AUDIT_GIT_RANGE` は強制対象から除外（CI が正当に渡す差分範囲の入力のため）。
- `ci/pre-push.example` は `AUDIT_STRICT=1` を既定化。

### C-3（medium）scribe nonce の防御水準の正直化

- `README.md` の C-4b 節に「同一 UID で動作する AI プロセス自身が `.scribe-nonce` を読むこと自体は env 掌握を要さない通常の読み取りである」旨を明記し、DB系監査の信頼の主線を外部 append-only 証跡（署名付き NDJSON・D-1/E-2/E-3 パッケージ所有）へ委ねる設計主線を明文化。nonce の暗号強度は現状維持。

### C-4（medium）「物理強制」表記 × hook 実在の是正

- `DESIGN.md` の Layer1 表から「フェーズ飛ばしの Write 拒否」「scribe 未実行の次 Task 拒否」を除外し、CI/audit のみの検知（hook 未実装・CI では SKIP されうる）である旨を注記として追加。
- `README.md` の該当箇所（「矯正するもの」節）も同様に是正。

### C-5（medium）jq 非搭載時の agent_id fail-safe

- `PreToolUse.sh` の `json_get()` で、jq 非搭載時の `agent_id` フォールバック抽出を廃止し、常に空文字を返すよう変更（`IS_SUBAGENT=0` に固定）。他キー（tool_name/command/file_path）のフォールバックは変更なし。

### C-6（medium）worker の bash -c 迂回検知

- `PreToolUse.sh` の `is_sqlite3_invocation()` に、`bash|sh|zsh|dash|ksh -c "sqlite3 ..."` を python 分岐と対称に検知するロジックを追加。

### C-7（low）R1 carve-out の `..` トラバーサル除外

- `PreToolUse.sh` の R1 で、対象パスが `..` を含みかつ `.agent-skill-chain/runtime/` を参照する場合、carve-out（.gitignore 厳密一致／templates／doc）の判定に進ませず通常 block へ落とすガードを追加。

### C-8（low）check_25 の検出限界の正直化

- `audit.sh` の `check_25_main_did_real_work` コメントおよび `README.md` #25 該当箇所に、「対象差分と無関係な別 issue の証跡でも許容窓内なら PASS しうる」限界を明記。突合実装は費用対効果により見送り（可逆的判断）。

### C-9（low）audit.sh の `set -e` → `set +e`

- `audit.sh` 冒頭の `set -e` を `set +e` に変更（1行変更）。合否判定は既存の `EXIT_CODE` 集約方式に変更なく依存。

## テスト観点

- **構文チェック**: 変更した全シェルスクリプト（`PreToolUse.sh`・`PostToolUse.sh`・`audit.sh`・`pre-push.example`・`worktree_record_guard.sh`）を `bash -n` で検証し、全て構文エラーなし。
- **C-1（R1B）**: stdin JSON を模擬入力し、(a) enforcement 正本ファイルへの worker Edit が `ASC_ENFORCEMENT_SELF_DEV` 未設定時に exit 2 で block されること、(b) 設定時に `[enforcement:warn]` を出力し exit 0 で許可されること、(c) `orchestrator-allowlist.txt`・`.scribe-nonce` も同様に block されること、(d) 無関係な `src/foo.ts` への編集は影響を受けないこと、を実機相当のフック呼び出しで確認済み。
- **C-1（audit #42）**: 一時 git リポジトリ＋`workflow.db` を用意し、(a) enforcement 正本を変更したコミットに証跡が無い場合に FAIL すること、(b) `implement-feature` ログを1件追加すると PASS することを確認済み。
- **C-2（AUDIT_STRICT）**: `GITHUB_ISSUE_GATE_ENABLED=false` を設定した状態で、(a) `AUDIT_STRICT` 未設定時は無効化が素通りする（後方互換）こと、(b) `AUDIT_STRICT=1` 設定時は無視されて `[audit] WARN:` が出力されることを確認済み（`MAIN_WORK_GATE_TOLERANCE_SECONDS`・`WORKFLOW_DIRS` も同様に確認）。
- **C-5（jq fail-safe）**: `jq` を含まない PATH で、`agent_id` を含む JSON を渡した orchestrator ロールの Edit が、C-5適用前なら worker 扱いで許可されるはずのところ、適用後は main 扱いとして block されることを確認。jq を含む PATH（jq 相当のスタブで代替）では従来どおり worker として許可されることも確認し、他キーの fallback ロジックに回帰がないことを確認済み。
- **C-6（bash -c 検知）**: `is_sqlite3_invocation` を単体抽出し、`bash -c "sqlite3 foo.db"`・`sh -c "sqlite3 foo.db"`・`zsh -c "sqlite3 foo.db"` が block、`bash -c "echo sqlite3 is neat"`（言及のみ）・`grep sqlite3 doc.md`（既存の非対象ケース）が allow のままであることをテーブル駆動でテストし全件 PASS。
- **C-7（`..` 除外）**: `.agent-skill-chain/runtime/templates/../../some_other_issue/secret.md` のような traversal パスへの Edit が block されること、通常の templates carve-out・doc carve-out（`..` を含まない）は従来どおり allow されることを実機相当のフック呼び出しで確認済み。
- **C-9（set +e）**: 変更後の `audit.sh` を実データ（git リポジトリ・workflow.db 有り/無し双方）に対して実行し、全チェックが実行され最終的に `Audit passed.`／FAIL が既存仕様どおり出力され、途中終了（早期 skip）が発生しないことを確認済み。
- **回帰確認**: 上記いずれのテストでも、既存の R1〜R9・#1〜#41 の判定が意図せず変化していないことを個別ケースで確認済み（特に R2 の orchestrator block・doc/templates carve-out の allow 経路）。
