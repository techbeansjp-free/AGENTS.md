## 2. 採用（要設計判断）6件の詳細と選択理由

### C-1（high・要ユーザー確認）強制正本ファイル自体の保護 × ドッグフーディング両立

**論点**: `source/enforcement/**` 等の強制正本を全 ROLE block すると、本リポ自身のドッグフーディング開発（worker が enforcement を編集する正規作業）と衝突する。消費者配備と本リポ開発をどう区別するか。

**選択肢**:
- (A) 消費者では全 ROLE hard block、本リポ開発は env オプトアウトで解除＋audit 証跡必須。【推奨】
- (B) worker は常時許可し、CI audit の証跡要求のみで担保。
- (C) 一律全 ROLE block（脱出弁なし）。

**推奨: (A)**。理由:
- (B) は消費者 runtime の自己弱体化穴（worker が `source/enforcement/PreToolUse.sh` を自由に書換）を**塞げない**。CI は A-2 のとおり非ブロッキング/SKIP が常態のため、runtime で止めない限り high 経路が残る。C-1 の核心（消費者環境で強制を無効化できる）を解消できない。
- (C) はドッグフーディング開発を不可能にし、00_要求定義 §3.3 の互換性要件に反する。
- (A) は**消費者環境**（`ASC_ENFORCEMENT_SELF_DEV` 未設定）では全 ROLE hard block となり穴を塞ぎ、**本リポ**（env 設定）では worker 編集を許可しつつ、既存 `ASC_WORKTREE_CLOSE_BYPASS` と同型の stderr 警告で監査痕跡を残す。

**具体案**:
1. **hook 層（`PreToolUse.sh`・R1 と同レイヤーの path 軸ガードを追加）**: 対象 `TOOL ∈ {Edit,Write}` かつ `PATH_TARGET` が次のいずれかに前方一致/実体一致するとき block。
   - `.../.agent-skill-chain/source/enforcement/`（配下全体）
   - `.../.agent-skill-chain/project/orchestrator-allowlist.txt`
   - `.../.agent-skill-chain/project/settings.enforce.json`
   - `.../.scribe-nonce`
   - ただし `ASC_ENFORCEMENT_SELF_DEV` が非空かつ `"0"` 以外なら block を解除し、`_wt_record_bypass_warn` と同型の `[enforcement:warn]` を stderr へ出す（監査痕跡）。
   - **実装制約**: 既存 R1/R2 と同じく、解除時も no-op フォールスルーで後続判定を妨げない。ただし本ガードは path 軸・全 ROLE（R1 と同性格）であり、R2（role 軸）とは独立。block は `block()` 経由で即 `exit 2`。
   - **allowlist は AI が編集すべきでない**: `orchestrator-allowlist.txt` は「消費先ユーザーが手で編集する opt-in 資産」であり、**AI（worker）がツールで追記すること自体が C-1 の攻撃シナリオ**。フック は AI のツール呼び出しのみを止め、人間の直接編集（フック外）は妨げないため、worker block と人間カスタマイズは両立する。
2. **audit 層（`ci/audit.sh` に新 check 追加）**: 差分（`GIT_RANGE`）が `source/enforcement/**` または allowlist/settings/nonce に触れる場合、対応する `workflow_log` 証跡（implement-feature/design-feature/verify-and-close 等）の存在を要求し、無ければ FAIL（委譲・レビュー証跡の必須化）。本リポで env オプトアウトを使って編集しても、audit で証跡が突合され追跡可能になる。
3. **文書（`README.md`・`DESIGN.md`）**: 強制正本の保護方針・env オプトアウトの意味・残余リスク（後述）を明記。`PROTECTED_PATHS.txt` に強制正本パス群を「参照用リスト」として追記（現状の docs/src 等と同様、参照用途）。

**残余リスク（受容・正直化）**: `ASC_ENFORCEMENT_SELF_DEV` は env であり、env 空間を掌握した相手には偽装可能。これは既存 `ASC_WORKTREE_CLOSE_BYPASS`・scribe nonce と**同一の脅威モデル**（env 掌握相手は対象外、最終保証は CI audit＋外部証跡）であり、新たなリスククラスを増やさない。現状比の改善は「消費者環境で 0 → hard block」「本リポで無痕跡 → env 痕跡＋audit 証跡必須」。

**他パッケージ連携（言及のみ・本 issue 対象外）**: 配備後に実際に走るのは `.claude/hooks/PreToolUse.sh`（コピー）であり、`.claude/hooks/**` と `.claude/settings.json`（enforce on/off 配線）も同等に機微だが、これらは config/setup 層（本パッケージ非所有）のため、保護対象化は別 issue で扱う（本設計では正本 `source/enforcement/**` 保護に限定）。

**→ 要ユーザー確認**: 「識別方式に env オプトアウト（`ASC_ENFORCEMENT_SELF_DEV`）を採用し、その forgeable-env 残余リスクを既存バイパス群と同水準で受容する」点と、「本リポ開発時は当該 env を設定する運用に変える」点。推奨案は確定済みだが、本リポ自身の開発フローと残余リスク受容に関わるため最終確認を推奨。

### C-3（medium）scribe nonce の防御水準

**論点**: 現状維持＋限界記述強化か、署名付き NDJSON 等への格上げか。

**推奨: 現状維持（nonce 暗号強度据え置き）＋文書の正直化・信頼アンカーの外部証跡への格上げ**。理由:
- 同一 UID で動く AI は 0600 ファイルを普通に読めるため、nonce のパーミッション依存は原理的限界であり、フック層でこれ以上強化しても same-UID 相手には無意味（バグでなく本質）。
- 既に README C-4b・DESIGN ADR-2 が限界を記述済み。本 issue では「nonce は素朴な手動 export の遮断に限定」「DB系監査の信頼は外部 append-only 証跡（署名付き NDJSON）が主線」を設計主線として明確化する（文書のみ）。
- **署名付き NDJSON エクスポート実体の実装は本パッケージ外**（`gen_entry_hash`/`entry_hash`/`prev_hash`/NDJSON export は領域D-1・E-2・E-3 の所有＝`scribe/`・`ledger/`・`scripts/`）。本 issue では当該外部証跡へ**依存・参照する形に文書を整える**にとどめ、実装は D/E パッケージへ申し送る。

**→ 確定**（本パッケージ分は文書格上げのみ。外部証跡実装は D/E への依存として明記）。

### C-4（medium）「物理強制」表記 × hook 実在

**論点**: 表現を実態に格下げするか、hook を新規実装するか。

**推奨: 表現の格下げ（hook 新規実装しない）**。理由:
- `DESIGN.md` Layer1 表の「フェーズ飛ばしの Write 拒否」は、R1 が memo/DB 保護に絞り 00〜04 を phase 非依存で allow する**意図的設計**と衝突する。ここに phase 連動 block を戻すのは設計思想の後退。
- 「書記未実行の次 Task 拒否」は cross-Task 状態を PreToolUse が信頼できる形で追跡できず、フック層では脆い。実効は CI audit #5/#29 が担うが、それらは CI で SKIP されうる。
- したがって当該2項目を Layer1（物理強制）から「CI/audit のみ・CI では SKIP されうる」注記へ移す正直化が最善。既存の「**完全物理強制ではない**」注記（DESIGN.md L16）と一貫。

**→ 確定**。

### C-6（medium）worker の bash -c 迂回 / R9 バイパス痕跡

**論点**: 追加ハードニングの費用対効果。

**推奨: `bash -c` 経由 sqlite3 の best-effort 検知を追加。worker Bash 全面制限はしない。R9 バイパス痕跡は既実装につき追加不要**。理由:
- `is_sqlite3_invocation` は現状 `bash -c "sqlite3 ..."` の第1トークンが `bash` のため素通り（既存 `python -c "import sqlite3"` は検知済みで非対称）。`bash|sh|zsh|dash|ksh -c` の -c 引数に sqlite3 のコマンド名起動が現れるパターンを既存 python 分岐と対称に追加すれば、最も分かりやすい迂回を低コストで塞げる。
- worker の Bash 無条件 allow は「worker が実作業をする」意図的設計であり、全面サンドボックス化は非現実的かつ正規作業を破壊するため見送り。
- R9 バイパス（`ASC_WORKTREE_CLOSE_BYPASS`）は `lib/worktree_record_guard.sh` の `_wt_record_bypass_warn` で**既に stderr 警告（監査痕跡）を出している**（fable 指摘は現状とややズレ）。追加不要。
- 限界（静的シェル解析では alias/関数/スクリプト内 import 等を完全には防げない）は既存コメントどおり正直に残す（best-effort 明示）。

**→ 確定**（部分採用：bash -c 検知のみ追加、他は既実装/意図的設計として据え置き）。

### C-8（low）check_25 の許容窓・突合

**論点**: 変更ファイル・issue との突合強化の要否。

**推奨: 突合実装は見送り（再判定）。検出限界を README #25 へ正直に明記するにとどめる**。理由:
- low 深刻度、48h 許容窓は意図的選択済み、command 種別絞り込みは既存（fable の「対応を一切問わない」はやや不正確）。
- 変更ファイル群 ↔ `changed_files_json`/`issue_path` のファイル単位突合は、実装コスト・false-FAIL リスク（現状は fail-open で可用性優先）が high で、low の便益に見合わない。
- 現行 README #25 行は既に「変更者同一性を識別しない」を明記済み。加えて「対象差分と無関係な issue の証跡でも許容窓内なら PASS しうる」限界を明記して honest-doc を完成させる。

**→ 確定**（採用＝honest-doc、突合実装は費用対効果により見送りへ再判定。低深刻度の判断であり、より強い検出を望む場合はユーザー裁量で覆せる可逆判断）。

### C-9（low）audit.sh 全体 set -e

**論点**: `set +e`＋EXIT_CODE 集約への切替の要否。

**推奨: `set -e` → `set +e`（1行変更）**。理由:
- 合否は全 check が `EXIT_CODE=1` を設定し末尾 `exit $EXIT_CODE` で確定する設計であり、set -e は合否に一切寄与しない（非 load-bearing）。set -e は「途中 check の想定外非0で以降が飛ぶ」ハザードのみを生む。
- 前段（GIT_RANGE 無害化・ディレクトリ設定等）も明示条件分岐・フォールバックで書かれ set -e 非依存を静的確認済み（`exit 1` は末尾の `exit $EXIT_CODE` 以外に存在しない）。
- check 定義と呼び出しがファイル全体で交互配置のため単一「dispatch 節」で括れず、グローバル `set +e` が最もクリーン。fable 改善案に一致。

**代替（不採用）**: 各 check 呼び出しを `check_x || true` にする案も set -e を関数内まで抑止でき（§4 で実測確認済み）有効だが、約40箇所の変更で冗長。`set +e` 一括が優る。

**→ 確定**。

## 4. 自己レビュー実施記録（review-docs 相当・指摘0件まで反復）

**観点**: シェル変更提案のロジックが `set -e`/`set +e`・no-op フォールスルー・fail-safe 方向・既存挙動非破壊の各点で正しく機能するかを机上＋最小実測で検証。

### 反復1（初回検出 → 是正）

- **指摘1（C-9 の set -e 抑止範囲）**: 代替案「`check_x || true`」が関数**内部**の非0まで抑止するか要確認だった。→ 実測で検証（下記）。関数が `|| true` 文脈で呼ばれると set -e は関数本体まで抑止されることを確認。設計本文へ「§4 で実測確認済み」と反映。**是正済み**。
  - 実測: `bash -c 'set -e; f(){ false; echo A; }; f || true; echo B'` → `A`（関数内 false 後）と `B` が両方出力。set -e が関数内で抑止されることを確認。
- **指摘2（C-2 の AUDIT_STRICT が AUDIT_GIT_RANGE を潰す誤り）**: 当初「strict は無効化系 env を全て既定へ強制」と広く書いたが、`AUDIT_GIT_RANGE` は CI が正当に渡す**入力**であり disable トグルではない。強制対象に含めると CI の差分範囲指定を壊す。→ strict の強制対象を「`*_GATE_ENABLED`・`MAIN_WORK_GATE_TOLERANCE_SECONDS`・`WORKFLOW_DIRS`（scan-nothing 化の防止）」に限定し、`AUDIT_GIT_RANGE` は据え置く（既に注入対策サニタイズ済み）と明確化。**是正済み**（表・C-2 詳細へ反映）。
