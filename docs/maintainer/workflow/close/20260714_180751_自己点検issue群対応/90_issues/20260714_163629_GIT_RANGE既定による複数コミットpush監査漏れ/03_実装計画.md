# 実装計画書: GIT_RANGE 既定 `HEAD~1..HEAD` により多コミット push の監査漏れ

**プロジェクト名**: GIT_RANGE 既定 `HEAD~1..HEAD` により多コミット push の監査漏れ
**作成日**: 2026年07月14日
**最終更新**: 2026年07月14日

---

## 1. 実装概要

### 1.1 実装方針（必須）

`audit.yml` に push イベント専用の「Resolve GIT_RANGE」ステップを追加して `before`/`after` から `AUDIT_GIT_RANGE` を組み立て、`audit.sh` には全ゼロ SHA を含む range を無害化する防御チェックを追加する。checkout は `fetch-depth: 0` にする。

### 1.2 実装順序（必須: 1 件以上）

1. `audit.sh` の GIT_RANGE 解決部に全ゼロ SHA フォールバックを追加（タスク 1）。
2. `audit.yml` に Resolve GIT_RANGE ステップを追加し、`fetch-depth` を `0` に変更（タスク 2）。

---

## 2. タスク分解

### 2.1 タスク 1: audit.sh の GIT_RANGE 全ゼロ SHA 防御

#### 2.1.1 概要（必須）

`AUDIT_GIT_RANGE` に全ゼロ SHA（新規ブランチ作成時の push before 等）が含まれる場合、既存の不正 range 無害化ロジックと同様に既定 `HEAD~1..HEAD` へフォールバックさせる。

#### 2.1.2 実装内容（必須: 1 件以上）

- `.agent-skill-chain/source/enforcement/ci/audit.sh` の `GIT_RANGE` 決定直後に、`^0{40}(\.\.\.?.*)?$` または `\.\.\.?0{40}$` にマッチする場合に WARN を出して `HEAD~1..HEAD` へ差し替える処理を追加。

#### 2.1.3 テスト観点（必須）

##### 単体（本タスクの具体ケース・必須 1 件以上）

- `AUDIT_GIT_RANGE="0000000000000000000000000000000000000000..<after>"` を渡すと WARN ログを出力し `GIT_RANGE` が `HEAD~1..HEAD` に置き換わる。
- 通常の `<before>..<after>`（有効な SHA 同士）は既存どおり素通りする（回帰なし）。
- 既存の不正 range 無害化（`--option` 注入等）の挙動が変わらない（回帰なし）。

##### 結合/API（本タスクの具体ケース・該当時は必須 1 件以上）

- tmp git リポジトリで 3 コミットを作成し、`AUDIT_GIT_RANGE=<commit1>..<commit3>` で `audit.sh` を実行し、`file2` と `file3` の両方が差分検出対象になることを確認する（本 03 §テスト観点 に実施結果を記載）。

##### E2E/受け入れ（本タスクの具体ケース・未達時は理由記載）

- 実 GitHub Actions 上での push イベント実行による確認は、本 PR マージ後の実 push で確認する（ローカル実行環境では GitHub Actions のイベントペイロードを再現できないため未達。tmp 隔離環境でのシェルスクリプト直接実行で代替検証済み）。

##### バリデーション（該当する場合の具体ケース）

- 全ゼロ SHA を「起点」「終点」いずれに含む場合も検知すること（`before` が全ゼロになるケースが主だが、対称性のため両方チェックする）。

#### 2.1.4 単体テスト仕様（BDD）（必須）

```gherkin
Feature: audit.sh の GIT_RANGE 全ゼロ SHA 防御
  Scenario: AUDIT_GIT_RANGE の起点が全ゼロ SHA
    Given AUDIT_GIT_RANGE="0000000000000000000000000000000000000000..<有効なSHA>"
    When audit.sh を実行する
    Then WARN ログ「GIT_RANGE の起点/終点が全ゼロ SHA...」が標準エラーに出力される
    And GIT_RANGE は "HEAD~1..HEAD" に置き換わる
    And audit.sh はエラー終了しない
```

**テストコード例（bash・実施結果を記録）**:

```bash
# Given: 全ゼロ SHA を起点に持つ AUDIT_GIT_RANGE
export AUDIT_GIT_RANGE="0000000000000000000000000000000000000000..$C3"
# When: audit.sh を実行する
bash audit.sh . 2>&1 | grep -i "GIT_RANGE"
# Then: WARN ログが出力される（フォールバック確認）
```

実施結果（tmp 隔離環境）:
```
[audit] WARN: GIT_RANGE の起点/終点が全ゼロ SHA (新規ブランチ作成時等) のため既定 (HEAD~1..HEAD) にフォールバックします: '0000000000000000000000000000000000000000..<C3>'
```
（実行日: 2026-07-14。tmp git リポジトリで実施、詳細は 04_review.md §3.1 参照）

- なし（タスク 2 と独立に実装可能）。

#### 2.1.6 見積もり

### 2.2 タスク 2: audit.yml の Resolve GIT_RANGE ステップ追加・fetch-depth 変更

#### 2.1.1 概要（必須）

push イベント時に `github.event.before`/`github.event.after` から `AUDIT_GIT_RANGE` を組み立てて `GITHUB_ENV` に設定するステップを追加し、`fetch-depth` を `0` に変更する。

#### 2.1.2 実装内容（必須: 1 件以上）

- `.agent-skill-chain/runtime/templates/github/workflows/audit.yml` に `if: github.event_name == 'push'` の「Resolve GIT_RANGE for push events」ステップを追加。
- `actions/checkout@v4` の `fetch-depth` を `2` から `0` に変更。
- `before` が空/全ゼロの場合は `AUDIT_GIT_RANGE` を設定せず（既定にフォールバック）、ログのみ出力する。

#### 2.1.3 テスト観点（必須）

##### 単体（本タスクの具体ケース・必須 1 件以上）

- YAML として構文的に妥当であること（`python3 -c "import yaml; yaml.safe_load(...)"` で検証済み）。
- `before` が空/全ゼロのときの分岐ロジック（bash の `[[ -z ]] || [[ =~ ^0+$ ]]`）を tmp シェルで単体検証する。

##### 結合/API（本タスクの具体ケース・該当時は必須 1 件以上）

- 該当なし（GitHub Actions ランナー上でのみ実行されるステップであり、ローカルでの結合実行は不可）。

##### E2E/受け入れ（本タスクの具体ケース・未達時は理由記載）

- 実 push イベントでの動作確認は本 PR マージ後の実運用 push で確認する（未達理由: ローカル環境では `github.event.before/after` を含む実際の push イベントペイロードを再現できないため）。

##### バリデーション（該当する場合の具体ケース）

- 該当なし。

#### 2.1.4 単体テスト仕様（BDD）（必須）

```gherkin
Feature: audit.yml の Resolve GIT_RANGE ステップ
  Scenario: before が有効な SHA
    Given github.event.before="<C1>", github.event.after="<C3>"
    When Resolve GIT_RANGE ステップが実行される
    Then GITHUB_ENV に AUDIT_GIT_RANGE="<C1>..<C3>" が書き込まれる

  Scenario: before が全ゼロ SHA
    Given github.event.before="0000000000000000000000000000000000000000"
    When Resolve GIT_RANGE ステップが実行される
    Then GITHUB_ENV への書き込みは行われない（既定 GIT_RANGE にフォールバック）
```

**テストコード例（bash・分岐ロジックの単体検証）**:

```bash
# Given: before が空文字列（新規ブランチ相当）
PUSH_BEFORE=""
PUSH_AFTER="deadbeef"
# When: 分岐ロジックを評価する
if [[ -z "$PUSH_BEFORE" ]] || [[ "$PUSH_BEFORE" =~ ^0+$ ]]; then
  echo "fallback"  # Then: フォールバック分岐に入ることを確認
else
  echo "AUDIT_GIT_RANGE=${PUSH_BEFORE}..${PUSH_AFTER}"
fi
```

実施結果: `fallback` が出力されることを確認済み（tmp シェルで実施）。

#### 2.1.5 依存関係

- なし（タスク 1 と独立に実装可能。ただしテンプレートが設定する `AUDIT_GIT_RANGE` を audit.sh が正しく解釈することはタスク 1 の防御ロジックと合わせて確認する）。

## テスト観点

本実装の中心的なテスト観点は「(a) 全ゼロ SHA を含む GIT_RANGE で audit.sh がクラッシュせず既定にフォールバックすること」「(b) 有効な before..after 範囲では複数コミットの差分が正しく検出されること」「(c) PR イベント・ローカル実行時の既存挙動（HEAD~1..HEAD）に回帰が無いこと」の 3 点。各タスクの §2.x.3 に具体ケースを記載した。
