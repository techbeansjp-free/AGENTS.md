# 要件定義書: GIT_RANGE 既定 `HEAD~1..HEAD` により多コミット push の監査漏れ

**プロジェクト名**: GIT_RANGE 既定 `HEAD~1..HEAD` により多コミット push の監査漏れ
**作成日**: 2026年07月14日
**最終更新**: 2026年07月14日

> **用語**: [.agent-skill-chain/source/CONCEPTS.md §用語規約](../../../../../../../.agent-skill-chain/source/CONCEPTS.md#用語規約) を参照。

---

## 1. 概要

### 1.1 システム概要

`audit.sh` の差分監査範囲（`GIT_RANGE`）は既定で `HEAD~1..HEAD`（直近1コミットのみ）であり、消費者テンプレート `audit.yml` も `fetch-depth: 2` に固定されている。push イベントで複数コミットをまとめて push すると、最終コミット以外の変更が監査対象から漏れる。ユーザー判断により**対応する**ことが確定した（背景 00 参照）。

### 1.2 用語集

| 用語 | 説明 |
| --- | --- |
| GIT_RANGE | `audit.sh` が `git diff --name-only` に渡す差分範囲。CI・ローカル両方で環境変数 `AUDIT_GIT_RANGE` により上書き可能。 |
| before/after SHA | GitHub push イベントペイロードの `github.event.before`/`github.event.after`。push 前後の HEAD を表す。 |

---

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: push イベントの全コミット差分監査

- **As a** 本リポジトリの保守者
- **I want to** push イベントで複数コミットをまとめて push した場合でも、push 前後の全差分が監査対象になってほしい
- **So that** 途中コミットでの成果物変更（証跡なしの直接編集等）が監査をすり抜けない

**受け入れ基準**:

- push イベントの `before`/`after` から動的に `GIT_RANGE`（`AUDIT_GIT_RANGE`）が設定される。
- `before` が全ゼロ SHA（新規ブランチ作成時等）の場合は、既定の `HEAD~1..HEAD` にフォールバックする（クラッシュ・誤動作しない）。
- PR イベントでの監査範囲（既定 `HEAD~1..HEAD`）は変更しない（本 issue の除外要件）。

### 2.2 BDD ユースケース

#### ユースケース 1: 複数コミット push の監査範囲解決

**シナリオ 1: 通常の複数コミット push**

```gherkin
Feature: push イベントの GIT_RANGE 動的設定
  Scenario: before が有効な SHA で複数コミットが push される
    Given github.event.before が有効な SHA、github.event.after が push 後の HEAD である
    When audit.yml の Resolve GIT_RANGE ステップが実行される
    Then AUDIT_GIT_RANGE が "<before>..<after>" として GITHUB_ENV に設定される
    And audit.sh はその範囲で git diff --name-only を実行する
```

**シナリオ 2: 新規ブランチ作成時（before が全ゼロ SHA）**

```gherkin
Feature: push イベントの GIT_RANGE 動的設定
  Scenario: before が全ゼロ SHA（新規ブランチ作成）
    Given github.event.before が "0000000000000000000000000000000000000000" である
    When audit.yml の Resolve GIT_RANGE ステップが実行される
    Then AUDIT_GIT_RANGE は設定されない（既定 HEAD~1..HEAD にフォールバック）
    And audit.sh はエラー終了せず既定範囲で実行される
```

**シナリオ 3: audit.sh 側の防御（全ゼロ SHA が直接渡された場合）**

```gherkin
Feature: audit.sh の GIT_RANGE 検証
  Scenario: AUDIT_GIT_RANGE に全ゼロ SHA を含む範囲が渡される
    Given AUDIT_GIT_RANGE が "0000...0..<after>" のような全ゼロ SHA を含む
    When audit.sh が起動する
    Then WARN ログを出力し GIT_RANGE を既定 HEAD~1..HEAD に無害化する
```

### 2.3 ビジネスルール

- PR イベントの監査範囲見直しは対象外（既存仕様を維持）。
- `fetch-depth` は before..after の差分解決を優先し、`fetch-depth: 0`（全履歴）を採用する。

---

## 3. 非機能要件

### 3.1 パフォーマンス要件

- `fetch-depth: 0` により CI のチェックアウト時間が増加しうるが、本リポジトリの規模では許容範囲と判断する（大規模リポジトリでの再検討は別途）。

### 3.2 セキュリティ要件

- 該当なし（`GIT_RANGE` の任意引数注入対策は既存の正規表現検証を維持）。

### 3.3 ユーザビリティ要件

- 該当なし。

### 3.4 可用性要件

- 該当なし。

---

## 4. 外部インターフェース要件

### 4.1 API 要件

- GitHub Actions push イベントペイロードの `github.event.before` / `github.event.after` を使用する。

### 4.2 データ形式要件

- `AUDIT_GIT_RANGE` 環境変数（既存の受け渡し経路を再利用、新規インターフェースは追加しない）。

---

## 5. 制約事項

- `before` が全ゼロ SHA になるケース（新規ブランチ作成等）への対応が必須（00 §4.1）。
- 既存の `GIT_RANGE` 検証正規表現（オプション注入対策）との整合を維持する。
