# 要件定義書: R6 の sqlite3 判定が部分文字列 regex で過剰ブロック・回避耐性不足

**プロジェクト名**: R6 の sqlite3 判定が部分文字列 regex で過剰ブロック・回避耐性不足
**作成日**: 2026年07月14日
**最終更新**: 2026年07月14日

---

## 1. 概要

### 1.1 システム概要

`.agent-skill-chain/source/enforcement/claude/PreToolUse.sh` の R6（sqlite3 直接実行禁止）は、`[[ "$CMD" =~ sqlite3 ]]` という部分文字列一致で判定しており、`grep sqlite3 doc.md` のような引数中の文字列言及まで一律ブロックする過剰検知と、`python3 -c "import sqlite3"` のような別経路のアクセスを見逃す回避耐性不足の両方を抱えている。ユーザー判断により**対応する**ことが確定した（00 参照）。

### 1.2 用語集

| 用語 | 説明 |
| --- | --- |
| R6 | `PreToolUse.sh` の sqlite3 直接実行禁止ルール（全 ROLE 適用）。scribe 経路（先行判定）と、全ロール共通の後続判定の 2 箇所に実装されている。 |
| コマンド名としての起動 | シェルコマンド文字列をセパレータ（`;` `&` `|` 改行）で分割した各セグメントの、先頭トークン（実行ファイル名）が対象文字列と一致すること。引数中の文字列言及とは区別する。 |

---

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: 過剰ブロックの解消

- **As a** PreToolUse フックの制約下で作業するエージェント
- **I want to** `grep sqlite3 doc.md` のように sqlite3 という文字列を引数として扱うだけのコマンドを誤ブロックされたくない
- **So that** R6 の本来の目的（sqlite3 データベースへの直接アクセス禁止）を損なわずに通常の調査作業ができる

**受け入れ基準**:

- `grep sqlite3 doc.md` 等、先頭コマンド名が `sqlite3` でないコマンドは R6 で block されない。
- `sqlite3 db.sqlite "SELECT 1"` 等、コマンド名として `sqlite3` を起動するコマンドは引き続き block される（既存検知の維持）。

#### ストーリー 2: 回避耐性の強化

- **As a** R6 による sqlite3 直接操作制限の実効性を担保したい保守者
- **I want to** `python3 -c "import sqlite3 as s; ..."` のような別経路の sqlite3 アクセスも一定程度検知してほしい
- **So that** コマンド名判定の厳密化によって生まれうる新たな回避経路の一部を塞げる

**受け入れ基準**:

- `python3 -c "import sqlite3 ..."` / `python3 -c "from sqlite3 import ..."` は block される。
- `-c` を伴わない通常の python スクリプト実行（ファイル内部の import 有無は静的解析できない）は本 issue のスコープ外とし、誤検知しない。

### 2.2 BDD ユースケース

#### ユースケース 1: sqlite3 直接実行の判定（R6）

**シナリオ 1: 文字列言及の誤ブロック解消**

```gherkin
Feature: R6 sqlite3 直接実行禁止判定
  Scenario: grep の検索対象文字列としての "sqlite3"
    Given Bash コマンドが "grep sqlite3 doc.md" である
    When PreToolUse.sh の R6 判定が実行される
    Then block されない
```

**シナリオ 2: コマンド名としての sqlite3 起動（既存検知の維持）**

```gherkin
Feature: R6 sqlite3 直接実行禁止判定
  Scenario: sqlite3 の直接起動
    Given Bash コマンドが "sqlite3 db.sqlite \"SELECT 1\"" である
    When PreToolUse.sh の R6 判定が実行される
    Then block される
```

**シナリオ 3: パイプ・セミコロン区切り後の起動検知**

```gherkin
Feature: R6 sqlite3 直接実行禁止判定
  Scenario: セミコロン区切り後の sqlite3 起動
    Given Bash コマンドが "echo hi; sqlite3 x.db" である
    When PreToolUse.sh の R6 判定が実行される
    Then block される
```

**シナリオ 4: python -c 経由の import アクセス（回避耐性強化）**

```gherkin
Feature: R6 sqlite3 直接実行禁止判定
  Scenario: python3 -c 経由の sqlite3 モジュール import
    Given Bash コマンドが "python3 -c \"import sqlite3 as s; s.connect(1)\"" である
    When PreToolUse.sh の R6 判定が実行される
    Then block される
```

### 2.3 ビジネスルール

- 判定対象は「コマンド名としての sqlite3 起動」（先頭トークンまたはパス付き実行のベースネーム一致）に限定する。
- 回避耐性強化は `python(3)?/python2` の `-c` インライン実行における `import sqlite3` / `from sqlite3 import` パターンの簡易検知に限定し、スクリプトファイル内部の import 等、静的解析が本質的に困難な経路までは追わない（00 §7.1 のリスク対策方針に整合）。
- scribe 経路（先行判定）・全ロール共通判定（後続）の両方に同一の判定ロジックを適用し、判定基準の重複・乖離を生まない。

## 3. 非機能要件

### 3.3 ユーザビリティ要件

- block 時のメッセージ文言は変更しない（既存の `sqlite3 direct execution forbidden (use write-workflow-log.sh)` 案内を維持）。

### 3.4 可用性要件

該当なし。

---

## 5. 制約事項

- 既存の `write-workflow-log.sh` 単独実行許可（R5）や複合シェル禁止（R4）等、他判定ロジックとの整合を崩さないこと（00 §4.2）。
- シェルコマンド文字列の静的解析には限界があり、あらゆる回避経路を完全に防ぐことは目的としない（00 §4.1・§7.1）。過度な複雑化を避け、実用上のバランスを重視する。
