# 要件定義書: #25（メイン直接作業検知）の「1件でも記録があれば永久PASS」問題

**プロジェクト名**: #25（メイン直接作業検知）の「1件でも記録があれば永久PASS」問題
**作成日**: 2026年07月14日
**最終更新**: 2026年07月14日

> **用語**: [.agent-skill-chain/source/CONCEPTS.md §用語規約](../../../../../../../.agent-skill-chain/source/CONCEPTS.md#用語規約) を参照。

## 1. 概要

### 1.1 システム概要

`audit.sh` の `check_25_main_did_real_work()`（失敗条件 #25「メイン直接作業・絶対強制」の検出）は、現状「差分に成果物変更があり、かつ workflow_log の対象 command 行数が 0 件」の場合のみ FAIL する設計になっている。workflow.db は累積型のため、過去に対象 command のログが 1 件でも存在すれば、それ以降のどんな直接編集も検出されなくなる（時系列・対象差分との対応関係を見ていない）。ユーザー判断により **対応する**ことが確定した（00 参照）。

### 1.2 用語集

| 用語 | 説明 |
| --- | --- |
| GIT_RANGE | `audit.sh` が `git diff --name-only` / `git log` に渡す差分範囲。環境変数 `AUDIT_GIT_RANGE` で上書き可能（既定 `HEAD~1..HEAD`）。 |
| 時系列突合 | 対象差分（GIT_RANGE）のコミット日時と、workflow_log の対象 command ログの ts_utc とを時間軸上で対応づけて検証すること。単純な件数（COUNT）判定と対比される。 |
| 許容窓（tolerance window） | 「ログがコミットより前後どの程度の範囲内であれば対応関係ありとみなすか」の時間幅。実装 → ログ記録 → コミット の順序が必ずしもログ記録が先とは限らないため設ける。 |

---

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: 対象差分と時系列的に対応する証跡の検証

- **As a** 本リポジトリの保守者
- **I want to** check_25 が、対象差分（GIT_RANGE）と時系列的に対応する workflow_log エントリの有無を検証してほしい
- **So that** 過去のどこかで記録された 1 件のログによって、それ以降のあらゆる直接編集が恒久的に検知をすり抜ける状態を解消できる

**受け入れ基準**:

- 対象差分に成果物変更（`.agent-skill-chain/runtime/*.md` / `docs/*.md` / `src/` / `app/`）があり、workflow_log の対象 command（`implement-feature`/`design-feature`/`verify-and-close`/`review-docs`/`create-pr-review-issue`）のログが**皆無**なら、従来どおり FAIL する（既存動作の回帰なし）。
- 対象差分に成果物変更があり、workflow_log に対象 command のログは存在するが、その**最新ログが対象差分の最古コミット日時から許容窓を超えて古い**（＝対象差分と無関係な過去のログしかない）場合は FAIL する（**新規検知**。旧実装ではここが見逃されていた）。
- 対象差分の最古コミット日時から許容窓以内に対象 command の最新ログがあれば FAIL しない（正常フロー）。
- 許容窓は環境変数（`MAIN_WORK_GATE_TOLERANCE_SECONDS`）で上書き可能とする。
- 対象差分のコミット日時が取得できない場合（GIT_RANGE 解決不能等）は、時系列突合ができないため従来どおり件数のみの判定にフォールバックする（fail-open 寄りの安全側。既存消費者との互換維持）。

### 2.2 BDD ユースケース

#### ユースケース 1: check_25 の時系列突合

**シナリオ 1: 対象 command ログが皆無（既存動作の回帰確認）**

```gherkin
Feature: check_25 の時系列突合
  Scenario: 対象差分に成果物変更があり workflow_log が空
    Given 成果物変更を含む git 差分（GIT_RANGE）
    And workflow_log に対象 command のログが 0 件
    When audit.sh を実行する
    Then #25 の FAIL メッセージが出力される
```

**シナリオ 2: 対象差分と無関係な古いログのみ（新規検知）**

```gherkin
Feature: check_25 の時系列突合
  Scenario: workflow_log に対象 command のログはあるが対象差分より遥かに古い
    Given 成果物変更を含む git 差分（最古コミットが「今」）
    And workflow_log の対象 command 最新ログの ts_utc が 30 日前
    When audit.sh を実行する（既定許容窓 48 時間）
    Then #25 の FAIL メッセージ（時系列不整合）が出力される
```

**シナリオ 3: 対象差分に対応する直近ログがある（正常フロー）**

```gherkin
Feature: check_25 の時系列突合
  Scenario: workflow_log の対象 command 最新ログが対象差分の直近
    Given 成果物変更を含む git 差分
    And workflow_log の対象 command 最新ログの ts_utc が現在時刻に近い
    When audit.sh を実行する
    Then #25 の FAIL メッセージは出力されない
```

**シナリオ 4: 許容窓の env 上書き**

```gherkin
Feature: check_25 の許容窓上書き
  Scenario: 既定許容窓超のログを env で許容窓を拡大して救済する
    Given workflow_log の対象 command 最新ログの ts_utc が対象差分の最古コミットより 3 日前
    When MAIN_WORK_GATE_TOLERANCE_SECONDS=604800（7日）を指定して audit.sh を実行する
    Then #25 の FAIL メッセージは出力されない
```

### 2.3 ビジネスルール

- 既存の「差分に成果物変更なし・workflow.db 不在・sqlite3 不在・非 git ツリー」時の SKIP（fail-open）は変更しない。
- 00 §4.1 制約（A-2＝workflow.db 非追跡問題による CI 側 SKIP）は本 issue のスコープ外。本 issue はローカル実行時の検知精度改善が主眼。

## 3. 非機能要件

### 3.1 パフォーマンス要件

- `git log --format=%cI $GIT_RANGE` の追加実行によるオーバーヘッドは、既存の `git diff --name-only` と同オーダーであり無視できる。

### 3.2 セキュリティ要件

- 該当なし（`GIT_RANGE` の任意引数注入対策は既存の正規表現検証を維持。新規追加の `git log` 呼び出しも同一の検証済み `$GIT_RANGE` を使う）。

### 3.3 ユーザビリティ要件

- 該当なし。

### 3.4 可用性要件

- 該当なし。

---

## 4. 外部インターフェース要件

### 4.1 API 要件

- 該当なし。

### 4.2 データ形式要件

- 新規環境変数 `MAIN_WORK_GATE_TOLERANCE_SECONDS`（整数秒、既定 172800=48時間）を追加する。既存の `workflow_log` スキーマ（`ts_utc` ISO8601 UTC）はそのまま利用する。

---

## 5. 制約事項

- A-2（workflow.db 非追跡による CI 側 SKIP）が解消されない限り、本改善自体も CI では発火しない（00 §4.1）。
- 既存の `workflow_log` フォーマット・列との整合が必要（新規列は追加しない）。
