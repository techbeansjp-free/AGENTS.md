# 設計書: orchestrator 許可ツール allowlist に Skill を追加する

**プロジェクト名**: orchestrator 許可ツール allowlist に Skill が無く委譲経路と矛盾（自己ロックアウトリスク）
**作成日**: 2026年07月14日
**最終更新**: 2026年07月14日

---

## 1. 設計概要

### 1.1 設計方針

本 issue は `.agent-skill-chain/source/enforcement/claude/PreToolUse.sh` R2 の許可ツール `case` 文（allowlist）1 箇所への 1 ツール名追加のみである。既存の分岐構造（`Read|Grep|...|AskUserQuestion)` の並びに `Skill` を追加し、既存コメント（Agent 追加時の注記パターン）に倣って追加理由を注記する。新規ファイル・新規関数・新規分岐は作らない。

### 1.2 設計原則

- **単一責務**: 適用する。allowlist の定義は PreToolUse.sh R2 の 1 箇所のみに存在させ、二重管理しない（既存構造を維持）。
- **明確な境界**: 適用する。ツール名レベルの許可可否と、呼び出し先 skill 種別の絞り込み（対象外）を混同しない。

## 2. 変更内容

### 2.1 対象ファイルと変更点

| ファイル | 変更内容 |
| -------- | -------- |
| `.agent-skill-chain/source/enforcement/claude/PreToolUse.sh` | R2 の allowlist `case` 文（239行目付近）に `Skill` を追加し、追加理由のコメントを付す。 |
| `test/test-pretooluse-hook.sh` | UC1 に `uc1_orchestrator_skill_allowed`（orchestrator の Skill 呼び出しが exit 0 になることを検証するケース）を追加。 |

```diff
-      Read|Grep|Glob|LS|list_dir|Task|Agent|mcp_task|ReadLints|fetch_mcp_resource|list_mcp_resources|AskUserQuestion)
+      Read|Grep|Glob|LS|list_dir|Task|Agent|Skill|mcp_task|ReadLints|fetch_mcp_resource|list_mcp_resources|AskUserQuestion)
```

既存の `Bash` 明示拒否・`Edit|Write|Delete|...` 明示拒否・`*)` fail-closed デフォルト分岐は変更しない。

### 2.3 参照関係・影響範囲

- 影響は R2 の `case` 文内のみ。R1（runtime/ 直接編集禁止）・R3〜R6（Bash 判定）・subagent worker 判定（IS_SUBAGENT=1 除外）には一切影響しない。
- `.agent-skill-chain/project/orchestrator-allowlist.txt`（project opt-in 拡張）とは独立。今回は本体 allowlist への追加であり opt-in 拡張ファイルは使わない（00 の対応方針どおり）。

## 3. セキュリティ検討（01 §2.2 を踏まえた確定）

- PreToolUse.sh はツール名のみで判定する構造であり、`Skill` 呼び出しの引数（どの skill を呼ぶか）まで絞り込む機構は無い。既存の `Task`/`Agent` も同様の粒度で許可されている。`Skill` を同水準で追加することは既存設計との整合性が高く、過剰設計（新規の引数解析ロジック追加）を避ける。
- 万一の乱用（意図しない skill 実行）への抑止は、本 hook より上位のガバナンス（CLAUDE.md の運用規約・レビュー体制）に委ねる。これは既存の `Task`/`Agent` 許可と同じ前提であり、本変更で新たなリスク層を追加するものではない。

## 4. テスト観点

- orchestrator ロールで `tool_name=Skill` が exit 0 になること（新規追加）。
- 既存の allowlist 対象ツール・Bash 拒否・Edit/Write 拒否・`*)` fail-closed の挙動に回帰がないこと（既存テスト全件 green を維持）。
