# 要件定義書: orchestrator 許可ツール allowlist に Skill を追加する

**プロジェクト名**: orchestrator 許可ツール allowlist に Skill が無く委譲経路と矛盾（自己ロックアウトリスク）
**作成日**: 2026年07月14日
**最終更新**: 2026年07月14日

> **判断**: [00_要求定義.md](./00_要求定義.md) の成功基準どおり、R2 allowlist へ `Skill` を追加して対応する（軽微な allowlist 追従修正であり、要求定義以上の追加検討は不要と判断）。

---

## 1. 概要

`.agent-skill-chain/source/enforcement/claude/PreToolUse.sh` の R2（orchestrator 許可ツール allowlist・237-266行目付近）は `Read|Grep|Glob|LS|list_dir|Task|Agent|mcp_task|ReadLints|fetch_mcp_resource|list_mcp_resources|AskUserQuestion` のみを許可し、`Skill` を含んでいない。CLAUDE.md は「command 実行時は run_command と commands/{name}.md を読むこと」とし、Claude Code 配備では command 実行の入口が `Skill` ツール（`.claude/skills/agent`）である。`enforce on` 環境で orchestrator が `Skill` を呼ぶと、allowlist の `*)` （fail-closed のデフォルト分岐）に落ちてブロックされ、正規の委譲経路そのものが使えなくなる自己ロックアウトが起こりうる（過去の Agent ツール未対応ロックアウト事故と同型）。

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: orchestrator が enforce on 環境下で Skill ツールを使える

- **As a** enforce on 環境で稼働する orchestrator
- **I want to** `Skill` ツールで command（agent skill chain）を呼び出してもブロックされない
- **So that** 本フレームワークが要求する正規の委譲経路が enforcement 自身によって塞がれる自己矛盾が起きない

**受け入れ基準**:

- `AGENT_ROLE=orchestrator` かつ `IS_SUBAGENT!=1` の状態で `tool_name=Skill` の PreToolUse 呼び出しが exit 0（許可）になる。
- 既存の allowlist 対象ツール（Read/Grep/Glob/LS/list_dir/Task/Agent/mcp_task/ReadLints/fetch_mcp_resource/list_mcp_resources/AskUserQuestion）の許可、および Bash/Edit/Write 等の明示拒否の挙動は変更しない（回帰なし）。

### 2.2 非機能要件

- **セキュリティ**: 00 §3.2 の懸念（Skill 無条件許可のリスク）を踏まえ検討したが、PreToolUse.sh はツール名レベルでしか判定できず、呼び出し先 skill 種別（agent 等）を hook 側で絞り込む手段が無い。既存の `Task`/`Agent`（委譲ツール）も同様にツール名レベルの許可であり、`Skill` もこれらと同水準の単純追加とする（過剰設計は行わない）。実際の乱用防止は既存の fail-closed 設計（未知ツール・Bash・Edit/Write 等の明示拒否は本変更後も維持）に委ねる。
- **互換性**: 既存 allowlist・fail-closed 設計思想を維持する。

## 3. 除外要件

- `Skill` 呼び出し専用の許可分岐（skill 種別による絞り込み）の新設は行わない（00 §5 のとおり対象外）。

## 4. 成功基準

- `enforce on` 環境で orchestrator の `Skill(agent)` 呼び出しがブロックされずに実行できる（テストで確認）。
