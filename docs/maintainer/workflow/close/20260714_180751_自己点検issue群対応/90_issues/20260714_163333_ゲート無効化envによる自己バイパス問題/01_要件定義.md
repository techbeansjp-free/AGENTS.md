# 要件定義書: ゲート無効化 env・grandfather env による自己バイパス防止の運用ルール明文化

**プロジェクト名**: ゲート無効化env自己バイパス問題
**作成日**: 2026 年 07 月 15 日
**最終更新**: 2026 年 07 月 15 日

> **重要**: 本 issue は**技術的強制ではなく運用ルールの明文化**を扱う（00 §4.1 技術的制約）。env 変数はシェル環境で自由に設定可能であり、AI エージェントが設定できないよう技術的に強制することは困難である。よって本 01 は「AI エージェントが該当 env を自律的に設定・変更してはならず、人間の明示指示がある場合のみ設定可」という運用ルールを、正本ドキュメントに明記することをゴールとする。ドキュメントの**具体的な配置先**（`.agent-skill-chain/project/自己拡張ワークフロー.md` か `.agent-skill-chain/source/AGENT_CONDUCT.md` か、または両方）は本 01 では決定せず、02_設計.md の ADR で決定する。
>
> **用語**: [.agent-skill-chain/source/CONCEPTS.md §用語規約](../../../../../../../.agent-skill-chain/source/CONCEPTS.md#用語規約) を参照。

## 1. 概要

### 1.1 システム概要

`.agent-skill-chain/source/enforcement/ci/audit.sh` の各ゲート（#32 review-docs 未実行検知・#33 close 移動未実施検知・#34 GitHub Issue 起票ゲート・#35 ブランチ紐づけゲート・#36 PR 紐づけゲート・#38 モデルティア明記ゲート）は、それぞれ env 変数によって無効化・grandfather 判定を上書きできる設計になっている（evidence_source: existing_code、`audit.sh` grep 結果）。

- **完全無効化トグル**（既定 `true`）: `GITHUB_ISSUE_GATE_ENABLED`（#34）・`BRANCH_LINK_GATE_ENABLED`（#35）・`PR_LINK_GATE_ENABLED`（#36）・`MODEL_TIER_GATE_ENABLED`（#38）。`false`/`0`/`no`/`off` で当該ゲート単体を SKIP させる。
- **grandfather 基準日上書き**: `REVIEWDOCS_GATE_EFFECTIVE_FROM`（#32）・`CLOSE_MOVE_GATE_EFFECTIVE_FROM`（#33）・`GITHUB_ISSUE_GATE_EFFECTIVE_FROM`（#34）・`BRANCH_LINK_GATE_EFFECTIVE_FROM`（#35）・`PR_LINK_GATE_EFFECTIVE_FROM`（#36）・`MODEL_TIER_GATE_EFFECTIVE_FROM`（#38）。基準日を未来方向へ上書きすると、対象範囲の issue が grandfather 扱いとなり実質的にゲートを無効化できる。

これらの env は audit 実行主体（AI エージェント自身）が同一セッション内で自由に設定できるため、AI エージェントが自らチェックを SKIP させる「自己バイパス」が技術的に可能である（00 §1.2）。一方でこれらのトグルは GitHub 非採用環境等の正当な運用ニーズのために存在し（`.agent-skill-chain/project/自己拡張ワークフロー.md` §8 で本リポジトリは `GITHUB_ISSUE_GATE_ENABLED` を意図的に既定 `true` のまま設定していないことが明記されている）、トグル機構自体を廃止することは 00 §5 除外要件により対象外である。

本 issue が定義するのは、この両立（正当な運用ニーズは維持しつつ、AI エージェントによる自律的な自己バイパスは禁止する）を成立させる**運用ルールの明文化**である。

### 1.2 用語集

| 用語 | 説明 |
| -------- | ------ |
| ゲート無効化 env | `*_GATE_ENABLED` 系 env（既定 `true`）。`false`/`0`/`no`/`off` で対象ゲートを SKIP させる |
| grandfather env | `*_GATE_EFFECTIVE_FROM` 系 env（既定は各ゲートのハードコード日時）。基準日を未来方向へ上書きすると対象 issue が遡及適用外（SKIP）になる |
| 自己バイパス | audit 実行主体（AI エージェント自身）が、自らの作業に対するゲートを SKIP させる目的で上記 env を自律的に設定・変更する行為 |
| 正当なトグル運用 | GitHub 非採用環境等、プロジェクトの恒常的な運用方針としてゲートを無効化する、人間が判断した既存の正当な設定行為（例: `.agent-skill-chain/project/自己拡張ワークフロー.md` §8 に記載の判断） |
| 人間の明示指示 | ユーザーが自然文・設定変更依頼等で明確にゲート無効化 env の設定・変更を指示していること。AI エージェントの自律判断による設定・変更とは区別される |

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: AI エージェントの自律的なゲート無効化 env 設定を禁止する運用ルールを明文化する

- **As a** 本パッケージの正本ドキュメント保守担当・AI エージェント自身
- **I want to** 「AI エージェントがゲート無効化 env（`*_GATE_ENABLED`・`*_GATE_EFFECTIVE_FROM`）を自律的に設定・変更してはならず、人間の明示指示がある場合のみ設定可」という運用ルールが正本ドキュメントに明記されている
- **So that** audit 実行主体である AI エージェント自身が自己バイパス目的でこれらの env を設定する余地を、運用ルールレベルで塞ぐ

**受け入れ基準**:

- 対象ドキュメント（`.agent-skill-chain/project/自己拡張ワークフロー.md` または `.agent-skill-chain/source/AGENT_CONDUCT.md`。配置は 02_設計 ADR で決定）に、ゲート無効化 env（`*_GATE_ENABLED` 系）と grandfather env（`*_GATE_EFFECTIVE_FROM` 系）の両方を対象として、AI エージェントの自律的な設定・変更を禁止する文言が明記される。
- 明記された文言には「人間の明示指示がある場合のみ設定可」という例外条件が含まれる。
- 明記された文言は、対象 env のパターン（`*_GATE_ENABLED`・`*_GATE_EFFECTIVE_FROM`）または具体列挙（`GITHUB_ISSUE_GATE_ENABLED` 等）のいずれかで、どの env が対象かが読み手に一意に分かる形で書かれている。

#### ストーリー 2: 既存の正当なトグル運用記述と矛盾しない形で追記する

- **As a** 本パッケージの保守担当
- **I want to** 新設する運用ルールが、`.agent-skill-chain/project/自己拡張ワークフロー.md` §8 に既存する「本リポジトリでは `GITHUB_ISSUE_GATE_ENABLED` を設定せず既定 `true` のままにする」等の記述と矛盾しない
- **So that** 既存の正当な運用判断（プロジェクト単位でのトグル設定は人間判断で行われてきた事実）を否定せず、今回追記する規律と整合させる

**受け入れ基準**:

- 新設する運用ルールの文言は、「プロジェクト単位でのトグル設定自体（人間が判断した既存の正当な設定）」を禁止する内容ではなく、「AI エージェントが自律的にその設定を行うこと」のみを禁止する内容であることが読み取れる。
- `.agent-skill-chain/project/自己拡張ワークフロー.md` §8・ブランチ紐づけ・PR 紐づけ節の既存記述（各トグルを本リポジトリでは既定のままにする、という記述）を削除・改変しない。

#### ストーリー 3: 対応要否・配置先の判断根拠が追跡できる

- **As a** 後続フェーズ（02 設計）の担当・レビュアー
- **I want to** 配置先候補（project 側 vs source 側）の比較検討が 02_設計.md の ADR に記録される
- **So that** なぜその配置を選んだかが後から追跡できる

**受け入れ基準**:

- 02_設計.md 作成時、配置先の決定が EVIDENCE_POLICY.md §節2 の ADR 形式（コンテキスト・検討した選択肢・決定・根拠・帰結）で記録される（本 01 では決定を確定せず、判断材料の提示に留める）。

#### ユースケース 1: 運用ルールの明記有無を判定する

**シナリオ 1: 対象ドキュメントに運用ルールが明記されている（○）**

```gherkin
  Scenario: 正本ドキュメントを確認する

```

**シナリオ 2: 運用ルールが明記されていない（×）**

```gherkin
Feature: ゲート無効化 env 自律設定禁止ルールの明記
  Scenario: 正本ドキュメントに該当記述が無い
    Given 対象ドキュメントに §8 GITHUB_ISSUE_GATE_ENABLED 等トグルの存在自体は記載されているが、設定権限（誰が設定してよいか）についての記述が無い
```

#### ユースケース 2: 既存トグル運用記述との非矛盾性を判定する

**シナリオ 1: 既存記述が維持されている（○）**

```gherkin
Feature: 既存の正当なトグル運用記述との整合
  Scenario: 自己拡張ワークフロー.md §8 を確認する
    Given 自己拡張ワークフロー.md §8「本リポジトリでは GITHUB_ISSUE_GATE_ENABLED を設定せず既定 true のままにする」という既存記述がある
    When 新設する運用ルールを追記する
    Then 既存記述は削除・改変されず、新設ルールは「AI エージェントの自律設定」のみを対象とする文言として併存する
```

**シナリオ 2: 既存の正当な運用判断そのものを禁止する記述になっている（×・矛盾）**

```gherkin
Feature: 既存の正当なトグル運用記述との整合
  Scenario: 新設ルールがトグル運用自体を一律禁止している
    Given 新設した運用ルールの文言が「いかなる場合もゲート無効化 env を設定してはならない」等、人間判断による正当な設定も含めて一律禁止する内容になっている
    When レビュアーが 00 §5 除外要件（トグル機構自体の廃止は対象外）と照合する
    Then 矛盾（×）と判定され、文言の修正が必要となる
```

#### ユースケース 3: 対象 env の範囲が一意に特定できるか判定する

**シナリオ 1: 対象 env パターンが一意に特定できる（○）**

```gherkin
Feature: 対象 env 範囲の明確性
  Scenario: 追記された文言を読む
    Given 追記された運用ルールの文言に "*_GATE_ENABLED" "*_GATE_EFFECTIVE_FROM" のパターン表記、または GITHUB_ISSUE_GATE_ENABLED 等の具体列挙のいずれかが含まれる
    When 読み手（AI エージェントまたは人間レビュアー）がこの文言を読む
    Then どの env 変数が禁止対象かを一意に判定できる
```

### 2.3 ビジネスルール

- ゲート無効化 env（`*_GATE_ENABLED`）・grandfather env（`*_GATE_EFFECTIVE_FROM`）のいずれも、AI エージェントが自律的に設定・変更してはならない。
- 人間の明示指示がある場合に限り、AI エージェント（サブエージェント含む）が委譲されてこれらの env を設定・変更してよい。
- プロジェクト単位での正当なトグル運用判断（例: GitHub 非採用環境での恒常的な無効化）自体は禁止対象ではなく、既存の運用（`.agent-skill-chain/project/自己拡張ワークフロー.md` §8 等）を継続してよい。
- 本ルールは advisory（運用ルール明文化）であり、技術的な機構強制（hooks/CI での env 設定自体のブロック）は本 issue のスコープ外（00 §4.1・§5）。

## 3. 非機能要件

### 3.1 パフォーマンス要件

- 該当なし（ドキュメント追記のみ、実行時性能に影響しない）。

### 3.2 セキュリティ要件

- 自己バイパスによる enforcement 機構の無力化リスクを、運用ルール明文化によって低減する（00 §3.2）。
- 技術的強制ではないため、本ルールのみで自己バイパスを完全に防げるわけではない（00 §7.1 リスクと対策を参照）。

### 3.3 ユーザビリティ要件

- AI エージェントが本ルールを参照した際、「どの env が対象か」「いつなら設定してよいか」が具体的に分かること（抽象的な訓示に留めない）。

### 3.4 可用性要件

- 既存のゲート判定ロジック（audit.sh の SKIP 条件・grandfather 判定）自体は変更しない。

## 5. 制約事項

- 技術的な機構強制（env 設定自体を AI エージェントに行わせない仕組み）は本 issue のスコープ外。運用ルール明文化が対応の中心（00 §4.1）。
- ドキュメントの具体配置先（`.agent-skill-chain/project/自己拡張ワークフロー.md` か `.agent-skill-chain/source/AGENT_CONDUCT.md` か、または両方への記載）は本 01 では決定せず、02_設計.md の ADR で決定する。
- 追記は要点のみとし、既存節（自己拡張ワークフロー.md §8・ブランチ紐づけ・PR 紐づけ節、または AGENT_CONDUCT.md 第 1〜3 部）の重複再定義をしない。
- トグル機構自体の廃止は対象外（00 §5 除外要件）。

### 未検証・要人間確認事項（inference_only）

- **対応要否そのもの**: 00 §7.2 のとおり、本 issue の対応要否（着手するか否か）自体がユーザー判断待ちである。本 01 は「対応する場合」の要件を定義したものであり、対応不要と判断された場合は本 01 に基づく後続フェーズ（02 設計・03 実装）は実施しない。
- **配置先の最終決定**: `.agent-skill-chain/project/自己拡張ワークフロー.md`（本リポジトリ固有・最優先）と `.agent-skill-chain/source/AGENT_CONDUCT.md`（汎用・全消費者向け advisory）のどちらに書くかで、適用範囲（本リポジトリ限定 vs 全消費者プロジェクト）が変わる。この判断は一次情報（両ファイルの§0 読み替え規則・汎用/固有境界の既存記述）に基づき 02 設計で ADR として確定する必要があり、本 01 では inference_only（推論のみ）に留まる。RULES.md §高リスク操作には該当しないため「要注意」（非ブロッキング）として扱い、後続フェーズで確定させる。
