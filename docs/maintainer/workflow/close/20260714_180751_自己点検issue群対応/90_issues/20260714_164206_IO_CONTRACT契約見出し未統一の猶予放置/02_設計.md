## 1. 設計概要

### 1.1 設計方針

本タスクはコードを持たないドキュメント修正であり、[01_設計原則](../../../../../../../.agent-skill-chain/source/spec/01_設計原則.md) のうち**単一責務・明確な境界**を適用する。「猶予の判定基準」という責務は IO_CONTRACT.md 1 か所に集約し、契約見出しの実装（追加作業）は名指しされた `skills/agent/SKILL.md` のみに限定する。

### 1.2 設計原則（本プロジェクトで適用するもの）

- **単一責務**: 猶予の対象・期限・監査基準の定義は IO_CONTRACT.md のみが持つ。他ファイル（本 02_設計 等）はそれを参照するのみで重複定義しない。
- **明確な境界**: 「基準の明文化」（IO_CONTRACT.md）と「見出しの実装」（skills/agent/SKILL.md）を分離し、後者は前者が示す優先対象のみに限定する。

### 2.5 横断設計判断（ADR）

#### ADR-1: 猶予期限は固定日付ではなく「次回実質改修時」とする

- **コンテキスト**: 00 §4.3 は「猶予期限を設ける場合、既存 skill の棚卸し結果を踏まえて現実的な期限を検討する」としている。棚卸しの結果、猶予対象は 11 件と判明した。
- **検討した選択肢**:
  1. 固定の カレンダー日付（例: 2026-09-01 まで）を期限とする。
  2. 「当該 skill を実質改修する回（次回改修時）」を期限とする（lazy migration）。
- **決定**: 選択肢 2（次回実質改修時）を採用する。
- **根拠**: 00 §4.1 は「既存 skill 全件の見出し対応には一定の作業量が見込まれるため、優先度づけが必要」と明記しており、11 件を一律の固定日付までに強制改修するタスクを本 issue（小規模issue）のスコープで発生させるのは 00 §5 の除外要件（全 skill の即時完全準拠はスコープ外）に反する。固定日付は「日付が来たら未改修分が一斉 FAIL する」崖を作り、07_リスク §7.1 の「大量改修が必要になり作業が肥大化するおそれ」を助長する。次回実質改修時の運用は、当該 skill に実際に手を入れるタイミングでのみ見出し追加を要求するため、無駄な一斉改修を発生させずに済む。
- **帰結**: IO_CONTRACT.md の運用節に「次回実質改修時（typo 修正等の非実質差分は含まない）」を期限として明記し、監査基準（機械チェック時の FAIL/PASS 条件）を併記する。

#### ADR-2: `skills/agent/SKILL.md` の契約見出しは既存内容を維持したまま再配置する

- **コンテキスト**: 00 の対象ファイル節は「契約見出しの追加のみ行う。委譲定義等の内容には触れない」と明記している。
- **検討した選択肢**:
  1. 既存の「委譲の形（共通）」「実行要領」節をそのまま残し、末尾に契約見出し節を追加で併記する。
  2. 契約見出し（Purpose/Inputs/Process/Outputs/Done/Forbidden）を導入し、既存の各節をその対応する見出しの下（または Process のサブ見出し）に再配置する。
- **決定**: 選択肢 2（見出し構造への再配置）を採用する。
- **根拠**: 選択肢 1 は「契約見出しに揃える」という IO_CONTRACT.md の趣旨（既存の「目的」「手順」等をこの対応に揃える）を満たさず、見出しの二重併記になる。write-bdd/SKILL.md の実例（`**契約**:` 宣言＋6 見出し）に倣い、既存の「委譲の形（共通）」「実行要領」の文言・内容は一切変更せず、`## Process` 見出しの下にサブ見出し（`### 委譲の形（共通）`・`### 実行要領`）として配置することで、内容に触れずに構造のみ契約へ揃えられる（`existing_code` 根拠: write-bdd/SKILL.md の既存パターン）。
- **帰結**: `skills/agent/SKILL.md` に `## Purpose`/`## Inputs`/`## Process`/`## Outputs`/`## Done`/`## Forbidden` を追加し、既存の「委譲の形（共通）」「実行要領」は `## Process` 配下のサブ見出しとしてそのまま保持する。「## 参照」節も既存のまま維持する。
