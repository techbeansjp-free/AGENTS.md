# 要件定義書: enforcement 失敗条件記述の一元化（統合）

**プロジェクト名**: enforcement 失敗条件記述の一元化（バッチ5・統合）
**作成日**: 2026 年 07 月 14 日
**最終更新**: 2026 年 07 月 14 日

> 本 01 はバッチ5・3 件（163330 重複解消 / 163403 未実装ラベル / 163432 欠落行）の統合受け入れ基準を扱う。設計の正本は本 issue の `02_設計.md`。

---

## 1. 概要

### 1.1 システム概要

`enforcement/README.md §失敗条件と差し戻し` の失敗条件対応表（レジストリ）を単一正本に格上げし、実装状態列の追加・欠落行の補完・他 5 箇所の参照化を 1 回の構造変更で行う。

### 1.2 用語集

| 用語 | 説明 |
| ---- | ---- |
| レジストリ | 失敗条件対応表（表 A）。全失敗条件の概要・実装所在・実装状態・強制レベルの正本。 |
| 実装状態 | `実装済み`/`推奨（未強制）`/`未実装（人手監査）`/`未実装（抽象仕様のみ・将来hook）` の統制語彙。 |
| 未実装 7 項目 | #22/#23/#24/#30・系統A/C/E。 |

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: 保守者が失敗条件を 1 か所で保守できる（163330）

- **As a** 本フレームワークの保守者
- **I want to** 失敗条件の詳細を README のレジストリ 1 か所で保守
- **So that** 1 ゲート追加時に 6 箇所を同期する手間と同期漏れ（#37 実績）を無くせる

**受け入れ基準**:
- 失敗条件の {概要・実装所在・実装状態・強制レベル} の正本が README 失敗条件対応表 1 か所に集約されている。
- audit.sh ヘッダの冗長「失敗とみなす条件」ブロック・README 散文が要点 1 行＋参照へ短縮されている。
- 共通前提の共有ノート化により、従来 1,000 字超だったセルが有意に短縮されている（目標: 各セル 1,000 字未満。ゲート固有の必須記述で超える場合は、共通前提へ移せる分を最大限移したうえで許容する）。
- **核となる成功基準**（00 §6）: 1 ゲートの失敗条件記述の変更時に同期が必要な箇所が、現状の 6 箇所から削減されている。

#### ストーリー 2: 読者が実装済み/未実装を機械的に区別できる（163403）

- **As a** 本システムの利用者・監査者
- **I want to** 未実装の失敗条件を実装済みと機械的に区別
- **So that** 「機械強制されている」との誤認を避けられる

**受け入れ基準**:
- 未実装 7 項目に統制語彙 `未実装（...）` が一貫付与されている。
- `grep` で未実装項目を機械抽出できる。

#### ストーリー 3: 正本と実装のドリフトが解消される（163432）

- **As a** 本システムの保守者
- **I want to** audit.sh 実装済み全チェックがレジストリに漏れなく記載されている状態
- **So that** ルール正本と実装が乖離しない

**受け入れ基準**:
- 表 A に #2・#4・#7・#21・#37 の行が追加されている。
- 表 B・表 C に #37 の行が追加されている。

### 2.2 BDD ユースケース

#### ユースケース 1: 欠落行の網羅（163432）

```gherkin
Feature: 失敗条件対応表の網羅性
  Scenario: audit.sh 実装済みチェックが表 A に漏れなく載る
    Given audit.sh に check_docs_transient_issue_ref(#37) 等の実装がある
    When enforcement/README.md の失敗条件対応表を確認する
    Then #2 #4 #7 #21 #37 の行が対応表に存在する
    And 表 B と表 C に #37 の行が存在する
```

#### ユースケース 2: 実装状態の機械可読化（163403）

```gherkin
Feature: 実装状態の区別
  Scenario: 未実装項目にラベルが付く
    Given #22 #23 #24 #30 系統A 系統C 系統E は未実装である
    When 失敗条件対応表の実装状態列を確認する
    Then 各行に「未実装」で始まる統制語彙が付与されている
    And grep -E '未実装' で 7 項目を抽出できる
```

#### ユースケース 3: 重複解消と回帰非発生（163330）

```gherkin
Feature: 重複解消かつ挙動不変
  Scenario: ドキュメントのみ変更し audit 挙動は不変
    Given audit.sh の関数本体は変更しない
    When audit.sh をローカルで変更前後に実行する
    Then PASS/FAIL/SKIP の出力が一致する
    And audit.sh の diff はヘッダコメントのみに限定される
```

### 2.3 ビジネスルール

- 失敗条件番号 `#1`–`#37` の付け替えを禁止（外部参照保全）。
- 見出し `## 失敗条件と差し戻し` を維持（外部参照保全）。
- 「対応表」の名称を維持（DESIGN.md 名指し保全）。
