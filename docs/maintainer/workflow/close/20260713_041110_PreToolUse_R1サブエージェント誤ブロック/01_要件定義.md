# 要件定義書: PreToolUse R1/R2 非対称性の文書化と汎用調査規律の明文化

**最終更新**: 2026 年 07 月 13 日

> **重要**: 調査の結果、R1 の全 ROLE 一律 runtime/ block は**意図的設計でありバグではない**（根拠・evidence_source は [00_要求定義.md §1.4](./00_要求定義.md) を正とする）。よって**コード修正は不要**。**ユーザー決定によりスコープを拡大**し、本 01 は (1) 現行の正しい挙動の明文化・ドキュメント追記、(2)「バグ/矛盾」断定前の関連ルール横断確認という**汎用調査規律の明文化**、の 2 点を扱う。

## 1. 概要

### 1.1 システム概要

`PreToolUse.sh`（Layer2 Tool hook）には目的の異なる 2 つのガードがある。**R1（path-axis・全 ROLE）** は `.agent-skill-chain/runtime/` 配下への直接 Write/Edit を全 ROLE で禁止し、Bash 経由のみ許可する。**R2（role-axis）** は orchestrator の直接実作業を禁止し subagent worker を除外する。両者は意図的に非対称であり、subagent は runtime/ 配下へ **Bash（heredoc/cp/new-workflow-memo.sh）経由**で書くのが正規ルートである。

フィールド報告の「R1 は subagent を誤ブロックするバグ」は、R2/DESIGN.md L49 の「worker は Edit/Write 許可」を「runtime/ を含めどこでも Edit/Write 可」と過大に読み、**同一ファイル内の R2（IS_SUBAGENT 除外）・R3(b)（Bash 許可）という関連ルールを横断確認せずに矛盾と断定した**誤診断であった（詳細は [00 §1.4](./00_要求定義.md)）。本 issue は、この 2 つの帰結（ドキュメント明確化・調査規律明文化）を扱う。

### 1.2 用語集

| 用語 | 説明 |
| -------- | ------ |
| R1（path-axis） | runtime/ 配下への直接 Write/Edit を全 ROLE 禁止（L167-172）。Bash 経由のみ許可 |
| R2（role-axis） | orchestrator の直接実作業を禁止・subagent（IS_SUBAGENT=1）は除外（L182） |
| R3(b) | subagent worker（IS_SUBAGENT=1）の Bash を allow（L250-253） |
| 正規ルート | subagent が runtime/ 配下へ書く経路＝Bash（heredoc/cp/new-workflow-memo.sh） |
| 横断確認 | 「バグ/矛盾」と断定する前に、同一ファイル・同一機構内の関連ルール（分岐条件・例外コメント等）をすべて確認すること |

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: 現行の R1/R2 非対称挙動を維持する（コード変更なし）

- **As a** enforcement の維持担当
- **I want to** R1（runtime/ 全 ROLE 禁止・Bash のみ）と R2（subagent 除外）の現行挙動を維持する
- **So that** timestamp memo/DB 保護と subagent の実作業許可を両立した設計が壊れない

**受け入れ基準**:

- PreToolUse.sh に変更を加えない。
- subagent が runtime/ 外（src・コード等）を Edit/Write できる現行挙動が維持される。
- subagent が runtime/ 配下へは Bash 経由で書ける現行挙動が維持される。

#### ストーリー 2: 設計意図をドキュメントで明確化する

- **As a** 本パッケージの利用者・保守者
- **I want to** R1/R2 の非対称性と「Bash が subagent の runtime/ 書き込み正規ルート」であることが enforcement/README.md・DESIGN.md に明記されている
- **So that** 同種の「バグでは?」という誤解が再発しない

**受け入れ基準**:

- enforcement の README.md **または** DESIGN.md（design-feature で配置決定）に「R1=path-axis・全 ROLE / R2=role-axis・subagent 除外」の非対称が意図的である旨と、subagent の runtime/ 書き込み正規ルート（Bash）が明記される。
- 判定ロジックの二重実装はせず、説明追記に留める。

#### ストーリー 3（新規スコープ）: 「バグ/矛盾」断定前の横断確認規律に従う

- **As a** requirement-discovery・design-feature・review-code 等を実行する AI エージェント（サブエージェント）
- **I want to** ある挙動を「バグ/矛盾」と結論づける前に、同一ファイル・同一機構内の関連ルール（分岐条件・例外コメント等）を横断的に確認し、意図的な非対称性を示す記述（例:「全 ROLE」「対象外」等の明示コメント）の有無を確認する
- **So that** 今回のような部分的な読みによる誤診断（R1 だけを読み R2/R3(b) を未確認のまま「矛盾＝バグ」と断定）を再発させない

**受け入れ基準**:

- EVIDENCE_POLICY.md または REVIEW_RULE.md（design-feature の ADR で決定した配置先）に、「バグ/矛盾」と結論づける前に関連ルールを横断確認することが明文化される。
- 明文化された規律には、(a) 部分的な読みでの結論を禁止する旨、(b) 意図的な非対称性を示す明示コメント（例:「全 ROLE」「対象外」等）の有無を確認する旨、の両方が含まれる。
- 既存の evidence_source・重要判断の定義（EVIDENCE_POLICY.md 節3）と矛盾・重複しない形で追記される。

### 2.2 BDD ユースケース

#### ユースケース 1: R1 は runtime/ 配下を全 ROLE で block（現行・正しい・変更なし）

**シナリオ 1: subagent の runtime/ 配下 Edit は現行仕様どおり block される**

```gherkin
Feature: R1 は runtime/ 配下を全 ROLE で block（意図的）
  Scenario: agent_id を持つ worker が runtime 配下を Edit する
    Given IS_SUBAGENT=1 の worker
    And tool_name が "Edit" で file_path が ".agent-skill-chain/runtime/<issue>/00_要求定義.md"
    When PreToolUse.sh が R1 を評価する
    Then exit 2（block）となる（バグではなく設計どおり。runtime/ へは Bash 経由で書く）
```

**シナリオ 2: subagent は runtime/ 配下へ Bash 経由で書ける（正規ルート）**

```gherkin
Feature: subagent の runtime/ 書き込み正規ルートは Bash
  Scenario: worker が Bash(heredoc/cp) で runtime 配下にファイルを作成する
    Given IS_SUBAGENT=1 の worker
    And tool_name が "Bash" で複合シェルでない単一コマンド
    When PreToolUse.sh が R3 を評価する
    Then R3(b) により allow される（sqlite3 直接は R6 で別途 block）
```

**シナリオ 3: subagent は runtime/ 外を Edit/Write できる**

```gherkin
Feature: R2 は subagent を除外
  Scenario: worker が src/ 配下を Edit する
    Given IS_SUBAGENT=1 の worker（ROLE 継承は orchestrator）
    And tool_name が "Edit" で file_path が "src/foo.ts"（runtime/ 外）
    When PreToolUse.sh が R1・R2 を評価する
    Then R1 非該当・R2 は IS_SUBAGENT=1 で除外され allow される
```

#### ユースケース 2: timestamp memo 保護が全 ROLE で効く（R1 全 ROLE の理由）

**シナリオ 1: worker でも memo timestamp の自由入力 Write は block**

```gherkin
Feature: timestamp memo 保護は全 ROLE
  Scenario: worker が memo/YYYYMMDD_HHMMSS_*.md を自由入力 Write する
    Given IS_SUBAGENT=1 の worker
    And tool_name が "Write" で file_path が ".agent-skill-chain/runtime/<issue>/memo/20260713_041110_x.md"
    When PreToolUse.sh が R1 を評価する
    Then block される（memo は new-workflow-memo.sh 等・システム時計経由のみ。R1 全 ROLE の主要な正当理由）
```

#### ユースケース 3（新規スコープ）: 「バグ/矛盾」断定前の横断確認

**シナリオ 1: 関連ルールを横断確認せずに矛盾と断定することを禁止する**

```gherkin
Feature: 部分的な読みでの矛盾・バグ断定を禁止する
  Scenario: AI エージェントが同一機構内の 1 ルールのみを読んで矛盾を主張しようとする
    Given AI エージェントが PreToolUse.sh の R1（runtime/ 全 ROLE 禁止）を読み「設計文書の worker 許可規定と矛盾する」と考えている
    And 同一ファイル内に R2（IS_SUBAGENT 除外）・R3(b)（Bash 許可）という関連ルールが存在する
    When AI エージェントが「バグ/矛盾」と結論づけようとする
    Then 明文化された調査規律により、結論づける前に R2・R3(b) 等の関連ルール・例外コメントの有無を横断確認することが要求される
```

**シナリオ 2: 意図的な非対称性を示す明示コメントがある場合はバグと断定しない**

```gherkin
Feature: 明示コメントの確認によりバグ断定を回避する
  Scenario: 対象ルールに「全 ROLE」「対象外」等の明示コメントが付与されている
    Given R1 のコメントに「（全 ROLE）」という意図的適用範囲の明示がある
    When AI エージェントが横断確認規律に従い当該コメントを確認する
    Then 「バグではなく意図的設計」と正しく判断し、誤った「矛盾/バグ」の断定を行わない
```

### 2.3 ビジネスルール

- R1（path-axis）と R2（role-axis）は目的の異なる独立ガードであり、非対称は意図的。
- subagent の runtime/ 書き込みは Bash が正規ルート。Edit/Write の直接使用は runtime/ 外に限る。
- 判定ロジックの実体は PreToolUse.sh のみに集約（DESIGN.md L49）。
- 「バグ/矛盾」の断定は、同一ファイル・同一機構内の関連ルール（分岐条件・例外コメント等）を横断確認した後にのみ行う（新規ビジネスルール）。

## 5. 制約事項

- コード修正は不要かつ範囲外。ドキュメント追記のみ。
- 調査規律の配置先（EVIDENCE_POLICY.md / REVIEW_RULE.md / 両方）は design-feature（02_設計.md）で ADR 形式により決定する（本 01 では決定しない）。
- 追記は要点のみとし、既存節（EVIDENCE_POLICY.md の節1〜節5・REVIEW_RULE.md の既存チェックリスト）の重複再定義をしない。

### 未検証・要人間確認事項（inference_only）

- **agent_id 注入の公式仕様**: Claude Code が stdin トップレベルに `.agent_id` を注入することは DESIGN.md ADR-2 の記述とフィールド報告の症状整合からの推定であり、公式 hook API ドキュメントに対する独立再検証は本 issue では未実施。R1/R2/R3 の挙動理解自体はこの前提の成否に依らず（agent_id 非伝達時は IS_SUBAGENT=0 で保守側に倒れる）成立する。
- **調査規律の適用範囲**: EVIDENCE_POLICY.md は現状「requirement-discovery / design-feature を実行するサブエージェント」に節1 の義務を限定しているため、review-code・verify-and-close 等の他 command にもこの横断確認規律を及ぼすべきかは、design-feature の ADR で判断する（本 01 では決定しない）。
