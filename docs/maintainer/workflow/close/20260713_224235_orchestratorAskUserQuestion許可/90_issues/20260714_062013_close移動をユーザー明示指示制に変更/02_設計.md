## 1. 設計概要

### 1.1 設計方針

完了 issue の `close/` 移動における「**完了検知**」と「**移動（`git mv`）の実行確定**」を明確に分離する。**完了検知（verify-and-close 完了判定・CI 督促 #33）は一切変更しない**。変更するのは「進行役が完了を自己判定したら direct push で `git mv` を確定する」という**実行確定経路のみ**であり、これを **GitHub 連携有無で 2 分岐**させる。

- **分岐 A（GitHub 連携時）**: `close/` への移動は **PR 経由に統一**する。進行役は完了検知後に移動作業（feature branch 作成・リンク補正・`git mv`）に着手する自動性を保ちつつ、確定手段を direct push から **PR マージ**へ変更する。
- **分岐 B（GitHub 非連携時）**: PR という確定手段が存在しないため、完了検知だけでは移動せず、**ユーザーの明示指示**（構造化確認 `AskUserQuestion` の肯定応答、または明示コマンド句）を受けてから `git mv` を実行する。

配置境界は既存パターンを厳守する。**汎用原則は `.agent-skill-chain/source/workflow/PHASES.md`（コア）**に、**本リポ固有の具体手順・判定シグナル・PR/AskUserQuestion 手順は `.agent-skill-chain/project/自己拡張ワークフロー.md`（project）**に書く。`boot/CORE.md`（宣言）・`enforcement/README.md` #33（CI 仕様）・`enforcement/ci/audit.sh`（実装）は**変更しない**。

### 1.2 設計原則（本プロジェクトで適用するもの）

- **単一責務・1 ファイル 1 責務**: トリガー定義の正本は PHASES.md 1 か所。project は「配置先＋固有具体手順」のみを担い、原則を重複再定義しない（既存の close 移動節の分担をそのまま踏襲）。
- **明確な境界（コア抽象／project 具体）**: 「GitHub 連携有無で実行経路が分岐する」という**原則**はコア（PHASES.md）。`git remote -v` の実コマンド・`gh pr create` 手順・`AskUserQuestion` の具体は project。
- **重複実装の回避**: GitHub 連携判定シグナルは、既存の GitHub Issue 起票ゲート（自己拡張ワークフロー.md §3「対応判定・到達性」）および コア audit.sh #34 SKIP 判定と**同一シグナル**（`git remote -v` に `github.com` を含むか）を**参照のみ**で再利用し、新規判定ロジックを実装しない。
- **既存不変条件の保全**: 移動前リンク補正の「移動前に完結・移動後の close/ 配下は Read/Grep/Glob しない」という強制手順（`.claude/settings.json` の deny 対応）を破らない。

## 3. インターフェース／契約（トリガー契約）

本 issue は API を新設しないが、「進行役が close 移動を実行してよい条件」を**契約**として定義する。契約の消費者は進行役（orchestrator）と CI（#33）。

### 3.1 実行確定トリガー契約

| 分岐 | 入力（前提） | 実行可否 | 確定手段 | 契約違反（禁止挙動） |
| --- | --- | --- | --- | --- |
| A: GitHub 連携（`git remote -v` に `github.com`） | トップレベル完了検知済み | 移動作業への着手は可・確定は PR マージ後のみ | feature branch → リンク補正（移動前）→ `git mv` → `gh pr create` → レビュー → マージ | main への direct push で close 移動を確定する |
| B: GitHub 非連携 | トップレベル完了検知済み | ユーザー明示指示（AskUserQuestion 肯定応答 or 明示コマンド句）まで移動不可 | 明示指示受領後にリンク補正（移動前）→ `git mv` | 指示を推測して自動移動する／完了検知のみで移動する |

### 3.2 完了検知契約（不変・再掲）

- 完了＝verify-and-close 完了（issue 直下 04_review.md 作成＋write-workflow-log 記録）かつトップレベルとして残タスク・未完了サブ issue が無い（PHASES §完了の定義）。**本 issue で変更しない。**
- CI #33（`check_close_move_pending`）は「完了済みだが未移動・猶予超過」を**検知するのみ**（`git mv` を強制しない・Query 専任）。**本 issue で変更しない。**

### 3.3 契約違反時の扱い

- 分岐 A で direct push が行われた場合: プロセス違反として PR 経由へ是正（機械強制は無い＝enforcement #24「高リスク前確認省略」/#25 と同型の人手監査領域。ただし #36 PR 紐づけ・通常の PR 運用が実質的な抑止として働く）。
- 分岐 B で推測移動が行われた場合: 同じく人手監査領域（機械検知の痕跡を残さないため。00 リスク 1 対策として「AskUserQuestion 構造化確認 or 明示句のみを指示とみなす」ことを文書で一意化する）。

## 5. 設計判断（ADR）

> 形式は [EVIDENCE_POLICY.md](../../../../../../../.agent-skill-chain/source/EVIDENCE_POLICY.md) の ADR に準拠。各 ADR に evidence_source を付す。

### ADR-1: 完了検知と移動実行確定を分離し、検知ロジックは一切変更しない

- **決定**: 完了検知（verify-and-close DoD・CI #33）は不変とし、変更は `git mv` の実行確定経路のみに限定する。
- **理由**: 00 の要求（完了検知は維持・変更は実際の移動トリガー）と一致。検知ロジックを触ると grandfather/猶予/order 監査の既存テストに波及し、変更範囲が肥大化する。責務分離により影響範囲を最小化できる。
- **代替案**: 完了判定に「ユーザー承認済みフラグ」を組み込む案 → 完了定義そのものを汚染し監査 #33 の意味が変質するため却下。
- **evidence_source**: repo_file, `00_要求定義.md:67`（完了検知自体はいずれの分岐でも維持）／`.agent-skill-chain/source/enforcement/ci/audit.sh:979-1015`（#33 は 04_review.md 検出＋猶予判定のみで `git mv` を強制しない Query 専任実装）。

### ADR-2: GitHub 連携有無で実行確定を 2 分岐させる（分岐 A=PR 統一／分岐 B=ユーザー明示指示）

- **決定**: 分岐 A（GitHub 連携）は PR 経由に統一し direct push を排す。分岐 B（非連携）はユーザー明示指示を必須とする。
- **理由**: ユーザーが本セッションで「デフォルトでは PR 経由に統一すべき（GitHub 連携時の話）。連携していない場合は明示的に close しないといけない」と決定した。PR という人間関与点は連携時にのみ存在するため、非連携時は別の人間関与点（明示指示）で代替するのが自然。
- **代替案**: 全環境で「ユーザー明示指示のみ」に一本化 → 連携時に PR レビューという既存の強い関与点を捨てることになり、また既存の PR 運用（#36 等）と二重の確認になるため却下。
- **evidence_source**: human_decision, 本セッションのユーザー発言（00_要求定義.md:79 に記録）。

### ADR-3: GitHub 連携判定シグナルは既存シグナルを参照のみで再利用する

- **決定**: `git remote -v` に `github.com` を含むか、を判定シグナルとし、自己拡張ワークフロー.md §3 および audit.sh #34 と同一のものとして参照する。新規判定ロジックは実装しない。
- **理由**: 判定ロジックの重複実装を避け（00 効果 4）、将来シグナルを変更する際の単一情報源を保つ。既に §3 が ADR-4 として同シグナルを正本化している。
- **代替案**: `gh auth status` を併用した厳密判定 → §3 が既に「一時障害と恒久非採用を区別」する方針を持ち、close 移動トリガーでその厳密性は過剰。恒久非採用の判定は remote シグナルで十分。
- **evidence_source**: repo_file, `.agent-skill-chain/project/自己拡張ワークフロー.md:77`（`git remote -v` に github.com を含むかで GitHub 採用を判定・ADR-4）／`.agent-skill-chain/source/enforcement/ci/audit.sh:1044`（`git remote -v | grep github.com` の #34 SKIP 判定）。

### ADR-4: 配置境界＝原則はコア（PHASES.md）・具体は project、CORE/enforcement/audit.sh は不変

- **決定**: 「連携有無で分岐する」原則は PHASES.md に、実コマンド・PR/AskUserQuestion 手順は自己拡張ワークフロー.md に書く。CORE.md 宣言・enforcement/README.md #33・audit.sh は変更しない。
- **理由**: 既存の close 移動節が「宣言=CORE／ライフサイクル原則=PHASES／具体=project」の 3 層分担を確立しており（1 ファイル 1 責務・重複禁止）、これを踏襲するのが最小差分かつ整合的。トリガー分岐は「いつ・どう移動するか」＝ライフサイクル詳細なので PHASES の責務であり、宣言（CORE）は不変でよい。
- **代替案**: CORE.md 宣言にも分岐を書く → 宣言とライフサイクルの二重定義になり重複禁止に反するため却下。
- **evidence_source**: repo_file, `.agent-skill-chain/source/boot/CORE.md:138-140`（宣言のみ・いつ/どう移動するかは PHASES へ委譲）／`.agent-skill-chain/source/workflow/PHASES.md:71`（宣言は CORE・本節はライフサイクル）。

### ADR-5: CI 督促 #33 は現状維持（コード・仕様不変）、猶予の意味のみ運用上再解釈する（FR-2）

- **決定**: `check_close_move_pending`・`CLOSE_MOVE_GRACE_DAYS`・grandfather・Query 専任方針・FAIL メッセージをすべて**変更しない**。猶予期間の意味を「進行役が自発移動するまで」から「分岐 A=PR マージ完了まで／分岐 B=ユーザー指示→移動まで」へ**運用解釈のみ**変更する。
- **理由**: #33 は `git mv` を強制せず「完了済みなのに未移動」を検知するだけの Query であり、トリガーを変えても「完了 issue の整理漏れを督促する」目的は不変。むしろ分岐 B で「完了したがユーザー指示待ち」の状態を**可視化し続ける**リマインダとして有用（放置防止）。コードを触ると grandfather/猶予/ts 解析の既存挙動に波及するため、無変更が最小リスク。FAIL メッセージ（「verify-and-close 完了だが close/ 未移動・猶予超過」）は分岐後も文言として正確なため改訂不要。
- **リスクと対応**: 分岐 B でユーザー指示前に猶予超過し FAIL しうる（00 リスク 2）。これは「督促」として意図通りの挙動であり、#33 は移動を強制しない（Query 専任）ため待機自体はブロックされない。閾値変更・分岐別メッセージ化（00 FR-2(b)）は**採用しない**（scope 肥大・審査済みロジックの破壊リスク回避）。
- **代替案**: 分岐 B で grace を延長／非連携時 SKIP を audit.sh に追加 → 検知ロジック改変となり ADR-1（検知不変）と矛盾、かつ「完了放置」を見逃す穴を作るため却下。
- **evidence_source**: repo_file, `.agent-skill-chain/source/enforcement/README.md:299`（close 移動という状態変更自体＝git mv は #33 の対象外・検知のみ・Query に徹する）／`.agent-skill-chain/source/enforcement/ci/audit.sh:1007-1012`（FAIL 時も EXIT_CODE=1 を立てるのみで `git mv` を実行しない）。

### ADR-6: PR 経由統一の採否＝GitHub 連携時のみ採用（FR-3）

- **決定**: 「close 移動を PR 経由に統一する」は分岐 A（GitHub 連携時）でのみ採用する。分岐 B ではユーザー明示指示で代替する。
- **理由**: PR は GitHub 連携時にのみ存在する仕組み。過去の direct push 事例（`41d2722`＝親コミット単一・PR 非経由）の再発を、連携時は PR ゲートで、非連携時は明示指示ゲートで、それぞれ塞ぐ。既存の PR 運用（PR #38 等・#36 PR 紐づけ監査）と自然に接続する。
- **代替案**: 非連携でも「ローカルレビュー branch」を必須化 → PR レビューという実効性のある人間関与が無いローカル branch は形骸化しやすく、ユーザー明示指示の方が意図に忠実。
- **evidence_source**: repo_file, `00_要求定義.md:113`（FR-3・PR 統一は GitHub 連携時のみ）／`git show --stat 41d2722`・`git log -1 --format=%P 41d2722`（00_要求定義.md:199 に記録された direct push 事例の一次確認）。

### ADR-7: 分岐 B の「明示指示」は AskUserQuestion 構造化確認または明示コマンド句に限定する（リスク 1 対策）

- **決定**: 分岐 B で移動を許可する「明示指示」は、(i) `AskUserQuestion` の肯定応答、または (ii) 移動を一意に指示する明示コマンド句（「close へ移動して」等）に限定し、文脈からの推測を指示とみなさない。
- **理由**: 「指示があったと誤認して自動移動」する誤動作（00 リスク 1）を防ぐため、指示の判定を曖昧にしない。親 issue で `AskUserQuestion` が orchestrator の allowlist に追加済みのため、進行役から構造化確認を発話できる（本サブ issue はその活用先の 1 つ）。
- **代替案**: 自由発話の意図解釈に委ねる → 誤認リスクが残るため却下。機械強制（audit チェック新設）→ 発話は痕跡を残さず機械検知不能（#22-#24 と同型）なため文書規約＋人手監査に留める。
- **evidence_source**: repo_file, `00_要求定義.md:176-177`（リスク 1 と対策）／親 issue `02_設計.md`（AskUserQuestion を orchestrator allowlist へ追加する設計）。

### ADR-8: 消費者ランタイム（汎用パッケージ標準）への反映は原則の自動適用に留め、本 issue で具体実装しない

- **決定**: PHASES.md に書く分岐原則はコアなので消費者ランタイムにも自動的に適用される。消費者ランタイム固有の具体シグナル/PR 手順は各消費者の `.agent-skill-chain/project/` 上書きに委ねる。本 issue では消費者ランタイムの `close/` 運用へ個別の実装追加を行わない。
- **理由**: 00 §5 で「消費者ランタイム側への反映要否は ADR 化に留め実装を確約しない」と定めた。コア原則が委譲構造（具体は project）を保つ限り、消費者は自リポの project 上書きで具体化できるため、本 issue でのコア変更だけで汎用性は担保される。
- **代替案**: コアに消費者向け具体手順まで書く → コア抽象/project 具体の境界を崩すため却下。
- **evidence_source**: repo_file, `00_要求定義.md:129,159`（消費者ランタイム反映は 02 で ADR 化・実装非確約）。

### ADR-9: 移動前リンク補正の「移動前完結・移動後 close/ 非読取」不変条件を分岐 A/B とも維持する

- **決定**: 分岐 A では feature branch 上で `git mv` を行う前に、既存 §close 移動時の相対リンク補正 手順（列挙→分類→編集→移動前検証）を完結させる。分岐 B も同様に移動前に完結させる。移動後の `close/` 配下への Read/Grep/Glob は両分岐とも禁止。
- **理由**: `.claude/settings.json` の `close/` 配下 deny により移動後検証は環境によりブロックされる（must-preserve）。PR 化しても `git mv` の実行自体は変わらないため、既存の移動前完結手順を PR フローに内包するだけでよい。
- **代替案**: PR の CI で移動後にリンク検証 → deny 環境で実行不能になりうるため却下。
- **evidence_source**: repo_file, `.agent-skill-chain/source/workflow/PHASES.md`（検証は必ず移動前に行う・強制）／`.agent-skill-chain/project/自己拡張ワークフロー.md` §close 移動時の相対リンク補正（手順 6・移動後の禁止事項）。
