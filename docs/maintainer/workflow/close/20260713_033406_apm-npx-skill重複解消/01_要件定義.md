# 要件定義書: apm と npx 導線併用時のスキル二重コピー解消

## 1. 概要

### 1.1 システム概要

本パッケージ（agent-skill-chain）は 3 導線で配布される: apm（一次配布・推奨）・npx（GitHub 直接参照・補助）・Claude marketplace（副）。apm と npx を併用すると、両導線が**同一の `.claude/skills/` ディレクトリ**へ**異なる命名規則**で同じスキルを配備し、Claude Code が同一スキルを 2 件として認識する（二重コピー）。本 issue は原因を確定し、解消のための受け入れ基準を定義する。修正方式の決定は後続フェーズ（design-feature）。

### 1.2 用語集

| 用語 | 説明 |
| ---- | ---- |
| npx 導線 | `npx github:techbeansjp-free/AGENTS.md <cmd>`。内部で `setup.sh` を実行し `.claude/skills/`・`.cursor/skills/` へスキルを同期する |
| apm 導線 | `apm install ...`。Claude ターゲットでは `.claude/skills/` へスキルを配備する |
| ダブルアンダースコア名 | npx 側の配備名 `{domain}__{capability}`（例: `architecture__define-boundaries`） |
| ハイフン名 | apm 側の配備名 `{domain}-{capability}`（apm が `__`→`-` 正規化。例: `architecture-define-boundaries`） |
| 所有集合 | `list_owned_skill_names` が返す npx 側が管理するスキル名集合（ダブルアンダースコア名） |
| 二重コピー | 同一 `.claude/skills/` に同じスキルが別名で 2 件存在し Claude Code が別スキルとして数える状態 |

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: 推奨手順どおりの導入で重複しない

- **As a** 本パッケージの利用者（Claude Code ユーザー）
- **I want to** README の推奨手順（apm＋必要に応じて npx）どおりに導入しても、スキルが二重にならないこと
- **So that** Claude Code のスキル一覧が汚染されず、skill chain が正しく機能する

**受け入れ基準**:

- 採用方針適用後、apm 導線と npx 導線の両方を実行しても `.claude/skills/` に同一スキルの別名コピーが 0 件である。
- 認識スキル数がパッケージ所有スキル数（15 件＋バンドル）を超えない。

#### ストーリー 2: 再同期・アップグレードで再発しない

- **As a** 本パッケージの利用者
- **I want to** `npx upgrade` や `apm install` の再実行を繰り返しても重複が再発しないこと
- **So that** アップグレード運用が安全（冪等）である

**受け入れ基準**:

- 採用方針適用後、いずれの導線を複数回再実行しても `.claude/skills/` の同一スキル別名コピーは 0 件のまま（冪等）。
- ユーザー自作スキル（所有集合外のディレクトリ）は再同期後も保持される。

#### ストーリー 3: 単独導入の後方互換

- **As a** apm 単独／npx 単独の既存利用者
- **I want to** これまでどおり単独導線での導入が壊れないこと
- **So that** 併用問題の修正が既存利用者に副作用を与えない

**受け入れ基準**:

- npx 単独導入・apm 単独導入それぞれで、スキルが正しく（重複なく）配備される。
- enforcement・契約本体・管理 CLI を必要とする利用者が npx 導線で従来どおり全機能を得られる。

#### ストーリー 4: 導線設計とドキュメントの整合

- **As a** 保守者
- **I want to** 「どの機能をどの導線で配るか」と README の推奨表記が実態と一致していること
- **So that** 利用者が README どおりに操作して不具合に陥らない

**受け入れ基準**:

- 採用方針に応じ README・apm-package.md・adapters.md が更新され、apm がスキルのみ／npx が契約本体＋enforcement＋CLI という役割と、併用時の扱いが明記される。

#### ストーリー 5: 既存の重複プロジェクトの是正

- **As a** 既に併用して重複が発生している利用者
- **I want to** 重複コピーを掃除する手段があること
- **So that** 既存プロジェクトを修正後の正常状態へ移行できる

**受け入れ基準**:

- 重複を除去する手順またはコマンドが提供され、実行後 `.claude/skills/` の別名コピーが 0 件になる（ユーザー自作スキルは保持）。

### 2.2 BDD ユースケース

#### ユースケース 1: 併用時にスキルが重複しない

**シナリオ 1: apm 導入後に npx init しても重複しない（採用方針適用後）**

```gherkin
Feature: apm と npx の併用でスキルが二重コピーされない
  Scenario: apm 導入済みプロジェクトへ npx init
    Given apm install（Claude ターゲット）でスキルが .claude/skills/ に配備済みである
    And 採用された修正方針が適用されている
    When npx github:techbeansjp-free/AGENTS.md init を実行する
    Then .claude/skills/ に同一スキルの別名コピー（ダブルアンダースコア名とハイフン名の重複）が 0 件である
    And Claude Code が認識するスキル数がパッケージ所有スキル数を超えない
```

**シナリオ 2: 現状（未修正）の再現＝バグの定義**

```gherkin
Feature: 現状の二重コピー（是正対象の振る舞い）
  Scenario: 修正前は併用で重複する
    Given 修正が未適用である
    And apm install（Claude ターゲット）で .claude/skills/ にハイフン名スキルが配備されている
    When npx init（setup.sh の sync_skills）を実行する
    Then .claude/skills/ にダブルアンダースコア名スキルが追加される
    And 同一スキルがハイフン名とダブルアンダースコア名の 2 件として共存する
    And Claude Code は約 30 skills を認識する
```

（evidence_source: observed_runtime＝フィールド報告、existing_code＝setup.sh/deploy-skills.sh、external_spec＝apm 公式。end-to-end 実機再現は要人間確認）

#### ユースケース 2: 再同期の冪等性

**シナリオ 3: 繰り返し再同期しても重複しない**

```gherkin
Feature: 再同期の冪等性
  Scenario: upgrade / apm install の反復
    Given 採用された修正方針が適用されている
    When npx upgrade と apm install を任意の順序で複数回実行する
    Then 各実行後も .claude/skills/ の同一スキル別名コピーは 0 件である
    And ユーザー自作スキル（所有集合外）は削除されずに保持される
```

**シナリオ 4: 現状の恒久再発（是正対象）**

```gherkin
Feature: 現状の恒久再発
  Scenario: 片方の再同期は相手の別名コピーを消さない
    Given .claude/skills/ にハイフン名（apm 由来）とダブルアンダースコア名（npx 由来）が共存している
    When npx upgrade を実行する
    Then npx は所有集合（ダブルアンダースコア名）のみ削除→再配備する
    And apm 由来のハイフン名コピーは所有集合外のため削除されずに残る
    And 重複が解消されない
```

#### ユースケース 3: 単独導入の後方互換

**シナリオ 5: npx 単独・apm 単独は重複しない**

```gherkin
Feature: 単独導入の後方互換
  Scenario Outline: 単独導線
    Given 修正方針が適用されている
    When <導線> のみで導入する
    Then .claude/skills/ に重複コピーは存在しない
    And 当該導線が本来配れる成果物が配備される
    Examples:
      | 導線     |
      | npx 単独 |
      | apm 単独 |
```

#### ユースケース 4: 既存重複プロジェクトの是正

**シナリオ 6: 掃除手段で重複を除去できる**

```gherkin
Feature: 既存重複の是正
  Scenario: 重複掃除
    Given 併用により .claude/skills/ に別名コピーが共存している
    When 提供される是正手順（コマンド等）を実行する
    Then 重複した別名コピーが除去され同一スキルが 1 件になる
    And ユーザー自作スキルは保持される
```

### 2.3 ビジネスルール

- **BR1**: 命名規約の単一正本は `lib/deploy-skills.sh`。修正方針が命名変更を伴う場合も、正本の一元化原則を崩さない。
- **BR2**: 保持・上書き契約（ユーザー自作スキル・独自フック・project 資産を無断破壊しない）を崩さない（正本: SETUP.md）。
- **BR3**: apm 本体（microsoft/apm）の仕様は外部依存であり、本パッケージ側で apm の挙動変更を前提とした解決策は採らない。
- **BR4**: 修正方針の採否は本 issue では決定せず、design-feature／human_decision に委ねる。フィールド報告の「apm 廃止」案も他案と同格の一選択肢として扱う。

## 3. 非機能要件

### 3.1 パフォーマンス要件

- 導入・再同期の所要時間を実質的に悪化させない。

### 3.2 セキュリティ要件

- 既存の fail-closed（`.package-manifest` 検証）・保持契約を踏襲する。新規のセキュリティ後退を生まない。

### 3.3 ユーザビリティ要件

- README の推奨手順どおりに操作した利用者が二重コピーに遭遇しない。
- 併用時の扱い（重複が起きる／起きない条件）がドキュメントで明確である。

### 3.4 可用性要件

- 単独導線・併用導線のいずれでもスキル配備が決定的（冪等）に完了する。

---

## 4. 外部インターフェース要件

### 4.1 API 要件

- apm CLI（`apm install --target ...`）の挙動: Claude ターゲットは `.claude/skills/` へ、他ハーネスは `.agents/skills/` へ配備（external_spec: apm 公式）。この外部契約を前提とする。
- npx CLI（`agents-md init/upgrade/uninstall`）: `setup.sh` 経由で `.claude/skills/`・`.cursor/skills/` を選択的同期（existing_code）。

### 4.2 データ形式要件

- スキルは Agent Skills 形式（SKILL.md ＋ YAML frontmatter）。frontmatter `name` はディレクトリ名にかかわらず正本のまま（apm 公式もディレクトリ名優先）。
- apm ディレクトリ名規則: 小文字英数字とハイフンのみ・連続ハイフン禁止（external_spec）。これにより `{domain}__{capability}` は apm 側でそのまま維持不可。

---

## 5. 制約事項

- **C1**: apm ではスキルディレクトリ名にダブルアンダースコアを使えない（external_spec: 連続ハイフン禁止・ハイフンのみ）。命名統一案は npx→ハイフン方向のみ可能。
- **C2**: apm v1 スコープはスキルのみ。`AGENTS.md`/`CLAUDE.md`・enforcement・管理 CLI は npx でしか配備できず、フル機能利用者は npx が実質必須（existing_code, external_spec）。→ 「apm 単独で完結」は成立しない前提。
- **C3**: Claude は `.claude/skills/` を走査（`.agents/skills/` は非対象）。よって apm も Claude 向けには `.claude/skills/` に置くため、npx と物理的に同じディレクトリを共有する（external_spec）。
- **C4**: apm CLI がローカル未導入のため、併用の end-to-end 実機再現・命名統一の統合挙動は未検証（要人間確認・inference_only）。design-feature で apm CLI を用いた tmp 隔離検証を必須とする。
- **C5**: 現行の「apm・npx・.adapters は独立チャネルとして共存」という設計判断（apm-package.md／adapters.md）は併用重複を検討していない。設計見直しの対象になりうる。
