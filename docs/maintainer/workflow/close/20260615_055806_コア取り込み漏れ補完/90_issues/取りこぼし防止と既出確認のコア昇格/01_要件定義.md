## 1. 概要

### 1.1 システム概要

本サブ issue は、AGENTS.md パッケージのコア（`.agents/`）に対し、クローズアウト工程における 2 つの汎用原則――(1) **取りこぼし0（no-drop）**: クローズ時のフォローアップ/残件を散文・memo 言及で終わらせず必ず追跡可能な issue/サブ issue に落とす、(2) **既出確認（dedup スキャン）**: 起票前に issue ツリーの先祖・兄弟・子孫を機械的に走査し、既出なら新規起票せず既存へ紐付ける――を昇格・明文化することを目的とする。両者は「落とし忘れ防止」と「起票しすぎ防止」の対の原則であり、`.agents/REVIEW_DUAL_LENS.md` の churn 防止と同型の緊張関係として記述する。

grep 確認の事実: `.agents/` 配下で `取りこぼし / 既出確認 / 重複起票 / 二重起票 / 先祖 / 兄弟 / 子孫 / 申し送り` は 0 ヒットであり、両原則が完全欠落している。コアは 90_issues.md の出力要件（`.agents/commands/implement-feature.md:49,58`）しか持たない。

本 issue の範囲は**要求・要件まで**。具体配置（`implement-feature.md §クローズアウト` の新節 か 独立コアファイル化 か）は設計フェーズ（02_設計）で親 issue の S5「構造是正」との関係を踏まえて決める。

### 1.2 用語集

| 用語 | 説明 |
| ---- | ---- |
| 取りこぼし0（no-drop） | クローズ時に挙がったフォローアップ/残件を、散文・memo 言及だけで終わらせず、必ず追跡可能な issue/サブ issue に落とす原則 |
| 既出確認（dedup スキャン） | 起票前に issue ツリーの先祖・兄弟・子孫を機械的に走査し、既出なら新規起票せず既存へ紐付ける原則 |
| 先祖 / 兄弟 / 子孫 | 起票対象 issue から見た親系列（ancestors）/ 同階層（siblings）/ 子系列（descendants）の issue ツリー範囲 |
| 追跡可能 issue | issue/サブ issue として正式に起票され、ツリー上で検索・追跡できる状態。散文・memo 言及はこれに該当しない |
| churn | 起票しすぎ・蒸し返し等により無駄な作業が増える状態。取りこぼし0 と dedup の対で抑止する |
| PF 中立 | コアが特定プラットフォーム・固有値に依存しない抽象原則のみを持つ状態 |

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: 取りこぼし0（no-drop）のコア化

- **As a** フレームワークの保守者（およびクローズアウトを実行するエージェント）
- **I want to** クローズ時に挙がったフォローアップ/残件を必ず追跡可能な issue に落とすことをコアの普遍ルールとして参照できるようにしたい
- **So that** フォローアップが散文・memo に埋もれて追跡不能になる「取りこぼし」を構造的に防げる

**受け入れ基準**:

- コア（`.agents/`）に「フォローアップは追跡可能 issue に必ず落とす（取りこぼし0）」原則が抽象形で 1 か所明文化されている。
- 散文・memo 言及だけで残件を処理することが no-drop 違反である旨が明記されている。
- 親 issue がある場合は課題有無に関わらず 90_issues 更新が必須である旨が、既存の 90_issues 出力要件と矛盾なく示されている（再定義ではなくリンク委譲でも可）。

#### ストーリー 2: 既出確認（dedup スキャン）のコア化

- **As a** 新規 issue を起票するエージェント
- **I want to** 起票前に先祖・兄弟・子孫を機械的に走査し既出を検出する手順をコアの普遍ルールとして参照できるようにしたい
- **So that** 同一論点の二重起票を防ぎ、既存 issue へ正しく紐付けられる

**受け入れ基準**:

- コアに「起票前に先祖・兄弟・子孫を走査し、既出（追跡可能 issue が存在）なら新規起票せず既存へ紐付ける」原則が抽象形で明文化されている。
- 記述はあるが追跡可能 issue 化されていない場合は、出自パスを参照に明記して起票してよい旨が記載されている。
- 走査は機械的（grep 等）に行う旨が示されている（具体コマンド・パスはコアに固定しない）。

#### ストーリー 3: 対の原則としての記述

- **As a** フレームワークの保守者
- **I want to** 取りこぼし0 と dedup を対の原則として記述したい
- **So that** 片方だけの強化による churn（過剰起票・落とし忘れの偏り）を防げる

**受け入れ基準**:

- 取りこぼし0（落とし忘れ防止）と dedup（起票しすぎ防止）が緊張関係にある対の原則として本文に表現されている。
- `.agents/REVIEW_DUAL_LENS.md` の churn 防止と同型である旨が示されている（リンク委譲可）。

#### ストーリー 4: PF 中立性の維持

- **As a** パッケージ配布の責任者
- **I want to** 昇格時に固有値をコアへ混入させないようにしたい
- **So that** コアのマルチプラットフォーム中立性と 1 ファイル 1 責務を維持できる

**受け入れ基準**:

- 具体ファイル名・90_issues パス・タグ運用・grep の具体コマンド等の固有値がコアに混入していない。
- 既存正本（REVIEW_RULE / RULES / run_command §Constraints / REVIEW_DUAL_LENS 等）へリンク委譲し、定義を 2 か所に重複させていない。

### 2.2 BDD ユースケース

#### ユースケース 1: 取りこぼし0 原則のコア参照

クローズアウト時にフォローアップ/残件が発生したとき、それを追跡可能 issue に落とすことをコアの原則から確認できる。

**シナリオ 1: フォローアップを追跡可能 issue に落とす**

```gherkin
Feature: 取りこぼし0（no-drop）のコア化
  Scenario: クローズ時のフォローアップを追跡可能 issue に落とす
    Given クローズアウト工程でフォローアップ/残件が挙がっている
    When エージェントがコアのクローズアウト原則を参照する
    Then 「散文・memo 言及だけで終わらせず追跡可能 issue に落とす」no-drop 原則が読み取れる
    And 親 issue があれば 90_issues 更新が必須である旨が確認できる
```

**シナリオ 2: memo 言及だけでの残件処理を検出**

```gherkin
Feature: 取りこぼし0（no-drop）のコア化
  Scenario: memo 言及だけの残件処理が no-drop 違反だと判定できる
    Given 残件が memo にのみ記載され追跡可能 issue 化されていない
    When コアの no-drop 原則に照らす
    Then その状態が取りこぼし（no-drop 違反）であると判定できる
```

#### ユースケース 2: 既出確認（dedup スキャン）

新規起票の前に先祖・兄弟・子孫を走査し、既出を検出して二重起票を防ぐ。

**シナリオ 1: 既出なら新規起票せず紐付け**

```gherkin
Feature: 既出確認（dedup スキャン）のコア化
  Scenario: 既出の追跡可能 issue が見つかったら新規起票しない
    Given 起票しようとする論点について先祖・兄弟・子孫を機械的に走査する
    When 既出の追跡可能 issue が見つかる
    Then 新規起票せず既存 issue へ紐付ける
```

**シナリオ 2: 記述はあるが issue 化されていない場合**

```gherkin
Feature: 既出確認（dedup スキャン）のコア化
  Scenario: 記述はあるが追跡可能 issue 化されていない場合は出自を参照に起票
    Given 先祖・兄弟・子孫の走査で論点の記述は見つかるが追跡可能 issue は存在しない
    When 新規起票する
    Then 出自パスを参照に明記して起票する
```

#### ユースケース 3: 対の原則と PF 中立の両立

**シナリオ 1: 対の原則として記述されている**

```gherkin
Feature: 対の原則としての記述
  Scenario: 取りこぼし0 と dedup が対で記述される
    Given コアのクローズアウト/起票原則を参照する
    When 取りこぼし0 と dedup の記述を確認する
    Then 両者が「落とし忘れ防止」と「起票しすぎ防止」の対の原則（churn 防止と同型）として表現されている
```

**シナリオ 2: 固有値が混入していない**

```gherkin
Feature: PF 中立性の維持
  Scenario: コアに固有値が混入していない
    Given 昇格後のコア記述を確認する
    When 具体ファイル名・90_issues パス・具体 grep コマンド等の固有値を探す
    Then それらはコアに存在せず、既存正本/.agents-project へリンク委譲されている
```

### 2.3 ビジネスルール

- コアは抽象原則のみを持ち、固有値・具体パス・具体コマンドは置かない（PF 中立）。
- 既存正本（REVIEW_RULE / RULES / run_command §Constraints / REVIEW_DUAL_LENS）へリンク委譲し、定義を 2 か所に重複させない（1 ファイル 1 責務・重複禁止）。
- 取りこぼし0 と dedup は必ず対で記述する（片方のみの強化を禁止）。
- 本 issue は要求・要件まで。具体配置（新節 or 独立ファイル）は設計フェーズで決める。
- 親の 90_issues.md は本 issue では編集しない（状態列の更新は別サブが一括で行う＝競合回避）。

## 3. 非機能要件

### 3.1 パフォーマンス要件

- 本原則はクローズアウト工程に組み込まれる軽量な規律であり、通常作業のコンテキスト効率を悪化させない。

### 3.2 セキュリティ要件

- 高リスク操作は伴わない。本 issue は要求・要件文書の作成のみで、コア正本への編集は後続フェーズで扱う。

### 3.3 ユーザビリティ要件

- 原則は AI フレンドリーに記述する（小さな責務・明確な意図・1 か所定義）。エージェントが迷わず参照・適用できること。

### 3.4 可用性要件

- 既存クローズアウト節・90_issues 出力要件を破壊せず、欠落分の補完にとどめる（後続フェーズの方針として引き継ぐ）。

## 5. 制約事項

- **PF 中立**: コアは抽象原則のみ。具体ファイル名・90_issues パス・タグ運用・grep 具体コマンド等の固有値はコアに置かない。
- **1 ファイル 1 責務・重複禁止**: 既存正本へリンク委譲する。
- **範囲**: 本 issue は要求・要件まで。02 設計以降で具体配置（新節 or 独立ファイル化）・差分適用を扱う。
- **設計原則**: `.agents/spec/01_設計原則.md`（単一責務・明確な境界・AI フレンドリー設計）、`.agents/spec/06_設計判断の優先順位.md`（可読性 > 単一責務 > 仕様整合性…／再利用のために責務を曖昧にしない）に従う。
- 親の 90_issues.md は本 issue では編集しない。

### 5.x 既出確認（dedup）の結論

本サブ issue 起票にあたり先祖・兄弟・子孫を走査した結果: 親 issue（取り込み漏れ補完）の配下で本件と同主題の追跡可能 issue は未起票。兄弟サブ（S2 verify 報告様式分離 / S3 モデル選定裁量禁止 / S4 must-preserve ラウンド継承 / S5 クローズアウト構造是正）はいずれも別主題で重複なし。関連 close 済み issue `docs/maintainer/workflow/close/20260614_162712_コア取り込み候補調査/` は「4 ポリシーの取り込み調査」であり、本件（取り込み後の漏れ補完）とは別物。よって新規起票が妥当（既存への紐付けではなく新規）と判断した。
