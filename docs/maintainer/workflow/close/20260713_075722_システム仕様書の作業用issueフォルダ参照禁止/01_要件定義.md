# 要件定義書: システム仕様書の作業用 issue フォルダ参照禁止

**プロジェクト名**: システム仕様書の作業用 issue フォルダ参照禁止
**作成日**: 2026 年 07 月 13 日
**最終更新**: 2026 年 07 月 13 日

> **重要**: このドキュメントは常に更新する。実装内容と常に同期させる。

---

## 1. 概要

### 1.1 システム概要

システム仕様書（`docs/` 配下の仕様書。ただし作業用 issue フォルダである `docs/maintainer/workflow/` を除く）およびソースコードのコメント/docstring が、作業用 issue フォルダ（`.agent-skill-chain/runtime/{issue}/` および `docs/maintainer/workflow/{issue}/`）への依存参照を持たないことを、規約（DOCS_NOISE_RULES.md・CODE_COMMENT_RULES.md）で禁止し、CI（audit.sh #37・#26/`check-comment-refs.sh`）で機械検出する。

### 1.2 用語集

| 用語 | 説明 |
| ---- | ---- |
| システム仕様書 | `docs/` 配下の仕様書。それ自体で完結すべき永続文書。 |
| 作業用 issue フォルダ | 消費者標準 `.agent-skill-chain/runtime/{issue}/`、本リポ上書き `docs/maintainer/workflow/{issue}/`。一時的で、完了後 `close/` へ移動される。 |
| issue フォルダ名 | `<timestamp>_<title>` 形式。timestamp は `YYYYMMDD_HHMMSS`（先頭 8 桁が日付）。 |

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: 規約の明文化

- **As a** フレームワークの保守者・利用者
- **I want to** システム仕様書が作業用 issue フォルダを参照してはならないことが規約に明記されている状態
- **So that** レビュー（意味的検証）で違反を判定でき、導入プロジェクトでの再発を防げる

**受け入れ基準**:

- DOCS_NOISE_RULES.md の禁止パターン (iv) 壊れやすい参照の定義が、行番号直リンクに加えて作業用 issue フォルダへの参照を含む。
- 既存 (i)(ii)(iii) の記述は変更されない。1 ファイル 1 責務・重複回避が保たれる。

#### ストーリー 2: 機械監査による強制

- **As a** CI（audit.sh）
- **I want to** システム仕様書ファイルが作業用 issue フォルダへのパス参照を含むかを検出する
- **So that** 違反を FAIL として差し戻せる

**受け入れ基準**:

- 消費者標準パス・本リポ上書きパスの両方を検知対象にする。
- `close/` 参照・汎用ディレクトリ参照を誤検知しない。
- 既存監査番号と衝突しない番号（#37）で追加される。

#### ストーリー 3: コード層の対称強制（追加スコープ）

- **As a** フレームワークの保守者・利用者
- **I want to** ソースコードのコメント/docstring も作業用 issue フォルダへのパス参照を持たない状態を機械的に検証できる
- **So that** docs 層だけでなく code 層でもコメントの陳腐化（issue close によるリンク切れ）を防げる

**受け入れ基準**:

- CODE_COMMENT_RULES.md §2 に作業用 issue フォルダへのパス参照禁止が明記され、§3「他コードファイルへの参照は許可」に含まれない旨が明確化される。
- 既存 #26（`check-comment-refs.sh`）が、`.md` 以外のファイル参照・フォルダのみの参照（実測で既存ロジックが見逃すことを確認済みのギャップ）を検出できるよう拡張される。
- `close/` 参照・日時プレフィックスなしの汎用参照は誤検知しない（docs 層と対称の安全側設計）。
- 新規の監査番号は追加しない（#26 の既存検出ロジックを拡張。単一正本の重複回避）。

### 2.3 ビジネスルール

- システム仕様書・ソースコードは自己完結すべきであり、一時的な作業用フォルダへの依存を持たない。
- 検出は「issue フォルダ名の日時プレフィックス」を含むパスに限定し、誤検知ゼロを最優先とする（docs 層・code 層で同一の設計思想）。

## 3. 非機能要件

### 3.1 パフォーマンス要件

- 既存監査と同等（grep/find ベースの静的走査）。

### 3.2 セキュリティ要件

- 読み取りのみ。検証は tmp 隔離。

### 3.3 ユーザビリティ要件

- FAIL メッセージは違反ファイルと差し戻し先を示す（既存 ROLLBACK_MSG に準拠）。

### 3.4 可用性要件

- sqlite3/git 非依存（純粋にファイル走査のみ）。非 git ツリーでも動作する。

---

## 4. 外部インターフェース要件

### 4.1 API 要件

- 該当なし（CI スクリプト内の関数として追加）。

### 4.2 データ形式要件

- 検出対象は `docs/` 配下の `*.md` テキスト（docs 層）、およびソースコード（既定 `src/` `app/` `components/`。`CODE_COMMENT_SRC_DIRS` で上書き可）のコメント/docstring 行（code 層）。

---

## 5. 制約事項

- 既存禁止パターン (i)(ii)(iii)・既存監査番号（#1〜#32、および他 issue が実装/予約済みの #33〜#36）のロジックを変更・破壊しない。
- 既存 CODE_COMMENT_RULES §2/§3・既存 #26 の章節番号/追跡番号/ドキュメント名検出ロジックを変更・破壊しない（拡張のみ）。
- 本番の workflow.db・.claude/ 等を検証で破壊しない（tmp 隔離必須）。
