## 1. 概要

### 1.1 システム概要

S-3 は親 issue「issue 運用ポリシーの GitHub Issue 中心への全面移行（二重モード方式）」の**契約層**サブ issue である。配布物 `.agent-skill-chain/source/` の契約ドキュメントへ、二重モード（`ISSUE_TRACKING_MODE`）の**抽象原則**を追記し（T4）、消費者が手動起票を構造強制するために自リポへコピーして使う**汎用 GitHub Issue Forms 雛形**（inert `.example.yml`）を新設する（T6）。本リポ固有の具体手順・実効ファイルは S-2 のスコープであり、S-3 は source（配布物）側の抽象契約と汎用雛形のみを扱う。

### 1.2 用語集

| 用語 | 説明 |
| -------- | ------ |
| `ISSUE_TRACKING_MODE` | 二重モードを選ぶ唯一の設定 env。値は `github_native`｜`local_tracked`、既定 `local_tracked`（S-1 で audit.sh に実装済み）。 |
| 実効モード | `ISSUE_TRACKING_MODE == github_native` かつ git remote に github.com を含むときのみ `github_native`、それ以外は `local_tracked`（非 GitHub フォールバック）。 |
| 抽象原則（source） | 消費者共通の契約。env の存在・既定値・フォールバック・close 分岐・AI 自律設定禁止。具体手順は含めない。 |
| 具体手順（project） | 本リポ固有。実効モード固定・body テンプレートの実文言・close 処理の実装。`自己拡張ワークフロー.md`（S-2 で改訂）に置く。 |
| 配置境界（ADR-5 前例） | 抽象＝source／具体＝project の分離原則。二重記載を避ける。 |
| inert 雛形 | enforcement・audit.sh・フックから読まれない不活性サンプル（`.example.` 命名）。消費者がコピーして有効化する。前例＝`orchestrator-allowlist.example.txt`。 |
| GitHub Issue Forms | `.github/ISSUE_TEMPLATE/*.yml`。`required` フィールドで Web UI 手動起票の構造を機械的に強制する GitHub の仕組み。 |

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: source だけで二重モードの存在を把握できる

- **As a** 配布物 source を読むエージェント／消費者
- **I want to** `run_command.md` §Constraints を読むだけで `ISSUE_TRACKING_MODE` の存在・既定・フォールバック・close 分岐を把握し、具体手順は project へ辿れる
- **So that** source だけを配布された環境でも新方式の契約を理解でき、非 GitHub 環境では従来方式へ安全に倒れる

**受け入れ基準**:

- `run_command.md` §Constraints に `ISSUE_TRACKING_MODE`（既定 `local_tracked`・`github_native` 二値・非 GitHub は local_tracked へフォールバック・close 移動は local_tracked 専用・AI 自律設定禁止）の抽象原則が 1 箇所記載される。
- 具体手順（本リポ実効モード固定・body テンプレートの実文言）は `自己拡張ワークフロー.md` へリンク委譲され、source に二重記載されない。
- 既存 3 ゲート（GitHub Issue 起票／branch／PR）の記述は変更されず、非交差の独立項目として追記される。

#### ストーリー 2: close 分離契約が二重モードを反映する

- **As a** close 移動の可否を判断するエージェント
- **I want to** CORE（宣言）と PHASES（ライフサイクル本体）の close 分離契約が「close 移動は local_tracked 専用・github_native は Issue close で完結」を明記している
- **So that** github_native 採用時に不要な close 移動 PR を作らず、local_tracked では従来どおり移動する

**受け入れ基準**:

- `CORE.md` §完了 issue の close 分離 に「close 移動（`git mv`）は local_tracked 専用。github_native は GitHub Issue の close で完結」の抽象注記がある。
- `PHASES.md` §完了 issue の close 移動 に同趣旨の注記があり、既存の GitHub 連携／非連携の分岐（実行確定手段）と矛盾しない。
- ライフサイクル定義・「1 ファイル 1 責務」構造・既存 close 手順は破壊されない。

#### ストーリー 3: モード切替 env の自己無効化が禁止される

- **As a** enforcement 設計者
- **I want to** `ISSUE_TRACKING_MODE` を AI が自律的に設定・変更してはならない対象へ含める
- **So that** エージェントが自らのゲートを SKIP させる目的でモードを切り替える自己バイパスを防げる

**受け入れ基準**:

- `AGENT_CONDUCT.md` §enforcement ゲートの自己無効化禁止 の対象に `ISSUE_TRACKING_MODE` が含まれる（既存の `*_GATE_ENABLED`／`*_GATE_EFFECTIVE_FROM` 列挙へ追加）。
- サブエージェント向け凝縮版（同ファイル）にも同趣旨が反映される。
- 「人間が判断した正当なトグル運用は禁止対象でない」という既存の但し書きと整合する。

#### ストーリー 4: 消費者が手動起票を構造強制できる汎用雛形を得る

- **As a** github_native を採用する消費者（本リポ以外）
- **I want to** source から自リポ `.github/ISSUE_TEMPLATE/` へコピーするだけで、Web UI 手動起票でも目的／成功基準／受け入れ基準を必須入力させられる
- **So that** AI 起票（`--body`）と手動起票の双方で GitHub Issue 本文の構造が一致する

**受け入れ基準**:

- `.agent-skill-chain/source/enforcement/github/` に GitHub Issue Forms の inert 雛形（`.example.yml`）が新設される。
- フィールドは親 02 §3.3.2 と一致し、目的／成功基準／受け入れ基準が `required: true` の `textarea`、全体像・フロー／参照が `required: false`。
- SETUP.md／enforcement/README.md に、雛形の存在・コピー先・使い方が `orchestrator-allowlist.example.txt` 前例に倣って追記される。
- 雛形は inert（enforcement・audit.sh・フックから読まれない）で、AI 経路（`gh issue create --body`）は Forms を経由せず §3.3.2 を直接渡せる（AI 経路不変）。

#### ストーリー 5: 抽象／具体の二重記載がなく既存監査に抵触しない

- **As a** レビュアー（review-docs）
- **I want to** 追記が抽象＝source／具体＝project の配置境界を守り、既存のドキュメント監査に抵触しない
- **So that** 配布物の保守性が保たれ、監査 CI が赤くならない

**受け入れ基準**:

- source 契約と project 具体手順で同一内容が二重記載されていない（配置境界＝ADR-5）。
- 追記した env 名（`ISSUE_TRACKING_MODE`）・既定値（`local_tracked`）が S-1 実装の audit.sh と grep 突合で一致する。
- 内部参照禁止（enforcement #6・PR 本文のみ対象）・DOCS_NOISE 等の既存ドキュメント監査に抵触しない。雛形が enforcement から誤って読まれない。

### 2.3 ビジネスルール

- **配置境界（ADR-5 前例）**: source＝抽象原則のみ、project＝具体手順。二重記載しない。
- **env 名の単一情報源**: `ISSUE_TRACKING_MODE`・既定 `local_tracked`・値 `github_native` は S-1 実装（audit.sh）を正とし、契約はそれに一致させる。
- **inert 原則**: 雛形は `.example.` 命名で enforcement・フックから読まれない。消費者がコピーして有効化する。
- **非交差・非破壊**: 既存 3 ゲート・close 分離・自己無効化禁止の既存記述を変更・弱化せず、追記・追加のみ。
- **フォールバック**: 非 GitHub 環境では既定 `local_tracked` により従来方式へ倒れ、ロックアウトしない。

## 3. 非機能要件

### 3.1 パフォーマンス要件

- ドキュメント・inert 雛形のみで、実行時性能への影響はない。雛形は enforcement から読まれない。

### 3.2 セキュリティ要件

- `ISSUE_TRACKING_MODE` を AI 自律設定禁止対象へ含める（自己バイパス防止）。
- 雛形・記述例にトークン実値・認証情報を残さない（親 02 §8 踏襲）。

### 3.3 ユーザビリティ要件

- 消費者は雛形を自リポ `.github/ISSUE_TEMPLATE/` へコピーするだけで手動起票の構造強制を得られる。使い方は SETUP／README に明記する。
- source を読むエージェントが二重モードの契約を 1 箇所で把握できる。

### 3.4 可用性要件

- 非 GitHub 環境・GitHub 非採用消費者でロックアウトしない（既定 `local_tracked`）。抽象原則にフォールバックを明記する。

## 4. 外部インターフェース要件

### 4.1 API 要件

- 本 issue に実行時 API はない。「契約」は (a) source 契約ドキュメントの記述、(b) GitHub Issue Forms スキーマ（`name`／`body`／`type: textarea`／`validations.required`）。
- Forms 雛形は GitHub Issue Forms スキーマとして妥当（GitHub がパースできる）であること。

### 4.2 データ形式要件

- 雛形は YAML（`.example.yml`）。フィールドの `required: true`（目的／成功基準／受け入れ基準）・`required: false`（全体像・フロー／参照）を親 02 §3.3.2 の見出しと一致させる。

## 5. 制約事項

- 対象は実在ファイルのみ（00 §4.1 の 6 ファイル＋新設 `enforcement/github/`）。存在しない想像上のファイル名を使わない。
- 配置境界（ADR-5）を守り、source へ具体手順を書かない。
- env 名・既定値は S-1 実装（PR #116）に一致させる。
- 依存順 S-1 → S-3 → S-2 を守る（S-2 スイッチ投入前に S-3 完了）。
- `90_issues/` 配下のサブ issue のため GitHub Issue 個別起票はしない（親 #115 に集約）。
