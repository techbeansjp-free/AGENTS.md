# 要求定義書: システム仕様書の作業用 issue フォルダ参照禁止

**プロジェクト名**: システム仕様書の作業用 issue フォルダ参照禁止
**作成日**: 2026 年 07 月 13 日
**最終更新**: 2026 年 07 月 13 日

> **重要**: このドキュメントは常に更新する。実装内容と常に同期させる。

---

## 1. 目的・背景

### 1.1 目的（必須）

システム仕様書・ソースコードから作業用 issue フォルダへの参照を規約で禁止し機械監査で強制する。

### 1.2 背景

- **現状の課題**:
  - 導入プロジェクトで「システム仕様書が仕様書内で完結せず、issue への参照を持つ」違反が発生した（フィールド報告）。
  - 作業用 issue フォルダ（消費者標準 `.agent-skill-chain/runtime/{issue}/`、本リポ上書き `docs/maintainer/workflow/{issue}/`）は一時的な場所であり、完了後は `close/` へ移動される。移動でリンクが壊れる。
  - `.agent-skill-chain/source/DOCS_NOISE_RULES.md` の禁止パターン (iv) 壊れやすい参照は定義が「行番号直リンク（`<file>.md:NNN`）」に限定されており、作業用 issue フォルダへの参照は 4 パターンのどれにも明示的に当てはまらない未定義ギャップだった。
  - つまり「強制が効いていない」根本原因は、監査欠落だけでなく規約自体がこのケースを定義していないことにある。
  - **追加スコープ**: システム仕様書だけでなく、ソースコードのコメント/docstring も同種の陳腐化リスクを持つ。`CODE_COMMENT_RULES.md` §3 の「他コードファイルへの参照は許可」という既存規定に、作業用 issue フォルダへのパス参照が紛れて見逃されうる。実際に既存の #26 検出ロジック（`check-comment-refs.sh`）を実測したところ、issue フォルダ内の特定 `.md` ファイルへの参照は（ドキュメント名パターンで偶然）検出されるが、**フォルダのみの参照・`.md` 以外のファイルへの参照は検出されない**ことを確認した（evidence_source: measurement）。

- **必要性**:
  - 規約に本ケースを明示し、機械監査で継続的に検出できるようにする必要がある（docs 層・code 層の両方）。

### 1.3 期待される効果（必須: 1 件以上）

- **効果 1**: システム仕様書が作業用 issue フォルダへの依存参照を持たない（自己完結）状態を機械的に検証できる。
- **効果 2**: 導入プロジェクトで再発した場合、CI（audit.sh）が違反を FAIL として検出する。
- **効果 3**: ソースコードのコメント/docstring も同様に、作業用 issue フォルダへの直接パス参照を機械的に検出できる（コード層の自己完結性）。

## 2. 機能要件

### 2.1 既存機能の維持（該当する場合）

- 既存の禁止パターン (i)(ii)(iii) および既存監査項目（#1〜#32、および他 issue が実装/予約済みの #33〜#36）のロジックを一切変更・破壊しない。
- 既存の CODE_COMMENT_RULES §2/§3 の許可・禁止カテゴリ、既存 #26 の章節番号・追跡番号・ドキュメント名検出ロジックを変更・破壊しない（拡張のみ）。

### 2.2 新規機能要件

- DOCS_NOISE_RULES.md の禁止パターン (iv) の定義に、作業用 issue フォルダへの参照を含める（規約の明文化）。
- audit.sh に、システム仕様書ファイルが作業用 issue フォルダへのパス参照を含んでいないかを検出する新規監査項目（#37）を追加する。
- test-audit.sh に新規監査項目の回帰テスト（正例・負例・SKIP ガード）を追加する。
- **追加スコープ（コード層）**: CODE_COMMENT_RULES.md §2 に、作業用 issue フォルダへのパス参照禁止を明記し、§3「他コードファイルへの参照は許可」に含まれない旨の除外注記を追加する。
- 既存の #26 検出ロジック（`check-comment-refs.sh`。audit.sh と self-enforce.yml の両方から共有される単一正本）に、作業用 issue フォルダへのパス参照を検出する新規パターンを追加する（既存の章節番号・追跡番号・ドキュメント名パターンと同じ扱いで拡張。新規の監査番号は追加しない）。
- test-check-comment-refs.sh にコード層の回帰テスト（正例・負例）を追加する。

## 3. 非機能要件

### 3.1 パフォーマンス

- grep ベースの静的検出であり、既存監査項目と同等の実行コストに収める。

### 3.2 セキュリティ

- 破壊的操作を行わない（読み取りのみ）。検証は tmp 隔離で行う。

### 3.3 互換性

- 消費者標準パス（`.agent-skill-chain/runtime/`）と本リポ上書きパス（`docs/maintainer/workflow/`）の両方を検知対象に含める。
- 誤検知（false positive）を出さないこと（既存監査の安全側設計に倣う）。

### 3.4 保守性

- 検出ロジック・規約定義は正本 1 か所に置き、重複させない（1 ファイル 1 責務）。

---

## 4. 制約条件

### 4.1 技術的制約

- 既存 audit.sh の番号体系と衝突しない番号を採番する（#33〜#36 は他 issue が実装済み/予約済みのため使用不可。#37 を採番）。
- bash + grep/find で実装する（既存監査と同じ技術基盤）。
- コード層の拡張は新規監査番号を追加せず、既存 #26 の検出ロジック（`check-comment-refs.sh`）を拡張する（単一正本の重複回避）。

### 4.2 既存システムとの互換性

- 既存テスト（`test/run-all.sh`）が非回帰であること。

### 4.3 移行期間・スケジュール

- 単一 issue として一括で requirement-discovery → design → review-docs → implement-feature を進める。

---

## 5. 除外要件

- verify-and-close（04_review 作成・close 移動）は本 issue のスコープ外（オーケストレータが後続で実施）。
- `close/` 配下（完了済み issue の永続パス）への参照の機械 FAIL 化は行わない（設計 ADR で扱いを確定）。

## 6. 成功基準（必須: 1 件以上）

- DOCS_NOISE_RULES.md の (iv) が作業用 issue フォルダ参照を含む形に改訂されている（○/×）。
- audit.sh の新規監査項目（#37）が、システム仕様書内の作業用 issue フォルダ参照を FAIL として検出する（○/×）。
- 新規監査項目が `close/` 参照・汎用ディレクトリ参照・DB 参照を誤検知しない（○/×）。
- CODE_COMMENT_RULES.md が作業用 issue フォルダ参照禁止を明記している（○/×）。
- #26（`check-comment-refs.sh`）が、ソースコードのコメント中の作業用 issue フォルダ参照（`.md` 以外のファイル・フォルダのみの参照を含む）を検出する（○/×）。
- コード層の検出が `close/` 参照・日時プレフィックスなしの汎用参照を誤検知しない（○/×）。
- `bash test/run-all.sh` が非回帰（新規テスト含め PASS/SKIP のみ、FAIL=0）である（○/×）。

## 7. リスクと対策

### 7.1 技術的リスク

- **リスク**: 検出パターンが広すぎて汎用ディレクトリ参照（`.agent-skill-chain/runtime/workflow.db` 等）を誤検知する。
  - **対策**: issue フォルダ名（`YYYYMMDD_` 始まる日時プレフィックス）を含むパスに限定して検出する。

### 7.2 スケジュールリスク

- **リスク**: スコープ膨張。
  - **対策**: 既存パターンへの追従に留め、規約追記＋監査 1 項目＋回帰テストに限定する。
