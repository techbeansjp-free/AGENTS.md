## 1. 設計概要

### 1.1 設計方針

既存の DOCS_NOISE_RULES.md「(iv) 壊れやすい参照」の抽象カテゴリを活かし、その定義を作業用 issue フォルダ参照まで拡張する（規約層）。並行して audit.sh に grep ベースの検出項目 1 つ（#37）を追加し、機械検証と意味的検証の二段構え（既存思想）を保つ（enforcement 層）。

**追加スコープ（コード層）**: システム仕様書（docs 層）と対称に、ソースコードのコメント/docstring（code 層）も同じ陳腐化リスクを持つ。CODE_COMMENT_RULES.md §2 に禁止カテゴリを追加し、既存 #26（`check-comment-refs.sh`）の検出ロジックを拡張する。新規の監査番号は追加しない（#26 の既存検出パイプラインへの機能追加）。

### 1.2 設計原則（本プロジェクトで適用するもの）

- **単一責務**: 規約定義は DOCS_NOISE_RULES.md（docs 層）／CODE_COMMENT_RULES.md（code 層）、検出ロジックは audit.sh（docs 層）／check-comment-refs.sh（code 層。audit.sh #26 と self-enforce.yml が共有する単一正本）に置き、重複させない。
- **明確な境界**: 「システム仕様書（走査対象）」と「作業用 issue フォルダ（禁止参照先・走査対象外）」を明確に分ける（docs 層）。同様に「ソースコード（走査対象）」と「作業用 issue フォルダ（禁止参照先）」を分ける（code 層）。
- **UNIX 哲学**: 既存監査項目と同じく grep/find の小さな検出を 1 つ足すだけに留める。コード層は既存の検出パイプライン（check-comment-refs.sh の pattern 群）への 1 パターン追加に留める。

### 2.5 横断設計判断（ADR）

#### ADR-1: 禁止パターンは「(iv) の定義拡張」を採用する（(v) 新設ではなく）

- **コンテキスト**: フィールド報告の違反（作業用 issue フォルダ参照）は、DOCS_NOISE_RULES.md の禁止 4 パターンのどれにも明示的に当てはまらない未定義ギャップ。これを規約化する方法として、(iv) の定義拡張と (v) 新設の 2 案がある。
- **検討した選択肢**:
  - 案 A: 既存 (iv)「壊れやすい参照」の定義を、行番号直リンクに加え作業用 issue フォルダ参照を含む形に拡張する。
  - 案 B: 新たに「(v) 作業用 issue フォルダへの依存参照」を追加し、禁止パターンを 5 種にする。
- **決定**: 案 A（(iv) の定義拡張）。
- **根拠**: (iv) のカテゴリ名は既に抽象的な「壊れやすい参照」であり、行番号直リンクはその一事例にすぎない（現行文言も「行番号直リンク（`<file>.md:NNN`）**等**」と例示形）。作業用 issue フォルダ参照も「編集・移動で容易に陳腐化する参照」という同一カテゴリに属する。案 B は「壊れやすい参照」を扱うカテゴリを 2 つに分割し、責務重複（同一目的の規定が 2 か所）を生む＝1 ファイル 1 責務・重複回避（CORE.md §境界）に反する。evidence_source: existing_code（DOCS_NOISE_RULES.md (iv) を実読。カテゴリ名が既に汎用で、定義を DOCS_RULES §行番号直リンク禁止へ委譲する構造）。
- **帰結**: 禁止パターンは 4 種のまま。(iv) の定義に 2 つの下位種（行番号直リンク＝既存の DOCS_RULES 委譲を維持／作業用 issue フォルダ参照＝本ファイルで新規定義）を明記する。既存 (i)(ii)(iii) は不変。

#### ADR-2: 検出パターンは「issue フォルダ名の日時プレフィックスを含むパス」に限定する

- **コンテキスト**: 誤検知（false positive）ゼロが最優先（既存監査の安全側設計）。`.agent-skill-chain/runtime/` や `docs/maintainer/workflow/` という文字列は、汎用ディレクトリ言及（例: `.agent-skill-chain/runtime/workflow.db`、規約説明文中の一般記述）でも登場する。
- **検討した選択肢**:
  - 案 A: `.agent-skill-chain/runtime/` または `docs/maintainer/workflow/` の文字列出現を全て検出。
  - 案 B: これらの直後に issue フォルダ名（`YYYYMMDD_` で始まる日時プレフィックス）が続くパスのみ検出。
- **決定**: 案 B。正規表現 `(\.agent-skill-chain/runtime|docs/maintainer/workflow)/[0-9]{8}_`。
- **根拠**: 作業用 issue フォルダは必ず `<timestamp>_<title>`（timestamp 先頭 8 桁が日付）で命名される（自己拡張ワークフロー.md・CLAUDE.md の作成規約）。この日時プレフィックスを要求することで、壊れやすい「issue フォルダへの参照」だけを正確に捉え、汎用ディレクトリ参照・DB 参照（`workflow.db`）・規約説明文を誤検知しない。案 A は既存 `docs/maintainer/IMPLEMENTATION_REVIEW.md` 内の正当な汎用記述を誤 FAIL させる（実測: 案 B のパターンでは既存 docs に一致 0 件、案 A では複数一致）。evidence_source: measurement（`grep -rEn '(\.agent-skill-chain/runtime|docs/maintainer/workflow)/[0-9]{8}_' docs --include='*.md' | grep -v '/workflow/'` が空＝既存違反 0 件を確認）。
- **帰結**: 検出は日時プレフィックス付き issue フォルダ参照に限定される。ディレクトリ名の命名規約（日時プレフィックス）が検出の前提となる。

#### ADR-3: `close/` 配下への参照は機械 FAIL の対象外とする（意味的検証に委ねる）

- **コンテキスト**: 完了 issue は `close/` へ移動され、以後パスは永続的（移動しない）。「close 済みパスは参照してよいか、それでも要約＋リンクにすべきか」を確定する必要がある。
- **検討した選択肢**:
  - 案 A: `close/` 参照も機械 FAIL にする。
  - 案 B: `close/` 参照は機械 FAIL の対象外とし、意味的検証（レビュー）に委ねる。
- **決定**: 案 B。
- **根拠**: (1) `close/` 配下のパスは移動されないため「壊れやすい参照」（(iv) の本質＝陳腐化・リンク切れ）には該当しない。機械 FAIL は「壊れうる参照」に限定するのが (iv) の定義と整合する。(2) grep は「単なる出典リンク」と「内容依存」を区別できず、close 参照を一律 FAIL すると誤検知になりうる（安全側）。(3) ただしシステム仕様書の自己完結性の観点では、close 済み issue であっても直接依存より要約＋リンクが望ましい。これは意味的判断であり、既存の「機械検証と意味的検証の役割分担」に従いレビュー（review-docs / R-5）で担保する。この分担を DOCS_NOISE_RULES.md に明記する。evidence_source: existing_code（audit.sh 内で `*/close/*` を各所で in-progress 前提チェックの対象外にする既存前例＝#2b/#3/#7/#9/#20/#29/#31/#32 と一貫）。
- **帰結**: 検出正規表現 `(\.agent-skill-chain/runtime|docs/maintainer/workflow)/[0-9]{8}_` は、`workflow/` または `runtime/` の直後に `close` セグメントが来る close 参照には構造的に一致しない（`close` は数字で始まらない）。追加の close 除外ロジックは不要。規約側で「close 参照は機械 FAIL 対象外だがレビューで要約＋リンクを推奨」と明文化する。

#### ADR-4: 監査番号は #37 を採番する

- **コンテキスト**: 既存監査番号と衝突しない番号が必要。当初は現行最大番号 #32 の次として #33 を採番したが、並行して進行していた別 issue「close 移動監査強制」（`check_close_move_pending`）が #33 を、「GitHub Issue 起票ゲート追加」が #34 を実装し先に main へマージされた（PR #24）。加えて「issue 紐づけ機械強制」が #35・#36 を設計で予約済みであることが判明した。
- **検討した選択肢**: (a) #33 のまま据え置き（他 issue の実装と衝突）、(b) #34〜#36 のいずれか（他 issue の実装/予約と衝突）、(c) #37（それらすべての次の空き番号）。
- **決定**: #37。
- **根拠**: 番号衝突は監査ロジックの取り違え・失敗条件表の不整合を招くため回避が必須。#33・#34 は既に他 issue が実装し main にマージ済み、#35・#36 は別 issue が設計で予約済みのため使用不可。#37 はこれらいずれとも衝突しない次の空き番号。evidence_source: orchestrator_report（進行役からの訂正指示。PR #24 のマージおよび #35/#36 予約の事実を進行役が確認・伝達）。
- **帰結**: 新関数コメント・FAIL メッセージ・テストで一貫して #37 を用いる。当初案の「#32 の次だから #33」という単純な採番方針は、複数 issue が並行して番号を消費しうる状況では不十分であり、実装直前に最新の番号使用状況を再確認する必要があることが判明した（教訓として残す）。

#### ADR-5: コード層（追加スコープ）は新規監査番号を追加せず既存 #26 を拡張する

- **コンテキスト**: ユーザー指摘により、docs 層だけでなくソースコードのコメント/docstring も同種の陳腐化リスクを持つことが判明した。既存 #26（`check_code_comment_external_ref`）は CODE_COMMENT_RULES §2 の外部参照禁止を検出するが、実測（`check-comment-refs.sh` に issue フォルダパスを含むコメントを渡すテスト）の結果、`.md` ファイル名を伴う参照は（ドキュメント名パターンで偶然）検出されるが、**フォルダのみの参照・`.md` 以外のファイルへの参照は検出されない**ギャップを確認した。この検出ギャップをどう埋めるかの決定。
- **検討した選択肢**: (a) 新規監査番号（#38）を audit.sh に追加し、独立した grep 関数で src/ 配下を再走査する。(b) 既存 #26 が委譲する `check-comment-refs.sh`（audit.sh と self-enforce.yml の両方が共有する単一正本）に新規パターン `pat_issuefolder` を追加し、既存の章節番号・追跡番号・ドキュメント名パターンと同列に扱う。
- **決定**: (b)。既存 #26 の検出ロジックを拡張する。新規監査番号は追加しない。
- **根拠**: `check-comment-refs.sh` は自身のヘッダーコメントで「検出ロジックはこのスクリプト 1 本に集約し、監査（audit.sh）と自己強制 CI（self-enforce.yml）の両方がこのスクリプトを別の対象に対して呼ぶ（ロジックを二重化しない）」と明記している（evidence_source: existing_code）。(a) 案は audit.sh 専用の別経路を作ることになり、self-enforce.yml（GitHub Actions CI）には自動反映されず二重管理になる。(b) 案は 1 箇所の拡張で audit.sh・self-enforce.yml の両方に同時に効き、かつ既存のパターン追加方式（pat_section/pat_ticket/pat_docname と同列に pat_issuefolder を OR 条件へ追加するだけ）に自然に沿う。1 ファイル 1 責務（check-comment-refs.sh＝検出ロジックの単一正本）を保つ。
- **帰結**: `check-comment-refs.sh` に `pat_issuefolder` を追加し、`scan_file` の OR 条件に組み込む。audit.sh の `check_code_comment_external_ref`（#26）関数自体は変更しない（説明コメントの更新のみ）。監査番号は #26 のまま。CODE_COMMENT_RULES.md §2 に禁止カテゴリを追加し、§3 に「他コードファイルへの参照」許可に含まれない旨の注記を追加する。

## 3. 機能設計

### 3.1 機能 1: `check_docs_transient_issue_ref`（#37）

#### 3.1.1 概要

`docs/` 配下のシステム仕様書が作業用 issue フォルダへのパス参照を含む場合に FAIL する。

#### 3.1.2 処理フロー

1. SKIP ガード: `$PROJECT_ROOT/docs` が存在しなければ `return 0`（docs/ 未採用プロジェクトでは不発動）。
2. `find "$PROJECT_ROOT/docs" -name '*.md' -type f` で走査。次を除外:
   - パスに `/workflow/` を含むファイル（作業用 issue フォルダ＝issue ドキュメント自身。走査対象外）。
   - パスに `/templates/` を含むファイル（テンプレート。防御的除外）。
3. 各ファイルに対し `grep -nE '(\.agent-skill-chain/runtime|docs/maintainer/workflow)/[0-9]{8}_'` を実行。
4. 一致行があれば FAIL メッセージ（違反ファイル・行）を stderr 出力し、`ROLLBACK_MSG` を付し `EXIT_CODE=1`。

#### 3.1.3 入力・出力

- **入力**: `docs/` 配下の `*.md`。
- **出力**: 違反時 FAIL メッセージ＋`EXIT_CODE=1`。違反なしは無出力（`[audit] checking ...` の進捗行のみ）。

#### 3.1.4 エラーハンドリング

- git/sqlite3 に非依存。`docs/` 不在は SKIP。find の失敗は `2>/dev/null || true` で無害化（既存パターン踏襲）。

#### 3.1.5 規約正本の自己 FAIL 回避（レビュー F4）

- 本ルールを説明する規約正本（`DOCS_NOISE_RULES.md`・`DOCS_RULES.md` 等）は `.agent-skill-chain/source/` 配下にあり、走査対象（`docs/`）の外である。したがって、規約文中に検出パターン相当の例示（issue フォルダパス）を書いても #37 で自己 FAIL しない。逆に言えば、システム仕様書（`docs/`）側でそうした例示を書くことは（例示であっても）自己完結性を損なうため避ける。

### 3.2 機能 2: `pat_issuefolder`（check-comment-refs.sh 拡張・追加スコープ・ADR-5）

#### 3.2.1 概要

ソースコードのコメント/docstring 行が作業用 issue フォルダへのパス参照を含む場合に検出する。既存 #26（`check_code_comment_external_ref`）の検出パイプラインに新規パターンとして追加する（監査番号は増やさない）。

#### 3.2.2 処理フロー

1. `check-comment-refs.sh` に既存の `pat_section`／`pat_ticket`／`pat_docname` と同列で `pat_issuefolder='(\.agent-skill-chain/runtime|docs/maintainer/workflow)/[0-9]{8}_'` を定義する（docs 層 #37 と同一の正規表現。日時プレフィックス限定で汎用参照・close/ を誤検知しない）。
2. `scan_file` 関数の OR 条件（`pat_section` / `pat_ticket` / `pat_docname` の判定チェーン）に `pat_issuefolder` を追加する。
3. 既存の走査対象（拡張子 sh/py/js/ts/go/rb/rs/java/yml/yaml のコメント行。import/require 等の行は除外）・出力形式（`<file>:<line>`）・終了コード契約（0=違反なし/1=違反あり/2=使用方法エラー）は変更しない。
4. audit.sh の #26（`check_code_comment_external_ref`）はロジックを変更せず、`check-comment-refs.sh` への委譲のみのため、説明コメントの更新のみで新パターンが自動的に効く。

#### 3.2.3 入力・出力

- **入力**: ソースコード（既定 `src/` `app/` `components/`。`CODE_COMMENT_SRC_DIRS` で上書き可）のコメント/docstring 行。
- **出力**: 違反時 `<file>:<line>` を標準出力へ列挙し `exit 1`。違反なしは無出力で `exit 0`（既存契約不変）。

#### 3.2.4 エラーハンドリング
