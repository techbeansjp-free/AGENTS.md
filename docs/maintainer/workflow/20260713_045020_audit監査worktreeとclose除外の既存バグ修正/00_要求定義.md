## 1. 目的・背景

### 1.1 目的（必須）

audit.sh の worktree 誤 SKIP（偽陰性）と close 済み issue の永久 FAIL という 2 つの既存バグを是正する。

### 1.2 背景

- **現状の課題**:
  - **バグ A（worktree 誤 SKIP）**: 複数の監査チェックが `[[ ! -d "$PROJECT_ROOT/.git" ]]` で「非 git ツリーなら SKIP」を判定している。git worktree 環境では `.git` はディレクトリではなく gitdir ポインタの「ファイル」になるため、この判定が誤って真になり、チェック自体が静かに SKIP される（fail-open＝偽陰性）。本セッションは worktree 上で全 issue を作業しており、当該チェックは一貫して SKIP されていた可能性が高い。
  - **バグ B（close 除外漏れ）**: 「テスト観点未記載」チェック（03_実装計画）と「docs 更新要否未記載」チェック（04_review）の `find` ループが `*/templates/*` のみ除外し `*/close/*` を除外していない。そのため close 済み issue が未来永劫 FAIL し続ける。
- **必要性**:
  - 監査は fail-open してはならない（偽陰性は監査の存在意義を損なう）。
  - close 済み issue は完了済みであり、in-progress 前提の記載要求を課すべきでない（既存の #29/#31/#32 は `/close/` を明示除外しており、#4/#5 だけが取り残されている）。

### 1.3 期待される効果（必須: 1 件以上）

- **効果 1**: worktree 環境でも `-d .git` 系ガードを持つ全監査（#10・#18・#19・#25・#27、および同型バグを持つ #28）が正しく実行される（○/×: worktree 上で `audit.sh` を実行したとき各チェックの実行ログが出力され、SKIP されない）。
- **効果 2**: close 済み issue の 03/04 が「テスト観点未記載」「docs 更新要否未記載」で FAIL しなくなる（○/×: 本 worktree ルートで `audit.sh .` を実行したとき close 由来 FAIL が 0 件）。

## 2. 機能要件

### 2.1 既存機能の維持（該当する場合）

- 既存の正しく動作している監査（#29・#31・#32、および本ブランチには未導入だが将来の #33・#34）のロジックは変更しない（参考にするのみ）。
- 非 git ツリー・DB 非採用環境での既存 SKIP 挙動（偽 FAIL を出さない安全側）は維持する。

### 2.2 新規機能要件

- **タスク A**: `-d .git` 判定を `git rev-parse --is-inside-work-tree` へ統一し、worktree でも実 git ツリーとして扱う。
- **タスク B**: 「テスト観点未記載」「docs 更新要否未記載」チェックの `find` ループに `*/close/*` 除外の `continue` を追加する。

## 3. 非機能要件

### 3.1 パフォーマンス

- 追加コストは無視できる（git サブコマンド 1 回・文字列一致 1 回の増分）。

### 3.2 セキュリティ

- 外部入力を新たに扱わない。既存の GIT_RANGE 無害化等には影響しない。

### 3.3 互換性

- 通常の（worktree でない）git リポジトリ・非 git ツリー・DB 非採用環境の既存挙動を破壊しない。

### 3.4 保守性

- 既存の正しい修正パターン（#28:769 の `is-inside-work-tree`、#29/#31/#32 の `/close/` 除外）と同一表現に揃え、単一の慣用形へ収束させる。

## 6. 成功基準（必須: 1 件以上）

- worktree を再現したテストフィクスチャで、`-d .git` 系ガードを持つ監査が SKIP されず実行されることを確認する回帰テストが PASS する。
- close/ 配下の 03/04 が「テスト観点未記載」「docs 更新要否未記載」で FAIL しないことを確認する回帰テストが PASS する。
- `bash test/run-all.sh` が非回帰（既存テストの FAIL 増加なし）。
- 本 worktree ルートで `bash .agent-skill-chain/source/enforcement/ci/audit.sh .` を実行し、close 由来の既存 FAIL が解消していることを確認する。

## 7. リスクと対策

### 7.1 技術的リスク

- **リスク**: `is-inside-work-tree` 化で非 git ツリー・DB 非採用環境の既存 SKIP を壊す。
  - **対策**: 既存の非 git・DB 非採用シナリオ（test-audit.sh シナリオ 1/2）を非回帰で確認する。

### 7.2 スケジュールリスク

- **リスク**: close 除外を過剰適用し、in-progress issue の正当な FAIL を握り潰す。
  - **対策**: close 外の in-progress issue で従来どおり FAIL することを回帰テストで確認する。
