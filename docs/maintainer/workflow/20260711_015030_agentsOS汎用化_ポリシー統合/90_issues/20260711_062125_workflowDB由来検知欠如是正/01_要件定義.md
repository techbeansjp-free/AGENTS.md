## 1. 概要

### 1.1 システム概要

`.agents/scripts/setup.sh` の `init_workflow_db` および `.agents/scripts/write-workflow-log.sh` は、`.workflow/workflow.db` の初期化要否をファイルの存在確認のみで判定しており、既存ファイルが本パッケージ由来の正規スキーマかを検証しない。由来不明ファイルが存在する場合、setup はそれを無警告でスキップし、その後の書記（scribe）ステップで初めて sqlite3 のエラーとして問題が顕在化する。本要件は、setup 実行時点で軽量な検査により利用者に警告できるようにする改修を要件化する。発端・一次情報は親 issue `docs/maintainer/workflow/20260711_015030_agentsOS汎用化_ポリシー統合/02_設計.md §2.6.7` に記載済み（本ドキュメントでは再掲しない）。

### 1.2 用語集

| 用語 | 説明 |
| --- | --- |
| サイレントスキップ | `init_workflow_db` が `[[ -f "$db" ]]` の真偽のみで初期化要否を判定し、既存ファイルの中身を検証せず処理を終える現状の挙動。 |
| 軽量検査 | 本要件で追加する、既存ファイルが有効な sqlite3 データベースであり `workflow_log` テーブルを持つかを確認する処理。fail-closed（処理中止）は伴わない。 |
| fail-closed | 親 issue ストーリー8（`.agent-skill-chain/` 本体）が採る、判定不能時に処理を中止する安全側の方針。本要件では**採用しない**（除外要件・00 §5）。 |

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: `workflow.db` 由来不明ファイルの setup 時点での警告

- **As a** 本パッケージの採用先プロジェクトの利用者
- **I want to** `.workflow/workflow.db` に由来不明のファイルが存在する場合、setup 実行時点でそれを警告してほしい
- **So that** 後続の書記ステップで原因不明の sqlite3 エラーに遭遇し、自力で原因を遡って調査する手間を負わずに済む

**受け入れ基準**:

- `init_workflow_db` は、既存ファイルをスキップする前に、当該ファイルが有効な sqlite3 データベースであり `workflow_log` テーブルを持つかを検査する。
- 検査に失敗した場合（sqlite3 として開けない、または `workflow_log` テーブルが存在しない）、ファイルパス・推定される問題・人間が確認すべき手順を含む警告メッセージを標準エラー出力へ表示する。
- 警告表示後も setup 処理は中止せず、正常終了コード（0）で完了する（既存ファイルは変更しない）。
- 正規の `workflow_log` テーブルを持つ既存 DB（スキーマバージョン差分がありマイグレーション対象のものを含む）に対しては警告を表示しない（false positive を避ける）。

### 2.2 BDD ユースケース

#### ユースケース 1: 由来不明ファイルが存在する場合の警告

```gherkin
Feature: workflow.db 由来検知（軽量警告）
  Scenario: 非 sqlite3 ファイルが .workflow/workflow.db に存在する状態で setup を実行する
    Given 配備先の .workflow/workflow.db に本パッケージ非由来の任意ファイル（sqlite3 として開けない）が存在する
    When setup（init/upgrade 相当）が実行される
    Then setup はファイルパス・推定される問題・確認手順を含む警告を標準エラー出力へ表示し、当該ファイルを変更せず、正常終了コードで完了する

  Scenario: workflow_log テーブルを持たない sqlite3 ファイルが存在する状態で setup を実行する
    Given 配備先の .workflow/workflow.db が有効な sqlite3 ファイルだが workflow_log テーブルを持たない
    When setup が実行される
    Then setup は同様に警告を表示し、当該ファイルを変更せず、正常終了コードで完了する
```

#### ユースケース 2: 正規 DB では警告が発生しないこと（false positive 回避）

```gherkin
Feature: workflow.db 由来検知（false positive 回避）
  Scenario: 正規の workflow_log テーブルを持つ既存 DB が存在する状態で setup を実行する
    Given 配備先の .workflow/workflow.db が workflow_log テーブルを持つ正規の DB である（マイグレーション対象の旧スキーマ差分を含む）
    When setup が実行される
    Then setup は警告を表示せず、既存の初期化スキップ・マイグレーション処理をそのまま実行する
```

### 2.3 ビジネスルール

- 本要件は `.agent-skill-chain/` 本体（親 issue ストーリー8）と同水準の配備マーカー・フィンガープリント判定・fail-closed 中止を導入しない（00 §5 除外要件）。あくまで軽量な警告表示に限定する。
- `init_workflow_db`・`write-workflow-log.sh`・`src/agents-md.ts`（該当ロジックが存在する場合）で判定ロジックが重複・ドリフトしないよう、設計フェーズで単一定義（またはミラー関係の明示）を確定する。

## 3. 非機能要件

### 3.1 パフォーマンス要件

- 追加する検査は sqlite3 の軽量クエリ（`PRAGMA table_info` 相当）1 回に限定し、setup 全体の実行時間に有意な影響を与えない。

### 3.2 セキュリティ要件

- fail-closed（処理中止）を新規導入しない。警告表示のみに限定し、既存ファイルへの書込み・削除は行わない。

### 3.3 ユーザビリティ要件

- 警告メッセージは、ファイルパス・推定される問題・人間が確認すべき手順の 3 点を含む具体的な内容とする（抽象的な「エラーが発生しました」のみの表示は不可）。

### 3.4 可用性要件

- 該当なし（setup 完了後の可用性への影響は無い）。
