## 1. 概要

### 1.1 システム概要

本 issue は、親 issue「issue 運用ポリシーの GitHub Issue 中心への全面移行（二重モード方式）」の依存順の**最後のサブ issue（S-2・親タスク T2/T3/T5/T7＋スイッチ投入）**である。S-1（audit.sh の `resolve_issue_tracking_mode`＋#33 の github_native SKIP ガード・PR #116 マージ済み）で「強制層」、S-3（source 契約への `ISSUE_TRACKING_MODE` 抽象原則追記・汎用 Issue Forms 雛形・PR #121 マージ済み）で「抽象契約」が整った前提のもと、**本リポ自身を `github_native` 実効へ切り替える**。具体的には (a) ローカル issue ドラフト（00〜04）の `.gitignore` 非追跡化（T3）、(b) project override（`自己拡張ワークフロー.md`）の両モード具体手順化（T2）、(c) 恒久 ADR 記録先 `docs/maintainer/decisions/DECISIONS.md` 新設（T5）、(d) 本リポ `.github/ISSUE_TEMPLATE/` の Issue Forms 実ファイル新設（T7）、(e) `ISSUE_TRACKING_MODE=github_native` スイッチの最終投入、を対象とする。さらに (f) 非追跡化と直接衝突する **audit.sh #28（`check_issue_doc_in_gitignored_path`）への github_native SKIP ガード追加**（S-1 の #33 と同型・C2 参照）を含む。**source（S-3）は変更せず、audit.sh も #28 ガード追加を唯一の例外として `resolve_issue_tracking_mode`／#33 本体・その他チェックは変更しない**（本 issue は本リポ固有の project／`.gitignore`／`.github/`／決定ログ＋#28 ガードのみを対象）。

## 2. 背景・前提条件（identify-assumptions）

> 本セクションは、00_要求定義.md の目的・成功基準（SC1〜SC8）が成り立つための前提・制約・リスクを洗い出したものである。各項は BDD の Given 節・受け入れ基準の素材として転用する。前提は **検証可能なもの**（マージ状態・ファイル存在・値一致など、証拠で確認できる）と **仮定として置くもの**（後続の検証で確定するまで前提として置く）に分ける。

### 2.1 前提（Assumptions）

#### 2.1.1 検証可能な前提（証拠で確認できる）

- **A1（S-1 完了）**: audit.sh に純関数 `resolve_issue_tracking_mode` と `check_close_move_pending`（#33）の github_native SKIP ガードが**既に main へマージされている**（PR #116）。S-2 はこの解決ロジック・SKIP ガードを**変更せず**、実効モードを切り替えるだけで #33 が SKIP されることに依存する。（検証: audit.sh に当該関数・SKIP ガードが存在）
- **A2（S-3 完了）**: source 契約に `ISSUE_TRACKING_MODE` の二重モード抽象原則（`skills/agent/run_command.md` §Constraints）・close 移動の local_tracked 専用化（`boot/CORE.md`・`workflow/PHASES.md`）・AI 自律設定禁止（`AGENT_CONDUCT.md`）・汎用 Issue Forms 雛形（`enforcement/github/issue-request.example.yml`）が**既に main へマージされている**（PR #121）。S-2 はこの抽象契約に従う**本リポ固有の具体実装**であり、契約自体を再定義・二重記載しない。（検証: 当該 source ファイル群に記述が存在）
- **A3（env 三値の一致）**: env 名 `ISSUE_TRACKING_MODE`・既定値 `local_tracked`・採用値 `github_native` が、S-1 実装（audit.sh の `resolve_issue_tracking_mode`）と S-3 の source 契約で**同一表記で一致している**。S-2 の project 設定・記述はこの確定値に厳密一致させる。（検証: source と audit.sh を grep して同一表記）
- **A4（github.com remote の存在）**: 本リポの `git remote -v` は **github.com を含む**。`github_native` の実効化条件（env=github_native かつ remote に github.com）を満たす前提が成立する。（検証: `git remote -v | grep github.com`）
- **A5（実効モード解決は 2 因子のみ）**: 実効モードは `ISSUE_TRACKING_MODE` env と github.com remote 有無の **2 因子だけ**から決定論的に解決される。S-2 が触る `.gitignore`・ドキュメント・Issue Forms はモード解決に影響しない。（検証: audit.sh `resolve_issue_tracking_mode` の入力）
- **A6（close 移動は local_tracked 専用）**: `github_native` では GitHub Issue 自体の close で完結し、`close/` への `git mv` は行わない（S-3 で CORE.md・PHASES.md に契約済み）。本リポの完了フローはこの契約に従う。（検証: CORE.md・PHASES.md の記述）
- **A7（Issue Forms は AI 起票に非干渉）**: `.github/ISSUE_TEMPLATE/` の Issue Forms は GitHub Web UI 手動起票のみ構造強制し、AI 起票（`gh issue create --body`）・audit.sh・hook のいずれからも読まれない（S-3 契約明記）。T7 の Forms 追加は既存の AI 起票フロー・監査に影響しない。（検証: enforcement/README.md の Issue Forms 拡張点記述）
- **A8（利用者はオーナー単独）**: 本リポの現行利用者はオーナー本人のみで、他の現行利用者への後方互換配慮は不要（親 issue #115 背景）。ゆえに本リポ source 側設計変更は済んでおり、S-2 はスイッチ投入に集中できる。

#### 2.1.2 仮定として置く前提（後続の検証で確定する）

- **A9（非追跡化と audit.sh 走査の両立・#28 は要ガード追加）**: 非追跡化した 00〜04 に対する既存監査の挙動を、監査手法別に次のとおり整理する（audit.sh 実読により確認済み・SC7／親 S5/S6 で tmp 隔離検証して確定）。
  - **(a) #28（`check_issue_doc_in_gitignored_path`, audit.sh:858-875）は要対応**: `find` で 00〜04 を走査し `git check-ignore -q` が exit 0（＝ ignore 配下）を返すと FAIL する。github_native ガードが無いため非追跡化すると**確実に FAIL する**（誤 FAIL／偽陽性）。→ S-1 の #33 と同型の github_native SKIP ガード追加で解消（C2・AC7）。
  - **(b) `find` ベースで git 追跡状態に非依存＝誤 FAIL・検知漏れなし**: #4/#5/#9（find + workflow.db）・#29/#31/#32（find + DB）・#34/#35（find + frontmatter）は非追跡ドラフトにも到達し、非追跡化で挙動が変わらない。#3 は workflow.db 駆動＋ファイルシステム `-f` 判定で非追跡ファイルも検知でき影響なし。
  - **(c) #36（`check_pr_issue_linkage`, audit.sh:1305）は追跡ファイルのみ起点＝検知漏れ（偽陰性）あり**: 起点が `git diff --name-only $GIT_RANGE`（**追跡ファイルのみ**列挙）のため、非追跡ドラフトは PR 差分に現れず issue_dir 抽出経路から外れる。これは github_native 運用の設計上の帰結（ドラフトは PR に載らない使い捨て・Issue 紐づけは GitHub Issue 側と #34 ゲートで担保）であり、S-2 では**検知漏れが起きることを認識・記録**する（AC7）。
- **A10（波及しないスイッチ）**: 本リポでの `github_native` スイッチ投入は本リポ固有の project／env 設定に閉じ、**既定 local_tracked・非 GitHub 環境の消費者へ波及しない**、と仮定する（SC8・親 S8 で確認して確定）。
- **A11（#33 SKIP の実環境有効性）**: 実効 `github_native` 化後、close 未移動・猶予超過の既存 issue があっても #33 は本リポ実環境で SKIP し FAIL（EXIT_CODE=1）を出さない、と仮定する（SC5/SC6・親 S3/S4 で tmp 隔離検証して確定）。
- **A12（DECISIONS.md の恒久性）**: 新設する `docs/maintainer/decisions/DECISIONS.md` は git 追跡され、非追跡化後の設計判断の恒久記録先として機能する、と仮定する（2026-07-15 の worktree 削除で 02/03 が失われた事故の再発防止に直結）。

### 2.2 制約（Constraints・守らないと失敗するもの）

> YAGNI に従い「守らないと 00_要求定義.md の目的が達成できない」ものに限定する。詳細な受け入れ基準への落とし込みは後続 define-constraints で行う。

- **C1（env 三値の厳密一致）**: project 設定・記述で用いる env 名・既定値・採用値は `ISSUE_TRACKING_MODE` / `local_tracked` / `github_native` と厳密一致させる。表記ずれは実効モード解決の失敗（スイッチが効かない）を招く。（A3 対応）
- **C2（配置境界の維持・#28 ガードは例外的に S-2 内）**: 抽象＝source／具体＝project の境界を維持する。本リポ固有の具体手順（両モード起票〜完了手順・実効モード固定・起票本文テンプレート）は project（`自己拡張ワークフロー.md`）へ集約する。**source（S-3 成果）は変更しない。audit.sh も原則変更しないが、唯一の例外として #28（`check_issue_doc_in_gitignored_path`）への github_native SKIP ガード追加は S-2 スコープに含む**。理由: #28 は github_native ガードを持たず非追跡化した 00〜04 を `find` で走査し `git check-ignore` exit 0 で確実に FAIL するため、非追跡化（SC1/AC1）と直接衝突する。S-1（PR #116）が確立した `resolve_issue_tracking_mode`＋冒頭 SKIP のパターンを #28 の 1 箇所に適用する小規模拡張であり、`resolve_issue_tracking_mode`／#33 本体・audit.sh のその他チェックは変更しない。
- **C3（対象ファイルの限定）**: 変更対象は本リポ**実在**の固有ファイルに限定する（`.agent-skill-chain/project/自己拡張ワークフロー.md`・`.gitignore`・`docs/maintainer/decisions/DECISIONS.md`（新設）・`.github/ISSUE_TEMPLATE/`（新設））。実在しないファイルの参照・作成をしない。
- **C4（env 自律設定の禁止・人間の明示指示前提）**: `ISSUE_TRACKING_MODE` の設定・変更は AI エージェントの自律実行を禁止し、人間の明示指示がある場合のみ行う（AGENT_CONDUCT.md §ゲート自己無効化禁止）。ただし project 単位の恒常トグル設定（本リポの github_native 採用）は「人間が判断した正当な運用設定」であり禁止対象外（同 §正当なトグル運用との区別）。
- **C5（ロックアウト非発生・回帰安全）**: 非追跡化・スイッチ投入は、既定 local_tracked・非 GitHub 環境の消費者へ波及させず、既存監査（#3/#9/#29/#31/#32・#34/#35/#36）を誤 FAIL・ロックアウトさせない。
- **C6（tmp 隔離検証・本番自己インストール禁止・非追跡再現の是正）**: SC5〜SC8 の実効モード・監査挙動の検証は `mktemp -d`＋`git archive` の tmp 隔離で行い、本番の自己インストール（`init`/`upgrade`/`enforce`/`uninstall`）を伴わない（破壊的 CLI の対象 dir 明示・誤操作事故の再発防止）。**ただし `git archive` は追跡ファイルのみをアーカイブするため、「非追跡ドラフトが存在する状態での監査挙動」（#28・SC7/AC7）は git archive だけでは再現できず偽 PASS になる**。当該シナリオは tmp 隔離環境内で `.gitignore` 適用後に新規 00〜04 ファイルを実際に作成し `git status --porcelain` 空＝非追跡を確認してから audit.sh を走らせて再現する。
- **C7（過剰 ignore の禁止）**: `.gitignore` の非追跡パターンは新規ローカルドラフト（00〜04）に限定し、既存の追跡済みファイル（過去 issue・`close/` 配下・DECISIONS.md・Issue Forms 等の git 追跡対象）を巻き込まない。
- **C8（機密の非残置）**: 成果物・記述例にトークン実値を残さない（S-3 のセキュリティ原則を踏襲）。

### 2.3 リスクと緩和方針

## 3. 受け入れ基準（define-constraints）

> 本節は §2 の制約（C1〜C8）・前提（A1〜A12）を、00_要求定義.md の成功基準（SC1〜SC8）に 1:1 対応する**検証可能（machine-checkable）な受け入れ基準（AC1〜AC8）**へ落とし込んだものである。各 AC は「誰が・何を・どう検証するか（具体コマンド／観測可能な出力）」を明記する。ユーザーストーリー・BDD シナリオ（When/Then）は後続 write-bdd で §3.3 以降に追記する。
>

### 3.2 制約と受け入れ基準の対応・DoD 整合

- **env 三値の厳密一致（C1・R4）**: AC2〜AC6 で用いる env 名・既定値・採用値は `ISSUE_TRACKING_MODE`／`local_tracked`／`github_native` に厳密一致させる（`grep` で source の `run_command.md §Constraints`・audit.sh `resolve_issue_tracking_mode` と表記一致を確認）。表記ずれはスイッチ無効化を招くため、いずれかの AC が満たせない場合は不合格とする。
- **env 自律設定の禁止（C4）**: `ISSUE_TRACKING_MODE=github_native` のスイッチ投入は人間の明示指示に基づく project 恒常トグル設定として扱い、AI エージェントの自律設定は禁止（`AGENT_CONDUCT.md` §ゲート自己無効化禁止）。本 issue のスイッチ投入自体が「正当なトグル運用」に該当する根拠を DECISIONS.md に記録する。
- **機密の非残置（C8）**: 成果物・記述例・Issue Forms 雛形にトークン実値を残さないことを、`grep` によるシークレットパターン検査で確認する。
- **DoD 整合**: 上記 AC1〜AC8 は 00_要求定義.md §6 の成功基準 SC1〜SC8 と 1:1 対応し（AC_n ↔ SC_n）、requirement-discovery フェーズの DoD（目的・成功基準・前提・制約・受け入れ基準の確定）を満たす。重複記載を避けるため、SC 本文は 00 を正とし、本節は検証可能化した AC のみを保持する。

### 3.3 ユーザーストーリー・BDD シナリオ（write-bdd）

> §2.4 の Given 素材と §3.1 の AC1〜AC8 を、ユーザーストーリー（As a／I want／So that）と BDD シナリオ（Given／When／Then）へ展開する。各 US_n・シナリオ n は AC_n（＝ SC_n）に 1:1 対応する。BDD の Given は §2.1 の前提（A1〜A12）・§2.2 の制約（C1〜C8）と矛盾させない。検証コマンドの正本は §3.1（AC 表）とし、本節は Then で観測可能な結果のみを述べ再掲しない。

#### 3.3.1 ユーザーストーリー

- **US1（非追跡化 / AC1・SC1）**: リポジトリオーナーとして、新規ローカル issue ドラフト（00〜04）を `.gitignore` で非追跡化したい。なぜなら起票検討段階の使い捨てドラフトを git 履歴に残さず、GitHub Issue 側の記録のみを正本として残したいからである。
- **US2（両モード手順 / AC2・SC2）**: 進行役エージェントとして、`自己拡張ワークフロー.md` から `github_native`／`local_tracked` 双方の起票〜完了手順を辿りたい。なぜなら実効モードに応じて「本文完全転記＋Issue close で完結」か「close 移動 PR」かを迷わず選べるようにしたいからである。
- **US3（恒久 ADR / AC3・SC3）**: リポジトリオーナーとして、設計判断を git 追跡される `DECISIONS.md` に永続記録したい。なぜなら非追跡化・worktree 削除後も設計判断の記録先を失わないようにしたいからである（2026-07-15 事故の再発防止）。
- **US4（Issue Forms / AC4・SC4）**: 手動起票者として、GitHub Web UI からの起票時に目的・成功基準・受け入れ基準を必須入力として構造強制されたい。なぜなら AI 起票を阻害せず、人手起票の質だけを底上げしたいからである。
- **US5（スイッチ実効 / AC5・SC5）**: リポジトリオーナーとして、`ISSUE_TRACKING_MODE=github_native` を投入して本リポの実効モードを切り替えたい。なぜなら close 未移動・猶予超過の issue があっても #33 を SKIP させ、GitHub Issue の close で完結する運用にしたいからである。
- **US6（監査回帰 #33 / AC6・SC6）**: リポジトリオーナーとして、スイッチ投入後の実効 github_native 環境で audit.sh 全体が #33 起因の FAIL を出さないことを確認・記録したい。なぜなら切り替えによるロックアウトが無いことを証拠付きで保証したいからである。
- **US7（監査回帰 非追跡由来・偽陽性/偽陰性双方 / AC7・SC7）**: リポジトリオーナーとして、非追跡化後の既存監査を**誤 FAIL（偽陽性）と検知漏れ（偽陰性）の双方**の観点で確認・記録したい。なぜなら (a) #28 は非追跡化と直接衝突し FAIL するため github_native SKIP ガード追加で解消する必要があり、(b) find ベースの監査が git 追跡状態に非依存であることを実測し、(c) #36 は `git diff` 起点ゆえ非追跡ドラフトを検知できない（設計上の検知漏れ）ことを明示的に把握しておきたいからである。
- **US8（非波及 / AC8・SC8）**: 配布物のメンテナとして、本リポの github_native 採用が既定 `local_tracked`・非 GitHub 環境の消費者へ波及しないことを保証したい。なぜならスイッチを本リポ project／env に閉じ、消費者環境をロックアウトさせたくないからである。

#### 3.3.2 BDD シナリオ（Given／When／Then）

**シナリオ 1: 新規ローカルドラフトの非追跡化（US1・AC1・SC1）**

- **Given** `.gitignore` の非追跡パターンは新規ドラフト 00〜04 に限定し既存追跡ファイルを巻き込まない（C7・A9）
- **And** `docs/maintainer/decisions/DECISIONS.md`・`.github/ISSUE_TEMPLATE/` は git 追跡対象である
- **When** `docs/maintainer/workflow/**` 配下に新規ドラフト（例: `_probe_/00_要求定義.md`）を配置し `git status --porcelain` / `git check-ignore` を実行する
- **Then** 新規ドラフトは ignore され `git status --porcelain <path>` が空・`git check-ignore` が exit 0 となり、既存追跡 issue・DECISIONS.md・Issue Forms は追跡され続け削除（`D `）が現れない

**シナリオ 2: 両モードの起票〜完了手順の具体化（US2・AC2・SC2）**

- **Given** 抽象＝source／具体＝project の境界を維持し具体手順は `自己拡張ワークフロー.md` へ集約する（C2）
- **When** `自己拡張ワークフロー.md` を `github_native`／`local_tracked` で `grep` して分岐節を確認する
- **Then** 両モードの節が存在し、github_native 節に「本文（目的・成功基準・受け入れ基準・必要な図）の完全転記」「GitHub Issue の close で完結（close 移動 PR 不要）」、local_tracked 節に「close 移動 PR」が記載されている

**シナリオ 3: 恒久 ADR 記録先の新設（US3・AC3・SC3）**

- **Given** `github_native` では close 移動を行わず GitHub Issue の close で完結する（A6）ため設計判断の永続記録先が別途必要である（A12）
- **When** `docs/maintainer/decisions/DECISIONS.md` を新設し `git add` して追跡させる
- **Then** `git ls-files` が当該ファイルを 1 行返し、ADR 最小集合（コンテキスト／選択肢／決定／根拠／帰結）の見出しと記録手順が存在し、`.gitignore` の非追跡パターンに巻き込まれない（`git check-ignore` が exit 1）

**シナリオ 4: GitHub Issue Forms の新設（US4・AC4・SC4）**

- **Given** `.github/ISSUE_TEMPLATE/` の Issue Forms は AI 起票（`gh issue create --body`）・audit.sh から読まれず手動起票のみ構造強制する（A7）

- **Then** Forms が YAML パース可能で、目的・成功基準・受け入れ基準フィールドが `required: true`、全体像・フロー・参照フィールドが `required: false` の妥当なスキーマである

**シナリオ 5: スイッチ投入で実効 github_native・#33 SKIP（US5・AC5・SC5）**

- **Given** 本リポの `git remote -v` は github.com を含む（A4）
- **And** audit.sh の `resolve_issue_tracking_mode` と #33 の github_native SKIP ガードが main にマージ済み（A1・PR #116・変更しない）
- **And** 検証は `mktemp -d`＋`git archive` の tmp 隔離環境で行い本番自己インストールを伴わない（C6）

**シナリオ 6: スイッチ投入後の audit.sh 全体の #33 非 FAIL 確認・記録（US6・AC6・SC6）**

**シナリオ 8: 消費者環境への非波及・非ロックアウト（US8・AC8・SC8）**
