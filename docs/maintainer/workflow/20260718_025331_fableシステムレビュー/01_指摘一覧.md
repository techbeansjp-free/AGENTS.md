## 領域A: 起動契約・行動規範 (boot/CORE.md, LOAD_POLICY.md, AGENT_CONDUCT.md, RULES.md, CONCEPTS.md, IO_CONTRACT.md, PLATFORM_SAFETY_RESPONSE.md, META_LAYER.md)

### A-1. 進行役の外部書き込み carve-out と enforcement の Bash 全面ブロックが物理的に矛盾
- **深刻度**: high
- **対象**: .agent-skill-chain/source/boot/CORE.md（76行目）、.agent-skill-chain/source/skills/agent/run_command.md（53〜63行目）、.agent-skill-chain/source/enforcement/README.md（13・148行目）
- **問題**: CORE と run_command は「`git push` / `gh pr create` / `gh issue create` 等の外部書き込みは進行役（orchestrator）自身が Bash で実行する」と定める。一方 enforcement は「ロールが渡る環境では orchestrator の Shell を必ず exit 2 で拒否」「`Bash` は allowlist より手前で明示 block され拡張では覆せない」と定めており、hook が有効な環境では規約が要求する操作を規約自身の enforcement が物理的に禁止する。両文書はこの衝突を一切調停していない。
- **失敗シナリオ**: enforce on の環境で PR 作成フェーズに到達すると、進行役は「自分が実行しなければならない」ルールと「実行が block される」hook に挟まれてデッドロックする。実際に allowlist 未追従で orchestrator が完全ロックアウトされた事故が過去に発生している。最悪の場合、エージェントは「復旧のために enforce off する」（後述）という規約公認の抜け道に流れる。
- **改善案**: PreToolUse に「外部書き込みコマンドの限定 allowlist（`gh pr create` 等の厳密パターン）」を carve-out として実装するか、carve-out 自体を廃止して外部書き込みもサブ＋進行役承認のフローに一本化する。

### A-2. 「最終保証は CI audit」が構造的に空洞化している
- **深刻度**: high
- **対象**: .agent-skill-chain/source/enforcement/README.md（101〜105・223〜227行目）、skills/agent/run_command.md（47〜50行目）、workflow/PHASES.md（65〜66行目）
- **問題**: 強制力マトリクスは「最後の砦は CI audit」と宣言するが、同じファイルの後段で「workflow.db は Git 非追跡のため、DB 系チェック（#3、#8〜#25、#29、#31〜#35）は CI 上では常に SKIP される」と認めている。さらに本リポ自身の CI は audit step を非ブロッキング運用中、Cursor 等は advisory のみ、runtime hook はロールが渡る環境限定。つまり run_command や PHASES が随所で「未通過なら enforcement #32/#34/#35 で FAIL する」と断定するゲートの大半は、実際には「ローカルで pre-push を任意インストールした人の環境でのみ」動く口頭ルールに近い。
- **失敗シナリオ**: 消費者プロジェクトが GitHub Actions のみで CI を回す標準構成を取ると、review-docs ゲート・Issue 起票ゲート・branch 紐づけゲート・メイン直接作業検知はすべて SKIP され、「機械強制されている」という前提で設計された運用（人間レビューの省力化等）が無担保のまま回る。規約を読んだ人間は強制されていると誤信する。
- **改善案**: 各ゲートの記述に「実効環境（ローカル pre-push のみ／CI では SKIP）」を必ず併記する。または workflow.db の NDJSON export を Git 追跡化して CI で突合可能にし、「最後の砦」を実体化する。

### A-3. enforcement 自己無効化の手順が規約自身に文書化されており、禁止は advisory のみ
- **深刻度**: high
- **対象**: .agent-skill-chain/source/boot/CORE.md（127行目）、AGENT_CONDUCT.md（76〜84行目）
- **問題**: CORE §禁止事項に「ロックアウトされたら `!` シェルモードで `enforce off` を実行して復旧する」という手順が書かれている。一方、ゲート無効化 env（`*_GATE_ENABLED` 等）の自律設定禁止は AGENT_CONDUCT で「advisory であり技術的強制は困難」と明言されている。つまり (a) enforcement を丸ごと外すコマンドの存在と実行手順を、監督対象のエージェント自身が必ず読む文書に記載し、(b) それを止める仕組みは「エージェントが自制する」ことだけ、という構造になっている。`!` シェルモードの実行主体（人間かエージェントか）も明記されておらず曖昧。
- **失敗シナリオ**: エージェントが正当なブロック（例: #1 の carve-out 衝突）をロックアウトと誤認し、「復旧手順」として善意で `enforce off` を実行。以後の全作業が無強制で進行し、CI も SKIP（#2）のため誰も気付かない。悪用ではなく事故シナリオとして現実的に成立する。
- **改善案**: 復旧手順から実行主体を「人間のみ」と明記し、`enforce off` 実行に人間の対話的確認（tty 判定等）を要求する。

### A-4. quick モードの mode 信号が循環しており実質発動不能（または自己矛盾）
- **深刻度**: high
- **対象**: .agent-skill-chain/source/RULES.md（15・21行目）、skills/agent/run_command.md（47〜49行目）
- **問題**: quick モードの必須成果物は「設計メモと変更理由のみ」で 00〜04 のフルセットを作らないとされる。しかし mode の機械可読な正本は「00_要求定義.md frontmatter の `mode:`」であり、欠落時は standard 扱い（fail-safe）。さらに #35 branch 紐づけゲートは「quick でも必須」で、記録先はやはり 00 の frontmatter。つまり quick を成立させるには 00_要求定義.md を作成して frontmatter を書く必要があり、「00 を作らない軽量モード」という定義と矛盾する。00 を作らなければ standard 扱いになり #32/#34 で FAIL し、quick は永久に発動しない。
- **失敗シナリオ**: typo 修正 1 件の依頼で quick を選んだサブが、mode 信号を立てるためだけに 00_要求定義.md（テンプレート全セクション必須・Mermaid マインドマップ含む）を作成する羽目になり、軽量化の目的が完全に失われる。あるいは 00 を省略して audit FAIL。
- **改善案**: quick の mode 信号を 00 に依存しない場所（issue ディレクトリ直下の軽量マーカーファイル等）に定義し、quick の最小成果物セットにそのマーカーと branch 記録を含める。

### A-5. 「例外は認めない」絶対制約がユーザーの明示指示すら上書き不能で、委譲不可環境がデッドロックする
- **深刻度**: high
- **対象**: .agent-skill-chain/source/boot/CORE.md（9・17・74行目）、AGENT_CONDUCT.md（26行目）
- **問題**: CORE は「メインの実作業は例外なく禁止。委譲できない環境では委譲計画のみ返し実作業は行わない。例外は認めない」とする。AGENT_CONDUCT は「例外はユーザーの明示指示とプロジェクト実行契約のみ」とするが、§0 で「矛盾時は実行契約側が常に優先」と定めるため、ユーザーが「この環境ではサブが使えないから直接編集して」と明示指示しても、規約上メインは永久に拒否し続けるのが正しい挙動になる。ユーザー主権による override 経路と、障害時のエスカレーション経路がどこにも定義されていない。
- **失敗シナリオ**: サブエージェント機能が使えない環境（障害・非対応プラットフォーム）で、ユーザーの依頼に対しフレームワークは「委譲計画」を返すだけの状態が無限に続く。ユーザーの明示指示でも解除できないため、実質的にフレームワークを剥がすしか手段がない。
- **改善案**: 「ユーザーの明示指示（対象・操作を特定した発言）は CORE の委譲強制に対する唯一の override である」旨を CORE 側に定義する。

### A-6. 同一ルールの重複記載が大量にあり、自らの「正本 1 か所・重複禁止」原則に違反
- **深刻度**: high
- **対象**: .agent-skill-chain/source/boot/CORE.md（9・15・32・38・59・74行目ほか）、RULES.md（33・43行目）、skills/agent/run_command.md（3・19行目ほか）、enforcement/README.md（11行目）、HEARTBEAT.md
- **問題**: CORE 149行目は「実行契約の正本は本ファイル 1 か所のみ。重複記載をしてはならない」と定めるが、実態は逆で、(a)「メインは実作業をしない・例外なし」が CORE 内だけで 5 節以上、リポ全体で 8 か所以上ほぼ同文で反復、(b) タイムスタンプ取得ルール（`TZ=Asia/Tokyo date` 実行必須・推測禁止）が CORE/RULES/run_command（memo 用と issue フォルダ用にほぼ同一段落が 2 連）/PHASES の 4 ファイル 5 か所以上に重複、(c) close 移動のモード差説明が CORE 143行目（「宣言のみ」と言いつつ詳細まで記述）・PHASES 74行目・run_command 52行目に三重記載、(d) quick 免除条件が RULES/run_command/PHASES に三重記載。
- **失敗シナリオ**: ルール改定時に 1 か所だけ更新され、残りが旧文言のまま残る。LLM は複数の微妙に異なる文言から「どれが現行か」を判定できず、環境ごとに挙動が割れる。
- **改善案**: 各ルールに正本 1 か所＋他は 1 行参照の原則を機械監査（重複文言検知）するか、少なくとも CORE 内の反復を 1 節に統合する。

### A-7. 必読ファイル連鎖が自らの監視指標（参照文書 ≤ 8）を超過し、読了義務とコンテキスト経済が自己矛盾
- **深刻度**: high
- **対象**: .agent-skill-chain/source/boot/LOAD_POLICY.md（15・20〜21行目）、META_LAYER.md（125〜132行目）、enforcement/README.md（65〜68行目・系統C）
- **問題**: 1 件の作業依頼を full モードで通すと、CLAUDE.md → AGENTS.md → CORE → LOAD_POLICY → PHASES → PHASE_COMMAND_MAP → agents/orchestrator.md → run_command → commands/{name}.md → 各 SKILL.md（3〜4 件）→ TEMPLATES → テンプレート実体 → spec/ 4 ファイル → MODEL_SELECTION → MODEL_TIER_TABLE → EFFORT_POLICY → AGENT_CONDUCT → project/ 上書き群、と 20 ファイル前後の読了が要求される。META_LAYER 自身が「参照必須文書 ≤ 8 を超えたら簡素化を検討」と定める基準を恒常的に超過している。さらに enforcement 系統C は「orchestrator の Read/Grep 過大読込を警告する」hook を予定しており、読了義務を果たすほど警告される自己矛盾構造になっている。
- **失敗シナリオ**: サブ・メインともにコンテキストの大半を規約読了で消費し、肝心の成果物品質に使える文脈が枯渇する。実際には LLM が読了をスキップ・斜め読みし、「読了した」という未検証申告を誘発する。
- **改善案**: META_LAYER の指標を実測して基準内に収める簡素化 issue を最優先で立てる。読了義務を「凝縮版（1 ファイル）＋オンデマンド参照」に再設計する。

### A-8. プラットフォーム安全機構ブロック時の 4 原則と「進行役エスカレーション実行」が直接矛盾
- **深刻度**: medium
- **対象**: .agent-skill-chain/source/PLATFORM_SAFETY_RESPONSE.md（27〜47行目）、skills/agent/run_command.md（58・65行目）
- **問題**: PLATFORM_SAFETY_RESPONSE は「(a) 別経路での迂回を一切試みない」「(c) ユーザー自身の言葉で具体的対象が明示されるまで実行に進まない」と定める。一方 run_command は、分類器にブロックされたサブの操作を「進行役へエスカレーションし進行役が実行する」と定め、脚注では「進行役自身が実行すると成功した」事例を推奨パターンとして記録している。別セッション（進行役）から同一コマンドを再実行することはまさに (a) の「別経路での迂回」であり、スタンディング承認による実行は (c) の「新たな明示的承認」を経ない。両文書はどちらが優先するかを規定していない。
- **失敗シナリオ**: サブがブロックされた際、run_command を読んだ進行役は即エスカレーション実行し、PLATFORM_SAFETY_RESPONSE を読んだ進行役は停止してユーザー承認を待つ。同じ状況で挙動が二分され、前者の解釈が「安全機構の組織的迂回」として常態化する。
- **改善案**: PLATFORM_SAFETY_RESPONSE に「run_command §既承認済み操作は本 4 原則の明示的例外である（またはでない）」の優先関係を 1 行で定義する。

### A-9. AGENT_CONDUCT「凝縮版をそのまま転記」と run_command「リンクのみで足りる」の矛盾（ドリフト実例）
- **深刻度**: medium
- **対象**: .agent-skill-chain/source/AGENT_CONDUCT.md（88〜90行目）、skills/agent/run_command.md（88行目）
- **問題**: AGENT_CONDUCT 第 3 部は「進行役は委譲パケット組み立て時、Constraints 末尾へ以下を**そのまま転記する**」と命令形で定めるが、run_command は「参照リンクのみ記載すれば足り、**全文の逐語転記は不要**」と定める。§0 の優先規則で run_command が勝つとしても、負けた側の命令文が現役の文面のまま残っており、正本分散によるドリフトが既に顕在化した実例になっている。
- **失敗シナリオ**: AGENT_CONDUCT だけを読んだ進行役が毎回約 20 行を全委譲パケットに転記し、コンテキストとコストを浪費する。逆にリンク先を読まないサブは規範を一切受け取らない。
- **改善案**: AGENT_CONDUCT 第 3 部の見出し・導入文を「転記または参照（運用は run_command §委譲時の行動規範参照が正本）」に修正する。

### A-10. skill ファイルである run_command.md が policy の巨大集積地となり、META_LAYER の責務境界を自ら破っている
- **深刻度**: medium
- **対象**: .agent-skill-chain/source/skills/agent/run_command.md（44〜96行目）、META_LAYER.md（89〜106行目）
- **問題**: META_LAYER は「skill に rule を書く」「command に policy を書く」を禁止例として明記する。しかし run_command.md（skills/ 配下）の §Constraints は、review-docs ゲート・GitHub Issue 起票ゲート・branch/PR 紐づけゲート・ISSUE_TRACKING_MODE 二重モード・外部書き込み実行主体・モデルティア/effort 選定・バックグラウンド実行抑止と、フレームワーク最大級の policy 集積になっている。また META_LAYER の 4 層モデル（RULES/COMMANDS/SKILLS/TEMPLATES）は、実在する構造（boot/・workflow/・spec/・enforcement/・ルート直下 20 超の policy ファイル）と対応しておらず、AGENT_CONDUCT や CLOSEOUT がどの層かも判定不能。
- **失敗シナリオ**: 「委譲の I/F だけ知りたい」サブが 126 行の policy 混在ファイルを全読了させられる。ゲートのルール変更のたびに skill ファイルが改版され、META_LAYER 違反チェック（基盤変更レビューの必須項目）が形骸化する。
- **改善案**: 各ゲートの正本を workflow/ 配下の独立 policy ファイルへ移し、run_command は委譲 I/F（Task/Constraints/OutputSpec の形式）だけに戻す。

### A-11. CORE 禁止リストの「Read/Grep/Glob…を自分の作業として説明すること」が多義的で、Read 使用可否が判定不能
- **深刻度**: medium
- **対象**: .agent-skill-chain/source/boot/CORE.md（63〜72行目）
- **問題**: 「やってはいけないこと」列挙の最終項が「Read / Grep / Glob / Write / Edit / Shell を**自分の作業として説明すること**」となっており、(a) ツールの使用自体の禁止か、(b) 使用を「自分の実作業」として説明することの禁止か、が文法的に決定できない。(a) と読むと、phase 判定・PHASES 読了・HEARTBEAT 読了・完了証跡の確認というメインの必須責務がすべて Read を要するため自己矛盾する。107行目は Write/Edit/Shell のみ使用直前チェックを課しており、Read/Grep/Glob は使用可と示唆するが、明文はない。
- **失敗シナリオ**: 保守的に (a) と解釈したメインが読了義務を果たせず停止する。逆に (b) と解釈したメインとの間で挙動が割れ、enforcement 系統C（Read/Grep 抑制）の閾値設計とも整合が取れない。
- **改善案**: 「Read/Grep/Glob は phase 判定・証跡確認のため使用可。Write/Edit/Shell は使用禁止（carve-out を除く）」と 1 文で明示する。

### A-12. META_LAYER Rule 3「enforcement を伴わないルール追加禁止」と advisory ルール群の量産が自己矛盾
- **深刻度**: medium
- **対象**: .agent-skill-chain/source/META_LAYER.md（71〜85・110〜132行目）、AGENT_CONDUCT.md（7・62〜72行目）、PLATFORM_SAFETY_RESPONSE.md 全体
- **問題**: META_LAYER は「enforcement を伴わないルール」「ルール追加のみの変更」を禁止する。しかし AGENT_CONDUCT（8 原則すべて advisory・CI 非強制と自認）、PLATFORM_SAFETY_RESPONSE（強制機構なし）、ゲート自己無効化禁止（advisory）、失敗条件 #22〜#24・#30（未実装・人手監査）と、機構を伴わないルールが体系的に追加され続けている。メタ層の監視指標（command ≤ 4 等）自体を測る監査も存在せず、指標も口頭ルールに留まる。
- **失敗シナリオ**: 「advisory と明記すれば Rule 3 を通過できる」という運用が先例化し、基盤膨張防止ルールが実質失効。文書量が増えるほど #7 の読了コスト問題が加速する。

### C-1. 強制機構それ自身が hook / audit のどちらでも保護されていない（自己弱体化の直接経路）
- **深刻度**: high
- **対象**: PreToolUse.sh R1（L778-837）, audit.sh check #19（L634-646）, PROTECTED_PATHS.txt, orchestrator-allowlist の項（README L148）
- **問題**: R1 が直接 Write/Edit を一律 block するのは `.agent-skill-chain/runtime/` 配下のみ。強制の正本である `.agent-skill-chain/source/enforcement/`（PreToolUse.sh・audit.sh・check-comment-refs.sh・worktree_record_guard.sh）や `.agent-skill-chain/project/orchestrator-allowlist.txt`・`settings.enforce.json`・`.scribe-nonce` は、どの runtime ガードの保護対象でもない。audit の成果物対応チェックも `source/enforcement/*.sh` の改変には一切対応する監査項目が存在しない。worker サブエージェント（IS_SUBAGENT=1）は Edit/Write が許可されているため、hook スクリプトや allowlist・audit スクリプト自体を自由に書き換えられる。
- **失敗シナリオ**: 自律稼働中の worker が PreToolUse.sh の R2 block 行を削除、または orchestrator-allowlist.txt に書込ツールを追記、あるいは audit.sh の check を潰す編集を行っても、どの hook も止めず、どの audit 項目も FAIL しない。
- **改善案**: 少なくとも `source/enforcement/`・`project/orchestrator-allowlist.txt`・`settings.enforce.json` への Write/Edit を全 ROLE（worker 含む）で block する path ガードを追加し、これらの差分を検出したら委譲・レビュー証跡を要求する項目を足す。

### C-2. audit の各ゲートが env トグルで無効化でき、ローカル pre-push（唯一の実効経路）を AI が自ら中和できる
- **深刻度**: high
- **対象**: audit.sh（GITHUB_ISSUE_GATE_ENABLED L1187, BRANCH_LINK_GATE_ENABLED L1269, PR_LINK_GATE_ENABLED L1331, MODEL_TIER_GATE_ENABLED L1459, WORKTREE_NAMING_AUDIT_ENABLED L1575, MAIN_WORK_GATE_TOLERANCE_SECONDS L690, WORKFLOW_DIRS L132, AUDIT_GIT_RANGE L84）, ci/pre-push.example

### E-1. setup.sh の論理パス比較により、シンボリックリンク経由実行で自分自身の source を rm -rf しうる
