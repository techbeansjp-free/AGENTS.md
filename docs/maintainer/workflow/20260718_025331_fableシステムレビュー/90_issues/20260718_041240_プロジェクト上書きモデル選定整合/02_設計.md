## 0. 前提整理（読み取り確認で確定した事実）

- **`.agents` は「存在しないディレクトリ」ではなく `.agent-skill-chain/source` 層のフレームワーク別称**である。`source/README.md` の見出しが `# .agents — 構成と索引`、`META_LAYER.md`・`GETTING_STARTED.md`・`platforms/SKILLS.md` 等でも `.agents` を「本フレームワーク／source 層」の意味で多用。したがって F-11 の「存在しないディレクトリを指す」という前提は誤読で、実体は**用語不統一**（同一概念を `.agents` と `.agent-skill-chain/source` の 2 表記で書いている）である（02_対応方針の判定と一致）。
- **`ledger/schema.sql` は `model_tier`/`tier_rationale`/`tier_exception` 列を持つが `effort` 相当列は無い**（21〜30 行目を実測確認）。D-12 の「model_tier には記録系があるが effort には無い」は事実。
- **`schema.sql`・`scripts/write-workflow-log.sh`・`enforcement/ci/audit.sh`（#38 tier ゲート）は #145「台帳記録整合強化」パッケージおよび enforcement 系パッケージの所有**であり、本パッケージの所有物ではない。#145 の 00 は「D-11・D-12 は別パッケージへ移管済み・本パッケージ対象外」と明記しつつ、`schema.sql`/`write-workflow-log.sh`/`audit.sh` を自パッケージの対象ファイルに含む。→ **D-12 の ledger 記録欄追加は #145 所有ファイルへ波及する**（§4 で扱う）。
- **`source/MODEL_SELECTION.md`・`source/EFFORT_POLICY.md` は本パッケージの対象ファイル**（00 §8）であり、他サブ issue の対象ファイルと重複しない（#145 は EVIDENCE_POLICY/REVIEW_RULE/CODE_COMMENT_RULES/DOCS_*/CLOSEOUT/HEARTBEAT を対象とし MODEL_SELECTION/EFFORT_POLICY を含まない）。
- **`enforcement/README.md`（#40 grandfather 救済のセマンティクス正本）は enforcement 系パッケージの所有**。F-6 は grandfather **ファイル本体**（`project/worktree-naming-grandfather.txt`）のみを本パッケージで改修し、`enforcement/README.md` の #40 記述変更は enforcement パッケージへ連携する（§4）。
- **`source/COVERAGE_AND_EXCEPTIONS.md`（カテゴリ 1〜4 の正本）は本パッケージの対象ファイルに含まれない**。F-9 は本パッケージ所有の `project/COVERAGE_EXCEPTIONS.md` 内で完結する方式を採る（source のカテゴリ追加はしない）。

## 2. 要設計判断 4 件の詳細（複数案・トレードオフ・推奨）

### F-3: opus 要否先行判定の判定基準をどこまで明文化するか

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A | 複雑さの数値閾値（行数・ファイル数等）を明文化 | 完全に機械的・非裁量 | 硬直化。閾値が実態に合わず頻繁更新、境界値付近で誤誘導 |
| **B（推奨）** | **チェックリスト形式の判定観点を列挙（目安）。1 つでも該当なら opus、全て非該当なら sonnet。該当観点を TIER_RATIONALE に 1 行記録** | 非裁量性（観点明示・事後監査可能）を保ちつつ、目安なので過度に硬直しない | 観点の当てはめに最小限の判断が残る（ただし記録により検証可能） |
| C | 現状維持（基準を書かない） | コストゼロ | 空洞のまま。指摘未対応 |

**推奨: B**。理由: 00 §1.2 が求める「非裁量の建前と実運用の乖離解消」を、A の硬直化を避けつつ達成できる唯一の折衷。チェックリスト例（本表に明記する内容）:

1. 複数コンポーネント／複数フェーズへ横断的に影響するか
2. 公開 I/F・契約・スキーマ・enforcement・セキュリティ/権限/課金に触れるか
3. 後戻りコストが高いか（データ移行・破壊的変更・不可逆操作）
4. 要件が曖昧で設計判断を多く含むか
5. 同種タスクで過去に sonnet が収束しなかった実績があるか

→ 1 つでも「はい」なら opus、すべて「いいえ」なら sonnet。判定結果と該当番号を TIER_RATIONALE に記録。
このチェックリストは F-1 で追加する「実装／要求・要件執筆／issue 起票／調査／デフォルト」各行の「opus 要否先行判定」の共通判定機構として再利用する（機構を 1 か所に集約し重複を防ぐ）。

## 3. 要ユーザー確認 論点

1. **【D-12・主論点】effort の ledger 記録欄追加を「今」実施するか**
   effort/effort_rationale 列の追加は `ledger/schema.sql`・`scripts/write-workflow-log.sh`・`enforcement/ci/audit.sh`（いずれも #145「台帳記録整合強化」または enforcement パッケージ所有）へ波及し、既存 workflow.db のスキーマ移行（#145 の D-1/E-2 entry_hash 再計算方針と連動しうる）を伴う。選択肢:
   - (A) 本 issue で #145 と調整のうえ列追加・audit 化まで進める（推奨。ただし cross-package 実施の go サイン要）。
   - (C) 本 issue は EFFORT_POLICY.md の明記義務明確化＋ project 側 role×effort 受け皿の新設までを確定し、schema/audit 実装は #145 または専用 issue へ委譲（所有境界を侵さない）。
