## 4. 敵対的観点リスト（すべて検証・解消を確認）

1. **E-1 のアサートが恒常的にデッドコードにならないか**: 外側 if を物理パス比較にしたため、通常経路ではアサートに到達する前に分岐で弾かれる。しかし変数の独立再解決（`assert_dest`）により、将来同ファイル内の他コードが `src_phys`/`dest_phys` を誤って再代入・共有した場合の防波堤として機能する（多重防御の意図どおり）。デッドコードではなく回帰時のみ発火する設計であることを確認。
2. **own 判定（`pwd -P`）と E-1 修正の相互作用**: own モード（PACKAGE_ROOT=PROJECT_ROOT）でも E-1 修正後のブロックは実行される（own 判定はバックアップ・移行の要否のみを分岐させ、AGENTS_SOURCE/ASC_SOURCE_DEST 比較はモードに関わらず通る）。own かつ物理パス同一の通常ケースでは「コピーをスキップ」に正しく倒れることを実測確認済み（§2 T-E1-1 の own 分岐実行結果）。
3. **E-4 の trap が正常系の出力を変えないか**: `trap on_move_fail ERR` → 成功時 `trap - ERR` で解除する構造のため、正常時の stdout（移動ログ・件数）は変更されない。エラーパス（`die` は独自に `exit 1` するため ERR trap とは独立）との相互作用も確認し、想定通り分離されている。
4. **E-5 のクォート修正が既存の正常パス（メタ文字を含まないパス）で結果を変えないか**: `${var#"$prefix"/}` は非メタ文字パスでは従来と同じ結果を返す（パラメータ展開のパターンをリテラル化するだけで、通常文字列には影響しない）。実測でも通常ディレクトリ名でのテストと [WIP] 付きテスト双方で正しい挙動を確認。
5. **E-6 の緩和が traversal を再び通す余地がないか**: `/` `..` チェック（既存）→ 先頭ドット・制御文字チェック（新設）→ base 配下判定（既存 90-95 行相当）の 3 段防御が維持されており、緩和したのは ASCII 限定という中間層のみ。traversal 系の REJECT は実測でも維持されていることを確認。
6. **E-7 の一時ファイル方式がリソースリーク（mktemp の後片付け漏れ）を生まないか**: 正常パス・失敗パスの両方で `rm -f "$_links_tmp"` を通ることを確認（失敗時は即 `exit 2` する直前に `rm -f`、正常時はループ末尾で `rm -f`）。
7. **E-9 の sqlite3 スキップが後続処理（enforcement 既定 on 配線）を止めないか**: `init_workflow_db` の `return 0` はこの関数のみに閉じており、呼び出し元 `init_workflow_db` の後続行（`enforce_default_on_if_possible` 呼び出し）はこの関数の戻り値を見ていないため影響しない。コードを目視確認済み。
8. **E-11 の noclobber がリトライループの再試行機会を奪わないか**: `if ( set -C; ... ) 2>/dev/null` はサブシェル＋条件文脈のため、redirect 失敗時も外側 `set -e` は発火せず `return 1` に到達する。単体テストで 2 回連続呼び出しを行い、1 回目成功・2 回目失敗（return 1）・スクリプト継続、を実測確認済み。
9. **E-12 の無条件 JST 化が他スクリプトとの一貫性を壊さないか**: 波及先とされた `new-workflow-memo.sh`・`create-pr-review-issue-dir.sh` のフォールバックの双方も同時に無条件 JST 化し、`memo-prefix.sh` 含め 3 経路すべてが同一の挙動（TZ 環境変数の値に関わらず JST を使う）に統一されていることをコード上で確認。
10. **E-13 の警告が stdout（関数の唯一の出力である件数）を汚さないか**: 警告メッセージはすべて `>&2` で出しており、`deploy_skills_impl` の最終行 `echo "$n_skill"` への影響がないことをコードで確認。
11. **E-15 の事前存在チェックが通常の（同一秒でない）再配備を誤って止めないか**: チェックは `bak.$ts`（当該実行のタイムスタンプ）のみを見るため、秒をまたぐ通常再配備では新しい ts でパスが変わり誤爆しない。既存の E-9 sqlite3 検証等と同様、ロジックが単純なため目視確認に留めた。
12. **E-16 の書込みロジックへの影響有無**: `write_yaml_version` は変更していない（読取専用の修正であることを diff で確認）。既存の非クォート apm.yml に対する `--check`/`--write` の実行結果に変化がないことを実測確認済み。
13. **E-17 の連番方式が既存の「hint 指定時は既存ディレクトリを採用」分岐と衝突しないか**: 連番ロジックは新規作成パス（`ISSUE_DIR_HINT` が空の場合）にのみ追加されており、hint 指定時の既存ディレクトリ採用分岐（74-98 行相当）には触れていないことをコードで確認。
14. **E-19 のロジック二重化（extract_links と check_anchor の両方に同一の fence 追跡コードを重複実装）が将来のドリフト源にならないか**: 設計書 §1 E-19 の理由欄で「ロジック二重化はコメントで明示」とされている方針に従い、両ヘルパーの該当箇所に「E-19: extract_links と同一のフェンス種別・長さ追跡ロジック」という相互参照コメントを付与し、変更時に見落とされにくくした（1 ファイルへの統合は python ヘルパーが埋め込み heredoc のため構造上困難であり、02_設計.md も二重化を許容する前提で設計されている）。
