# fableシステムレビュー 指摘: 対応方針

**前のステップ**: [01_指摘一覧.md](./01_指摘一覧.md)
**次のステップ**: ユーザーが本ファイルの方針を確定させたのち、採用分について進行役が GitHub Issue 化の要否を判断する

---

## 方針の決め方

- **採用**: 指摘が正しく、対応する（対応の実施は本 issue の対象外。方針確定後、必要に応じて別途 GitHub Issue 化する）。
- **見送り**: 指摘が誤り・過剰・スコープ外と判断し、対応しない（理由を記載）。
- **要検討**: 実装・設計を確認したうえで、採用か見送りをあとで決める。

> 本ファイルの「方針」列は、進行役の判断で採用/見送りを確定させることなく、**全件「要検討」で初期化**しています。ユーザーが確認のうえ、各行の方針を確定させてください。

## 深刻度別の参考情報（high 深刻度の指摘）

> 以下は優先順位付けの参考情報であり、方針を決めるものではありません（上記の一覧表がすべての判断の正本です）。

- **A-1**: 進行役の外部書き込み carve-out と enforcement の Bash 全面ブロックが物理的に矛盾
- **A-2**: 「最終保証は CI audit」が構造的に空洞化している
- **A-3**: enforcement 自己無効化の手順が規約自身に文書化されており、禁止は advisory のみ
- **A-4**: quick モードの mode 信号が循環しており実質発動不能（または自己矛盾）
- **A-5**: 「例外は認めない」絶対制約がユーザーの明示指示すら上書き不能で、委譲不可環境がデッドロックする
- **A-6**: 同一ルールの重複記載が大量にあり、自らの「正本 1 か所・重複禁止」原則に違反
- **A-7**: 必読ファイル連鎖が自らの監視指標（参照文書 ≤ 8）を超過し、読了義務とコンテキスト経済が自己矛盾
- **B-1**: 「各フェーズ完了時の verify-and-close 必須」と「04_review は実装後のみ」の正面衝突
- **B-2**: README.md と SKILL.md の二重定義ドリフト（review 系で DoD レベルの相違が実在）
- **B-3**: create-pr-review-issue が「実装前（03 完了後）」に位置づけられ時系列が成立しない
- **C-1**: 強制機構それ自身が hook / audit のどちらでも保護されていない（自己弱体化の直接経路）
- **C-2**: audit の各ゲートが env トグルで無効化でき、ローカル pre-push（唯一の実効経路）を AI が自ら中和できる
- **D-1**: entry_hash / prev_hash による改ざん検知が実質形骸化している
- **D-2**: document_id の「必須・任意禁止」宣言と DB スキーマの NULL 許容が真っ向から矛盾
- **D-3**: 「必須キー」の定義が 4 ファイルで食い違い、正本が決まらない
- **D-4**: INSERT OR IGNORE 推奨が新スキーマでは重複防止にならず、逆に証跡のサイレント欠落を招く
- **E-1**: setup.sh の論理パス比較により、シンボリックリンク経由実行で自分自身の source を rm -rf しうる
- **F-1**: MODEL_TIER_TABLE の役割カバレッジに欠落があり、非裁量原則とデッドロックする
- **F-2**: enforcement 配下の bash が計測分母外なのに台帳行が無い（台帳なし除外）
- **G-1**: 追跡ポリシーの正面矛盾（「00〜04 は git 追跡」対「gitignore で非追跡」）
- **G-2**: 「機械強制の三層」が本リポでは実質すべて無効で、73KB の手順文書の遵守だけが頼り
- **G-3**: ADR 参照の名前空間が非一意（同一番号が別決定を指す）かつ参照先が読解不能
- **G-4**: 書き戻し漏れの「唯一の予防策＝手順遵守」宣言と、委譲往復がむしろ漏れを助長する構造
- **G-5**: worktree データロスト事故への対症療法の三重積層（根本原因は未解決のまま）
