## 1. 概要

### 1.1 システム概要

サブ委譲時のモデルティア選定について、コア（`.agents/`）に「裁量での上振れ・下振れの両禁止」と「根拠（対応表の該当行）明記必須」というエスケープハッチ形骸化防止の抽象統治原則を昇格する。具体ティア表・モデル名・降格判断は `.agents-project/` に委ねる現行の汎用/固有境界を維持する。

### 1.2 用語集

| 用語 | 説明 |
| ---- | ---- |
| ティア | サブ委譲先に割り当てるモデルの段階（上位・標準・軽量等）。具体名はコアに置かない。 |
| 上振れ | 本来割り当てるべきより上位のティアを選ぶこと。旧「迷ったら上位」がこれを誘発した。 |
| 下振れ | 本来割り当てるべきより下位のティアを選ぶこと（コスト都合の降格）。 |
| 根拠（対応表の該当行） | 委譲パケットに 1 行で記す、どの対応表行に基づいてティアを選んだかの明示。 |
| エスケープハッチ形骸化 | 例外条項（迷ったら上位の裁量上振れ・裁量下振れ許可・上位エスカレーションの常用化等）が日常運用化し、対応表・閾値が骨抜きになる現象。なお `MODEL_SELECTION.md §4` の未収束エスカレーションは「収束しない」という条件で発火する非裁量の手続きであり、条件を満たさないのに常用すると形骸化に転じる点を区別する。 |

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: 裁量上振れの禁止

- **As a** 委譲を行うオーケストレータ
- **I want to** 「迷ったら上位」という裁量での上振れを禁止する原則をコアで参照できる
- **So that** サブの大半が最上位ティアへ流れて対応表が形骸化する再発を防げる

**受け入れ基準**:

- コアに「裁量での上振れ（迷ったら上位）はしない」旨が明文化されている。
- 「迷ったら上位」が形骸化を招いた事実（再発防止の根拠）が、コア本文または参照で辿れる（一次参照は親 00 §S3／本サブ 00 §1.2 の背景記載。元ポリシー `MODEL_SELECTION_POLICY.md` は本リポに現存しないため、リポ内導線は親 00 を辿る形とする＝00 §9 と整合）。

#### ストーリー 2: 裁量下振れの禁止と手続き

- **As a** 委譲を行うオーケストレータ
- **I want to** コスト都合での裁量的な下振れ（降格）も禁止し、許可される条件を知りたい
- **So that** 品質ゲートを犠牲にした安易な降格を防げる

**受け入れ基準**:

- コアに「裁量での下振れはしない」旨が明文化されている。
- 下振れが許される手続き（計測データ＋ユーザー承認＋対応表更新）が必要であることがコアで示される（具体閾値・手順は `.agents-project/` 委譲）。
- 既存 §3「品質ゲート最上位固定」と矛盾しない（コスト都合で品質ゲートを下げない）。

#### ストーリー 3: 根拠明記の必須化

- **As a** 委譲を受けるサブエージェント
- **I want to** 委譲パケットにティアだけでなく根拠（対応表の該当行）が 1 行で明記されている
- **So that** どの基準でそのティアになったかを検証でき、エスケープハッチの形骸化を監査できる

**受け入れ基準**:

- コア §2 のティア明記義務に「根拠（対応表の該当行）を 1 行明記」が加わる。
- 根拠の具体的な対応表（行の中身）はコアに置かず `.agents-project/` 参照とする。

#### ストーリー 4: 昇格先の決定材料

- **As a** 本サブ issue の設計者
- **I want to** 昇格先を `MODEL_SELECTION.md` に置くか `COVERAGE_AND_EXCEPTIONS.md` の汎用原則へ集約するかの判断材料を要件で得たい
- **So that** 1 ファイル 1 責務・重複禁止を守って設計フェーズで一本化できる

**受け入れ基準**:

- 両案の論点（責務の近さ・重複リスク・参照導線）が 01 に整理されている（§2.3 参照）。
- 最終決定は設計フェーズに委ねる旨が明記されている。

### 2.2 BDD ユースケース

#### ユースケース 1: 裁量を絞った委譲

**シナリオ 1: 上振れの抑止**

```gherkin
Feature: モデルティア選定の裁量禁止
  Scenario: 迷ったときに上位へ流さない
    Given ティア選択可能なランタイムでサブ委譲を行う
    And オーケストレータがティアの選定に迷っている
    When コアの選定原則を参照する
    Then 「迷ったら上位」という裁量上振れは禁止されている
    And 対応表の該当行に基づいてティアを選び、その行を根拠として明記する
```

**シナリオ 2: 根拠明記の必須化**

```gherkin
Feature: モデルティア選定の裁量禁止
  Scenario: 委譲パケットに根拠を 1 行明記する
    Given サブ委譲のパケットを組み立てる
    When ティアを決定する
    Then パケットにティアと根拠（対応表の該当行）が 1 行で明記される
    And 根拠の無いティア指定は不可である
```

**シナリオ 3: 下振れの手続き要求**

```gherkin
Feature: モデルティア選定の裁量禁止
  Scenario: 裁量的な降格を拒否する
    Given コスト都合で下位ティアへ落としたい
    When 計測データ・ユーザー承認・対応表更新のいずれかが欠けている
    Then 裁量での下振れは禁止され、降格できない
    And 品質ゲート（レビュー・テスト・受け入れ基準）は最上位に固定される
```

**シナリオ 4: 対象外環境での不発火**

```gherkin
Feature: モデルティア選定の裁量禁止
  Scenario: ティア選択概念が無い環境では発火しない
    Given ティア選択の概念が存在しないランタイムである
    When サブ委譲を行う
    Then 本原則（裁量禁止・根拠明記）は適用されず、ランタイムのデフォルトに従う
```

#### ユースケース 2: 昇格先の決定（設計入力）

**シナリオ 5: 昇格先の論点整理**

```gherkin
Feature: 昇格先の決定材料
  Scenario: 重複を避けて昇格先を決める
    Given 同種の「例外形骸化防止」原理が COVERAGE_AND_EXCEPTIONS.md に部分存在する
    When 昇格先の候補（MODEL_SELECTION.md / COVERAGE_AND_EXCEPTIONS.md 集約）を比較する
    Then 各案の責務の近さ・重複リスク・参照導線が整理される
    And 最終決定は設計フェーズへ委ねられる
```

### 2.3 ビジネスルール

- **裁量両禁止**: ティア選定は裁量で上振れも下振れもしない。
- **根拠明記必須**: 委譲パケットにティア＋根拠（対応表の該当行）を 1 行明記する。
- **下振れの手続き**: 下振れは計測データ＋ユーザー承認＋対応表更新を経てのみ許可（具体手順は `.agents-project/`）。
- **エスケープハッチ常用化の防止**: 例外経路（裁量上振れ・裁量下振れ・上位エスカレーション）が日常運用化して対応表・閾値を骨抜きにしないこと。`MODEL_SELECTION.md §4` の未収束エスカレーションは「収束しない」条件でのみ発火する非裁量手続きとして既存どおり維持し、本 issue は再設計しない（00 §5 除外と整合）。
- **PF 中立**: 具体ティア表・モデル名・コスト実測・降格閾値はコアに置かない。
- **1 ファイル 1 責務・重複禁止**: 昇格先は一本化し、採用しない側は相互参照で結ぶ。
- **昇格先の論点（設計入力。最終決定は設計フェーズ）**:
  - **案 A: `MODEL_SELECTION.md` §2 を拡張**。利点＝モデルティアの責務に閉じ、参照導線が短い。論点＝「例外形骸化防止」という汎用原理が `COVERAGE_AND_EXCEPTIONS.md` と概念的に重なるため、相互参照を張らないと二重定義に見えるおそれ。
  - **案 B: `COVERAGE_AND_EXCEPTIONS.md` の汎用原則として集約**（例外の二重化・禁止する回避パターンと同列に「裁量を絞り根拠を要求する」一般原則を置き、`MODEL_SELECTION.md` から参照）。利点＝形骸化防止の汎用原理を一箇所に集約でき DRY。論点＝当該ファイルはテストカバレッジ例外の正本であり、モデルティアという別文脈を混ぜると単一責務が薄まるおそれ。
  - 判断材料: 設計原則「再利用より責務の明確さ」「docs と実装の不整合を放置しない」を踏まえ、責務の純度（案 A 寄り）と DRY（案 B 寄り）のトレードオフを設計で決する。

## 5. 制約事項

- 具体ティア対応表・モデル名・コスト実測・降格判断ロジックはコアに置かない（PF 中立性）。

- 昇格先は 1 ファイルに一本化し、重複定義しない（相互参照で結ぶ）。
- 対象外環境（ティア選択概念が無いランタイム）では本原則を発火させない。
