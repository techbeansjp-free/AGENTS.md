# 実装レビュー: PreToolUse / PostToolUse / audit.sh

**読む際の注意**: 本ドキュメントは、hook 実装レビューの結果として**未解決事項を整理したもの**である。現状、PreToolUse/PostToolUse は案内のみで物理強制（reject）は未達。以下では、**現状の統制（案内＋CI）** と **プラットフォームがメタ情報を渡す場合の実装方針** を分けて記載する。**次にやるべきレビュー**: audit.sh 本体の中身だけを単独で見ること（監査観点の設計が実装に厳密に反映されているかの確認）。

設計レビューから hook 実装レビューへ進んだ結果をまとめる。**本当にメインの Write/Edit/Shell が拒否されるか**「書記以外が sqlite3 を叩けないか」を実装レベルで明確にする。

---

## PreToolUse.sh

| 項目 | 内容 |
|------|------|
| **責務** | ツール実行前に読了・契約を確認するフック。メインの (1) .workflow 配下 00/01/02/03/04 または memo への直接 Write/Edit、(2) 実装・設計・レビュー本文の直接執筆、(3) Shell の直接実行、および書記以外の sqlite3 実行を**可能な範囲で**ブロックする。 |
| **現在の実装** | CORE.md 等の存在時のみ、標準エラーへ**案内メッセージ**を出力する（「00/01/02/03/04 やコードを直接編集しない」「memo の YYYYMMDD_HHMMSS_ を手で付けない」等）。**exit 0 で終了**。ツール名・対象パス・コマンド文字列は引数や環境変数で渡されない。 |
| **限界** | **Write/Edit のブロック**: 実装では **exit 1 していない**。案内のみ。**Shell のブロック**: 同様に **exit 1 していない**。**書記以外の sqlite3 のブロック**: 呼び出し元がメインかサブか・ロールが書記かは本フックでは判別できないため、**区別してブロックしていない**。 |
| **補完** | プラットフォームの権限設定または CI（audit.sh）で、03→04 未実施・memo プレフィックス違反・timestamp 乖離等を事後検知し reject する。 |

---

## PostToolUse.sh

| 項目 | 内容 |
|------|------|
| **責務** | ツール実行後の証跡確認。workflow.db 本則・memo 過渡的・例外であること、および memo の YYYYMMDD_HHMMSS_ プレフィックス規約を案内する。 |
| **現在の実装** | 標準エラーへ**案内メッセージ**を 1 行出力するのみ。**exit 0 で終了**。作成されたファイルのプレフィックス形式の検証は行わない。 |
| **限界** | 作成ファイルのプレフィックス・内容の検証は**行っていない**。環境依存のため厳密な検証は CI に委ねるとコメントにある。 |
| **補完** | audit.sh で memo の YYYYMMDD_HHMMSS_ プレフィックス・プレースホルダ・年範囲・prefix と mtime の乖離を検知する。 |

**検知している失敗条件の一覧**（enforcement/README §失敗条件と差し戻し と一致）:

**memo 関連の検知**:

- memo ファイルの**プレフィックス**が YYYYMMDD_HHMMSS_ でない → FAIL。
- プレースホルダ（00000000, 000000）→ FAIL。
- 年の範囲が 2000〜2100 以外 → FAIL。
- プレフィックス時刻とファイル mtime が 10 分以上乖離 → FAIL。

**hooks でブロックできない分の補完**: メインの直接 Write/Edit で 03 だけ更新して 04 を書かないケースは、hooks ではブロック不可のため、本 script の「03 存在かつ 04 不在」で reject している。

## verify-and-close 未実行・ログ未記録を落とせるか

- **verify-and-close 未実行**: **落とせる**。audit.sh の #3（117〜127 行）で、`.workflow` 配下の `03_実装計画.md` を find し、同一 issue ディレクトリに `04_review.md` が存在しない場合に `EXIT_CODE=1` で FAIL とする。
- **ログ未記録**: audit.sh では workflow.db の件数やログ有無までは検証していない旨を注記する。現状の audit は 04 ファイルの**存在**と内容キーワードのみを対象とする。

## A. 現状の統制（メタ情報を渡さない場合）

PreToolUse.sh と PostToolUse.sh は上記の表のとおり、案内メッセージの出力のみで **exit 0** で終了しており、違反時の exit 1 による物理的拒否は実装されていない。その場で違反を止めるのではなく、**CI（audit.sh）で事後検知する構成**である。物理強制の判定チェックリストおよび総合判定を参照。

---

## B. プラットフォームがメタ情報を渡す場合の reject 実装

将来、Claude Code 等のプラットフォームが PreToolUse に「ツール名」「対象パス」を引数で渡す場合の例（疑似コード）:

```bash
# 例: $1=ツール名, $2=対象パス（または $2 が空の場合は Shell のコマンド文字列）
if [[ "$1" == "Write" || "$1" == "Edit" ]]; then
  if [[ -n "${2:-}" ]] && [[ "$2" == *".workflow"* ]]; then
    case "$2" in
      *"/00_"*|*"/01_"*|*"/02_"*|*"/03_"*|*"/04_"*|*"/memo"*) echo "BLOCKED: direct edit to workflow artifact" >&2; exit 1 ;;
    esac
  fi
fi
exit 0
```

※ 実際の採用時は、パスの正規化・サブディレクトリの扱い・Shell 時の $2 の解釈を仕様に合わせて定義する必要がある。

## 総合判定

- **PreToolUse.sh**: 設計思想の再通知としては OK。**物理強制フックとしては NG 寄り**。違反を止めるのではなく違反前の注意喚起になっている。ツール名・対象パス・呼び出し元ロールが取れないため、現状では拒否判定ができない。
- **PostToolUse.sh**: 補助的な案内としては OK。**強制フックとしては弱い**。証跡規約のリマインドはするが、違反をその場で止めていない。
- **audit.sh**: **事後監査としては良い**。03→04 未実施・テスト観点・docs 言及・PR 内部参照・memo プレフィックス等を検知する。ただし**物理強制の代替にはならない**。その場で防ぐのではなく後で落とす方式。
- **全体**: 現状の enforcement は **「注意→注意→CIで発覚」** の構成であり、**「その場で物理的に拒否」** の構成にはなっていない。**今の版は、物理強制を目指した設計にはなっているが、実装はまだ「物理強制」ではなく「案内＋監査」段階である。**

## 3 点に対する改善ロードマップと修正方針

- **第 1 優先**: README / DESIGN / IMPLEMENTATION_REVIEW の表現を完全に揃える。最上位 README にも「現状は案内＋CI、hook reject は未達」を明記する（enforcement/README.md の「矯正するもの（物理強制の例）」に従い実施）。
- **第 2 優先**: sqlite3 直接実行をやめ、**専用ラッパー 1 本**経由に一本化する。
  - ラッパー要件: 書き込み先は .workflow/workflow.db 固定、workflow_log テーブルのみ、INSERT のみ、必須カラム未指定なら失敗、1 回の呼び出しで 1 レコードのみ、UPDATE/DELETE/任意 SQL 禁止。hook で「誰が sqlite3 を叩いたか」を当てにしない。
- **第 3 優先**: audit を「存在チェック」から「経路・証跡チェック」に強化する。
  - workflow.db の品質監査: 異常件数、created_at/ts_utc 形式、command が許可一覧にあるか、summary が空でないか。
  - 成果物と証跡の対応: 03/04 と command 実行ログの有無、verify-and-close 痕跡。
- **第 4 優先**: orchestrator の権限を本当に狭める。理想形は Read のみ。無理でも「ファイル更新は worker 経由のみ」を運用と監査でセットにする。ROLE 付き Task を必須フォーマット化し監査対象にする。

---

## 何を直すべきか（優先順位）

1. **PreToolUse.sh を「案内」から「拒否」へ変える**（いちばん価値が高い）。拒否条件に当たる場合は **exit 1** にする。そのためには、フックが受け取れるメタ情報の整理・メイン/サブ/書記の識別方法・対象ツールと対象パスの取得方法を先に固める必要がある。
2. **PostToolUse.sh に実ファイル検証を入れる**。作成/更新された memo のパスを受け取り、YYYYMMDD_HHMMSS_ プレフィックスを検証し、違反時は **exit 1** にする。
3. **audit.sh は維持しつつ、hook の代替と考えない**。役割はあくまで**最後の砦**（事後監査）。メインがその場で違反できない状態を作るには Pre/Post 側の拒否が必要。

## PreToolUse を案内から拒否に変えるための前提設計

- **フックが受け取れるメタ情報の整理**: ツール名（Write / Edit / Shell 等）、対象パス（編集対象ファイルや作業ディレクトリ）、コマンド文字列（Shell 実行時）。現状は Claude Code / Cursor の hook 仕様でこれらが渡されないため、ブロック不可。プラットフォームの公式ドキュメントで渡される引数・環境変数を確認し、利用可能なメタ情報を一覧化する必要がある。
- **メイン / サブ / 書記の識別方法**: 呼び出し元が orchestrator（メイン）か worker/scribe（サブ）かをフック側で判別する方法。例: 環境変数で ROLE や SESSION_TYPE が渡されるか、プロセスツリーや呼び出しコンテキストで判定できるか。現状は判別できないため、書記以外の sqlite3 禁止もブロックできていない。
- **対象ツールと対象パスの取得方法**: 上記メタ情報が渡される場合、拒否条件の例。「Write/Edit かつ対象パスが .workflow 配下の 00/01/02/03/04 または memo なら exit 1」「Shell かつコマンドが npm test / pytest / git 等の実作業系ならメインの場合は exit 1」等。本ドキュメントの「B. プラットフォームがメタ情報を渡す場合の reject 実装」の疑似コードを参照し、前提が満たされた場合の拒否ロジックを補足する。
- **次にやるべきこと**: **PreToolUse.sh を"案内"から"拒否"に変えるための前提設計レビュー**（プラットフォームの hook インターフェース調査と、受け取り可能なメタ情報に基づく拒否条件の定義）。

---

## PostToolUse に実ファイル検証を入れるための前提

作成/更新された memo のパスをフックが受け取れるか。受け取れる場合、プレフィックス形式（YYYYMMDD_HHMMSS_）を検証し違反時は **exit 1** とする。受け取れない場合は現状と同様に audit.sh に委ねる。
