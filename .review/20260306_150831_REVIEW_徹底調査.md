# AGENTS-spec 徹底調査レビュー

**本ドキュメントは 2026-03-06 時点の監査記録であり、現行仕様ではない。**

**作成日**: 2026年3月6日  
**目的**: AGENTS-spec 全体が適切であり、AI が遵守できる設計になっているかを、サブエージェントとの議論・文献・公式情報を参照しつつ検証する。

---

## 1. 調査方法

- **本流ドキュメントの精読**: CORE, LOAD_POLICY, WORKFLOW, RULES, CONCEPTS, AGENTS.md, delegate_to_sub, SUBAGENT, EXECUTION_CONTRACT, workers/README, 書記役とログ委譲, capabilities/POLICY 等を対象に、一貫性・遵守可能性・認知負荷・検証可能性を調査した。
- **サブエージェントによる分担レビュー**: (1) 内部一貫性・MUST/MUST NOT の明確さ・実行前契約の現実性・優先順位の明確さ、(2) 認知負荷・条件分岐の複雑さ・指示の順序・検証可能性 の観点で並行して評価した。
- **参照した公式・知見**:
  - OpenAI Prompt engineering: instructions の優先度（`instructions` パラメータが input より優先）、メッセージロールによる「differing levels of authority」、Chain of Command。明示的な指示が一貫した振る舞いにつながる旨。
  - Instruction following の一般的なベストプラクティス: 重要な制約を先に置く、番号付き手順、例外の明示、検証可能な完了条件の明文化。

## 2. 総合評価：AI が遵守できるか

**結論**: **設計は「守らせる」意図に沿ってよく整理されているが、技術的強制がなく「読了」「条件に応じて読む」の履行はモデルの自己遵守に依存する。用語の統一・「読了」の定義・例外の一元化・条件分岐のチェックリスト化を行うと、遵守可能性がさらに高まる。**

| 観点 | 評価 | 備考 |
|------|------|------|
| **一貫性** | ◎ 良い | 4ファイル読了・委譲一意・ログ先・テンプレート・5行前提・role 対応が他文書と一致。「原則」の解釈ゆれのみ要修正。 |
| **MUST/MUST NOT** | ○ おおむね良い | 禁止・確認義務は明文化。必須/強制/必ずの混在、「原則」と必須の混在あり。用語定義の統一を推奨。 |
| **実行前契約** | △ 要強化 | 契約内容は明確だが「読了」未定義・技術的強制なし・委譲による迂回・確認省略でゲート外せる・サブの適用範囲曖昧。 |
| **優先順位** | ○ 良い | CORE 4.5 で 1 種類の衝突を一意に解決。他パターンは LOAD_POLICY のソース優先で補完可能。対象範囲の明記を推奨。 |
| **認知負荷** | ○ 許容範囲 | 必須読了 4 ファイル・約 390 行。CORE §1 のサブセクション数と LOAD_POLICY §2 の条件分岐がやや多い。 |
| **条件分岐** | △ 要整理 | 「条件に応じて読む」のトリガーが多く、書記使用/暫定・フェーズ→worker が複数ファイルに分散。チェックリスト化で取りこぼしを削減可能。 |
| **指示の構造** | ◎ 良い | 実行前契約が冒頭、番号付きリスト・完了条件・チェックリストが一貫。制約の前置は満たしている。 |
| **検証可能性** | ○ 良い | 証跡・workflow.db・テンプレート照合で検証可能。「読了」「条件に応じて読んだか」は証跡では直接検証できない。 |

## 3. 良い点（維持すべき設計）

- **実行前契約の明文化**: 4 ファイル読了まで行動禁止・着手時は冒頭で確認、が CORE・LOAD_POLICY・AGENTS で一致しており、人間がチェックする基準として明確である。
- **委譲の一意入口**: delegate_to_sub のみ・直接呼び出し禁止が一貫しており、トレーサビリティとコンテキスト注入が揃う。
- **ログの保存先**: workflow.db のみ・書記一任が CORE/RULES/WORKFLOW/capabilities で一致。原則と暫定の区別も明示されている。
- **確認義務の 3 点**: 成果物照合・テスト実施証跡・ログ記録が RULES と WORKFLOW のチェックリストで固定され、次に進む前のゲートになっている。
- **優先順位の固定**: LOAD_POLICY §0 のソース優先（AGENTS > CORE > …）、CORE 4.5 の出力方針（証跡・ログ詳細優先）、サブの Task Contract 最優先が矛盾なく書かれている。
- **目的・制約・完了条件の 3 点セット**: CORE の各サブセクションで繰り返し使われており、LLM が「何を満たせばよいか」を把握しやすい。
- **テンプレート・フォーマット強制**: テンプレート存在時は必ずコピーして使用・一から作成禁止が RULES/WORKFLOW/CORE で一貫している。

## 4. 問題点・リスクと推奨修正

### 4.1 実行前契約の「読了」が未定義（高）

- **問題**: 「読了するまで行ってはならない」の「読了」が、(a) コンテキストに含まれたこと (b) read ツールで取得したこと (c) 解釈・承認したこと のいずれを指すか書かれていない。プラットフォームは「4 回 read の後にのみ write/delegate 可」を保証していないため、**自己遵守に依存**している。
- **推奨**: CORE §0 に「読了: 当該ファイルの内容が本ターンまたは直前のターンでコンテキストに含まれ、エージェントが参照可能な状態になったことを指す」などの一文を追加する。実行前契約が**メインにのみ**義務か**サブにも**義務かを明示し、サブに義務がある場合は SUBAGENT の注入に 4 ファイルまたは要約を含めることを検討する。

### 4.2 「原則」と必須の解釈ゆれ（中）

- **問題**: CORE §3 の「**原則は** workflow.db への保存を**強制**する」は、「原則」を「できるだけ」と読む余地がある。本則／暫定の意図は直後の文で分かるが、MUST 文だけ抜くと曖昧。
- **推奨**: 「**本則**: ログは workflow.db への保存を**必須**とする。**例外**: 書記未使用時のみ、以下に従い memo に暫定記録する。」のように、本則／例外と「必須」を分けて記載する。

### 4.3 MUST / 必須 / 強制 / 必ずの用語混在（中）

- **問題**: capabilities/POLICY は MUST / MUST NOT を明示しているが、CORE・RULES・WORKFLOW では「必ず」「必須」「強制」が混在し、RFC 2119 的な MUST/SHOULD の区別がない。「原則」が MUST か SHOULD か一読で分かりにくい箇所がある。
- **推奨**: CONCEPTS または CORE 冒頭で「**必須（MUST）**／**禁止（MUST NOT）**／**推奨（SHOULD）**」の用語を 1 文で定義し、本流で統一する。確認文の「短く」「1 行でよい」は「MUST: 応答冒頭で 1 行以内の確認文を記載する」のように必須の範囲を一文で書く。

### 4.4 条件に応じて読むもののトリガーが多い（中）

- **問題**: LOAD_POLICY §2 に「フェーズ進行」「フェーズ完了時」「委譲仕様」「記憶」「誰が何を書けるか」「ログ」「監査時」「レビュー時」などトリガーが多く、「今どの条件が成立しているか」の判定を LLM に委ねている。該当ファイルの読み忘れや、監査時に RULES だけ読んで WORKFLOW の監査観点を読まないリスクがある。
- **推奨**: 「条件に応じて読む」を**フェーズ/イベント（委譲前・フェーズ完了時・監査時・レビュー時など）ごとの表**にし、「このときはこのファイルを読む」を 1 行で示す。トリガーを 5〜7 個にまとめ、各トリガーに読むファイルのリストを 1 対 1 で対応させる。

### 4.5 書記未使用時の例外が複数ファイルに分散（中）

- **問題**: 原則＝workflow.db・書記必須、例外＝書記未使用時は memo 暫定、が CORE §3、RULES、WORKFLOW、書記役とログ委譲、delegate_to_sub などに分散している。どちらのモードで動くかを毎回正しく選ぶ必要があり、取り違えのリスクがある。
- **推奨**: **書記未使用時にすべきこと**（memo のパス、CONTRACT 準拠の項目、移行前提）を**書記役とログ委譲の 1 セクション**にまとめ、CORE / WORKFLOW / RULES では「原則＝書記＋workflow.db。例外は [書記役とログ委譲 §○] の暫定手順に従う」と 1 行で参照する。

### 4.6 CORE 4.5 の対象衝突が 1 種類のみ（低）

- **問題**: 明示されているのは「監査・証跡・ログの詳細 vs 会話の簡潔（SILENT MODE）」のみ。テンプレート強制 vs 納期、4ファイル読了 vs ユーザー「今すぐやって」など、他パターンは優先順位が 4.5 に書かれていない。「詳細優先」が会話のみか成果物・証跡の粒度までか、やや曖昧。
- **推奨**: CORE §4.5 に「本節が対象とする衝突は、**出力の簡潔化（SILENT MODE）と、監査・証跡・ログに必要な詳細さ・完全性との衝突に限る**」と明記する。「上記以外のルール同士の衝突は、LOAD_POLICY §0 のソース優先順位に従い、それでも決まらない場合は CORE の該当セクションの MUST / MUST NOT を優先する」を追加する。「監査・証跡・ログの詳細優先」が**成果物・証跡の必須項目・粒度**にも及ぶことを 4.5 または WORKFLOW の監査観点で一言書く。

### 4.7 確認省略でゲートが外せる（低）

- **問題**: ユーザーが「規約は読んだ前提で」と言えば確認文は省略可のため、ユーザー発言一つで実行前契約の確認ゲートを外せる。監査・オンボーディングで省略が多用されると、読了の検証が難しくなる。
- **推奨**: 「監査・証跡の観点から、初回セッションまたは規約改訂後の初回では確認文の省略を推奨しない」などの注記を CORE §0 または AGENTS に追加する。

### 4.8 委譲内容の証跡が規約上明示されていない（低）

- **問題**: 委譲時の Task/Constraints/OutputSpec が 5 行以内か、後から検証するには委譲ペイロードがどこに残るかが必要。会話ログのみだと検証しづらい場合がある。
- **推奨**: delegate_to_sub で委譲するたびに、**Task/Constraints/OutputSpec の要約を memo に 1 行で追記する**ことを推奨（または必須）にする。

## 5. 文献・公式情報に照らした評価

- **指示の優先度・権威の階層**: OpenAI の prompt engineering では、`instructions` パラメータや developer ロールで「differing levels of authority」を与え、input より指示を優先させる設計が推奨されている。AGENTS-spec では **LOAD_POLICY §0 のソース優先順位（AGENTS > CORE > …）** と **CORE 4.5 の出力方針** で階層が固定されており、同種の考え方と整合している。
- **制約の前置・重要度の明確化**: 重要な制約を先に置くという一般的なベストプラクティスは、**実行前契約が CORE §0 と AGENTS 冒頭にある**ことで満たされている。必須読了リストも番号付きで明確である。
- **具体的な手順の番号付き**: 必須読了 1〜4、CORE §2 の「必ず守る運用」1〜3、RULES 確認義務 1〜3、WORKFLOW の確認チェック、delegate_to_sub の手順 1〜7、SUBAGENT の注入順序など、実行に直結する手順は番号付きまたは表で固定されており、instruction following の観点で適切である。
- **検証可能性**: 証跡・workflow.db・テンプレート照合により、多くのルールは事後検証可能である。「読了」や「条件に応じて読んだか」は内部状態のため直接は検証できないが、確認文の発話とその後の行動の一貫性で間接的に確認する設計になっている。

| 観点 | 内容 | 推奨 |
|------|------|------|
| **暫定記録のファイルの一意性** | 同一 issue で複数セッション・複数日の場合、1 ファイルに追記するか別ファイルにするかが未規定。 | CONTRACT §5 に「同一 issue では既存の `YYYYMMDD_HHMMSS_実行ログ.md` が存在する場合はそのファイルに追記する」などを追加。 |
| **記録確認の方法** | 「書記が workflow.db に記録したことが確認できる」が、書記の出力のみでよいか DB 参照確認が必要か未規定。 | CORE または RULES に「可能であれば workflow.db の当該 issue_id の直近 INSERT を確認する」などを追記。 |
| **テンプレート「対応」の定義** | 「同名（または対応）テンプレート」の「対応」の定義がない。 | WORKFLOW §2 で「対応＝当該成果物のベース名をファイル名に含む templates/ 内のファイル。複数ある場合は同名を優先」などを明記。 |
| **同一ファイル内の優先順位** | ルール同士の衝突は CORE §4.5 だが、同一ファイル内の節どうしの矛盾時の扱いが未規定。 | CORE §4.5 に「同一ファイル内の節どうしを含む」または「節番号の大きい方を優先する」などを追記。 |
| **ログとそれ以外の memo の区別** | ログ以外の memo（作業メモ等）の扱いが CONTRACT にない。ログと混同する余地がある。 | CONTRACT または RULES に「ログとして扱う記録は workflow.db または CONTRACT §5 形式の memo のみ。それ以外の memo はトレーサビリティの証跡に使わない」などを追記。 |

### 7.5 文献・ベストプラクティスとの対応（再評価）

- **単一の正本（SSoT）**: ログは CONTRACT が唯一の正本と明言され、規約上「その時々で書き方がブレる」問題は解消されている。ワークフロー・DoD は WORKFLOW、委譲の形は EXECUTION_CONTRACT に集約されている。
- **指示の優先度**: LOAD_POLICY §0 のソース優先・CORE §4.5 の衝突時の方針は維持されている。同一ファイル内の優先順位のみ補足を推奨。
- **検証可能な完了条件**: 確認義務 3 点・完了条件の明文化は維持。DoD の検証を「誰が・どの操作で」完了とするかの具体化でさらに強化可能。

## 8. まとめ

AGENTS-spec は、**実行前契約・委譲の一意性・ログの workflow.db 強制・確認義務 3 点・テンプレート強制・優先順位の固定**など、AI に規約を守らせるための設計がよく揃っている。サブエージェントによる分担レビューと、OpenAI の prompt engineering 等の知見に照らしても、**指示の前置・番号付き手順・検証可能な証跡**の点で適切である。

**追調査（§7）で確認したとおり、ログ保存は CONTRACT を唯一の正本にしたことで規約上のブレは解消され、書記未使用時の例外も CONTRACT §5 参照に集約済みである。** また、スキーマの `target_artifact` と `summary` を NOT NULL に揃え、CONTRACT §2 と DDL の一致をとった。

一方で、**「読了」の未定義**と**技術的強制の欠如**は未解消であり、**「原則」の解釈ゆれ**や**MUST/必須/強制の用語混在**も残っている。さらに、暫定記録のファイル一意性・記録確認の具体的方法・テンプレート「対応」の定義・ログとそれ以外の memo の区別など、**新たに判明したリスク**（§7.4）への対応を行うと、AI がより確実に遵守できる設計に近づく。
