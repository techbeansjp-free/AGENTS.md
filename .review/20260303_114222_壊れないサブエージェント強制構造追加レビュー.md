## 2. 規約・ドキュメント間の整合性

### 2.1 CORE との整合

- ✅ CORE の「2. 委譲」で delegate_to_sub を唯一の入口とし、SUBAGENT_MINIMUM の最小読込保証を要求している。delegate_to_sub および SUBAGENT_PACK の注入順序（EXECUTION_CONTRACT を 3 番目に含む）と一致する。
- ✅ CORE の「3. トレーサビリティ」で書記へのログ委譲を必須とし、書記以外の logs 直書きを禁止している。scribe/CONTRACT および enforcement の「書記のみ書く」と矛盾しない。
- ✅ CORE の参照に SUBAGENT_MINIMUM・SUBAGENT_PACK・delegate_to_sub・書記役とログ委譲が含まれており、CONTRACT は書記役とログ委譲や ledger 経由で参照される構成で一貫している。

### 2.2 workers/README との対応

- ✅ workers の 6 人格（要件BDDリード・総合レビューリード・実装者・テスト者・監査者・書記）と、delegate_to_sub の固定 JSON の `role`（implementer | reviewer | tester | auditor | scribe）は **5 ロール** に整理されている。
- **改善提案（低）**: 「壊れない強制構造」では 5 ロールに正規化し、要件BDDリード・総合レビューリードは LOAD_POLICY や運用で implementer/reviewer 等にマッピングする前提である旨を、delegate_to_sub または LOAD_POLICY に 1 行追記すると、採用側の解釈が揃いやすい（任意）。

### 2.3 書記役とログ委譲・CONTRACT・ledger の関係

- ✅ 書記役とログ委譲が書記の責務・テンプレ（scribe_claude / scribe_cursor）を参照し、CONTRACT は「親→書記で渡す 1 件分のスキーマ」として保存先・ファイル名・フロントマターを固定している。ledger（SQLite）は CONTRACT と併用可能な別方式として記載されており、CONTRACT の「.workflow/**/logs/」のみ固定と矛盾しない。
- ✅ capabilities/POLICY の「書記のみ logs/ に書く」と enforcement の「logs/ 以外拒否」が一致している。

### 2.4 参照パス

- ✅ delegate_to_sub からの `../../boot/`・`../../scribe/`・`../../rules/` は `.agents/skills/agent/` 起点で正しい。
- ✅ enforcement/cursor/agents からの `../../../boot/`・`../../../scribe/`・`../../../skills/` は `.agents/enforcement/cursor/agents/` 起点で正しい。
- ✅ サブエージェント抜かし防止の subagent-guard.yml へのリンクは `.agents/rules/` 起点で `../../.workflow/...` であり、AGENTS-spec ルートの .workflow を正しく指している。

## 3. テンプレート・CI の妥当性

### 3.1 subagent-guard.sh

- ✅ logs/ 以外で `^issue_id:` を含む .md を検知して exit 1 する。意図どおり。
- ✅ logs/ 配下の .md で issue_id, agent_id, action_type, timestamp, target_artifact, summary の必須キーを grep で検査している。CONTRACT の必須キーと一致。
- ✅ `[[ "$f" != .workflow/*/logs/* ]]` は bash のパターンマッチで、.workflow/ 以下かつ logs/ 以外の .md を正しく「ログ外」として扱える。
- **軽微**: `git diff --name-only --diff-filter=AM` は新規追加・修正のみ。リネームや削除は含まないが、監査目的としては十分。

### 3.2 subagent-guard.yml

- ✅ テンプレート出典・採用先での配置の注記がある。`.workflow/templates/github/scripts/` と `.github/scripts/` の両方に対応する条件分岐で、採用先の構成の違いを吸収している。
- ✅ checkout@v4 使用で問題なし。

### 3.3 pretooluse_write_guard.json

- ✅ Write の allow が `.workflow/**/logs/**` のみ、deny が `**`。Edit/Bash は deny `**`。書記以外の書き込みを物理的に拒否する設計と一致。
- **注意**: Claude Code の PreToolUse が実際にこの JSON スキーマ（allow/deny の key や path の解釈）をそのまま受け付けるかは、採用先の Claude Code ドキュメントで要確認。README に「採用先の Claude Code ドキュメントで要確認」とあるため、運用で補完できる。
