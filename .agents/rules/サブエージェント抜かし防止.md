# サブエージェント抜かし防止（工程の固定ゲート・提出物・DoD）

> **AI 向け**: サブエージェント・メインエージェントが「作業を抜かす」のを防ぐため、**工程を固定ゲート化**し、**提出物（証跡）** と **完了の定義（DoD）** を義務化する。本ファイルは [`実行ルール.md`](./実行ルール.md) および [`AGENTS.md`](../../AGENTS.md) から参照される。

**サブエージェント運用（MVP）**: メインは [boot/CORE.md](../boot/CORE.md) と [boot/LOAD_POLICY.md](../boot/LOAD_POLICY.md) に従い、フェーズごとに workers に Task/Constraints/OutputSpec で委譲する。証跡に加え、**トレーサビリティのため各サブ実行後に書記へログを委譲する**（[書記役とログ委譲.md](../scribe/書記役とログ委譲.md)）。

---

## 1. よくある原因（抜かす理由）

- **ゴールだけ見えていて、工程が固定されていない**  
  → 設計・検証・差分確認・テストなどが「任意」扱いになり飛ばされる。
- **完了条件（DoD）が曖昧**  
  → 「できた」と思って終了する（テスト未実施、エッジケース未確認など）。
- **チェックが自己申告**  
  → 「やったつもり」で通る（実ファイル・ログ・差分の提示がない）。
- **大きすぎるタスクを一撃でやらせている**  
  → 途中を省略してでも最後まで到達しようとする。

---

## 2. 抜かさない運用の型

### 2.1 工程を「固定のゲート」にする

フェーズを**飛ばす選択肢を無くす**。AGENTS の順序を毎回強制する。

- 00_システム理解（既存プロジェクト時のみ）→ 00_要求定義 → 01_要件定義 → 02_設計 → 03_実装計画 → **4.5 ドキュメント徹底レビュー（必須）** → （必要なら 90_issues）→ 実装 → 04_review
- 前フェーズの**完了条件を満たすまで次に進まない**。完了条件は次の両方を満たすこととする：
  - **(1) 提出物が揃っていること**
  - **(2) メインが [監査者用工程フロー](./監査者用工程フロー.md)・[監査者用チェックリスト](./監査者用チェックリスト.md) の該当フェーズの確認を証跡ベースで実施し、満たしていると判断したこと**

- **4.5 は省略禁止**。指摘ゼロ＋最低3回実施まで実装に進まない。詳細は [ワークフローとフェーズ定義.md](./ワークフローとフェーズ定義.md) の「フェーズ定義」「完了条件」「4.5 ドキュメント作成後の徹底レビューワークフロー」を参照。

### 2.2 各フェーズに提出物を義務化（証跡ベース）

**成果物の共通定義（サブあり・なし共通）**: 本提出物表は、実行形態（メインのみ／メイン＋サブ）に依存せず、同一の必須成果物とする。00_要求定義〜04_review、memo（各フェーズで要求されるもの）、提出物一覧は、サブエージェントを使用しない場合も同じ一覧を満たすこと。

提出物が揃わない限り**完了扱いにしない**。根拠は**実ファイル名・diff 要約・実行コマンド・結果**で示す。

| フェーズ | 提出物（必須） |
|---------|----------------|
| 00_要求定義 | 不明点リスト（あれば）、DoD（完了条件）の明文化、`00_要求定義.md` |
| 01_要件定義 | ユーザーストーリー・受け入れ基準・BDD Feature/Scenario、`01_要件定義.md` |
| 02_設計 | 影響ファイル一覧（想定）、実装方針・リスク・想定外ケース、`02_設計.md` |
| 03_実装計画 | タスク一覧・テスト観点・優先度、`03_実装計画.md` |
| **4.5 ドキュメント徹底レビュー** | `memo/YYYYMMDD_HHMMSS_ドキュメント徹底レビュー結果_第N回.md`（最低3回）、指摘一覧・対応状況・前回リンク、指摘ゼロの確認 |
| 実装 | **テストコード**（03 のテスト観点に沿い、**先に**実装）・プロダクションコード・変更ファイル一覧（テスト/本番の区別）・diff 要約・実行コマンド・テスト結果（または手動確認手順） |
| 04_review | 指摘一覧・対応状況、変更点サマリ・残課題、`04_review.md` |

- **証跡の主体**: エージェントが直接出せる証跡は**実ファイル名・diff 要約・実行コマンド・手順**まで。**テスト実行結果**は人間または CI が実行した場合の記載とする。実行ルール上、エージェントは「実行した」と書かず、実行コマンドと期待結果を提示する。
- **設計**: 影響範囲・想定外ケースを簡潔に記載する。
- **4.5 ドキュメント徹底レビュー**: レビュールールの観点で 00〜03 をレビューし、結果を `memo/YYYYMMDD_HHMMSS_ドキュメント徹底レビュー結果_第N回.md` に保存。指摘対応後に再レビューし、**最低3回**実施した証跡（ファイル名・回数・前回リンク）を残す。実施内容の詳細は [ワークフローとフェーズ定義.md](./ワークフローとフェーズ定義.md) を参照。
- **実装**: **テストファースト**を守る。03_実装計画のテスト観点に沿って**テストコードを先に**実装し、その後にプロダクションコードを実装する。提出物には**追加・変更したテストファイル一覧**と本番コードの変更ファイル一覧を区別して示し、diff 要約・実行コマンド・期待結果（または手動確認手順）を提示する。詳細は [`テストガイドライン.md`](./テストガイドライン.md) を参照。

### 2.3 完了の定義（DoD）をテンプレで固定

開発タスクの DoD 例（採用先で `.agents-project/` に上書き可能）:

- lint / format / typecheck が通る（または実行コマンドと期待結果が記載されている）。
- **テストコード**が 03_実装計画のテスト観点を満たし、主要ケース＋異常系をカバーしている（または手動確認手順が書かれている）。[`テストガイドライン.md`](./テストガイドライン.md) 参照。
- 影響範囲が説明されている（**テストファイル・本番コード**の変更ファイル一覧または 02_設計 との対応）。
- 差分（diff）の要点が説明されている（実装フェーズ完了時）。

### 2.4 タスクを小さく切る（抜かす余地を減らす）

「1 タスク = 1 成果物」に寄せる。例: 「実装まで」と「テスト追加」を別タスクに分ける。大きな issue は `90_issues` で分割する。詳細は [ワークフローとフェーズ定義.md](./ワークフローとフェーズ定義.md) の「Issue 作成」「タスク分解の判断」を参照。

## 3. 指示文ひな形（コピペ用）

サブエージェントやメインに「抜かさない」よう指示するときの例。

```text
以下の Phase を順番に実施。Phase の省略は禁止。
各 Phase の最後に「提出物」を必ず列挙し、根拠（差分/ログ/ファイル名）を示すこと。

Phase1 要件確認：不明点/前提/完了条件(DoD)を明文化
提出物：不明点リスト、DoD、00_要求定義.md

Phase2 設計：影響範囲、実装方針、代替案、リスク
提出物：影響ファイル一覧、方針、リスク、01_要件定義.md、02_設計.md

Phase3 実装計画：タスク・テスト観点・優先度を 03 に記載
提出物：03_実装計画.md

Phase3.5 ドキュメント徹底レビュー：00〜03 の齟齬・矛盾・漏れを洗い出し、指摘ゼロ＋最低3回まで実施
提出物：memo/YYYYMMDD_HHMMSS_ドキュメント徹底レビュー結果_第N回.md、指摘一覧・対応済み、前回結果へのリンク

Phase4 実装：テストファースト（03 のテスト観点に沿ったテストコードを先に実装）→ プロダクションコード → 検証
提出物：テストコード（追加/変更したテストファイル一覧）、本番コード（変更ファイル一覧）、diff 要点、実行コマンド、結果（または手順）

Phase5 仕上げ：変更点サマリ、残課題
提出物：サマリ、残課題、04_review.md
```

※ **AGENTS 利用時**: Phase1=00、Phase2=**01＋02**、**Phase3=03**（実装計画のみ。実装とは別フェーズ）、**Phase3.5=4.5 ドキュメント徹底レビュー**（省略禁止。03 のあと実施）、Phase4=実装＋検証、Phase5=04。03 → 4.5 → 実装 の順を守る。

## 4. サブエージェント定義での参照（推奨）

サブエージェント（agents-docs, agents-implement, agents-review 等、または MVP の workers/01〜06）の定義内に、**提出物・証跡のルールは本ファイルを参照する**旨を 1 行入れることを推奨する。これにより「抜かさない」運用がサブエージェントに伝わる。例: 「各 Phase 終了時に提出物を列挙し根拠を示す。詳細は .agents/rules/サブエージェント抜かし防止.md を参照。」  
**MVP 運用時**: 委譲先の対応は [boot/LOAD_POLICY.md](../boot/LOAD_POLICY.md) の「フェーズ→worker」と [workers/README.md](../workers/README.md) の 6 人格（01〜06）を参照する。

## 4.5 サブ呼び出しの入口一本化（直呼び禁止）

- **運用強制**: サブエージェントは**必ず** [skills/agent/delegate_to_sub.md](../skills/agent/delegate_to_sub.md) を経由する。**直接呼び出しは禁止**。**違反はレビューで即修正対象**。メインは必ず delegate_to_sub の手順に従い、[SUBAGENT_PACK](../boot/SUBAGENT_PACK.md) の注入順序でサブにコンテキストを渡す。
- **ログは書記のみ**: 書記以外が `workflow.db` に直接書かない。書記の保存先は **workflow.db のみ**。`.workflow/**/logs/` は使用禁止・廃止。書記サブにだけログ記録を委譲する（[書記役とログ委譲](../scribe/書記役とログ委譲.md)、[scribe/CONTRACT](../scribe/CONTRACT.md)）。
- **CI で検知**: 「直呼びっぽい文言」や「書記以外のログ直書き」を検知して失敗させると、運用上壊れにくい。 [.workflow/templates/github/workflows/subagent-guard.yml](../../.workflow/templates/github/workflows/subagent-guard.yml) および [enforcement/cursor/](../enforcement/cursor/README.md) を参照。

## 4.6 進行役が次に進む前のチェックリスト

各フェーズ完了前に、進行役（メイン）は以下を確認する。

- [ ] 当該フェーズの**提出物が揃っているか**（[提出物表](#22-各フェーズに提出物を義務化証跡ベース) に準拠）
- [ ] **トレーサビリティが満たされているか**（サブ運用時は各サブ実行後に書記へログ委譲済み。メインのみの場合は [書記役とログ委譲](../scribe/書記役とログ委譲.md) に従い memo の実行ログに CONTRACT 同様の項目で記録済みのいずれかで足りる）
- [ ] **次フェーズの委譲先**を把握しているか（[LOAD_POLICY](../boot/LOAD_POLICY.md) のフェーズ→worker）
- [ ] **依頼内容（Task/Constraints/OutputSpec）**を組み立てたか
- [ ] **監査確認済み**か（提出物＋該当フェーズの必須確認を証跡ベースで満たしたか。詳細は [監査者用チェックリスト](./監査者用チェックリスト.md)・[監査者用工程フロー](./監査者用工程フロー.md)）

詳細な手順は [進行役手順](./進行役手順.md) を参照する。
