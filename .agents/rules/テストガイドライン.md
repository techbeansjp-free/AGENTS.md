# テストガイドライン - テスト作成ガイドライン

> このファイルは、AI エージェントがテストを作成・レビューする際に遵守すべき「テスト技法」「観点」「レベル」を整理したガイドラインです。  
> **AI エージェント向け**: このガイドラインは [`実行ルール.md`](./実行ルール.md) の実装フェーズから参照されます。  
> 詳細な思想・背景は [`AGENTS.md`](../../AGENTS.md) を参照し、ここでは **テストに特化した実践的な指針** を定義します。  
> **サブエージェント運用時**: テストタスクを委譲された worker（テスト者等）が本ガイドラインを参照する。

**AI向け 自律時の判断**: テスト方針で迷った場合は、直下のクイックリファレンスの優先度（正常系最小・異常系・境界値重点、バリデーション網羅、エラーレスポンス形式必須、ブラックボックス優先、E2E は data-testid）に従う。不足があれば本ファイルの該当セクションを参照する。

## クイックリファレンス

### テスト作成の基本方針

1. **仕様ベース（BDD）で書く**: 受け入れ条件を Given-When-Then で表現
2. **リスクベースで優先度を決める**: クリティカルな機能は厚くテスト
3. **テストピラミッドを意識**: 単体テスト多め、結合/API テストそこそこ、E2E 少なめ
4. **運用保守に耐えうるテスト**: 実装の詳細に依存せず、値の変更に強いテスト設計
5. **正常系は動いて当たり前**: 異常系・境界値に重点を置く。正常系は最小限で OK
6. **バリデーションは網羅的に**: バリデーション系のテストは漏れなく実施
7. **エラーレスポンス形式の検証は必須**: すべてのエラーレスポンス（400, 401, 403, 404, 422, 500等）の形式を検証
8. **ブラックボックステストを優先**: APIの入力と出力のみを検証し、内部実装に依存しない
9. **ホワイトボックステストで補完**: エラーハンドラーや例外処理の内部実装を検証
10. **E2Eテストでは`data-testid`を使用**: UIの変更に影響されにくい、安定したテストを書く

### テスト観点のチェックリスト

- **入力・データ**: 正常系、境界値、異常系、組み合わせ、ロケール/文字種
- **状態・フロー**: 状態遷移、画面/ステップフロー、中断・キャンセル
- **時間・並行・順序**: 日付境界、並行実行、順序依存
- **エラー/障害系**: 外部 API、DB、ネットワーク、エラーハンドリング
- **非機能**: パフォーマンス、セキュリティ、ログ・監視

### レベル別の意識

- **単体テスト**: 多方向で攻める（値のバリエーション、条件分岐の全パス、状態変化前後）
- **結合/API テスト**: コンポーネント間の契約チェック、代表的なフロー
- **E2E/受け入れテスト**: BDD の Feature/Scenario をそのままテストに
- **回帰テスト**: バグ修正時に必ずテストを追加

## 全体方針（要約）

仕様（BDD）・リスクベース優先度・テストピラミッド（単体多め/結合そこそこ/E2E少なめ）・運用保守に耐える設計・正常系最小限・異常系・境界値重点。詳細はクイックリファレンスおよび以下各セクション参照。

---

## 正常系と異常系のテスト配分

正常系は最小限（代表1〜2件）。異常系は網羅（全エラーケース・エラーメッセージ）。境界値は重点（最小・最大・0・NULL等）。

---

## バリデーション系のテスト

網羅的に実施（必須・型・フォーマット・長さ・範囲・境界値・エラーメッセージ）。サービス層で共通化しフォーム間で一貫・一元管理。詳細はクイックリファレンスの観点チェックリストを参照。

---

## エラーレスポンス形式の検証

400/401/403/404/422/500 等の形式を検証（ステータスコード・Content-Type・ボディ構造・期待しないフィールドなし）。422 は detail 配列と各要素（type, loc, msg 等）を検証。正常系レスポンスの形式も必須。

---

## ブラックボックステストとホワイトボックステスト

ブラックボックスを優先（入力と出力のみ検証、内部実装に依存しない）。ホワイトボックスで補完（エラーハンドラー・例外処理の内部実装、カバレッジ抜け漏れ）。API/ビジネスロジック/統合はブラックボックス、例外ハンドラ・分岐網羅はホワイトボックス。

---

## 運用保守に耐えうるテスト設計

実装の詳細に依存しない（公開API・振る舞いを検証）。値の変更に強い（定数化・相対検証・データ駆動）。フレーキー回避（時間/順序/外部環境はモック）。テストコードはDRY・テスト名明確・アサーション明確。マジックナンバー・ハードコード・内部値依存は禁止。

---

## フロントエンド向けのテストガイドライン

E2E・コンポーネントテストでは **`data-testid` を優先**。UI変更に強く strict mode violation を防ぐ。命名はケバブケース・`{feature}-{element-type}-{purpose}`。フォーム・ボタン・エラーメッセージ・モーダル等に付与。アクセシビリティで一意なら getByRole 可、複数マッチしうる場合は data-testid。

---

## 観点のチェックリスト

**入力・データ**: 正常系最小限、境界値（最小/最大/0/空/NULL）、異常系網羅、組み合わせ・ロケール/文字種。  
**状態・フロー**: 状態遷移（許可/不許可）、画面フロー（ハッピーパス・中断・戻る・リロード・セッション切れ）。  
**時間・並行・順序**: 日付境界・並行実行・順序依存。  
**エラー/障害**: 外部API・DB・ネットワーク・エラーレスポンス形式（必須）。  
**非機能**: パフォーマンス・セキュリティ・ログ/監視（ざっくり可）。

---

## レベル別の意識

**単体**: 値のバリエーション・条件分岐全パス・状態変化前後。ブラックボックス寄り、値の変更に強い設計。テストファースト・BDDコメント。  
**結合/API**: 契約チェック・エラーレスポンス形式必須・代表フローのみ・外部はスタブ/モック。  
**E2E**: BDD Feature/Scenario をそのまま、重要機能に集中、data-testid で安定化。  
**回帰**: バグ修正ごとにテスト1本追加、重大インシデントは専用セットで常時実行。

---

## BDD 前提でのテストの作り方

ストーリー/ユースケース → 受け入れ条件（AC）→ Given-When-Then の Scenario → レベル割り振り（ビジネスルール=単体、コンポーネント協調=結合/API、ユーザー操作=E2E）→ 実装。ドキュメント生成時は参照パス確認必須（AGENTS.md ドキュメント原則参照）。

### テストコード内の BDD インラインコメント（必須）

**各テスト（it ブロック）内で、どの行が Given/When/Then/And に該当するかをインラインコメントで明示する。** そうしないと、前提・操作・期待結果の対応が読み手に伝わらない。

- **Given**: 前提条件（モック設定、初期データ、render の前の準備）
- **When**: 操作・実行（render、ユーザー操作、関数呼び出し）
- **Then**: 期待結果（expect によるアサーション）
- **And**: 追加の前提または期待結果（複数ある場合）

**記載例**（コメントは該当する処理の直前に付ける）:

```ts
it('リンクが正しく表示される', () => {
  // Given: AppLink に href と children を渡す前提
  const href = '/about';
  const children = '私たちについて';

  // When: レンダリングする
  render(<AppLink href={href}>{children}</AppLink>);

  // Then: アンカー要素が表示される
  const link = screen.getByRole('link', { name: children });
  expect(link).toBeInTheDocument();

  // And: href と表示テキストが渡した値と一致する
  expect(link).toHaveAttribute('href', href);
  expect(link).toHaveTextContent(children);
});
```

1 行で完結する場合は行末に `// Given: ...` 等形式でよい。複数行にまたがるブロックの場合はブロック直前に 1 回だけ付ける。

## テスト作成時の小さな指針

1テスト1振る舞い。正常系最小・異常系・境界値重点。バリデーション網羅・エラーレスポンス形式必須。ブラックボックス優先・ホワイトボックス補完。E2E は data-testid。バグ修正前にテスト追加。カバレッジは抜け漏れ検知用。テスト名明確・独立・高速・保守しやすく・実装に依存せず・値に強い。テストファースト・プロダクションレディ・フレーキー回避。

## 参考資料

### テスト技法

- **回帰テスト**: 既存機能が壊れていないことを確認
- **エッジケース**: 境界値や特殊な条件での動作確認
- **ブラックボックス**: 内部実装を知らずに入力と出力を確認
- **ホワイトボックス**: 内部実装を理解した上でテスト
- **境界値**: 最小値、最大値、0、NULL 等の境界での動作確認
- **BDD**: 振る舞い駆動開発、Given-When-Then 形式
- **テストファースト**: 実装前にテストを書く
- **単体テスト多方向**: 様々な観点からテストを書く
