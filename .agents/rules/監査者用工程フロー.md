# 監査者用工程フロー

> **AI 向け**: 監査者が「いつ・誰に・何を指示し、何が揃えば完了か」を参照する。フェーズごとの確認項目は [サブエージェント抜かし防止](./サブエージェント抜かし防止.md) の提出物表および [監査者用チェックリスト](./監査者用チェックリスト.md) と組み合わせて使う。

---

## 実装の基本パターン（アジャイル風 BDD）

本規約では**アジャイル風 BDD を実装の基本**とする。監査はこのパターンに沿った検証を行う。

- **要件**: ユーザーストーリー・受け入れ基準・**BDD Feature/Scenario（Given-When-Then）** を 01_要件定義に記載する。
- **設計・計画**: 02_設計・03_実装計画は上記 BDD と整合し、テスト観点は BDD シナリオから抽出する。
- **実装**: **テストファースト**。BDD に沿ったテスト（受け入れ・ユースケース・シナリオ）を先に実装し、その後にプロダクションコードを実装する。段階的（インクリメンタル）に進める。
- **監査の網羅**: 上記の流れ（01 の BDD → 02・03 との整合 → テストファーストでの実装 → テストの実際の実行）が証跡で満たされているかを [監査者用チェックリスト](./監査者用チェックリスト.md) で検証する。他パターン（ウォーターフォール単体等）を採用する場合は、本規約のフェーズ・提出物に合わせて証跡を整える。

---

## 前のステップ / 次のステップ

- **前**: [LOAD_POLICY](../boot/LOAD_POLICY.md) の「監査時」または [05_監査者](../workers/05_監査者.md) から本ファイルを参照する。
- **次**: 監査実施時は [監査者用チェックリスト](./監査者用チェックリスト.md) で観点ごとに検証する。**メイン（進行役）のフェーズ別の依頼・完了確認は [進行役手順](./進行役手順.md) を参照すること。**

---

## システム開発における品質担保（守るべきルール）

監査者は、次の**守るべきルール**が満たされているかを証跡ベースで検証する。満たされていない場合は GO にしない。

- **テスト**: テストは**必須**である。03_実装計画のテスト観点に沿ったテストコードを実装し、**実際に実行**する。結果は**証跡**（実行コマンド・結果ログ、または手動確認手順）で示す。「書いたが実行していない」は NG。
- **ドキュメント**: 00〜04 および該当する場合はシステム仕様書（docs/）を**作成・更新**し、**実装と常に同期**させる。変更したら必ず該当ドキュメントを更新する。詳細は [ドキュメントルール](./ドキュメントルール.md) および AGENTS の「ドキュメントと実装を常に同期させる」に従う。
- **実際に実行すること**: テスト・フォーマット・リント・型チェックは**自己申告では完了としない**。**実行コマンドと結果**（または手動確認手順）を証跡として示す。監査者は証跡がない場合は「未実施」とみなし、該当役割に実行・再実行を指示する。
- **各工程で必ずログを残す**: **各フェーズ・各サブ実行後に、メインは書記へログ項目を委譲し、ログを残す**。トレーサビリティのため必須。記録は書記のみ（[書記役とログ委譲](../scribe/書記役とログ委譲.md)、[CORE](../boot/CORE.md)）。証跡は **workflow.db の記録のみ**（`.workflow/**/logs/` は廃止・使用禁止）。監査時は「各工程に対応するログが存在するか」および**ログ保存ポリシー（SQLite 統一）の遵守**を確認する。
- **.workflow 配下の memo 等の成果物ファイル名**: **YYYYMMDD_HHMMSS_** 形式とすること。日時はファイル作成時にシステムから取得し、日本標準時（JST）を用いる（手入力・推測・記憶は禁止）。日付のみ（YYYYMMDD_）やプレフィックスなしは禁止。監査時に遵守を確認する。

詳細なチェック項目は [監査者用チェックリスト](./監査者用チェックリスト.md) の観点ごとの項目に従う。**ドリフト点検**を行う際は、[AgentDrift対策](./AgentDrift対策.md) および [監査者用チェックリスト](./監査者用チェックリスト.md) のドリフト項目を参照する。**監査時の workflow.db 確認手順**は [監査者用チェックリスト](./監査者用チェックリスト.md) の「監査時の workflow.db 確認手順」セクションを参照する。

## 監査確認済みの定義

**「監査確認済み」**とは、次の両方を満たした状態を指す。(1) **提出物が揃っていること** (2) **該当フェーズの必須確認項目について証跡で確認し、メインが不足なしと判断したこと**。証跡とは自己申告でなく第三者検証可能なもの（実ファイル・workflow.db ログ・実行コマンドと結果等）。証跡の残し方は、毎フェーズの memo/ログ、または 04_review 委譲時の観点別確認結果に記載する。

## 各フェーズで必ず確認する項目（飛ばしたら NG）

| フェーズ | 必須確認（省略不可） |
|----------|----------------------|
| 00_システム理解 | 00_システム理解.md の存在・内容 |
| 00_要求定義 | 00_要求定義.md、DoD の明文化 |
| 01_要件定義 | 01_要件定義.md、ストーリー・BDD Feature/Scenario |
| 02_設計 | 02_設計.md、影響範囲・テスト戦略 |
| 03_実装計画 | 03_実装計画.md、タスク・テスト観点 |
| 4.5 | 指摘ゼロ＋最低3回のレビュー証跡、memo のファイル名 YYYYMMDD_HHMMSS_ |
| 実装 | テストコード（先に）・本番コード・実行結果、docs/ 更新時は更新履歴・レビュー |
| 04_review | 04_review.md、観点ごとの確認結果 |

## 監査者が次に進むために必要な成果物（サブエージェント抜かし防止との整合）

各フェーズ完了時に、[サブエージェント抜かし防止](./サブエージェント抜かし防止.md) の提出物表に沿った成果物が揃い、かつ上記「各フェーズで必ず確認する項目」を証跡ベースで満たした時点で次に進む。**03 完了時**の成果物は `03_実装計画.md` および 4.5 実施前のタスク一覧・テスト観点。用語は 00_システム理解・01_要件定義 とサブエージェント抜かし防止の表記にそろえる。

---

## 04_review 委譲時の必須（強制メカニズム）

- **委譲側（メイン）の MUST**: Constraints に [監査者用チェックリスト](./監査者用チェックリスト.md) の観点一覧（または参照）および各観点を確認することを必ず含める。
- **受領側（総合レビューリード）の MUST**: 観点ごとの確認結果（実施有無・証跡または指摘）を OutputSpec で返す。

---

## 監査者の立ち位置とゴール

- 監査者は**プロジェクトマネージャー的な立ち位置**とする。issue の**ゴール（00_要求定義の目的・成功基準）を常に把握したうえで**検証する。
- 監査開始時に**当該 issue の 00_要求定義**（または目的・成功基準の要約）を**必ず**参照する。ゴールに照らして「この成果物は目的を満たしているか」を判断する。
- 監査者は実装・テストの直接編集は行わず、指摘・指示・GO/NG のみを返す（[05_監査者](../workers/05_監査者.md) の禁止事項を維持）。

## 監査タイミング×指示先×指示内容×完了成果物

監査者は**どのタイミングで誰に指示を出すか**を常に理解する。不足時は該当役割に再実行・修正を指示し、完了成果物が揃うまで GO にしない。

| 監査タイミング | 指示先（役割） | 指示内容の例 | 完了として認める成果物 |
|----------------|----------------|--------------|------------------------|
| 01 完了後 | 要件BDDリード | 不明点の解消、BDD の補完 | 更新された `01_要件定義.md`、受け渡し契約 |
| 02 完了後 | 実装者・テスト者 | 設計に沿った実装・テスト観点の具体化 | 02 と整合した 03、または実装・テスト成果物 |
| 03 完了後 | （次は 4.5） | ドキュメント徹底レビュー実施 | 指摘ゼロ＋最低3回のレビュー証跡 |
| 4.5 完了後 | 実装者 | 実装開始（テストファースト） | テストコード・本番コード・実行結果 |
| 実装完了後 | 実装者（該当時） | 設計・実装の変更に伴う**システム仕様書（docs/）の作成・更新**。docs/ 更新時は**更新履歴**（docs/README.md）と**レビュー**（docs/00_review/）を必須とし、監査時にその実施を確認する | [ドキュメントルール](./ドキュメントルール.md) に沿った docs/ の更新。更新履歴・レビュー必須。更新ファイル名・diff 要約。該当しないプロジェクトでは省略可 |
| 実装完了後 | テスト者 | テスト実装・実行、不足観点の追加 | テストコード・実行結果・証跡。単体・結合・受け入れ・境界値・ブラックボックス・ホワイトボックス等の網羅（[監査者用チェックリスト](./監査者用チェックリスト.md) のテスト観点参照） |
| 実装完了後（不足時） | テスター or 実装者 | 再実行・追加実施の指示 | 再実行結果・追加テストの証跡 |
| 04_review 委譲時 | 総合レビューリード | 監査者用チェックリストの**全観点**（ドキュメント・テスト・証跡・品質・**サブエージェント使用**・**更新履歴・レビュー**・**ログ保存ポリシー**・**ワークフロー成果物のファイル名（YYYYMMDD_HHMMSS_ 命名規則）**）を確認すること。委譲側は Constraints に上記観点を含め、受領側は観点ごとの確認結果を OutputSpec で返す | 観点ごとの確認結果（実施有無・証跡または指摘） |
| 04 完了後 | （issue 完了 or 05 へ） | 残課題の対応 or 05_最終確認 | `04_review.md`、必要なら `05_最終確認チェックリスト.md` |

## 外部指摘受領時の対応

実装完了後に**外部から指摘**を受けた場合の流れ。

1. **指摘の分類**: ドキュメント修正／実装修正／テスト追加 等に分類する。
2. **指示先**: 該当する役割（要件BDDリード・実装者・テスト者等）に、修正内容と完了条件を伝える。
3. **進める工程**: 該当するフェーズ（01 の更新、実装の修正、テストの追加実行等）を実施する。
4. **完了として認める成果物**: 指摘対応一覧の解消、該当ファイルの更新証跡（diff 要約・ファイル名）、テスト再実行の結果。監査者が再検証し、GO とした時点で完了。

| 役割 | 確認すべきドキュメント・ルール（主なもの） |

| 監査者 | 00_要求定義（ゴール）、01〜04、本ファイル・[監査者用チェックリスト](./監査者用チェックリスト.md)、[レビュールール](./レビュールール.md)、[サブエージェント抜かし防止](./サブエージェント抜かし防止.md) |
