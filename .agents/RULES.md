# RULES - 実行・ドキュメント・テスト・レビュー（1ファイル完結）

> **役割**: **チェックリスト**で各工程の考慮漏れを防ぎ、**概念・思想・観点**で推論を支える。チェックリストと判断観点を記載し、考慮漏れを防ぐ。絶対制約（MUST/MUST NOT）は CORE に定義される。過去の詳細・背景は本ファイルの要約で足りる。必要時は .review/ を参照。
> **責務**: **RULES.md = 判断観点の要約、または横断ルールの案内**。実行・ドキュメント・テスト・レビュー時のチェックリスト。人間向けは [CONCEPTS](CONCEPTS.md) および [human/](human/) を参照。**定義しない**: 絶対制約（CORE）、機能有効化・適用条件（capabilities/POLICY）、ワークフロー順・DoD（WORKFLOW）。

---

## 推論に使う概念・思想・観点

判断・設計・実装・レビュー時に**推論のよりどころ**として使う。チェックリストは「やったか」を担保し、ここは「どう考えるか」を担保する。

**命題（全体を通じて前提とする）**: **システム開発は常に UNIX 哲学に基づく。** 要求定義から実装・レビューまで、あらゆる判断はこの命題を前提とする。以下はそのうえでの思想・哲学・観点である。

**思想（何を大切にするか）**

- **証跡で判断する**: 「やった」ではなく、ファイル・実行結果・手順で示す。自己申告で完了にしない。
- **フェーズを飛ばさない**: 順序と提出物を固定ゲートにする。何が揃えば次に進むかは固定し、手段は推論に委ねる。
- **委譲の一意性**: 委譲は delegate_to_sub のみ。サブには Goal と制約だけを渡し、人格・記憶は渡さない。
- **トレーサビリティ**: 誰が何をしたかを書記にだけ記録する。ログは workflow.db に保存を必須とする。
- **ドキュメントと実装の同期**: 変更したら該当 md を更新する。

**哲学（判断の土台）**

- **UNIX哲学**: 一つのことをうまくやる。組み合わせて動かす。入出力を明確にし疎結合に。
- **KISS**: できるだけシンプルに。
- **YAGNI**: 今いらないものは作らない。

**判断時の問い（観点・自問してから決める）**

1. シンプルにできないか  
2. 今のスコープに本当に必要か  
3. 責務が混ざっていないか  
4. 変更影響を局所化できているか  
5. 証跡で説明できるか  

曖昧な場合やトレードオフがある場合は、上記の問いと思想に照らして推論し、そのうえでチェックリストで漏れがないか確認する。

## 共通：着手前チェックリスト（毎タスク）

次を満たすまで、ワークフロー開始・フェーズ進行・コード変更・委譲・成果物作成をしてはならない。

- [ ] CORE / LOAD_POLICY / WORKFLOW / CONCEPTS の 4 ファイルを読了した（読了＝本ターンまたは直前ターンでコンテキストに含まれ参照可能な状態）。
- [ ] 着手時、応答冒頭に 1 行以内の確認文を記載した（例: CORE/LOAD_POLICY/WORKFLOW/CONCEPTS に従い、…）。初回セッション・規約改訂後は省略を推奨しない。
- [ ] SILENT MODE 時は先頭に `🧠 Mode: SILENT MODE`、会話は最大 15 行とした。
- [ ] 対応は `.workflow/{YYYYMMDD_HHMMSS_issue名}/00_要求定義.md` から開始する。フェーズを飛ばさない。

## 共通：毎フェーズ完了時チェックリスト（次に進む前に必須）

次の項目を**すべて**満たすまで次フェーズに進まない。未実施のまま進んだ場合は規約違反。

- [ ] **成果物**: WORKFLOW の必須成果物表と照合し、当該フェーズの必須成果物が揃っていることを証跡で確認した。テンプレートが存在する成果物はテンプレートをコピーして作成し、必須セクション・フォーマットを維持している。一から作成した成果物は不備とする。
- [ ] **テスト**: 該当フェーズでテストがある場合は**必ずテストを実行**し、実行コマンド・結果を証跡として残した。自己申告のみでは不十分。実装フェーズではテストファースト（テストコード先）の証跡に加え、テスト実行の証跡が必須。
- [ ] **ログ**: サブ実行後は書記へログ委譲済みで、書記が workflow.db に記録したことが確認できる。具体的な確認手段は [platforms/README](platforms/README.md) の「ログ記録の確認」を参照。書記未使用時は [CONTRACT §5](scribe/CONTRACT.md) のフォーマットにのみ従い、memo の `YYYYMMDD_HHMMSS_実行ログ.md` に YAML ブロックで 1 件ずつ追記した。同一 issue では既存の実行ログファイルに追記する。
- [ ] **カバレッジ**: 全テストレベルでカバレッジが100%である、または未達の場合は理由を 02_設計のテスト戦略または 03_実装計画の該当タスクに記載した（証跡で確認可能）。
- [ ] **単体 BDD 網羅**: 単体テストで正常系・異常系・境界値・回帰・結合を BDD（Given/When/Then）で仕様書レベルで網羅している（該当フェーズで単体テストがある場合。証跡で確認可能）。
- [ ] **API ブラックボックス**: 該当する場合、バックエンド API をブラックボックステストで網羅している（証跡で確認可能）。
- [ ] **E2E 網羅**: 該当する場合、フロントエンドの主要フローを E2E で網羅している（証跡で確認可能）。

## テスト戦略（必須要件）

以下は全フェーズで守るテスト方針である。毎フェーズ完了時・02_設計・03_実装計画のチェックリストで証跡確認する。

- **カバレッジ100%原則・未達時理由記載**: 全テストレベル（単体・結合/API・E2E）で、対象範囲のカバレッジを100%とすることを原則とする。やむを得ず未達とする場合は、理由を必ず記載する（記載場所: 02_設計のテスト戦略または 03_実装計画の該当タスク）。
- **単体 BDD 網羅**: 単体テストでは、正常系・異常系・境界値・回帰・結合を BDD（Feature/Scenario または Given-When-Then）で仕様書レベルで網羅することを必須とする。詳細は [テストコード_BDD形式.md](テストコード_BDD形式.md) を参照。
- **API ブラックボックステスト必須**: バックエンド API については、エンドポイントごとに正常・異常・境界をブラックボックスで検証することを必須とする。内部実装に依存しない入出力・ステータス・エラーメッセージの検証を含む。
- **E2E 網羅必須**: フロントエンドの主要ユーザーシナリオ（ログイン、主要画面遷移、クリティカル操作）を E2E でカバーすることを必須とする。未達時は理由記載とする。

- [ ] 03_実装計画のタスク単位で進行した（タスク実装→追加/修正テストの確認→テスト実行→関連ドキュメント更新→テスト通過後のみ次タスク）。

- [ ] レビュー対象の概要、指摘事項一覧（ID/内容/対応方針/対応状況）を 04_review.md に記載した。

- [ ] docs/ を運用している場合は、実装内容がシステム仕様書に反映されているか確認し、必要なら更新・更新履歴（docs/README.md）・レビュー記録（docs/00_review/）を実施した。
- [ ] 指摘へ対応した。対応後はテスト・品質確認の証跡を残した。

## 実行・運用で絶対に守ること

- [ ] 委譲は [delegate_to_sub](skills/agent/delegate_to_sub.md) を唯一の入口とした。直接サブを呼ばない。
- [ ] フェーズごとの作業を**毎回・自律的に** workers に委譲した。委譲なしでメインが単独でドキュメント作成・実装・監査の実作業・ログ記録をしなかった。
- [ ] 提出物が揃い、証跡で確認するまで次フェーズに進まなかった。監査者に委譲する場合はその結果を受領してから次に進んだ。
- [ ] 監査の実作業は監査者サブに委譲し、メインは委譲・完了受領・次フェーズ判定のみ行った。
- [ ] ドキュメントを変更したら該当 md を即時更新した。参照元を明示し、Mermaid を活用した。見出しに連番を付けない。

## 指摘対応時の共通手順

指摘（4.5 / 04_review / PR 指摘）への対応時は、次の順で実施する。

- [ ] 指摘を一覧化した（4.5 は memo のレビュー結果、04 は 04_review.md、PR は 指摘対応/01_指摘一覧.md 等）。
- [ ] 各指摘について採用・見送り・要検討を決め、理由を 1 行残した。
- [ ] 採用した指摘について対応を実施した。
- [ ] 対応後にテストを実行し、03 のテスト観点・品質観点を満たすことを証跡で確認した。
- [ ] 実装または docs/ に変更があった場合、実装とシステム仕様書（docs/）を照合し、齟齬がないか確認した。
- [ ] レビュー結果を記録した（docs/ 運用時は `docs/00_review/YYYYMMDD_HHMMSS_review.md`、それ以外は 04_review.md または memo）。
- [ ] docs/ を更新した場合は `docs/README.md` の更新履歴に追記した。
