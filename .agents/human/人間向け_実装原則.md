# 人間向け - 実装原則の詳細

> **読み手**: 人間。AI は [AGENTS.md](../../AGENTS.md) の実装原則セクション（要約と表）を参照し、このファイルは参照しない。

---

このドキュメントでは、AGENTS の基本方針で定義した開発手法を実践するための具体的な原則を説明します。規約の動かし方（サブエージェント運用・トレーサビリティ）は [AGENTS.md](../../AGENTS.md) の「サブエージェント運用（MVP）」を参照。

> **重要**: ここに列挙している原則は「必要なときに取り出す道具箱」です。**システム開発の土台**として **UNIX哲学** を置き、日常的に常に意識すべきなのは **UNIX哲学・KISS・YAGNI** です。それ以外は「複雑さが増してきたときに取り出す」程度で構いません。

## UNIX哲学（システム開発の土台）

- **一つのことをうまくやる**: Write programs that do one thing and do it well。小さな関数・モジュールに分割する。
- **組み合わせて動かす**: Write programs to work together。標準入出力・一貫したデータ形式・パイプライン化しやすいインターフェース。
- **疎結合**: Expect the output of every program to become the input to another。純粋関数に近い形で、隠れた状態を減らす。

AI が「巨大な一つの関数」「密結合なクラス」を生成しがちな問題を、複雑なテクニックなしで軽減するために本規約で明示的に据えている。

## 思考原則

1. **解決したいことを明確化**: 何を解決したいのか、何を達成したいのかを明確にする
2. **振る舞いを定義**: 解決のために必要な振る舞い（動作・機能）を定義する
3. **逆算でステップ洗い出し**: 解決したいことや振る舞いから逆算して必要なステップを洗い出す
4. **最適か/シンプルか自問**: 各ステップで最適性とシンプルさを検証
5. **統合**: すべてのステップを統合して結果を得る

## プログラミング原則

### 基本原則

1. **要件明確化**: 実装前に要件を明確にする
2. **工程抽出**: 設計 → 実装 → テスト → リファクタ → デプロイを逆算で抽出
3. **工程ごとに自問**: 各工程で最適性を検証
4. **統合**: すべての工程を統合して高品質化

### DRY 原則（Don't Repeat Yourself）

- **主な焦点**: コードの重複排除。**適用場面**: 実装レベル。
- **目的**: コードの重複を減らし、再利用性を高め、保守性・可読性を向上させる。
- **注意点**: 過剰に DRY を追求すると逆に複雑になる。類似だが異なる要件のコードを無理に統合しない。
- **ワークフロー**: 要件定義で共通化を特定、設計で共通コンポーネントを特定、実装で重複を関数・コンポーネントに抽出。

### SOLID 原則

- **主な焦点**: オブジェクト指向設計。5 つの原則で柔軟・拡張性・保守性を高める。
- **S - 単一責任**: 1 クラス・モジュールは 1 責任のみ。
- **O - オープン・クローズド**: 拡張に開き、修正に閉じる。
- **L - リスコフの置換**: 派生は基底と置換可能であること。
- **I - インターフェース分離**: 使わないインターフェースに依存しない。
- **D - 依存性逆転**: 上位は下位に依存せず、両方とも抽象に依存。

### KISS / YAGNI

- **KISS**: シンプルに保つ。複雑な解決策より理解しやすい解決策を選ぶ。
- **YAGNI**: 今必要のない機能は実装しない。必要になったときに実装する。

### デメテルの法則、GRASP、CoC、PoLA、TDAE、クリーンアーキテクチャ

- **Law of Demeter**: 直接の友人とだけ通信。`a.getB().getC()` を避け、`a.getC()` のように委譲する。
- **GRASP**: 責務の割り当て（情報エキスパート、クリエイター、低結合、高凝集）。SOLID を具体化。
- **CoC**: 設定より規約。フレームワークの規約に従い設定を最小限に。
- **PoLA**: 直感性・予測可能性。API/UI はユーザーの期待を裏切らないようにする。
- **TDAE（Tell, Don't Ask）**: 状態を聞かずに命令を送る。カプセル化を強化。
- **クリーンアーキテクチャ**: 依存は内側向き。Entities → Use Cases → Interface Adapters → Frameworks。中規模以上で検討。

### 原則の使い分け

- **常に（システム開発の土台）**: UNIX哲学。**常に**: KISS、YAGNI。
- **規模**: 小規模は KISS/YAGNI/DRY。中規模は SOLID・クリーンアーキ検討。大規模は SOLID/GRASP/クリーンアーキ。フレームワーク開発は CoC/PoLA。
- **過剰適用は避ける。実用性を優先。**

### 原則の適用場面まとめ

| 原則                   | 主な焦点             | 適用場面                  | 適用推奨度             |
| ---------------------- | -------------------- | ------------------------- | ---------------------- |
| **UNIX哲学**           | 単一責任・連携・疎結合 | 設計・実装全般（システムの形） | **常に適用**           |
| KISS                   | シンプルさ           | 実装・設計全般            | **常に適用**           |
| YAGNI                  | 必要性に基づく開発   | 要件定義・実装            | **常に適用**           |
| DRY                    | コードの重複排除     | 実装レベル                | 適度に適用             |
| クリーンアーキテクチャ | 依存関係と層の分離   | 中規模以上の issue/タスク | 中規模以上で検討       |
| SOLID                  | オブジェクト指向設計 | 設計レベル                | 複雑な設計で適用       |
| GRASP                  | 責務の割り当て       | オブジェクト指向設計      | 複雑な設計で適用       |
| Law of Demeter         | 依存関係の削減       | オブジェクト間通信        | 必要に応じて適用       |
| CoC                    | 規約の活用           | フレームワーク開発        | フレームワーク使用時   |
| PoLA                   | 直感性・予測可能性   | API/UI 設計               | UI/API 設計時          |
| TDAE                   | カプセル化           | オブジェクト指向実装      | オブジェクト指向設計時 |
