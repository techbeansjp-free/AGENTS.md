# Platform Adapter: Gemini

## 目的

この実行基盤で、共通仕様（boot の CORE / LOAD_POLICY / EXECUTION_CONTRACT 等）を壊さずに動かす。

## 前提

- **利用可能**: 長文理解が強い。要件・監査・ドキュメント照合に向く。
- **利用の注意**: 指示の固定力・出力の安定性で差が出やすい。参照境界と出力形式をより明示した方が安全。
- **文脈保持**: 長いコンテキストを読ませる設計と相性が良いが、「どこまでが規約でどこからが依頼か」をはっきりさせた方がよい。

## 必須ルール

- **最初に読む順序**: boot の実行前契約どおり（CORE → LOAD_POLICY → WORKFLOW → CONCEPTS）。Gemini では参照する範囲（例: この 4 ファイルのみ先に読む）を明示すると安定しやすい。
- **委譲の表現**: サブエージェント相当がある場合、Task/Constraints/OutputSpec を共通契約の形式で渡す。長文を載せない。
- **ログ記録**: 書記サブに委譲。workflow.db への記録は書記のみ。CONTRACT §5 の暫定記録を守る。
- **出力制約**: 出力形式（Markdown・セクション名・必須項目）を CORE と OutputSpec で固定し、揺れを抑える。応答長の制御が必要な場合は Constraints に 1 行で書く。

## 注意点

- **破綻しやすいポイント**: 指示が長いと解釈が揺れやすい。Task は結果述語 1 文、Constraints は最大 5 行に抑える。
- **長文化しやすい箇所**: 説明を補足しがち。規約では「手段は推論に委ねる」ため、必要以上に手順を書かない。
- **コンテキスト漏れ**: 参照境界（どのファイル・どのセクションまで見るか）を Constraints で明示すると、出力の一貫性が上がる。

## 実行時の差分

- **サブエージェント相当**: 製品による。ある場合は共通契約の Task/Constraints/OutputSpec を渡す。監査・レビュー・長文の要件整理との相性が良い。
- **ツール呼び出し**: 環境依存。ファイル編集が可能な場合はテンプレートコピー・必須セクション維持を守る。
- **ファイル編集**: 可能な場合は CORE のファイル名規則・frontmatter を守る。参照境界と出力形式を明示すると失敗が減る。
