# ワークフロー・成果物・監査（1ファイル統合）

> **役割**: ワークフロー順・必須成果物・DoD・命名規則・進行役のやること・監査観点を**1ファイル**に集約。「どこを変えれば何が変わるか」をここで把握する。  
> 絶対制約は [boot/CORE.md](boot/CORE.md)、委譲先は [boot/LOAD_POLICY.md](boot/LOAD_POLICY.md)、思想・観点は [CONCEPTS.md](CONCEPTS.md)。

---

## 1. フェーズ順（固定ゲート）

順序を飛ばさない。提出物が揃い、証跡で確認するまで次に進まない。

```text
00_システム理解（既存時のみ）→ 00_要求定義 → 01_要件定義 → 02_設計 → 03_実装計画
  → 4.5 ドキュメント徹底レビュー（必須・指摘ゼロ＋最低3回）
  → 実装（必要なら 90_issues で分割）
  → 04_review → 05_最終確認（外部設定が必要な場合のみ）
```

---

## 2. 必須成果物・DoD

| フェーズ | 必須成果物 | 完了条件（DoD） |
|----------|------------|-----------------|
| 00_要求定義 | `00_要求定義.md`、DoD 明文化 | 提出物あり＋証跡確認済み |
| 01_要件定義 | `01_要件定義.md`（ストーリー・受け入れ基準・BDD Feature/Scenario） | 同上 |
| 02_設計 | `02_設計.md`（影響範囲・方針・テスト戦略） | 同上 |
| 03_実装計画 | `03_実装計画.md`（タスク・テスト観点・優先度） | 同上 |
| 4.5 | `memo/YYYYMMDD_HHMMSS_ドキュメント徹底レビュー結果_第N回.md` 最低3回、指摘ゼロ | 指摘ゼロ＋3回以上 |
| 実装 | テストコード（先）・本番コード・変更一覧・diff要約・実行結果、カバレッジレポートまたは理由記載、単体テスト一覧・BDD シナリオ、API テスト一覧、E2E シナリオ | 提出物＋証跡確認済み。テスト方針（RULES のテスト戦略）に基づく証跡が揃っていること。 |
| 04_review | `04_review.md`（指摘・対応・サマリ） | 指摘解消・GO |

**テンプレート使用の強制**: 上記の各成果物は、`.workflow/templates/` に同名（または対応）テンプレートが存在する場合、**必ずテンプレートをコピー**して作成する。一から作成してはならない。**「対応」とは**、当該成果物のベース名（例: 00_要求定義）をファイル名に含む `.workflow/templates/` 内のファイルを指す。複数ある場合は同名を優先する。テンプレートの必須セクション・見出し構造・フォーマットを維持する。詳細は [RULES テンプレート・フォーマット強制](RULES.md)。

証跡＝実ファイル名・実行コマンド・結果・手順。自己申告では完了にしない。

**次に進む前の確認チェック（毎フェーズ必須）**: 下記を満たすまで次フェーズに進まない。詳細は [RULES.md 確認義務・テンプレート・フォーマット強制](RULES.md)。

- [ ] **成果物**: 本フェーズの必須成果物が上表どおり揃い、DoD を証跡で確認したか。
- [ ] **テンプレート・フォーマット**: テンプレートが存在する成果物は、テンプレートをコピーして作成し、必須セクション・フォーマットを維持しているか。
- [ ] **テスト**: 該当フェーズでテストがある場合、テストを実行し、実行コマンド・結果を証跡として残したか。テスト作成は 01 の BDD 形式・03 のテスト観点に従っているか。
- [ ] **テスト実行・証跡の提出**: 実装フェーズおよびレビュー前では、テストを実行し、RULES のテスト戦略に基づく証跡（カバレッジ・単体 BDD・API・E2E）を提出物として揃えるまで次フェーズに進まない。
- [ ] **ログ**: サブ実行後は書記へログ委譲済みか。**書記が workflow.db（SQLite）に記録したこと**が確認できるか（書記未使用時は memo に CONTRACT 準拠で暫定記録したか）。

## 3. 命名・配置

- **issue 直下**: `.workflow/{YYYYMMDD_HHMMSS_issue名}/`
- **日時**: システム取得・JST。`YYYYMMDD_HHMMSS_` プレフィックス必須。日付のみ・プレフィックスなし禁止。
- **memo**: `memo/YYYYMMDD_HHMMSS_*.md`

---

## 4. 進行役のやること（誰に委譲・何を渡す・次に進む条件）

| フェーズ | 委譲先 | 完了の受け取り | 次に進む条件 |
|----------|--------|----------------|---------------|
| 01 | 要件BDDリード | 01_要件定義.md | 提出物＋監査確認済み |
| 02 | 実装者・テスト者 | 02_設計.md | 同上 |
| 03 | 実装者・テスト者→監査者 | 03_実装計画.md | 同上 |
| 4.5 | 総合レビューリード | レビュー結果 memo | 指摘ゼロ＋3回以上 |
| 実装 | 実装者→テスト者→監査者 | コード・テスト結果・diff要約 | 同上 |
| 04_review | 総合レビューリード | 04_review.md、観点別結果 | 指摘解消・GO |

委譲先の詳細は [LOAD_POLICY 4. フェーズ→worker](boot/LOAD_POLICY.md)。**各サブ実行後は書記へログを委譲し、書記は workflow.db（SQLite）にのみ記録する。** ログの SQLite 保存は強制。書記未使用時は memo に暫定記録（のちに workflow.db へ移行前提）。

## 5. 監査観点（証跡で確認する項目）

- **共通**: 提出物が揃っているか。証跡（ファイル・実行結果・手順）があるか。自己申告でないか。**テンプレートが存在する成果物はテンプレートをコピーして作成し、必須セクション・フォーマットを維持しているか。** **ログは workflow.db に記録されているか**（サブ運用時は書記経由で SQLite に保存済みか。暫定時は memo に CONTRACT 準拠で記録済みか）。
- **01**: ストーリー・受け入れ基準・BDD Feature/Scenario が 01 にあり、02・03 と一貫しているか。01 はテンプレートのフォーマットに従っているか。
- **02**: 影響範囲・テスト戦略が 02 にあり、01 と整合しているか。
- **03**: タスク・テスト観点が 03 にあり、01 の BDD から抽出されているか。
- **4.5**: レビュー最低3回・指摘ゼロの証跡があるか。
- **実装**: テストファースト（テストコード先）の証跡。03 のテスト観点を満たすテストが存在・実行されているか。テストは 01 の BDD 形式・03 のテスト観点に沿ったフォーマットか。テスト方針（RULES のテスト戦略）に基づく証跡（カバレッジ・単体 BDD・API・E2E）が揃っているか。ドキュメントと実装の同期。
- **04**: 指摘一覧・対応状況・変更サマリが 04_review.md にあるか。04 はテンプレートのフォーマットに従っているか。

監査は監査者サブに委譲。メインは委譲・完了受領・次フェーズ判定のみ。

## 6. 指摘対応の流れ（4.5 / 04 / PR 共通）

1. 指摘一覧化 → 2. 対応方針（採用・見送り・理由）→ 3. 対応実施 → 4. テスト・品質確認（証跡）→ 5. docs/ 照合（該当時）→ 6. レビュー結果記録 → 7. 変更履歴（docs/ 更新時）
