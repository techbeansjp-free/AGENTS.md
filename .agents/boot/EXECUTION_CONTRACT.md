# 実行契約（全人格の共通 I/F）

> **AI 向け**: すべての人格が従う共通入力・出力の仕様。メインがサブに委譲するときの **作業契約（contract）** と、成果物の正規形を固定する。

**作業契約（Task Contract）とは**: サブには ① 共通ルール ＋ ③ ツール仕様 だけを常時渡し、人格・記憶は渡さない。ただし **毎回、親（メイン）からそのタスク用の「作業契約（今回の必須前提）」を必ず添付する**。これで USER.md を丸ごと渡さずに、命名規約・禁止事項・ドキュメントルール・セキュリティ方針などの事故だけを防ぐ。契約がないと「正しいけどズレた成果物」が出やすい。

**落とし穴**: サブに「記憶を渡さない」だけでは不十分。**依頼文に背景・ユーザー情報を書いた瞬間にサブは知る。** そのため [CORE の「2. 委譲」の必ず守る運用](CORE.md) の 3 点（①+③+Skill 1 つ+契約まで／背景は原則書かない／USER・memory 全文は渡さず要約して Constraints へ）を必ず守る。

---

## 1. 作業契約（メイン→サブに毎回添付する 4 項目）

サブへの依頼は **毎回** 次の 4 項目を短く添付する。混ぜるべきでない情報を入れないため、フォーマットを固定する。

- **Task**: 結果述語（〜が揃った状態を出す／〜を完了する）で 1 文に書く。
- **Constraints**: 禁止・必須・参照・前提（最大 5 行）のみ。背景・経緯の長文は書かない。

| 契約項目 | 対応ブロック | 内容 | 原則 |
|----------|--------------|------|------|
| **ゴール** | Task | 何を出せば完了か。1 文で明示。 | 必須。Task は結果述語（〜が揃った状態を出す／〜を完了する）で 1 文。 |
| **入力** | Constraints の一部 | どのファイル・どの範囲を読むか。参照してよいパス。 | 最大 5 行。 |
| **制約** | Constraints | 禁止事項、出力形式・粒度、前提（タスクに必要なユーザー事情はメインが要約してここに。USER.md 全文は渡さない）。 | 禁止・必須・参照・前提（最大 5 行）のみ。背景・経緯の長文は書かない。 |
| **受け入れ条件** | OutputSpec / 完了条件 | 何が揃えば完了とみなすか。チェックリスト。 | 必須。 |

**背景**: ユーザー意図・経緯・判断理由は **原則書かない**。必要なら 1〜2 文で最小限に留める。

MUST: サブへの入力は上記の範囲のみとする。それ以外のブロックや長文は作らない。

### 1.1 コピペ用 contract テンプレ（Markdown）

Task は結果述語（〜が揃った状態を出す／〜を完了する）で 1 文。Constraints は禁止・必須・参照・前提（最大 5 行）のみとし、背景・経緯の長文は書かない。

```markdown
## Task
（何を完了すればよいか 1 文・結果述語で書く）

## Constraints
- 前提: （今回の必須前提。命名規約・禁止事項・ドキュメントルール等を要約、最大 5 行）
- 参照してよいファイル: （パスを限定して列挙）
- 禁止: （例: Tailwind 不可、推測記載禁止、物理削除しない 等）

## OutputSpec
- 成果物: （パス・形式・必須項目）
- 完了条件: （チェックリスト）
```

## 2. 出力（サブの返却フォーマット）

サブは次の形式で返す。メインが統合し、次フェーズの IN を組み立て、必要なら書記にログ項目を渡す。

- **成果物**: Task で指定された形式・パスの成果物。コード・ドキュメント・指摘一覧等。
- **成果物に含めるヘッダ（frontmatter または固定ヘッダ）**: 再現性・監査のため、以下を必須とする。
  - `issue_id`（UUID）
  - `phase`（01 / 02 / 03 / 04）
  - `agent_id`（人格 ID）
  - `inputs`（参照したアーティファクトの ID またはパス一覧）
  - `outputs`（生成・更新したアーティファクトの ID またはパス一覧）
  - （任意）`decision`（判断理由・採用した前提・分岐）
  - （任意）`model`（モデル識別子。将来の再現用）
  - （任意）`risks`（想定リスク・前提の不確実性）
  - （任意）`next_actions`（メインへの提案：次にやること・確認してほしいこと）

サブは「成果物」を主に返す。判断理由・リスク・次アクションは、メインの統合に役立つ場合だけ任意で付ける。

### 2.1 phase と execution_logs.action_type の対応（メイン・書記の一貫性）

成果物の `phase` と、書記へ渡すログの `action_type`（execution_logs に格納）は、次の規則で対応させる。メインは書記にログ項目を渡すとき、この対応で `action_type` を決める。

| phase（frontmatter 等） | action_type（execution_logs） | 備考 |
|-------------------------|-------------------------------|------|
| 01 | plan | 要件・BDD 計画 |
| 02 | execute | 設計・実装 |
| 03 | execute または plan | 実装計画 |
| 03_review | review | 03 の監査 |
| 4.5 | review | ドキュメント徹底レビュー |
| 04 / 04_review | review | 総合レビュー・監査 |
| その他 | フェーズ名をそのまま（例: 00_要求定義） | 一意に識別できる値 |

**正規ルール**: 上記にない phase は、`01`→plan、`02`→execute、`03`→execute、`*_review`→review とし、それ以外は phase をそのまま action_type に使う。execution_logs の action_type はこの規則に従い、書記とメインで一致させる。

## 3. 不明点の扱い

- サブが質問を返してきた場合: メインは「前提を明示して A/B 案を出す」形で Constraints を更新し、再度渡す。質問に直接答えるだけにしない。
