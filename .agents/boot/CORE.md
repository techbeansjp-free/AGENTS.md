# CORE - 絶対制約（サブエージェント運用 MVP）

> **AI 向け**: メイン・サブを問わず常に守る MUST / MUST NOT。サブエージェント基盤で動かす前提。思想・長文は書かず、ここでは制約のみ。
> **責務**: **CORE.md = 絶対制約**。結果の境界・委譲の境界・出力の境界を固定する。**定義しない**: 判断観点の細則・横断ルールの案内（RULES）、機能有効化・適用条件（capabilities/POLICY）。

**固定するもの**（ルールとして書く）: 結果の境界・委譲の境界・出力の境界。  
**動的に委ねるもの**（推論に委ねる）: 手段・優先順位・参照タイミング。

---

## 0. 実行前契約（強制力の根拠）

- **読了の定義**: 本規約で「読了」とは、当該ファイルの内容が**本ターンまたは直前のターンでコンテキストに含まれ、エージェントが参照可能な状態になったこと**を指す。技術的強制はなく、履行は自己遵守に依存する。
- **適用範囲**: 本実行前契約は**メインにのみ**義務とする。サブには [SUBAGENT](SUBAGENT.md) の注入で最小読込を保証する。
- **禁止**: 以下 4 ファイルを**読了するまで**、いかなるワークフロー開始・フェーズ進行・コード変更・委譲・成果物作成も行ってはならない。未読のまま行ったアクションは規約上無効とする。
- **必須読了リスト**（この順で読む）:
  1. 本ファイル [CORE.md](CORE.md)
  2. [LOAD_POLICY.md](LOAD_POLICY.md)
  3. [WORKFLOW.md](../WORKFLOW.md)（フェーズ・成果物・DoD・監査観点）
  4. [CONCEPTS.md](../CONCEPTS.md)（思想・方法論・哲学・観点・フォーマット）
- **確認義務**: 上記を読了したうえで初めて作業に着手する。**必須（MUST）**: 着手時は応答の冒頭で 1 行以内の確認文を記載する（例: `🧠 Mode: SILENT MODE` の次に「CORE/LOAD_POLICY/WORKFLOW/CONCEPTS に従い、…」）。ユーザーが「規約は読んだ前提で」と明示した場合のみ確認文を省略してよい。**注記**: 監査・証跡の観点から、初回セッションまたは規約改訂後の初回では確認文の省略を推奨しない。
- **目的**: 思想・方法論・フォーマット・成果物を AI が確実に認識し、規約を守ったうえでだけ動作させる。

## 1. 入口と進行

- **解釈**: 本規約で `.workflow/` が指すパスは、**規約の入口である AGENTS.md が置かれているディレクトリ（プロジェクトルート）** 直下の `.workflow/` とする。AGENTS-spec をサブフォルダとしてコピーした場合は、プロジェクトルートに AGENTS.md を置き、そのルートの `.workflow/` を使用する。

### ワークフロー崩壊防止

- **目的**: どの issue でも「何のためのタスクか」が一意に決まり証跡の起点が分かる状態、および工程の抜け漏れがなく各フェーズの証跡が揃った状態を達成する。
- **制約**: すべての対応は `.workflow/{YYYYMMDD_HHMMSS_issue_name}/00_要求定義.md` から開始する。既存プロジェクト導入時は `00_システム理解.md` からとすること。フェーズを飛ばさない。順序は 00 → 01 → 02 → 03 → 4.5 ドキュメント徹底レビュー（必須）→ 実装 → 04_review を守る。各フェーズの提出物が揃うまで次に進まない。サブを使用しない場合も、同じ提出物表・同じ完了条件を満たすこと。**成果物作成時は、`.workflow/templates/` に該当テンプレートが存在する場合は必ずテンプレートをコピーして使用し、必須セクション・フォーマットを維持する。一から作成してはならない。** 詳細は [WORKFLOW](../WORKFLOW.md)、[RULES テンプレート・フォーマット強制](../RULES.md)。
- **完了条件**: 当該フェーズの提出物表が満たされ、次フェーズに進む根拠が説明できること。

### 証跡の完全性

- **目的**: フェーズ完了が「自己申告」ではなく証跡で検証可能な状態を達成する。
- **制約**: フェーズ完了時は [WORKFLOW](../WORKFLOW.md) の監査観点に沿って実施し、証跡が満たされるまで次フェーズに進まない。提出物が存在するだけでは不十分とする。上記確認はメインが証跡ベースで行う。04_review では総合レビューリードへ委譲する際に、04 委譲時の Constraints（チェックリスト観点含む）を満たすこと。進行役（メイン）は [WORKFLOW](../WORKFLOW.md) を参照し、各フェーズで当該手順の完了条件を満たすまで次フェーズに進まない。
- **完了条件**: 証跡に基づく確認が実施され、監査者用チェックリスト（該当時）に沿った証跡確認が完了していること。

### フェーズ完了時の確認義務（3 点・満たすまで次に進まない）

- **目的**: テスト未実行・成果物未照合・ログ未記録のまま次に進むことを防ぐ。
- **制約**: 各フェーズ終了時に [RULES 確認義務](../RULES.md) に従い、次の 3 つを満たすまで次フェーズに進まない。(1) **成果物**: WORKFLOW の必須成果物表と照合し、揃っていることを証跡で確認した。(2) **テスト**: 該当フェーズでテストがある場合は必ず実行し、実行コマンド・結果を証跡として残した。(3) **ログ**: サブ実行後は書記へログ委譲済みで、**書記が workflow.db に記録したこと**が確認できること。具体的な確認手段は実行基盤により異なるため、[platforms/README](../platforms/README.md) の「ログ記録の確認」を参照する。書記未使用時は memo に [CONTRACT §5](../scribe/CONTRACT.md) 準拠の暫定記録を残す（本則は workflow.db への保存を必須とする）。
- **完了条件**: 上記 3 点がすべて満たされたことをメインが確認したうえで次フェーズに進んでいること。

### メインの読込と責務

- **目的**: メインが「絶対制約」と「いつ何を読むか」を把握した上で判断し、委譲・完了受領・次フェーズ判定に集中した状態を達成する。
- **制約**: メインは本 CORE と [LOAD_POLICY](LOAD_POLICY.md) を最初に読む。常時ロードは廃止し、必要なときだけ LOAD_POLICY に従って他のファイルを読む。メインの責務は進行役に集中する。監査の実作業（証跡に基づく合格判定・チェックリスト検証）は監査者サブに委譲し、メインは委譲・完了受領・次フェーズ判定を行う。監査委譲時は [WORKFLOW](../WORKFLOW.md) の監査観点を参照する。ドキュメント作成・レビュー実施は workers に委譲し、メインは各フェーズの完了を証跡ベースで検証する。
- **完了条件**: メインが CORE と LOAD_POLICY を読んだ上で、委譲・受領・判定のみを行い実作業を委譲していること。

### 委譲の自律と一意入口

- **目的**: 委譲経路が一意であり、トレーサビリティとコンテキスト注入が一貫した状態を達成する。
- **制約**: ユーザーが「サブエージェントと協議」等と明示的に指示しなくても、フェーズごとの作業を毎回・自律的にサブエージェント（workers）に委譲する。委譲は [delegate_to_sub](../skills/agent/delegate_to_sub.md) を唯一の入口とする。ログの記録は書記サブに委譲する。委譲なしでメインが単独でドキュメント作成・実装・監査の実作業・ログ記録を行うことは禁止する。.workflow 配下に成果物ファイル（00_要求定義.md 等の固定フェーズ文書を除く、memo・レビュー結果・実行ログ等の成果物ファイル）を作成する場合は、ファイル名に YYYYMMDD_HHMMSS_ プレフィックスを付ける。プレフィックスの日時はファイル作成時にシステムから取得し、日本標準時（JST, UTC+9）を用いる（手入力・推測・記憶は禁止）。日付のみ（YYYYMMDD_）やプレフィックスなしは禁止。
- **完了条件**: フェーズごとの作業が delegate_to_sub 経由で委譲され、成果物に規定のファイル名規則が満たされていること。

## 2. 委譲（メイン → サブ）

サブには**達成すべき結果（Goal）と制約だけを渡す**。背景・経緯は要約して Constraints に長く載せず、必要なら 1〜2 文で Task に含める。

**必ず守る運用**（この 3 点を破ると、実質的に人格・記憶を渡しているのと同じになる）:

1. **サブに渡すコンテキストは「① + ③ + そのタスクの Skill 1 つ + 作業契約」まで**。例外は [workers/README のホワイトリスト](../workers/README.md) に閉じる（例: 書記＝ログ仕様・保存先だけ）。
2. **背景は原則書かない**。必要なら 1〜2 文で最小限に留める。
3. **USER.md 全文・memory 全文は渡さない**。メインが要約し、必要な分だけ Constraints に載せる。

### 委譲の一意性（入口・最小保証）

- **目的**: 委譲経路が一意であり、サブが必ず同一の最小ルールを読んだ上で動く状態を達成する。
- **制約**: サブエージェントの呼び出しは [skills/agent/delegate_to_sub](../skills/agent/delegate_to_sub.md) を唯一の入口とする。直接呼び出し禁止。メインはサブを呼ぶ前に、サブのコンテキストを [SUBAGENT](SUBAGENT.md) の注入順序で組み立てる（最小読込保証。含めないとルールが強制されず破綻する）。委譲手順は [skills/agent/delegate_to_sub](../skills/agent/delegate_to_sub.md) に従う。
- **完了条件**: 委譲が delegate_to_sub 経由で行われ、サブのコンテキストが SUBAGENT の順序で組み立てられていること。

### 委譲の正規化（契約形式・コンテキスト境界）

- **目的**: サブが「そのタスクに必要な最小情報」だけを持ち人格・記憶の漏れが起きない状態、および委譲内容が正規化されサブの判断範囲が明確な状態を達成する。
- **制約**: フェーズごとの作業は workers に Task / Constraints / OutputSpec の 3 ブロックのみで委譲する。共通 I/F は [EXECUTION_CONTRACT](EXECUTION_CONTRACT.md)、人格一覧は [workers/README](../workers/README.md)。サブに背景・経緯・ユーザー情報の長文を渡さない。Constraints の「前提」は最大 5 行に要約する。
- **完了条件**: 委譲が Task / Constraints / OutputSpec の 3 ブロックで行われ、Constraints の前提が 5 行以内に収まっていること。

## 3. トレーサビリティ（誰が何をしたか）

### トレーサビリティ（ログは workflow.db に保存することを必須とする）

- **目的**: 「誰が何をしたか」が一意に記録され、ログの改ざん・分散が起きない状態を達成する。
- **制約**: **本則**: ログの保存先は **workflow.db（SQLite）のみ**とし、その保存を**必須**とする。サブ運用時は**書記サブを必ず使用**し、各サブ実行後にメインはログ項目を書記サブに委譲する。書記は受け取ったログ項目を **workflow.db にのみ**記録する（INSERT）。書記以外の人格が workflow.db に直接書くことは禁止。`.workflow/**/logs/` は使用禁止・廃止。トレーサビリティは最初から必須。詳細は [書記役とログ委譲](../scribe/書記役とログ委譲.md)、[capabilities/POLICY](../capabilities/POLICY.md)、[ワークフローログ_SQLiteスキーマ](../ledger/ワークフローログ_SQLiteスキーマ.md)。
- **完了条件**: 各サブ実行後にログ項目が書記へ委譲され、**書記が workflow.db に 1 件記録したこと**が確認できること。書記未使用時は下記例外に従う。

### 書記未使用時の暫定記録（例外）

- **目的**: 書記サブをまだ導入していない場合のみ、「誰が何をしたか」を暫定的に追える状態を達成する。
- **制約**: **例外**: 書記サブを呼ばない場合（メインのみで実行する場合）**に限り**、[CONTRACT §5 暫定記録](../scribe/CONTRACT.md) のフォーマットに**のみ**従い、`.workflow/{issue}/memo/YYYYMMDD_HHMMSS_実行ログ.md` に YAML ブロックで 1 件ずつ追記する。形式・必須キー・区切りを変えてはならない。本則は workflow.db への保存を必須とする。暫定運用後は書記サブを導入し、workflow.db に記録する運用へ移行すること。
- **完了条件**: メインのみ実行時、memo 内の実行ログに CONTRACT 同様の項目で暫定記録が存在すること。

## 4. 出力形式

### 出力形式の一貫性（会話）

- **目的**: 会話が簡潔に保たれ、長文は .workflow/memo に寄せる状態を達成する。
- **制約**: 応答は常に SILENT MODE（会話は最大15行、先頭に `🧠 Mode: SILENT MODE`）。ユーザーが「詳細を」「全文を」と明示した場合を除く。
- **完了条件**: 応答が SILENT MODE に従っていること（ユーザーが明示した場合は除く）。

### ドキュメントと実装の同期

- **目的**: 仕様と実装の乖離が起きない状態を達成する。
- **制約**: ドキュメントと実装を常に同期させる。変更したら必ず該当 md を更新する。
- **完了条件**: 変更したアーティファクトに対応するドキュメントが更新されていること。

## 4.5 衝突時の優先順位

### 衝突時の優先順位

- **目的**: ルール同士が矛盾したときに、どちらを優先するかを一意に決められる状態を達成する。
- **対象範囲**: 本節が対象とする衝突は、**出力の簡潔化（SILENT MODE）と、監査・証跡・ログに必要な詳細さ・完全性との衝突に限る**。上記以外のルール同士の衝突は、[LOAD_POLICY §0](LOAD_POLICY.md) のソース優先順位に従い、それでも決まらない場合は CORE の該当セクションの MUST/MUST NOT を優先する。**本節（4.5）の対象範囲内**で、同一主題の補足同士が矛盾する場合に限り、節番号の大きい方を優先する。
- **制約**: ルール同士が矛盾したときは、本節の優先順位に従う。監査・証跡・ログについては詳細を優先する（簡潔化より証跡の完全性）。通常の会話出力については簡潔を優先する（SILENT MODE）。上記が衝突する場合は、**監査・証跡・ログの詳細優先**に従う。この「詳細優先」は**成果物・証跡の必須項目・粒度**にも及ぶ。
- **完了条件**: 衝突時に本節の優先順位に従って判断が行われていること。
