## 6. テスト戦略

**重要**: テスト戦略の定義は必須です。各コンポーネント/API/機能に対して、どのテストレベル（単体/結合/E2E）で何をテストするかの方針を定義してください。詳細は **RULES のテスト戦略** または **本設計書 §6** を参照してください。

### 6.1 テストレベル方針（カバレッジ100%・理由記載）

各テストレベル（単体/結合/API/E2E）でのカバレッジ方針と、未達時の理由記載ルールを定義します。

- **カバレッジ方針**: {原則として100%とする / 対象範囲ごとに記載}
- **未達時の理由記載**: {やむを得ず未達とする場合は理由を必ず記載する。記載場所: 本節または 03_実装計画の該当タスク}
- **理由記載の例**: {レガシー部分・外部モック不可・コスト対効果 等}

#### テストピラミッド

```
        E2E/シナリオ
      （少ないが重要なハッピーパス＋主要バッドパス）

    ────────────────────────

    結合/APIテスト
    （そこそこ）

    ────────────────────────

    単体テスト
    （多い：高速・細かい）
```

| レベル | 責務 | カバレッジ・理由記載 |
|--------|------|----------------------|
| 単体 | 関数・メソッド・コンポーネント単位。BDD で仕様書レベルを網羅。 | {原則100%。未達時は理由記載必須} |
| 結合/API | バックエンド API をブラックボックスで検証。 | {原則100%。未達時は理由記載必須} |
| E2E | フロントエンドの主要フローを端末から検証。 | {主要シナリオ網羅。未達時は理由記載必須} |

### 6.2 単体テストの網羅（正常系・異常系・境界値・回帰・結合）

単体テストでは次を BDD（Feature/Scenario または Given-When-Then）で仕様書レベルで網羅する。

- **正常系**: {期待どおりの入力で期待どおりの結果となること}
- **異常系**: {不正入力・エラー条件で期待どおりのエラーまたはフォールバックとなること}
- **境界値**: {境界付近の値（最小・最大・0・空など）で期待どおりとなること}
- **回帰**: {既存の振る舞いが変更で壊れていないこと（既存テストで担保）}
- **結合**: {他モジュール・サービスとの境界（モック/スタブで制御）で期待どおりとなること}

バリデーション系は上記に加え、すべてのバリデーションルール・境界値・エラーメッセージをテストする。

### 6.3 API ブラックボックステスト

- API エンドポイントごとに、正常・異常・境界を**ブラックボックス**でテストする（内部実装に依存しない入出力検証）。
- リクエスト・レスポンス・ステータスコード・エラーメッセージを仕様に照らして検証する。
- {対象 API 一覧または 5. API 設計との対応表}

### 6.4 E2E 網羅

- フロントエンドの主要ユーザーシナリオ（ログイン、主要画面遷移、クリティカル操作）を E2E でカバーする。
- {主要シナリオ一覧または 7. UI 設計との対応}

### 6.5 監査・レビューでの確認（証跡・チェックリスト）

| 確認観点 | 証跡 | チェックリスト例 |
|----------|------|------------------|
| カバレッジ100% or 理由記載 | カバレッジレポート、または 02/03 内の「未達理由」記載 | 全レベルでカバレッジが100%である、または理由が明記されているか |
| 単体の BDD 網羅 | 01 要件定義の Feature/Scenario、03 のタスク別テスト観点、テストコード内の Given/When/Then | 正常系・異常系・境界値・回帰・結合が BDD で記載され実装されているか |
| API ブラックボックス | API テスト一覧・実行結果 | 全 API がブラックボックステストでカバーされているか |
| E2E 網羅 | E2E シナリオ一覧・実行結果 | 主要フローが E2E でカバーされているか |
